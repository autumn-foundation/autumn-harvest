# Restate (restate.dev): Virtual Objects and server architecture, as prior art for owner-per-key with colocated embedded storage

Scope: Restate server 1.2 (Feb 2025) through 1.7.x (July–Sept 2026). Research date: 2026-10-19. Source tags: **[P]** marks a primary source (Restate docs, Restate blog, Restate source code, Restate GitHub issues and release notes). **[S]** marks a secondary source (aggregators and search summaries). Where a fact comes only from a search-engine summary of a primary page, it is tagged [S].

## 1. Virtual Objects: handlers, per-key queue, K/V state, storage, lock holding, deadlocks, Workflows

### Takeaway
A Virtual Object is a keyed entity with a single-writer guarantee. At most one exclusive (writing) handler runs per key, and later calls wait in a per-key inbox, executed serially in arrival order. Shared (read-only) handlers run concurrently. State is a K/V map that lives in the same Restate partition store as the invocation journal. State updates are journaled with the execution steps, so state and progress commit together. Request-response calls between exclusive handlers can deadlock (A→B→A, or A→B→C→A). Restate does not detect these deadlocks. An operator recovers by cancelling invocations by hand. A Restate Workflow is a specialised Virtual Object: its `run` handler executes exactly once per workflow ID, and shared handlers resolve durable promises and query state while `run` executes.

### Cited Findings
- Virtual Objects are "identified by a unique key". "At most one handler with write access can run at a time per object key". Shared handlers are read-only and run concurrently, and different keys run concurrently. The comparison table summarises this as "Single writer per key (+ concurrent readers)". State is "K/V state retained indefinitely and shared across requests", read and written with `ctx.get` / `ctx.set`. [P] — [Restate docs: Services concepts](https://docs.restate.dev/concepts/services)
- Exclusive is the default for Virtual Object handlers. The `exclusive` wrapper in the TS SDK exists only for symmetry. [S, summarising the TS SDK reference] — [restate-sdk handlers.object.exclusive](https://docs.restate.dev/tsdocs/functions/_restatedev_restate-sdk.handlers.object.exclusive)
- Ordering: "Calls to a Virtual Object execute in order of arrival, serially." For two sends from the same caller to the same key, "Call A is guaranteed to execute before B", "However, other invocations may interleave between A and B." [P] — [Restate docs: TS service communication](https://docs.restate.dev/develop/ts/service-communication)
- Deadlocks: "Request-response calls between exclusive handlers of Virtual Objects may lead to deadlocks." The docs list a cross deadlock (A calls B and B calls A, same keys) and a cycle deadlock (A→B→C→A). Recovery is to "use the UI or CLI to cancel" the deadlocked invocations. The Go and Python pages carry the same text. [P] — [TS service communication](https://docs.restate.dev/develop/ts/service-communication); [Python](https://docs.restate.dev/develop/python/service-communication); [Go](https://docs.restate.dev/develop/go/service-communication)
- The server stores state: "The Restate Server stores all state and execution history, delivering them with each request". "State updates are recorded alongside execution steps for consistency." [P] — [Restate docs: Key concepts](https://docs.restate.dev/foundations/key-concepts)
- "Object state and invocation journals live in the partition's processor state." Journal entries are committed to the log first. They are applied to the invocation's journal state when the processor reads them back. [P] — [Blog: Building a modern Durable Execution Engine from First Principles, 2025-02-20 (Ewen, Farghal, Rohrmann)](https://restate.dev/blog/the-anatomy-of-a-durable-execution-stack-from-first-principles/)
- Eager vs lazy state: v1.7 adds `eager-state-size-limit`, which caps the state sent in the StartMessage. "Remaining keys are fetched lazily" by the SDK. `0` disables eager state and replaces the deprecated `disable_eager_state`. [P] — [v1.7.0 release notes](https://github.com/restatedev/restate/blob/main/release-notes/v1.7.0.md)
- Introspection tables expose the per-key queue and lock directly: `sys_inbox` ("invocations queued per Virtual Object or Workflow key"), `sys_locks` ("locks held on Virtual Object keys"), and `state` ("per-key state of Virtual Objects and Workflows"). To find the invocation that blocks an object, query `sys_locks` for `lock_name = 'Service/key'`. [P] — [SQL introspection reference](https://docs.restate.dev/references/sql-introspection); [Operate: introspection](https://docs.restate.dev/operate/introspection)
- Workflows: "The `run` handler executes exactly once per workflow ID." Shared handlers run concurrently with `run` to resolve workflow promises, query state, or wait for workflow events. Example: `run` awaits a promise `email-link-clicked`, and a shared `click` handler resolves it. [P] — [Services concepts](https://docs.restate.dev/concepts/services)
- Durable promises of Workflows are exposed in `sys_promise`. [P] — [SQL introspection reference](https://docs.restate.dev/references/sql-introspection)
- Retention: v1.7 adds `default-` and `max-` settings for idempotency retention and workflow-completion retention. The defaults are 24h. "Journal retention is capped at the idempotency retention." Completed invocations leave `sys_invocation` after the retention time. [P] — [v1.7.0 release notes](https://github.com/restatedev/restate/blob/main/release-notes/v1.7.0.md); [Operate: introspection](https://docs.restate.dev/operate/introspection)
- v1.7 pausing with vqueues: pause is "persisted and applied by the partition processor, so it is deterministic". Suspended invocations can be paused, and resume replays the journal. Pausing a running invocation aborts the current attempt, so unjournaled work re-runs. [P] — [v1.7.0 release notes](https://github.com/restatedev/restate/blob/main/release-notes/v1.7.0.md)
- In the v1.7 scheduler, a `lock` is one of the resources that can block a vqueue head entry (`sys_scheduler`), and `sys_vqueues` carries a lock flag. [P] — [v1.7.0 release notes](https://github.com/restatedev/restate/blob/main/release-notes/v1.7.0.md)

### Inferences
- The Restate model maps almost one-to-one onto the Harvest "keyed entity" sugar: key = Virtual Object key (Harvest: workflow id), exclusive handler = signal handler, state = K/V in the same store as the journal. The structural difference is that Restate keeps state as a mutable K/V table in the partition store. The log stays the source of truth, and state is a materialised view of log commands. Harvest would keep state in history. The Restate analogue of "per-entity user SQLite committed atomically with history" is "state writes are journal entries applied in the same partition-store transaction as the journal", because a single processor applies both from one log record.
- The deadlock section implies that an exclusive handler keeps the key lock for its whole lifetime, including while it awaits a call response. Otherwise A→B→A could not deadlock. A Harvest design that holds an entity lock across awaits needs the same warning, or a detector. Restate ships neither a detector nor timeouts by default; it relies on manual cancel.
- The `sys_locks` + `sys_inbox` split shows the useful decomposition: lock holder and per-key FIFO are separate, queryable tables.

### Gaps
- No primary source found that states, in so many words, that the key lock is held while the handler is suspended or sleeping (`ctx.sleep`). The deadlock text implies it for awaits on calls. Confirm from SDK docs before relying on it.
- The exact storage key layout of state and journal in RocksDB (column families, key prefixes) was not retrieved.
- Whether shared handlers read a consistent snapshot relative to the running exclusive handler was not found.

## 2. Server architecture: partitions, processors, Bifrost, RocksDB store, snapshots, trimming, metadata store, cluster controller

### Takeaway
Restate is a log-first architecture. Each partition has its own segmented virtual log (Bifrost), written by one sequencer/leader and quorum-replicated to log servers. One partition-processor leader (plus optional follower processors) tails that log and materialises all invocation, journal, state, timer and inbox data into an embedded RocksDB "partition store". That store is a cache that "can always be rebuilt from the log". It is snapshotted to S3/GCS/Azure, and the log is trimmed behind the snapshot. Strong consensus (Raft) exists only in the metadata store, and the control plane needs only an atomic CAS. The data path uses leader epochs that the control plane hands out. Partition count is fixed at provisioning (default 24).

### Cited Findings
- Work is sharded by key: workflow IDs, virtual-object keys or idempotency keys hash to a partition. "The invocation ID encodes the partition." Each partition owns both orchestration and state for its keys, so hot-path steps, state updates and timers need no cross-partition coordination. [P] — [Architecture reference](https://docs.restate.dev/references/architecture)
- Each partition has one processor leader and optional followers. Only the leader invokes deployed services. Followers "keep up with the log without taking action" and can take over. The count is set by the "partition replication" option. [P] — [Architecture reference](https://docs.restate.dev/references/architecture)
- Partition replication adds failover speed, not durability: followers are hot standbys. The docs recommend partition replication ≤2 unless recovery-time requirements are strict. Log replication sets how many log servers store each segment, and "is the basis of durability", with quorum-acknowledged writes. `default-replication` sets both. [P] — [Clusters docs](https://docs.restate.dev/server/clusters.md)
- Bifrost: "A write is committed when a quorum of replicas acknowledges the append." The log is a segmented virtual log. "Reconfiguration seals the active segment and atomically publishes a new segment as the head." [P] — [Architecture reference](https://docs.restate.dev/references/architecture)
- Bifrost lineage: it combines Delos (Virtual Consensus) and LogDevice ideas. The virtual-log abstraction lets new log implementations plug in "without building new consensus machinery". Segments can change leader and replica set, and processors see one contiguous log. The quorum write takes a single network round trip. [P] — [Blog, 2025-02-20](https://restate.dev/blog/the-anatomy-of-a-durable-execution-stack-from-first-principles/)
- v1.4 (2025-07-03) made the **Replicated loglet the default**, with automatic migration even for single-node setups. The Local loglet stays available only by explicit configuration. v1.4 also removed the local metadata backend and made the replicated metadata server the default. [P] — [Restate 1.4 announcement](https://restate.dev/blog/announcing-restate-1.4)
- RocksDB partition store: processors keep "a full cache of partition state in an embedded RocksDB", which "can always be rebuilt from the log" and "is not a second source of truth". [P] — [Architecture reference](https://docs.restate.dev/references/architecture)
- Snapshots: processors "create periodic snapshots of their RocksDB partition store and upload them to S3". A new processor restores the latest snapshot and replays "only the log suffix since the snapshot's sequence number". Only the leader writes snapshots. [P] — [Architecture reference](https://docs.restate.dev/references/architecture); [Blog, 2025-02-20](https://restate.dev/blog/the-anatomy-of-a-durable-execution-stack-from-first-principles/)
- v1.2 (2025-02-18) described three storage tiers: log for primary durability, embedded RocksDB for invocations/state/timers, and object-store snapshots, "so nodes keep only a few minutes of data locally". [P] — [Restate 1.2 announcement](https://restate.dev/blog/announcing-restate-1.2)
- v1.6 snapshot changes: a time-based `snapshot-interval`, Azure Blob (`az://`) and GCS (`gs://`) next to S3, experimental retention `experimental-num-retained`, removal of `file://`. Partition-driven trimming became the default, with leaders trimming independently and no central hourly task. `worker.durability-mode` options are `balanced` (default with snapshots), `snapshot-only`, `snapshot-and-replica-set`, `replica-set-only` (default without snapshots) and `none`. Multi-node clusters need a snapshot destination to trim at all. [P] — [v1.6.0 release notes](https://github.com/restatedev/restate/blob/main/release-notes/v1.6.0.md)
- v1.7 snapshot changes: `num-retained` (default 1) replaces the experimental key. The V2 `latest.json` pointer is always written. Restate deletes snapshots that "can no longer bootstrap partition processors because the log was trimmed past them". Rollback below v1.6 is unsupported once V2 pointers exist. [P] — [v1.7.0 release notes](https://github.com/restatedev/restate/blob/main/release-notes/v1.7.0.md)
- Without a usable snapshot, a node can hit trim-gap errors and crash-loop. Shared filesystems are not supported as a snapshot store, and `file://` lacks conditional updates. [P] — [Clusters docs](https://docs.restate.dev/server/clusters.md)
- Metadata store: a "built-in Raft-based metadata store" on metadata-server-role nodes, "designed to support relatively low volumes of read and write operations". Tolerating n failures needs 2n+1 metadata servers. The jepsen repo also exercises object-store (S3/GCS/MinIO) and DynamoDB metadata backends. [P] — [Architecture reference](https://docs.restate.dev/references/architecture); [Clusters docs](https://docs.restate.dev/server/clusters.md); [restatedev/jepsen](https://github.com/restatedev/jepsen)
- The control plane "needs only an atomic compare-and-swap (CAS) operation". Raft implements it, and other CAS stores can be plugged in. One control plane coordinates both log and processor, so the processor leader can be colocated with the log leader. [P] — [Blog, 2025-02-20](https://restate.dev/blog/the-anatomy-of-a-durable-execution-stack-from-first-principles/)
- Cluster controller: it manages log nodes and processors and "initiates failover when health checks fail". "Strong consensus is limited to the metadata layer". The data path uses a leader/epoch configuration that the control plane revokes and reassigns. [P] — [Architecture reference](https://docs.restate.dev/references/architecture)
- v1.7: `restatectl partition leader` can pin a leader to a node (soft) or freeze elections (hard). The policy is stored in the metadata store. [P] — [v1.7.0 release notes](https://github.com/restatedev/restate/blob/main/release-notes/v1.7.0.md)
- Issue #3965 "Ensure Partition Processor Leader Is the Sole Log Writer (for vqueues support)" (opened 2025-11-07, closed 2026-01-08). v1.6 experimental Kafka batch ingestion made the processor "the sole writer to its logs". v1.7 made batch ingestion of Kafka and the partition shuffle the only implementation. [P] — [GitHub issue search result #3965](https://github.com/restatedev/restate/issues/3965); [v1.6.0 notes](https://github.com/restatedev/restate/blob/main/release-notes/v1.6.0.md); [v1.7.0 notes](https://github.com/restatedev/restate/blob/main/release-notes/v1.7.0.md)
- Sizing: tolerating `default-replication - 1` failures needs at least `2 * default-replication - 1` nodes. The docs advise against autoscalers. [P] — [Clusters docs](https://docs.restate.dev/server/clusters.md)

### Inferences
- Harvest option (2) is "Postgres append-only events as the durable log with a local SQLite cache on the owner". It is the same shape as Restate's "Bifrost is the source of truth, RocksDB is a rebuildable cache". Restate frames Bifrost as the transaction WAL and the processor as query engine plus table storage. The key Restate lesson is that the cache must be *deterministically derived from the log*, so any replica can rebuild it and snapshots are only a recovery accelerator.
- The Restate trimming design ties log GC to snapshot durability through explicit durability modes. A Harvest owner-local SQLite cache with Postgres as the log does not need this, because Postgres keeps the full history. A Harvest snapshot of the SQLite cache would still need an LSN or `event_id` watermark, so a new owner replays only the suffix.
- Restate deliberately avoided "just use Postgres". The blog gives three reasons: access patterns, open-source logs lagging proprietary ones, and developer experience. Harvest takes the opposite bet, so Restate's latency numbers are not a like-for-like baseline.

### Gaps
- Internal names such as "sequencer", "nodeset", "copyset", "log server" internals and flexible quorums were not covered in the fetched pages. The 2025-02-20 post says a follow-up covers flexible quorums, but it was not retrieved.
- The exact metadata store API surface was not retrieved.

## 3. Ownership and fencing: epochs, stale-leader fencing, failover time, rebalancing, partition count changes

### Takeaway
Restate fences at two levels. (a) **The log level:** reconfiguration seals the active segment, so "a quorum of replicas refuses further appends". A new segment with a new sequencer is then published by metadata CAS. (b) **The state-machine level:** a new processor leader takes the next epoch from a strictly monotonic control-plane sequence and appends an epoch-bump (`AnnounceLeader`) record. Every replica then drops self-proposed records stamped with a lower epoch, because the processor compares records against a persisted `(epoch, seq)` dedup watermark. Invocation attempts are fenced the same way. Restate publishes no absolute failover time. Partition count is fixed at provisioning (default 24); there is no online resharding.

### Cited Findings
- "Attempts carry increasing epochs, and the processor rejects any events from superseded epochs." Late appends from superseded leaders or stale handler attempts "are fenced at the epoch boundary and ignored". When a processor is promoted, it "obtains a new epoch" and appends an epoch-bump record. [P] — [Architecture reference](https://docs.restate.dev/references/architecture)
- New leaders take the next epoch "from a strictly monotonic sequence supplied by the control plane". The old leader steps down at the epoch-bump point in the log. It keeps materialising state as a follower, stops dispatching invocations and aborts ongoing function executions. Messages with epochs lower than the latest epoch-bump are ignored. "An in-flight commit appended after the bump cannot take effect." The processor tracks execution attempts per invocation and rejects events from older attempts. Simple in-memory state suffices for this "because invocations are sticky to partitions and partitions have strong leaders". [P] — [Blog, 2025-02-20](https://restate.dev/blog/the-anatomy-of-a-durable-execution-stack-from-first-principles/)
- Concretely, in `crates/worker/src/partition/processor/dedup.rs`, each record carries optional `DedupInformation { producer_id, sequence_number }`. For the self producer (the processor's own proposals) the sequence number must be an `EpochSequenceNumber { leader_epoch, sequence_number }`. A self-proposal is a duplicate iff `my_dedup_esn >= esn`, with the comment "The processor will reject self proposals < than this epoch". Other producers (for example, other partitions' shuffles) are checked as `last >= incoming` per `ProducerId`, with either ESN or a plain SN. Accepted values are written in the same storage transaction via `put_dedup_seq_number`. [P, source code] — [dedup.rs](https://raw.githubusercontent.com/restatedev/restate/main/crates/worker/src/partition/processor/dedup.rs)
- The ESN ordering compares epoch first, then sequence. `AnnounceLeader(eN+1)` records dedup state `(SELF, eN+1, 0)`. Any older-epoch self-proposal that lands after it in the log is dropped. [P] — [Issue #4566](https://github.com/restatedev/restate/issues/4566)
- Log failover: the controller seals the active segment, and "a quorum of replicas refuses further appends". It then finds the authoritative tail, elects a new sequencer and replica set, and publishes the new segment "via a metadata compare-and-swap". Processors and log servers "gossip their detection of peer failures". Ingress is "leader-aware", so clients need not reconnect. [P] — [Architecture reference](https://docs.restate.dev/references/architecture)
- Reconfiguring a log "seals its current segment and opens a new one, briefly pausing appends". [P] — [Clusters docs](https://docs.restate.dev/server/clusters.md)
- Failover speed: v1.4 (2025-07-03) brought gossip-based failure detection with "up to 10x faster detection of network partitions or node failures". It added explicit drain and warm-up phases on leadership change, automatic partition rebalancing across nodes, and startup "up to 2.5x faster compared to v1.3". **No absolute failover time is published.** The Jepsen-driven latency plot (3 nodes, one node partitioned at a time) says only that v1.4 latency was "significantly lower" than v1.3. [P] — [Restate 1.4 announcement](https://restate.dev/blog/announcing-restate-1.4)
- Issue #4937 (opened 2026-06-15, closed 2026-06-22): "Cluster Controller epoch metadata staleness can leave the partition leader-less for up to 30secs". This is a real-world bound on a failover gap before the fix. [P, title only] — [Issue #4937](https://github.com/restatedev/restate/issues/4937)
- Partition count: the default is 24 (`default-num-partitions` or `restatectl provision --num-partitions`). It is "fixed at provisioning". `restatectl config set` cannot change it, and there is no online resharding: you provision a new cluster and migrate. Each partition has one leader, so N partitions cap the leading nodes at N. [P] — [Clusters docs](https://docs.restate.dev/server/clusters.md); "the number of partitions is configured at cluster creation", design leaves room for future migration or key-range splits — [Architecture reference](https://docs.restate.dev/references/architecture)
- **Conflict:** the 2025-02-20 blog says partitions are hidden from applications, "This allows changing the partition count without losing consistency". This is a design intent, not a shipped feature. The current docs say the count is fixed. [P] — [Blog, 2025-02-20](https://restate.dev/blog/the-anatomy-of-a-durable-execution-stack-from-first-principles/) vs [Clusters docs](https://docs.restate.dev/server/clusters.md)
- Cluster features are fixed at provisioning. Only one node should auto-provision: "clusters that form in a split can't be merged". [P] — [Clusters docs](https://docs.restate.dev/server/clusters.md)

### Inferences
- "Processor rejects events from superseded epochs" means a **read-side filter in the deterministic state machine**, not a write-side lock. Every replica applies the same rule to the same log, so all replicas agree on which stale records are no-ops. For Harvest with Postgres as the log, the analogue is this: the owner stamps every appended event with `(owner_epoch, seq)`. The shard row in Postgres holds the current epoch. Either (a) the append is a conditional insert that checks the epoch in the same transaction (write-side fence, which Postgres makes cheap), or (b) the reader ignores rows whose epoch is below the last epoch-bump row (Restate-style read-side fence). Postgres gives (a) for free, and Restate needs (b) because Bifrost appends are not conditional on processor epoch.
- Issue #4566 is a direct warning for Harvest. A read-side epoch filter **silently drops** work that a stale leader accepted and acknowledged (HTTP 202) before the bump. Restate fixed it by acknowledging only after the state machine applied the command, so the client retries against the new leader. Any Harvest design that acks a signal before the fenced write is durable *and applied* has the same bug class.
- Restate's log-level seal (quorum refuses appends) is what makes the epoch filter safe against an arbitrarily delayed stale writer. With Postgres as the single log, the equivalent is that the fencing check and the insert share one transaction. A lease check outside the transaction does not fence.

### Gaps
- No published failover-time SLO (ms or s) was found.
- No details were found on how the cluster controller chooses the new processor leader, beyond colocating with the log leader.
- Issue #4937 was read by title only; the 30 s figure comes from the title.

## 4. Exactly-once cross-key / cross-partition messaging

### Takeaway
A call or one-way send to a key in another partition is first written as an outbox-style record to the *origin* partition's log, in the same append as the caller's journal step. An internal **shuffle** component then delivers it to the destination partition's log. The destination processor deduplicates by `(ProducerId, sequence number)` against a persisted per-producer watermark, which gives exactly-once application despite at-least-once shuffle delivery. Same-partition messages need no shuffle.

### Cited Findings
- Cross-partition events are recorded in the origin partition's log and "delivered exactly once to the destination partition via an internal shuffler", "addressed and deduplicated by sequence numbers". Duplicate client calls with the same idempotency key "resolve to the same invocation", which returns the committed result without re-running. [P] — [Architecture reference](https://docs.restate.dev/references/architecture)
- Events for another partition are "first written to the local partition", and an "out-of-band exactly-once event shuffler" moves them. [P] — [Blog, 2025-02-20](https://restate.dev/blog/the-anatomy-of-a-durable-execution-stack-from-first-principles/)
- Dedup mechanics: per-`ProducerId` stored `DedupSequenceNumber` (ESN or SN). A record is a duplicate iff `last >= incoming`. The watermark update happens inside the apply transaction. A `todo` notes that non-self producers have no in-memory cache yet. [P, source code] — [dedup.rs](https://raw.githubusercontent.com/restatedev/restate/main/crates/worker/src/partition/processor/dedup.rs)
- v1.6 introduced an experimental batched shuffle path, and v1.7 made it mandatory: "The legacy shuffle and Kafka consumer code is deleted." The experimental shuffle's `IngestRecords` path does not use ESNs for dedup. [P] — [v1.7.0 notes](https://github.com/restatedev/restate/blob/main/release-notes/v1.7.0.md); [Issue #4566](https://github.com/restatedev/restate/issues/4566)
- Within one handler execution, Restate deduplicates calls automatically. Across independent handlers, users pass an idempotency key. v1.7 with `controlled-idempotent-sharding` (default on new clusters) auto-generates idempotency keys for ingress calls to services and objects without one. [P] — [TS service communication](https://docs.restate.dev/develop/ts/service-communication); [v1.7.0 notes](https://github.com/restatedev/restate/blob/main/release-notes/v1.7.0.md)
- v1.7 bug fix: "Awakeable signals could be lost during leadership transitions. Ingress signals are now appended without dedup info." [P] — [v1.7.0 notes](https://github.com/restatedev/restate/blob/main/release-notes/v1.7.0.md)

### Inferences
- In Harvest terms this is a transactional outbox plus an idempotent inbox. The source shard writes `(target_key, producer=source_shard, seq)` in the same Postgres transaction as its own history event. A relay copies it to the target. The target keeps `max_seq_seen[producer]` and applies the message and the watermark in one transaction. If the target's history and the dedup table are in the same Postgres database, the relay can be a single cross-row transaction, which is simpler than Restate's shuffle. The shuffle pattern matters only if per-owner SQLite becomes the write-ahead store.
- The watermark is per producer and monotone, so the producer must emit strictly increasing sequence numbers per destination stream (or globally). Restate uses the producer's own epoch and sequence for this.

### Gaps
- Shuffle internals were not retrieved: the outbox table layout, the retry/ack protocol, and how the shuffle survives source-leader change.
- No source says whether producer IDs are per source partition or per (source, destination) pair.

## 5. Visibility / listing: SQL introspection

### Takeaway
Restate exposes all invocations, journals, inboxes, locks, state, promises and (v1.7) vqueue/scheduler data as SQL tables, through DataFusion. Queries go to `restate sql` or `POST :9070/query`, and leaf scans run directly against live RocksDB partition stores, routed leader-first. Restate documents no cross-partition consistency guarantee. Heavy queries hurt transaction processing: an August 2026 issue measured one periodic query using ~97% of a cell's read bandwidth, and the proposed fix is query-only follower replicas.

### Cited Findings
- Access: `restate sql --json "<query>"`, `restate sql describe <table>`, or HTTP `localhost:9070/query` with `{ "query": ... }`. The API "is built on DataFusion and supports standard SQL syntax". [P] — [Operate: introspection](https://docs.restate.dev/operate/introspection)
- Tables: `sys_invocation`, `sys_journal`, `sys_journal_events`, `sys_inbox`, `sys_locks`, `state`, `sys_promise`, `sys_deployment`, `sys_service`, plus the v1.7 tables `sys_vqueues`, `sys_vqueue_meta`, `sys_vqueue_entry_status`, `sys_scheduler`, `sys_rules`, `sys_user_limits`. Each row carries an internal `partition_key` column. The docs advise using `raw_length` / `key_length` / `value_length` instead of `length(raw)` for efficiency. [P] — [SQL introspection reference](https://docs.restate.dev/references/sql-introspection)
- v1.7 removed `sys_idempotency` and added `partition_state` columns: `enabled_features`, `applied_rule_book_version`, `applied_schema_version`. v1.6 made `sys_journal_events` populated by default. v1.6 also cut the query engine memory budget from 4 GiB to 1 GiB (`admin.query-engine.memory-size`). [P] — [v1.7.0 notes](https://github.com/restatedev/restate/blob/main/release-notes/v1.7.0.md); [v1.6.0 notes](https://github.com/restatedev/restate/blob/main/release-notes/v1.6.0.md)
- Issue #5170 (opened 2026-08-13, open): `POST /query` "runs leaf scans directly against live partition stores", "routed leader-first", on the nodes that also run invoker, timers, shuffle and Bifrost appends. Admission control is one token per statement at the initiator only. Serving nodes have none. Scans share the transactional storage thread pool, and each can hold a thread for the 60 s scanner TTL. There are no DataFusion metrics. One query pattern every ~19 s "used roughly 97% of one cell's read bandwidth and measurably affected invocation processing". The issue proposes query-only replicas (a `query-worker` role, never elected leader) and accepts that "reads would be best-effort stale". [P] — [Issue #5170](https://github.com/restatedev/restate/issues/5170)
- Related open issues: #5171 "Throttle DataFusion Partition-Store Scanners by Logical Bytes Read" (2026-08-13); #5070 (secondary indexes) and #1958 (pre-materialised aggregates) are referenced from #5170. [P, titles] — [Issue #5171](https://github.com/restatedev/restate/issues/5171); [Issue #5170](https://github.com/restatedev/restate/issues/5170)
- `restate invocations list` shows active invocations only unless `--all` is passed. `sys_invocation` reports retrying invocations as `ready`, so you query `sys_vqueues` for `backing-off`. [P] — [Operate: introspection](https://docs.restate.dev/operate/introspection)

### Inferences
- Restate's listing is a scatter-gather over per-partition stores with no global index (secondary indexes are an open issue). Each partition's answer reflects that replica's applied LSN, so there is no global snapshot. Harvest already has Postgres as the log, so listing can stay a Postgres query with real indexes. That is a structural advantage over the owner-local-cache design, *provided* listing reads Postgres and not the owners' SQLite caches.
- Operational lesson: introspection on the hot transactional store needs its own resource budget. Restate is retrofitting this in 2026.

### Gaps
- No primary statement was found on the consistency of a multi-partition query (for example, whether DataFusion pins each partition scan to a snapshot).

## 6. Determinism model: journal-based replay vs Temporal strict replay

### Takeaway
Restate is journal-based. Each side-effecting action (calls, `ctx.run` blocks, timers, state updates) is recorded with its result. On retry, the SDK replays the journal: completed steps return their recorded results and are not re-executed, and execution resumes from the first unjournaled step. Restate does not document Temporal-style strict command matching against history (non-determinism errors on a mismatched command stream) in the pages retrieved. Determinism is maintained mainly by routing non-determinism through journaled actions, with ordinary retries rather than workflow-task replay against a history.

### Cited Findings
- Restate records each side-effecting operation (service calls, database updates, timers) and its result in a journal. After a failure it replays the journal, skips completed steps and resumes "from exactly where it left off". [P] — [Key concepts](https://docs.restate.dev/foundations/key-concepts)
- Journal entries are committed to the log first, then applied to the invocation's journal state. "any step or activity result is committed exactly once", and "no split-brain view is possible". [P] — [Blog, 2025-02-20](https://restate.dev/blog/the-anatomy-of-a-durable-execution-stack-from-first-principles/)
- v1.7 `experimental_enable_unique_random_seeds` (opt-in, one-way) "fixes replay issues with `ctx.rand()` during restart-from-prefix". Invocations created before activation keep the old seed derivation. Protocol v7 lets errors request pause or immediate failure, and suspension records what the invocation waits on (`SuspendedEvent`). [P] — [v1.7.0 notes](https://github.com/restatedev/restate/blob/main/release-notes/v1.7.0.md)
- v1.6 added "restart from journal prefix" (`restart-as-new` with a `from` index). It copies entries 0..from to a new invocation ID, requires a completed original and Protocol V6 for `from > 0`, and is not available for Workflows. [P] — [v1.6.0 notes](https://github.com/restatedev/restate/blob/main/release-notes/v1.6.0.md)
- `sys_journal.entry_json` etc. are "Filled only if journal version is 2", so the journal format itself is versioned. [P] — [SQL introspection reference](https://docs.restate.dev/references/sql-introspection)

### Inferences
- The Restate journal is per invocation (per handler call), not per long-lived entity. A Virtual Object's history is its K/V state plus a series of short invocations, each with its own journal. In Harvest's keyed-entity-as-workflow design, one ever-growing history holds all signals. Restate's split (short per-call journals + materialised K/V state) avoids unbounded history replay for long-lived entities. That is the main design difference to weigh for the keyed-entity layer.
- The `ctx.rand()` seed fix shows that "restart from prefix" and journal-copy features create new determinism hazards. Any Harvest equivalent (reset or rewind) must re-derive seeds deterministically.

### Gaps
- No primary source was found on how a Restate SDK detects a journal mismatch on replay (for example, a different command type at the same index) or what error results. This needs SDK protocol docs (service-protocol spec).

## 7. Operational issues, testing, and performance numbers

### Takeaway
Restate has an official Jepsen suite (restatedev/jepsen) that checks set-append linearizability on the metadata store and on a Virtual Object, under kill/pause/partition nemeses. I found no public write-up of correctness bugs it found and no independent Jepsen (jepsen.io) analysis. Real 2026 bugs cluster around leadership transitions and log sealing: lost acknowledged signals (#4566), a stuck reader after a failed seal (#5033), and a leaderless window of up to 30 s (#4937). Published performance (v1.2, Feb 2025, 3-way replicated, c6id.8xlarge): p50 3 ms per single step at low load, ~94k actions/s, 8,571 nine-step workflows/s at p99 163 ms.

### Cited Findings
- restatedev/jepsen workloads: `set-mds` (embedded replicated metadata store), `set-mds-s3/gcs/minio/ddb` (alternative metadata backends), `set-vo` (a `Set` Virtual Object, so SDK services are included), and `set-vo-s3` (with S3 snapshots). Nemeses: `none`, `kill-random-node`, `pause-random-node` (SIGSTOP), `partition-random-node`. The checker is the Jepsen set-append checker, which "validate[s] linearizability". The README warns that a run can pass trivially if all nodes return service errors through misconfiguration. No findings are reported. [P] — [restatedev/jepsen](https://github.com/restatedev/jepsen)
- No independent jepsen.io analysis of Restate was found. [S, negative search result] — [jepsen.io analyses](https://jepsen.io/analyses)
- Issue #4566 (2026-04-07 → closed 2026-04-14, milestone 1.7): awakeable resolve/reject signals that ingress accepted with **HTTP 202** could be "silently lost during partition leadership transitions", leaving invocations suspended forever. The cause was epoch-first ESN dedup dropping an old-epoch self-proposal committed after `AnnounceLeader`. Also affected: `append_invocation_response` and `restart_as_new_invocation`. Fix PR #4582 responds only after the state machine applies the command. [P] — [Issue #4566](https://github.com/restatedev/restate/issues/4566)
- Issue #5033 (opened 2026-07-13, open as of the fetch, fix PR #5054 pending): after a failed chain seal during node restarts, partition leaders still report Active and accept appends (tail LSN grows), but applied LSN freezes at a segment boundary. Invocations hang, and they "never appeared in the invocation tables". It was reported on 1.6.2 (3 nodes, 128 partitions, RF 2) and again on 1.7.2 after ~11 days of uptime with no restarts. The workaround is to restart the node or pin leadership elsewhere. [P] — [Issue #5033](https://github.com/restatedev/restate/issues/5033)
- Issue #4937 (2026-06-15 → 2026-06-22): controller epoch metadata staleness could leave a partition leader-less for up to 30 s. [P, title] — [Issue #4937](https://github.com/restatedev/restate/issues/4937)
- Other 2026 issues (titles): #4534 snapshot restore could crash the processor because of existing column families (closed 2026-04-02). #5142 "Ensure that no snapshot tasks are running when starting a partition processor" (open, 2026-08-06). #5061 "Partition processor effect flow control" (open, 2026-07-20). #3930 "Allow to resume partition processor not only from the latest snapshot" (open since 2025-10-27). [P, titles] — [GitHub issues search: restatedev/restate](https://github.com/restatedev/restate/issues)
- v1.6 fixed a log-stall hazard: journal entries over 32 MiB previously made the SequencerAppender retry "indefinitely and could stall the log". Now they fail with RT0003. [P] — [v1.6.0 notes](https://github.com/restatedev/restate/blob/main/release-notes/v1.6.0.md)
- Documented data-loss conditions: losing all nodes that hosted a partition means "permanent data loss". Reusing a node ID can put a log server into `data-loss`. Misusing `set-storage-state` can cause unavailability or data loss. Changing `node-name` while it is in use risks data loss. [P] — [Clusters docs](https://docs.restate.dev/server/clusters.md)
- Performance (v1.2, 3-node 3-way replicated cluster, mock handlers). Low load (10 clients), p50/p90/p99: 0 steps 5/34/54 ms, 3 steps 15/42/69 ms, 9 steps 31/57/93 ms, 27 steps 61/106/155 ms. High load (1,200 clients): 0 steps 28/41/58 ms, 9 steps 116/138/163 ms, 27 steps 283/320/356 ms. Single-step median 3 ms at low load. Throughput 94,286 actions/s = 8,571 nine-step workflows/s on c6id.8xlarge. The authors say they "have not optimized performance deeply". [P] — [Blog, 2025-02-20](https://restate.dev/blog/the-anatomy-of-a-durable-execution-stack-from-first-principles/)
- The v1.2 announcement gives the high-load rps per workflow shape: 1-step 23,131 rps (p99 40 ms), 3-step 16,844 rps (p99 98 ms), 9-step 8,571 rps (p99 163 ms). It also quotes a peak of "about 17,000 rps (84,000 actions/s) with p90 of 76 ms". The 84k (v1.2 post) and 94k (anatomy post) actions/s figures refer to different workflow shapes. [P] — [Restate 1.2 announcement](https://restate.dev/blog/announcing-restate-1.2)

### Inferences
- Every serious 2026 bug sits at the seam between ownership change and the log: epoch bump vs in-flight self-proposals, and seal vs reader. A Harvest shard-lease-plus-epoch design should budget its testing for exactly that seam. Useful tests: stale owner acks then loses lease, lease flaps during an append, and a new owner reading a suffix that a stale owner is still writing.
- No published number is per partition. The throughput figures are cluster-wide, and the partition count for the benchmark was not stated.

### Gaps
- No per-partition throughput figure.
- No benchmark newer than v1.2 (Feb 2025) was found.
- No public post-mortem of a production data-loss incident was found.

## 8. Restate 1.4–1.7 changes relevant to the above (timeline)

### Takeaway
1.2 (2025-02-18) made Restate distributed. 1.4 (2025-07-03) made the replicated loglet and replicated metadata server the defaults and added gossip failure detection and auto-rebalancing. 1.6 (Feb 2026) made partition-driven trimming the default, added multi-cloud snapshots, durability modes and invocation pause/restart. 1.7 (July 2026) added vqueues, a per-partition scheduler and concurrency limits (experimental, fresh clusters only), made the batched shuffle mandatory, and added leader pinning.

### Cited Findings
- 1.2, 2025-02-18: distributed, highly available clusters. Segmented replicated log ("Virtual Consensus and LogDevice"). Strong consensus only in the control plane. `restatectl`. [P] — [Restate 1.2 announcement](https://restate.dev/blog/announcing-restate-1.2)
- 1.4, 2025-07-03: replicated loglet default, replicated metadata default, gossip failure detection ("up to 10x faster"), drain/warm-up on leadership change, automatic partition rebalancing, new network fabric, Zstd. [P] — [Restate 1.4 announcement](https://restate.dev/blog/announcing-restate-1.4)
- 1.5: not researched (no source retrieved).
- 1.6 (blog dated February 2026 per search summary [S]): manual pause/resume, restart from journal prefix, batch operations, multi-cloud snapshots, snapshot retention, partition-driven trimming, `durability-mode`, an automatic RocksDB memory manager (rebalanced every 5 s), a 32 MiB journal entry limit, and deprecated SDKs rejected (RT0020). Invocations pause on max attempts (default 70) instead of being killed. [P] — [v1.6.0 notes](https://github.com/restatedev/restate/blob/main/release-notes/v1.6.0.md); date [S] — [Restate 1.6 blog](https://restate.dev/blog/announcing-restate-1-6)
- 1.7 (blog dated 2026-07-07 per search summary [S]; patch releases up to v1.7.10 by mid-September 2026 [S]): **vqueues** (`experimental_enable_vqueues`). "Enabling vqueues on a cluster with in-flight invocations will stop the cluster from booting." The first flow-control primitive is per-scope concurrency limits (`restate rules`, `/restate/scope/{scopeKey}/call|send`). The per-partition scheduler "provid[es] fairness". 1.7 also brings deterministic persisted pause, mandatory batched shuffle, adaptive Bifrost store timeouts (P99.99 tracking), leader pinning/freeze, `eager-state-size-limit`, auto idempotency keys, protocol v7 (one-way), and an ingress 32 MiB/413 limit. [P] — [v1.7.0 notes](https://github.com/restatedev/restate/blob/main/release-notes/v1.7.0.md); dates [S] — [Restate GitHub releases](https://github.com/restatedev/restate/releases)

### Inferences
- The vqueue rework shows that the per-key FIFO inbox plus a global invoker concurrency cap was not enough for fairness and flow control. Restate is moving queueing *into* the partition state machine (deterministic scheduler, persisted pause). For Harvest's keyed entities, put per-key queue, fairness and limits into replicated, deterministic state from the start, rather than in an in-memory dispatcher.
- Several features are one-way or fixed at provisioning: protocol v7, unique random seeds, V2 snapshot pointers, cluster features, partition count. Restate pays for evolvability with irreversible migrations, which is a cost to plan for in Harvest's own format changes.

### Gaps
- Restate 1.5 contents and date were not retrieved.
- The exact 1.6 and 1.7 release dates come from search summaries [S], not the posts themselves.
- Restate 1.8 status (if released by October 2026) is unknown. The 1.7 notes mention removals planned "in v1.8".
