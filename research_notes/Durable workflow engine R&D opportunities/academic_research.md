# Academic and Industrial Research on Durable Execution, Stateful Serverless, and Workflow Orchestration (2018–2026)

Scope note: this file covers published and preprint research only. It does not look at the autumn-harvest codebase. "Implemented" means the paper built and evaluated a system. "Proposed" means a vision, sketch, or design without a full evaluation. arXiv IDs that start with 26xx are 2026 preprints. Most of them are not peer-reviewed. Several have a single author. Treat them as signals of direction, not as settled results.

## 1. Core durable-execution / stateful-serverless papers (annotated bibliography)

### Takeaway
The field has three lineages. (a) Log-based exactly-once execution over cloud storage: Olive, Beldi, Boki, Halfmoon. (b) Replay-based workflow runtimes with formal semantics: Durable Functions, Netherite, ExoFlow, DBOS. (c) Transactional stateful dataflows and actors: Styx, StateFun transactions, Orleans/Snapper. From 2023 to 2026 the research moved toward database-backed workflows with ACID-like semantics (DBOS, AC/DC). It also moved toward speculation that hides persistence latency (DARQ, DSE, Netherite). Agent-oriented durability is the newest strand (LogAct).

### Cited Findings

**Replay-based workflow runtimes**
- *Durable Functions: Semantics for Stateful Serverless*. Burckhardt, Gillum, Justo, Kallas, McMahon, Meiklejohn. OOPSLA 2021. Implemented (Azure Durable Functions) and formalized. The paper defines DF with an idealized model based on untyped lambda calculus. It proves that the distributed, unreliable runtime matches that model by proving equivalence between progressively more complex execution models. The programming model adds actors (entities), workflows (orchestrations) and critical sections to FaaS. — [MSR page](https://microsoft.com/en-us/research/?p=782968); [PDF with proofs](https://microsoft.com/en-us/research/uploads/prod/2021/10/DF-Semantics-With-Proofs.pdf); [SPLASH listing](https://2021.splashcon.org/details/splash-2021-oopsla/37/Durable-Functions-Semantics-for-Stateful-Serverless)
- *Netherite: Efficient Execution of Serverless Workflows*. Burckhardt et al. PVLDB 15 (VLDB 2022); arXiv version Feb 2021 titled "Serverless Workflows with Durable Functions and Netherite". Implemented and evaluated. Workflows are task-parallel code in a host language, translated to stateful communicating processes. Techniques: partitioning and load balancing over elastic clusters, recovery logs plus asynchronous snapshots, and "speculative communication". Claim: lower latency and higher throughput than prevailing serverless workflow approaches on Azure and AWS, "by orders of magnitude in some cases". An extended journal version exists. — [PVLDB PDF](https://www.vldb.org/pvldb/vol15/p1591-burckhardt.pdf); [MSR page](https://www.microsoft.com/en-us/research/publication/serverless-workflows-with-durable-functions-and-netherite/); [extended journal version](https://www.microsoft.com/en-us/research/publication/netherite-efficient-execution-of-serverless-workflows-extended-journal-version/)
- *ExoFlow: A Universal Workflow System for Exactly-Once DAGs*. Zhuang, Wang, Liang, Cheng, Stoica (UC Berkeley / Anyscale). OSDI 2023. Implemented on Ray. ExoFlow decouples execution from recovery and provides exactly-once semantics as a separate layer. This lets one application mix different recovery-versus-performance tradeoffs. Tasks can return references that capture arbitrary inter-task communication. Task annotations declare execution semantics such as nondeterminism. It covers ETL pipelines through stateful serverless workflows. — [USENIX](https://usenix.org/conference/osdi23/presentation/zhuang); [Berkeley thesis "Providing Efficient Fault Tolerance in Distributed Systems"](https://www2.eecs.berkeley.edu/Pubs/TechRpts/2024/EECS-2024-86.html)
- *Doing More with Less: Orchestrating Serverless Applications without an Orchestrator* (Unum). Liu et al. (Princeton). NSDI 2023. Implemented. An intermediate representation partitions the application definition at compile time. Orchestration runs as a library in-situ with each FaaS function and coordinates through strongly consistent data stores, with no central orchestrator. Claim vs. AWS Step Functions on representative apps: about 2x faster and about 9x cheaper. — [USENIX](https://www.usenix.org/conference/nsdi23/presentation/liu-david); [PDF](https://www.usenix.org/system/files/nsdi23-liu-david.pdf)

**Log-based exactly-once over cloud storage**
- *Realizing the Fault-Tolerance Promise of Cloud Storage Using Locks with Intent* (Olive). Setty et al. OSDI 2016. Implemented. A client library that gives exactly-once semantics to a code snippet despite failures and concurrent duplicate executions. It needs few assumptions about storage and runs on DynamoDB and Azure Storage. It is used to build snapshots, OCC transactions, secondary indices and live re-partitioning. — [USENIX](https://www.usenix.org/conference/osdi16/technical-sessions/presentation/setty); [PDF](https://web.eecs.umich.edu/~manosk/assets/papers/lockswithintent.pdf)
- *Fault-tolerant and Transactional Stateful Serverless Workflows* (Beldi). Zhang, Cardoza, Chen, Angel, Liu. OSDI 2020. Implemented on AWS Lambda. It extends Olive's log-based fault tolerance with new data structures and protocols, adds transactions across functions, and supports a federated model in which each function owns its data. It adds new garbage collection. Evaluated on 1,000 Lambda instances with three apps (movie review, travel reservation, social media). — [USENIX](https://www.usenix.org/conference/osdi20/presentation/zhang-haoran)
- *Boki: Stateful Serverless Computing with Shared Logs*. Jia, Witchel (UT Austin). SOSP 2021. Implemented. Boki exports a shared-log API to functions. Its "metalog" separates ordering, consistency and fault tolerance. Support libraries implement fault-tolerant workflows, durable object storage and message queues. Claim: up to 4.7x speedup on important serverless workloads. — [GitHub](https://github.com/ut-osa/boki); [MIT 6.824 lecture notes](https://pdos.csail.mit.edu/6.824/notes/l-boki.txt)
- *Halfmoon: Log-Optimal Fault-Tolerant Stateful Serverless Computing*. Qi, Liu, Jin. SOSP 2023. Implemented on Boki. Key insight: logging both reads and writes is unnecessary. Logging only one side (asymmetric logging) is enough. Two protocols give exactly-once semantics with log-free reads (for read-heavy work) or log-free writes (for write-heavy work). They are proven log-optimal: no protocol can log less. Claim vs. Boki: 20–40% lower latency and 1.5–4.0x lower logging overhead. — [DOI](https://doi.org/10.1145/3600006.3613154)
- *A Fault-Tolerance Shim for Serverless Computing* (AFT). Sreekanti et al. EuroSys 2020. Implemented. AFT sits between the FaaS platform and storage. It buffers a request's writes and commits them atomically at request end, which gives read-atomic isolation (no partial side effects visible). — [arXiv](https://arxiv.org/pdf/2003.06007); [Berkeley thesis "The Design of Stateful Serverless Infrastructure"](https://www2.eecs.berkeley.edu/Pubs/TechRpts/2020/EECS-2020-140.html)

**Database-oriented durable execution (DBOS lineage)**
- *DBOS: A DBMS-oriented Operating System*. Skiadopoulos et al. PVLDB 15(1), 2022. Proposal with prototype. All OS and application state lives in a DBMS. — [PVLDB PDF](https://vldb.org/pvldb/vol15/p21-skiadopoulos.pdf); [ACM DL](https://dl.acm.org/doi/10.14778/3485450.3485454)
- *A Progress Report on DBOS*. CIDR 2022. — [PDF](https://people.eecs.berkeley.edu/~matei/papers/2022/cidr_dbos.pdf)
- *DBOS: three years later*. VLDB Journal 34(3). Retrospective. — [Springer](https://link.springer.com/article/10.1007/s00778-024-00899-0)
- *Apiary: A DBMS-Integrated Transactional Function-as-a-Service Framework*. Kraft, Li, Kaffes, Skiadopoulos et al. arXiv 2208.13068 (2022/2023). Implemented. This is the academic DBOS prototype (Java). — cited in [CIDR 2026 Stonebraker et al.](https://www.vldb.org/cidrdb/papers/2026/p9-stonebraker.pdf), reference [5]
- *R3: Record-Replay-Retroaction for Database-Backed Applications*. Li, Kraft, Cafarella, Demiralp, Graefe, Kozyrakis, Stonebraker, Suresh, Yu, Zaharia. PVLDB 16(11), 2023, pp. 3085–3097. Implemented. Record-replay plus "retroaction" (re-running past requests against modified code). — cited in [CIDR 2026 Stonebraker et al.](https://www.vldb.org/cidrdb/papers/2026/p9-stonebraker.pdf), references [6] and [7]
- *Consistency and Correctness in Data-Oriented Workflow Systems*. Stonebraker, Zhou (MIT), Kraft, Li (DBOS Inc.). CIDR 2026. Position paper plus prototype and small evaluation. It argues that durable execution is necessary but not sufficient. ACID should extend to whole workflows as "AC/DC" (atomic, consistent, durable, correct). Isolation is dropped on purpose, because long-term locks are too costly. The prototype is in dbos-transact-py. It supports per-step physical backout (one Postgres transaction over the whole workflow, with a savepoint per step) and saga compensation. Consistency guarantees are "not-yet-implemented". The authors claim durability automates "typically 10%" of an application and AC/DC is needed for "the other 90%". This is an opinion, not a measurement. — [PDF](https://www.vldb.org/cidrdb/papers/2026/p9-stonebraker.pdf)

**Transactional stateful functions / dataflows (Delft lineage)**
- *Styx: Transactional Stateful Functions on Streaming Dataflows*. Psarakis et al. (TU Delft / Inria). SIGMOD 2025. Implemented. A dataflow SFaaS runtime that runs serializable transactions over arbitrary call graphs of stateful functions with exactly-once guarantees. It extends a deterministic transaction protocol with (i) function acknowledgments to find transaction boundaries, (ii) function-execution caching, and (iii) early-commit replies. Claim: at least 10x higher throughput than prior work on YCSB, TPC-C and DeathStar, with near-linear scaling. — [arXiv 2312.06893](https://arxiv.org/html/2312.06893v4); [TU Delft](https://research.tudelft.nl/en/publications/styx-transactional-stateful-functions-on-streaming-dataflows/)
- *Transactions across serverless functions leveraging stateful dataflows*. de Heus, Psarakis, Fragkoulis, Katsifodimos. Information Systems 2022 (earlier DEBS 2021 paper "Distributed Transactions on Serverless Stateful Functions"). Implemented on Flink StateFun. Supports 2PC serializable transactions and Sagas. Overhead about 10% over StateFun. Sagas reach up to 34% more transactions per second than 2PC at under 200 ms latency. — [ScienceDirect](https://www.sciencedirect.com/science/article/pii/S0306437922000229); [DEBS 2021](https://dl.acm.org/doi/pdf/10.1145/3465480.3466920)

**Actors and virtual actors**
- Orleans actor-oriented database transactions (Bernstein et al., MSR). — [MSR project publications](https://www.microsoft.com/en-us/research/project/actor-oriented-databases/publications/?lang=ko-kr)
- Snapper (Liu et al., SIGMOD 2022), "hybrid deterministic and nondeterministic execution of transactions in actor systems". A transaction library on Orleans that uses deterministic execution to speed up multi-actor transactions. — [DOI via unpaywall](https://unpaywall.org/10.1145%2F3514221.3526172)

**Composable resilient steps and speculation (MIT/MSR lineage)**
- *DARQ Matter Binds Everything: Performant and Composable Cloud Programming via Resilient Steps*. Li, Chandramouli, Burckhardt, Madden. PACMMOD / SIGMOD 2023. Implemented. It proposes Composable Resilient Steps (CReSt): receive, process and send as one atomic unit. DARQ (Deduplicated Asynchronously Recoverable Queues) stores participant state. Services built on it are "resilient by construction" and compose without loss of resilience. A speculative scheme runs steps without waiting for message persistence. — [MIT DSpace](https://dspace.mit.edu/entities/publication/1b1cff53-08aa-44ee-b9ca-dc0e3cd1aae9)
- *Serverless State Management Systems* (SSMS). Li, Chandramouli, Burckhardt, Madden. CIDR 2024. Vision paper with a small preliminary evaluation. An SSMS is analogous to a DBMS. It has a logical application model (like relational algebra), resilient primitives (like ACID, based on CReSt), and cost-based optimization of placement and scheduling (like a query optimizer). It names Temporal and ExoFlow as tools users need today because the cloud lacks cross-service guarantees. — [PDF](https://www.vldb.org/cidrdb/papers/2024/p16-li.pdf)
- *Distributed Speculative Execution for Resilient Cloud Applications* (libDSE). Li, Chandramouli, Bernstein, Madden. arXiv 2412.13314, Dec 2024. Implemented. Developers write code as if persistence were synchronous. The runtime skips synchronous persistence and repairs state after a failure. Programming model: message passing, atomic code blocks, lightweight threads. Claim: up to 10x lower end-to-end latency than current durable execution systems (Temporal and Azure Durable Functions are named as baselines) with small runtime overhead. — [arXiv](https://arxiv.org/abs/2412.13314)

**Hydro / CALM lineage (coordination avoidance)**
- *Keep CALM and CRDT On*. Laddad, Power, Milano, Cheung, Crooks, Hellerstein. PVLDB 16(4), 2022/2023. Mostly an agenda paper. It extends CRDTs with a query model that uses CALM monotonicity to decide which queries are safe without coordination. — [Princeton page](https://www.cs.princeton.edu/~mpmilano/publication/keep-calm-and-crdt-on); [arXiv 2210.12605](https://arxiv.org/abs/2210.12605v1); [PVLDB PDF](https://www.vldb.org/pvldb/vol16/p856-power.pdf)
- Hydroflow / DFIR. Berkeley tech report 2021 and an OOPSLA 2023 paper "Hydroflow: A Compiler Target for Fast, Correct Distributed Programs". A Rust dataflow runtime with a lattice-based IR. It supports provably monotonic programs and automatic partitioning and replication rewrites. DFIR is the current name and ships as a Rust crate (0.12.0, March 2025). — [Tech report](https://www2.eecs.berkeley.edu/Pubs/TechRpts/2021/EECS-2021-201.html); [SPLASH 2023](https://2023.splashcon.org/details/splash-2023-oopsla/112/Hydroflow-A-Compiler-Target-for-Fast-Correct-Distributed-Programs); [lib.rs dfir_rs](https://lib.rs/crates/dfir_rs)

**Adjacent serverless work**
- *Process-as-a-Service: Unifying Elastic and Stateful Clouds with Serverless Processes*. Copik et al. (ETH). SoCC 2024. Implemented (AWS Fargate, Knative). It combines ephemeral functions with transient state and an MPI-style point-to-point data plane. State access takes ns–µs. — [PDF](https://www.dpss.inesc-id.pt/~rbruno/papers/mcopik-socc24.pdf)
- SeBS-Flow (EuroSys 2025) benchmarks serverless workflow managers such as AWS Step Functions and Azure Durable Functions to find throughput bottlenecks. — [EuroSys 2025 summaries](https://eunomia.dev/blog/2025/04/25/eurosys-2025-paper-summaries-and-analysis/)

### Inferences
- Temporal, Restate and DBOS appear in these papers mainly as baselines or as the "status quo" (DSE, SSMS, LogAct, CIDR 2026). The research community treats replay-based durable execution as solved in function and open in *performance* and *semantics* (isolation, compensation correctness, composition).
- The MSR/MIT group (Burckhardt, Chandramouli, Bernstein, Madden, Li) has a three-paper arc: DARQ (2023), then SSMS (2024), then DSE (2024). It points at one engine direction: speculative persistence plus composable atomic steps. No mainstream engine has adopted it as a user-facing guarantee.

### Gaps
- I found no paper titled "Flux" about exactly-once serverless transactions. The name may be wrong, or it may be one of Beldi, AFT or Halfmoon.
- I found no peer-reviewed academic study of Temporal or Cadence (bug study, formal model, or performance characterization). Temporal appears only as a baseline or a citation.
- Ray (OSDI 2018), Ownership (NSDI 2021) and Exoshuffle (SIGCOMM 2023) lineage-based fault tolerance were not re-verified this session. ExoFlow is the verified workflow-level paper from that group.
- Cloudburst (VLDB 2020) and Flink StateFun's own design paper were not re-verified this session.
- Epoxy ("ACID Transactions Across Diverse Data Stores", Kraft et al., PVLDB 2023) is relevant to cross-store transactions. Its URL was not verified this session.
- Durable Objects (Cloudflare) has no peer-reviewed research paper that I found.

## 2. Exactly-once / transactional guarantees across steps and external side effects

### Takeaway
The proposals fall on a spectrum. (1) Per-step exactly-once through logging and idempotency keys: Olive, Beldi, Boki, Halfmoon, DBOS. (2) Atomic multi-write steps: AFT read-atomic, DARQ CReSt. (3) Full serializable transactions over function graphs, mostly by deterministic (Calvin-style) execution: Styx, Snapper, StateFun 2PC. (4) Workflow-level atomicity through physical backout or compensation: CIDR 2026 AC/DC. External, non-transactional side effects stay the unsolved edge in every paper. The best available answer is still "assume idempotency or ask a human".

### Cited Findings
- Sagas (Garcia-Molina and Salem, SIGMOD 1987) remain the baseline for long-running transactions. — [DOI](https://doi.org/10.1145/38713.38742) (cited in [CIDR 2026](https://www.vldb.org/cidrdb/papers/2026/p9-stonebraker.pdf))
- CIDR 2026 defines a correct concurrent backout outcome. It equals (1) restoring all persistent state to its value when the errant workflow started, then (2) re-running the other concurrent workflows that finished since then. It notes that compensation alone does not guarantee a correct outcome, because of phantoms and cascading backouts. One exception: workflows made only of increments and decrements under non-negativity constraints "can always be backed out" with no cascade. — [CIDR 2026](https://www.vldb.org/cidrdb/papers/2026/p9-stonebraker.pdf)
- CIDR 2026 gives a protocol for external services that are not idempotent. Read prior values "for update", send the request, log prior and post values. On a missing reply, query again and compare. If the result matches neither, the platform "has no idea" and needs a human. The authors do not expect external services to support XA "anytime soon" because of lock-holding costs. — [CIDR 2026](https://www.vldb.org/cidrdb/papers/2026/p9-stonebraker.pdf)
- CIDR 2026 design rules: put an irreversible step last; split a workflow at a human or user stall (one becomes three, detectable at compile time); "returns" becomes a separate workflow; merge two conflict-prone steps into one step. — [CIDR 2026](https://www.vldb.org/cidrdb/papers/2026/p9-stonebraker.pdf)
- CIDR 2026 measured physical backout against sagas on an e-commerce benchmark. Physical backout is up to 1.8x faster under low contention (one commit vs. four). Under hot items or long steps, abort rates reach up to 48.8%. With long-running steps: saga goodput 15.9 vs. physical backout 2.0, and P90 latency 1,100 ms vs. 24,554 ms. — [CIDR 2026](https://www.vldb.org/cidrdb/papers/2026/p9-stonebraker.pdf)
- DBOS keeps workflow status and an operation log (step inputs, outputs, timestamps) in the same Postgres database as application data. A transactional step and its log entry commit together, which "eliminates the need for complex two-phase commit protocols between workflow and application logging". Multiple instances share the database, so failover needs no consensus protocol. — [CIDR 2026](https://www.vldb.org/cidrdb/papers/2026/p9-stonebraker.pdf)
- Olive's "locks with intent" give exactly-once execution for a code snippet despite concurrent duplicate executions. Beldi extends this to transactional workflows over serverless functions. — [Olive](https://www.usenix.org/conference/osdi16/technical-sessions/presentation/setty); [Beldi](https://www.usenix.org/conference/osdi20/presentation/zhang-haoran)
- AFT buffers writes and commits them atomically at request end, so readers never see partial side effects (read-atomic isolation). — [AFT](https://arxiv.org/pdf/2003.06007)
- Styx gets serializable, exactly-once transactions over arbitrary function call graphs by extending a deterministic transaction protocol. — [Styx](https://arxiv.org/html/2312.06893v4)
- StateFun transactions: 2PC adds about 10% overhead; Sagas give up to 34% more TPS than 2PC. — [Information Systems 2022](https://www.sciencedirect.com/science/article/pii/S0306437922000229)
- Snapper uses deterministic execution for multi-actor transactions on Orleans. — [SIGMOD 2022](https://unpaywall.org/10.1145%2F3514221.3526172)
- DARQ's CReSt makes receive, process and send one atomic unit, so composed services keep their resilience. — [DARQ](https://dspace.mit.edu/entities/publication/1b1cff53-08aa-44ee-b9ca-dc0e3cd1aae9)
- Agent-specific side effects: "Beyond Single-Use Tokens" (arXiv 2608.01710, 2026) finds that replanning, retry, delegation and crash-resume can cause one user authorization to run several times under freshly issued token IDs. It proposes durable authorization state. — [arXiv](https://arxiv.org/abs/2608.01710v1)

### Inferences
- Production engines (Temporal, Restate, DBOS Transact) give at-least-once activities plus a recorded result, and leave compensation to the user. Research prototypes go further on three axes that no mainstream engine exposes as a first-class guarantee: (a) workflow-level physical backout through a database transaction or savepoints; (b) serializable multi-entity transactions by deterministic execution (Styx); (c) a formal model of saga isolation (CIDR 2026 names this as future work).
- "Escrow for commutative operations" and hybrid backout (physical when conflicts are rare, compensation when common) are named but not built. They are clear R&D candidates for an engine that co-locates workflow state with application data in Postgres.
- Idempotent replay of authorization and credentials is a new kind of side effect that engines do not model. The 2026 token-replay paper suggests that "exactly-once" must cover authority, not only data writes.

### Gaps
- I did not verify Calvin (SIGMOD 2012) or Aria in this session, although Styx and Snapper build on that deterministic-database idea.
- No paper I found gives a general solution for exactly-once effects on arbitrary third-party APIs without idempotency keys.

## 3. Reducing replay cost: logging, checkpointing, speculation, shared logs

### Takeaway
There are four families. (1) Minimal logging: Halfmoon proves asymmetric logging is optimal. (2) Speculation that overlaps persistence with computation: Netherite's speculative communication, DARQ, libDSE, SpecLog. (3) Shared-log substrates that trade ordering latency for throughput: Boki's metalog, LazyLog, SpecLog. (4) Snapshots plus log truncation: Netherite's asynchronous snapshots. Speculative persistence shows the largest reported gains (up to 10x latency). It is not exposed by any mainstream durable-execution engine as far as these papers say.

### Cited Findings
- Halfmoon: logging either reads or writes (not both) is enough for exactly-once. It gives 20–40% lower latency and 1.5–4.0x lower logging overhead than Boki. Its protocols are proven log-optimal. — [Halfmoon](https://doi.org/10.1145/3600006.3613154)
- Netherite combines recovery logs, asynchronous snapshots and speculative communication. Claim: orders-of-magnitude gains in some cases over prevailing Azure and AWS workflow approaches. — [Netherite](https://www.microsoft.com/en-us/research/publication/serverless-workflows-with-durable-functions-and-netherite/)
- libDSE states the problem directly: durable execution "forces frequent and synchronous persistence and results in hefty latency overheads". DSE removes that cost transparently and gives up to 10x lower end-to-end latency. — [libDSE](https://arxiv.org/abs/2412.13314)
- DARQ runs resilient steps without waiting for message persistence while it keeps CReSt guarantees. — [DARQ](https://dspace.mit.edu/entities/publication/1b1cff53-08aa-44ee-b9ca-dc0e3cd1aae9)
- Boki's metalog separates ordering, consistency and fault tolerance in a shared log for serverless. — [Boki](https://github.com/ut-osa/boki)
- LazyLog (UIUC, SOSP 2024, Best Paper): it binds records to linearizable global positions lazily, before a position is read, not at ingestion. This lowers ingestion latency for apps that need order only when they consume. — [Confluent talk](https://current.confluent.io/post-conference-videos-25/lazylog-a-new-log-abstraction-for-low-latency-applications-e-nola25); [artifact](https://github.com/DistributedSystemResearch/24SOSP-LazyLog-Artifact)
- SpecLog / Belfast (Bhat, Hong, Luo, Hu, Ganesan, Alagappan; UIUC). **OSDI 2025** (not 2024 as the brief suggested). It delivers records against a *speculated* global order so application computation overlaps log coordination. "Fix-ante ordering" fixes the global order in advance and makes shards follow it. — [USENIX OSDI '25](https://www.usenix.org/conference/osdi25/presentation/bhat)
- DBOS's argument against a separate checkpoint layer: the operation log in Postgres is "immediately durable and does not require separate checkpointing", and the log can be queried with SQL. — [CIDR 2026](https://www.vldb.org/cidrdb/papers/2026/p9-stonebraker.pdf)
- ExoFlow lets one app choose different recovery-versus-performance tradeoffs per task, for example skipping persistence for deterministic tasks and re-running them from lineage instead. — [ExoFlow](https://usenix.org/conference/osdi23/presentation/zhuang)
- LogAct (Meta, 2026) records LLM inference outputs in a shared log before execution, so replay is deterministic despite LLM non-determinism. — [LogAct](https://arxiv.org/html/2604.07988v1)
- AstronOS (iFLYTEK, arXiv 2608.16381, 2026) compared five ways to hand an agent's work to a fresh model session. Full-history replay passed 2 of 15 runs; runtime-mediated handoff of versioned authoritative state passed 14 of 15. — [arXiv](https://arxiv.org/abs/2608.16381)

### Inferences
- **Speculative durable execution** is the most-evidenced frontier idea. Three independent systems point the same way: Netherite (speculative communication), DARQ (speculative steps) and libDSE (speculation behind a synchronous-looking API). The engineering cost is rollback and repair of downstream effects that were already exposed. External side effects must be held back until the speculation commits.
- **Asymmetric logging** (Halfmoon) applies to engines that log both activity inputs and results. Where a step's reads come from a versioned store, logging writes only (or reads only) can roughly halve log volume. This is unproven outside the Boki substrate.
- For LLM agents, the AstronOS result suggests that "replay the full history" is a poor recovery strategy at the *semantic* level, not only at the cost level. A compact, versioned authoritative state (a snapshot of the continuation) beats it. This supports snapshot or continuation checkpoints over pure event-log replay for agent workloads. The study is a small single-benchmark preprint.
- Lazy ordering (LazyLog) fits event-history tables where order matters only at replay or read time. That could lower append latency for high-fan-out workflows.

### Gaps
- Scalog (NSDI 2020) and Delos / Virtual Consensus (OSDI 2020) were not re-verified this session.
- I found no paper that measures replay cost on a production replay-based engine (Temporal-style history sizes, sticky-cache miss rates). Workflow "continue-as-new" and history compaction have no academic treatment that I found.
- I found no academic work on snapshotting *language-level continuations* (serializing a coroutine or stack) for durable workflows in the 2023–2026 window, apart from the Active DSU stack-rewriting work in Section 4.

## 4. Workflow evolution, dynamic software updating, live upgrade

### Takeaway
This is the thinnest area of the research literature compared with its practical importance. Classic DSU (state transfer, stack rewriting) and event-sourcing schema-evolution work exist. I found no 2023–2026 peer-reviewed paper on safely upgrading *in-flight replay-based durable workflows*: determinism-preserving code changes, patch markers, or version routing. This is an open R&D direction.

### Cited Findings
- *Active DSU: Dynamic Software Updates for Active Functions*. Onward! / SPLASH 2024. It updates long-running active functions (for example a server main loop) by rewriting the call stack to migrate data and control flow. It does not wait for a quiescent point. — [SPLASH 2024](https://2024.splashcon.org/details/splash-2024-Onward-papers/3/Active-DSU-Dynamic-Software-Updates-for-Active-Functions)
- *Back to the Future: Fault-tolerant Live Update with Time-traveling State Transfer*. Giuffrida et al. USENIX LISA 2013. Old and new versions run as separate processes. Semantics-preserving state-transfer transactions move state across versions, so a failed update rolls back. — [EPFL Infoscience](https://infoscience.epfl.ch/record/227472); [USENIX](https://www.usenix.org/conference/lisa13/technical-sessions/papers/giuffrida)
- DAPPER (2024) transforms program state from an original process to a new one to update running processes. — [search result, NSF PAR](https://par.nsf.gov/servlets/purl/10547986) (venue not verified)
- *An Empirical Characterization of Event Sourced Systems and Their Schema Evolution — Lessons from Industry*. Overeem, Spoor, Jansen, Brinkkemper. Journal of Systems and Software 2021. Interviews with 25 engineers. Challenges named: event system evolution, a steep learning curve, missing technology, rebuilding projections, and data privacy. Evolution tactics: versioned events, weak schema, upcasting, in-place transformation, copy-and-transform. — [PDF](https://dspace.library.uu.nl/bitstream/1874/412217/1/1_s2.0_S0164121221000674_main.pdf); [arXiv 2104.01146](https://ar5iv.labs.arxiv.org/html/2104.01146)
- Industrial BPM practice: Camunda migrates a running process instance from one definition version to another by mapping activities. Migration fails when instance state does not allow it, for example when there are non-migrated jobs. — [Camunda docs](https://docs.camunda.org/manual/webapps/cockpit/bpmn/process-instance-migration/)
- R3 (PVLDB 2023) "retroaction" re-runs recorded requests against modified code. This mechanism could test a new workflow version against old histories. — cited in [CIDR 2026](https://www.vldb.org/cidrdb/papers/2026/p9-stonebraker.pdf)
- AstronOS keeps "versioned authoritative state" per work item across model sessions, which is a versioning approach for agent state. — [arXiv](https://arxiv.org/abs/2608.16381)

### Inferences
- Replay-based engines turn DSU into a determinism problem: new code must produce the same command sequence for the recorded prefix. The research toolkit that maps onto this is (a) retroactive replay of stored histories against new code (R3), (b) BPM-style activity mapping for migration, (c) event upcasting (Overeem), and (d) stack and state transfer (Active DSU, time-traveling state transfer). No paper I found combines them for durable workflows. Candidate directions: automatic compatibility checking by replaying a sample of stored histories; a formal "replay-compatible change" relation; mapping-based migration of in-flight workflows at step boundaries.
- Snapshot-based recovery (Section 3) and DSU interact. If a workflow resumes from a state snapshot rather than a full replay, code changes before the snapshot point no longer need to be deterministic. That is an argument for snapshotting that has not been explored in the papers I found.

### Gaps
- The academic BPM instance-migration literature (Rinderle, Reichert, Dadam, "correctness criteria for dynamic changes", ADEPT2) was not verified this session, so no citation is given.
- Kitsune, Rubah and Ginseng were not verified this session.
- No peer-reviewed paper on Temporal-style workflow versioning (patching, worker build IDs) was found.

## 5. Deterministic simulation testing, record/replay, formal verification

### Takeaway
Industry practice (AWS's P and TLA+ use, deterministic simulation) is documented in CACM 2025. Durable Functions is the only orchestration engine with a published formal semantics and equivalence proof (OOPSLA 2021). From 2023 to 2026 the activity shifted to (a) trace validation of implementations against TLA+ specs, (b) record/replay and retroaction for database-backed apps (R3), and (c) 2026 preprints that machine-check resume semantics of agent workflow frameworks and find real exactly-once bugs.

### Cited Findings
- *Systems Correctness Practices at Amazon Web Services*. Brooker, Desai. CACM, June 2025. Covers TLA+, the P language (a state-machine language AWS adopted because many engineers struggled with TLA+), property-based testing, fault injection, and deterministic event-based simulation. — [CACM](https://cacm.acm.org/practice/systems-correctness-practices-at-amazon-web-services)
- Durable Functions has a formal semantics and a proof of equivalence between the idealized model and the distributed runtime. — [DF with proofs](https://microsoft.com/en-us/research/uploads/prod/2021/10/DF-Semantics-With-Proofs.pdf)
- *Validating Traces of Distributed Programs Against TLA+ Specifications*. arXiv 2404.16075 (2024). Checks recorded implementation traces against a TLA+ spec. — [arXiv](https://arxiv.org/pdf/2404.16075)
- SSMS (CIDR 2024) proposes verifying CReSt-based compositions with composition, hiding and simulation relations, and lists this as future work. — [SSMS](https://www.vldb.org/cidrdb/papers/2024/p16-li.pdf)
- *Resume Means Resume* (Sajjad Khan, arXiv 2608.03836, Aug 2026; single author, not peer-reviewed). It defines a six-property conformance contract for checkpoint, interrupt and resume. It model-checks with TLA+ (7.4M states) and proves 196 TLAPS obligations. It reports real bugs: "LangGraph 1.2.9 durably records a second resume value and never consults it". "CrewAI 1.15.2 re-executes completed effect-bearing methods". Concurrent delivery breaks consume-once across processes in 36 of 40 test cells. It proposes REMIT, a reference sequencer with a Verus-verified recovery core. — [arXiv](https://arxiv.org/abs/2608.03836)
- *Safe to Resume? Breaking Execution Continuity of Agent Execution via Rollback* (arXiv 2608.29381, 2026). Treats checkpoint selection and rollback (resume from an earlier superstep, branching) as an attack surface. — [arXiv](https://arxiv.org/pdf/2608.29381)
- *Verified Detection and Prevention of Concurrency Anomalies in Multi-Agent LLM Systems* (arXiv 2606.17182, 2026). Frames durable-execution engines (Temporal, Cadence) as giving exactly-once activity completion through deterministic replay, and applies verification to multi-agent anomalies. — [arXiv](https://arxiv.org/pdf/2606.17182)
- R3 gives record, replay and retroaction for database-backed apps. CIDR 2026 proposes extending the DBOS operation log to speculative "what-if" analysis and automated bug detection. — [CIDR 2026](https://www.vldb.org/cidrdb/papers/2026/p9-stonebraker.pdf)
- *Deterministic Replay for AI Agent Systems* (agrepl; Rasheed Mudasiru, arXiv 2607.16200, 2026; single author). A MITM proxy records all external interactions at the transport layer and replays them in isolation. It defines a request-key matching function with a determinism invariant and a noise-aware diff for HTTP headers. Replay fidelity 1.0 over 250 instances and five workloads; median 98.3% per-step latency reduction. — [arXiv](https://arxiv.org/abs/2607.16200)
- *Chronicle: Cut-Point Replay for Regression Testing of LLM Agents* (arXiv 2609.20625, 2026). — [arXiv](https://arxiv.org/pdf/2609.20625)

### Inferences
- An open opportunity: a published, machine-checked semantics for a Temporal-style engine (commands, events, replay, versioning). Durable Functions (2021) has one. The 2026 resume-semantics paper shows agent frameworks have exactly-once bugs that such a contract catches. Trace validation (arXiv 2404.16075) gives a cheap bridge: emit engine histories and check them against a TLA+ or P model in CI.
- A persisted event history is a ready-made trace for trace validation and for retroactive replay testing (R3-style). Few engines use their own history store as a verification oracle.
- Rollback and resume as an attack surface (2608.29381, 2608.01710) is a new threat model. "Resume from an earlier checkpoint" or "fork" can repeat authorized effects.

### Gaps
- I found no public TLA+ or P specification of Temporal or Cadence in peer-reviewed literature.
- IronFleet, Verus (SOSP 2024) and Grove were not re-verified this session. Only Verus's use inside REMIT was observed.
- FoundationDB's simulation-testing paper (SIGMOD 2021) was not re-verified this session.

## 6. Durable execution for AI agents / LLM workflows (2024–2026)

### Takeaway
2026 brought a burst of arXiv work. Most of it is preprints, and several are single-author. Two recurring ideas: (1) log LLM outputs before acting, so replay is deterministic and actions can be vetted (LogAct). (2) Resume and checkpoint semantics in agent frameworks are under-specified and buggy (Resume Means Resume). Agents break the classic durable-execution assumption that control flow is defined up front, and compensation cannot be pre-written for open-ended actions.

### Cited Findings
- *LogAct: Enabling Agentic Reliability via Shared Logs*. Balakrishnan, Bharambe, Testuggine et al. (Meta). arXiv 2604.07988, Apr 2026. Implemented. Each agent is a deconstructed state machine over an "AgentBus", a linearizable, durable, typed shared log with access control. It cycles through Inferring, Voting, Deciding and Executing stages, and records intentions durably before execution. Pluggable safety voters approve or block actions. It was integrated with Claude Code (hooks), an internal harness, and a clean-slate Rust implementation (LogClaw). Results: 1.4% attack success with 78.4% benign utility on AgentDojo; semantic crash recovery in which a replacement agent diagnosed a performance issue (290x faster execution); a supervisor reading peer logs got 17% more work with 41% fewer tokens in a 6-agent swarm. It contrasts itself with Temporal and Restate, which "require the developer to define the workflow's control flow graph upfront, including explicit compensating actions". — [arXiv](https://arxiv.org/html/2604.07988v1)
- LogAct's named open problems: multi-agent coordination protocols; no guarantee that semantic recovery restores a clean state when inference is "arbitrary and difficult to test"; and executor Byzantine behavior, which needs infrastructure isolation. — [arXiv](https://arxiv.org/html/2604.07988v1)
- *Resume Means Resume*: framework-level resume bugs in LangGraph and CrewAI (see Section 5). — [arXiv](https://arxiv.org/abs/2608.03836)
- *AstronOS* (iFLYTEK, Aug 2026): versioned authoritative state per work item ("Cases, Tasks, Scenario Packs") beats full-history replay (14/15 vs. 2/15 passes). It costs more wall-clock time per attempt but uses fewer tokens per success. — [arXiv](https://arxiv.org/abs/2608.16381)
- *Sherlock: Reliable and Efficient Agentic Workflow Execution* (arXiv 2511.00330, 2025). It uses counterfactual analysis to find error-prone components in agentic workflows and verifies them selectively, trading verification cost for reliability. — [arXiv](https://arxiv.org/pdf/2511.00330)
- *Causal Agent Replay: Counterfactual Attribution for LLM-Agent Failures* (arXiv 2606.08275, 2026). — [arXiv](https://arxiv.org/pdf/2606.08275)
- *Beyond Single-Use Tokens* (arXiv 2608.01710): retries and resumes repeat authorizations (see Section 2). — [arXiv](https://arxiv.org/abs/2608.01710v1)
- *GraphFlow* (arXiv 2605.14968, 2026): formally verifiable visual workflows for agentic automation. — [arXiv](https://arxiv.org/pdf/2605.14968)
- CIDR 2026 explicitly treats an LLM or agent step as one more workflow step that needs AC/DC guarantees. — [CIDR 2026](https://www.vldb.org/cidrdb/papers/2026/p9-stonebraker.pdf)
- Industry: Microsoft describes durable, deterministic multi-agent orchestrations built on Durable Functions / Durable Task. — [Microsoft Tech Community](https://techcommunity.microsoft.com/blog/appsonazureblog/building-durable-and-deterministic-multi-agent-orchestrations-with-durable-execu/4408842)

### Inferences
- Agent-oriented frontier ideas that mainstream engines do not ship as primitives: (a) an intent log with pre-execution voting or approval as part of the durable log (LogAct); (b) semantic recovery, where a successor agent reads the log and repairs state instead of replaying deterministically; (c) a machine-checked resume contract (consume-once resume values, no re-execution of effectful steps); (d) authorization-aware idempotency; (e) state handoff rather than full-history replay for long-horizon agents.
- Cost-aware retries (retry budgets in tokens or dollars, model fallback on retry) are widely discussed in industry. I found no rigorous paper on them. Sherlock's selective verification is the closest.

### Gaps
- I found no peer-reviewed (non-arXiv) paper from 2024–2026 on durable execution for LLM agents. All agent items above are preprints.
- I found no paper that quantifies the cost of re-running LLM calls on replay versus caching them, beyond LogAct's design argument and agrepl's latency numbers.

## 7. Recurring open problems and the research frontier (synthesis)

### Takeaway
Across the papers, the same open problems recur: (1) isolation and correctness for sagas and compensations under concurrency; (2) persistence latency, now attacked with speculation; (3) composition of resilient services without losing guarantees; (4) external non-idempotent side effects; (5) cost-based, declarative placement and optimization of workflows; (6) live evolution of long-running instances; (7) formal contracts and verification of engine semantics; (8) open-ended agent control flow that cannot be specified up front. Items 1, 2, 6 and 7 are the clearest candidate R&D directions for a replay-based engine.

### Cited Findings
- CIDR 2026 future work: (i) apply the semantic model to GDPR and PII deletion through the platform log, including coordinated cross-enterprise deletion; (ii) formally define isolation guarantees for saga-style workflows, "analogous to how ANSI SQL isolation levels formalize" transaction isolation; (iii) higher isolation for sagas through OCC, escrow for commutative operations, or hybrid physical-backout and compensation; (iv) time-travel debugging extended to speculative "what-if" analysis and automated bug detection. Workflow-level consistency is listed as "not-yet-implemented". — [CIDR 2026](https://www.vldb.org/cidrdb/papers/2026/p9-stonebraker.pdf)
- SSMS research challenges: logical application model, resilient primitives, and cost-based optimization of scheduling and placement, much like a DBMS query optimizer. — [SSMS CIDR 2024](https://www.vldb.org/cidrdb/papers/2024/p16-li.pdf)
- libDSE frames synchronous persistence as the main latency tax of current durable execution. It names the tension between programming restrictions and supported use cases. — [libDSE](https://arxiv.org/abs/2412.13314)
- LogAct names multi-agent coordination, unverifiable semantic recovery, and Byzantine executors as open. — [LogAct](https://arxiv.org/html/2604.07988v1)
- Overeem et al. list event-system evolution, rebuilding projections and data privacy as practitioner challenges. — [JSS 2021](https://ar5iv.labs.arxiv.org/html/2104.01146)
- Resume Means Resume implies a need for a cross-framework standard resume contract. — [arXiv](https://arxiv.org/abs/2608.03836)
- Keep CALM and CRDT On sets an agenda for coordination-free queries over replicated state. — [PVLDB](https://arxiv.org/abs/2210.12605v1)

### Inferences — candidate R&D directions (proposed or prototyped in papers, not mainstream in production engines)
1. **Speculative durable execution** (Netherite, DARQ, libDSE, SpecLog). Run ahead of log persistence, hold external effects until commit, and repair on failure. Reported up to 10x latency reduction. Status: implemented in research. One instance (Netherite) belongs to a production-adjacent Microsoft runtime.
2. **Asymmetric, log-optimal step logging** (Halfmoon). Status: implemented and proven on Boki only.
3. **Workflow-level physical backout** (savepoint per step inside one DB transaction) as an alternative to sagas, chosen per workflow by contention profile. Status: prototype in dbos-transact-py. The paper shows a contention crossover.
4. **Formal saga isolation levels and escrow-based compensation**. Status: proposed (CIDR 2026 future work).
5. **Serializable multi-entity transactions by deterministic execution** inside the workflow engine (Styx, Snapper). Status: implemented in research runtimes.
6. **Replay-compatibility checking for code upgrades** using retroactive replay of stored histories (R3) plus activity mapping (BPM) and upcasting (event sourcing). Status: components exist separately; no combined system found.
7. **Machine-checked engine semantics and trace validation** (DF OOPSLA 2021, TLA+ trace validation, Resume Means Resume, AWS P). Status: done for DF and agent frameworks. Not done publicly for Temporal-style engines.
8. **Agent-native durability**: an intent log with voters (LogAct), consume-once resume values, authorization-aware idempotency, state handoff instead of history replay (AstronOS). Status: 2026 preprints.
9. **Log as governance substrate**: PII erasure and coordinated deletion through the workflow log (CIDR 2026), and SQL-queryable history. Status: proposed.
10. **Cost-based placement and optimization of workflows** (SSMS). Status: vision with preliminary evaluation.

### Gaps
- Many 2026 agent-durability preprints are single-author and unreviewed (Resume Means Resume, agrepl). Their bug findings against LangGraph and CrewAI should be reproduced before anyone relies on them.
- No paper gave production-scale measurements of how often non-determinism errors or version-incompatibility failures happen in replay-based engines. That measurement would itself be a contribution.
