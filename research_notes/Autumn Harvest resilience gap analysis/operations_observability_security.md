## Q1. What do established external sources recommend (SRE, AWS Builders' Library, gray failure, Temporal operator surface)?

### Takeaway
The consensus is: define SLOs and page on multi-window burn rates rather than static thresholds; keep the data plane statically stable when the control plane fails; limit blast radius with cells/shuffle sharding and one-box → wave deployments that roll back automatically on scoped alarms; avoid rarely-exercised fallback paths; and close the "differential observability" gap that causes gray failure by measuring health from the application's point of view. Temporal's operator surface centres on schedule-to-start latency, slot availability, poller counts, sticky-cache behaviour and workflow-task failures.

### Cited Findings
**SLOs and alerting (Google SRE Workbook, "Alerting on SLOs"; content dates from 2018 but remains the reference):**
- Recommended starting parameters for a 99.9% SLO: page when the 1 h window AND 5 min window burn rate is 14.4 (2% of budget consumed); page at 6 h/30 min windows with burn rate 6 (5% of budget); ticket at 3 d/6 h windows with burn rate 1 (10% of budget). — [SRE Workbook: Alerting on SLOs](https://sre.google/workbook/alerting-on-slos/)
- Alert quality is judged on precision ("proportion of events detected that were significant"), recall ("proportion of significant events detected"), detection time and reset time; multiwindow alerts improve reset time because both long and short windows must exceed the threshold. — [SRE Workbook: Alerting on SLOs](https://sre.google/workbook/alerting-on-slos/)

**Static stability (AWS Builders' Library):**
- "In a statically stable design, the overall system keeps working even when a dependency becomes impaired." Recommendations: separate data plane from control plane; pre-provision capacity (e.g., 50% overprovision across 3 AZs); do not depend on control-plane actions (provisioning, config changes) during recovery; keep traffic AZ-local. — [Static stability using Availability Zones](https://aws.amazon.com/builders-library/static-stability-using-availability-zones/)

**Safe continuous deployment (AWS Builders' Library, Clare Liguori, 2020):**
- The gamma one-box stage checks that "the latest code is backward-compatible and can be safely deployed alongside the current code", e.g., to "detect whether the latest code writes data in a format that the current code can't parse"; the one box runs "for some period of time, such as 30 minutes or one hour" and monitors canary success and service metrics to detect impact "from having a 'mixed' fleet deployed side by side." — [Automating safe, hands-off deployments (PDF)](https://d1.awsstatic.com/builderslibrary/pdfs/automating-safe-hands-off-deployments-clareliguori.pdf)
- Production waves start with a one-box stage that "serves at most ten percent of overall requests for the Region or Availability Zone"; on negative impact "the pipeline automatically rolls back the change and doesn't promote it". Rolling deployments replace "at most 33 percent" of boxes per batch so ≥66% capacity stays healthy. — [same PDF](https://d1.awsstatic.com/builderslibrary/pdfs/automating-safe-hands-off-deployments-clareliguori.pdf)
- One-box stages "additionally roll back on metrics that are scoped to only the one box" (e.g., fault rate of requests served by the one box), because a small-traffic box may not trip aggregate alarms; bake time continues monitoring high-severity aggregate alarms, longer in early waves. Automatic rollback frequently completes "before the on-call engineer is even logged in." — [same PDF](https://d1.awsstatic.com/builderslibrary/pdfs/automating-safe-hands-off-deployments-clareliguori.pdf); [search summary of the same article](https://www.infoq.com/podcasts/clare-liguori-aws-deployments/)

**Avoiding fallback (AWS Builders' Library, Jacob Gabrielson, 2019):**
- Fallback "isn't exercised regularly and is likely to fail or increase the scope of impact when it triggers during an outage"; if needed, run both paths continuously so it becomes failover. Amazon favours "code paths that are exercised in production continuously rather than rarely", pushing data proactively, and making the primary more robust. Retries and timeouts must not become untested fallback. — [Avoiding fallback in distributed systems (PDF)](https://d1.awsstatic.com/builderslibrary/pdfs/avoiding-fallback-in-distributed-systems.pdf)

**Blast radius: cells and shuffle sharding:**
- AWS codifies cells as REL10-BP03 "Use bulkhead architectures to limit scope of impact"; a cell-based architecture partitions a workload into independent, self-contained replicas each serving a slice of clients routed by partition key; shuffle sharding gives each customer a near-unique combination of nodes so a bad actor overlaps only partially with others. — [AWS Well-Architected REL10-BP03](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/rel_fault_isolation_use_bulkhead.html); [Reducing the Scope of Impact with Cell-Based Architecture (FAQ)](https://docs.aws.amazon.com/wellarchitected/latest/reducing-scope-of-impact-with-cell-based-architecture/faq.html) (via search summary; the Builders' Library shuffle-sharding article now redirects to a JS-rendered builder.aws.com page that could not be fetched)

**Gray failure (Huang et al., HotOS 2017):**
- "A key feature of gray failure is differential observability: that the system's failure detectors may not notice problems even when applications are afflicted by them." Formal definition: "a system is defined to experience gray failure when at least one app makes the observation that system is unhealthy, but observer observes that system is healthy." — [Gray Failure: The Achilles' Heel of Cloud-Scale Systems (PDF)](https://www.microsoft.com/en-us/research/wp-content/uploads/2017/06/paper-1.pdf)
- Mitigation direction: "close the observation gaps between the system and the apps"; the authors "advocate moving from singular failure detection (e.g., with heartbeats) to multi-dimensional health monitoring." — [same PDF](https://www.microsoft.com/en-us/research/wp-content/uploads/2017/06/paper-1.pdf)

**Temporal operator metrics (SDK metrics reference, current docs):**
- Schedule-to-start: `temporal_activity_schedule_to_start_latency`, `temporal_workflow_task_schedule_to_start_latency`; capacity: `temporal_worker_task_slots_available`, `temporal_worker_task_slots_used`; pollers: `temporal_num_pollers`; sticky cache: `temporal_sticky_cache_hit/miss/size/total_forced_eviction`; failures: `temporal_workflow_task_execution_failed` (includes non-determinism). Alerting guidance prioritises schedule-to-start spikes and workflow-task failures. — [Temporal SDK metrics reference](https://docs.temporal.io/references/sdk-metrics)

### Inferences
- A durable workflow engine is itself a control plane for its callers' business processes; the AWS static-stability argument implies Harvest workers should keep draining already-claimed work if the management API, schedulers or config store degrade, and that recovery runbooks should avoid "reconfigure the fleet" as the first step.
- For workflow engines, the SRE-style SLIs map naturally to: schedule-to-start latency (latency SLI), workflow/activity terminal success ratio excluding operator cancels (availability SLI), and a synthetic end-to-end probe (freshness SLI). Harvest ships all three raw signals (see Q3), but not the SLO/burn-rate layer.

### Gaps
- OpenTelemetry semantic-convention pages (messaging/RPC stability status as of 2026) were not fetched; claims about OTel alignment below rely on Harvest's own ADR only.
- Builders' Library "Ensuring rollback safety during deployments" (two-phase serialization changes) is referenced by the deployment PDF but was not fetched; its specific prescriptions are not cited here.
- The AWS shuffle-sharding numeric example (8 workers, shard size 2) could not be retrieved from the redirected page.

## Q2. What are the external practices for graceful shutdown/draining, rolling-deploy compatibility, and security of workflow engines/WASM sandboxes/supply chain?

### Takeaway
Kubernetes gives a process a SIGTERM and a default 30 s grace window (concurrently removing it from Service endpoints) before SIGKILL, so a worker must stop claiming new work, finish or hand off in-flight work, and exit inside that budget; readiness and liveness are distinct signals. Temporal-class engines are insecure by default (no-op authorizer) and rely on mTLS, a pluggable namespace-scoped authorizer, and client-side payload codecs. OWASP API Top 10 flags broken object/function-level authorization and unrestricted resource consumption as the top API risks. Wasmtime recommends fuel for deterministic bounds, epochs for cheap wall-clock bounds, and a ResourceLimiter for memory.

### Cited Findings
**Kubernetes pod termination and probes (current docs):**
- On termination Kubernetes sends SIGTERM, runs preStop hooks, waits `terminationGracePeriodSeconds` (default 30 s) while endpoints are removed from Services concurrently, then sends SIGKILL. — [Kubernetes Pod Lifecycle](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/)
- Startup probe gates the others for slow starters; liveness decides restart; readiness "determines if the container is ready to receive traffic" and controls Service endpoints. — [Kubernetes Pod Lifecycle](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/)

**Rolling deploy / mixed fleet:**
- AWS explicitly tests "mixed" fleets in a one-box stage to catch new code writing data old code cannot parse. — [Automating safe, hands-off deployments (PDF)](https://d1.awsstatic.com/builderslibrary/pdfs/automating-safe-hands-off-deployments-clareliguori.pdf)

**Workflow-engine security (Temporal self-hosted security guide):**
- mTLS is configurable separately for `internode` and `frontend`; authorization uses a `ClaimMapper` (JWT → roles read/write/worker/admin) and an `Authorizer`, scoped per namespace (`<namespace>:<permission>`). — [Temporal self-hosted security](https://docs.temporal.io/self-hosted-guide/security)
- "If you do not explicitly configure an `Authorizer`, Temporal uses the default `noopAuthorizer`. This default allows every API request, with no authentication or access control." Payload encryption is via a Data Converter / Payload Codec, with a Codec Server for remote decoding. — [Temporal self-hosted security](https://docs.temporal.io/self-hosted-guide/security)

**OWASP API Security Top 10 (2023 edition, still current as of Sept 2026 per the site):**
- API1 Broken Object Level Authorization; API2 Broken Authentication; API3 Broken Object Property Level Authorization; API4 Unrestricted Resource Consumption; API5 Broken Function Level Authorization; API6 Unrestricted Access to Sensitive Business Flows; API7 SSRF; API8 Security Misconfiguration; API9 Improper Inventory Management; API10 Unsafe Consumption of APIs. — [OWASP API Security Top 10 2023](https://api-security.owasp.org/editions/2023/en/0x11-t10)

**WASM sandbox limits (wasmtime `Config` docs):**
- Fuel "can be used to deterministically prevent infinitely-executing WebAssembly code" and "should be used when deterministic yielding or trapping is needed", but "fuel instrumentation is somewhat expensive"; epoch interruption is cheaper ("up to 2-3x" faster in some measurements) but non-deterministic. Hosts needing strict time limits should bound heap size with a `ResourceLimiter` because a large `memory.copy` is a single instruction. — [wasmtime Config](https://docs.wasmtime.dev/api/wasmtime/struct.Config.html)

### Inferences
- Because K8s removes the pod from endpoints concurrently with SIGTERM (not before), a pull-based worker is less exposed to "traffic after SIGTERM" than an HTTP server, but its management HTTP surface and its DB-claim loop still need to stop quickly; a drain budget equal to the default grace period leaves no headroom for the post-drain bookkeeping.
- Temporal's default is less safe than Harvest's for admin routes (see Q3), so "secure by default" parity with Temporal is a low bar; OWASP API1/API5 are the relevant yardsticks for Harvest's coarse read/mutate model.

### Gaps
- Temporal worker graceful-shutdown specifics (e.g., `WorkerStopTimeout`, activity heartbeat hand-off) were not fetched.
- RustSec/cargo-deny documentation was not fetched; supply-chain assessments below rely on the repo's own `deny.toml` commentary plus general practice.

## Q3. Codebase audit: what does Autumn Harvest actually provide for operability?

### Takeaway
Harvest's operability surface is unusually deep for an embedded engine: ~80 documented `harvest.*` metrics including schedule-to-start and oldest-pending-age, a 30+ rule starter alert pack tied to runbooks and a 48-panel Grafana dashboard, a synthetic liveness canary, control-loop liveness heartbeats, per-execution stall diagnosis, a worker drain protocol with remote deadlines, build-id routing with percent ramps, a fail-closed admin gate, opt-in scoped tokens, audit trail with SIEM export, and a well-bounded WASM sandbox. The weak spots are the SLO/burn-rate layer, health/readiness semantics, automated rollback, DB-pool/HTTP golden signals inside Harvest, coarse authorization/tenant isolation, and release/supply-chain hardening.

### Cited Findings

**Observability — metrics (present and tested for docs parity):**
- `docs/telemetry.md` documents 83 distinct `harvest.*` identifiers (metrics plus a few attribute names such as `harvest.execution.id`), including `harvest.queue.depth` (`docs/telemetry.md:325`, sampled every 5 s and summed across shards), `harvest.queue.schedule_to_start`, `harvest.queue.oldest_pending_age`, `harvest.worker.slots_in_use/slots_available/slot_target`, `harvest.workflow.non_determinism`, `harvest.workflow.history_size`, `harvest.shard.stranded_pending` (`docs/telemetry.md:330`), `harvest.queue.paused` (`docs/telemetry.md:342`), `harvest.workflow.active` (`docs/telemetry.md:345`), replication lag/RPO and audit-export lag gauges. — `docs/telemetry.md` (grep of backticked `harvest.*` names)
- No Harvest-emitted DB-pool (connections in use / acquire wait), DB query latency, or poller-count metrics were found (`grep "harvest.(db|pool|http|poll|heartbeat)"` over `autumn-harvest/src` and `autumn-harvest-plugin/src` returned nothing). Sticky-cache hit/miss is covered by `harvest.workflow.cache_hit` / `harvest.workflow.cache_miss` (`autumn-harvest/src/telemetry.rs:545-558`, emitted at `autumn-harvest/src/worker.rs:20441-20449`). HTTP golden signals come from the host: the built-in scrape recorder renders alongside autumn-web's `autumn_http_*` families (`autumn-harvest-plugin/src/metrics_scrape.rs:1-11`). **Absent** in Harvest for DB; delegated for HTTP.
- The built-in scrape endpoint does not provide bucketed histograms; dashboards require the `metrics-rs` adapter plus `metrics-exporter-prometheus` (`docs/dashboards/README.md:26-30`; `docs/telemetry.md:89-108`).
- Tracing: ADR-0001 defines span contracts and W3C `traceparent` propagation stored on `harvest_task_queue.trace_context` (`docs/adr/0001-otel-trace-contract.md:23`, `:85`), with replay attaching a span *link* rather than a parent (`:158-190`). It states Harvest "does not yet have upstream OTel semconv entries" and uses a `harvest.*` namespace (`docs/adr/0001-otel-trace-contract.md:48-49`). No `opentelemetry` crate dependency exists in `autumn-harvest/Cargo.toml` or `autumn-harvest-plugin/Cargo.toml` (grep), so OTLP export is embedder-supplied via `tracing`/`metrics` bridges. `trace_export.rs` is **not** an OTel exporter: it converts a simulated DAG profile to Chrome Trace Event Format (`autumn-harvest/src/trace_export.rs:1-4`).

**Alerts and dashboards (present; static docs-guard tests exist):**
- Starter alert pack `docs/alerts/starter-pack-v0.1.0.json` contains rules for schedule-to-start p99 > 30 s, oldest-pending-age > 30 s, growing depth, slot utilisation > 90%/5 m, activity failure ratio > 5%, workflow failure ratio > 10%/5 m, non-determinism, saga compensation failures, paused-queue-too-long, scanner-tick stalls, capability-miss escalation, replication down/lag/RPO-unknown, shard fencing, audit-export lag/absent/unobservable, and dropped dispatch hints (extracted `expr`/`name` fields). Rules carry dependency tags and "pending" rules are marked non-enforceable (`docs/alerts/README.md:28-32`). A guard test exists (`autumn-harvest/tests/integration/alert_pack_docs.rs:310`).
- Thresholds are explicitly "starter defaults, not universal SLOs" (`docs/alerts/README.md` intro; `starter-pack-v0.1.0.json:230`, `:588`). No burn-rate, error-budget, or multi-window rule exists: grep for `burn.?rate|error budget` across `docs/alerts`, `docs/dashboards`, `docs/runbooks`, `docs/telemetry.md`, `docs/operations` returned only "not a universal SLO" disclaimers and one "primary success-rate SLO signal" description (`docs/runbooks/harvest-alerts.md:996`). **Absent:** SLO definitions and burn-rate alerting.
- Grafana starter dashboard: 48 panels including overview, schedule-to-start p99, slot utilisation, scanner liveness, synthetic canary, cross-region DR (RPO, standbys, WAL backlog, generation skew, fencing), audit export (`docs/dashboards/starter-pack-v0.1.0.json`, panel titles). Linked runbooks: `docs/runbooks/harvest-alerts.md`, `synthetic-incident-drills.md`.

**Gray-failure detection:**
- Synthetic liveness canary: a built-in throwaway workflow per probe queue exercises "start → dispatch → activity → durable-timer → complete" so a wedged pipeline is detected "within one probe interval" (`autumn-harvest/src/canary.rs:1-8`, `:23-38`); canary terminals are excluded from business SLO counters (`docs/telemetry.md:366`). **Present and tested** (`autumn-harvest/tests/integration/canary_tests.rs`, `autumn-harvest-plugin/tests/canary_integration.rs`).
- Control-loop liveness: background loops (timeouts, SLA scanner, poison-pill reclaimer, outboxes, retention, schedule ticker, audit export) emit heartbeats because a stalled loop "fails silently" (`autumn-harvest/src/scanner_health.rs:1-14`); alerted via `harvest_scanner_tick_total` rate == 0 rules.
- Per-execution stall root-cause classifier distinguishing "no live worker polling", "circuit open", "rate-limited", "queue paused" (`autumn-harvest/src/stall_diagnosis.rs:1-14`).
- Worker health itself is binary heartbeat-based: `classify` returns stale when no heartbeat within `stale_threshold` ("typically 2 × heartbeat_interval") (`autumn-harvest/src/workers.rs:137-150`; `WorkerHealth::Stale` parse at `workers.rs:245`). No per-worker error-rate/outlier health dimension was found. **Present (heartbeat only).**

**Health/readiness endpoint:**
- `GET /health` is the only `PublicSafe` route (`docs/security-posture.md:42`). The handler returns `503` only when shard-readiness enforcement is on and the shard report is not `Ready`; otherwise it returns `200` with `runtime_ready: runtime.is_some()` in the body (`autumn-harvest-plugin/src/api.rs:40251-40291`, status logic `:40265-40273`). So a process whose runtime is not yet started (or already stopped) still answers 200 by default, and there is no draining state in the response. No separate liveness vs readiness endpoint, and no Kubernetes probe / `terminationGracePeriodSeconds` / `preStop` guidance in `docs/` (grep returned nothing). **Present but semantically weak; K8s guidance absent.**

**Graceful shutdown / draining:**
- `WorkerConfig.shutdown_timeout` ("Maximum time to wait for in-flight tasks during shutdown", `autumn-harvest/src/worker.rs:172-173`) defaults to 30 s (`autumn-harvest/src/builder.rs:3931`); separate `cancellation_grace_period` for cooperative activity unwind (`worker.rs:174-176`, enforced at `worker.rs:14459-14491`).
- Sequence (single shard): poll loop exits on the cancellation token → status `Draining` → `drain_in_flight()` → `Stopped` → cancel heartbeat → join monitors (`autumn-harvest/src/worker.rs:27961-27978`). Multi-shard path bounds each shard's status write so one exhausted pool cannot park the drain (`worker.rs:27546-27575`, issue #1209).
- `drain_in_flight` waits to reacquire every semaphore permit, with a deadline that a remote drain request can extend (re-read every 1 s); on timeout it only logs "shutdown timeout elapsed — some tasks may still be running" and returns (`autumn-harvest/src/worker.rs:30728-30799`). No explicit release/hand-off of still-running claimed tasks was found (grep for release/hand-off in `worker.rs` found none); recovery therefore relies on lease/heartbeat expiry elsewhere (inference). `Worker::shutdown()` just cancels the token (`worker.rs:30802-30804`).
- Plugin path: autumn-web's `on_shutdown` hook calls `stop_harvest_runtime` (`autumn-harvest-plugin/src/plugin.rs:1462-1468`), which stops broker connectors first so committed dispatches are acked (`plugin.rs:2423-2458`). Explicit SIGTERM handling in this repo exists only in the dev runtime (`autumn-harvest-plugin/src/dev/mod.rs:519-539`); production SIGTERM trapping is delegated to autumn-web (not in this repo).
- Operator drain: `POST /workers/{id}/drain` (classified Mutating, `docs/security-posture.md:38`), CLI `harvest worker drain --deadline/--wait`, `drain-preview`, audit of `worker.drain`, and post-drain queue-coverage check (`docs/runbooks/safe-deploy.md:1-150`, `:156-230`). Preflight fails when only draining workers cover a queue (`autumn-harvest-plugin/tests/preflight_integration.rs:765`). **Present; drain-timeout behaviour itself: no dedicated test located.**
- Open issue #1552: "Worker::run_with_listener's heartbeat task detaches (not aborts) under external cancellation" (GitHub, open, 2026-09-14).

**Rolling upgrade / mixed-version support:**

- Codec compatibility: workers advertise registered codec key ids (`CODEC_REGISTERED_KEY_IDS_LABEL`, `autumn-harvest/src/payload_codec.rs:204-225`), supporting mixed-key fleets during rotation (`docs/operations/codec-key-rotation.md`).

No expand/contract (old-code-compatible schema) policy was found in the upgrade guides (grep for expand/contract/downgrade). **Partially present (ordering guidance), compatibility contract absent.**

**Configuration safety:**

**Management API authN/authZ, tokens, TLS:**
- Harvest ships no IdP/RBAC; auth is "delegated to the host Autumn application" (`docs/security-posture.md:8`). Shards provide data placement/residency (`docs/security-posture.md:288-315`) but not per-tenant authZ.

**WASM sandbox (present and tested):**
- Defaults: fuel 100,000,000 (`autumn-harvest/src/wasm_activities.rs:81`), memory 16 MiB (`:63`), wall clock 300 s via epoch interruption (`:134`, `:313-314`), stack 512 KiB (`:120`, `:318`), 1 memory, 1 instance, ≤16 tables, ≤100k table elements; fresh store per attempt (`:850-854`); filesystem/network not representable, ungranted imports → non-retryable `sandbox_denied` (`:39`, `:161`). Tests: `ungranted_fs/net/env_get_import_is_sandbox_denied` (`:1200-1233`), `fuel_exhaustion_is_retryable_resource_exhausted` (`:1600`), `memory_limit_is_resource_exhausted` (`:1617`), multi-memory rejection (`:1712`). Module store keys by SHA-256 content hash and verifies integrity before compile (`autumn-harvest/src/wasm_store.rs:17`, `:187`, `:254`). No publisher signature/provenance check.

**Supply chain / CI:**
- `cargo deny check` (advisories, licenses, bans, sources) runs in CI `dependency-audit` (`.github/workflows/ci.yml:1713-1724`); `deny.toml` sets `yanked = "deny"` (`deny.toml:22`) and `unsound = "all"` (`deny.toml:49`) after cargo-deny 0.19 silently re-narrowed unsound scope (`deny.toml:23-48`); each ignore carries a reachability verdict.
- CI triggers are push/PR/workflow_dispatch only (`.github/workflows/ci.yml:19-24`); `dependency-audit` is additionally skipped when the `changes` filter reports no code change (`ci.yml:1716-1719`). No `schedule:` trigger in `ci.yml` (grep), so a new RUSTSEC advisory against an unchanged lockfile is caught only by the next code push or an external "Ballast" run (`deny.toml:40-42` cites a 2026-09-28 Ballast run).
- Actions are pinned by mutable tags (`actions/checkout@v4`, `EmbarkStudios/cargo-deny-action@v2`, etc.), not commit SHAs (`.github/workflows/*.yml` grep); no `.github/dependabot.yml` (`ls .github` → `ci`, `workflows`).
- Release workflow (tag `v[0-9]+.*`, `permissions: contents: write`) runs fmt/clippy/tests and creates a GitHub release with git-cliff; no SBOM, signing, attestation or provenance step (`.github/workflows/release.yml:1-40`, grep for sbom/sign/attest empty).
- Other CI assurance: MSRV, fuzz smoke, loom, chaos (scheduled, `.github/workflows/chaos.yml:23`), harvest-verify determinism analyzer (`ci.yml:1752`).

### Inferences
- The metrics set already covers Temporal's core operator signals except poller counts; the biggest observability hole is **saturation of the Postgres dependency** (pool/latency), which is the engine's single most important dependency.
- The health endpoint's 200-when-not-ready default makes it usable as liveness but misleading as readiness; combined with the 30 s default `shutdown_timeout` equal to K8s' 30 s default grace, a pod can be SIGKILLed between "drain timeout" and the `Stopped` status write, leaving a stale `Draining` row until heartbeat expiry.
- Harvest's security posture is "safe admin, open data plane unless the embedder wraps it": stricter than Temporal's default `noopAuthorizer` for `/admin`, but the workflow start/signal/cancel surface is unauthenticated by default outside the embedder's middleware.

### Gaps
- Whether autumn-web (external crate) traps SIGTERM in production, and how long its `on_shutdown` waits, is outside this repo and unverified.
- Whether the diesel-async/deadpool query pool (not just LISTEN/NOTIFY) enforces verified TLS was not confirmed.
- Exactly which non-admin mutating routes are ungated by default was taken from docs (`security-posture.md:383`), not enumerated from `CLASSIFIED_ROUTES`.
- Whether `effective_config` detects config drift across a fleet (vs per-process) was not verified.
- The reclaim path for tasks still running when `shutdown_timeout` elapses was inferred (lease expiry), not traced to a specific function.

## Q4. Gap ratings and remedies

### Takeaway
No Critical operability gaps were found; Harvest's primitives are strong. The High items are the default-open non-admin mutating API surface and the coarse, tenant-blind authorization model. Medium items cluster around SLO/burn-rate alerting, readiness/drain semantics under Kubernetes, lack of automated rollback, missing DB-pool/cache saturation metrics, no production encryption codec, per-client API rate limiting, and scheduled advisory scanning. Low items are OTel semconv alignment, release provenance, audit tamper-evidence, and WASM module signing.

### Inferences
- The absence of Critical findings reflects that the riskiest items (open data-plane API, coarse authZ) are documented, fail closed for `/admin`, and mirror Temporal's own default; they become Critical only when an embedder exposes Harvest beyond a trusted network without middleware.
- Several remedies compose: a `build_id` metric label (gap 6), per-worker outlier health (gap 8) and a readiness endpoint that reflects draining (gap 4) together would give Harvest AWS-style one-box auto-rollback and gray-failure coverage without new subsystems.

### Gaps
- Ratings assume a production Kubernetes deployment with a shared Postgres; single-process or SQLite deployments would downgrade gaps 4, 5 and 12.
- No load or chaos data was consulted for drain behaviour under SIGKILL; `chaos.yml` scenarios were not reviewed in detail.
