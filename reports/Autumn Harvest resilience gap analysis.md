# Harvest's defaults undercut its resilience toolbox

As of September 2026, the literature on resilient distributed systems agrees on five things. Fence every change of ownership with a monotonic epoch that the storage write checks. Bound every wait and every retry, with jitter and budgets. Treat the age of queued work as the main health signal, and finish work before starting new work. Search for failures with deterministic simulation and model checking instead of waiting for CI to hit them. Ship safe defaults, because a protection that is rarely exercised fails when it is finally needed. Measured against that bar, **Autumn Harvest 0.6.0 (HEAD `937b655`) matches or beats Temporal on determinism tooling, non-determinism parking, cross-region generation fencing, the transactional outbox, restore verification and breadth of telemetry**. Most of its protections, though, are opt-in, and the defaults leave three serious classes of gap. The first is overload. The default Postgres poll path claims tasks past local capacity while timeout clocks run from claim time, and database pool waits and SQL statements have no bound on the default single-shard path. Together these form a plausible metastable loop that turns a short database brownout into terminal activity failures. The second is ownership. Activity completion and heartbeat writes check only `state = 'RUNNING'`, so a zombie attempt's result or heartbeat lands on the live, re-claimed attempt. The production worker also appears to skip the unconsumed-history drift check that the strict replayer relies on. The third is assurance. The nightly chaos suite has never run because its workflow file does not parse, loom has zero runs, about 60 database test suites are allowlisted as unwired, and there is no deterministic simulation, formal model or process-level crash test. Most top-priority fixes are cheap, because the correct pattern already exists elsewhere in the tree. Every codebase finding here comes from reading source and docs: nothing was built, run or reproduced.

## Five disciplines separate resilient systems from lucky ones

The execution-model state of the art is event sourcing with strict replay. In Temporal, the commands emitted during replay "are compared with the existing Event History", and a mismatch is a non-deterministic error ([Temporal: Workflow Definition](https://docs.temporal.io/workflow-definition)). That error is a *retryable workflow-task failure*, not a workflow failure, so teams can "fix bugs and redeploy without losing Workflow state" ([temporalio/rules TMPRL1100](https://github.com/temporalio/rules/blob/main/rules/TMPRL1100.md)). Versioning has converged on two tools used together. In-flight runs are pinned to the build that started them: a pinned workflow "is guaranteed to complete on a single Worker Deployment Version" ([Temporal Worker Versioning](https://docs.temporal.io/production-deployment/worker-deployments/worker-versioning)). Patch markers handle runs that must move to new code. DBOS by default recovers only workflows whose source hash matches the running application ([DBOS upgrading workflows](https://docs.dbos.dev/python/tutorials/upgrading-workflows)). Every engine that publishes limits caps history. **Temporal warns at 10,240 events and terminates at 51,200** ([Temporal: Events](https://docs.temporal.io/workflow-execution/event)), and Step Functions fails an execution at 25,000 events ([AWS Step Functions quotas](https://docs.aws.amazon.com/step-functions/latest/dg/service-quotas.html)). Temporal's sticky execution caches the *live workflow state* in the worker, so a warm worker skips replay entirely ([Temporal: Sticky Execution](https://docs.temporal.io/sticky-execution)). Its shards are fenced by a RangeID, "a monotonically increasing generation number", and every history write is conditional on it ([temporalio/temporal history-service](https://github.com/temporalio/temporal/blob/main/docs/architecture/history-service.md)). These mechanisms still fail in production. Temporal issue #12300 reports transfer tasks lost for good after a shard reload on PostgreSQL, leaving workflows "permanently stuck in RUNNING" ([temporalio/temporal #12300](https://github.com/temporalio/temporal/issues/12300)).

On failure handling, the AWS Builders' Library and the Google SRE book give the same guidance. Retry at one layer only: five layers with three retries each multiply database load "243x" ([Brooker, Timeouts, retries and backoff with jitter](https://d1.awsstatic.com/builderslibrary/pdfs/timeouts-retries-and-backoff-with-jitter.pdf)). Cap retries at three attempts, with a per-client budget of about 10% of requests ([SRE book, Handling Overload](https://sre.google/sre-book/handling-overload/)). Add jitter "to all timers, periodic jobs, and other delayed work". For asynchronous systems, alarm on the *age* of queued messages, because dead-letter volume arrives "too late", and have "each component … protect itself from overload" ([Yanacek, Avoiding insurmountable queue backlogs](https://d1.awsstatic.com/builderslibrary/pdfs/avoiding-insurmountable-queue-backlogs.pdf)). Services should "prioritize end() requests over start() requests" ([Yanacek, Using load shedding](https://d1.awsstatic.com/builderslibrary/pdfs/using-load-shedding-to-avoid-overload.pdf)). The metastable-failure research explains why these rules matter. Bronson et al. place the root cause in "the sustaining feedback loop, rather than the trigger" ([HotOS'21](https://sigops.org/s/conferences/hotos/2021/papers/hotos21-s11-bronson.pdf)). Huang et al. found that **retry policy is the sustaining effect in more than 50% of 22 studied incidents**, and that at least 4 of 15 major AWS outages in a decade were metastable. They also showed that capping retries at two limits amplification to 3x ([OSDI'22](https://www.usenix.org/system/files/osdi22-huang-lexiang.pdf)). A WebFetch summary of that paper reported about 25%, but the full text says more than 50%, and this report uses the full-text figure.

At the data layer, a lease with a timeout does not by itself guarantee mutual exclusion. A paused holder can "go ahead" after expiry. The fix is a monotonic fencing token that storage checks on every write ([Kleppmann 2016](https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html)). River, a Postgres queue, had to add this guard to its job rescuer, because a stale snapshot could overwrite a job's new owner ([riverqueue/river PR #1373](https://github.com/riverqueue/river/pull/1373)). Postgres ships with `statement_timeout`, `lock_timeout`, `idle_in_transaction_session_timeout` and `transaction_timeout` **all disabled by default**, and its docs recommend setting them per session or role ([PostgreSQL client defaults](https://www.postgresql.org/docs/current/runtime-config-client.html)). One long transaction slowed a `SKIP LOCKED` queue's lock time about 15x and backed up 60,000 jobs in an hour ([brandur, Failure by MVCC](https://brandur.org/postgres-queues)). A transaction that issued `NOTIFY` takes a database-wide lock at commit that "effectively ensures that only a single COMMIT query can be handled at a time", and Recall.ai had three outages with that signature ([Recall.ai](https://www.recall.ai/blog/postgres-listen-notify-does-not-scale)). Recall.ai reports an upstream fix. The claim that it ships in PostgreSQL 19 is unverified. If the NOTIFY queue fills, "transactions calling NOTIFY will fail at commit" ([PostgreSQL NOTIFY](https://www.postgresql.org/docs/current/sql-notify.html)).

For testing, the leading teams search for failures rather than wait for them. FoundationDB runs "tens of thousands of simulations every night" ([FDB testing](https://apple.github.io/foundationdb/testing.html)). TigerBeetle's VOPR runs "24/7 on 1024 cores" ([TigerBeetle safety](https://docs.tigerbeetle.com/concepts/safety/)). WarpStream ran its whole SaaS, **including a real PostgreSQL**, under Antithesis. It found a data race in 233 seconds that "10s of thousands of hours" of CI had missed ([WarpStream](https://www.warpstream.com/blog/deterministic-simulation-testing-for-our-entire-saas)). Resonate, a durable-execution peer, tests in three layers: a Lean 4 specification, differential testing against an in-memory oracle with Porcupine linearizability checks, and seeded deterministic simulation run twice per seed with the logs diffed ([Resonate testing](https://docs.resonatehq.io/evaluate/how-resonate-is-tested)). AWS describes a portfolio of TLA+, P, Dafny, Kani, fault injection and deterministic simulation ([CACM 2025](https://dl.acm.org/doi/10.1145/3729175)). Datadog used TLA+ to find a delivery bug in Courier, the queue behind its Workflow Automation product ([Datadog](https://www.datadoghq.com/blog/engineering/formal-modeling-and-simulation/)).

For operations, the SRE Workbook pages on multi-window burn rates of 14.4x over 1 h and 6x over 6 h ([SRE Workbook](https://sre.google/workbook/alerting-on-slos/)). AWS deploys to a one-box stage that serves at most 10% of traffic, then rolls back automatically on metrics scoped to that box ([Liguori, Automating safe deployments](https://d1.awsstatic.com/builderslibrary/pdfs/automating-safe-hands-off-deployments-clareliguori.pdf)). AWS also avoids fallback paths that are "not exercised regularly" ([Gabrielson, Avoiding fallback](https://d1.awsstatic.com/builderslibrary/pdfs/avoiding-fallback-in-distributed-systems.pdf)). Gray failure is defined by "differential observability", and the proposed response is to move beyond heartbeats to multi-dimensional health ([Huang et al., HotOS'17](https://www.microsoft.com/en-us/research/wp-content/uploads/2017/06/paper-1.pdf)). Kubernetes sends SIGTERM and then SIGKILL after a 30 s default grace period, and it separates readiness from liveness ([Kubernetes pod lifecycle](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/)). The low bar for security is Temporal's default `noopAuthorizer`, which "allows every API request" ([Temporal security](https://docs.temporal.io/self-hosted-guide/security)). The yardstick is the OWASP API Top 10, led by broken object-level authorization ([OWASP API 2023](https://api-security.owasp.org/editions/2023/en/0x11-t10)).

## Harvest already clears the bar on determinism, disaster recovery and visibility

Harvest is a Rust library embedded in the host process. Postgres is its only required dependency and its only source of truth. There is no leader: every replica runs a worker, a scheduler and all background scanners, and they coordinate only through row claims, advisory locks and leases (`docs/runbooks/ha-deployment.md:7-32`; `docs/shipped-work.md:6138-6140`). The real single points of failure are each shard's Postgres primary and the operator-initiated regional failover (`docs/cross-region-dr.md:3-9`). Several of Harvest's mechanisms are rare in self-hosted engines, and the scorecard below credits them before turning to the gaps.

The execution-model and data-layer researchers each concluded that Harvest's per-execution safety is sound for a Postgres design. The execution-row lock, the `UNIQUE (workflow_exec_id, event_id)` constraint and the claim-held check together keep history from forking. The WASM sandbox also follows wasmtime's guidance, with fuel, a memory limiter, epoch wall-clock bounds and no filesystem or network imports (`wasm_activities.rs:63-318`; [wasmtime Config](https://docs.wasmtime.dev/api/wasmtime/struct.Config.html)).

The gaps concentrate where the engine's *defaults* meet concurrent actors. The project's own defect stream shows the pattern. More than 120 issues were closed or updated between 2026-09-10 and 2026-09-30. Many of them are races between concurrent dispatchers, sweepers and redrives: zombie terminal writes ([#1184](https://github.com/autumn-foundation/autumn-harvest/issues/1184)), a parent wedged RUNNING by pool contention ([#1459](https://github.com/autumn-foundation/autumn-harvest/issues/1459)), host-clock skew in deadlines ([#1389](https://github.com/autumn-foundation/autumn-harvest/issues/1389)), a quota ABBA deadlock ([#1228](https://github.com/autumn-foundation/autumn-harvest/issues/1228)), and payloads that corrupted replay ([#1253](https://github.com/autumn-foundation/autumn-harvest/issues/1253)). Each fix added a compare-and-swap, an ownership check or a TTL for one path. No single fencing abstraction covers them all, and that explains the gaps that remain.

## Over-claiming workers can trap the engine in a metastable loop

The most dangerous gap is in the default claim path. `poll_once` claims a row and dispatches it at once. The code states that "the worker can over-claim past `max_concurrent_*` (the semaphore gates execution, not claiming)" (`worker.rs:30209-30214`), and the poll loop re-claims immediately after every success (`worker.rs:29592-29625`). The claim stamps `started_at = NOW()` (`queue.rs:1113`), and start-to-close and heartbeat deadlines are measured from `started_at` (`timeout.rs:86-105`). **A task waiting behind a saturated worker's local semaphore therefore burns its timeout budget while never running**, and idle peers cannot claim it. When the timeout fires, the scanner appends `ActivityTimedOut` and calls `fail_task` (`timeout.rs:1452-1466`). That timeout also feeds the per-activity circuit breaker (`timeout.rs:1470-1494`). Once open, the breaker fails later dispatches with a **non-retryable** `CircuitOpen` (`circuit_breaker.rs:12-15`). The opt-in Redis dispatch path already gates claims on free permits, and its comment describes the problem exactly (`worker.rs:26548-26556`). Only the default Postgres path lacks the gate. This is the "cascading brownout" pattern from work outliving its lease ([Yanacek](https://d1.awsstatic.com/builderslibrary/pdfs/avoiding-insurmountable-queue-backlogs.pdf)). It is also Bronson's warning in concrete form: a structure that favours intake over completion encodes the wrong priority under overload ([HotOS'21](https://sigops.org/s/conferences/hotos/2021/papers/hotos21-s11-bronson.pdf)).

The second Critical item makes the first worse. **Harvest configures no deadpool `Timeouts`, so "every `pool.get().await` is an unbounded wait"** (`worker.rs:5920-5921`; `codec_rotation.rs:1372-1374`). The single-shard path deliberately keeps that unbounded acquire (`worker.rs:5956-6010`). Only multi-shard workers bound it, at max(poll_interval, 5 s). No engine connection sets `statement_timeout`, `lock_timeout` or `idle_in_transaction_session_timeout`. The only `SET LOCAL` timeouts are in partition and replication maintenance (`partition.rs:1014, 4250`; `replication.rs:1113, 1794`). Pool contention has already wedged work twice ([#1459](https://github.com/autumn-foundation/autumn-harvest/issues/1459), [#1426](https://github.com/autumn-foundation/autumn-harvest/issues/1426)). A hung connection also pins `xmin`, which is the brandur queue-bloat mechanism. The heartbeat flusher competes for the same pool every second and only logs on failure (`heartbeat.rs:53-93`). A missed flush therefore lets `COALESCE(last_heartbeat_at, started_at) + heartbeat_timeout < NOW()` fire, which terminally times out an activity that was healthy.

Several amplifiers act on that loop. **Retry jitter defaults to `None`** (`policy.rs:35-42, 162, 186`), even though Full, Equal and Decorrelated jitter are implemented and seeded deterministically (`worker.rs:5024-5042`). Activities that fail together therefore retry together at 1 s, 2 s and 4 s. The no-policy fallback is a fixed 1 s retry (`worker.rs:5091-5100`). The ND-block and panic backoffs are unjittered, and schedule fire jitter defaults to zero (`policy.rs:878-895`). No retry budget or token-bucket throttle exists anywhere. The only aggregate brake is the opt-in breaker, whose modal behaviour Brooker cautions against ([Brooker 2022](https://brooker.co.za/blog/2022/02/28/retries.html)). Nothing sheds load automatically. The admission gate is a manual operator switch, and it correctly exempts continuations (`admission_gate.rs:1-45`). When an operator turns the gate on, the start API maps `AdmissionBlocked` to 503 (`api.rs:19148-19198`). Backlog depth or age never turns the gate on by itself. Background scan load grows with fleet size. Every worker runs the timeout checker per shard every 500 ms with no jitter and no leader election, and the start-to-close and heartbeat scans have no `LIMIT` (`worker.rs:81, 28302-28308`; `timeout.rs:100-105, 488-491, 5186-5189`). About ten metric samplers run on the same interval, though whether each one queries the database was not checked. **Adding workers to clear a backlog therefore adds database load**, which Huang et al. classify as capacity-degradation amplification. Finally, every history append and enqueue issues `pg_notify` inside its write transaction on one global channel, and errors propagate (`store.rs:237-245`; `notify.rs:229-245`). This puts the NOTIFY commit lock and the queue-full failure on the hot write path.

Other defaults leave work unbounded. Activities have **no default start-to-close or heartbeat timeout** (`builder.rs:3938`; `info.rs:1371-1372`), so a hung activity on a live worker runs forever. The stuck-running backstop covers only workflow tasks (`poison_pill.rs:125-145`). Activity timeouts are terminal for the task, but the March 2026 design draft says start-to-close is "retried per policy" (`docs/autumn-workflow-architecture.md:1127`), and Temporal retries them. No claim-time check stops work whose parent run's deadline has already passed. Workflow tasks of running executions get no default priority over the first tasks of new starts, so the end-before-start rule applies only when an operator pulls the manual gate.

None of these loops has been reproduced, and none of the 30 open GitHub issues on 2026-09-30 tracks overload or metastability. The mitigations are real. The default of three attempts keeps a stable region, and the breaker excludes schedule-to-start timeouts. But **the protective toolbox is opt-in, and the amplifiers are on by default**, which is the opposite of the ordering the literature recommends.

## Stale owners can still write activity results

Harvest fences workflow-task terminal writes. It does not fence activity writes. `finalize_activity_completion` checks that the activity is still pending in history and that the task row is `RUNNING` (`worker.rs:13043-13083`). `queue::complete_task` then filters only on `id` and `state = 'RUNNING'` (`queue.rs:2476-2505`, confirmed at HEAD). `fail_task` accepts any PENDING or RUNNING row "regardless of `worker_id`" (`queue.rs:2517-2545`), and `record_heartbeat` also filters only on `id` and state (`queue.rs:2853-2878`). Reclaim is a normal event. Heartbeat and start-to-close timeouts, and orphan reclaim after worker-liveness loss (`poison_pill.rs:103-114`), all requeue a task that worker B can then claim. If worker A then finishes, **A's result becomes the activity outcome, B's own completion fails with `NotFound`, and A's heartbeats refresh B's liveness and overwrite B's checkpoint**. A heartbeat that hits a non-running row only logs a warning and does not cancel the activity (`heartbeat.rs:74-90`), so a fenced-off attempt keeps working. History cannot fork, but ownership semantics break in exactly the Kleppmann and River class of bug. No test targets a late zombie completion after reclaim.

Two smaller fencing holes follow the same pattern. The #1184 guard `claim_still_held_for_update` checks `worker_id` and `crash_strikes` but not `attempt` (`queue.rs:4181-4188`, confirmed). The code's own comments at the workflow-task timeout reset say that `requeue_stuck_task` leaves `crash_strikes` unchanged, so "this reset must also check `attempt`" (`worker.rs:31260-31277`). A same-worker re-claim therefore lets a stale dispatcher pass the guard. Separately, the per-task heartbeat is stamped with the host clock `Utc::now()` (`queue.rs:2866`) but judged against the database's `NOW()` (`timeout.rs:86-91`). Host-to-database skew therefore produces false heartbeat timeouts or hides real ones, the same bug class #1389 fixed for retry deadlines. CockroachDB treats bounded skew as a hard invariant and shuts a node down when it is exceeded ([CockroachDB FAQ](https://docs.cockroachlabs.com/docs/stable/operational-faqs)). Harvest can avoid the issue by stamping `NOW()` in SQL.

The remaining data-layer gaps are about keeping the database healthy. Only 2 of 113 migrations set `lock_timeout`, and none actually runs `CREATE INDEX CONCURRENTLY`, although `migrate.rs` supports non-transactional migrations. Migration `20260915231809` drops and rebuilds a unique index on `harvest_workflow_executions` inside its transaction with no `lock_timeout` (`up.sql:48-54`). That blocks reads and writes on the executions table for the duration of the build. The migration hygiene tests check prefixes, not lock safety. `harvest_task_queue` carries about 15 indexes and has no autovacuum or fillfactor tuning. Terminal task rows are never deleted while history retention is off, which is the default (`retention.rs:484-495`). The queue's heap and vacuum load therefore grow without bound. Lock ordering is documented per path and not globally, and there is no generic retry on `40P01` or `40001`. DR fencing is strong but opt-in per process, so admin scripts and unfenced workers can still write after a failover (`docs/cross-region-dr.md:241-276`). The unwired `claim_task_batched` lacks the DR fence splice (`queue.rs:7186-7215`), which becomes a live bypass if issue #1340 makes it the default claim.

## The live executor guesses when a workflow has suspended

The strict and canary replayers check for unconsumed history. The production worker does not appear to. `history_has_unconsumed_events()` is called at `executor.rs:1182, 1312, 1482, 1578` in the strict and canary executors, and it is used for terminal queries. The production `drive_workflow` (`executor.rs:1890`) maps `Ok(Ok(output))` to `Completed` and a timeout to `Suspended` with no such check, and `worker.rs` never calls it. Yet the replay matcher's comments depend on the guard. They say `executor.rs` "fails the workflow if `history_has_unconsumed_events()`", and that a stray event is ND-blocked "instead of letting it park forever" (`replay.rs:4150-4158, 4268-4280`). Suppose a deploy deletes the last two activity calls of an in-flight workflow. The new code would return `Ok` while `ActivityScheduled` rows are still unmatched, and the worker would persist `WorkflowCompleted`. The pinning tests exercise only the strict replayer (`replayer_tests.rs:9838`). **This is a High correctness gap, pending a worker-path reproduction.** The offline #798 drift gate catches it only if operators run that gate.

Suspension is inferred from wall-clock time. `SUSPENSION_TIMEOUT` is **100 ms**: "if the workflow hasn't completed within this window, it's blocked … (suspended)" (`executor.rs:89-91`, confirmed). Every suspending decision therefore costs at least 100 ms while it holds a slot and a connection. Whether a cycle suspends depends on scheduling, not on workflow semantics. The codebase names the hazard: a dispatch "still mid-flight on some other I/O" when the window elapses suspends with zero commands and is failed terminally (`worker.rs:17043-17053`). The hot-swap trampoline hit the same failure (`docs/changelog.d/pr-967-hot-code-swap.md:127-137`). Temporal's dispatcher runs until every coroutine is blocked. It uses a 1 s timer only as a deadlock *detector* that fails the task ([Temporal forum](https://community.temporal.io/t/potential-deadlock-detected-workflow-goroutine-root-didnt-yield-for-over-a-second/2414)).

Replay cost grows quadratically, and nothing caps it by default. Each cycle re-runs the handler from the top with the full history (`worker.rs:20680-20684`). The workflow cache stores events, not live state (`cache.rs:31-45`), and sticky routing is off by default (`sticky_timeout: ZERO`, `builder.rs:3933`). The repo's own profile concludes that run cost stays O(n²) even with a delta cache (`docs/performance-sqlite-runtime-drive.md:440-457`). There is no default history hard cap (`max_workflow_history_events: None`, `builder.rs:198`), only an advisory `should_continue_as_new` at 10,000 events, and there is no byte cap outside tenant quotas. A runaway signal loop therefore grows `harvest_events` and replay CPU without bound. Build pinning fails open: the claim predicate includes `OR $3 = ''`, "Legacy worker (empty build_id) can claim anything" (`build_routing.rs:28`; `queue.rs:1031`), and `build_id` defaults to empty. One misconfigured worker can therefore claim runs pinned to any build. History has no decision-boundary event recording which build produced each decision, which weakens incident attribution.

These gaps interact. A timing-dependent partial suspension produces commands that differ from history. The divergences that end in a completion or a park, rather than a positional mismatch, are the ones the missing drift guard lets through. A deterministic readiness check is also a precondition for any resident-state cache, because a cached future has to be resumed deterministically.

## The resilience evidence has never actually run

The test suite is large: about 8,400 test attributes in the core crate and a 21-shard Docker-Postgres CI matrix. It also has distinctive determinism tooling. The components built to find *unknown* faults, however, are present but not wired. **`.github/workflows/chaos.yml` fails YAML parsing** at line 57, column 72 (`ScannerError: mapping values are not allowed here`, reproduced at HEAD). The nightly job has zero scheduled runs. Open [PR #1773](https://github.com/autumn-foundation/autumn-harvest/pull/1773) confirms that the suite "never ran" and that it has not been verified to compile or pass. Meanwhile `ci_run_coverage.rs:199-202` allowlists the chaos suite with the reason that it "DOES run in CI", which is false. That suite holds the only crash-convergence oracle and the scheduler exactly-once reproducers for #350. The loom workflow is manual-only and has **zero runs ever**, and its four models cover two modules. Fuzzing runs only on manual dispatch, 30 s per target, and no target drives replay. The `ci_run_coverage` allowlist has 64 entries, and about 60 carry "not yet wired" reasons. They include `scheduler_ha_tests`, `poison_pill_tests`, `signal_tests`, `replayer_integration_tests` and the plugin's `erase_payloads_integration`, which exercises sanctioned append-only exception #1 (`ci_run_coverage.rs:210-314`). The guard's own header cites a suite in which 6 of 9 tests never ran and 3 real bugs hid.

Beyond the wiring failures, Harvest has no tool that *searches* interleavings. The chaos seed fixes the fault plan but not the thread or transaction schedule (`chaos_tests.rs:1425`). The sweep covers one injection point with a no-op workload. The simulators are single-workflow SDK test aids. The project's own evaluation rejected Turmoil, madsim and Shuttle because "none … can model a Postgres server" (`docs/testing/concurrency-model-checking.md:7-14`). That is true of those tools, but WarpStream shows a hypervisor approach works with real Postgres, and Resonate shows an oracle-store approach. No `verus!`, `kani::`, `.tla` or P file exists, so the "spec-first" stance has no artifact behind it. No test crashes a process, restarts Postgres, partitions the network or exercises an ambiguous commit. The chaos KILL fault is an in-process task panic (`chaos.rs:61-63`). The append-only invariant in CLAUDE.md is enforced by a source grep (`lifecycle.rs:597-614`). The grep misses a third in-place writer of the `cohort` column (`partition.rs:3783`) and any raw SQL built another way, and no database trigger backs it. No coverage tooling exists, so the 85–90% coverage goal is unmeasured. CI flakiness remains unexplained, including recurring `quota_enforcement_tests` hangs and a source-completion hang seen 8 times across 6 branches. Deterministic replay of failures would remove that class by construction.

## Operations signals are rich, but readiness, rollback and authorization lag

Harvest's telemetry covers Temporal's core operator signals: about 80 `harvest.*` metrics, a 30-plus rule alert pack linked to runbooks, and a 48-panel dashboard. It does not cover saturation of its own critical dependency. **No metric reports database pool usage or wait, query latency or poller count**, even though Temporal exposes poller counts ([Temporal SDK metrics](https://docs.temporal.io/references/sdk-metrics)). The sticky-cache hit rate is available: `harvest.workflow.cache_hit` and `harvest.workflow.cache_miss` (`telemetry.rs:545-558`) are emitted on every prepared workflow task (`worker.rs:20441-20449`). The alerts use static 5-minute thresholds and are labelled "not universal SLOs". No SLO definitions or burn-rate rules exist. Worker health is binary and heartbeat-based (`workers.rs:137-150`), which is the "singular failure detection" the gray-failure paper argues against.

Deployment and shutdown have gaps at the edges. `/health` returns 200 even when the runtime has not started, unless shard readiness is opted into (`api.rs:40265-40273`). There is no liveness/readiness split, no draining state and no Kubernetes probe guidance. The default `shutdown_timeout` is 30 s (`builder.rs:3931`), the same as Kubernetes' default grace period. When the drain times out, the worker only logs "some tasks may still be running" (`worker.rs:30728-30799`) and does not release its claims. Recovery then waits for lease expiry, and open issue [#1552](https://github.com/autumn-foundation/autumn-harvest/issues/1552) reports a heartbeat task that detaches under cancellation and holds its connection indefinitely. The build ramp aborts with one command, but nothing aborts it automatically on metrics, and `build_id` is not a metric label. The AWS one-box pattern is therefore out of reach.

Security is "safe admin, open data plane". Admin routes fail closed outside `dev`. But "any caller can reach the ungated mutating endpoints without credentials" unless the embedder adds middleware (`docs/security-posture.md:383`). That exposes start, signal and cancel for every workflow, although Temporal's default is worse. Authorization has two levels, read and mutate. There is no tenant or object-level check, and "a compromised `mutate` token can mint replacement tokens" (`security-posture.md:275, 293-298`), which falls under OWASP API1 and API5. Payloads are stored as plain JSON, and no production AEAD codec ships, only `IdentityCodec` (`payload_codec.rs:642`). The management API has no rate limiting. On the supply chain, `cargo deny` runs only when code changes, actions are pinned by mutable tags, Dependabot is not configured, and releases have no SBOM, signature or provenance (`release.yml`).

Some scanner hot paths use a UUID round-trip `expect`, and the retention lease `Drop` guard can panic on a poisoned lock, which would abort the process.

## Conclusion

Harvest does not lack resilience mechanisms. It has more of them than most self-hosted engines. The weakness is that its safety depends on configuration. The AWS argument against fallback applies directly. A breaker, throttle, slot tuner, sticky cache, history cap or DR fence that a default deployment never turns on is a code path that is "not exercised regularly", while the amplifiers (unjittered retries, over-claiming, unbounded waits, per-replica scans) are on by default. Two changes in stance would close most of the gap. The first is one claim-epoch abstraction, `(task_id, worker_id, attempt)` checked in the same SQL statement, used by every write that asserts ownership, in place of guards added per issue. The second is to flip defaults so the protections are on and operators opt out. The recent defect stream, dominated by races between leaderless background actors, is what that missing abstraction predicts.

The assurance gap changes how to read the project's existing claims. Workflow files that do not parse and allowlists that assert coverage that does not exist mean that part of the believed safety net has never been observed working. The first fixes are cheap: parse the YAML, wire the suites, run loom. They will likely surface failures before any new test is written. Treat every finding in this report as static analysis. The drift-guard and zombie-completion gaps in particular need a reproduction test before the fix, and the three metastable loops need a database-backed load test to confirm their thresholds.
