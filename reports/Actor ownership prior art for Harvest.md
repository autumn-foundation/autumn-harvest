# Borrow the owner, keep Postgres as truth

The owner-per-key idea transfers to self-hosted Harvest, but only in one form. Every system surveyed that delivers a real single-writer guarantee enforces it **at the storage commit, not through membership or a heartbeat**. Temporal stamps a `RangeID` on every write. Golem added a per-oplog epoch inside the append transaction after a chaos run and code review showed that leases alone were not enough. Cloudflare's storage layer refuses a stale Durable Object's writes even while its code keeps running. Every system that keeps an embedded store next to the owner (Restate's RocksDB, Durable Objects' SQLite, Netherite's FASTER, Rivet's per-actor SQLite) treats it as **a cache or materialization over a replicated log**. The systems that make a local SQLite file authoritative either accept a loss window (Litestream, LiteFS) or become a quorum database (dqlite, Durable Objects' 3-of-5 followers). For Harvest this means **stage 1 is sound and attacks the measured bottleneck**, provided the owner epoch is checked inside each decision's Postgres transaction. On the benchmark shape, 4 of the 7 claims per workflow are workflow-task claims that an owner removes. **Stage 2 should start as the existing in-memory cache made durable by ownership, not as a SQLite file.** Harvest's own snapshot spike found replay cheap, and a disk copy adds PII-erasure and key-rotation hazards. Because Postgres never trims history, "snapshot plus log tail" collapses to "local copy plus a per-execution delta". **Stage 3 as written cannot be atomic**: a Postgres commit and a local SQLite commit are two stores, which is exactly Golem's in-doubt-commit problem. It should become state-change events committed with history and projected into a table or an optional SQLite file. Harvest keeps two structural advantages that every per-key system lacks: same-database exactly-once for cross-run effects, and indexed global listing in Postgres. The design must not trade either away.

## Every safe owner-per-key system fences at the storage commit

The surveyed systems split cleanly by where the single-writer guarantee lives. **Temporal** fixes its history-shard count at cluster creation. A Ringpop membership ring decides which host should own each shard ([Temporal history-service.md](https://github.com/temporalio/temporal/blob/main/docs/architecture/history-service.md)). The hard guarantee is the `RangeID`: each acquisition increments it by a compare-and-swap on the shard row, and every create, update and task write carries it, so a host holding an old range gets `ShardOwnershipLostError` and unloads the shard instead of retrying ([context_impl.go](https://github.com/temporalio/temporal/blob/main/service/history/shard/context_impl.go)). One subtle rule is worth copying exactly. `renewRangeLocked` **drains in-flight requests before bumping the range**, because "requests are conditioned on rangeID, if rangeID is updated before draining them, those requests could fail" ([context_impl.go](https://github.com/temporalio/temporal/blob/main/service/history/shard/context_impl.go)). Temporal sizes this at about **one history process per 500 shards** and has run with 1 to 128K shards ([Temporal Server docs](https://docs.temporal.io/temporal-service/temporal-server)).

**Golem** is the cautionary tale of building the lease first and the fence second. In an August 2026 chaos run on golem-dev, **460 of 1024 shards had no owner for 43 minutes and "the cluster never repaired itself"**. Review of the proposed fix found that writes already past their ownership check could still land after a drain ([PR #3766](https://github.com/golemcloud/golem/pull/3766)). The PR was closed in favour of a redesign. PR #3845 states the lesson plainly: a lease bounds how long a lost shard is served, but it cannot stop a paused or partitioned executor from finishing a write it already started. Before the fix, only an index primary key decided the winner, and it "rejected whichever executor wrote second, often the rightful owner". The fix stores a monotonic writer epoch per oplog and asserts it in the same transaction as the insert. In Postgres this is a `SELECT ... FOR UPDATE`. A refused write raises `OplogFenced`, and the executor **relinquishes the agent rather than restarting it**, because a restart would reopen the oplog at the stale epoch ([PR #3845](https://github.com/golemcloud/golem/pull/3845)). The fence still covers only the oplog. KV records, status blobs and blob payloads stay unfenced, so a stale status write can be visible until the next change ([PR #3845](https://github.com/golemcloud/golem/pull/3845)). The code shipped in Golem 1.6, released on the research date, so it has no production track record yet ([Golem 1.6 post](https://golem.cloud/blog/golem-1-6-agents-tools-and-artifacts/)).

**Cloudflare Durable Objects** promise "exactly one instance in the whole world" per name ([Cloudflare blog, 2020](https://blog.cloudflare.com/introducing-workers-durable-objects/)). The documented reality is narrower. Uniqueness is checked when an event starts and when storage is touched. A stale instance that runs long without storage access "may never detect this" ([Known issues](https://developers.cloudflare.com/durable-objects/platform/known-issues/)). The real fence is in the Storage Relay Service. A new instance cannot start until the old one is known dead. If the old host is unreachable, **a quorum of 3 of the 5 WAL followers tells it to stop confirming writes** ([Cloudflare blog, 2024](https://blog.cloudflare.com/sqlite-in-durable-objects/)). The quorum that acknowledges writes is the same quorum that fences an old writer. So the guarantee is "at most one instance commits", not "at most one instance runs".

**Restate** fences at two layers. Log reconfiguration seals the active segment so "a quorum of replicas refuses further appends". A new processor leader then takes the next epoch from a strictly monotonic control-plane sequence and appends an `AnnounceLeader` record. Replicas drop any self-proposal stamped with a lower epoch ([Restate architecture](https://docs.restate.dev/references/architecture); [dedup.rs](https://raw.githubusercontent.com/restatedev/restate/main/crates/worker/src/partition/processor/dedup.rs)). This is a **read-side filter**, needed because Bifrost appends are not conditional on the processor epoch. Restate's sharpest 2026 bug shows what that costs. In issue #4566, awakeable signals that ingress had **acknowledged with HTTP 202 were silently dropped** when a leadership change landed between the ack and the apply. The fix acknowledges only after the state machine applies the command ([Issue #4566](https://github.com/restatedev/restate/issues/4566)).

**Azure Netherite** keeps each partition on at most one host with storage leases ([PVLDB 2022](https://www.vldb.org/pvldb/vol15/p1591-burckhardt.pdf)), and the readable text does not say whether every log append is conditioned on the lease. **Akka** and **Orleans** show the weaker alternative. Akka's single writer per `persistenceId` rests on membership and the Split Brain Resolver. Without correct downing, "two instances of a persistent actor with the same `persistenceId` are running and writing concurrently" ([Akka SBR](https://doc.akka.io/libraries/akka-core/current/split-brain-resolver.html)). Its journal replay filter (`repair-by-discard-old`) exists to clean up after that ([Akka Persistence](https://doc.akka.io/libraries/akka-core/current/typed/persistence.html)). Orleans' default directory "allows occasional duplicate activations during cluster instability". A strongly consistent directory is still in preview in Orleans 10 ([Orleans grain directory](https://learn.microsoft.com/en-us/dotnet/orleans/host/grain-directory)), and v10.2 shipped a run of handoff and stale-entry fixes ([v10.2.0 notes mirror](https://newreleases.io/project/github/dotnet/orleans/release/v10.2.0)). **Rivet** says its actors are "single-writer by design" with a dual-write guard "enforced structurally", but it publishes no mechanism ([Rivet blog](https://rivet.dev/blog/2026-07-31-how-we-built-the-first-zero-disk-s3-tiered-storage-engine-for-sqlite/)). The SQLite replicators fence even less. Litestream's v0.5.8 lease is a conditional write on `lock.json` with a `generation` counter, and it serializes *replicators*. The docs do not say it stops a deposed host's application from committing locally ([Litestream S3 advanced](https://litestream.io/guides/s3-advanced/)). LiteFS has no fencing token. A former primary detects divergence by a rolling checksum and re-snapshots, which **discards writes it never replicated** ([LiteFS ARCHITECTURE.md](https://github.com/superfly/litefs/blob/main/docs/ARCHITECTURE.md)).

The pattern is unambiguous, and it maps onto machinery Harvest already has. The DR write-authority fence takes the shard generation row `FOR SHARE` on every append, and the epoch bump takes it exclusively, which the docs call "a commit-order barrier, not a racy read" ([cross-region-dr.md:294-320](../docs/cross-region-dr.md); [store.rs:1006-1009](../autumn-harvest/src/store.rs); [queue.rs:2019](../autumn-harvest/src/queue.rs)). The scanner lease supplies the acquire SQL with holder, `clock_timestamp()` TTL and an epoch that counts holder changes. It is explicitly "a load control, not a fence" ([scanner_lease.rs:1-35, 440-475](../autumn-harvest/src/scanner_lease.rs)). Stage 1 is the combination of the two. Nothing in the repository proposes it today. The nearest idea, eager activity dispatch, was deferred because it "changes claim ownership and needs its own fence review" ([docs/design/DESIGN-claim-concurrency.md:72-94](../docs/design/DESIGN-claim-concurrency.md)).

## Local embedded stores survive only as caches over a replicated log

The second dimension, durable truth, divides the field the same way. Restate's partition store "can always be rebuilt from the log" and "is not a second source of truth". Snapshots to S3 exist so the log can be trimmed and a new leader replays only the suffix ([Restate architecture](https://docs.restate.dev/references/architecture)). Cloudflare runs SQLite in WAL mode with a VFS hook and forwards frames to five followers. It confirms a write after three acknowledge, and batches uploads to object storage every 10 s or 16 MB ([Cloudflare blog, 2024](https://blog.cloudflare.com/sqlite-in-durable-objects/)). The local file is a materialization of a replicated log, not the durable artifact. Rivet keeps 4 KiB SQLite pages in a replicated hot tier on FoundationDB, Postgres or RocksDB. It stays off S3 on the write path because PUTs take 30 to 45 ms, and it insists actors "must be able to start on any machine with no data on it" ([Rivet blog](https://rivet.dev/blog/2026-07-31-how-we-built-the-first-zero-disk-s3-tiered-storage-engine-for-sqlite/)). Netherite event-sources each partition into a FASTER commit log with checkpoints, and FasterKV "acts as a LRU cache for instance states" with lazy instant recovery ([PVLDB 2022](https://www.vldb.org/pvldb/vol15/p1591-burckhardt.pdf)).

The SQLite replication systems confirm the rule from the other side. Litestream ships WAL asynchronously every second, so a crash loses the latest window, and synchronous replication is only "on the roadmap" ([Litestream tips](https://litestream.io/tips/)). LiteFS's loss window is "typically subsecond", and Fly.io now gives it "limited updates" with no significant planned work ([LiteFS ARCHITECTURE.md](https://github.com/superfly/litefs/blob/main/docs/ARCHITECTURE.md); [Fly community](https://community.fly.io/t/what-is-the-status-of-litefs/23883)). dqlite is synchronous, but it holds the SQLite write lock across a Raft round trip ([Canonical dqlite](https://canonical.com/dqlite/docs/explanation/replication)). rqlite replicates statements and so misses non-determinism in defaults, triggers, generated columns and `ORDER BY RANDOM()` ([rqlite docs](https://rqlite.io/docs/api/non-deterministic/)). mvSQLite gets real multi-writer safety by moving pages onto FoundationDB, so the file is no longer local ([mvSQLite README](https://github.com/losfair/mvsqlite)). Turso now "strongly discourage[s]" embedded replicas in favour of local read-write plus push/pull sync, which is a reconciliation model, not a fenced log ([Turso Rust SDK](https://docs.turso.tech/sdk/rust)). In short, **an authoritative local SQLite file costs either an RPO above zero or a per-write quorum**. Harvest already has a fenced, RPO-zero log in Postgres. Rebuilding dqlite or the Storage Relay Service inside Harvest would buy nothing that log does not already give.

The per-key state models differ more than the durability models, and that difference matters most for Harvest's keyed entity. Restate's journal is per invocation. A Virtual Object is a K/V map plus a series of short journals, and state updates "are recorded alongside execution steps for consistency" ([Restate key concepts](https://docs.restate.dev/foundations/key-concepts)). Harvest's entity is one long workflow. Each op is a `harvest.entity.op` signal, state is the workflow input rebuilt by replay, and the history is bounded by continue-as-new checkpoints that cost one `SideEffectRecorded` event per op ([ADR 0006:29-41, 64-87](../docs/adr/0006-keyed-entity.md); [entity.rs:90, 355-402](../autumn-harvest/src/entity.rs)). Golem records every host call in an oplog. Its per-agent SQLite is *not* journaled at the SQL level: a file-backed database is restored by replay, and since October 2026 by reflink filesystem snapshots uploaded in restic format and confirmed by a `SnapshotConfirmed` oplog entry ([PR #4061](https://github.com/golemcloud/golem/pull/4061); [PR #4019](https://github.com/golemcloud/golem/pull/4019)). Rivet batches `c.state` mutations into one write every second by default, a weaker default than commit-before-ack ([Rivet persistence](https://rivet.dev/docs/actors/persistence)). Durable Objects make storage feel synchronous with **input gates**, which hold new events during a storage operation. They pair them with **output gates**, which hold every response and outgoing fetch until the writes before it are durable, and restart the object if a write fails ([Cloudflare blog, 2021](https://blog.cloudflare.com/durable-objects-easy-fast-correct-choose-three/)).

Two of these lessons are already true in Harvest by construction, and recognizing that keeps the design small. A Harvest decision has no external effect before commit. The whole outcome commits in one transaction ending in `DecisionCommitted` ([worker.rs:24199-24250](../autumn-harvest/src/worker.rs); [decision-boundaries.md:8-25](../docs/decision-boundaries.md)), and the event notify is staged and sent only after commit ([notify.rs:1-30](../autumn-harvest/src/notify.rs)). That is a Durable Objects output gate. Strict deterministic replay plays the role of "crash and rebuild from committed state".

## Cross-key exactly-once and global listing are where Postgres already wins

Exactly-once across owners always reduces to the same recipe: an outbox written atomically with the sender's step, at-least-once relay, and a receiver-side high-water mark committed atomically with consumption. Netherite stores cross-partition messages in an outbox, sends them only after the producing event persists, and deduplicates with "a deduplication vector, which records the position of the last-processed incoming message from each remote partition" ([PVLDB 2022](https://www.vldb.org/pvldb/vol15/p1591-burckhardt.pdf)). Restate writes a cross-partition call to the origin partition's log in the same append as the caller's journal step. A shuffle delivers it, and the destination drops any record whose `(ProducerId, sequence)` is at or below the stored watermark ([Restate architecture](https://docs.restate.dev/references/architecture); [dedup.rs](https://raw.githubusercontent.com/restatedev/restate/main/crates/worker/src/partition/processor/dedup.rs)). Temporal's transfer queue is the same outbox between history and matching ([history-service.md](https://github.com/temporalio/temporal/blob/main/docs/architecture/history-service.md)). Golem derives idempotency keys from oplog position, and external HTTP is exactly-once only if the remote honours them ([Golem: What's This Golem Cloud Thing About?](https://golem.cloud/blog/whats-this-golem-cloud-thing-about/)). Durable Objects document no delivery guarantee for DO-to-DO RPC. Errors carry a `.retryable` flag, and a retry is safe "only if the requests are idempotent" ([DO error handling](https://developers.cloudflare.com/durable-objects/best-practices/error-handling/)). Akka defaults to at-most-once ([Akka delivery reliability](https://doc.akka.io/libraries/akka-core/current/general/message-delivery-reliability.html)).

Harvest does better than all of them inside a physical shard, because the sender and receiver share one Postgres database. A child completion appends `ChildWorkflowCompleted` to the parent and wakes it in the child's own transaction ([worker.rs:15560-15584](../autumn-harvest/src/worker.rs)). Signal-with-start is "one shard-local transaction" ([architecture.md:527-533](../docs/architecture.md)). A same-shard completion trigger starts its target "within the same database transaction that persists the source" ([completion-triggers.md:10-35](../docs/completion-triggers.md)). Only cross-shard paths use an outbox with dedupe, and "the parent's decision transaction stays shard-local. Always." ([sharding.md:576-597](../docs/sharding.md)). Netherite and Restate built the shuffle because their partitions do not share a transactional store. **The owner design must preserve this by committing every decision in the execution's physical Postgres database**, so ownership changes who decides, never where the commit happens. The Golem RDBMS story shows the cost of losing it. When the user's database and the oplog are separate stores, a commit followed by a crash forces transaction-ID introspection or a `golem_transactions` marker table to decide whether to replay ([Golem issue #1514](https://github.com/golemcloud/golem/issues/1514)).

Listing is the sharpest contrast. No owner-per-key system has a good global index. Durable Objects offer no in-Worker enumeration, and Cloudflare tells users to keep their own index in a parent object or D1 ([Rules of Durable Objects](https://developers.cloudflare.com/durable-objects/best-practices/rules-of-durable-objects/)). Golem says enumeration "is a slow operation and should not be used as part of the application logic" ([Golem listing docs](https://learn.golem.cloud/how-to-guides/common/golem-list-and-filter-agents)). Restate runs DataFusion leaf scans directly against live partition stores on the transactional nodes. In August 2026 one periodic query "used roughly 97% of one cell's read bandwidth and measurably affected invocation processing", and the proposed fix is query-only replicas with stale reads ([Restate issue #5170](https://github.com/restatedev/restate/issues/5170)). Temporal accepts an asynchronous, eventually consistent visibility store ([Temporal visibility](https://docs.temporal.io/visibility)). Harvest's listing is an indexed Postgres query over the same rows the decisions commit. **Every stage must keep it that way**: list, search and describe must read Postgres, never an owner's cache.

Failover cost is where the published numbers are thinnest, and the ones that exist are sobering. Akka's defaults give "around 45 seconds" for a sharded entity to fail over, or about 25 s tuned ([Akka SBR](https://doc.akka.io/libraries/akka-core/current/split-brain-resolver.html)). Restate fixed a bug in June 2026 that could leave a partition leaderless "for up to 30secs" ([Issue #4937](https://github.com/restatedev/restate/issues/4937)). It also has an open bug where, after a failed segment seal, leaders still accept appends while the applied LSN freezes and invocations hang ([Issue #5033](https://github.com/restatedev/restate/issues/5033)). In Netherite, a planned scale-out moved 24 of 32 partitions on 4 nodes, and throughput returned to peak about 7 s later ([arXiv 2103.00033](https://arxiv.org/html/2103.00033v1)). Durable Objects never relocate, so a regional incident hits every key homed there ([DO data location](https://developers.cloudflare.com/durable-objects/reference/data-location/)). Harvest's present failover is already in this range: after a crash, each pinned execution waits up to one 5 s sticky window ([sticky-routing.md:83-90](../docs/sticky-routing.md)). Rebuilding state on the new owner is cheap: a cold replay costs 0.13 / 0.61 / 1.25 ms at 1k / 5k / 10k events ([sticky-routing.md:113-117](../docs/sticky-routing.md)). Harvest therefore starts with the cheapest part of failover, warm-up, already solved. The risk is concentrated in the lease and fence protocol, which is exactly where Restate's and Golem's 2026 bugs sit.

## The staged design holds, with four refinements

The three stages survive the prior art, with four refinements. Fence inside the commit. Keep the owner's cache in memory until cold-hit data demands disk. Drop the snapshot, because Postgres never trims. Turn stage 3 into state-change events with projections. One vocabulary fix comes first: in this codebase a "shard" is a separate Postgres database ([sharding.md:5](../docs/sharding.md)). The proposal's logical ownership unit needs another name, for example "decision partition", or every doc and metric will be ambiguous.

### Stage 1: a fenced decision owner per logical partition

The measured case for stage 1 is strong. Throughput follows `1 / (claims per workflow × claim latency)` with **7 claims per 3-activity workflow**, and claim-loop occupancy was 0.91 to 0.99 in all 72 assay runs while only 2 to 4 of 32 pool connections were in use ([assay 0014:199-216](../docs/assays/0014-harvest-vs-temporal-0.7.0-depth-sweep.md)). Four of those claims are workflow-task claims. Mean claim time rises from about 4 ms with one loop to 9 ms with four. That gives 32 to 35 workflows/s at one loop and 48.2 to 51.2 at four, against Temporal's 31.9 to 37.3 ([performance.md:1690-1737](../docs/performance.md)). If workflow tasks leave the `FOR UPDATE SKIP LOCKED` path, the formula predicts up to about 2.3x per claim loop (7 claims down to 3). The 4 to 6 ms persist per decision remains and caps the real gain. That figure is an extrapolation, not a measurement. Ownership also deletes two known taxes. The sticky predicate costs **+18.9% to +36.2% buffers** with "no query-shape fix" ([performance-sticky-routing.md:1-30](../docs/performance-sticky-routing.md)). Two claim loops produced **64 extra decisions, all cold**, under the untested hypothesis that a second workflow task for a run is claimed while the first decision holds the cache entry ([resident-hit-rate:104-128](../docs/rnd/2026-10-11-resident-hit-rate.md)). One owner per execution removes that race by construction.

The refined protocol borrows each part from a system that paid for it. **Lease rows must live in the same physical database as the history they fence.** The DR doc rejected TTL leases for failover because "the lease lives in the database that just failed over" ([cross-region-dr.md:459](../docs/cross-region-dr.md)). For ownership that same property is required: the lease fails over with the data, and the check is atomic with the append. A table such as `harvest_decision_owner(partition, holder, epoch, lease_until)` per physical database should copy the scanner-lease upsert ([scanner_lease.rs:440-475](../autumn-harvest/src/scanner_lease.rs)). It needs one change taken from Temporal: **every acquisition increments the epoch**, and renewal never does. A renewal that must bump the epoch first drains in-flight commits. Each decision persist takes the owner row `FOR SHARE` and compares the epoch it pinned at acquisition, exactly as the DR fence does with the generation row. A takeover takes the row exclusively. The lock order should be fixed and documented as generation row, then owner row, then execution row. Harvest already resolves an advisory-lock against mutex-lock order hazard by `40P01` and a re-pend ([sharding.md:70-76](../docs/sharding.md)), and a takeover must not add a new one. The DR fence's process-level rule, "never adopt a newer epoch; restart", is too strict for routine churn ([cross-region-dr.md:294-320](../docs/cross-region-dr.md)). The owner fence must be per partition and per acquisition. On a fenced commit the owner should follow Temporal and Golem. It unloads the partition, drops resident futures and cache entries, and does not retry at the stale epoch. The existing per-execution row lock plus `MAX(event_id)` and the `UNIQUE(workflow_exec_id, event_id)` "optimistic-concurrency detector" stay as a backstop ([store.rs:976-1090](../autumn-harvest/src/store.rs); [partitioned-events.md:100-118](../docs/partitioned-events.md)).

Routing should come in two steps, so correctness lands before throughput. **Stage 1a** keeps workflow-task rows and the parking machinery ([queue.rs:7130-7146, 7431-7446](../autumn-harvest/src/queue.rs)) but filters the workflow-task claim to `partition = ANY($owned)` and drops the sticky predicate for owned partitions. That alone should end the cross-loop cold decisions and make resident hits survive the 5 s sticky expiry. **Stage 1b** removes the workflow-task claim from the contended path. The owner learns of pending work from the post-commit notify and from a periodic index scan of its own partitions' pending rows, which backs up a missed notify. Activities stay on shared queues, as Temporal keeps matching separate from history ([Temporal Server docs](https://docs.temporal.io/temporal-service/temporal-server)). A later option is **group commit across executions in one partition**, which Netherite uses under load ([PVLDB 2022](https://www.vldb.org/pvldb/vol15/p1591-burckhardt.pdf)). It attacks the 4 to 6 ms persist floor, but it couples failures and needs a savepoint per decision. The owner must serialize per execution, not per partition. A single-threaded owner is why Durable Objects cap near 1,000 requests/s per object, and only 200 to 500 with storage writes ([Rules of Durable Objects](https://developers.cloudflare.com/durable-objects/best-practices/rules-of-durable-objects/)).

Size the partition count from the precedents: Akka recommends ten times the maximum node count ([Akka sharding](https://doc.akka.io/libraries/akka-core/current/typed/cluster-sharding.html)), Temporal recommends about 500 shards per history process, and Golem uses 1024. A fixed count of a few hundred to 1024 partitions per physical database, hashed from the same `(workflow_name, workflow_id)` input `ShardRouter` already uses ([shard.rs:235-242](../autumn-harvest/src/shard.rs)), avoids the 1/N remap that rendezvous causes when a physical shard is added. It is also fixed forever, as at Restate, whose count "is fixed at provisioning" ([Restate clusters](https://docs.restate.dev/server/clusters.md)).

The main stage 1 risks are specific. First, **foreign writers stay foreign**. At least 13 modules append to `harvest_events` outside the owning decision, including activity completions, timeouts, cancels, resets and cross-shard relays ([store.rs:167-997](../autumn-harvest/src/store.rs); [execution.rs](../autumn-harvest/src/execution.rs); [timeout.rs](../autumn-harvest/src/timeout.rs)). They need no ownership, because the row lock serializes them, but each one must wake the owner rather than a random worker. Two partitions on one database can also have different owners, so a child terminal written into its parent invalidates another owner's cache. Second, **an acknowledgment must never come from owner memory**. Signals are staged as `harvest_signals` rows in Postgres today ([signal.rs:17-60](../autumn-harvest/src/signal.rs)), so the acknowledgment follows a durable write. If stage 1b adds an in-memory inbox, it must keep that order, or it will reproduce Restate #4566. Third, **lease expiry during a long decision** is the durable mutex's "honest caveat" ([mutex.rs:1-39](../autumn-harvest/src/mutex.rs)). It is safe here only because the fence aborts the whole decision transaction. Fourth, **two `FOR SHARE` rows on every append**. The cost of both fences together under high decision rates is unmeasured and should be benchmarked before stage 1b ships. Fifth, a **mixed fleet during rollout**, where some workers claim by partition and some do not, must be impossible. Make owner mode a per-physical-shard switch that also fences the legacy claim.

Validation should target the ownership-change seam, where every 2026 bug in this survey sits. Extend the existing TLA+ activity-claim model and the deterministic simulator ([architecture.md:186-235](../docs/architecture.md)) with an owner-lease model. Cover four nemeses: a stale owner that commits after takeover, a lease flap during an append, a renewal during in-flight commits, and a signal acknowledged just before an epoch bump. Port Golem's end-to-end test: SIGSTOP an owner, move its partitions, resume it, and assert no duplicate or lost event ([PR #3845](https://github.com/golemcloud/golem/pull/3845)).

The open questions for stage 1 are these. Should the hash input include `workflow_name`, given cross-type continue-as-new? How do partitions interact with tenant cells and `with_shard_assignments` ([sharding.md:418-475](../docs/sharding.md))? Should graceful drain hand partitions over explicitly, given Golem's 5 s serial-drain failure ([PR #3766](https://github.com/golemcloud/golem/pull/3766))? And what lease TTL makes sense, given that the scanner lease defaults to 10 s and must cover three ticks ([scanner_lease.rs:41-63](../autumn-harvest/src/scanner_lease.rs))?

### Stage 2: the in-memory cache first, a SQLite file only when cold rates demand it

Restate's shape is "replicated log, local materialized store, snapshots to object storage so the log can be trimmed". Harvest does not trim history, so it does not need the snapshot. **"Snapshot plus log tail" reduces to "whatever local copy exists, plus the per-execution delta `event_id >= next_event_id`"**, which `WorkflowCache` already loads. It already declines to a cold replay on any gap or unexpected shape ([cache.rs:33-51](../autumn-harvest/src/cache.rs); [resident.rs:28-40, 86-110](../autumn-harvest/src/resident.rs)). Under stage 1, that in-memory cache plus resident futures *is* the owner's materialized state, the analogue of Temporal's mutable-state cache. A resident decision costs 2.6 to 2.8 µs, flat ([sticky-routing.md:113-117](../docs/sticky-routing.md)). Harvest's own snapshot spike concluded that "snapshots would buy little speed", because a cold replay at the 50,000-event cap costs about 6 ms. It set explicit verdict changers: `outcome="cold"` above 20% for a week, or cold p99 above 50 ms ([typed-state-snapshots.md:88-137, 245-296](../docs/rnd/typed-state-snapshots.md)). **Stage 2 should be gated on the same counter.** A disk copy saves the Postgres history read after an owner restart and lets the cache exceed RAM, which is bounded today at 1,000 entries by count ([sticky-routing.md:121-129](../docs/sticky-routing.md)). It does not save replay CPU.

If the gate trips, the disk copy should follow Rivet's rule that local disk is only a cache. Reuse the SQLite event-table shape, which is byte-identical per event, and the `flock` single-writer sidecar ([sqlite-backend.md:38-47](../docs/sqlite-backend.md); [lock.rs:1-30](../autumn-harvest-sqlite/src/lock.rs)). Do not reuse `SqliteRuntime`, which reloads and reparses the full history every cycle ([performance-sqlite-runtime-drive.md:1-25](../docs/performance-sqlite-runtime-drive.md)) and lacks the Postgres-only features. No `StorageBackend` trait is needed, which matches the feasibility verdict ([sqlite-feasibility.md:39-55](../docs/rnd/sqlite-feasibility.md)). Rebuild lazily on first decision after takeover, as Netherite's instant recovery does, not eagerly for a whole partition.

Two compliance hazards are specific to a disk copy and absent from the in-memory LRU. PII erasure rewrites terminal histories in place ([erase.rs:21, 149-177](../autumn-harvest/src/erase.rs)), so **a persisted terminal history would keep erased PII**. "Purge on terminal" is not enough on its own. An owner can crash or lose its lease after the terminal commit and before the purge. Erasure later rewrites only Postgres, and no process may ever revisit that file: the run is never scheduled again, and the old owner may never reacquire the partition. Two rules close that window. First, encrypt every cache file under a node-local key that lives only in memory, so that a crash leaves ciphertext under a key that no longer exists (crypto-shredding). Second, delete every cache file on process start and on lease loss, before the node serves any partition. The cache is disposable, so it needs no durable inventory. Codec rotation re-encrypts live histories ([codec_rotation.rs:1179-1180](../autumn-harvest/src/codec_rotation.rs)). A disk copy of ciphertext would block destruction of the retired key, and a disk copy of decoded plaintext bypasses encryption at rest. Each cached file therefore needs a validity stamp: owner epoch, execution state, codec key generation and the last event's hash. Any mismatch should purge the file, in the spirit of LiteFS's TXID plus rolling checksum ([LiteFS ARCHITECTURE.md](https://github.com/superfly/litefs/blob/main/docs/ARCHITECTURE.md)). Execution-row state changes made by other processes, such as pause, reset, rebalance cutover, retention and partition rebuilds, must also evict. No test today states how `WorkflowCache` reacts to them beyond the delta and `KeyChanged` checks. At scale, each WAL-mode file holds several descriptors, and practitioners report filesystem limits at around 50,000 tenants ([DEV per-tenant SQLite](https://dev.to/helperx/multi-tenant-data-isolation-in-sqlite-per-user-database-files-vs-row-level-5glm)). One file per partition, not per execution, is the safer default.

Validate stage 2 in this order. First, measure fleet `harvest.workflow.resident{outcome}` under stage 1, which the hit-rate study lacks ([resident-hit-rate:137](../docs/rnd/2026-10-11-resident-hit-rate.md)). Then measure history load time from Postgres against local SQLite for 10k and 50k-event histories, a gap no document fills. Then measure owner-restart warm-up for 1k, 10k and 100k live executions. Add correctness tests that erase a terminal run and assert no local bytes remain. Also kill the owner between the terminal commit and the purge, then erase the run, and assert that no readable plaintext or ciphertext remains on any node. Also add tests that rotate and retire a key and assert no retired-key ciphertext on disk, and that corrupt a cached file and assert a cold replay rather than a non-determinism error.

### Stage 3: entity state as a projection of history, not a second store

As written, stage 3 asks for something no surveyed system delivers. It wants a user SQLite file on the owner, "committed atomically with history" that lives in Postgres. Two stores cannot commit atomically without two-phase commit or making one derived from the other. Golem's fence stops at the oplog and leaves side stores unfenced ([PR #3845](https://github.com/golemcloud/golem/pull/3845)). Its RDBMS integration needed in-doubt recovery machinery ([issue #1514](https://github.com/golemcloud/golem/issues/1514)). Its per-agent SQLite stays consistent only through replay, plus snapshots taken with no open transaction ([PR #4019](https://github.com/golemcloud/golem/pull/4019)). Harvest's ADR already rejected "state outside history behind `ctx.mutex(key)`" because "replay cannot rebuild the state" ([ADR 0006:155-164](../docs/adr/0006-keyed-entity.md)). The SQLite feasibility report says multi-writer must be "re-opened, not extended" ([sqlite-feasibility.md:500-506](../docs/rnd/sqlite-feasibility.md)).

The Restate model answers the ADR's objection. In Restate, state writes are journal entries, and a K/V table is materialized from them in the same apply. Under an owner, Harvest can do the same. **Stage 3a**: entity state changes become history events committed in the decision transaction under the owner fence. A Postgres state table is materialized from them in that same transaction, so it is atomic, indexable and listable. Replay rebuilds the state from the events. Continue-as-new must still carry the state itself, or an equivalent snapshot event, into the new run. The table is mutable, so a version number alone cannot rebuild the new run's starting state on replay or reset. This is not a third append-only exception, because the state table is not `harvest_events`. It joins rotation's `CODEC_COLUMNS` and erasure's coverage, as other mutable tables do ([CLAUDE.md](../CLAUDE.md)). **Stage 3b**, only on customer demand, applies the same events after commit to an owner-local SQLite file for user SQL queries. That file is a rebuildable projection with the stage 2 hygiene rules, never a source of truth. The cost is the one the ADR named: a new event variant, a trigger change and SQLite-backend work ([ADR 0006:155-164](../docs/adr/0006-keyed-entity.md)). The native entity is ranked 13, "behind customer pull" ([ADR 0006](../docs/adr/0006-keyed-entity.md)). The atomicity spike also showed that one-transaction atomicity pays only for cold keys ([contention-adaptive-atomicity.md:17-36](../docs/rnd/contention-adaptive-atomicity.md)). So stage 3 should wait for evidence.

One more Restate lesson applies before Harvest adds what an owner makes tempting: synchronous op replies, and queries answered from memory instead of by replay ([executor.rs:743, 825](../autumn-harvest/src/executor.rs)). Restate documents that request-response calls between exclusive handlers deadlock (A→B→A, or A→B→C→A), ships no detector, and recovers by manual cancel ([Restate service communication](https://docs.restate.dev/develop/ts/service-communication)). Harvest's entity has no op reply today ([ADR 0006:100-101](../docs/adr/0006-keyed-entity.md)), so the class is absent. If replies arrive, an entity must not hold its key across an awaited cross-entity reply, or Harvest needs a detector.

Validate stage 3 by first filling the gap that blocks any decision: no measurement exists of entity throughput, per-op latency or checkpoint cost. Then require a fidelity test modelled on `replay_fidelity_is_byte_identical_across_a_sweep`. Build the projection, drop it, rebuild it from history, and assert byte-identical state. Add a crash test between the Postgres commit and the SQLite apply, and a fenced-owner test proving that a stale owner cannot advance the projection.

## Conclusion

The prior art changes the question. "Should Harvest colocate storage with an owner?" becomes "where is the commit point, and is the fence inside it?". Harvest's odd position, a thin library over Postgres in a field of log-first engines, turns out to be an asset. The parts that Restate, Golem and Cloudflare spent 2025 and 2026 debugging are the parts Postgres gives Harvest for one `FOR SHARE` row lock: the fence, RPO-zero durability, same-store exactly-once and indexed listing. The parts they got cheaply are what Harvest lacks. That is a compute owner that keeps state warm and never races itself. The right design takes only the owner and leaves the storage where it is.

The sequencing follows from that. Stage 1a is cheap, reuses two existing mechanisms and should fix a measured hit-rate defect. Stage 1b is where the throughput lives, and it should be judged on the assay shape against the 7-claims formula. Stage 2 is mostly done already in memory, and its disk form should wait on the cold-rate gate. Stage 3 should be rewritten as state-change events with projections and wait on customer demand. The likeliest way to get this wrong is the one every surveyed system hit: an acknowledgment, a side store or a renewal that sits outside the fenced commit.
