# Upgrading from 0.8.0 to 0.9.0

This guide covers the move from `0.8.0` to `0.9.0`. Section 1 lists the
breaking and behavior changes. Section 2 lists the migrations. Section 3
lists the rules for a rolling deploy of the new agent features. Section 4
lists the new opt-in features. Section 5 lists the dependency changes.

`autumn-web` stays at 0.9. The MSRV stays at 1.88.0.

Do the steps in this order:

1. Read section 1 and fix each change that affects you.
2. Bump the Harvest crates, as section 5.1 shows.
3. Run `cargo check`, then your tests. If you gate on a schema contract,
   read section 1.1 first.
4. Run the migrations in section 2, then deploy.
5. Turn on a new agent feature only after every worker runs `0.9.0`. See
   section 3.

---

## 1. Breaking and behavior changes

### 1.1 The `schema` feature uses `schemars` 1.x — BREAKING

**What changed (PR #2504).** The `schema` feature of `autumn-harvest` now
depends on `schemars` 1.2. In `0.8.0`, it depended on `schemars` 0.8. The
`with_schemas` helpers on `WorkflowInfo`, `ActivityInfo` and the query,
signal and update infos take types that implement `schemars::JsonSchema`.
Cargo treats `schemars` 0.8 and 1.x as different crates. A type that
derives the 0.8 trait does not implement the 1.x trait, and the build fails.

**Who is affected.** Every app that turns on the `schema` feature and
derives `JsonSchema` on its workflow, activity, query, signal or update
types.

**What to do.**

1. Bump your own `schemars` entry to `"1.2"`. Read the
   [`schemars` changelog](https://github.com/GREsau/schemars/blob/master/CHANGELOG.md)
   for each `#[schemars(...)]` attribute or hand-written `JsonSchema` impl.
2. Check your schema contract. `schemars` 1.x emits a different schema for
   some Rust types. `harvest schema check` against a baseline from `0.8.0`
   reports these deltas, with no change to your code:

   | Rust type | `schemars` 0.8 | `schemars` 1.x | Verdict |
   |---|---|---|---|
   | `i8`, `i16`, `u8`, `u16` | no bound | `minimum` and `maximum` of the type | Breaking (`BoundTightened`) |
   | Tag of a `#[serde(tag = "...")]` enum | one-value `enum` | `const` | Breaking (`UnanalysedConstraintChanged`) |
   | Tuple, such as `(u8, String)` | `items` array | `prefixItems` | Breaking (`UnanalysedConstraintChanged`) |

   No recorded value changes its meaning. Serde already refused a value
   outside the range of the Rust type. A one-value `enum` and a `const`
   accept the same value. The two tuple forms accept the same arrays.
3. Acknowledge the deltas once, with the new schemas as the baseline:

   ```console
   $ harvest schema update \
       --current /tmp/current.json \
       --acknowledge "schemars 1.x schema form, Harvest 0.9.0 upgrade; no value changes meaning"
   ```

   See [Acknowledging a deliberate breaking change](../workflow-schema-contract-guide.md#acknowledging-a-deliberate-breaking-change).
   Do the acknowledgement in its own change, with no type edit in it. Then
   each later delta comes from your code only.

**How to check.** `cargo tree -i schemars` shows one `schemars v1`. Input
validation at start and at signal time accepts the same valid values as
before.

### 1.2 Three Diesel tables split into a core and an extension declaration

**What changed (issue #2492).** `harvest_workflow_executions`,
`harvest_task_queue` and `harvest_schedules` had more than 32 columns in their
`diesel::table!`. So the workspace built Diesel at its 128-column tier, and
Cargo unified that tier into every embedder. Each table now has a core
declaration of 32 columns and an extension declaration, `<table>_ext`, on the
same physical table. No migration is needed.

**Who is affected.** Only code that queries these tables through
`autumn_harvest::schema` or builds their rows by hand. Code that uses the
engine and plugin APIs is not affected.

**What to do.**

- A column that moved changes its path from `<table>::<column>` to
  `<table>_ext::<column>`. The compiler names each one.
- To read or filter an extension column in a query on the core table, use
  the column as before. To insert an extension value, wrap it in
  `table_split::Ext(..)`. To assign it in an update of the core table, use
  `table_split::SetExt(..)`.
- An insert of `NewWorkflowExecution`, `NewTaskQueueItem` or
  `NewHarvestSchedule` borrows the row. Pass `&row`, or a slice for a batch.
- `WorkflowExecution` holds the four shard-rebalance columns in a new field,
  `rebalance: RebalanceMarkers`. Read `exec.rebalance.migrated_from_shards`
  in place of `exec.migrated_from_shards`. The JSON form is flat, as before.

Read `autumn-harvest/src/table_split.rs` for the bridge. If your own crate
has a `table!` over 32 columns, turn on the Diesel column tier in your own
manifest. Harvest no longer turns it on for you.

### 1.3 New public fields and variants

Each change below can break code that compiles with `0.8.0`. Add the field
to each struct literal, or add an arm for each new variant.

- `autumn-harvest`: `WorkerConfig` has a new field, `cost_hold`
  (`Option<CostHold>`). A struct literal without `..WorkerConfig::default()`
  must name it. Use `None` for the old behavior. `WorkerConfigView`, the
  body of `GET /admin/config`, adds `cost_hold_activities`.
- `autumn-harvest-sqlite`: `SqliteError` has two new variants,
  `SignalPayloadInvalid` and `WorkflowInputInvalid` (issue #2467). The
  runtime now checks a signal against its `arg_schema`, and a start against
  its `input_schema`, as Postgres does. An exhaustive `match` needs an arm
  for each.
- `autumn-harvest-agent`: `AgentTask` adds `tool_guidance`, `skills`,
  `context_reset` and `draw`. `AgentProfile` adds `tool_guidance`, `skills`
  and `context_reset`. Use an empty map and `None` for the old behavior.
- `autumn-harvest-agent`: `ChatRequest` adds `draw` (issue #2440). Use
  `draw: None` for one draw. A request with no draw keeps its
  response-cache key.
- `autumn-harvest-agent`: `ModelTurnRequest` adds `tool_guidance`, `skills`
  and `draw`. `ToolCallRequest` adds `skill`. `AgentReport` adds `resets`.
  Each one is skipped when empty, so a recorded history keeps its bytes.
- `autumn-harvest-agent`: `eval::Evaluation` adds `overlay_digest`
  (issue #2375).
- `autumn-harvest-agent`: `AgentTask`, `ModelTurnRequest` and
  `ToolCallRequest` add `allowed_effects` (issue #2439). Use `None` for
  the old behavior. It is skipped when `None`, so a recorded history keeps
  its bytes.
- `autumn-harvest`: `ForkEffects` adds `LiveQuiet` (issue #2378). An
  exhaustive `match` needs an arm. `fork_workflow_execution_with_codecs`
  is new.
- `autumn-harvest-agent`: `AgentTask` adds `probe`, and `ToolCallRequest`
  adds `probe_effects` (issue #2378). Use `None` for the old behavior. Each
  one is skipped when `None`, so a recorded history keeps its bytes.
  `EvalError` adds `Unsupported` and `Fork`.
- `autumn-harvest-agent`: `AgentTask` and `AgentOp` now fail to decode when
  they carry a key of `sampling::SAMPLING_POLICY_FIELDS`, such as
  `max_draws` (issue #2439). No earlier field has such a name.

### 1.4 `load_skill` is a reserved tool name — BEHAVIOR CHANGE

**What changed (issue #2373).** A run with skills offers the model the
built-in `load_skill` tool. So the name is reserved. An app tool named
`load_skill` is no longer shown to the model, and `AgentHarness::tool` logs
a warning.

**Who is affected.** An app that registers its own tool named `load_skill`.

**What to do.** Rename the tool before you upgrade.

### 1.5 An evaluation candidate checks its model first — BEHAVIOR CHANGE

**What changed (issue #2375).** `eval::Candidate::model` now sets the model
of the candidate overlay, and the harness checks it before the first model
call. Before, a model that the harness did not hold failed at the first
turn. A model that the source mandate forbade ran unchecked. Both now fail
at once with `EvalError::Overlay`. A delegated child with no peer model now
inherits the model of its parent.

**Who is affected.** An evaluation that sets `Candidate::model`.

**What to do.** Register the candidate model on the harness. If the source
mandate forbids the model, set operator ceilings with
`Candidate::ceilings`. `Candidate::agent_model` stays a route and is not
checked.

## 2. Migrations

`0.9.0` adds five migrations. Each one only adds or drops an index, or adds
new tables. None rewrites `harvest_events`. Each one sets `lock_timeout`
to 5 s. If it fires, run the migration again. See
[the migration table](0.5.0.md) for each row.

### 2.1 The retention index drop runs in its own migration — RUN THE MIGRATION

**What changed (issue #2395).** In `0.8.0`,
`20261029034500_harvest_retention_candidates_index` built
`idx_harvest_we_retention_candidates` and dropped
`idx_harvest_we_retention_scan` in one transaction. The build holds `SHARE`
on `harvest_workflow_executions` until the commit. The drop then asks for
`ACCESS EXCLUSIVE`. A step transaction that waited behind the build made a
deadlock, and the whole build rolled back.

In `0.9.0`, `20261029034500` only builds the new index. The new migration
`20261101012649_harvest_retention_scan_index_drop` drops the old index, in
its own transaction. It holds no earlier lock, so it cannot deadlock. The end
schema is the same.

**Who is affected.** Every deployment.

- A database that applied `20261029034500` from `0.8.0` already has the end
  schema. Diesel does not run `20261029034500` again. The new migration finds
  no old index and takes no lock.
- A database that has not applied `20261029034500` runs the `0.9.0` form,
  then the drop.

**What to do.** Run the migrations. On a large deployment that has not
applied `20261029034500`, build the new index `CONCURRENTLY` first. Then run
`DROP INDEX CONCURRENTLY IF EXISTS idx_harvest_we_retention_scan;`. Both
migration headers give the statements.

The `migration_lock_safety` lint has a new rule, `lock-upgrade`. It fails a
plain drop or `ALTER TABLE` of a hot table after a plain build of the same
table in one file. See
[online-migrations.md](online-migrations.md#5-the-guarded-build).

### 2.2 Signal reads by execution use an index — RUN THE MIGRATION

Before this release, these statements read the whole of `harvest_signals`
(issue #2367):

- the signal move of a workflow-level retry;
- the signal scrub of a PII erasure;
- the signal copy and delete of a shard rebalance;
- each `ON DELETE CASCADE` from an execution, which retention triggers;
- the unkeyed signal check of a backup verification.

**Who is affected.** Every deployment. Each retry, erasure, rebalance move
and retention delete read more rows as the signal table grew.

**What to do.** Run migration `20261030182800_harvest_signals_exec_index`. It
builds `idx_harvest_signals_exec`. A plain build blocks each write to the
table and each execution delete until it ends. On a large table, build the
index `CONCURRENTLY` first. The header of the migration's `up.sql` gives the
statement.

Pending signal reads now send `NOT consumed` as a literal, not a bound
parameter. A generic plan can then use the partial pending index. No action
is needed.

### 2.3 A versioned store for agent profile overlays — RUN THE MIGRATION

Issue #2371 adds `ProfileOverlayStore` to `autumn-harvest-agent`. It keeps
each overlay version of an agent kind, and an active pointer. A version
never changes after its put. A rollback activates an earlier version.

**Who is affected.** An app that installs a Postgres overlay store. The
Postgres store needs the new `postgres` feature of `autumn-harvest-agent`.

**What to do.** Run migration `20261031200812_harvest_agent_overlays`. It
creates two new tables and their triggers. It takes no lock on a hot table.
A role that runs the store needs `SELECT` and `INSERT` on
`harvest_agent_overlays`, and `SELECT`, `INSERT` and `UPDATE` on
`harvest_agent_overlay_heads`.

### 2.4 Dead-letter reads use an index — RUN THE MIGRATION

Before this release, these statements read the whole of
`harvest_dead_letters` (issue #2401):

- the newest-first DLQ list, in the engine and the plugin DLQ page;
- the newest-age probe of `GET /admin/status`;
- the delete of a callback redrive, once per row of a bulk redrive;
- each `queue_name` filter of a redrive, a bulk replay, a bulk discard and
  an aggregate.

**Who is affected.** Every deployment. The DLQ is largest during an
incident, which is when operators list, filter and redrive it.

**Trade-off.** A redrive or bulk replay that filters on `activity_name` or
`error`, with no time window, can now walk the `failed_at` index. When the
matches are the newest rows and the heap is shuffled, that walk costs more
than the old full scan. Set `failed_after` or `dead_lettered_after`, or a
queue, to bound the read.

**What to do.** Run migration `20261102143438_harvest_dead_letter_indexes`.
It builds three indexes. A plain build blocks each dead-letter insert, and
so each terminal task failure, until it ends. A blocked failure keeps its
row locks, so signals and cancels on that run wait too. On a large DLQ,
build each index `CONCURRENTLY` first. The header of the migration's
`up.sql` gives the statements.

### 2.5 Operate agent profile overlays — RUN THE MIGRATION

Issue #2374 adds the `/agents/{kind}/profile` routes and
`harvest agents profile`. Each store logs each move of the pointer, and
`rollback` reverses the last move.

**Who is affected.** An app that installs an overlay store. A Postgres
store needs the new table. `ProfileOverlayStore::activate` takes an actor,
a `Provenance`, as its last argument. A custom store also implements
`last_activation` and `rollback`. The raw log functions take a
`MoveRequest`.

**What to do.** Run migration
`20261102142302_harvest_agent_overlay_activations`. It creates one new
table and a trigger. It takes no lock on a hot table. A role that runs the
store needs `SELECT` and `INSERT` on `harvest_agent_overlay_activations`.
Install the store on the plugin with `HarvestPlugin::agent_overlay_store`.
The SQLite plugin refuses that call for now (#2471).

### 2.6 The operator refine policy — RUN THE MIGRATION

Issue #2394 adds a refine policy for each agent kind, the
`/agents/{kind}/profile/policy` routes and
`harvest agents profile policy`. A kind with no policy uses every
default. The defaults change nothing that a store did before.

**Who is affected.** An app that installs an overlay store, or writes its
own store or validator. `OverlayValidator::validate` takes the policy. A
custom store also implements `policy`, `set_policy`, `reset_policy`,
`policy_log` and `auto_adopt`. `Provenance` has a new variant, `Auto`. A
`match` on it needs a wildcard arm. `put`, `activate` and `rollback`
refuse it. `AgentOp` refuses each refine policy key when it decodes.
`ProposeRequest` refuses each unknown key.

**What to do.** Run migration
`20261103134706_harvest_agent_refine_policies`. It creates one new table
and a trigger, and widens the author kind `CHECK` of
`harvest_agent_overlays` and `harvest_agent_overlay_activations`. It takes
no lock on a hot table. A role that runs the store needs `SELECT` and
`INSERT` on `harvest_agent_refine_policies`.

### 2.7 An operator sampling policy for agent kinds — RUN THE MIGRATION

Issue #2439 adds `SamplingPolicy` to `autumn-harvest-agent`. An operator
sets it per agent kind through `harvest agents sampling policy`. The new
workflow `agent_draws` reads it once per strategy run.

**Who is affected.** Nobody at once. A kind with no policy reads every
default, and the defaults allow no strategy.

**What to do.** Run migration `20261102032158_harvest_agent_policies`. It
creates two new tables. It takes no lock on a hot table. A role that reads
a policy needs `SELECT` on `harvest_agent_policies` and
`harvest_agent_policy_audit`. A role that sets one also needs `INSERT` and
`UPDATE` on `harvest_agent_policies`, `INSERT` on
`harvest_agent_policy_audit` and `USAGE` on its sequence. `GET
/admin/preflight` checks these grants.

## 3. Rolling deploy: turn on agent features after the roll

The [rolling-deploy contract](README.md) lets `0.8.0` and `0.9.0` workers
run together. A `0.8.0` worker does not know the new agent activities and
task fields. It cannot replay a history that holds them, and it drops a
field that it does not know. So turn on each feature below only after every
worker runs `0.9.0`.

| Feature | Turn it on with | What an old worker does |
|---|---|---|
| Recorded overlay read (issue #2372) | `AgentHarness::overlay_store` | Cannot replay the `agent_profile_overlay` activity of an op |
| Tool guidance and skills (issue #2373) | `tool_guidance` or `skills` on a profile, task or overlay | Drops the fields, and does not offer `load_skill` |
| Best-of-N draws (issue #2440) | `run_draws` | Drops the `draw` field, so draws share one cache key |
| Context reset (issue #2453) | `context_reset` on a profile or task | Drops the setting, so its replay of a run with a reset diverges |
| Overlay proposer (issue #2379) | `AgentHarness::proposer` | Does not register `agent_refine_propose` |
| Scorer (issue #2441) | `AgentHarness::scorer` | Does not register `agent_score` |
| Sampling policy (issue #2439) | `AgentHarness::sampling_policies`, then a policy with `strategies` | Does not register `agent_draws`. It drops `allowed_effects` from a draw, so it runs an `internal` tool that the policy refuses |
| Refine policy read (issue #2394) | `read_refine_policy` in a refine workflow | Does not register `agent_refine_policy` |
| Live probe (issue #2378) | `eval::live_probe` | Cannot decode the `live_quiet` fork marker, so it cannot run the probe |

`activities()` and `autumn_harvest_agent::sqlite::register` add the new
activities. A worker that builds its own activity list must add them too.

## 4. New opt-in features — NO ACTION

Each feature below is off until you turn it on.

- **Cost-aware deferral (autumn#1720).** A worker can hold named activity
  types while the autumn-web `CostSignal` is high. A held task stays
  `PENDING` and uses no attempt. See [Cost-aware deferral](../cost-deferral.md).
- **`HarvestPlugin` on SQLite, slice 1 (issue #2467).** The new `sqlite`
  feature of `autumn-harvest-plugin` boots the plugin in an Autumn app on
  the SQLite lane. Only an end application may turn it on. See
  [HarvestPlugin on SQLite](../sqlite-plugin.md).
- **Agent profile overlays (epic #2369).** Overlays under ceilings, a
  versioned store, a recorded read per op, tool guidance and skills,
  whole-overlay evaluation candidates and an overlay proposer. An operator
  lists, shows, diffs, activates and rolls back a version with
  `harvest agents profile` (issue #2374). See
  [the agent adapter guide](../agent-adapter.md), sections 12, 15 and 16.
- **Draws and scorers (epic #2438).** `run_draws` runs best-of-N draws as
  child runs. A `Scorer` records a verdict for a run, and `select` picks the
  best draw. See [the agent adapter guide](../agent-adapter.md), sections
  11 and 17.
- **Operator sampling policy (issue #2439).** An operator sets the
  strategies, draw caps, draw effects, scorers and judge models of each
  agent kind. `agent_draws` reads the policy once and runs the admitted
  draws. See [the agent adapter guide](../agent-adapter.md), section 19.
- **Context reset (issue #2453).** A long agent run saves progress notes
  and resets its window. See
  [the agent adapter guide](../agent-adapter.md#context-reset-issue-2453).

## 5. Dependency changes

### 5.1 Bump the Harvest crates — REQUIRED

Bump every Harvest crate in one change. `autumn-web` stays at 0.9.

```toml
[dependencies]
autumn-harvest = { version = "0.9", features = ["db"] }
autumn-harvest-plugin = "0.9"
autumn-web = "0.9"
```

`harvest new` writes these versions.

`autumn-harvest-plugin` now depends on `autumn-harvest-agent` with its
`postgres` feature, for the sampling policy routes (issue #2439). Cargo
pulls it in, so a manifest needs no new entry.

### 5.2 Diesel builds at its default column tier — NO ACTION

Harvest no longer turns on Diesel's `128-column-tables` feature (issue
#2492). A build of Diesel at the default 32-column tier takes about a third
of the time and memory of the 64-column tier. The workspace now names
Diesel's `i-implement-a-third-party-backend-and-opt-into-breaking-changes`
feature, which the insert bridge needs. Cargo unifies it into your build.

### 5.3 `schemars` 1.2 — REQUIRED with the `schema` feature

See section 1.1.
