# Upgrading from 0.7.0 to 0.8.0

This guide covers the move from `0.7.0` to `0.8.0`. Section 1 lists the
breaking and behavior changes in Harvest. Section 2 lists the dependency
changes. The main one is `autumn-web` 0.9.

Do the steps in this order:

1. Read section 1 and choose an option for each change that affects you.
2. Bump the three crates together, as section 2.1 shows.
3. Run `cargo check`, then your tests.
4. Run the migrations, then deploy.

---

## 1. Breaking and behavior changes

### 1.1 Decision boundaries are opt-in

**What changed (issue #1833).** A worker can append one `DecisionCommitted`
event after each decision that writes events. The event names the build id
and the worker id of that decision. See
[Decision boundaries](../decision-boundaries.md).

Boundaries are **off by default** in `0.8.0`. A process older than `0.8.0`
cannot decode `DecisionCommitted`, and the
[rolling-deploy contract](README.md) forbids writing a new event variant by
default. Every `0.8.0` process reads boundaries. A later release turns them
on by default.

**Who is affected.** Only a deployment that turns boundaries on. An upgrade
that leaves them off changes nothing in the history.

**What to do.**

1. Upgrade every process that reads history to `0.8.0`: workers, timeout
   leaders, API nodes, Vantage and the `harvest` CLI.
2. Then turn boundaries on for the workers:

   ```rust
   let harvest = HarvestBuilder::new()
       .record_decision_boundaries(true)
       // ... the rest of your configuration
       .build();
   ```

   A `HandlerRegistry` takes
   `WorkflowHistoryPolicy::with_decision_boundaries(true)`.
3. If a workflow runs close to a history limit, raise that limit first.

A process older than `0.8.0` fails on a history that holds a boundary:

- An old worker fails the execution for good.
- An old timeout leader cannot enforce activity timeouts for that run. It
  reports the error on every pass.
- An old API node, Vantage page or `harvest` CLI cannot show, export or
  cancel that run.

So do not roll back to `0.7.0` after a worker wrote boundaries. Turning
them off again stops new boundaries, but the rows already written stay.

Boundaries count toward the history limits. A run with one activity per
decision has about one third more events. These limits count them:

- `history_event_hard_cap`, which defaults to 50,000 events (issue #1804),
  and `history_continue_as_new_threshold`, and so
  `ctx.should_continue_as_new()`;
- `max_workflow_history_events`, the ceiling of the timeout scanner;
- the history-bloat warning, which is a fraction of the hard cap;
- the `history_bytes` quota, about 131 bytes for each boundary.

**How to check.** This query counts the boundaries. It stays at 0 while
boundaries are off:

```sql
SELECT count(*) FROM harvest_events WHERE event_type = 'DecisionCommitted';
```

### 1.2 The claim reads a bounded window and sets its own planner settings

**What changed (issue #1971).** The default claim reads a bounded window from
the head of each polled queue. It runs the old full scan only when the window
cannot prove its pick. The claim order does not change. See
[the seek window](../performance.md#the-seek-window-issue-1971).

The claim transaction now does four more things:

- It runs `SET LOCAL jit = off; SET LOCAL plan_cache_mode =
  force_generic_plan; SET LOCAL enable_bitmapscan = off` before the claim.
  This is one more round trip. The settings end with the transaction. A
  server or role setting for `jit`, `plan_cache_mode` or
  `enable_bitmapscan` no longer applies to the claim transaction. A claim
  with priority ageing on leaves out the bitmap setting.
- It keeps the claim statement as a prepared statement on each connection.
  Other Harvest statements already do this. `pg_prepared_statements` shows
  it, and `auto_explain` shows a generic plan.
- It returns a fixed column list, so a migration that adds a column to
  `harvest_task_queue` does not break the cached statement.
- A claim on a capped concurrency key counts the key again after the
  claim, in a fresh snapshot. If the key is over its cap, the claim gives
  the row back. This closes a race that let a key run tasks over its cap.
  Such a claim costs one more round trip. The by-id and batched claims run
  this re-check too.

**Who is affected.** A deployment that tunes `jit`, `plan_cache_mode` or
`enable_bitmapscan` for the engine role, or that reads `pg_stat_statements`
per claim.

**What to do.** Run migration
`20261008042107_harvest_task_queue_claim_seek_index`. A large table needs the
out-of-band `CREATE INDEX CONCURRENTLY` first. See
[the migration table](0.5.0.md). A new binary without the index still claims
correctly. Its claim then reads the whole backlog, as the old claim did.

### 1.3 `queue::complete_task` takes a claim

**What changed (issue #1992).** `queue::complete_task` takes a
`&queue::TaskClaim` in place of a task id. It returns `NotFound` when the row
is not `RUNNING` under that claim, for example when a later claim holds it.

**Who is affected.** Code that calls `queue::complete_task` directly.
Workflows and activities that run through a worker are not affected.

**What to do.** Pass the claim that you took. Build it with
`TaskClaim::of(&task)` or `TaskClaim::new(task_id, worker_id, attempt)`. To
treat a lost claim as a no-op, call `queue::complete_claimed_task`.

### 1.4 No reset forks a PII-erased run

**What changed (issue #1999).** Every reset fork refuses a run whose payloads
were erased. Before, `POST /workflows/batch_reset` forked an erased `FAILED`,
`CANCELLED` or `TIMED_OUT` run. It now skips the run with
`skip_reason: {"type": "erased_source"}`, in a preview and in a real reset.
`WorkflowResetRequest::refuse_erased_source` is removed, and
`ResetSkipReason::ErasedSource` is new.

**Who is affected.**

- Operators who batch-reset a cohort that holds erased runs.
- Code that builds a `WorkflowResetRequest` with a struct literal.
- Code that matches on `ResetSkipReason` with no wildcard arm.

**What to do.**

- Delete the `refuse_erased_source:` line from each `WorkflowResetRequest`.
- Add an `ErasedSource` arm to each exhaustive match on `ResetSkipReason`.
- To run the work of an erased run again, start a fresh run. See
  [Workflow reset](../workflow-reset.md#a-fork-never-uses-a-pii-erased-source).

### 1.5 A worker runs up to two claims at once by default — BREAKING DEFAULT

**What changed.** `WorkerConfig::default()` sets `max_concurrent_claims` to
`builder::DEFAULT_MAX_CONCURRENT_CLAIMS` (2). In `0.7.0`, one serial loop
ran one claim at a time. Assay #14 measured that loop busy 94% of the time,
so it capped throughput. A second loop claims only while claims return work,
so an idle worker polls as before. See
[claim concurrency](../performance.md#claim-concurrency).

`WorkerRuntimeConfig`, `WorkerConfig` and `workers::ExecutionPolicy` have a
new public field. Validation rejects `max_concurrent_claims = 0`.

**Who is affected.**

- Code that builds `WorkerRuntimeConfig`, `WorkerConfig` or
  `workers::ExecutionPolicy` with a struct literal and no `..` does not
  compile.
- A default worker can hold two pool connections for claims, not one. Each
  extra loop adds one. In embedded mode the worker shares the application
  pool. A worker warns at startup when its claim loops can hold every pool
  connection.
- `harvest_worker_pollers` reads 2 per default worker, not 1.
- A queue that one concurrency key or one rate limit dominates gains little.
  The loops contend for the same advisory lock or bucket row, and the loser
  gets an empty claim.
- Under an adaptive limit, two loops can race past a type's cap.
  `harvest.activity.concurrency_deferred` can then rise a little.
- A worker that uses a dispatch channel gains nothing. Extra loops claim
  only through Postgres, and they still count in `harvest_worker_pollers`.
- Two loops can claim rows slightly out of order, as two workers can.

**What to do.** Add `max_concurrent_claims` to struct literals. Use
`builder::DEFAULT_MAX_CONCURRENT_CLAIMS`, or `1` to keep the old loop. Add
`claim_loops` to `ExecutionPolicy` literals. Size the pool for the slots
plus `max_concurrent_claims`. Set `with_max_concurrent_claims(1)` for a small
pool, a hot-key queue or a test that needs a strict claim order.

**How to check.** `GET /admin/config` reports the active value as
`worker.max_concurrent_claims`.

### 1.6 The schema contract covers activities and side effects

**What changed (issue #1994).** Activities can publish input and output
schemas, and side effects can publish a value schema. `harvest schema check`
gates them. See
[Activities and side effects](../workflow-schema-contract-guide.md#activities-and-side-effects).

- `ActivityInfo` has two new fields, `input_schema` and `output_schema`.
- The schema contract format is `contract_version` `2`. A `0.8.0` binary
  reads a version `1` baseline. A `0.7.0` binary refuses a version `2` file.
- The artifact's `description` and `compatibility` text changed.
- The contract API changed. `SchemaRole` has a new `Value` variant.
  `ChangeKind` has four new variants. `SchemaDelta` and
  `AcknowledgedBreakingChange` have two new fields, `subject` and
  `side_effect`. `SchemaCoverage` and `WorkflowSchemaContract` have new
  fields too.
- A `schema check --format json` delta about an activity has
  `"subject": "activity"`, and its `workflow` key holds the activity name.

**Who is affected.** Code that builds an `ActivityInfo` as a struct literal.
Code that matches on `SchemaRole` or `ChangeKind`, or builds a contract type
as a struct literal. A tool that reads the JSON output of `schema check`. A
project that runs `harvest schema check --require-current`.

**What to do.**

1. Add `input_schema: None, output_schema: None` to each `ActivityInfo`
   struct literal. Code that uses the `#[activity]` macro needs no change.
2. Add match arms for the new variants, and the new fields to each struct
   literal of a contract type.
3. Make a JSON consumer read `subject` before it reads `workflow`.
4. Upgrade every `harvest` CLI that reads the baseline to `0.8.0`.
5. Run `harvest schema update` once to regenerate the baseline. The update
   has no breaking delta, so it needs no `--acknowledge`.

### 1.7 The usage report carries the agent cost ledger

**What changed (issue #1996).** An activity can record each LLM call with
`ActivityContext::record_llm_call`. The engine writes the model id, the
tokens, the cost and the latency to `harvest_llm_ledger`, outside the
encrypted payload. Each group of `GET /admin/usage` gains six `llm_*`
fields. The `harvest usage` table gains five columns. The
`agent_model_turn` activity of `autumn-harvest-agent` records one call per
model turn.

**Who is affected.** A script that parses the `harvest usage` table by
column position. A deployment that runs the agent adapter on Postgres: each
model turn now writes one small row. A security review: the ledger fields
are in clear. See [the security posture](../security-posture.md#llm-cost-ledger-issue-1996).

**What to do.**

1. Run migration `20261009050156_harvest_llm_ledger` before you deploy the
   new binary. A worker of this release fails a completion that records a
   call while the table is missing. The activity then runs again after its
   lease expires, and the provider bills the model call again.
2. A role with per-table grants needs `SELECT`, `INSERT` and `DELETE` on
   `harvest_llm_ledger`. `harvest preflight` checks them.
3. On a cross-region DR standby, run the migration first. Then run
   `ALTER SUBSCRIPTION ... REFRESH PUBLICATION`, so the table replicates.
4. Do not run a shard rebalance from an older binary after the migration.
   An older binary leaves the ledger rows on the sealed source, and the
   report then skips them.
5. Parse `harvest usage --json`, not the table.
6. To name the model in the agent ledger, implement `AgentModel::model_id`
   and `AgentModel::cost_usd_micros`.

See [the agent cost ledger](../llm-cost-ledger.md).

### 1.8 Fairness keys are opt-in

**What changed (issue #1976).** A task can carry a fairness key. A worker
with `WorkerConfig::with_fairness_keys(true)` serves the keys of a queue in
weighted round robin. See [Fairness keys](../fairness-keys.md).

Fairness keys are **off by default**. Off, the claim statement is unchanged.
A fair claim skips the seek window of §1.2 and runs the full scan, as a claim
with priority ageing does. Its cost then grows with the backlog. See
[the measured cost](../performance.md#fairness-keys-issue-1976).
A worker older than `0.8.0` ignores keys and does not charge them. An API
node older than `0.8.0` ignores a `fairness_key` in a start body. A run
started before the upgrade keeps the default key. Turn the option on only
after every worker and API node of the queue runs `0.8.0`.

Migration `20261008040947_harvest_fairness_keys` adds the nullable column
`harvest_task_queue.fairness_key`. It also adds the tables
`harvest_fairness_state` and `harvest_fairness_weights`. The `ALTER` changes
only the catalog. It fails after a 5-second lock wait, so claims do not queue
behind it. Run it again if it fails.

A least-privilege storage role needs `SELECT`, `INSERT`, `UPDATE` and
`DELETE` on both new tables. Preflight checks them.

### 1.9 Column encoding covers the activity rows and the short-lived copies

**What changed (issue #1979, issue #2043).** With column encoding on, the
engine stores more columns encoded. They are the activity task row, the
completion-callback body, the debounce, throttle and outbox inputs, the batch
job payload, the event batch buffer, the cross-shard child spec, the schedule
input and the context headers. The
[coverage table](../security-posture.md#column-coverage-issue-1979) names each
column.

Column encoding is **off by default**. `0.8.0` always decodes these columns. A
worker older than `0.8.0` does not. It runs an activity on the envelope, sends
the envelope to a webhook, starts a run on it, or sends it as a signal. Turn
column encoding on only after every worker and every API node runs `0.8.0`. If
it is on already, turn it off, finish the roll, and turn it on again.

A row written before the upgrade holds clear values. A clear value that has the
shape of an envelope reads as an envelope. Drain the activity queues before you
turn column encoding on. No migration is needed.

Three behaviors change when column encoding is on:

- The schedule API and the UI show the stored envelope for a schedule input.
- An export includes context headers only for a caller who may decode. The
  retention archive leaves an encoded header map out of the archived document.
- A run whose headers do not decode fails. It never runs without its headers.
  Give every worker every key that can read a row.

### 1.10 A keyed entity drops the input of a caller start

**What changed (issue #2082).** `ctx.info()` reports `start_source` and
`continued_from`. `Entity::run` uses them. A start route, a signal-with-start
or any other caller start no longer sets the first state, the pending ops or
the counters. The run starts from `S::default()`, or from
`Entity::initial_state`.

**Who is affected.** A deployment whose clients send a non-empty start input
to an entity. A run with a seeded input that is still open at the upgrade
replays from the default state, and it can report non-determinism.

**What to do.**

1. Drain the seeded runs before the upgrade, or call
   `Entity::trust_start_input` on that entity type first.
2. Upgrade every worker. An older worker still keeps the input.
3. Seed a fresh entity from code with `Entity::initial_state`. A change to
   that state changes replay, so version it.

A reset or a re-run copies the stored input of its source run, so it keeps a
forged one. The SQLite backend records no start source and keeps every input.

### 1.11 A dropped Session releases its slot

**What changed (issue #2193).** A `Session` that its owner drops without
`complete()` now releases its host slot. This covers a cancelled future, a
race loser and a `select!` branch. The release is a new reserved activity,
`__harvest_session_drop_release`. It is pinned to the host worker, and no body
awaits it. Replay treats its records as transparent.

**Who is affected.** A deployment that uses worker sessions and drops a
session before `complete()`.

**What to do.**

1. Upgrade every worker before a workflow drops a session. A worker of an
   older build cannot run the new name. If it hosts the session, it fails the
   run, because a session task has no other worker to go to.
2. An older build that replays a history with a release reports
   non-determinism. Do not roll back after a drop release is recorded.
3. A run that ends right after the drop keeps its slot until the
   broken-session scanner reaps it, as before.
4. A member activity of the dropped session may still be queued or running.
   The release then waits and checks again every five seconds. The session
   keeps its slot until that member settles, as it did before this change.
   Only the drop release waits. The release that `complete()` awaits does not.

The SQLite backend has no sessions, so it never issues the release.

### 1.12 An activity result nested past 100 levels fails

**What changed (issue #2225).** An activity result nested more than 100 levels
no longer completes. A regular or transactional activity records a
non-retryable `ActivityFailed` with `error_type = "PayloadTooDeep"` in its
place. A local activity or an external completion fails with the same message.
Those two failures keep only the message, so the workflow sees the error type
`Error`. A heartbeat checkpoint nested more than 100 levels is dropped with a
warning. The last good checkpoint stays, and the heartbeat time still advances.
The SQLite backend has had the same rule since issue #2216.

**Who is affected.** A deployment whose activity returns, completes with or
heartbeats a value nested 101 or more levels. A result nested 101 to 125
levels used to complete. A result nested 126 levels or more made every load of
the run history fail.

**What to do.**

1. Flatten the value, or keep it in your own store and return a reference.
2. During a rolling upgrade, a worker of an older build still completes a
   result nested 101 to 125 levels. The outcome depends on which worker claims
   the task.
3. The fix does not repair a history that already holds a result nested 126
   levels or more.

### 1.13 A workflow-side value nested past 100 levels fails

**What changed (issue #2224).** `WorkflowContext` refuses a value from
workflow code that nests more than 100 levels. It returns
`HarvestError::PayloadTooDeep` at the call site and writes no command or
event. The workflow can handle the error. The check covers activity, local
activity, child and continue-as-new input, external signal payloads and
side-effect values. An update result nested more than 100 levels fails the
update. Both backends apply these checks.

**Who is affected.** A deployment whose workflow code hands the engine a value
nested 101 or more levels. Before this change, Postgres had no depth cap, so
it stored such a value. A value deep enough to pass the `serde_json` read
limit then made every later load of the run history fail. A shallower value
worked, and it now fails.

**What to do.**

1. Flatten the value, or keep it in your own store and pass a reference.
2. The call-site check runs only on a new call. A value that a history
   already holds replays as before.
3. During a rolling upgrade, a worker of an older build still accepts the
   value. The outcome depends on which worker runs the workflow task.

A workflow result has no call site. On SQLite, a result nested more than 100
levels fails the run with a non-retryable `PayloadTooDeep` failure. A Postgres
workflow result is not capped yet.

### 1.14 A calendar tests the schedule's local date

**What changed (issue #2332).** A calendar used to test the UTC date of a fire
time. For a `CronInTimezone` schedule it now tests the date in the schedule's
timezone. A Mon–Fri 08:00 `Asia/Tokyo` schedule with `weekends-off` no longer
loses its Monday fire. `Cron` and `Interval` schedules keep the UTC date.

**Who is affected.** A `CronInTimezone` schedule with a calendar whose fire
time falls on a different UTC day. That is common beyond about UTC±5h, and for
evening or early-morning local times. The schedule can skip, shift or fire on
different days than before.

**What to do.**

1. Read each holiday date in a calendar used by a timezone schedule as a date
   in that timezone. Re-check dates that you entered as UTC days.
2. No migration is needed.
3. During a rolling upgrade, an older node and a new node can disagree on the
   calendar day of one slot. The window ends when the roll ends.

### 1.15 Other API changes

Each change below can break code that works with `0.7.0`. Each item names
the fix.

- `WorkflowCommand::ScheduleActivity` has a new field, `result_writer`
  (issue #1986). A struct literal or a pattern without `..` must name it.
- `QuotaPolicy` has new public fields: `max_run_llm_tokens`,
  `max_run_llm_cost_usd_micros`, `max_tenant_llm_tokens`,
  `max_tenant_llm_cost_usd_micros` and `tenant_llm_window_secs`
  (issue #1997). Add them to each struct literal, or end it with
  `..QuotaPolicy::new(key)`. The `#[workflow(quota(...))]` macro needs no
  change.
- `cross_shard_child::request_cross_shard_cancel` takes a new
  `reason: Option<&str>` parameter (issue #2194). Pass `None` for the old
  behavior.
- `autumn-harvest-sqlite`: `SqliteRuntime::register_activity` takes only
  `&ActivityInfo`, and it runs the `#[activity]` body (issue #2024). The
  old two-argument form is now `register_activity_with_body`.
- `autumn-harvest-sqlite`: `RunState` has the new variants `WaitingMutex`,
  `TimedOut`, `Cancelled`, `Terminated`, `ContinuedAsNew` and
  `WaitingWorkflow` (issues #2021, #2023, #2026 and #2029). An exhaustive
  `match` on `RunState` needs an arm for each.
- `policy::validate_schedule` rejects an interval period over
  `policy::MAX_INTERVAL_PERIOD`, 100 years of 365 days (issue #2048). Before
  this change, such a period never fired in practice, or it made the
  scheduler panic. `HarvestBuilder::try_build` returns the error, and
  `HarvestBuilder::build` panics. A registration through the runtime or the
  management API fails too. Use `Schedule::Manual` for a schedule that never
  fires.

### 1.16 The retention scan has a new index — RUN THE MIGRATION

The retention janitor selects terminal runs in six states, `TERMINATED`
included. Its partial index, `idx_harvest_we_retention_scan`, covered five.
So each retention tick read the whole of `harvest_workflow_executions`, on
every shard (issue #2395).

**Who is affected.** Every deployment that runs retention.

**What to do.** Run migration
`20261029034500_harvest_retention_candidates_index`. It builds
`idx_harvest_we_retention_candidates` and drops the old index. A plain build
blocks state changes on the table until it ends. On a large table, build the
new index `CONCURRENTLY` first, then drop the old one `CONCURRENTLY`. See
[the migration table](0.5.0.md) for both statements.

### 1.17 Scaling signals, canary status and rebalance use an index — RUN THE MIGRATION

Before this release, four statements read a whole table (issue #2424):

- the per-queue task counts of the scaling signals, which an autoscaler polls;
- the canary rows of `GET /admin/canary`;
- the cross-shard child check of a shard rebalance;
- the timer copy and delete of a shard rebalance.

**Who is affected.** Every deployment. The scaling signals and the canary
status read more rows as history grows.

**What to do.** Run migration `20261030015439_harvest_census_scan_indexes`. It
builds three indexes. A plain build blocks writes to its table until it ends.
On a large table, build each index `CONCURRENTLY` first. The header of the
migration's `up.sql` gives the statements. See [the migration table](0.5.0.md)
for the detail.

**Behaviour change.** `GET /admin/queues/scaling` and `GET /admin/metrics`
now count live tasks only. A queue with only finished tasks and no active
worker no longer appears. Before, it appeared with all counts at zero until
retention purged its rows. Its `harvest_queue_*` series disappear, so an
`absent()` alert on that queue can fire.

### 1.18 Signal reads by execution use an index — RUN THE MIGRATION

Before this release, four statements read the whole of `harvest_signals`
(issue #2367):

- the signal move of a workflow-level retry;
- the signal scrub of a PII erasure;
- the signal copy and delete of a shard rebalance;
- each `ON DELETE CASCADE` from an execution, which retention triggers.

**Who is affected.** Every deployment. Each retry and each retention delete
read more rows as the signal table grows.

**What to do.** Run migration `20261030182800_harvest_signals_exec_index`. It builds
`idx_harvest_signals_exec`. A plain build blocks signal writes until it
ends. On a large table, build the index `CONCURRENTLY` first. The header of
the migration's `up.sql` gives the statement. See
[the migration table](0.5.0.md) for the detail.

## 2. Dependency and plugin changes

### 2.1 `autumn-web` 0.9 — REQUIRED

**What changed.** Harvest `0.8.0` depends on `autumn-web` 0.9. In `0.7.0`,
it depended on 0.8. Cargo treats 0.8 and 0.9 as different crates. An app
that keeps `autumn-web = "0.8"` compiles two copies. `HarvestPlugin` then
does not implement the app's `Plugin` trait, and the build fails.

**Who is affected.** Every app that has its own `autumn-web` entry next to
`autumn-harvest-plugin`. An app that mounts `HarvestPlugin` always has one.
A `HarvestEmbedding` app with no `autumn-web` entry needs only the Harvest
bump.

**What to do.**

1. Follow Autumn's own
   [0.8 → 0.9 migration guide](https://github.com/autumn-foundation/autumn/blob/trunk/docs/migrations/0.9.0.md).
   Run `autumn upgrade` before you bump `autumn-web`. Most of its breaks are
   new fields on framework structs, such as `Route::criticality`.
2. Bump the three crates in one change:

   ```toml
   [dependencies]
   autumn-harvest = { version = "0.8", features = ["db"] }
   autumn-harvest-plugin = "0.8"
   autumn-web = "0.9"
   ```

Harvest needed one source change for 0.9. Its generated webhook, MCP tool
and MCP task routes set `criticality: Criticality::Default`, the value that a
route attribute without `criticality` gives. The MSRV stays at 1.88.0.

**How to check.** `cargo tree -i autumn-web` shows one `autumn-web v0.9`.

### 2.2 The `prod` profile checks config keys — BEHAVIOR CHANGE

**What changed.** In `autumn-web` 0.9, the `prod` profile sets
`server.strict_config = true`. An unknown top-level table in `autumn.toml`
then stops the boot. Autumn's schema does not know `[harvest]`, so a plugin
must declare that table as its own.

`HarvestPlugin` now declares `[harvest]` through
`AppBuilder::config_section`. The check accepts the table and does not read
its keys. Harvest reads them as before. The root name is the public constant
`autumn_harvest_plugin::config::HARVEST_CONFIG_ROOT`.

**Who is affected.** An app that runs with `AUTUMN_PROFILE=prod`, or sets
`strict_config = true`, and has a `[harvest]` table. With Harvest `0.7.0` on
`autumn-web` 0.9, such an app does not boot. With Harvest `0.8.0` it boots.

**What to do.** Nothing for `[harvest]`. A typo in another top-level table
still stops the boot. Fix the key. Do not set `strict_config = false` to
hide it.

### 2.3 Other `prod` defaults that reach Harvest — BEHAVIOR CHANGE

`autumn-web` 0.9 adds these `prod` defaults. Each one also applies to the
routes that `HarvestPlugin` mounts.

- **Load shedding.** `server.max_concurrent_requests` defaults to the primary
  pool size × 32, and at least 256. Under overload, a management API or
  Vantage request can get `503` with `Retry-After`. Generated Harvest routes
  have `default` criticality.
- **Statement timeout.** `database.statement_timeout` defaults to `30s`.
  Autumn sets it on each connection that its `Db` extractor or a repository
  checks out. In `embedded` mode, Harvest uses the same pool, so a Harvest
  query on such a connection can stop at 30 s too. Harvest's own maintenance
  paths set their own `SET LOCAL statement_timeout`. If a scanner or
  retention pass logs `canceling statement due to statement timeout`, raise
  `database.statement_timeout`, or run Harvest in `split` mode.
- **Readiness.** `/ready` pings the primary database. In `embedded` mode,
  that is also the Harvest database.

### 2.4 `HarvestPlugin` declares `autumn-web` 0.9 — NO ACTION

The plugin contract from `0.7.0` now declares `autumn-web = "0.9"`.
`AppBuilder::plugin` panics if the framework version is outside that range.
`autumn-harvest-plugin` 0.8 always brings `autumn-web` 0.9, so the check
passes in a build that compiles.

### 2.5 Framework migrations — no action

`autumn-web` 0.9 adds framework migrations, among them
`20261005143012_create_lease_locks`,
`20261005200000_create_idempotency_keys`,
`20261022120000_add_version_to_job_tracking` and
`20261026170000_add_jobs_queue_name_ready_index`. None of them shares a
version with a Harvest migration. The six versions that Harvest shares with
Autumn's job-queue set are unchanged since `0.6.0`. See
[`upgrading/0.7.0.md`](0.7.0.md) §2.4.

`20261026170000_add_jobs_queue_name_ready_index` builds its index on
`autumn_jobs` without `CONCURRENTLY`. Harvest does not use `autumn_jobs`. If
your app has a large ready backlog there, follow Autumn's guide and build
the index first.
