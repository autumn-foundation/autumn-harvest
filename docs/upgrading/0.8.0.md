# Upgrading from 0.7.0 to 0.8.0

This guide covers the move from `0.7.0` to the next release, `0.8.0`. It
grows as changes merge into `trunk-dev`. Section 1 lists the breaking and
behavior changes in Harvest.

Do the steps in this order:

1. Read section 1 and choose an option for each change that affects you.
2. Bump the crates together.
3. Run `cargo check`, then your tests.
4. Run the migrations, then deploy.

---

## 1. Breaking and behavior changes

### 1.1 Decision boundaries are opt-in

**What changed (issue #1833).** A worker can append one `DecisionCommitted`
event after each decision that writes events. The event names the build id
and the worker id of that decision. See
[Decision boundaries](../decision-boundaries.md).

Boundaries are **off by default** in `0.8.0`. A process older than `0.8.0`
cannot decode `DecisionCommitted`, and the
[rolling-deploy contract](README.md) forbids writing a new event variant by
default. Every `0.8.0` process reads boundaries. A later release turns them
on by default.

**Who is affected.** Only a deployment that turns boundaries on. An upgrade
that leaves them off changes nothing in the history.

**What to do.**

1. Upgrade every process that reads history to `0.8.0`: workers, timeout
   leaders, API nodes, Vantage and the `harvest` CLI.
2. Then turn boundaries on for the workers:

   ```rust
   let harvest = HarvestBuilder::new()
       .record_decision_boundaries(true)
       // ... the rest of your configuration
       .build();
   ```

   A `HandlerRegistry` takes
   `WorkflowHistoryPolicy::with_decision_boundaries(true)`.
3. If a workflow runs close to a history limit, raise that limit first.

A process older than `0.8.0` fails on a history that holds a boundary:

- An old worker fails the execution for good.
- An old timeout leader cannot enforce activity timeouts for that run. It
  reports the error on every pass.
- An old API node, Vantage page or `harvest` CLI cannot show, export or
  cancel that run.

So do not roll back to `0.7.0` after a worker wrote boundaries. Turning
them off again stops new boundaries, but the rows already written stay.

Boundaries count toward the history limits. A run with one activity per
decision has about one third more events. These limits count them:

- `history_event_hard_cap`, which defaults to 50,000 events (issue #1804),
  and `history_continue_as_new_threshold`, and so
  `ctx.should_continue_as_new()`;
- `max_workflow_history_events`, the ceiling of the timeout scanner;
- the history-bloat warning, which is a fraction of the hard cap;
- the `history_bytes` quota, about 131 bytes for each boundary.

**How to check.** This query counts the boundaries. It stays at 0 while
boundaries are off:

```sql
SELECT count(*) FROM harvest_events WHERE event_type = 'DecisionCommitted';
```

### 1.2 The claim reads a bounded window and sets its own planner settings

**What changed (issue #1971).** The default claim reads a bounded window from
the head of each polled queue. It runs the old full scan only when the window
cannot prove its pick. The claim order does not change. See
[the seek window](../performance.md#the-seek-window-issue-1971).

The claim transaction now does four more things:

- It runs `SET LOCAL jit = off; SET LOCAL plan_cache_mode =
  force_generic_plan; SET LOCAL enable_bitmapscan = off` before the claim.
  This is one more round trip. The settings end with the transaction. A
  server or role setting for `jit`, `plan_cache_mode` or
  `enable_bitmapscan` no longer applies to the claim transaction. A claim
  with priority ageing on leaves out the bitmap setting.
- It keeps the claim statement as a prepared statement on each connection.
  Other Harvest statements already do this. `pg_prepared_statements` shows
  it, and `auto_explain` shows a generic plan.
- It returns a fixed column list, so a migration that adds a column to
  `harvest_task_queue` does not break the cached statement.
- A claim on a capped concurrency key counts the key again after the
  claim, in a fresh snapshot. If the key is over its cap, the claim gives
  the row back. This closes a race that let a key run tasks over its cap.
  Such a claim costs one more round trip. The by-id and batched claims run
  this re-check too.

**Who is affected.** A deployment that tunes `jit`, `plan_cache_mode` or
`enable_bitmapscan` for the engine role, or that reads `pg_stat_statements`
per claim.

**What to do.** Run migration
`20261008042107_harvest_task_queue_claim_seek_index`. A large table needs the
out-of-band `CREATE INDEX CONCURRENTLY` first. See
[the migration table](0.5.0.md). A new binary without the index still claims
correctly. Its claim then reads the whole backlog, as the old claim did.

### 1.3 The usage report carries the agent cost ledger

**What changed (issue #1996).** An activity can record each LLM call with
`ActivityContext::record_llm_call`. The engine writes the model id, the
tokens, the cost and the latency to `harvest_llm_ledger`, outside the
encrypted payload. Each group of `GET /admin/usage` gains six `llm_*`
fields. The `harvest usage` table gains five columns. The
`agent_model_turn` activity of `autumn-harvest-agent` records one call per
model turn.

**Who is affected.** A script that parses the `harvest usage` table by
column position. A deployment that runs the agent adapter on Postgres: each
model turn now writes one small row. A security review: the ledger fields
are in clear. See [the security posture](../security-posture.md#llm-cost-ledger-issue-1996).

**What to do.**

1. Run migration `20261009050156_harvest_llm_ledger` before you deploy the
   new binary. A worker of this release fails a completion that records a
   call while the table is missing. The activity then runs again after its
   lease expires, and the provider bills the model call again.
2. A role with per-table grants needs `SELECT`, `INSERT` and `DELETE` on
   `harvest_llm_ledger`. `harvest preflight` checks them.
3. On a cross-region DR standby, run the migration first. Then run
   `ALTER SUBSCRIPTION ... REFRESH PUBLICATION`, so the table replicates.
4. Do not run a shard rebalance from an older binary after the migration.
   An older binary leaves the ledger rows on the sealed source, and the
   report then skips them.
5. Parse `harvest usage --json`, not the table.
6. To name the model in the agent ledger, implement `AgentModel::model_id`
   and `AgentModel::cost_usd_micros`.

See [the agent cost ledger](../llm-cost-ledger.md).
