# Upgrading from 0.6.0 to 0.7.0 (unreleased)

This guide collects the breaking changes merged after `0.6.0`. It grows until
`0.7.0` ships.

---

## 1. Breaking and behavior changes

### 1.1 Mutating routes fail closed outside `dev` — BREAKING DEFAULT

**What changed (issue #1802).** Outside the `dev` profile, a management API
with no declared auth layer now refuses every mutating route with `401`. In
`0.6.0`, only the admin-gated routes did. These routes were open to any
caller. They now fail closed:

- workflow start, `signal-with-start`, `update-with-start`, signal (by
  execution id and by business id), reset and update;
- DAG trigger, DAG `PATCH` and DAG run retry;
- schedule create, update, delete, pause, resume and backfill;
- external-activity `complete`, `fail` and `heartbeat`;
- worker drain;
- every Vantage `/ui` form post;
- the mutating MCP tool routes: `start_{wf}`, `start_{dag}`, `signal_{wf}`
  and `{wf}_update_{name}`.

Read routes do not change. The `dev` profile does not change.

**Who is affected.** A deployment is affected when all three are true:

1. The profile is not `dev`. `HarvestEmbedding` and a raw router with no
   declared profile use `unknown`, which is not `dev`.
2. The API is mounted with `HarvestPlugin::api(..)`, with `HarvestEmbedding`,
   or with a raw `harvest_api_router`. No auth boundary is declared. An app
   that enables `HarvestPlugin::mcp_tools()` with no `api_with_auth` also
   counts, even when it uses `secure_mcp`.
3. A client calls one of the routes above with no admin session and no scoped
   token. Remote workers that call the external-activity callbacks count.

**Check your profile.** autumn-web reads `AUTUMN_ENV`, then `AUTUMN_PROFILE`,
then `--profile`. With none of them, a release build from
`#[autumn_web::main]` resolves to `prod`. Any other build resolves to `dev`,
which leaves the routes open. Set the profile explicitly.

**What to do.** Pick one:

| Option | Change |
|---|---|
| Add an auth layer (recommended) | `HarvestPlugin::api_with_auth(path, middleware)`, or `StandaloneAdminAuth::with_admin_auth_boundary()` behind your own middleware. It also covers `secure_mcp` callers of the MCP tools. |
| Use scoped API tokens | `HarvestPlugin::enable_api_tokens()` or `StandaloneAdminAuth::with_api_tokens()`, and a `mutate` token on each client. Tokens do not cover the MCP tool routes. A `mutate` token also admits every admin route. |
| Keep the old posture for now | `HarvestPlugin::allow_unauthenticated_mutations()`, `StandaloneAdminAuth::allow_unauthenticated_mutations()` or `HarvestApiState::set_allow_unauthenticated_mutations(true)` |

Outside `dev`, the opt-out makes `HarvestPlugin` and `HarvestEmbedding` log a
`tracing::warn!` at startup. Remove it once an auth layer is in place.

**How to check.** `GET /admin/preflight` reports
`unauthenticated_mutations` on the `admin_auth_boundary` check. It is `true`
when a caller with no credential can reach a mutating route. The check fails
when the opt-out opens the routes outside `dev`. An anonymous
`POST /workflows/{name}/start` against a non-`dev` deployment must return
`401`.

See [`security-posture.md`](../security-posture.md#fail-closed-mutations-issue-1802)
for the full rule.

### 1.2 Default history event cap and byte cap — BREAKING DEFAULT

**What changed (issue #1804).** The worker now caps each run's history by
default. In `0.6.0`, both caps were off.

| Setting | `0.6.0` | `0.7.0` |
|---|---|---|
| `history_event_hard_cap` | none | `50_000` events |
| `history_byte_hard_cap` (new) | none | 50 MiB of stored `event_data` |
| `history_bloat_warn_fraction` | `0.75` | `0.2` |

A run that reaches a cap and does not `continue_as_new` fails. It moves to
the DLQ with `HistoryCapExceeded` or with the new `HistoryBytesCapExceeded`.
The byte measure is `pg_column_size(event_data)`, the same as the tenant
`max_history_bytes` quota.

`harvest.workflow.history_bloat` now fires at 10,000 events under the default
cap. The worker also logs a `tracing::warn!` at that point.

**Who is affected.**

- A run that legitimately grows past 50,000 events or 50 MiB without
  `continue_as_new`. An in-flight run already past a cap fails on its next
  decision.
- A deployment that set `history_continue_as_new_threshold` to `50_000` or
  more. The cap now fires before the advisory. `try_build` logs a warning.
- A deployment that set `max_workflow_history_events` above `50_000`. The
  worker cap now fires first.
- A deployment that set `history_event_hard_cap` but not
  `history_bloat_warn_fraction`. The warning now fires at 20% of the cap,
  not 75%.
- Code that matches `DeadLetterReason` exhaustively. Add an arm for
  `HistoryBytesCapExceeded`.

**What to do.**

| Goal | Change |
|---|---|
| Raise a cap | `.history_event_hard_cap(n)` or `.history_byte_hard_cap(n)` |
| Keep the `0.6.0` behaviour | `.history_event_hard_cap_unlimited()` and `.history_byte_hard_cap_unlimited()` |
| Keep the old warning point | `.history_bloat_warn_fraction(0.75)` |

With no event cap, the history-bloat warning does not fire.

**How to check.** Before you upgrade, find the runs that a cap would fail:

```sql
SELECT e.workflow_exec_id, COUNT(*) AS events,
       SUM(pg_column_size(e.event_data)) AS bytes
FROM harvest_events e
JOIN harvest_workflow_executions x ON x.id = e.workflow_exec_id
WHERE x.state IN ('RUNNING', 'PAUSED')
GROUP BY e.workflow_exec_id
HAVING COUNT(*) >= 50000 OR SUM(pg_column_size(e.event_data)) >= 52428800;
```

No migration, no new `WorkflowEvent` variant, and no `harvest_events` write.
