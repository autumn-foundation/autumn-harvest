# Upgrading from 0.6.0 to 0.7.0 (unreleased)

This guide collects the breaking changes merged after `0.6.0`. It grows until
`0.7.0` ships.

---

## 1. Breaking and behavior changes

### 1.1 Mutating routes fail closed outside `dev` — BREAKING DEFAULT

**What changed (issue #1802).** Outside the `dev` profile, a management API
with no declared auth layer now refuses every mutating route with `401`. In
`0.6.0`, only the admin-gated routes did. These routes were open to any
caller. They now fail closed:

- workflow start, `signal-with-start`, `update-with-start`, signal (by
  execution id and by business id), reset and update;
- DAG trigger, DAG `PATCH` and DAG run retry;
- schedule create, update, delete, pause, resume and backfill;
- external-activity `complete`, `fail` and `heartbeat`;
- worker drain;
- every Vantage `/ui` form post;
- the mutating MCP tool routes: `start_{wf}`, `start_{dag}`, `signal_{wf}`
  and `{wf}_update_{name}`.

Read routes do not change. The `dev` profile does not change.

**Who is affected.** A deployment is affected when all three are true:

1. The profile is not `dev`. `HarvestEmbedding` and a raw router with no
   declared profile use `unknown`, which is not `dev`.
2. The API is mounted with `HarvestPlugin::api(..)`, with `HarvestEmbedding`,
   or with a raw `harvest_api_router`. No auth boundary is declared. An app
   that enables `HarvestPlugin::mcp_tools()` with no `api_with_auth` also
   counts, even when it uses `secure_mcp`.
3. A client calls one of the routes above with no admin session and no scoped
   token. Remote workers that call the external-activity callbacks count.

**Check your profile.** autumn-web reads `AUTUMN_ENV`, then `AUTUMN_PROFILE`,
then `--profile`. With none of them, a release build from
`#[autumn_web::main]` resolves to `prod`. Any other build resolves to `dev`,
which leaves the routes open. Set the profile explicitly.

**What to do.** Pick one:

| Option | Change |
|---|---|
| Add an auth layer (recommended) | `HarvestPlugin::api_with_auth(path, middleware)`, or `StandaloneAdminAuth::with_admin_auth_boundary()` behind your own middleware. It also covers `secure_mcp` callers of the MCP tools. |
| Use scoped API tokens | `HarvestPlugin::enable_api_tokens()` or `StandaloneAdminAuth::with_api_tokens()`, and a `mutate` token on each client. Tokens do not cover the MCP tool routes. A `mutate` token also admits every admin route. |
| Keep the old posture for now | `HarvestPlugin::allow_unauthenticated_mutations()`, `StandaloneAdminAuth::allow_unauthenticated_mutations()` or `HarvestApiState::set_allow_unauthenticated_mutations(true)` |

Outside `dev`, the opt-out makes `HarvestPlugin` and `HarvestEmbedding` log a
`tracing::warn!` at startup. Remove it once an auth layer is in place.

**How to check.** `GET /admin/preflight` reports
`unauthenticated_mutations` on the `admin_auth_boundary` check. It is `true`
when a caller with no credential can reach a mutating route. The check fails
when the opt-out opens the routes outside `dev`. An anonymous
`POST /workflows/{name}/start` against a non-`dev` deployment must return
`401`.

See [`security-posture.md`](../security-posture.md#fail-closed-mutations-issue-1802)
for the full rule.

### 1.2 Activities time out after 10 minutes by default — BREAKING DEFAULT

**What changed (issue #1808).** `WorkerConfig::default()` now sets
`default_activity_start_to_close` to `DEFAULT_ACTIVITY_START_TO_CLOSE`
(10 minutes). In `0.6.0`, the field was `None`. With that value, a regular
activity with no timeout of its own could run forever and hold a worker slot.

The default is the last step of the #620 precedence chain:

1. call-site override;
2. `#[activity(start_to_close = ...)]`;
3. `default_activity_start_to_close` (now 10 minutes).

The default applies only to an activity type with no `start_to_close`, no
`schedule_to_close` and no `heartbeat_timeout`. Each of these already bounds
a running attempt. This rule also applies to a default that you set with
`with_default_activity_start_to_close`. In `0.6.0`, that default applied to
every activity type with no `start_to_close`.

A timeout fails the activity call. The scanner records `ActivityTimedOut`
and does not retry the attempt. The worker stores the timeout on the task row
at enqueue time. A task enqueued before the upgrade keeps the value that it
has.

**Who is affected.** A deployment is affected when it keeps the default.
It must also have an activity type with none of the three bounds above. That
type must be able to run longer than 10 minutes. `HarvestBuilder::new()`
uses `WorkerConfig::default()`, so a deployment that never builds a
`WorkerConfig` is affected too.

Two smaller cases:

- A local activity also gets the default, and
  `max_local_activity_start_to_close` caps it. At the 60 s default cap,
  nothing changes. With a cap above 10 minutes, a local attempt now stops at
  10 minutes.
- A WASM activity also gets the default. At the 300 s default
  `max_wall_clock`, nothing changes.

External activities do not change. A `harvest_external_tasks` row has its
own `schedule_to_close`.

**What to do.** Pick one:

| Option | Change |
|---|---|
| Declare a timeout (recommended) | `#[activity(start_to_close = "2h")]` on each long activity type. |
| Raise the fleet default | `WorkerConfig::default().with_default_activity_start_to_close(Duration::from_secs(7200))` |
| Keep the old behavior | `WorkerConfig::default().without_default_activity_start_to_close()`. The startup warning then says that the listed types can run forever. |

**How to check.** At build time, `HarvestBuilder::try_build` logs one `WARN`
line. The line names each regular activity type that the default governs.
`GET /admin/config` reports the active value as
`worker.default_activity_start_to_close_ms`.

See [`07-reliability-knobs.md`](../getting-started/07-reliability-knobs.md)
for the full precedence.

### 1.3 Workers drain in 25 seconds by default — BREAKING DEFAULT

**What changed (issue #1813).** `WorkerConfig::default()` now sets
`shutdown_timeout` to `DEFAULT_SHUTDOWN_TIMEOUT` (25 s). In `0.6.0`, it was
30 s. That is the Kubernetes default `terminationGracePeriodSeconds`, so the
platform could kill a pod at the moment its drain ended.

The drain also hands work over now:

- A claimed task that has not started goes back to `PENDING` at once. It
  does not use an attempt.
- One join window before the deadline, the worker cancels its running
  activities. The join window is `cancellation_grace_period`, capped at half
  the drain. `ActivityContext::is_cancelled()` turns true, and
  `heartbeat()` returns `ActivityCancelled`.
- A cancelled handler that returns a retryable error goes back to `PENDING`
  at once. A peer runs the next attempt, even past `max_attempts`. The next
  attempt's `previous_failure()` starts with `worker shutdown:`. The heartbeat
  details stay.
- A handler that ignores the cancel keeps its claim. The worker never aborts
  it.

**Who is affected.** A deployment is affected when it keeps the default and
relies on a 30 s drain. A drained attempt also counts as a failed attempt in
`harvest.activity.attempts` and `harvest.activity.failed`, so a deploy can
show a short spike there.

**What to do.** Keep `shutdown_timeout` at least 5 s below the platform grace
period. To restore 30 s, raise `terminationGracePeriodSeconds` to 35 s or
more, then set `shutdown_timeout: Duration::from_secs(30)` on the
`WorkerConfig`. A long activity that must not restart should heartbeat a
checkpoint and check `is_cancelled()`.

**How to check.** `GET /admin/config` reports the active value as
`worker.shutdown_timeout_ms`.
