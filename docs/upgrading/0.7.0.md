# Upgrading from 0.6.0 to 0.7.0 (unreleased)

This guide collects the breaking changes merged after `0.6.0`. It grows until
`0.7.0` ships.

---

## 1. Breaking and behavior changes

### 1.1 Mutating routes fail closed outside `dev` — BREAKING DEFAULT

**What changed (issue #1802).** Outside the `dev` profile, a management API
with no declared auth layer now refuses every mutating route with `401`. In
`0.6.0`, only the admin-gated routes did. These routes were open to any
caller. They now fail closed:

- workflow start, `signal-with-start`, `update-with-start`, signal (by
  execution id and by business id), reset and update;
- DAG trigger, DAG `PATCH` and DAG run retry;
- schedule create, update, delete, pause, resume and backfill;
- external-activity `complete`, `fail` and `heartbeat`;
- worker drain;
- every Vantage `/ui` form post;
- the mutating MCP tool routes: `start_{wf}`, `start_{dag}`, `signal_{wf}`
  and `{wf}_update_{name}`.

Read routes do not change. The `dev` profile does not change.

**Who is affected.** A deployment is affected when all three are true:

1. The profile is not `dev`. `HarvestEmbedding` and a raw router with no
   declared profile use `unknown`, which is not `dev`.
2. The API is mounted with `HarvestPlugin::api(..)`, with `HarvestEmbedding`,
   or with a raw `harvest_api_router`. No auth boundary is declared. An app
   that enables `HarvestPlugin::mcp_tools()` with no `api_with_auth` also
   counts, even when it uses `secure_mcp`.
3. A client calls one of the routes above with no admin session and no scoped
   token. Remote workers that call the external-activity callbacks count.

**Check your profile.** autumn-web reads `AUTUMN_ENV`, then `AUTUMN_PROFILE`,
then `--profile`. With none of them, a release build from
`#[autumn_web::main]` resolves to `prod`. Any other build resolves to `dev`,
which leaves the routes open. Set the profile explicitly.

**What to do.** Pick one:

| Option | Change |
|---|---|
| Add an auth layer (recommended) | `HarvestPlugin::api_with_auth(path, middleware)`, or `StandaloneAdminAuth::with_admin_auth_boundary()` behind your own middleware. It also covers `secure_mcp` callers of the MCP tools. |
| Use scoped API tokens | `HarvestPlugin::enable_api_tokens()` or `StandaloneAdminAuth::with_api_tokens()`, and a `mutate` token on each client. Tokens do not cover the MCP tool routes. A `mutate` token also admits every admin route. |
| Keep the old posture for now | `HarvestPlugin::allow_unauthenticated_mutations()`, `StandaloneAdminAuth::allow_unauthenticated_mutations()` or `HarvestApiState::set_allow_unauthenticated_mutations(true)` |

Outside `dev`, the opt-out makes `HarvestPlugin` and `HarvestEmbedding` log a
`tracing::warn!` at startup. Remove it once an auth layer is in place.

**How to check.** `GET /admin/preflight` reports
`unauthenticated_mutations` on the `admin_auth_boundary` check. It is `true`
when a caller with no credential can reach a mutating route. The check fails
when the opt-out opens the routes outside `dev`. An anonymous
`POST /workflows/{name}/start` against a non-`dev` deployment must return
`401`.

See [`security-posture.md`](../security-posture.md#fail-closed-mutations-issue-1802)
for the full rule.

### 1.2 Activities time out after 10 minutes by default — BREAKING DEFAULT

**What changed (issue #1808).** `WorkerConfig::default()` now sets
`default_activity_start_to_close` to `DEFAULT_ACTIVITY_START_TO_CLOSE`
(10 minutes). In `0.6.0`, the field was `None`. With that value, a regular
activity with no timeout of its own could run forever and hold a worker slot.

The default is the last step of the #620 precedence chain:

1. call-site override;
2. `#[activity(start_to_close = ...)]`;
3. `default_activity_start_to_close` (now 10 minutes).

The default applies only to an activity type with no `start_to_close`, no
`schedule_to_close` and no `heartbeat_timeout`. Each of these already bounds
a running attempt. This rule also applies to a default that you set with
`with_default_activity_start_to_close`. In `0.6.0`, that default applied to
every activity type with no `start_to_close`.

A timeout fails the activity call. The scanner records `ActivityTimedOut`
and does not retry the attempt. The worker stores the timeout on the task row
at enqueue time. A task enqueued before the upgrade keeps the value that it
has.

**Who is affected.** A deployment is affected when it keeps the default.
It must also have an activity type with none of the three bounds above. That
type must be able to run longer than 10 minutes. `HarvestBuilder::new()`
uses `WorkerConfig::default()`, so a deployment that never builds a
`WorkerConfig` is affected too.

Two smaller cases:

- A local activity also gets the default, and
  `max_local_activity_start_to_close` caps it. At the 60 s default cap,
  nothing changes. With a cap above 10 minutes, a local attempt now stops at
  10 minutes.
- A WASM activity also gets the default. At the 300 s default
  `max_wall_clock`, nothing changes.

External activities do not change. A `harvest_external_tasks` row has its
own `schedule_to_close`.

**What to do.** Pick one:

| Option | Change |
|---|---|
| Declare a timeout (recommended) | `#[activity(start_to_close = "2h")]` on each long activity type. |
| Raise the fleet default | `WorkerConfig::default().with_default_activity_start_to_close(Duration::from_secs(7200))` |
| Keep the old behavior | `WorkerConfig::default().without_default_activity_start_to_close()`. The startup warning then says that the listed types can run forever. |

**How to check.** At build time, `HarvestBuilder::try_build` logs one `WARN`
line. The line names each regular activity type that the default governs.
`GET /admin/config` reports the active value as
`worker.default_activity_start_to_close_ms`.

See [`07-reliability-knobs.md`](../getting-started/07-reliability-knobs.md)
for the full precedence.

### 1.3 Empty `build_id` cannot claim pinned runs — BREAKING

**What changed (issue #1805).** A worker with an empty `build_id` no longer
claims a run pinned to a build. Before, such a worker claimed any pinned run.
Unpinned runs and queues with no build policy are unchanged.

**Who is affected.** Workers that use the default `WorkerConfig` on a queue
with a build policy. Pinned runs stay `PENDING` while only these workers poll.

**How to detect.** The worker logs a warning at registration. It also sets
`harvest.worker.empty_build_policy{queue}`. The starter dashboard shows it.

**Fix.** Call `with_build_id(...)` on every worker before you advance the
policy. See [`safe-deploy.md`](../runbooks/safe-deploy.md).

### 1.4 Finished task rows are deleted after 7 days — BEHAVIOR CHANGE

**What changed (issue #1811).** The retention janitor now deletes
`harvest_task_queue` rows in `COMPLETED`, `FAILED` or `CANCELLED` state
when `completed_at` is more than 7 days old. In `0.6.0`, these rows went
only when their execution was deleted. History retention is off by
default, so the rows stayed forever.

The janitor never deletes a `PENDING` or `RUNNING` row. It keeps a finished
workflow-task row while its execution is still live, or while a dead letter
exists for the execution. It skips a row that another transaction holds.

Each shard deletes at most 50 batches of `batch_size` rows per tick. At the
default `batch_size` (1,000) and the hourly tick, that is 50,000 rows per
shard per hour. A shard that finishes more tasks per hour falls behind, and
a large backlog drains over many ticks. Raise `batch_size` (capped at
10,000 per statement) or lower `tick_interval_secs` to go faster. A
per-shard `deleted` equal to the budget in `GET /admin/retention` means
rows remain.

`RetentionConfig::enabled()` counts the janitor, so the retention runtime
now spawns even when every other pass is off.

Migration `20261003201739_harvest_task_queue_hygiene` also tunes the table.
It sets autovacuum to start at 2% dead rows and sets a fillfactor of 80.
It adds two indexes for the janitor, replaces one index and drops two.

**Who is affected.** Every deployment that does not call
`without_terminal_task_gc()`. A `RetentionConfig` built from `default()` or
`with_max_age()` has the janitor on. A tool that reads old finished rows
from `harvest_task_queue` no longer finds them.
These admin routes return `404` for a deleted row:

- `POST /workflows/{id}/activities/{activity_exec_id}/fail-now` and
  `.../retry-now`;
- `PATCH /tasks/{id}`;
- `GET /admin/tasks/{id}/eligibility`.

**What to do.**

1. Grant `DELETE` on `harvest_task_queue` to the runtime role.
   `GET /admin/preflight` now checks this grant. Without it, each sweep
   fails and reports the error in `GET /admin/retention`.
2. On a large live table, run the statements at the top of the
   migration's `up.sql` before you migrate. Run them one at a time, outside
   a transaction, as the table owner. Otherwise the index builds hold a
   `SHARE` lock and the drops hold an `ACCESS EXCLUSIVE` lock, which block
   enqueue, claim and completion.
3. To preview the janitor, set `RetentionConfig::dry_run`. The janitor
   then reports what it would delete and deletes nothing.
4. The first sweep of a large backlog leaves many dead rows, and claims
   slow down until vacuum runs. Run `VACUUM (ANALYZE) harvest_task_queue`
   after that sweep, or let autovacuum finish. See
   [`performance-task-queue-hygiene.md`](../performance-task-queue-hygiene.md).

| Option | Change |
|---|---|
| Keep the default (recommended) | Nothing. |
| Keep rows longer | `RetentionConfig::default().with_terminal_task_retention(Duration::from_secs(30 * 86_400))` |
| Keep the old behavior | `RetentionConfig::default().without_terminal_task_gc()`. `GET /admin/preflight` still requires `DELETE` on `harvest_task_queue`. |

**How to check.** `GET /admin/retention` shows `terminal_task_gc` for each
shard: the rows deleted per state, `dry_run`, and any `error`. The counter
`harvest.retention.terminal_tasks_deleted` counts real deletes per `state`.

### 1.5 Continuations are claimed before new starts — BEHAVIOR CHANGE

**What changed (issue #1824).** Two claim rules now apply by default.

- **Order.** At equal effective priority, the first workflow task of a
  freshly admitted run sorts as if it were due 30 seconds later. So under a
  backlog, activity tasks and woken workflow tasks of running workflows go
  first. A new start waits at most 30 seconds behind later continuations.
  An explicit priority still wins. Child starts, continue-as-new, reset
  forks, workflow retries and DLQ redrives count as continuations.
- **Run deadline.** A claim skips a task whose `RUNNING` run is past
  `deadline_at` or `chain_deadline_at`. The task stays `PENDING` and does
  not run. The timeout scanner then times out the run and fails the task.
  The task error now starts with `deadline_exceeded: `, followed by the
  timeout error. This prefix is new for every open task of a timed-out run.

Migration `20261004162927_harvest_task_queue_new_start` adds
`harvest_task_queue.new_start BOOLEAN NOT NULL DEFAULT FALSE`. The start
path sets it. A row from before the upgrade keeps `FALSE`, so its order
does not change. The migration fails after a 5-second lock wait, so claims
do not queue behind it. Re-run it after the blocker clears.

**Who is affected.** A deployment whose queues build a backlog. With idle
capacity, workers claim every due task at once, and the order does not
matter. A deployment that sets `execution_timeout` or
`chain_execution_timeout` also sees the new task error prefix. A tool that
matches the exact task error of a timed-out run must allow the prefix.

**What to do.** Nothing. To find the skipped tasks, see
[`operations/claim-order.md`](../operations/claim-order.md).

**How to check.** Query `harvest_task_queue` for `FAILED` rows whose
`error` starts with `deadline_exceeded:`.
