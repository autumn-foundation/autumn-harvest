# Upgrading from 0.5.0 to 0.6.0

This guide covers everything you need to move an autumn-harvest deployment from
`0.5.0` to `0.6.0`: the dependency-version bumps, the change in **who owns
applying migrations**, and the small set of source-breaking changes to verify
against your own code.

The defining change of this release is that **Autumn now owns Harvest's
migrations**. If you mount `HarvestPlugin` the standard way and run in the
default `embedded` mode, this is a pure upgrade-and-go: bump the crate versions
and you are done — there is nothing to wire up, and no new manual step.

---

## 1. Dependency upgrades

| Dependency | 0.5.0 | 0.6.0 | Notes |
|------------|-------|-------|-------|
| `autumn-web` | 0.6 | **0.7** | Required. Brings `AppBuilder::plugin_migrations`, which this release adopts. One source-breaking change if you construct `autumn_web::Route` by hand — see §3.1. |
| `rusqlite` (for `autumn-harvest-sqlite`) | 0.39 | **0.40** | Required even if you do not use the SQLite backend — see §1.1. |
| **MSRV** | 1.88.0 | **1.88.0** | Unchanged. |

The `wasm-activities` feature (opt-in, R&D) still carries an effective MSRV of
1.94 (wasmtime's own minimum); it is never compiled by the default build, so it
does not raise the crate MSRV for any non-`wasm` consumer.

### 1.1 The `rusqlite` bump is not optional

`autumn-web` 0.7 depends on `libsqlite3-sys` 0.38, while `rusqlite` 0.39 pins
0.37. `libsqlite3-sys` declares `links = "sqlite3"`, and Cargo permits only one
package in a dependency graph to claim a given `links` value — so the two
cannot coexist and resolution fails outright:

```
error: failed to select a version for `libsqlite3-sys`.
package `libsqlite3-sys` links to the native library `sqlite3`, but it
conflicts with a previous package which links to `sqlite3` as well
```

This bites **even if you never enable the `sqlite` feature on either crate**,
because Cargo resolves versions for optional dependencies too. Bump `rusqlite`
to `0.40` (which pins `libsqlite3-sys` 0.38) and the conflict clears.

## 2. Autumn now owns Harvest's migrations

Previously `HarvestPlugin` applied its own embedded migration sets from inside
its `on_startup` hook. As of 0.6.0 it **registers** them with Autumn instead,
via autumn-web 0.7's `AppBuilder::plugin_migrations`, and Autumn applies them
during its own database setup.

### What you get

- **Cross-plugin version-collision resolution.** Diesel's
  `__diesel_schema_migrations` table is keyed by version *alone*, with no notion
  of which source recorded a version. Nothing coordinates timestamps across a
  plugin, the framework, and your app, so two independently authored migrations
  reusing one version — e.g. both picking an all-zero placeholder for their
  first migration — was entirely possible. Applied naively, whichever ran first
  won the version and every other same-versioned migration was skipped forever
  as "already applied" even though its `up.sql` never ran. Autumn now sees every
  registered set at once and transparently tracks the loser under a substitute
  version, so **both** still apply. It logs this at `INFO` rather than doing it
  silently.
- **Easier plugin assembly.** Registration is declarative, so adding Harvest
  alongside other Autumn plugins no longer risks one plugin's startup migration
  step racing or shadowing another's.
- **One consistent policy.** Harvest's migrations now follow exactly the same
  dev/prod rules as your app's own and every other plugin's.

### What you need to change

**Nothing**, in the common case. The registration happens inside
`HarvestPlugin::build`, so simply mounting the plugin is enough.

### Ordering guarantee

Autumn applies registered migrations during `setup_database`, which runs
**before** any `on_startup` hook. Harvest's runtime boots in an `on_startup`
hook, so it still always observes an already-migrated database — the same
guarantee as 0.5.0, now enforced by the framework rather than by the plugin
sequencing itself.

### The dev/prod policy is unchanged

- **`dev` profile** — pending migrations are applied automatically at startup,
  so `AUTUMN_PROFILE=dev cargo run` still boots against a fresh schema with no
  manual step.
- **Non-`dev` profiles** — pending migrations are logged as warnings and **not**
  applied. Run a one-shot **`autumn migrate`** in your deploy pipeline before
  rolling web replicas, exactly as before.

### Split / external mode still applies its own Harvest migrations

`plugin_migrations` can only target the application's **primary** database.
That is the whole story under `harvest.mode = "embedded"` (the default), where
the application database *is* the Harvest database — so Autumn owns all of it.

Under `harvest.mode = "split"` or `"external"`, Harvest storage is a **separate**
database that Autumn has no handle on. Those sets are still applied by the
plugin itself, against `harvest.database.url`. Concretely:

| Migration set | Target database | `embedded` | `split` / `external` |
|---------------|-----------------|-----------|----------------------|
| Workflow-start outbox | application | Autumn | Autumn |
| Harvest core (`autumn_harvest::MIGRATIONS`) | Harvest | Autumn | plugin |
| Harvest plugin (connector dead-letters) | Harvest | Autumn | plugin |

The practical consequence for `split`/`external` operators is nil — the same
sets land in the same databases as in 0.5.0. The only difference is which
component applied them, and therefore which one participates in Autumn's
collision resolution (the application database's sets do; a dedicated Harvest
database's do not, since Autumn never sees them).

### Sharding is unchanged

Each Harvest shard database must still have the full migration set applied
manually. Autumn's own migration fan-out covers the `[[database.shards]]` it is
configured with, which are not the same thing as Harvest's `ShardRouter` shards
(`HarvestPlugin` is single-shard; multi-shard Harvest is standalone-runner
territory). See [`sharding.md`](../sharding.md) for the add-a-shard procedure.

### SQLite backend is unchanged

`autumn-harvest-sqlite` still manages its own additive schema via an idempotent
`migrate()` on `open()`; it does not consume the Postgres migration set and is
unaffected by any of this.

## 3. Breaking and behavior changes

### 3.1 `autumn_web::Route` gained a `seo` field — SOURCE-BREAKING

Only affects code that constructs `autumn_web::Route` with a **struct literal**
that lists every field. If you generate routes programmatically (most embedders
do not — this is plugin-author territory), add the new field:

```rust
autumn_web::Route {
    // ... existing fields ...
    timeout: autumn_web::RouteTimeout::Inherit,
    seo: autumn_web::SeoRouteDefaults::EMPTY,   // new in autumn-web 0.7
}
```

`SeoRouteDefaults::EMPTY` is what a route attribute without `seo(...)` produces,
so it is the correct value for any generated API route. Literals that already
end in `..Default::default()` need no change.

### 3.2 The TLS migration-connection hazard is fixed upstream

0.5.0 shipped a fix (issue #1232) for a panic — `"Cannot start a runtime from
within a runtime"` — when applying migrations against a TLS-requiring Postgres
(`sslmode=require`/`verify-ca`/`verify-full`) from an async startup hook. The
workaround was to route the blocking migration body through `spawn_blocking`.

autumn-web 0.7 fixes this at the source: `run_pending`/`pending_migrations` now
run both the connect and the migration body on a freshly spawned
`std::thread::scope` thread, which has never entered a runtime and is therefore
safe from **any** caller context.

No action required. Harvest still wraps its remaining (split/external-mode)
migration call in `spawn_blocking`, now purely so the blocking join never stalls
an async worker thread rather than for correctness.

## 4. Database migrations

0.6.0 introduces **no new migrations of its own** — the change above is about
*who applies* the existing sets, not about adding to them. Any migrations that
arrived with features in this release are listed in
[`CHANGELOG.md`](../../CHANGELOG.md) under `[0.6.0]`; each states explicitly
whether it adds a `WorkflowEvent` variant or a migration.

Apply them in timestamp order (every mechanism above does this automatically).
