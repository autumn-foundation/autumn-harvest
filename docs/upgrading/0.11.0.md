# Upgrading from 0.10.0 to 0.11.0

This guide covers the move from `0.10.0` to `0.11.0`. Section 1 lists the
breaking and behavior changes. Section 2 lists the migrations. Section 3
lists the rules for a rolling deploy of the new features. Section 4 lists
the new opt-in features. Section 5 lists the dependency changes.

`autumn-web` moves from 0.10 to 0.11. The MSRV stays at 1.97.0.

Two changes have their own guide. Read them first:

- [`autumn-web` 0.11](autumn-web-0.11.md): the bump, and the Harvest
  runtimes as Autumn background tasks.
- [`chrono` to `jiff`](chrono-to-jiff.md): the date and time types of the
  public API.

Do the steps in this order:

1. Read section 1 and fix each change that affects you. Sections 1.1 to
   1.3 affect every app.
2. Bump the Harvest crates and `autumn-web` in one change, as section 5.1
   shows.
3. Run `cargo check`, then your tests.
4. Let each pending shard move end (section 2.3). Then run the migrations
   in section 2, and deploy.
5. Turn on a new feature only after every process runs `0.11.0`. See
   section 3.

## 1. Breaking and behavior changes

### 1.1 `autumn-web` 0.11 — BREAKING

**What changed (issue #2480).** `autumn-harvest-plugin` now depends on
`autumn-web` 0.11, which adds role-aware background tasks (autumn#3545).
The public API of the plugin holds `autumn-web` types, so Cargo treats 0.10
and 0.11 as different crates. `HarvestPlugin` declares the range `0.11`.

**Who is affected.** Every app that mounts `HarvestPlugin`, and every app
that names `autumn-web` in its own manifest.

**What to do.**

1. Bump your own `autumn-web` entry to `"0.11"`. A leftover `"0.10"` builds
   two copies, and `HarvestPlugin` does not match the `AppBuilder` of the
   app.
2. Check that `cargo tree -i autumn-web` shows one version.
3. Bump `diesel` to 2.4, `diesel-async` to 0.10, `rusqlite` to 0.42 and
   `libsqlite3-sys` to 0.40 if you name them.

[`autumn-web` 0.11](autumn-web-0.11.md) sections 1 and 2 list each code
change of the bump, such as `ProcessSwitches::resolve`, which now takes
`Option<&autumn_web::config::Role>`.

### 1.2 Harvest runtimes are Autumn background tasks — BEHAVIOR CHANGE

**What changed (issue #2480).** The worker, the scheduler, the retention
janitor and the batch executor run as the Autumn background tasks
`harvest.worker`, `harvest.scheduler`, `harvest.retention` and
`harvest.batch`. Autumn places each one by the process role. A
`[roles.<name>]` preset places Harvest through the capabilities
`harvest.worker`, `harvest.scheduler` and `harvest.maintenance`.

**Who is affected.** An app that sets a named role preset, an app with a
short `server.shutdown_timeout_secs`, and an app that waits for a run in a
request during the drain.

**What to do.**

- Set `server.shutdown_timeout_secs` to at least twice
  `WorkerConfig::shutdown_timeout`. Autumn stops the Harvest loops when the
  listener stops.
- Check each `[roles.<name>]` preset. A preset with `job_workers = false`
  or `pin = []` now stops the Harvest worker. Set
  `capabilities = { "harvest.worker" = true }` to keep it.
- The batch executor now follows `harvest.maintenance`, not the worker.

[`autumn-web` 0.11](autumn-web-0.11.md) section 3 lists each behavior
change. [Process roles](../operations/process-roles.md) gives the full
model. A standalone `HarvestRunner` or `HarvestEmbedding` spawns its
runtimes as before.

### 1.3 Dates and times use `jiff` — BREAKING

**What changed ([ADR 0018](../adr/0018-jiff-date-and-time.md)).** Each
instant, duration, calendar date and time zone of the public API is a
`jiff` type. `DateTime<Utc>` is now `jiff::Timestamp`, `chrono::Duration`
is now `jiff::SignedDuration`, `NaiveDate` is now `jiff::civil::Date`, and
`chrono_tz::Tz` is now `jiff::tz::TimeZone`. `autumn_harvest::jiff`
re-exports the crate, and `autumn_harvest::chrono` is gone. No Harvest crate
depends on `chrono`.

**Who is affected.** Code that reads or builds a Harvest time value, such
as a schedule, a deadline, a calendar or a history event.

**What to do.** Follow [`chrono` to `jiff`](chrono-to-jiff.md). It maps each
type and call, and lists the recorded differences. No migration runs and no
stored data changes. A process reads each row, event and payload that an
older process wrote.

### 1.4 Batch and webhook-delivery starts take the execution timeout — BEHAVIOR CHANGE

**What changed (issue #2417).** `POST /workflows/batch_start` and the
outbound webhook-delivery start now pass the resolved execution timeout of
the type into the start, with its operator override and the fleet ceiling.
Before, a batch run had no `deadline_at`.

**Who is affected.** A type that declares an `execution_timeout`, or has an
override of it, and is started by a batch or a webhook delivery. Such a run
now times out at its deadline. A throttled batch row stored before the
upgrade keeps no timeout.

**What to do.** Check that the declared timeout of each such type fits the
work of a batch run.

### 1.5 The refine loop waits for an adoption — BEHAVIOR CHANGE

**What changed (issues #2381 and #2382).** A refine run that chose an
overlay no longer ends with `chosen`. It puts the overlay as an inactive
version, and waits on the signal `refine_approval:<run>` for the
`approval_timeout` of the policy. An allowed auto adoption goes live at
once. Each adoption adds one lesson to the lesson library of the kind.
`RefineInput::dry_run` keeps the old end. See
[the agent adapter guide](../agent-adapter.md), sections 23 and 24.

**What to do.**

1. A worker with a hand-picked activity list adds `agent_refine_adopt`,
   `agent_refine_decide`, `agent_refine_lesson`, `agent_lesson_match` and
   `agent_lesson_erase`. `workflow::activities()` holds them.
2. Approve, edit or reject a pending overlay with
   `harvest agents profile pending|approve|reject|edit`,
   `sqlite::decide_refine` or `postgres::decide_refine`.

A run that started on `0.10.0` opens no gate and ends with `chosen`.

### 1.6 An agent reset removes more — BEHAVIOR CHANGE

**What changed (issues #2382 and #2604).** `Control::ResetMemory` now
removes each lesson of the kind that names the agent, also one that other
agents share. Under the patch `agent_store_counts` it also counts the
memory entries that it removes, and erases the transcript windows of the
agent. `harvest agents erase` reports `lessons_removed`,
`memory_entries_erased` and `transcripts_erased`.

**What to do.** A worker with a hand-picked activity list adds
`agent_memory_count`, `agent_transcript_count` and
`agent_transcript_erase`. Upgrade every worker before an erase.

### 1.7 A sample run counts each draw against the mandate — BEHAVIOR CHANGE

**What changed (issue #2449).** A new `agent_sample` run under a profile
mandate counts each draw against `max_delegations`, which is 16 by
default. So best-of-17 and more is refused with `fan_out_exhausted`. A run
that started before the patch `agent_sample_mandate` skips the check on
replay.

**What to do.** Raise `max_delegations` of the mandate for a strategy that
needs more draws. `Mandate::max_draws` only caps the draws of one strategy
run further. It never admits more draws.

### 1.8 A gated tool call sends an approval notice — BEHAVIOR CHANGE

**What changed (issue #2603).** A tool call that parks on an approval now
runs the activity `agent_approval_notice` once before it waits. The
default `Delivery::notify_approval` writes the names to the `tracing` log.
A failed notice never fails the run.

**What to do.** A worker with a hand-picked activity list adds
`agent_approval_notice`. Implement `Delivery::notify_approval` to push the
notice to a person. See [the agent adapter guide](../agent-adapter.md),
section 5.

The same change fixes the engine. A `ctx.race()` that a signal settles on
its first poll now arms no other branch, so its replay no longer diverges.

### 1.9 Other agent behavior changes

- **A read-only run refuses a workspace change (issue #2692).** An
  `Internal` tool that changes the workspace on a read-only run now gets an
  error. Before, the run reported success and dropped the change.
- **A consolidation pass sets no output cap (issues #2695 and #2696).** The
  2048-token cap is gone. Set `EpisodeSettings::max_pass_output_tokens` to
  cap a pass. An Anthropic model gets 16 000 tokens with no cap. A capped
  reply that does not parse ends as `ConsolidationStop::OutputCapped`, not
  `InvalidReply`.
- **The memory snapshot follows the `memory` tool (PR #2725).** A run with
  no `memory` tool reads a head that says that it cannot edit the notes.
  The patch `agent_read_only_memory_snapshot` gates the new head.
- **An unanswered durable peer has a verdict (issue #2484).** A `delegate`
  call that gets no reply returns `reply_timeout`, `reply_rejected` or
  `reply_interrupted`. A reply value that is not a reply is now
  `reply_rejected`. Before, it failed the call with no record.
- **The examples share one Anthropic client (issue #2605).** The examples
  use the `anthropic` module of the agent crate. The default model of
  `claude-agent-daemon` is `claude-opus-5-5`, with effort `high`. The
  autoresearch model id now writes `effort:high`, not `effort=high`, so each
  old autoresearch response cache entry misses once. The autoresearch lab on
  Postgres sets a daily tenant budget of $20.

### 1.10 The plugin warns about an unserved `mcp` flag — BEHAVIOR CHANGE

**What changed (issues #2488 and #2609).** A workflow or an update that
sets `mcp` has no effect unless the plugin has its `mcp` feature and the
app calls `.mcp_tools()` or `.mcp_tasks()`. The plugin now logs one `WARN`
at build when no MCP route serves the flag. A bare `SqliteRuntime` warns at
registration. No run changes.

**What to do.** Mount the MCP routes, or remove the flag.

### 1.11 Database gauges sample every 15 s, once per shard — BEHAVIOR CHANGE

**What changed (issues #2668 and #2679).** Each database gauge sampler now
runs on `WorkerConfig::gauge_sample_interval`, 15 s by default. In 0.10 it
ran on the poll interval, 500 ms by default. One elected worker per shard
reads each gauge and writes the read to `harvest_gauge_samples`. Every
worker still emits each gauge, with the same value.

**Who is affected.** A dashboard or alert that expects a gauge to move
within a second. A time-based gauge on a standby worker, such as the oldest
pending age, can be up to one interval old. So
`harvest_queue_schedule_to_start_high` can fire up to 15 s later.

**What to do.** Nothing for most fleets. For the old cadence, set
`gauge_sample_interval` to the poll interval. To turn the election off,
set `ScannerConfig::elect = false`. See [Telemetry](../telemetry.md).

### 1.13 SQLite backend changes — NO ACTION

The SQLite backend changes its file on open. No step is needed.

- `harvest_external_tasks` is a new table (issue #2607).
- With `HarvestPlugin::sqlite_per_tenant()`, the control database gets the
  new table `harvest_tenant_wakes` at boot (issue #2650). The Harvest file
  of a tenant ships with its database when the fleet replicates (issue
  #2649).
- The Harvest file now records the identity of its tenant database file as
  `<dev>:<ino>:<birth ns>` (issue #2721). A record of `0.10.0` still matches
  its file. A downgrade reads each new identity as a new file, so let each
  `HarvestFleet::restore` return before a downgrade.
- The task index `idx_harvest_tasks_exec_state_seq` replaces
  `idx_harvest_tasks_exec`. The first open builds it from the stored tasks.
  That takes time in proportion to the rows of `harvest_tasks`. An older
  release still reads the file. It builds its own index again on open.

## 2. Migrations

`0.11.0` adds 17 Postgres migrations. None rewrites `harvest_events`. Each
migration that locks an existing table sets `lock_timeout` to 5 s. If it
fires, run the migration again. The three that only create a new table
(`20261106145618`, `20261106145707` and `20261119232341`) do not set it.
Six of them build or drop an index of a hot table, and a seventh builds an
index on the busy `harvest_llm_ledger`. Read section 2.6 before you apply
them on a large database. See [the migration table](0.5.0.md) for
the full row of each migration.

### 2.1 Runtime overrides of the activity defaults — RUN THE MIGRATION

`PATCH /admin/activity-types/{activity_name}/defaults` changes the retry
policy and the four timeouts of an activity type at runtime (issue #2410).
A change applies to the activities scheduled after it. See
[Activity default overrides](../operations/activity-default-overrides.md).

| Migration | Fields | When a change applies |
|---|---|---|
| `20261106145707_harvest_activity_default_overrides` | `retry_max_attempts`, `retry_initial_interval_ms`, `retry_max_interval_ms`, `start_to_close_ms`, `heartbeat_timeout_ms`, `schedule_to_start_ms`, `schedule_to_close_ms` | The next schedule of the activity. A scheduled activity keeps the values of its task row. A local activity keeps the values that its event froze. |

**Who is affected.** Nobody at once. An activity with no override keeps its
code values. A call-site value still wins.

**What to do.** Run the migration. It creates one new small table on the
default shard and takes no lock on a hot table. The runtime role needs
`SELECT`, `INSERT`, `UPDATE` and `DELETE` on
`harvest_activity_default_overrides`.

`GET /admin/overrides` adds `activity_default_overrides`. The `overrides`
count on `GET /admin/config` adds `activity_default_overrides`.

**Rollback.** Deploy `0.10.0` first, then run the `down.sql`, because
`0.11.0` reads the table. It drops the table and every stored override.

### 2.2 Runtime override of the activity cap — RUN THE MIGRATION

The same route takes `max_concurrent`, the fleet-wide cap of an activity
type (issue #2411). A change also sets the stored cap of the live task rows
of the activity, so a pending task waits under the new cap. See
[The concurrency cap](../operations/activity-default-overrides.md#the-concurrency-cap).

| Migration | Fields | When a change applies |
|---|---|---|
| `20261107194243_harvest_activity_default_max_concurrent` | `max_concurrent` | The next claim of each live task of the activity. A running task runs on. |

**Who is affected.** An activity with no cap override keeps its code cap.
One change applies at once. A dead-letter replay or redrive of an activity
task now restores its key and its cap. Before, such a task had no cap.

**What to do.** Run the migration. It adds one nullable column to the small
override table. No grant changes.

**Rollback.** Deploy `0.10.0` first, then run the `down.sql`, because
`0.11.0` reads the column. It deletes each override row that sets only the
cap. The task rows keep the cap that the last pass stored.

### 2.3 Schedule overrides across a reshard — RUN THE MIGRATIONS

The carry of a DAG schedule override to its new shard now fences both
shards and keeps a clear across any routing change (issues #2413 and
#2602).

| Migration | What it does |
|---|---|
| `20261106145618_harvest_schedule_override_receipts` | Creates `harvest_schedule_override_receipts`. |
| `20261108045837_harvest_schedule_override_floor` | Changes no schema. Each receipt becomes the floor of its DAG on its shard. It deletes the delivery receipts of the first migration. |

**Before the upgrade.** Let each pending shard move end. No shard should
hold an override row of a DAG that it does not own.

**What to do.** Run both migrations. Each worker role needs `SELECT`,
`INSERT`, `UPDATE` and `DELETE` on `harvest_schedule_override_receipts`.
`GET /admin/preflight` checks them. A missing grant fails each carry.

**Mixed versions.** A `0.10.0` process writes without the floor. Change no
override and no shard routing until every process runs `0.11.0`.

**Rollback.** Deploy `0.10.0`, then run the `down.sql` of both. The floor
migration then runs again on the next upgrade.

### 2.4 Input override of a code-declared schedule — RUN THE MIGRATION

`PATCH /admin/schedules/{id}` on a code-declared workflow schedule now takes
`input` (issue #2412). See
[Schedule overrides](../operations/schedule-overrides.md).

| Migration | What it does |
|---|---|
| `20261108003205_harvest_schedule_override_input` | Adds `workflow_input JSONB` and a unique `id UUID` to `harvest_schedule_overrides`. |

**What to do.** Run the migration. The volatile default of `id` rewrites
`harvest_schedule_overrides`, which holds one row per overridden schedule.
No grant changes. With column encoding on, the input cell is ciphertext,
and the codec rotation sweep re-encodes it.

**Mixed versions.** A `0.10.0` process ignores the column, and its tick
converges the row back to the code input. Set an input override only after
every process runs `0.11.0`.

### 2.5 Durable agent stores — RUN THE MIGRATION

The agent crate ships durable episode, memory and transcript stores for
SQLite and Postgres (issue #2604).

| Migration | What it does |
|---|---|
| `20261109005653_harvest_agent_stores` | Creates `harvest_agent_store_docs` and `harvest_agent_transcripts`. |

**What to do.** Run the migration. The tables are new and not hot. A role
that runs the stores needs `SELECT`, `INSERT`, `UPDATE` and `DELETE` on
both tables. The bodies hold text in clear, outside the payload codecs.

**Rollback.** Deploy `0.10.0` first. The `down.sql` deletes every episode
log, memory scope and window of the stores.

### 2.6 Index changes on hot tables — RUN THE MIGRATIONS

These migrations build or drop an index of a hot table. A plain build takes
`SHARE` on its table and blocks each write until the build ends. A plain
drop takes `ACCESS EXCLUSIVE` for a short time. On a large deployment, run
the `CONCURRENTLY` statement in the header of each `up.sql` first. The
migration then takes no long lock. See
[Lock-safe online migrations](online-migrations.md).

| Migration | Table | Change |
|---|---|---|
| `20261110194313_harvest_timers_exec_fired_index` | `harvest_timers` | Builds `idx_harvest_timers_exec_fired` on `(workflow_exec_id, fired)` (issue #2643). |
| `20261110194400_harvest_timers_exec_swap` | `harvest_timers` | Drops the old `idx_harvest_timers_exec`, and gives the new index its name. |
| `20261114213148_harvest_events_exec_index_drop` | `harvest_events` | Drops `idx_harvest_events_exec`, a duplicate of a constraint (issue #2684). The partitioned layout cannot drop it `CONCURRENTLY`. |
| `20261114213149_harvest_executions_redundant_index_drop` | `harvest_workflow_executions` | Drops four redundant or unused indexes (issue #2684). |
| `20261119233226_harvest_task_queue_concurrency_live_index` | `harvest_task_queue` | Builds the partial index `idx_harvest_tq_concurrency_live` (issue #2678). |
| `20261120145312_harvest_tq_workflow_task_index` | `harvest_task_queue` | Builds `idx_harvest_tq_workflow_task` (issue #2713). |
| `20261120174554_harvest_llm_ledger_run_recorded_index` | `harvest_llm_ledger` | Builds the covering index `harvest_llm_ledger_run_recorded` (issue #1997). The plain build took 4.4 s at 6.26M rows. |

Each guarded build accepts a valid prebuilt index with the same definition.
It refuses an `INVALID` index from a failed build. No data changes, and no
grant changes.

### 2.7 Gauge samples and the DLQ depth counter — RUN THE MIGRATIONS

| Migration | What it does |
|---|---|
| `20261119232341_harvest_gauge_samples` | Creates `harvest_gauge_samples`. One elected worker per shard reads each database gauge and writes the read there (issue #2679). |
| `20261119233037_harvest_dead_letter_counts` | Creates `harvest_dead_letter_counts`, four functions and three triggers on `harvest_dead_letters`. The DLQ depth gauge reads a counter, not the whole DLQ (issue #2677). |

**What to do.**

- The storage role needs `SELECT`, `INSERT`, `UPDATE` and `DELETE` on
  `harvest_gauge_samples`. Without them, each worker reads each shard
  itself, as before. Every worker still emits each gauge.
- The DLQ counter needs no grant. Its functions are `SECURITY DEFINER`.
- The DLQ migration takes `SHARE ROW EXCLUSIVE` on `harvest_dead_letters`
  while it counts the DLQ once. It refuses a transaction level above
  `READ COMMITTED`. `harvest migrate` pins the level.
- On a logical DR standby, the counter sum is wrong until
  `harvest dr promote` recounts it. The promote does that on each promoted
  shard.

### 2.8 The external outbox pending table — RUN THE MIGRATIONS

An idle external-outbox claim no longer reads the request history (issue
#2724).

| Migration | What it does |
|---|---|
| `20261119232545_harvest_external_outbox_pending` | Creates `harvest_external_outbox_pending` and its projection function. |
| `20261120004046_harvest_external_outbox_projection` | Installs the trigger `harvest_external_outbox_projection_trg` on `harvest_events`, and backfills each unresolved request. |

**What to do.**

- Each role that appends events or runs a shard move needs `SELECT`,
  `INSERT` and `DELETE` on `harvest_external_outbox_pending`. The startup
  preflight checks them.
- The trigger migration holds `SHARE ROW EXCLUSIVE` on `harvest_events`
  until it commits, so event appends wait for the backfill. It took about
  1.1 to 1.4 s for 200,000 requests. Count the requests first with the
  query in the migration header.
- The trigger is not an exception to the append-only rule of
  `harvest_events`. It writes only its own table.

**Mixed versions.** `idx_harvest_events_external_outbox_pending` stays, so
a `0.10.0` worker keeps its claim plan. The trigger keeps the table right
on writes from either release.

## 3. Rolling deploy: turn on new features after the roll

The [rolling-deploy contract](README.md) lets `0.10.0` and `0.11.0`
processes run together. A `0.10.0` process does not know the new fields,
activities and markers. It refuses a field that it does not know, cannot
replay a history that holds a new activity, or drops a field. So turn on
each feature below only after every process runs `0.11.0`.

| Feature | Turn it on with | What an old process does |
|---|---|---|
| Activity default overrides (issues #2410 and #2411) | `PATCH /admin/activity-types/{activity_name}/defaults` | Answers the route with a `404`, and schedules each activity with its code values and its code cap. The settle passes set only the rows that it stores within 5 minutes of the change |
| Schedule input override (issue #2412) | `PATCH /admin/schedules/{id}` with `input` | Ignores the column, and converges the row back to the code input |
| Schedule override reshard (issues #2413 and #2602) | A new override or a shard routing change | Writes without the floor, so a clear can come back |
| Claim slots (issue #2421) | `WorkerConfig::with_claim_slots_per_shard` | Takes no slot, so a mixed fleet can pass the cap. Set one value on every worker |
| Vote strategy (issue #2444) | `SampleStrategy::Vote` | Cannot decode a vote input |
| Model cascade (issue #2445) | A policy with `cascade_models`, then a `cascade` strategy | Cannot decode the whole policy of the kind. So each `agent_draws` and `agent_sample` run of the kind fails closed, best-of-N included, and so does each answer check. It cannot decode a `cascade` input or an `escalated` outcome |
| Beam search (issue #2446) | `SampleStrategy::Beam` | Cannot decode a `beam` strategy or a `beam_step` task |
| Dataset sweep (issue #2448) | `agent_sweep`, `sqlite::start_sweep` or `SampleStrategy::Single` | Does not register `agent_sweep` or `agent_sweep_items`. It cannot decode a `single` strategy or a `SampleInput` with `expected`, and it drops `ScoreInput::expected` |
| Sweep tool (issue #2716) | `AgentTask::sweep` or `AgentProfile::sweep` | Cannot decode the setting |
| Strategy ops and delegated strategies (issues #2449 and #2610) | `AgentOp::with_sample`, or a `delegate` call with `sample` | Cannot decode the op or the new refusal. Upgrade every worker of a mesh first |
| Durable peer verdicts (issue #2484) | A run that can record `reply_timeout`, `reply_rejected` or `reply_interrupted` | Cannot decode a report with a new verdict |
| Refine adoption gate and lessons (issues #2381 and #2382) | A new `agent_refine` run | Does not register the gate and lesson activities. It refuses a `ProposeRequest` that holds `lessons`. Upgrade each activity worker first |
| Agent store counts (issue #2604) | An erase, `Control::ResetMemory` | Does not register `agent_memory_count`, `agent_transcript_count` and `agent_transcript_erase` |
| Agent profile reload (issue #2658) | `Control::ReloadProfile`, `sqlite::reload_profiles`, `postgres::reload_profiles` or `harvest agents reload` | Cannot decode the op, so it counts a failed op. It cannot replay a run that holds the op |
| Process sandbox file system (issue #2697) | `ExecOptions::fs` | Runs the job with the whole file system of the worker |
| Harvest capabilities in a role preset (issue #2480) | `capabilities = { "harvest.worker" = ... }` | `autumn-web` 0.10 refuses the `capabilities` key, so the process does not boot |

`activities()`, `workflows()` and `autumn_harvest_agent::sqlite::register`
add the new activities and workflows. A worker that builds its own list
must add them too. Sections 1.5, 1.6 and 1.8 name most of them. A worker
with its own list also adds the `agent_vote_key` activity (issue #2444),
and the `agent_sweep` workflow and the `agent_sweep_items` activity (issue
#2448).

A 0.11 run uses some new activities with no opt-in. A gated tool call runs
`agent_approval_notice`, a new `agent_refine` run opens the adoption gate,
and an erase counts the stores. So upgrade every worker that hosts agent
workflows or agent activities before a new agent run starts.

## 4. New opt-in features — NO ACTION

Each feature below is off until you turn it on.

- **Runtime activity default overrides (issues #2410 and #2411).** See
  section 2.1 and
  [Activity default overrides](../operations/activity-default-overrides.md).
- **Schedule input overrides (issue #2412).** See section 2.4.
- **Claim slots (issue #2421).** Cap the claim statements that run at once
  on one shard, across the fleet. See
  [Claim slots](../operations/claim-slots.md).
- **Batch claim (issue #2693).** `WorkerConfig::with_claim_batch_max(n)`
  lets one claim statement take up to 2, 4 or 8 rows. See
  [Batch claim](../operations/claim-batch.md).
- **Lean claim.** A claim loop sends a smaller claim statement first. It
  is on by default, and `WorkerConfig::with_claim_lean(false)` turns it
  off. See [Lean claim](../operations/claim-lean.md).
- **External activities on SQLite (issue #2607).**
  `ctx.execute_activity_external` runs on the SQLite backend. See
  [The SQLite backend](../sqlite-backend.md).
- **A private file system for the process sandbox (issues #2697, #2715 and
  #2719).** `ExecOptions::fs` masks paths or builds a new root. See
  [Sandbox activities](../sandbox-activities.md).
- **Pre-deploy analyses.** DAG slack, leverage, crash and worker-demand
  plans, the DAG and activity retry envelopes, the retry storm and throttle
  forecasts, the shape census, and the schedule herd forecast, with
  `GET /admin/schedules/herd` and `harvest schedule herd`. See
  [DAG and retry analyses](../dag-and-retry-analyses.md).
- **`HarvestPlugin` on SQLite.** Host the durable agent with
  `HarvestPlugin::agent` (issue #2641). A tenant Harvest file ships with its
  database (issue #2649), and a closed tenant wakes when its next timer or
  schedule is due (issue #2650). The overlay store opens on a connection
  factory (issue #2656). See [HarvestPlugin on SQLite](../sqlite-plugin.md).
- **Inference strategies (epic #2438).** The vote (issue #2444), the model
  cascade (issue #2445), step-level beam search (issue #2446) and the
  dataset sweep (issue #2448). A durable agent op and a delegation can run a
  strategy (issues #2449 and #2610), and the `sweep` workflow tool starts a
  sweep (issue #2716). See [the agent adapter guide](../agent-adapter.md),
  sections 20, 26, 27 and 28, and [ADR 0017](../adr/0017-inference-strategies.md).
- **The refine loop (issues #2381, #2382, #2383, #2577 and #2579).** The
  adoption gate, the lesson library, a keyed live fork and the live rule.
  See [the agent adapter guide](../agent-adapter.md), sections 23 to 25,
  and [ADR 0016](../adr/0016-agent-refinement.md).
- **Agent models (issue #2605 and PR #2633).** The `anthropic` feature adds
  `anthropic::ClaudeModel`. The `openai` feature adds
  `openai::OpenAiModel`, which reaches any OpenAI-compatible endpoint. See
  [the agent adapter guide](../agent-adapter.md).
- **Durable agent stores (issue #2604).** Episode, memory and transcript
  stores for SQLite and Postgres. See section 2.5.
- **Agent operations.** Reload the profile of a running agent (issue
  #2658), and get an approval notice (issue #2603). See
  [the agent adapter guide](../agent-adapter.md), sections 5 and 15.
- **Examples.** `examples/rhai-scripts` runs a Rhai script as a durable
  workflow (PR #2590). `examples/agent-strategies` runs each strategy, and
  `autumn-harvest-agent/examples/sqlite_mesh.rs` runs a small mesh (issue
  #2486).

## 5. Dependency changes

### 5.1 Bump the Harvest crates and `autumn-web` — REQUIRED

Bump every Harvest crate and `autumn-web` in one change.

```toml
[dependencies]
autumn-harvest = { version = "0.11", features = ["db"] }
autumn-harvest-plugin = "0.11"
autumn-web = "0.11"
```

`harvest new` writes these versions.

### 5.2 `diesel` 2.4 and `rusqlite` 0.42 — REQUIRED if you name them

`autumn-web` 0.11 moves `diesel` to 2.4, `diesel-async` to 0.10,
`rusqlite` to 0.42 and `libsqlite3-sys` to 0.40. The last one fixes
RUSTSEC-2026-0459. See [`autumn-web` 0.11](autumn-web-0.11.md) sections 1
and 2.

### 5.3 `jiff` replaces `chrono` — REQUIRED if you use Harvest time types

`jiff` 1.0 is a dependency of `autumn-harvest`, with its bundled time zone
database. `chrono` and `chrono-tz` are gone. See
[`chrono` to `jiff`](chrono-to-jiff.md).

### 5.4 Other dependency moves — NO ACTION

- `autumn-harvest-agent` adds the optional features `anthropic` and
  `openai`. Without them, the crate gains no dependency.
- `ctor` is a new dev-dependency of `autumn-harvest-plugin`.
