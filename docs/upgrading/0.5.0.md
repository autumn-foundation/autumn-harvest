# Upgrading from 0.4.0 to 0.5.0

This guide covers everything you need to move an autumn-harvest deployment from
`0.4.0` to `0.5.0`: the dependency-version bumps, the database migrations that
land in this release, and the small set of source-breaking / behavior changes
you should verify against your own code.

If you only consume the engine through `HarvestPlugin` and the management API —
and you do not port your own `diesel-async` transactions or match on
`HarvestError` in workflow code — the upgrade is mechanical: bump the crate
versions, run the new migrations, and you are done.

> **Not yet on crates.io.** At the time of writing, `0.5.0` is published from
> the release branch but not yet on crates.io, so this guide shows dependency
> changes as prose rather than a copy-pasteable `autumn-harvest = "0.5"` snippet.
> Once published, pin the workspace crates to `0.5` in the usual way.

|------------|-------|-------|-------|
| `autumn-web` | 0.5 | **0.6.0** | Landed via the 0.6.0 upgrade PR. No harvest-facing API change for embedders who mount the plugin the standard way. |
| `diesel-async` | 0.8 | **0.9** | Transaction-closure signature change — see below. Only affects embedders who write their **own** `diesel-async` transactions. |
| `rusqlite` (for `autumn-harvest-sqlite`) | — | **0.39** (`bundled`) | New in 0.5.0. The embedded SQLite backend crate pins `rusqlite = { version = "0.39", features = ["bundled"] }` at the workspace level — bundled SQLite, no system dependency. Irrelevant unless you use the SQLite backend. |

The `wasm-activities` feature (opt-in, R&D) carries an effective MSRV of 1.94
(wasmtime's own minimum); it is never compiled by the default build, so it does
not raise the crate MSRV for any non-`wasm` consumer.

### Porting your own `diesel-async` transactions (0.8 → 0.9)

`diesel-async` 0.9 changed `AsyncConnection::transaction` from taking a closure
that returns a hand-boxed scoped future to taking a native **async closure**.
If you write transactions directly against a harvest connection (embedders
extending the schema, custom management routes, background jobs), update each
call site. If you only call harvest APIs, there is nothing to change — the
engine's own internals were ported for you.

**Before (0.8)** — a closure returning a scoped boxed future via
`.scope_boxed()`:

```rust
use diesel_async::scoped_futures::ScopedFutureExt;

conn.transaction(|tx| async move {
    // ... reads and writes on `tx` ...
    Ok::<_, diesel::result::Error>(())
}.scope_boxed())
.await?;
```

**After (0.9)** — a native `async` closure; wrap the whole `transaction(...)`
future in `Box::pin` at the await site if the surrounding context requires a
`'static`/boxed future:

```rust
Box::pin(conn.transaction(async |tx| {
    // ... reads and writes on `tx` ...
    Ok::<_, diesel::result::Error>(())
}))
.await?;
```

The `ScopedBoxFuture` / `.scope_boxed()` shape from 0.8 has no equivalent in the
async-closure form — remove the `.scope_boxed()` call and let the `async |tx|`
closure supply the future directly. The engine's `calendar.rs`, `store.rs`, and
`execution.rs` transactions were all converted this way; grep the release diff
for `conn.transaction(async |` if you want a set of worked examples to mirror.

nullable-or-defaulted columns, and indexes only. There is **no history rewrite
and no data backfill**, so they apply cleanly against a live database with no

| `20260722000000_harvest_activity_pause` | `harvest_activity_pauses` (`activity_name` PK, `reason`, `paused_by`, `paused_at`, `scope_shard_id`) -- durable per-activity-type dispatch holds (#807), plus partial B-tree `idx_harvest_tq_activity_pause` on `harvest_task_queue (activity_name, state) WHERE task_type = 'activity' AND activity_name IS NOT NULL`. The index exists because all four of this feature's queries narrow by *activity* first and no pre-existing index leads with `activity_name` -- without it the correlated held-count behind `GET /activities` is O(paused x task_queue) on every read, worst exactly mid-incident with the backlog at its largest. It is **partial on `task_type = 'activity'`**, so workflow rows never enter it and the hot enqueue path is untouched. On a live deployment prefer `CREATE INDEX CONCURRENTLY` (spelled out in the migration) rather than the transactional form Diesel runs. No column change to an existing table, no data migration, no `WorkflowEvent` variant. |
| `20260723000000_harvest_retry_chain_index` | Partial B-tree `idx_harvest_wfx_retry_of` on `harvest_workflow_executions (retry_of_exec_id) WHERE retry_of_exec_id IS NOT NULL` -- makes the workflow-level retry-chain walk index-servable (#843). It is **partial on a non-NULL parent**, so it covers only rows that are themselves a retry successor (a deployment that never retries a workflow carries an empty index) and the ordinary start path never enters it. On a live deployment prefer `CREATE INDEX CONCURRENTLY` (spelled out in the migration) rather than the transactional form Diesel runs. Index only -- no column, no table, no data change, no `WorkflowEvent` variant. |

### How migrations are applied

The engine ships its migrations **embedded** (`autumn_harvest::MIGRATIONS`), and
`HarvestPlugin` decides whether to auto-apply them based on the Autumn profile:

- **`dev` profile** — pending migrations are applied automatically at startup
  (`run_pending`), so a local `AUTUMN_PROFILE=dev cargo run` boots against a
  fresh schema with no manual step.
- **Non-`dev` profiles** (staging/production) — the plugin **checks** for
  pending migrations and, if any are outstanding, logs a warning and refuses to
  silently mutate the schema. Apply them explicitly in your deploy pipeline with
  **`autumn migrate`** (or `diesel migration run` from `autumn-harvest/` with
  `DATABASE_URL` set) before rolling out the new binary.

Notes:

- **Ordering.** Apply migrations in timestamp order (the mechanism above does
  this automatically). Because the whole 0.5.0 set is additive index/column/table
  work with no backfill, applying it against a live 0.4.0 database is safe — new
  columns default or are nullable, and the new workers pick up the new features
  once they start.
- **Split / external databases.** If you run harvest against a dedicated shard
  database (or multiple shards), each shard database must have the full
  migration set applied. The outbox migrations (if you use the transactional
  workflow-start outbox) apply against your **application** database, not the
  harvest shard DB.
- **SQLite backend.** `autumn-harvest-sqlite` manages its own additive schema
  via an idempotent `migrate()` on `open()` (probe-then-`ALTER TABLE ADD COLUMN`);
  it does not consume the Postgres migration set.

## 3. Breaking and behavior changes

Only changes introduced **after 0.4.0** are listed here. Each is verified
against the released source. Most are behavior refinements at the operator/API
boundary; exactly one is **source-breaking** for workflow authors (#767).

### 3.1 Failed child workflows now surface as `WorkflowFailed` (#767) — SOURCE-BREAKING

A child workflow that fails is now delivered to its parent as a **typed**
`HarvestError::WorkflowFailed`, not `HarvestError::ActivityFailed`. The
`child-workflow:{name}` name prefix is preserved for log disambiguation, but the
variant changed so a parent can branch on the child's typed failure cause
(`error_type` / `details` / `non_retryable`) with zero substring matching on the
message.

If your parent workflow matches on the child result, update the arm:

```rust
// BEFORE (0.4.0) — a failed child arrived as ActivityFailed:
match ctx.spawn_child_workflow(&fulfill_child_info(), order).await {
    Ok(result) => { /* ... */ }
    Err(HarvestError::ActivityFailed { name, .. }) => {
        // handle failed child
    }
    Err(e) => return Err(e.to_string()),
}

// AFTER (0.5.0) — a failed child arrives as WorkflowFailed; read the typed cause:
match ctx.spawn_child_workflow(&fulfill_child_info(), order).await {
    Ok(result) => { /* ... */ }
    Err(e) if matches!(e, HarvestError::WorkflowFailed { .. }) => {
        // route on the child's error class, not its message text:
        match e.workflow_error_type() {
            Some("PaymentDeclined") => { /* ... */ }
            _ if e.is_workflow_non_retryable() => { /* ... */ }
            _ => { /* ... */ }
        }
    }
    Err(e) => return Err(e.to_string()),
}
```

If you previously read `.activity_error_type()` / `.activity_details()` on a
failed child result, switch to `.workflow_error_type()` /
`.workflow_details()` / `.is_workflow_non_retryable()`.

Caveat: `HarvestError::WorkflowFailed` gained the additive fields `error_type`,
`details`, and `non_retryable`. If you construct or exhaustively destructure the
variant, add a `..` to your pattern (or the new fields) — an exhaustive match
without `..` will fail to compile.

See [`docs/typed-workflow-failures.md`](../typed-workflow-failures.md) for the
full typed-failure contract, including how a workflow publishes a typed
`WorkflowFailure` and how the parent, the typed handle, and `WorkflowReplayer`
recover it.

### 3.2 Rate-limit throttled metric label renamed `key` → `activity` (#699)

`harvest.rate_limit.throttled` is now labelled by the bounded **activity name**
(`activity`) instead of the unbounded bucket **key**. Update any dashboard or
alert that keys on the old `key` label. This is a live-label change, not stored
data — nothing is orphaned, but a query referencing `key` will stop matching.

### 3.3 Resume is idempotent — non-`PAUSED` now returns `200`, not `409` (#609)

`POST /api/harvest/workflows/{id}/resume` previously returned `409 Conflict` for
a non-`PAUSED` execution. It now returns a **success no-op** (`200`,
`newly_resumed: false`, pause duration `0`) for any *existing* non-`PAUSED`
execution, keeping `404` for an unknown id. This makes operator resume retries
idempotent. `PauseWorkflowResponse`/`ResumeWorkflowResponse` also gained
additive `paused_at` / `newly_resumed` fields. See
[`docs/runbooks/contain-runaway-execution.md`](../runbooks/contain-runaway-execution.md)
for the pause/cancel/terminate decision matrix.

### 3.4 Replay non-determinism blocks instead of failing the run (#603)

An engine-detected replay divergence (`HarvestError::NonDeterministic`, e.g. from
a bad deploy) on an in-flight execution **no longer writes a terminal
`WorkflowFailed` / transitions the run to `FAILED`**. Instead the run is *blocked*
(stays `RUNNING`, stamped `nd_blocked_at`, re-driven with capped exponential
backoff) so a rollback resumes it — the Temporal "a workflow-task failure never
fails the workflow" property. Operators discover blocked runs with
`GET /workflows?nd_blocked=true`; the new counter is
`harvest.workflow.nondeterministic_block{workflow, queue}`. See
[`docs/runbooks/nondeterminism-block.md`](../runbooks/nondeterminism-block.md)
for the detect → identify build → roll back → confirm-resume playbook. Migration:
`20260704000000_harvest_workflow_nd_block`.

### 3.5 The admission gate is authoritative across all start producers (#618/#1053)

Raising an admission gate now halts new workflow starts across **every**
in-process producer — the HTTP start route, completion triggers, the outbox
relay, the scheduler, debounce/throttle/batch, and the webhook delegate — either
by blocking-and-counting the start or by an explicit, observable
exempt-and-count. Enforcement is authoritative inside the core start primitive
(gate check under the same lock as the create-vs-attach decision), so a start
that would create a new execution while a matching gate is armed is refused with
`503`, and the exempt deferred-fire producers increment
`harvest.admission.bypassed{producer}`. This is a *tightening* — a start that
0.4.0 would have let through during an incident may now be gated. The full
producer contract is discoverable at `GET /admin/gates`; see
[`docs/operations/admission-gate-producers.md`](../operations/admission-gate-producers.md).

### 3.6 Cross-shard read endpoints degrade to `200 partial` instead of `500` (#756)

A single unreachable shard no longer turns a cross-shard **read** into a
whole-request `500`. Reachable shards' rows still flow, the unreachable shard is
named in a machine-readable `unavailable_shards`, and the endpoint returns
`200 OK` with a `status` verdict (`complete` / `partial` / `unavailable`). The
five legacy **bare-array** list endpoints (`GET /workflows`, `/workers`,
`/admin/schedules`, `/dead-letters`, `/dags`) keep their byte-for-byte bare-array
shape on the happy path and only switch to the `{ <items>, status,
unavailable_shards }` envelope when degraded — so a client that parses the happy
path is unaffected, but a client must be prepared for the envelope shape on a
partial read. **Writes keep strict failure semantics.** See the "Partial
cross-shard list reads" stanza in
[`docs/runbooks/harvest-alerts.md`](../runbooks/harvest-alerts.md) and
[`docs/sharding.md`](../sharding.md).

## New in 0.5.0 (no action needed)

These land as additive, opt-in features — nothing in this section requires an
upgrade step. A few highlights worth knowing about:

- **`ctx.mutex(key)` — durable named mutual exclusion (#691)** across workflows
  for a critical region: an RAII guard, FIFO fairness, lease-based crash safety,
  shard-local scope. See
  [`docs/getting-started/07-reliability-knobs.md`](../getting-started/07-reliability-knobs.md)
  and `autumn-harvest/examples/mutex_ledger.rs`.
- **Cancellable / renewable durable timers (#768)** — `ctx.start_timer(id, secs)`
  returns a `TimerHandle` you can `cancel()` / `reset(secs)` / `await_fire()`,
  for idle-session timeouts and sliding-window debounces.
- **Activity execution interceptors (#680)** — register an ordered middleware
  chain that wraps every activity (regular and local) once, for structured
  logging, custom metrics, or header propagation. See
  `autumn-harvest/examples/activity_interceptor.rs`.
- **`ctx.info()` — run metadata (#698)** (`execution_id`, `workflow_id`,
  `workflow_type`, `parent_execution_id`, …) readable from workflow code,
  replay-safe and zero-footprint. See `autumn-harvest/examples/ctx_info.rs`.
- **Scoped API tokens (#942)** — a least-privilege management-API credential
  layer (create / list / revoke scoped, optionally-expiring tokens; `read` vs
  `mutate` scope derived from route classification; per-token actor attribution).
  Opt-in via `HarvestPlugin::enable_api_tokens()`. See the "Scoped API tokens"
  section of [`docs/security-posture.md`](../security-posture.md).
- **`harvest new <name>` (#692)** — scaffold a complete, compiling, runnable
  autumn-harvest project (one workflow + one activity + `HarvestPlugin` wiring +
  `compose.yaml`) so your first durable execution is three commands away.
- **`harvest det-check [paths…]` (#778)** — a CLI determinism gate that
  statically scans `#[workflow]` bodies (plus one hop into first-party helpers)
  for non-deterministic calls, for CI/pre-commit use. See
  [`docs/workflow-determinism-guide.md`](../workflow-determinism-guide.md).
