- **R&D** (implemented): Time-travel replay debugger for recorded workflow histories — see issue #949. Gives an engineer the answer the existing replay surfaces stop short of: not *"does this history diverge?"* but ***"where exactly, and why?"***. Two entry points over one shared `ReplayTrace` type — the library `autumn_harvest::debugger` (behind a new `debugger` Cargo feature, which implies `testing`) and the local CLI `harvest debug`. **Read-only by construction (AC5): no new `WorkflowEvent` variant, no migration, no engine-runtime change, no activity execution, no database access.** Zero core-engine edits were needed — every primitive the design required (`WorkflowContext::for_replay_canary_with_state`, `executor::drive_query_replay_async`, `drain_commands`, `take_nd_details`, `take_deferred_nd_error`, `replay_position`, and the `with_*` builders) was already `pub`.

  **Mechanism — prefix replay, blessed by AC2's own wording.** Step `k` is a *fresh* replay of `events[0..=k]`; "backward" is re-run-forward, exactly as the AC describes ("replay is deterministic, so 'backward' is re-run-forward"). The load-bearing insight is that a clean replay emits **zero** replay-significant commands — commands are only emitted at the live frontier — so a prefix replay yields precisely *"what does this code do next, given history so far"*, which is both the per-step frontier command batch and the ideal diff signal. Two supporting choices: **canary, not strict** replay (`for_replay_canary_with_state` sets `strict_replay` **and** `canary_mode`, so `strict_replay_no_match_is_divergence()` still catches a *mid-prefix* divergence while allowing frontier command emission — a prefix genuinely *is* an in-flight execution parked at its frontier); and **`drive_query_replay_async`** (issue #612) rather than `drive_workflow`, because the latter's 100 ms `SUSPENSION_TIMEOUT` would cost `N × 100 ms` (100 s for a 1k-event history) whereas the former detects suspension instantly via a per-poll command delta. Since that driver deliberately discards the handler's `Ok`/`Err`, non-determinism is read back through `ctx.take_nd_details()` / `take_deferred_nd_error()`.

  **AC1 — the snapshot.** `DebugStep` carries, after each consumed event: the event index and type, the pending `WorkflowCommand`s, the **open awaitables** (kind, name, id, and — as the AC explicitly requires — the `opened_at` **event index that opened them**), resolved **version-gate** values (`version:` markers) and **patch gates** (`patch:` markers, issue #687), recorded **side effects** and **markers** verbatim, the resolved payload, the signal name, and any recorded divergence. `AwaitableKind` is reused from `awaitables.rs` as the shared vocabulary, but the projection is debugger-owned: `awaitables::project_awaitables` requires timestamped `(DateTime<Utc>, WorkflowEvent)` rows that a `HistorySnapshot` does not carry, and its `Awaitable` has no `opened_at` index at all.

  **Handler-free vs handler-backed split.** Everything except pending commands derives from history alone in a single **O(N)** fold (`ReplayTrace::from_history`); only commands need registered workflow code (`ReplayDebugger::trace_snapshot` / `trace_json`). This split is what makes the CLI viable at all: the shipped `harvest` binary is statically linked and **cannot register an application's `#[workflow]` handlers** — the same constraint `harvest-replay` already states. So the CLI covers stepping, breakpoints and inspection plus the *two fixture histories* arm of AC3, while the library covers per-step commands and the *two code registrations* arm. Both produce the same `ReplayTrace`, so a session that starts in the CLI graduates to the library without reshaping anything; the capability split is documented as a table in the CLI module doc and in `docs/replay-debugger.md`.

  **AC2 — the driver.** `harvest debug replay <HISTORY>` with `--step N`, four breakpoint forms (`--break-at-event-type` / `--break-at-index` / `--break-at-activity` / `--break-at-signal`, declared mutually exclusive at the clap layer so a breakpoint never silently loses to another), `--max-steps N`, `--format text|json`, and `--tui` for an interactive stepper (`n`/`p`/`g`/`G` to move, `d` to jump to the next divergence — which requires a handler-backed trace, so in the handler-free CLI it reports that in the footer rather than sitting inert — `q` to quit; `--step`/`--break-*` seed the opening cursor; the terminal is restored even on error). JSON mode always emits the **whole** trace — silently emitting a focused partial document would be a trap for a `jq` pipeline.

  **AC3 — diff mode.** `diff_traces(left, right)` walks steps in order and reports the **first** difference only, because one root cause routinely produces dozens of downstream differences and reporting them all would bury the actionable one. `harvest debug diff <LEFT> <RIGHT>` exits **`1`** on divergence, mirroring `diff(1)`'s "differences found", so it drops straight into a CI pipeline. The **#614 boundary is stated in the module doc**, in `docs/replay-debugger.md`, and in the cross-tool tables of `docs/replay-verify.md` / `docs/replay-drift-gate.md`: #614 is a one-shot server-side verdict on one live run; this is the interactive local tool you reach for *after* it says "yes, diverging".

  **Display vs identity separation (a real bug caught by the corpus).** `CommandSnapshot` carries **both** a short, truncatable `summary` (for terminals) and an exact, never-truncated `payload: Option<Value>` (used for diffing). The first cut folded the input into the summary and truncated it, so the *"changed activity input"* corpus scenario reported its first divergence at step 3 instead of step 2 (the input difference was invisible until strict verification fired mid-history). Truncating into the compared field would silently hide a divergence deep in a large payload — on a divergence-finding tool, the worst possible failure mode.

  **History-fact diffing + per-run identity normalization (the second arm of AC3).** A handler-free trace emits *no* commands, so a command-only comparison could not see two **fixture histories** differing at all — `harvest debug diff` was structurally incapable of finding anything, a gap the new CLI tests caught. `diff_traces` now compares the history-derived facts first (via `DiffKind::HistoryFacts { field }`), ordered deliberately: history facts → commands → outcome (if the two *recordings* already differ, comparing "what did the code do next" across them is apples to oranges). Because two *independent recordings* of the same scenario necessarily differ on freshly-minted per-run values, the comparison **normalizes them out**: activity/child execution UUIDs, and the recorded values of the non-deterministic side-effect kinds (`Now`/`Uuid`/`Random`, issue #384) — normalized once, coherently, so the individual field checks cannot drift apart. Everything semantically meaningful is still compared, in two layers (see the Codex round 1 paragraph below): **curated projections** first, because they yield the legible field name the report prints (event type, signal name, awaitable kind/name/`opened_at`, version and patch gates, marker names and details, and the values of `Custom` side effects — application data, not engine identity), then **`event_facts`** as the exhaustive completeness backstop. This cannot hide a code-caused divergence — in the two-registrations arm both sides replay byte-identical events, so the normalized fields are equal by construction and the divergence surfaces through `commands`; in the two-histories arm a change that matters (renamed/reordered activity, different input, new marker, changed version gate) moves a field that *is* compared. `history_fact_diff` **exhaustively destructures** `DebugStep`, so adding a field without classifying it as history-derived or code-derived is a compile error rather than a silent false "clean".

  **Gates at a truncated frontier (documented semantic).** Since a step replays `events[0..=k]`, an intermediate step models an execution *parked at that truncated frontier* — so a `ctx.patched(...)` (#687) or `ctx.version(...)` gate reached there is, correctly, **newly** patched. A correctly-gated build therefore legitimately differs from an ungated one at intermediate steps while still replaying the *full* recorded history perfectly. The two questions need two checks, both documented and both asserted in the example: *"where do these builds first differ?"* → `diff_traces(...).divergence`; *"does this build replay this history cleanly?"* → no step has `divergence.is_some()`.

  **Cost, bounded honestly.** Building a full trace is `N` replays and therefore **O(N²)** — fine for the interactive histories this is for (tens to low hundreds of events), and deliberately not how the CI gates work (they replay each history once). `--max-steps` / `ReplayDebugger::max_steps` caps it, and `ReplayTrace::truncated` reports the cap so a partial view is never mistaken for a complete one. `DEFAULT_MAX_STEPS = 500`, `DEFAULT_STEP_TIMEOUT = 5s`.

  **AC4 — exported histories.** Input is the `HistorySnapshot` JSON round-trip format (`harvest history export`), so a production history is debugged on a laptop with zero database access. Payload-codec and offload-envelope fields **display as their envelopes** when no codec or store is configured, rather than erroring.

  **Success metric — met.** `divergence_corpus_identifies_the_first_divergent_step_in_every_scenario` runs a **13-scenario** corpus (≥10 required) spanning the `NonDeterminismKind` classes the issue names, and identifies the exact first divergent step index in **13/13**: reordered commands, inserted activity at the front, renamed activity mid-history, changed activity input, changed target queue, activity→timer, activity→child-workflow, dropped trailing activity, `SideEffectDrift` (inserted `ctx.new_uuid()`), inserted version gate, count-mismatch fan-out (2→3), signal-wait→activity, and a fan-out whose *second* slot's input changed. That last one is load-bearing: the corpus asserts the **command index** as well as the step index (the metric names the divergent *command*), and it is the one scenario whose expected command index is **not** 0 — so a stub hardcoding `command_index: 0` fails it.

  **AC6 — docs and example.** New `docs/replay-debugger.md`: the cross-tool comparison table (vs `replay-verify` / the replay-drift gate / #614), the two-arms capability table, and a six-step worked walkthrough that takes a new user from an exported history to an identified root cause — overview → breakpoint → interactive stepper → **diff old vs new build** (which pinpoints `fraud_check` inserted ahead of an already-recorded `charge_card` with no gate) → gate the change → confirm clean. Cross-linked from `docs/replay-verify.md` and `docs/replay-drift-gate.md`. Runnable companion `autumn-harvest/examples/replay_debugger.rs` (`required-features = ["debugger"]`) prints that exact walkthrough and carries four self-verifying tests, including the "ungated build does **not** replay cleanly" control that proves the clean-replay assertion measures something.

  **Tests.** 53 core tests in `autumn-harvest/tests/integration/debugger_tests.rs` (handler-free projection, `trace_snapshot`, breakpoints, diff, the 13-scenario corpus, the fixture-vs-fixture normalization contract, the three `DiffKind` variants the corpus cannot organically reach — `CommandCount` / `Outcome` / `Divergence` — and the robustness guards: a spinning workflow times out rather than hanging, a panicking workflow is contained, `max_steps: 0` clamps to one step, a redacted export is refused, and a **structural** AC5 guard that scans `debugger.rs`'s own source for any persistence symbol); 2 unit tests in `debugger.rs` — one pinning the `version:`/`patch:` marker prefixes against the engine's own `replay::{version,patch}_marker_name` builders, so a rename there cannot silently reclassify every gate as an ordinary marker; 8 clap-layer tests in `autumn-harvest-cli/src/lib.rs` (defaults, every flag, each breakpoint alone, and all three mutual-exclusion rejections); 43 black-box CLI tests in `autumn-harvest-cli/tests/integration/debug_cli.rs` (breakpoint/focus resolution, every `render_step_detail` section, `run_replay`/`run_diff` end to end, every error path's exit code, JSON-mode wholeness, the redaction warning, activity-breakpoint precision against a name prefix and against a queue name, plus a guard on the fixture itself so an id-reuse regression cannot silently weaken every open-awaitable assertion); 6 pure `StepperState` unit tests in `debug_tui.rs`; and 5 example tests. Registered in `.github/ci/integration-suites.txt` as one sorted `allos` row (`testing,debugger`), so it runs on every OS with no DB, plus a dedicated CI step for the example's tests.

  **Post-review hardening.** Three parallel review agents (replay-semantics, API/CLI design, and test-quality/AC-evidence) produced one **P1** and several P2s, all fixed: (1) **the debugger was strictly weaker than canary replay** — the canary/strict runners apply `ctx.history_has_unconsumed_events()` *after* the handler returns, and omitting that check meant a build that **dropped an activity** (or did nothing at all) replayed 100% "clean", the exact class the tool exists to catch; now gated on `ReachedTerminal`, using only already-`pub` API so AC5 still holds, with `a_build_that_completes_early_does_not_replay_cleanly` as the falsifying control. (2) **`command_payload` had a `_ => None` catch-all**, collapsing `Complete` / `Fail` / `RecordUpdateResult` / `CancelRaceLosers` / `RecordLog` onto equal snapshots — two genuinely different commands diffing as identical, on a divergence-finding tool; it is now exhaustive (no `_` arm), so an added `WorkflowCommand` variant is a compile error rather than a silently hidden divergence. (3) `record_deferred_nd` populates **both** nd slots, so the original lazy `.or_else()` chain never reached the informative message and **every `SideEffectDrift` reported `<unknown>`/`<unknown>`** — the headline case in the issue's own success metric. (4) Eight missing awaitable arms (`ExternalSignal*` / `ExternalCancel*` / `ActivityAwaitingExternal`) left external-workflow operations invisible in the open-awaitable column. (5) **AC1's signal waits were unimplemented** behind a misleadingly-named test; a `WaitForSignal` command now synthesizes an `AwaitableKind::Signal` — and, because that is *code-derived*, it is excluded from `history_fact_diff` so a code difference is never misreported as "the recorded histories differ". (6) The docs' export recipe handed the tool a **redacted** history (`harvest history export` defaults to `--payload-policy redacted`, rewriting payload fields in place), which fabricates a divergence at the first payload-bearing activity; fixed in the docs *and* enforced — `ReplayDebugger` refuses one (`DebugError::RedactedHistory`) and the CLI warns, mirroring the replay-drift gate's precedent. (7) A recorded divergence is **code**-derived, so it is now its own `DiffKind::Divergence` rather than being misfiled as `HistoryFacts { field: "divergence" }` — which would have told an operator "these are different recordings", a wrong and actively misleading diagnosis. (8) `DiffKind::TraceLength` gained a `capped` flag so diffing two traces built with different `--max-steps` is self-diagnosing instead of reporting a divergence that does not exist. (9) CLI ergonomics: `--tui` silently discarded `--step`/`--break-*` (they now seed the opening cursor), JSON mode swallowed a missed breakpoint's exit code, a capped trace rendered as a complete one, and the `d` key sat structurally inert in the handler-free CLI (it now says why). (10) Driving the built binary against a real fixture surfaced one more: `harvest debug diff` named the differing history field and then showed nothing about it — since the handler-free arm emits no commands, a fixture diff printed "the recorded histories differ (open_awaitables)" above two identical `<no pending commands>` lines. Both sides now render the **value** of the named field (`activity charge_card (opened at 3)` vs `activity fraud_check (opened at 3)`), which is the entire point of the CLI's primary diff path.

  **Post-review hardening, Codex round 1 (two P1s, both a *false clean* — the single worst failure mode for a divergence-finding tool).** (1) **A `CommandSnapshot` carried only a command's name and input**, so two builds that dispatched the *same* activity with *different scheduling options* compared **equal**. Codex reported it for `ScheduleExternalActivity` (a changed target queue or schedule-to-close deadline was invisible); verifying it against the real command enum showed the class was broader — `ScheduleActivity`'s per-call retry/start-to-close/schedule-to-start overrides and session pin, `RunLocalActivity`'s timeout and retry policy, `SpawnDetachedChildWorkflow`'s `ParentClosePolicy`, `SignalExternalWorkflow`'s idempotency key, and `ArmTimer`'s `for_await` were all dropped too. `command_payload` now carries **every semantic dispatch field**, and documents what it deliberately excludes and why (per-run ids, oneshot channels, `token`/`lock_seq`, and the retry-bookkeeping fields `already_scheduled` / `failed_attempts` / `last_error`, which are engine state rather than a dispatch decision). Note that exhaustiveness at the *variant* level — already enforced since the pre-PR review — is **not** sufficient: dropping a field *within* a matched variant produces exactly the same false clean, which is why the guard is now the field list, not the arm list. (2) **The fixture-vs-fixture diff missed semantic event fields**, because it compared a *curated* `resolved_payload` projection: a changed timer duration, a changed activity error, a changed child-workflow name — none moved a compared field, so two genuinely different recordings reported "no divergence" and exited `0`. Reproduced empirically before fixing (`harvest debug diff` on two histories differing only in `TimerStarted.duration_secs` → *"no divergence … agree across all 2 steps"*, exit 0). Fixed **structurally** rather than by extending the curated list, which would rot again the moment `WorkflowEvent` grows: `WorkflowEvent` **is** `Serialize` (it is the persisted wire type), so the new `DebugStep::event_facts` is the whole serialized event with only per-run identity normalized to `<per-run>` (top-level `data` keys that parse as a UUID, `timestamp`, and the recorded `value` of the non-deterministic `Now`/`Uuid`/`Random` side-effect kinds — normalization is deliberately confined to the *top level* of `data`, since business payloads nest under `input`/`output`/`payload`/`details` where a UUID is real data). It is therefore exhaustive by construction. It is checked **last**, after the curated projections, so the good diagnostics survive — `open_awaitables` still beats "the events differ" for a renamed activity — while the hole is closed; the same normalization keeps two independent recordings of one scenario diffing clean. The now-superseded `comparable_payload` helper was deleted, and the CLI renders `event_facts` per side so the operator sees *which part of the event moved*: `{"data":{"duration_secs":30,…}}` vs `{"data":{"duration_secs":60,…}}`. Plus two P2s: (3) a parked `ctx.mutex(k).acquire()` (issue #691) has no opening event — its waiter row lives in `harvest_mutex_waiters` and only the *grant* records `MutexGranted` — so, like a signal wait, it exists solely as a frontier `AcquireMutex` command; the awaitable synthesis now covers both, mapping command→kind exactly as `awaitables.rs` does, so a mutex-blocked run no longer displays as waiting on nothing (and, being code-derived, it is excluded from the history-fact comparison alongside `Signal`). (4) TUI setup rolled back incompletely: `enable_raw_mode()` succeeded and a subsequent `?` returned *past* the restore block, leaving the user's shell in raw mode — on a partially-supported terminal, a debugger that wrecks the shell it was launched from is worse than the bug being chased; each setup step now unwinds the ones before it. Regressions: a queue-only and a deadline-only external-activity change, and a start-to-close-only activity change (which additionally asserts the two summaries are *identical*, so the test is only meaningful while the payload is what carries the difference), a mutex park appearing among the open awaitables, and — at the CLI layer — an `event_facts` divergence rendering both normalized events.

  **Post-review hardening, Codex round 2 (three P1s, two P2s — plus one found by the regression written for them).** (1) **Sub-second timeouts collapsed through `as_secs()`** — the round-1 fix rendered `start_to_close` / `schedule_to_start` as whole seconds, so a local activity configured at 100 ms versus 900 ms produced *identical* snapshots and diffed clean. That is the round-1 false-clean class reintroduced by the round-1 fix, and it is not hypothetical: `execute_local_activity_raw_resolved` carries a full `Duration` precisely so "a subsecond OR sub-millisecond floor never truncates to `0`" (issue #620, itself a Codex finding). Durations now serialize at full precision via `Duration`'s own `Serialize` impl (`{secs, nanos}`). (2) **The prefix context dropped three snapshot replay inputs** — `parent_execution_id`, `execution_timeout` and `deadline_at` are execution-*row* columns that live in no `WorkflowEvent`, which is exactly why `HistorySnapshot` carries them; a workflow branching on `ctx.info().parent_execution_id` (#698), reading its deadline, or calling the deadline-sensitive `should_continue_as_new()` (#772) therefore emitted commands from defaults and **fabricated a divergence on a valid production export**. This is the same threading debt #772 paid down across eight rounds for the worker, replayer, export and query-hydration paths; the debugger is a new replay path and now threads them too, using only already-`pub` builders so AC5 still holds. (3) **Per-run normalization was value-based, not field-based** — "anything that parses as a UUID" also ate `ExternalSignalRequested { idempotency_key }`, a *caller-chosen* exactly-once key (#521) that is very commonly a UUID and is semantic: two histories differing only in it are genuinely different, and normalizing it reported them equal. Normalization now keys on a field-name allowlist derived mechanically from `WorkflowEvent`'s own declared types (a field qualifies exactly when its type is a UUID newtype), with the UUID parse retained *in addition* so `target`'s business-id form still compares verbatim. The allowlist is hand-written, so it is guarded by `engine_minted_id_fields_match_the_event_enum`, which re-derives the set from `event.rs` at test time and fails in **both** directions — a missing field is silently compared verbatim (noise), an extra one is silently normalized away (a false clean); verified falsifiable by deleting an entry. (4) **P2 — `ReplayDebugger::history_policy` was a dead setter**: stored, never read, so `should_continue_as_new()` always saw the default threshold and deadline fraction; now threaded via `with_history_policy`. (5) **P2 — `--tui` swallowed an unsatisfiable focus**: a missed breakpoint or out-of-range `--step` fell through to cursor `0` and exited `0` once the user quit, unlike the text and JSON paths — a breakpoint that reports a hit it never made is the one thing a breakpoint must never do. Both now error *before* the terminal enters raw mode (which is also what lets the regression run headless). (6) Writing the regression for (3) surfaced a **third instance of the same normalization gap, one layer up**: `awaitable_shapes` dropped the separate `id` field but kept the display `name`, and `ExternalSignalRequested` renders its name as `"{signal_name} -> {target}"` — so a per-run target exec id leaked back in and two independent recordings of one "signal a sibling" scenario diffed as different. Fixed by normalizing UUID-shaped tokens inside comparison labels; a business-id (`ExternalTarget::WorkflowId`) target contains no UUID and still compares verbatim. Regressions: a sub-second local-activity timeout change (asserting the two summaries are *identical*, so the payload is provably what carries it), a UUID-shaped `idempotency_key` change **and** its inverse control (engine-minted `signal_id`/`target` in the same event still diff clean, so the allowlist cannot be "fixed" by normalizing nothing), a workflow branching on `parent_execution_id`, and `--tui` rejecting both unsatisfiable focus forms.

  **Post-review hardening, Codex round 3 (two P1s — both false cleans again — and two P2s).** (1) **Two equally-capped traces reported as clean.** `diff_traces` only carried a `capped` flag on `DiffKind::TraceLength`, which fires on a *length* difference — so when both traces hit the same `max_steps` cap (500 by default) their step counts were equal, that check never ran, and a difference living past the cap was returned as `divergence: None`. `TraceDiff` also dropped both inputs' `truncated` flags, so a caller could not even tell. A CI gate reading `divergence.is_none()` was therefore treating an unexamined suffix as a pass. `TraceDiff` now carries `truncated`, and the verdict is `TraceDiff::is_clean()` — `divergence.is_none() && !truncated` — which is what callers must read. The CLI renders an explicit `INCONCLUSIVE` report (never the "no divergence" wording) and exits **`2`**, joining the CLI's existing "could not determine" gates (`WorkflowReachabilityGate`, `QueueCoverageGate`, `RestoreUndetermined`) so a script can distinguish it from `1` = "differences found" and `0` = "compared in full and agree". (2) **Two recordings of different workflow types reported as agreeing.** `diff_traces` compared only steps, and `workflow_name` is an execution-*row* column that appears in **no** `WorkflowEvent` — not even `WorkflowStarted`, which carries only `input` — so the round-1 `event_facts` backstop is structurally blind to it. Two histories of genuinely different workflows with similarly-shaped event arrays walked every step and exited `0`; reproduced end to end against the built binary (`onboarding` vs `checkout` → *"no divergence … agree across all 1 steps"*, exit 0). A new `DiffKind::WorkflowName { left, right }` is now checked **before** the step walk — the same "if the recordings are not of the same thing, comparing what the code did next is apples to oranges" principle as `step_diff_kind`'s history-facts-first ordering, one level up. `execution_id` is deliberately **not** compared alongside it (it differs on every pair of independent recordings, so comparing it would fabricate a divergence on every fixture diff — the same reason it is normalized out of `event_facts`), and that exclusion is pinned by its own test. (3) **P2 — a signal breakpoint could not match a multi-word name.** `WaitForSignal`'s summary *is* the signal name with no qualifier appended (unlike `ScheduleActivity`'s `"{name} -> {queue}"`), but the frontier match ran it through the whitespace-splitting `summary_names`, so `SignalName("order approved")` was unmatchable — at exactly the step a breakpoint exists for, since a waiting frontier has no `SignalReceived` yet to match instead. Now an exact comparison; the now-unused `summary_names` helper was deleted rather than left dead. (4) **P2 — `worker_id` was compared verbatim**, so two independent recordings diverged at the *first* `ActivityStarted`, burying every later semantic difference behind pure per-run noise. This is the round-2 allowlist's own derivation rule showing its seam: the rule was "a field qualifies when its type is a UUID newtype", but `worker_id` is `WorkerId`, a **`String`-backed** newtype whose *value* `WorkerRuntimeConfig::from` always mints as a fresh `Uuid::new_v4()` (there is no `WorkerConfig::with_worker_id`) — engine-minted by value, not by type. My round-2 doc comment asserting the opposite was simply wrong and is corrected. The dual guard already in place handles the remaining nuance for free: `WorkerRuntimeConfig::worker_id` is a `pub` field, so an embedder may set a stable label (`WorkerId::new("worker-eu-1")`), which does not parse as a UUID and therefore still compares verbatim — engine identity normalized, operator's choice preserved. The drift test's type list was renamed `ENGINE_MINTED_FIELD_TYPES` and gained `WorkerId`, with a comment recording that the type is a *proxy* for the real predicate and this is where the proxy needs an explicit entry. A full re-enumeration of every field type in the enum confirmed `worker_id` is the only such case (`TimerId` is the mirror image — `String`-backed but author-chosen, so correctly excluded). Regressions, each verified to fail against its own pre-fix code: equally-capped traces are inconclusive (plus an uncapped control, so the fix cannot have made every diff inconclusive), different workflow types diverge (plus a differing-`execution_id` control), a multi-word signal name matches a waiting frontier (plus a partial-name control, so the breakpoint stays precise), and a differing `worker_id` is *not* a divergence (plus an operator-label control, so adding it to the allowlist cannot have discarded a real difference — the round-2 `idempotency_key` mistake, one field over). At the CLI layer: a workflow-type diff exits non-zero and names both types, and a capped comparison renders `INCONCLUSIVE`.

  **CI portability fix.** `engine_minted_id_fields_match_the_event_enum` — the round-2 drift guard that re-derives the allowlist from `event.rs` at test time — scanned for the enum's closing brace with `find("\n}\n")`, which finds nothing on a checkout with CRLF line endings, so the test *panicked* on the Windows CI runner instead of asserting (3070 passed, 1 failed). The source is now normalized to LF immediately after reading, which fixes both the terminator scan and the per-line field scan on every OS. Verified by converting `event.rs` to CRLF in the working tree: the test passes with the fix and reproduces the exact Windows panic without it.

  **Post-review hardening, Codex round 4 (two P1s — a third and fourth false-clean shape — and one P2).** (1) **A build that never replayed successfully was certified as clean.** A step that timed out (a spinning workflow) or panicked reports `divergence: None` because the replay never *finished*, not because the build agreed — and the documented single-build check was a scan for `divergence.is_some()`, so both certified clean. Two builds failing the *same* way likewise compared equal at every field, so `diff_traces` returned no divergence: agreement between two non-answers. Fixed with the round-3 `TraceDiff::is_clean()` pattern applied one level down — `ReplayTrace::is_clean()` (`!truncated && no unsuccessful step && no divergent step`) is now the documented verdict, with `first_unsuccessful_step()` / `first_divergent_step()` reporting *which* reason applies, and `TraceDiff` gained `inconclusive_step` so a both-sides-failed comparison renders `INCONCLUSIVE` and exits **2** rather than `0`. The docs table, the example's three assertions, and the CLI all moved onto it. **The `NotReplayed` carve-out is load-bearing and nearly went the wrong way**: the first cut folded it in with timed-out/panicked, which broke the pre-existing round-3 control — a handler-free `ReplayTrace::from_history` projection is `NotReplayed` at every step, so AC3's compare-two-recordings mode (the CLI's *primary* diff path) would have exited `2` on every fixture diff. The two questions need opposite treatment and now have separate predicates: `is_clean()` on a single trace requires `replay_succeeded()` (a projection that ran no code has verified nothing), while `inconclusive_step` keys on `replay_failed()` only (a fixture-vs-fixture diff compares history-derived facts, which the two recordings determine completely, so it is genuinely conclusive). Both directions are pinned, including a named guard for the carve-out itself. (2) **The candidate build's payload caps were not applied during prefix replay.** `max_activity_input` / `max_signal_payload` / `max_workflow_input` and the #524 offload threshold live in no `WorkflowEvent` — the live worker supplies its own from `BuiltHarvest` — and the cap is consulted exactly at the `NoMatch` frontier, which is where *every* prefix step lands. Left at library defaults the debugger answered a question about a worker that does not exist, in both directions: a candidate that lowers a cap has an over-cap dispatch accepted here and rejected in production (false-GREEN), while a candidate configuring an offload threshold has a legitimate over-cap payload rejected here (false-RED, a fabricated early-return divergence on a valid export). This is the same threading debt rounds 2 and #798 paid down for `parent_execution_id` / `execution_timeout` / `deadline_at` / `history_policy`; `ReplayDebugger` gains `payload_caps()` and `payload_offload_threshold()` mirroring `WorkflowReplayer`'s, applied through already-`pub` `WorkflowContext` builders so AC5 still holds. `max_activity_result` is deliberately absent — the worker enforces it after an activity returns, never `WorkflowContext`, so it cannot affect a replay. (3) **P2 — event-less race-loser timers stayed open forever.** A signal-win of a signal-or-deadline race (#476), or a child-win of a child-or-deadline race (#779), tears its reserved deadline timer down through an **event-less** `CancelRaceLosers` row delete: no `TimerFired`, no `TimerCancelled` is ever recorded. Closing timers only on those two events left the loser in `open_awaitables` for every later step, rendering a resolved race as a run still waiting on a timer — the same bug `awaitables.rs` fixed for the history projection in #615. The accumulator now mirrors that cleanup and calls **the same** id parsers (promoted to `pub(crate)`), so a change to the reserved prefixes cannot drift the two projections apart; `close` returns the removed awaitable because a child terminal names only the `child_id` while its reserved timer encodes the workflow *name*. Regressions, each verified to fail against its own pre-fix code: a spinning and a panicking build are not clean (with a genuinely-clean control, so the tightening cannot have made every trace unclean), a handler-free projection is never clean, two identically-failing builds diff inconclusive (with a differently-failing control that must stay a real divergence, and a healthy-pair control), a signal-win and a child-win close their reserved timers (with two controls: an author's own `ctx.timer` and another signal's reserved arm must survive, and a late signal after a timer-win must not close an unrelated timer), and a lowered cap changes the replay outcome while an offload threshold exempts it.
