- **R&D** (implemented): Time-travel replay debugger for recorded workflow histories — see issue #949. Gives an engineer the answer the existing replay surfaces stop short of: not *"does this history diverge?"* but ***"where exactly, and why?"***. Two entry points over one shared `ReplayTrace` type — the library `autumn_harvest::debugger` (behind a new `debugger` Cargo feature, which implies `testing`) and the local CLI `harvest debug`. **Read-only by construction (AC5): no new `WorkflowEvent` variant, no migration, no engine-runtime change, no activity execution, no database access.** Zero core-engine edits were needed — every primitive the design required (`WorkflowContext::for_replay_canary_with_state`, `executor::drive_query_replay_async`, `drain_commands`, `take_nd_details`, `take_deferred_nd_error`, `replay_position`, and the `with_*` builders) was already `pub`.

  **Mechanism — prefix replay, blessed by AC2's own wording.** Step `k` is a *fresh* replay of `events[0..=k]`; "backward" is re-run-forward, exactly as the AC describes ("replay is deterministic, so 'backward' is re-run-forward"). The load-bearing insight is that a clean replay emits **zero** replay-significant commands — commands are only emitted at the live frontier — so a prefix replay yields precisely *"what does this code do next, given history so far"*, which is both the per-step frontier command batch and the ideal diff signal. Two supporting choices: **canary, not strict** replay (`for_replay_canary_with_state` sets `strict_replay` **and** `canary_mode`, so `strict_replay_no_match_is_divergence()` still catches a *mid-prefix* divergence while allowing frontier command emission — a prefix genuinely *is* an in-flight execution parked at its frontier); and **`drive_query_replay_async`** (issue #612) rather than `drive_workflow`, because the latter's 100 ms `SUSPENSION_TIMEOUT` would cost `N × 100 ms` (100 s for a 1k-event history) whereas the former detects suspension instantly via a per-poll command delta. Since that driver deliberately discards the handler's `Ok`/`Err`, non-determinism is read back through `ctx.take_nd_details()` / `take_deferred_nd_error()`.

  **AC1 — the snapshot.** `DebugStep` carries, after each consumed event: the event index and type, the pending `WorkflowCommand`s, the **open awaitables** (kind, name, id, and — as the AC explicitly requires — the `opened_at` **event index that opened them**), resolved **version-gate** values (`version:` markers) and **patch gates** (`patch:` markers, issue #687), recorded **side effects** and **markers** verbatim, the resolved payload, the signal name, and any recorded divergence. `AwaitableKind` is reused from `awaitables.rs` as the shared vocabulary, but the projection is debugger-owned: `awaitables::project_awaitables` requires timestamped `(DateTime<Utc>, WorkflowEvent)` rows that a `HistorySnapshot` does not carry, and its `Awaitable` has no `opened_at` index at all.

  **Handler-free vs handler-backed split.** Everything except pending commands derives from history alone in a single **O(N)** fold (`ReplayTrace::from_history`); only commands need registered workflow code (`ReplayDebugger::trace_snapshot` / `trace_json`). This split is what makes the CLI viable at all: the shipped `harvest` binary is statically linked and **cannot register an application's `#[workflow]` handlers** — the same constraint `harvest-replay` already states. So the CLI covers stepping, breakpoints and inspection plus the *two fixture histories* arm of AC3, while the library covers per-step commands and the *two code registrations* arm. Both produce the same `ReplayTrace`, so a session that starts in the CLI graduates to the library without reshaping anything; the capability split is documented as a table in the CLI module doc and in `docs/replay-debugger.md`.

  **AC2 — the driver.** `harvest debug replay <HISTORY>` with `--step N`, four breakpoint forms (`--break-at-event-type` / `--break-at-index` / `--break-at-activity` / `--break-at-signal`, declared mutually exclusive at the clap layer so a breakpoint never silently loses to another), `--max-steps N`, `--format text|json`, and `--tui` for an interactive stepper (`n`/`p`/`g`/`G` to move, `d` to jump to the next divergence — which requires a handler-backed trace, so in the handler-free CLI it reports that in the footer rather than sitting inert — `q` to quit; `--step`/`--break-*` seed the opening cursor; the terminal is restored even on error). JSON mode always emits the **whole** trace — silently emitting a focused partial document would be a trap for a `jq` pipeline.

  **AC3 — diff mode.** `diff_traces(left, right)` walks steps in order and reports the **first** difference only, because one root cause routinely produces dozens of downstream differences and reporting them all would bury the actionable one. `harvest debug diff <LEFT> <RIGHT>` exits **`1`** on divergence, mirroring `diff(1)`'s "differences found", so it drops straight into a CI pipeline. The **#614 boundary is stated in the module doc**, in `docs/replay-debugger.md`, and in the cross-tool tables of `docs/replay-verify.md` / `docs/replay-drift-gate.md`: #614 is a one-shot server-side verdict on one live run; this is the interactive local tool you reach for *after* it says "yes, diverging".

  **Display vs identity separation (a real bug caught by the corpus).** `CommandSnapshot` carries **both** a short, truncatable `summary` (for terminals) and an exact, never-truncated `payload: Option<Value>` (used for diffing). The first cut folded the input into the summary and truncated it, so the *"changed activity input"* corpus scenario reported its first divergence at step 3 instead of step 2 (the input difference was invisible until strict verification fired mid-history). Truncating into the compared field would silently hide a divergence deep in a large payload — on a divergence-finding tool, the worst possible failure mode.

  **History-fact diffing + per-run identity normalization (the second arm of AC3).** A handler-free trace emits *no* commands, so a command-only comparison could not see two **fixture histories** differing at all — `harvest debug diff` was structurally incapable of finding anything, a gap the new CLI tests caught. `diff_traces` now compares the history-derived facts first (via `DiffKind::HistoryFacts { field }`), ordered deliberately: history facts → commands → outcome (if the two *recordings* already differ, comparing "what did the code do next" across them is apples to oranges). Because two *independent recordings* of the same scenario necessarily differ on freshly-minted per-run values, the comparison **normalizes them out**: activity/child execution UUIDs, and the recorded values of the non-deterministic side-effect kinds (`Now`/`Uuid`/`Random`, issue #384) — the latter suppressed once, coherently, in `comparable_payload` so the `resolved_payload` and `side_effects` checks cannot drift apart. Everything semantically meaningful is still compared: event type, signal name, resolved payload, awaitable kind/name/`opened_at`, version and patch gates, marker names and details, and the values of `Custom` side effects (application data, not engine identity). This cannot hide a code-caused divergence — in the two-registrations arm both sides replay byte-identical events, so the normalized fields are equal by construction and the divergence surfaces through `commands`; in the two-histories arm a change that matters (renamed/reordered activity, different input, new marker, changed version gate) moves a field that *is* compared. `history_fact_diff` **exhaustively destructures** `DebugStep`, so adding a field without classifying it as history-derived or code-derived is a compile error rather than a silent false "clean".

  **Gates at a truncated frontier (documented semantic).** Since a step replays `events[0..=k]`, an intermediate step models an execution *parked at that truncated frontier* — so a `ctx.patched(...)` (#687) or `ctx.version(...)` gate reached there is, correctly, **newly** patched. A correctly-gated build therefore legitimately differs from an ungated one at intermediate steps while still replaying the *full* recorded history perfectly. The two questions need two checks, both documented and both asserted in the example: *"where do these builds first differ?"* → `diff_traces(...).divergence`; *"does this build replay this history cleanly?"* → no step has `divergence.is_some()`.

  **Cost, bounded honestly.** Building a full trace is `N` replays and therefore **O(N²)** — fine for the interactive histories this is for (tens to low hundreds of events), and deliberately not how the CI gates work (they replay each history once). `--max-steps` / `ReplayDebugger::max_steps` caps it, and `ReplayTrace::truncated` reports the cap so a partial view is never mistaken for a complete one. `DEFAULT_MAX_STEPS = 500`, `DEFAULT_STEP_TIMEOUT = 5s`.

  **AC4 — exported histories.** Input is the `HistorySnapshot` JSON round-trip format (`harvest history export`), so a production history is debugged on a laptop with zero database access. Payload-codec and offload-envelope fields **display as their envelopes** when no codec or store is configured, rather than erroring.

  **Success metric — met.** `divergence_corpus_identifies_the_first_divergent_step_in_every_scenario` runs a **13-scenario** corpus (≥10 required) spanning the `NonDeterminismKind` classes the issue names, and identifies the exact first divergent step index in **13/13**: reordered commands, inserted activity at the front, renamed activity mid-history, changed activity input, changed target queue, activity→timer, activity→child-workflow, dropped trailing activity, `SideEffectDrift` (inserted `ctx.new_uuid()`), inserted version gate, count-mismatch fan-out (2→3), signal-wait→activity, and a fan-out whose *second* slot's input changed. That last one is load-bearing: the corpus asserts the **command index** as well as the step index (the metric names the divergent *command*), and it is the one scenario whose expected command index is **not** 0 — so a stub hardcoding `command_index: 0` fails it.

  **AC6 — docs and example.** New `docs/replay-debugger.md`: the cross-tool comparison table (vs `replay-verify` / the replay-drift gate / #614), the two-arms capability table, and a six-step worked walkthrough that takes a new user from an exported history to an identified root cause — overview → breakpoint → interactive stepper → **diff old vs new build** (which pinpoints `fraud_check` inserted ahead of an already-recorded `charge_card` with no gate) → gate the change → confirm clean. Cross-linked from `docs/replay-verify.md` and `docs/replay-drift-gate.md`. Runnable companion `autumn-harvest/examples/replay_debugger.rs` (`required-features = ["debugger"]`) prints that exact walkthrough and carries four self-verifying tests, including the "ungated build does **not** replay cleanly" control that proves the clean-replay assertion measures something.

  **Tests.** 38 core tests in `autumn-harvest/tests/integration/debugger_tests.rs` (handler-free projection, `trace_snapshot`, breakpoints, diff, the 13-scenario corpus, the fixture-vs-fixture normalization contract, the three `DiffKind` variants the corpus cannot organically reach — `CommandCount` / `Outcome` / `Divergence` — and the robustness guards: a spinning workflow times out rather than hanging, a panicking workflow is contained, `max_steps: 0` clamps to one step, a redacted export is refused, and a **structural** AC5 guard that scans `debugger.rs`'s own source for any persistence symbol); 1 unit test in `debugger.rs` pinning the `version:`/`patch:` marker prefixes against the engine's own `replay::{version,patch}_marker_name` builders, so a rename there cannot silently reclassify every gate as an ordinary marker; 8 clap-layer tests in `autumn-harvest-cli/src/lib.rs` (defaults, every flag, each breakpoint alone, and all three mutual-exclusion rejections); 37 black-box CLI tests in `autumn-harvest-cli/tests/integration/debug_cli.rs` (breakpoint/focus resolution, every `render_step_detail` section, `run_replay`/`run_diff` end to end, every error path's exit code, JSON-mode wholeness, the redaction warning, activity-breakpoint precision against a name prefix and against a queue name, plus a guard on the fixture itself so an id-reuse regression cannot silently weaken every open-awaitable assertion); 6 pure `StepperState` unit tests in `debug_tui.rs`; and 5 example tests. Registered in `.github/ci/integration-suites.txt` as one sorted `allos` row (`testing,debugger`), so it runs on every OS with no DB, plus a dedicated CI step for the example's tests.

  **Post-review hardening.** Three parallel review agents (replay-semantics, API/CLI design, and test-quality/AC-evidence) produced one **P1** and several P2s, all fixed: (1) **the debugger was strictly weaker than canary replay** — the canary/strict runners apply `ctx.history_has_unconsumed_events()` *after* the handler returns, and omitting that check meant a build that **dropped an activity** (or did nothing at all) replayed 100% "clean", the exact class the tool exists to catch; now gated on `ReachedTerminal`, using only already-`pub` API so AC5 still holds, with `a_build_that_completes_early_does_not_replay_cleanly` as the falsifying control. (2) **`command_payload` had a `_ => None` catch-all**, collapsing `Complete` / `Fail` / `RecordUpdateResult` / `CancelRaceLosers` / `RecordLog` onto equal snapshots — two genuinely different commands diffing as identical, on a divergence-finding tool; it is now exhaustive (no `_` arm), so an added `WorkflowCommand` variant is a compile error rather than a silently hidden divergence. (3) `record_deferred_nd` populates **both** nd slots, so the original lazy `.or_else()` chain never reached the informative message and **every `SideEffectDrift` reported `<unknown>`/`<unknown>`** — the headline case in the issue's own success metric. (4) Eight missing awaitable arms (`ExternalSignal*` / `ExternalCancel*` / `ActivityAwaitingExternal`) left external-workflow operations invisible in the open-awaitable column. (5) **AC1's signal waits were unimplemented** behind a misleadingly-named test; a `WaitForSignal` command now synthesizes an `AwaitableKind::Signal` — and, because that is *code-derived*, it is excluded from `history_fact_diff` so a code difference is never misreported as "the recorded histories differ". (6) The docs' export recipe handed the tool a **redacted** history (`harvest history export` defaults to `--payload-policy redacted`, rewriting payload fields in place), which fabricates a divergence at the first payload-bearing activity; fixed in the docs *and* enforced — `ReplayDebugger` refuses one (`DebugError::RedactedHistory`) and the CLI warns, mirroring the replay-drift gate's precedent. (7) A recorded divergence is **code**-derived, so it is now its own `DiffKind::Divergence` rather than being misfiled as `HistoryFacts { field: "divergence" }` — which would have told an operator "these are different recordings", a wrong and actively misleading diagnosis. (8) `DiffKind::TraceLength` gained a `capped` flag so diffing two traces built with different `--max-steps` is self-diagnosing instead of reporting a divergence that does not exist. (9) CLI ergonomics: `--tui` silently discarded `--step`/`--break-*` (they now seed the opening cursor), JSON mode swallowed a missed breakpoint's exit code, a capped trace rendered as a complete one, and the `d` key sat structurally inert in the handler-free CLI (it now says why). (10) Driving the built binary against a real fixture surfaced one more: `harvest debug diff` named the differing history field and then showed nothing about it — since the handler-free arm emits no commands, a fixture diff printed "the recorded histories differ (open_awaitables)" above two identical `<no pending commands>` lines. Both sides now render the **value** of the named field (`activity charge_card (opened at 3)` vs `activity fraud_check (opened at 3)`), which is the entire point of the CLI's primary diff path.
