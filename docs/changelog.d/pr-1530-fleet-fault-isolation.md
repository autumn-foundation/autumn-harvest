## Fix — one unsupported-command execution head-of-line-blocked unrelated executions in `poll_once`/`run_until_idle` (issue #1530)

`SqliteRuntime::poll_once`/`poll_once_as_of` drove `store::running_executions` — every `RUNNING` execution, in ascending `ExecutionId` order — with `self.drive_one_cycle(exec, now, &failure_now).await?`. The bare `?` propagated the first per-execution error and aborted the rest of that pass, so any execution ordered after a permanently-erroring one (an unsupported command such as `SignalExternalWorkflow`, but any `drive_one_cycle` error applies) never got a decision cycle — not once, forever, even after a restart, since the broken execution never reaches a terminal state and never enqueues anything for the orphan reclaim to touch. `running_executions` sorts by `ExecutionId` string, so roughly half of all newly started executions in a long-running app land on the stalled side once one broken execution exists.

**The fix keeps `poll_once`'s promise literal: drive *every* execution, not just the ones before the first failure.** Both loops now match on `drive_one_cycle`'s `Result` inline instead of using `?`: an `Err` is handed to the new free function `record_fleet_error`, which logs it (`tracing::warn!`, naming the execution and the error) and keeps only the first one for the caller, while the loop moves on to the next execution. `poll_once`'s return type is unchanged (`SqliteResult<bool>`) — no public API break — and the offending execution's error is still surfaced to the caller exactly as before (the crate's "rejected LOUDLY, not silently dropped" promise, `register_workflow`/`apply_commands` doc comments), just no longer at the cost of every other execution in the pass.

`run_until_blocked`/`run_until_blocked_as_of` (the single-execution driver) are unchanged and stay fail-fast on purpose — that call already targets one execution the caller knows about, so propagating immediately is correct there; the bug was specific to the fleet-wide loop driving many unrelated executions. Mirrors the same collect-and-continue shape already shipped for the Postgres scheduler's per-schedule loop (`register_workflow_schedules_for_shard`, "Defect 2" in the phase history): public/startup entry points keep fail-fast `?`; only the tick-path fleet loop collects.

**Zero unrelated engine impact:** no new `WorkflowEvent` variant, no migration, no schema change, no stored/durable behavior change — the broken execution still stays `RUNNING` and un-sealed, exactly as before, since automatically sealing a permanently-erroring execution to a terminal state is a separate design decision the issue explicitly left open and out of scope here.

Tests, red → green: `autumn-harvest-sqlite/tests/integration/fleet_fault_isolation.rs` reproduces the issue's exact repro shape (a `broken_wf` reaching `ctx.signal_external_workflow` through ordinary dynamic control flow, and a `healthy_wf` execution started until its `ExecutionId` sorts after the broken one) and asserts both that a single `poll_once` call still names the offending command AND drives the unrelated execution to completion in the same pass, and that a `run_until_idle` loop (mirroring the issue's own repro driver) no longer leaves the unrelated execution durably stuck. Full `autumn-harvest-sqlite` suite (125 tests) passes with no regressions.
