## Phase 3.51 — Deadline-aware continue-as-new for long-lived, low-event workflows (issue #772)

A long-lived entity workflow (a subscription, a cart, a device) can run for weeks while recording only a handful of events, so it never approaches the history event-count threshold `ctx.should_continue_as_new()` watches — yet if it declares an `execution_timeout` (#243) for runaway/SLA protection, that hard timeout eventually terminates it mid-flight even though it is healthy. This slice gives `should_continue_as_new()` a **second, independent trigger**: it now *also* returns `true` once the run has consumed at least a configurable fraction (default `0.8`) of its `execution_timeout` budget, so the author can `continue_as_new` **before** the hard deadline truncates the run, carrying state forward into a fresh run with a fresh deadline. Entirely additive, pure `WorkflowContext` + replay logic. **No new `WorkflowEvent` variant, no migration, no change to the adjacently-tagged event-JSON contract.**

New public `WorkflowContext` accessors, both **pure and replay-safe**: `deadline() -> Option<DateTime<Utc>>` = the recorded `WorkflowStarted` timestamp (`start_time`, no advancing clock) + the effective `execution_timeout`, `None` when there is no timeout or the sum overflows — records **no** event; and `time_until_deadline() -> Option<chrono::Duration>` = `deadline() - system_now()`, measured against the replay-safe recorded wall clock (`system_now()`, #384's `SideEffectRecorded{Now}`), **never** `chrono::Utc::now()`. `time_until_deadline` checks the pure `deadline()` first, so a workflow with **no** `execution_timeout` consults (and records) **zero** side-effects (AC4). The private `deadline_fraction_reached()` returns `false` (recording nothing) when there is no timeout, a non-positive budget, or an overflowing deadline, else trips when `remaining <= (1 - fraction) * total` (a deadline already in the past trips). `should_continue_as_new()` combines the two triggers as `by_events || by_deadline` with **both bound before the `||`** — the deadline branch is evaluated unconditionally so a timeout-bearing workflow's recorded side-effect stream is a pure function of "has a deadline" (constant across the run's life) rather than the task-varying event count.

**Cross-version replay safety (the tolerant clock read).** `should_continue_as_new()`'s deadline branch does **not** call the strict public `time_until_deadline()`/`system_now()`; it uses an internal **tolerant** clock read, `deadline_clock_read()`, backed by the new three-state `HistoryMatcher::match_side_effect_now_tolerant() -> SideEffectNowMatch` (`Matched{millis}` / `NotRecorded` / `Frontier`, re-exported from `lib.rs`). This closes a cross-version replay hazard two reviewers converged on: an execution recorded under a **pre-#772 binary** carries no `SideEffectRecorded{Now}` at the `should_continue_as_new()` call site, so when it resumes under the new binary the strict `system_now()` would hit whatever real event is recorded at the cursor (a `TimerStarted`/`ActivityScheduled`/`ChildWorkflowStarted` — the canonical `should_continue_as_new()`-then-`ctx.timer()` shape, the shipped example's shape) and record a `SideEffectDrift` non-determinism error → #603 nd-block, wedging a healthy long-lived workflow on a routine upgrade. The tolerant read instead: at the **live frontier** records a fresh `Now` and pushes the `RecordSideEffect` command exactly as `system_now()` does; on a **matching recorded `Now`** consumes it (identical to strict); on **any other recorded event** returns `None` **without consuming the cursor and without diverging**, so `deadline_fraction_reached()` degrades to history-count-only for that run's pre-upgrade recorded portion. It is replay-safe by construction (for a new execution, identical to strict; for an old one, a pure/stable function of the event at the cursor — a non-`Now` event always → `None`), and once the run executes live past its pre-upgrade frontier it records `Now`s normally and picks the deadline feature up. The only "masking" is fail-safe: a genuine control-flow reordering that lands a deadline clock-read on a recorded non-`Now` event degrades to a missed checkpoint *suggestion* rather than nd-blocking — it can never emit a wrong command, and any real divergence still nd-errors at the next real command. The public `system_now()`/`time_until_deadline()` stay **strict** (any direct call is new author code subject to normal versioning rules).

`WorkflowHistoryPolicy` gains `continue_as_new_deadline_fraction: f64` (default `DEFAULT_CONTINUE_AS_NEW_DEADLINE_FRACTION = 0.8`, re-exported from `lib.rs`) with a `continue_as_new_deadline_fraction()` accessor and a `with_continue_as_new_deadline_fraction(f64)` setter that **clamps to `[0.0, 1.0]`**. Because `f64` is not `Eq`, the struct's derive dropped from `PartialEq, Eq` to just `PartialEq` (a repo-wide grep confirmed no `Eq`/`HashMap`-key/whole-struct-`assert_eq!` usage — only accessor-level asserts). Builder: `HarvestBuilder::history_continue_as_new_deadline_fraction(f64)`.

**Threading**: the effective `execution_timeout: Option<chrono::Duration>` (the same value the execution row carries, so `deadline = start_time + execution_timeout` derives purely from the recorded start) is a new field on `WorkflowContext`, set via the new `with_execution_timeout` builder. It is threaded from `WorkflowExecuteSpanMeta` (new `execution_timeout` field, populated by the worker from `prepared.execution.execution_timeout`) into `run_workflow_with_state_history_policy_and_caps` (worker path) and `run_workflow_with_state_advancing_clock` (test-env path), and as a new trailing parameter on `run_workflow_strict` / `run_workflow_strict_advancing_clock` / `run_workflow_canary` (replayer path, which has no span_meta). `WorkflowReplayer::with_execution_timeout(chrono::Duration)` and `WorkflowTestEnv::with_execution_timeout(chrono::Duration)` expose it to the harnesses.

**Determinism contract**: a history that crossed the deadline replays to the same `ContinueAsNew` command on every worker, because the deadline is derived from the recorded start time and the clock read reuses the existing `SideEffectRecorded{Now}` event — the frozen-once, replayed-verbatim capture from #384. Proven by the falsifiable `deadline_triggered_can_replays_deterministically_1000x` replayer fixture, which pins the **decision** across 1000 **distinct** fixtures — varied frozen `system_now()` capture and budget, **mixing trip (≥0.85 of budget consumed) and not-yet (≤0.40 consumed) cases**, both well clear of the 0.8 boundary — via a branch probe that schedules `checkpoint_now` when it trips and `keep_working` otherwise: because the recorded activity fixes the expected decision, a **broken fraction comparison schedules the other activity and diverges**, so this bar actually falsifies a wrong decision rather than passing regardless (the earlier completing probe completed identically no matter the decision — a tautology). `replay_deadline_crossed_history_yields_continue_as_new` separately proves the actual `ContinueAsNew` command replays via a single `continue_as_new` fixture.

Docs: "Checkpoint before the deadline kills you" note in `docs/getting-started/07-reliability-knobs.md` (next to the SLA/`execution_timeout` material), plus a **call-once-per-decision-cycle** guidance line (each `should_continue_as_new()` records one `Now` when a timeout is set) and a **graceful-rollout** note (old in-flight executions degrade to history-count-only for their pre-upgrade portion and pick the feature up once they run live past their frontier — no "upgrade the fleet first" sequencing). Example `autumn-harvest/examples/long_lived_entity_deadline.rs` (a subscription entity with `#[workflow(execution_timeout = "24h")]` + embedded `WorkflowTestEnv`/`WorkflowReplayer` tests), now run in CI via a dedicated `--example long_lived_entity_deadline` step (its 4 embedded tests previously never ran).

**Post-review hardening (P2 — effective `deadline_at`, not a stale start+timeout recompute).** The initial cut derived `ctx.deadline()` purely from `start_time + execution_timeout`, but for a run that has been **paused/resumed (#383) or redriven** the row's hard deadline is no longer that value: `resume_workflow_execution` explicitly pushes `deadline_at` forward by the pause span, and redrive re-anchors it to `now + timeout`. Recomputing from the original start time therefore made the deadline branch of `should_continue_as_new()` see a **stale/past** deadline after a long pause — so a healthy run could continue-as-new immediately even though the timeout scanner honours the shifted `deadline_at`. Fixed by threading the **authoritative absolute `deadline_at: Option<DateTime<Utc>>`** from the execution row into `WorkflowContext` (new field + `with_deadline(...)` builder, mirroring `with_execution_timeout`; new `deadline_at` field on `WorkflowExecuteSpanMeta`, populated by the worker from `prepared.execution.deadline_at` and threaded into both real `run_workflow_*` construction sites). *(The next paragraph refines what `deadline()` itself returns: this round briefly made the **public** `deadline()` return the shifted value; the split below reverts that so the public accessor stays replay-stable nominal while only the internal budget check reads the shifted value.)* **No new `WorkflowEvent` variant, no migration, no `event.rs` change.**

**Post-review hardening, round 2 (P2 split — replay-stable public deadline + live internal continue-as-new budget).** Codex flagged that round 1 overcorrected: reading the LIVE mutable `deadline_at` from the **public** `ctx.deadline()`/`time_until_deadline()` accessors is not replay-safe — a run that is paused/resumed or redriven has `deadline_at` mutated by `execution.rs`, so replaying earlier history after the shift would see a different `deadline()` than the value seen when those earlier commands were recorded, and workflow code that branched on `ctx.deadline()` (or embedded it in an activity/child input) could take a different branch or fail strict input checks even though the code did not change. Fixed with a deliberate **split**: (a) the PUBLIC `ctx.deadline()`/`time_until_deadline()` now return the replay-STABLE **nominal** deadline `start_time + execution_timeout` — `start_time` is fixed in `WorkflowStarted` and `execution_timeout` is a fixed row value that pause does **not** mutate (pause shifts `deadline_at`, never `execution_timeout`), so the nominal deadline is identical on every replay cycle and every worker (no new recorded event — the append-only/AC6 contract is intact); (b) the INTERNAL `should_continue_as_new()` deadline branch reads a new private `effective_deadline_live()` (the pause/resume/redrive-shifted `deadline_at`, falling back to `start_time + execution_timeout`), so the continue-as-new budget matches the deadline the timeout scanner actually enforces and a healthy long-paused run does **not** spuriously checkpoint the moment it resumes. The internal live read is replay-safe by construction: pause/redrive only move `deadline_at` **forward**, and the documented contract is that `should_continue_as_new() == true` ⇒ the workflow calls `continue_as_new` (CONTINUED_AS_NEW terminates the run, so no later replay re-evaluates the branch), while a live `false` recomputed on any later replay is evaluated against an equal-or-larger deadline (a smaller consumed fraction) and stays `false`. The recorded `SideEffectRecorded{Now}` clock read matches via the frozen side-effect regardless. **No new `WorkflowEvent` variant, no migration, no `event.rs` change.** Pinned by `context.rs` unit tests `deadline_public_accessor_is_nominal_not_shifted_deadline_at` (a +120s resume shift → public `deadline()` returns the nominal value, **not** the shifted `deadline_at`) and `should_continue_as_new_uses_live_effective_deadline_not_nominal` (nominal budget fully consumed / in the past, but the shifted `deadline_at` is far in the future ⇒ the internal check does NOT trip — the still-open original P2 "no premature CAN after a long pause"; a control run with no threaded `deadline_at` DOES trip, proving the live read is what makes the difference), both red→green-verified against 4f32bd4; and by the DB e2e `worker_surfaces_nominal_deadline_not_shifted_deadline_at` (`tests/integration/integration_e2e.rs`), which starts a run with `execution_timeout = 30m`, directly shifts the row's `deadline_at` +2h (exactly what resume's SQL does), runs a real worker, and asserts the echoed public `ctx.deadline()` equals the NOMINAL start+timeout and is far from the shifted `deadline_at` — compile-checked in this sandbox (Docker/testcontainers unavailable), run Docker-backed in CI's integration step.

**Post-review hardening, round 3 (P2 — DB replay threads per-row `execution_timeout`/`deadline_at`).** Codex flagged that `WorkflowReplayer::replay_from_db` and the replay canary (`run_canary`) loaded only the workflow name/headers and reused the replayer-wide `self.execution_timeout` (usually `None`, and never the row's shifted `deadline_at`), so replaying a row whose deadline branch had recorded a `SideEffectRecorded{Now}` would leave that `Now` unmatched → **false non-determinism**. **Blast radius**: in this codebase the "replay canary" (`run_canary`, reached only via the admin `POST /admin/workflows/replay-canary` handler) is an **advisory, read-only deploy-verify** endpoint — it returns a verdict + audit row and does NOT nd-block, redrive, or mutate real executions (the production worker path is separate and already threads `deadline_at`). So the finding here only meant a false-negative deploy verdict for a deadline-aware-CAN workflow, not a wedged live run — but per-row threading is still correct and cheap. Fixed by loading each replayed execution row's own `execution_timeout` and live `deadline_at` (via the extended `load_workflow_name_and_headers` → `DbReplayMeta` for `replay_from_db`, and the extended `query_running_executions` → `SampledExecution` for `run_canary`) and threading them into that execution's `WorkflowContext` through new private `replay_from_snapshot_effective`/`replay_canary_snapshot_effective` methods (the public `replay_from_snapshot`/`replay_canary_snapshot`/`replay_from_events` still delegate with the global `execution_timeout` and no live `deadline_at` — a documented limitation of the file/JSON path, since a raw snapshot carries neither). The executor's `run_workflow_strict`/`run_workflow_strict_advancing_clock`/`run_workflow_canary` gained a trailing `deadline_at` parameter. Pinned by the DB integration test `replay_from_db_threads_per_row_execution_timeout_for_deadline_branch` (`tests/integration/replayer_integration_tests.rs`): a row with `execution_timeout = 30m` + a shifted `deadline_at` whose history recorded the deadline branch's `Now` replays `ReplaySucceeded` via `replay_from_db`, while replaying the SAME events with no per-row timeout threaded (the pre-fix global-option path) diverges on the unmatched `Now` — **executed green against a real local Postgres 16** in this sandbox (Docker/testcontainers unavailable; the equivalent test logic run directly against a local PG instance, then discarded), and run Docker-backed in CI's integration step.

**Post-review hardening, round 4 (P2 — name the deadline-probe clock read so migration never consumes a user `Now`).** Codex flagged that the tolerant deadline read (round-1 fix above) matched *any* `SideEffectRecorded { kind: Now, name: None }` at the cursor as its own read — but that is exactly the shape `ctx.system_now()`/`ctx.sleep_until()` record. When a pre-#772 history has `should_continue_as_new()` (deadline branch, `execution_timeout` set) sitting **immediately before** a user `ctx.system_now()` call, the pre-upgrade history carries no probe `Now` but *does* carry the author's own `Now` at the cursor. The tolerant matcher stole that user `Now`, advanced the cursor, and the subsequent `ctx.system_now()` then replayed against the following event (e.g. `TimerStarted`/`ActivityScheduled`) and reported false non-determinism (`SideEffectDrift`) on the upgrade — a genuine migration-path bug, not a live-run wedge for the strict path but a false nd-block for exactly the "check-then-`system_now()`" shape. Fixed by making the probe's clock read **self-identifying** via a reserved side-effect name: the deadline branch now records/matches its `Now` as `SideEffectRecorded { kind: Now, name: Some(DEADLINE_PROBE_SIDE_EFFECT_NAME) }` (`"__harvest_deadline_probe"`, a new `pub const` re-exported from `lib.rs`, following the `__harvest_*` / `__signal_timeout:` reserved-name convention). `HistoryMatcher::match_side_effect_now_tolerant` now resolves to `Matched` **only** for the probe's sentinel-named `Now`; a bare user `{Now, name: None}`, a differently-named `Now`, or any non-`Now` event all resolve to `NotRecorded` with the cursor **untouched**, so a pre-#772 history's user `Now` is left for the workflow's own strict `system_now()` read to consume. The two paths compose cleanly because the existing side-effect matcher is already `(kind, name)`-keyed: the strict `system_now()` matcher matches `{Now, name: None}` and never the probe's sentinel-named `Now`, and vice versa. This **strictly improves** the round-1 tolerant read — a pre-#772 history (no probe event at all) still degrades the deadline branch to history-count-only for its recorded portion, and now additionally never steals a user `Now`. Because the feature is unmerged, no production #772 histories exist, so changing the probe's recorded `name` from `None` to the sentinel is safe; the test fixtures on this branch that hard-coded a name-`None` probe `Now` were updated. **No new `WorkflowEvent` variant, no migration, no `event.rs`/`SideEffectKind` change** (the `name` field of the existing `SideEffectRecorded` variant carries the sentinel; the enum shape is untouched). **Post-review hardening, round 7 (three P2s — thread the execution deadline into the LAST remaining paths: JSON/export replay, update handlers, and the test-env virtual clock).** A final review pass found three more sites where the deadline budget (`execution_timeout`/`deadline_at`) was not threaded, each leaving the reserved `SideEffectRecorded{Now, name: "__harvest_deadline_probe"}` probe unconsumed (a false non-determinism) or the deadline branch silently disabled. All three fixed. **No new `WorkflowEvent` variant, no migration, no `event.rs`/`SideEffectKind` change** — the fixes reuse the existing `with_execution_timeout`/`with_deadline` builders, the existing `SideEffectRecorded{Now}` sentinel, and the existing advancing virtual clock.

- **(1) Carry deadline metadata in JSON replays / history exports (`testing.rs` + `history_export.rs` + plugin `api.rs`).** The advertised replay-compatible JSON / `harvest-replay` path (`WorkflowReplayer::replay_from_json` → `replay_from_snapshot`) supplied only the replayer's process-wide `with_execution_timeout` (normally `None`) and no `deadline_at`, and neither `testing::HistorySnapshot` nor the full-history-export envelope (`history_export::HistoryExportDocument`) carried those row values — so an exported deadline-aware history replayed with the deadline branch disabled, leaving the recorded probe unconsumed and false-reporting non-determinism. Fixed by adding two **additive** fields — `execution_timeout: Option<chrono::Duration>` (serialised as top-level integer milliseconds via a new shared `history_export::opt_duration_millis` serde adapter, since `chrono::Duration` has no serde impl) and `deadline_at: Option<DateTime<Utc>>` — to **both** `HistorySnapshot` and `HistoryExportDocument` (both `#[serde(default, skip_serializing_if = "Option::is_none")]`, backward-compatible: a legacy JSON without the fields deserialises to `None`). Because the export envelope serialises them at the same top-level names, an exported history round-trips into a `HistorySnapshot` verbatim. `replay_from_snapshot`/`replay_canary_snapshot` now **prefer the per-snapshot values** (`snapshot.execution_timeout.or(self.execution_timeout)`, `snapshot.deadline_at`), falling back to the replayer's global option for a legacy snapshot — so `replay_from_json` and the CLI `--workflow` override path both thread the deadline automatically. The metadata is populated on capture from the execution row: `HistoryExportRequest` gains the two fields, and the single-execution export handler (`export_history_for_execution` in plugin `api.rs`) fills them from `execution.execution_timeout`/`execution.deadline_at`. It is **non-payload operational metadata — never redacted** (carried verbatim under both `Full` and `Redacted` policy). The batch export candidate query does not select these columns, so batch exports carry `None` (documented; the JSON path falls back to the replayer's global timeout for them), and the retention archival snapshot (a terminal run being deleted) carries `None` (irrelevant for a finished execution). Tests, TDD red→green (red confirmed as a `NonDeterminismDetected` false report against the pre-fix `replay_from_snapshot`): `json_replay_threads_snapshot_execution_timeout_for_deadline_history` (the money test — a deadline-crossed history whose `execution_timeout` lives ONLY on the JSON snapshot, no replayer global, replays `ReplaySucceeded` via `replay_from_json`) and `json_replay_legacy_snapshot_without_fields_falls_back_to_global_timeout` (backward compat — a legacy snapshot with the fields omitted deserialises and replays via the global fallback) in `tests/integration/replayer_tests.rs`; `full_export_carries_deadline_metadata_round_tripping_into_a_snapshot` (`history_export.rs`, no-DB — a full export serialises `execution_timeout` as top-level `1800000` millis and deserialises back into a `HistorySnapshot` carrying both fields verbatim); the existing `history_export_integration` DB suite (plugin) stays green (the change is additive), executed green Docker-backed against local PG16 in this sandbox.
- **(2) Propagate deadlines into declarative update-handler contexts (`context.rs`).** `register_declarative_update_handler` builds each handler's context via `new_for_handler`, which initialised `execution_timeout`/`deadline_at` to `None` and never copied them from the parent — so `ctx.deadline()`/`time_until_deadline()` inside a declarative `#[update]` handler always returned `None` for a running workflow that has an `execution_timeout` (the workflow body and query handlers already saw them; update handlers were the missed path). Fixed by inheriting the parent's `execution_timeout`/`deadline_at` in both the registration path and the `invoke_update` declarative-fallback path (mirroring how `workflow_id`/`workflow_name`/`context_headers` are already threaded). Tests, TDD red→green: `update_handler_inherits_parent_deadline` (a handler on a workflow with `execution_timeout` observes `ctx.deadline() == Some(..)`) and `update_handler_inherits_parent_shifted_deadline_at` (`context.rs` unit tests).
- **(3) Use the advancing virtual clock for deadline probes under the test harness (`context.rs`).** In a live `WorkflowTestEnv::with_execution_timeout` run that advances time via durable timers (`run_workflow_with_state_advancing_clock`), the deadline probe's frontier read used the host `Utc::now()` instead of the context's advancing/virtual clock — so a workflow that sleeps past its deadline fraction via durable timers then calls `should_continue_as_new()` saw ~zero consumed budget in tests and never tripped the deadline branch, leaving the test-env timeout support unable to validate the long-lived low-event workflows the feature targets. Fixed by a new private `deadline_frontier_now_millis()` helper: in the test harness (advancing clock enabled) it reads the ADVANCING clock (`start_time + elapsed`, mirroring `ctx.now()`); the virtual-clock arm is `#[cfg(any(test, feature = "testing"))]`, so **production builds are byte-for-byte unchanged** (`Utc::now()`) — the `system_now()` #384 host-wall-clock contract is untouched, this internal probe is the only reader that consults the virtual clock. Tests, TDD red→green (red confirmed as the branch NOT tripping when it should): `deadline_probe_reads_advancing_clock_and_trips_in_test_env` (advancing 90s of a 100s budget past the 0.8 fraction trips `should_continue_as_new()` in the test env) and the control `deadline_probe_does_not_trip_below_fraction_in_test_env` (10s of 100s does not trip — stable across the fix, guards against an always-true regression) in `tests/integration/workflow_test_env_tests.rs`.
