## Phase 3.51 — Deadline-aware continue-as-new for long-lived, low-event workflows (issue #772)

A long-lived entity workflow (a subscription, a cart, a device) can run for weeks while recording only a handful of events, so it never approaches the history event-count threshold `ctx.should_continue_as_new()` watches — yet if it declares an `execution_timeout` (#243) for runaway/SLA protection, that hard timeout eventually terminates it mid-flight even though it is healthy. This slice gives `should_continue_as_new()` a **second, independent trigger**: it now *also* returns `true` once the run has consumed at least a configurable fraction (default `0.8`) of its `execution_timeout` budget, so the author can `continue_as_new` **before** the hard deadline truncates the run, carrying state forward into a fresh run with a fresh deadline. Entirely additive, pure `WorkflowContext` + replay logic. **No new `WorkflowEvent` variant, no migration, no change to the adjacently-tagged event-JSON contract.**

New public `WorkflowContext` accessors, both **pure and replay-safe**: `deadline() -> Option<DateTime<Utc>>` = the recorded `WorkflowStarted` timestamp (`start_time`, no advancing clock) + the effective `execution_timeout`, `None` when there is no timeout or the sum overflows — records **no** event; and `time_until_deadline() -> Option<chrono::Duration>` = `deadline() - system_now()`, measured against the replay-safe recorded wall clock (`system_now()`, #384's `SideEffectRecorded{Now}`), **never** `chrono::Utc::now()`. `time_until_deadline` checks the pure `deadline()` first, so a workflow with **no** `execution_timeout` consults (and records) **zero** side-effects (AC4). The private `deadline_fraction_reached()` returns `false` (recording nothing) when there is no timeout, a non-positive budget, or an overflowing deadline, else trips when `remaining <= (1 - fraction) * total` (a deadline already in the past trips). `should_continue_as_new()` combines the two triggers as `by_events || by_deadline` with **both bound before the `||`** — the deadline branch is evaluated unconditionally so a timeout-bearing workflow's recorded side-effect stream is a pure function of "has a deadline" (constant across the run's life) rather than the task-varying event count.

**Cross-version replay safety (the tolerant clock read).** `should_continue_as_new()`'s deadline branch does **not** call the strict public `time_until_deadline()`/`system_now()`; it uses an internal **tolerant** clock read, `deadline_clock_read()`, backed by the new three-state `HistoryMatcher::match_side_effect_now_tolerant() -> SideEffectNowMatch` (`Matched{millis}` / `NotRecorded` / `Frontier`, re-exported from `lib.rs`). This closes a cross-version replay hazard two reviewers converged on: an execution recorded under a **pre-#772 binary** carries no `SideEffectRecorded{Now}` at the `should_continue_as_new()` call site, so when it resumes under the new binary the strict `system_now()` would hit whatever real event is recorded at the cursor (a `TimerStarted`/`ActivityScheduled`/`ChildWorkflowStarted` — the canonical `should_continue_as_new()`-then-`ctx.timer()` shape, the shipped example's shape) and record a `SideEffectDrift` non-determinism error → #603 nd-block, wedging a healthy long-lived workflow on a routine upgrade. The tolerant read instead: at the **live frontier** records a fresh `Now` and pushes the `RecordSideEffect` command exactly as `system_now()` does; on a **matching recorded `Now`** consumes it (identical to strict); on **any other recorded event** returns `None` **without consuming the cursor and without diverging**, so `deadline_fraction_reached()` degrades to history-count-only for that run's pre-upgrade recorded portion. It is replay-safe by construction (for a new execution, identical to strict; for an old one, a pure/stable function of the event at the cursor — a non-`Now` event always → `None`), and once the run executes live past its pre-upgrade frontier it records `Now`s normally and picks the deadline feature up. The only "masking" is fail-safe: a genuine control-flow reordering that lands a deadline clock-read on a recorded non-`Now` event degrades to a missed checkpoint *suggestion* rather than nd-blocking — it can never emit a wrong command, and any real divergence still nd-errors at the next real command. The public `system_now()`/`time_until_deadline()` stay **strict** (any direct call is new author code subject to normal versioning rules).

`WorkflowHistoryPolicy` gains `continue_as_new_deadline_fraction: f64` (default `DEFAULT_CONTINUE_AS_NEW_DEADLINE_FRACTION = 0.8`, re-exported from `lib.rs`) with a `continue_as_new_deadline_fraction()` accessor and a `with_continue_as_new_deadline_fraction(f64)` setter that **clamps to `[0.0, 1.0]`**. Because `f64` is not `Eq`, the struct's derive dropped from `PartialEq, Eq` to just `PartialEq` (a repo-wide grep confirmed no `Eq`/`HashMap`-key/whole-struct-`assert_eq!` usage — only accessor-level asserts). Builder: `HarvestBuilder::history_continue_as_new_deadline_fraction(f64)`.

**Threading**: the effective `execution_timeout: Option<chrono::Duration>` (the same value the execution row carries, so `deadline = start_time + execution_timeout` derives purely from the recorded start) is a new field on `WorkflowContext`, set via the new `with_execution_timeout` builder. It is threaded from `WorkflowExecuteSpanMeta` (new `execution_timeout` field, populated by the worker from `prepared.execution.execution_timeout`) into `run_workflow_with_state_history_policy_and_caps` (worker path) and `run_workflow_with_state_advancing_clock` (test-env path), and as a new trailing parameter on `run_workflow_strict` / `run_workflow_strict_advancing_clock` / `run_workflow_canary` (replayer path, which has no span_meta). `WorkflowReplayer::with_execution_timeout(chrono::Duration)` and `WorkflowTestEnv::with_execution_timeout(chrono::Duration)` expose it to the harnesses.

**Determinism contract**: a history that crossed the deadline replays to the same `ContinueAsNew` command on every worker, because the deadline is derived from the recorded start time and the clock read reuses the existing `SideEffectRecorded{Now}` event — the frozen-once, replayed-verbatim capture from #384. Proven by the falsifiable `deadline_triggered_can_replays_deterministically_1000x` replayer fixture, which pins the **decision** across 1000 **distinct** fixtures — varied frozen `system_now()` capture and budget, **mixing trip (≥0.85 of budget consumed) and not-yet (≤0.40 consumed) cases**, both well clear of the 0.8 boundary — via a branch probe that schedules `checkpoint_now` when it trips and `keep_working` otherwise: because the recorded activity fixes the expected decision, a **broken fraction comparison schedules the other activity and diverges**, so this bar actually falsifies a wrong decision rather than passing regardless (the earlier completing probe completed identically no matter the decision — a tautology). `replay_deadline_crossed_history_yields_continue_as_new` separately proves the actual `ContinueAsNew` command replays via a single `continue_as_new` fixture.

Docs: "Checkpoint before the deadline kills you" note in `docs/getting-started/07-reliability-knobs.md` (next to the SLA/`execution_timeout` material), plus a **call-once-per-decision-cycle** guidance line (each `should_continue_as_new()` records one `Now` when a timeout is set) and a **graceful-rollout** note (old in-flight executions degrade to history-count-only for their pre-upgrade portion and pick the feature up once they run live past their frontier — no "upgrade the fleet first" sequencing). Example `autumn-harvest/examples/long_lived_entity_deadline.rs` (a subscription entity with `#[workflow(execution_timeout = "24h")]` + embedded `WorkflowTestEnv`/`WorkflowReplayer` tests), now run in CI via a dedicated `--example long_lived_entity_deadline` step (its 4 embedded tests previously never ran).
