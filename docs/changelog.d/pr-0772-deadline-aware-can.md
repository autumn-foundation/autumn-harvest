## Phase 3.51 — Deadline-aware continue-as-new for long-lived, low-event workflows (issue #772)

A long-lived entity workflow (a subscription, a cart, a device) can run for weeks while recording only a handful of events, so it never approaches the history event-count threshold `ctx.should_continue_as_new()` watches — yet if it declares an `execution_timeout` (#243) for runaway/SLA protection, that hard timeout eventually terminates it mid-flight even though it is healthy. This slice gives `should_continue_as_new()` a **second, independent trigger**: it now *also* returns `true` once the run has consumed at least a configurable fraction (default `0.8`) of its `execution_timeout` budget, so the author can `continue_as_new` **before** the hard deadline truncates the run, carrying state forward into a fresh run with a fresh deadline. Entirely additive, pure `WorkflowContext` + replay logic. **No new `WorkflowEvent` variant, no migration, no change to the adjacently-tagged event-JSON contract.**

New public `WorkflowContext` accessors, both **pure and replay-safe**: `deadline() -> Option<DateTime<Utc>>` = the recorded `WorkflowStarted` timestamp (`start_time`, no advancing clock) + the effective `execution_timeout`, `None` when there is no timeout or the sum overflows — records **no** event; and `time_until_deadline() -> Option<chrono::Duration>` = `deadline() - system_now()`, measured against the replay-safe recorded wall clock (`system_now()`, #384's `SideEffectRecorded{Now}`), **never** `chrono::Utc::now()`. `time_until_deadline` checks the pure `deadline()` first, so a workflow with **no** `execution_timeout` consults (and records) **zero** side-effects (AC4). The private `deadline_fraction_reached()` returns `false` (recording nothing) when there is no timeout or a non-positive budget, else trips when `remaining <= (1 - fraction) * total` (a deadline already in the past trips). `should_continue_as_new()` combines the two triggers as `by_events || by_deadline` with **both bound before the `||`** — the deadline branch is evaluated unconditionally so a timeout-bearing workflow records exactly one `system_now` per call regardless of the event-count branch, keeping the recorded side-effect stream a pure function of "has a deadline" (constant across the run's life) rather than the task-varying event count.

`WorkflowHistoryPolicy` gains `continue_as_new_deadline_fraction: f64` (default `DEFAULT_CONTINUE_AS_NEW_DEADLINE_FRACTION = 0.8`, re-exported from `lib.rs`) with a `continue_as_new_deadline_fraction()` accessor and a `with_continue_as_new_deadline_fraction(f64)` setter that **clamps to `[0.0, 1.0]`**. Because `f64` is not `Eq`, the struct's derive dropped from `PartialEq, Eq` to just `PartialEq` (a repo-wide grep confirmed no `Eq`/`HashMap`-key/whole-struct-`assert_eq!` usage — only accessor-level asserts). Builder: `HarvestBuilder::history_continue_as_new_deadline_fraction(f64)`.

**Threading**: the effective `execution_timeout: Option<chrono::Duration>` (the same value the execution row carries, so `deadline = start_time + execution_timeout` derives purely from the recorded start) is a new field on `WorkflowContext`, set via the new `with_execution_timeout` builder. It is threaded from `WorkflowExecuteSpanMeta` (new `execution_timeout` field, populated by the worker from `prepared.execution.execution_timeout`) into `run_workflow_with_state_history_policy_and_caps` (worker path) and `run_workflow_with_state_advancing_clock` (test-env path), and as a new trailing parameter on `run_workflow_strict` / `run_workflow_strict_advancing_clock` / `run_workflow_canary` (replayer path, which has no span_meta). `WorkflowReplayer::with_execution_timeout(chrono::Duration)` and `WorkflowTestEnv::with_execution_timeout(chrono::Duration)` expose it to the harnesses.

**Determinism contract**: a history that crossed the deadline replays to the same `ContinueAsNew` command on every worker, because the deadline is derived from the recorded start time and the clock read reuses the existing `SideEffectRecorded{Now}` event — the frozen-once, replayed-verbatim capture from #384. Proven by the falsifiable `deadline_triggered_can_replays_deterministically_1000x` replayer fixture (1000 **distinct** crossed-deadline fixtures — varied frozen `system_now()` capture, consumed fraction, and budget — each `ReplaySucceeded` with zero divergences; uses a fast completing probe so 1000 replays stay ~sub-second) plus `replay_deadline_crossed_history_yields_continue_as_new` (proves the actual `ContinueAsNew` command replays via a single `continue_as_new` fixture).

Docs: "Checkpoint before the deadline kills you" note in `docs/getting-started/07-reliability-knobs.md` (next to the SLA/`execution_timeout` material). Example `autumn-harvest/examples/long_lived_entity_deadline.rs` (a subscription entity with `#[workflow(execution_timeout = "24h")]` + embedded `WorkflowTestEnv`/`WorkflowReplayer` tests covering opt-in-safety, the far-deadline non-trip, and the deadline-triggered replay). Tests, TDD red→green (red confirmed as compile errors against the not-yet-existing API): 8 `context.rs` unit tests (`deadline` with/without timeout, `time_until_deadline` uses recorded clock / none-without-deadline + zero-side-effect, deadline-fraction trips / not-yet, no-timeout-records-nothing-and-is-false, event-count trigger preserved) + the policy default/clamp test; a `builder.rs` fraction-override test; the two replayer fixtures above; and the 4 example tests. Entirely no-DB — runs in the existing `--no-default-features --features testing --test integration` CI step and the `--example` CI step.
