## Fix — query-replay suspension classification: spinning terminal query is 408, cold-park query serves fast (issue #612)

`executor::drive_query_replay` (the read-only replay driver behind post-mortem queries on terminal workflows, issue #612) misclassified `Poll::Pending` cycles because it inferred workflow suspension from a custom `QueryReplayWaker` flag — assuming `tokio::task::yield_now()` calls the waker synchronously — but inside a tokio runtime (the real HTTP query path) `yield_now` **defers** its wake to the scheduler queue rather than invoking the custom waker synchronously. The sync driver's tight manual poll loop never yields back to the scheduler, so the deferred wake was never delivered and a genuinely-spinning terminal query was misread as a command-suspension → `classify_terminal_query(Suspended, sealed=false)` → **410** instead of the #612-documented **408**.

**Fix (executor-scoped redesign):** discriminate a `Poll::Pending` by a **per-poll delta** on the emitted replay-significant command count, then a **three-way** suspension discriminator:

- **Case 1 — command this poll** (positive delta): a genuine workflow suspension on a durable command (`WaitForActivity`/`StartTimer`/`WaitForSignal`/`StartChildWorkflow`/`ContinueAsNew`/…) → `Suspended`.
- **Case 2 — self-wake spin** (zero delta, `QueryReplayWaker` flag set): a `tokio::task::yield_now()` spin → keep driving to the deadline → `TimedOut` → 408.
- **Case 3 — command-less cold park** (zero delta, flag cold): the workflow parked waiting on an external re-poll that never comes during a query drive (the sole engine primitive that does this is non-timeout `ctx.await_condition`, which pushes no command and leaves its waker cold) → `Suspended` **immediately**, so a RUNNING query over such a park serves its partial state fast rather than burning the whole `query_timeout` budget, and a terminal run sealed while parked on it serves 200 (not 408/410).

The command signal is now a **delta** (`WorkflowContext::count_commands`), not a bare "any pending" peek: the command buffer is never drained during a query drive, so an "any pending" check stays true forever after the first command and would misclassify a *later* cold `await_condition` park as still making progress and busy-drive it to 408 — the delta reflects only what THIS poll emitted. Command classification reuses the executor's shared `is_replay_significant_command` deny-list (`UpsertSearchAttributes`/`SetCurrentDetails`/`CancelRaceLosers`), also used by the `run_strict_with_ctx`/`run_workflow_canary` non-determinism checks, so command kinds are never re-enumerated by hand.

**Sync + async twin driver.** The 16 pure `#[test]` callers run out of a tokio runtime (where `yield_now` fires synchronously) and keep the synchronous `drive_query_replay`; the single production caller (`hydrate_ctx_for_query`, already async) now uses `drive_query_replay_async`, which opens a **single `tokio::task::yield_now().await` quiet window** on a zero-delta poll to observe tokio's *deferred* `yield_now` wake before deciding case 2 vs case 3 — replacing the old busy-wait `std::thread::yield_now()`, so a spinning query cooperatively yields the runtime each cycle instead of hard-pinning a core. Both loop over one shared, `!Send`-safe `poll_query_step` helper that **builds and drops the `waker_ref`/`std::task::Context` internally**, so nothing `!Send` crosses the async driver's `.await` (the returned future stays `Send`, as the axum handler requires).

**Behavior change:** a spinning query on a terminal workflow returns **408** (retryable request timeout) instead of a misleading **410**; a RUNNING or sealed-while-parked query over `await_condition` now serves fast/200 instead of burning the full budget. The #612 contracts are preserved: sealed-while-parked runs still `Suspended` → **200**, truncated history (no terminal seal) still → **410**, code-drift still → **410**, unregistered name still → **404**. **No new `WorkflowEvent` variant, no migration, no route change** — production files only (`executor.rs`, `context.rs`, plugin `api.rs` call site). Pure `query_terminal` suite green (19/19, incl. the new RED→GREEN `await_condition` fast-suspend and sealed-while-parked tests, both proven to busy-drive to timeout under the old `any_pending_command` guard); `query_integration::ac6_spinning_replay_returns_408` still 408. Both suites run in CI.
