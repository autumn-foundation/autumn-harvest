## Fix — query-replay spin/timeout classification: a spinning terminal query is 408, not 410 (issue #612)

`executor::drive_query_replay` (the read-only replay driver behind post-mortem queries on terminal workflows, issue #612) misclassified a genuinely-spinning terminal-workflow query as HTTP **410** ("history unavailable") instead of the #612-documented **408** (`REQUEST_TIMEOUT`). Root cause: the driver inferred workflow suspension from a custom `QueryReplayWaker` flag — assuming `tokio::task::yield_now()` calls the waker synchronously — but inside a tokio runtime (the real HTTP query path) `yield_now` **defers** its wake to the scheduler queue rather than invoking the custom waker synchronously. The sync driver's tight manual poll loop never yields back to the scheduler, so the deferred wake is never delivered, the flag stays false, and the first `Poll::Pending` of a genuine spin (`loop { yield_now().await }`) is misread as a command-suspension → `classify_terminal_query(Suspended, sealed=false)` → 410. The bug only manifests **in-runtime**; in a pure no-runtime unit test `context::defer` falls back to a synchronous wake, masking it.

**Fix (executor-scoped):** discriminate suspension by **emitted `WorkflowCommand`s**, not waker timing. On `Poll::Pending`, a new non-consuming peek (`WorkflowContext::any_pending_command`) checks whether the coroutine parked after pushing ≥1 replay-significant command — a genuine suspension emits `WaitForActivity`/`StartTimer`/`WaitForSignal`/`StartChildWorkflow`/`ContinueAsNew`/…, a pure `yield_now` spin emits none. Command classification reuses the executor's own pure-metadata deny-list (`UpsertSearchAttributes`/`SetCurrentDetails`/`CancelRaceLosers`), now extracted into a single shared `is_replay_significant_command` helper used by both the existing `run_strict_with_ctx`/`run_workflow_canary` "new commands beyond history" non-determinism checks and the query driver, so command kinds are never re-enumerated by hand. Zero commands → keep driving to the deadline → `TimedOut` → 408 (re-polling makes progress since `yield_now`'s `Pending` is a one-shot; the loop yields the OS thread slice each spin and re-checks the deadline so it never polls past `query_timeout`). `QueryReplayWaker` is retained only as a synchronous out-of-runtime fast-path, never the authoritative signal. `drive_query_replay` stays a synchronous `fn` (the pure `query_terminal_tests` call it without a runtime).

**Behavior change:** a spinning query on a terminal workflow now returns **408** (retryable request timeout) instead of a misleading **410** (permanent "history unavailable"). The #612 contracts are preserved: sealed-while-parked runs (continue-as-new / timed-out-mid-activity / cancelled-mid-await) still emit a suspension command → `Suspended` → **200**, and a genuinely truncated history (pruned/released, no terminal seal) still → **410**. **No new `WorkflowEvent` variant, no migration, no route change** — production files only (`executor.rs`, `context.rs`). Verified in-runtime RED→GREEN on Postgres 16 (`query_integration::ac6_spinning_replay_returns_408`: 410 → 408) with the full no-DB `query_terminal` suite green (16/16 — sealed-while-parked→200, truncated→410, spin→408, code-drift→410, unregistered→404); both suites already run in CI.
