## Phase 3.50 — Inline-resolved mixed timer + external op wakes immediately (issue #678)

Fixes a latency bug where a `select!{ timer(3600s), signal_external_workflow(target) }` (or `request_cancel_external_workflow(target)`) whose external target lives on the **same shard** could park its timer for up to the full timer duration (an hour) instead of resolving on the external branch that already completed.

**Root cause.** For a mixed `[StartTimer, SignalExternalWorkflow/RequestCancelExternalWorkflow]` suspension batch, the drive-loop mixed arm strips the external commands (`split_mixed_signal_batch`) then delivers them inline (`persist_external_signal_inline`) — which for a same-shard target appends `ExternalSignalDelivered`/`ExternalCancelDelivered` to history **in this decision cycle** and returns them in `new_events`. The remaining `StartTimer` then reaches `persist_started_timer`, whose `is_mixed` detection uses a SQL probe for **unresolved** `External*Requested` events. Because the request was resolved inline, that probe finds nothing, the parked row is **not** tagged `mixed_signal_suspension`, and neither `wake_workflow_task`'s primary re-pend (which requires that tag) nor the existing post-park recheck (which only inspects incoming pending **signals**) ever self-wakes the task. It sleeps until `fires_at`.

**Fix (Option 1 — thread the resolution ids, self-wake).** New pure helper `resolved_external_ids(items: &[SignalBatchItem], new_events: &[WorkflowEvent]) -> ResolvedExternalIds` correlates each `Signal`/`Cancel` batch item against the `External{Signal,Cancel}{Delivered,Failed}` terminals appended **this cycle** (`Failed` counts as resolved; markers ignored; an unresolved item — cross-shard / `NotFound` → outbox route — contributes nothing). The mixed arm computes it right after `persist_external_signal_inline` returns and threads the result — via a new `ResolvedExternalIds` field on `SuspendedWorkflowContext` and a new by-value parameter on `persist_workflow_outcome` — down to `persist_started_timer`. There, `if !resolved_inline.is_empty() { is_mixed = true; }` marks the parked row `mixed_signal_suspension` (wakeable), and a new post-commit self-wake block — mirroring `persist_signal_wait_park`'s step-3 external self-wake — loads history, confirms one of the resolved ids has a terminal, and calls `queue::wake_workflow_task`, so the worker re-claims the task immediately and re-runs the workflow, which now observes the external terminal in history and takes the signal/cancel branch → `COMPLETED`.

**Correctness guard.** The self-wake fires **only** from `resolved_inline` — ids resolved in **this** decision cycle, threaded from the arm — never from a blanket history scan. A pure `ctx.timer()` sleep threads `ResolvedExternalIds::default()` (empty) and can never false-wake, even in a workflow that performed an earlier, fully-observed external op. Every suspension path other than the mixed timer + external arm passes the empty default, so their behaviour is byte-for-byte unchanged. No new events are appended by the fix, so the suspension shape / `suspended_command_event_count` is unaffected.

**No new `WorkflowEvent` variant, no migration, no replay-determinism change** — the fix is entirely in the worker's suspension/self-wake bookkeeping.

**Tests.** No-DB unit tests for `resolved_external_ids` in `worker.rs` (matches delivered signal / delivered cancel / ignores unresolved item / counts `Failed` terminals / ignores markers / empty batch — `db`-feature gated, since `worker.rs` is `db`-only). Two DB integration tests in `tests/integration/cross_workflow_signal_tests.rs` (`test_mixed_timer_suspension_signal_resolves_inline_wakes_immediately`, `test_mixed_timer_suspension_cancel_resolves_inline_wakes_immediately`): the target is started **first** and confirmed `RUNNING` so the caller's external op resolves inline, and a tight 30 s bound proves the caller wakes immediately on the inline terminal rather than sleeping out the 3600 s timer. The existing `test_mixed_timer_suspension_signal_wakes_timer` control (caller started first → `NotFound` → outbox path) is unchanged and still passes, confirming no regression to the unresolved/outbox route.
