## Tooling — Publish the admission gate to the process-global cache in the keyed-replay gate test (fix trunk-red, issue #618 / #808)

**Test-only fix — no production code changed.** After PR #1051 (issue #618/#607) merged, trunk-dev went RED on exactly one test: `autumn-harvest-plugin/tests/start_idempotency_integration.rs::keyed_replay_bypasses_a_raised_admission_gate` returned `201` where it asserted `503` at step 1 (a genuinely-fresh keyed start under a raised admission gate must be gated).

Root cause: issue #618 (landed via #1014/#1051) made admission-gate enforcement **authoritative inside the CORE start primitive** — `execution::evaluate_start_gate` reads the **process-global** cache (`admission_gate::global_admission_gate_cache()`), not any api_state-local `Arc<AdmissionGateCache>`. The failing test predates that relocation (it was introduced in #992 for issue #808) and only ever armed the gate in the **api_state-local** cache via `api_state.initialize_gate_cache(...)`, never publishing it to the global static. So the inline test app's global cache was empty → the plain/keyed fresh-start path (which routes through the core `GateMode::Check`) saw no gate → `201`. The core `admission_gate_authoritative_tests` (26/26 green) and the plugin `admission_gate_authoritative_localpg` suite already do the right thing: publish the live handle with `set_global_admission_gate_cache(Some(api_state.gate_cache()))` on raise and tear it down with `set_global_admission_gate_cache(None)`.

Fix: the test's `raise_gate`/`lift_gate` helpers now also publish the (interior-mutable) `api_state.gate_cache()` handle to the process-global static, and the test tears the global down to `None` at the end so sibling serial tests in the same binary (this suite runs `--test-threads=1`) are unaffected. This flips the assertion `201 → 503` and confirms the gap was purely test-harness: **production is unaffected** — the plugin publishes local→global at boot (`set_global_admission_gate_cache`), so the fresh keyed-start gate check works end-to-end in a real deployment; only the inline test app skipped the publish.

**Sweep for the same class:** the whole test tree was grepped for tests that mutate the api_state-local gate cache without publishing to the global. The three `start_throttle_integration.rs` gate tests (`retry_with_a_pending_throttle_row_bypasses_the_admission_gate`, `armed_gate_blocks_fresh_creating_start_under_reuse_policy_on_empty_bucket`, `batch_retry_with_a_pending_throttle_row_bypasses_the_admission_gate`) arm only the local cache and assert `503` — but they exercise a **different, intentional plugin-local enforcement path**: the throttle/batch branches do their own `api_state.gate_cache().check(...)` *before* `reserve_or_defer` returns a `202` DEFER (issue #607 round 7 — "halt beats pace"; a DEFER returns before the core `GateMode::Check` ever runs). Their `503` provably comes from that plugin-local check (an ungated empty-bucket throttled start would be `202`, not `503`), so they read the correct cache **by design** and were deliberately left unchanged. The two authoritative suites already publish to the global. Only `keyed_replay_bypasses_a_raised_admission_gate` exercised the core global-cache path with a local-only gate.

Validation (Docker-backed PG16): `start_idempotency_integration` 21/21, `start_throttle_integration` 19/19, and core `admission_gate_authoritative` 26/26 all green under `--test-threads=1` (no cross-test contamination from the shared global static). No new `WorkflowEvent` variant, no migration, no production code change.
