## Phase 4 — Scoped API tokens + rotation for the management API (issue #942)

Adds a first-class, least-privilege credential layer for the Harvest management API: create / list / revoke scoped, optionally-expiring, individually-revocable API tokens, with every mutating operation attributable to a named actor. Entirely a `autumn-harvest-plugin` auth layer plus **one additive config-table migration** — **no new `WorkflowEvent` variant, zero replay-determinism impact, no change to `harvest_events`** (AC9). The deterministic execution core is untouched.

### What shipped

- **Token table (`harvest_api_tokens`, migration `20260713000000`)** — a small, Postgres-only, shard-agnostic control table (`id`, `name`, `token_hash`, `scope`, `created_at`, `expires_at?`, `last_used_at?`, `revoked_at?`, `created_by`), mirrored into core `schema.rs`/`models.rs` exactly like `harvest_audit_log`. Verified on the **default (control) shard**; rows carry no `shard_id`.
- **Wire format & secret hygiene (AC2)** — a token secret is opaque `hvst_<base64url(32 random bytes)>`. Only `token_hash = hex(SHA256(secret))` is stored (UNIQUE-indexed); the plaintext is returned **exactly once** at creation and never persists. Verification hashes the presented secret and does one indexed `SELECT` — **no in-Rust hash comparison** (a 256-bit random hash is not an iterable timing oracle), so no constant-time-compare crate is added. `GET /admin/tokens` returns a **metadata-only** `TokenView` DTO that structurally cannot hold the hash/secret (the #695 redaction-view pattern, exhaustive-destructure guard); `MintResult`/`NewApiToken` redact the secret/hash in `Debug`. Uses `sha2`/`base64`/`rand` — all already workspace/core deps.
- **Scope from route classification (AC3/AC4)** — a token carries `read` or `mutate`, derived from the existing `audit::CLASSIFIED_ROUTES` (the #776 single source of truth — **no second route taxonomy**). The scope gate is `deny_readonly_mutation` over `classify_route`, which **fails closed**: an unclassified path resolves to `Mutating` and is denied to a `read` token. A `read` token gets **403 on 100% of `ALL_MUTATION_ROUTES`** and reaches 100% of read-only routes (the 100%/0% success-metric sweep).
- **Enforcement layer (`api_token::enforce_token_scope`)** — a `from_fn_with_state` layer installed on the nested `harvest_api_router` **only** under the new `HarvestPlugin::enable_api_tokens()` opt-in (default off → byte-identical, AC7). A bearer that does not start with `hvst_` (or an absent bearer) is passed through untouched — token auth **composes with**, never replaces, `api_with_auth` (AC7). A claimed `hvst_` bearer that cannot be verified (store unavailable) is rejected 503, never trusted unverified.
- **Rotation & expiry (AC5)** — optional `expires_at`; an expired or revoked token is rejected 401 on the **next request** because there is **no grant cache** (every request re-queries the table; bounded TTL = 0). Rotation is create-replacement → cut over → revoke old, over the existing routes.
- **Actor attribution (AC6)** — on a verified token the layer strips any inbound `x-harvest-actor` and injects `token:{id}`, so every audited mutation is attributed to the token (never the secret/hash) and a caller cannot spoof a different actor. Legacy embedder-authed requests keep the documented `x-harvest-actor`/`anonymous` fallback. A verified `TokenPrincipal` extension lets `require_harvest_admin` admit a token-authenticated request in standalone-token mode.
- **Routes (AC1)** — `POST /admin/tokens` (create, 201, audited `token.create`), `GET /admin/tokens` (list, metadata-only, read/no-audit), `DELETE /admin/tokens/{id}` (revoke, audited `token.revoke`), all admin-gated and registered across every registry: `harvest_api_router`, `management_api_routes()`/`_request_fields()`/`_response_fields()`, `docs/api-contract.json`, and core `audit` (`CLASSIFIED_ROUTES`, `ALL_MUTATION_ROUTES`, `AUDITED_OPERATIONS`, `OP_TOKEN_CREATE`/`OP_TOKEN_REVOKE`/`TARGET_TOKEN`, `EXCLUDED_ROUTES` for the GET), with a dedicated `token_routes_are_classified_and_audited` pin.
- **MCP composition** — a token-aware `enforce_token_scope_mcp_mutation` layer (mirroring `enforce_read_only_mcp_mutation`) is provided in `api_token` to hard-deny a `read`-scoped token the mutating generated MCP tool routes. `enable_api_tokens()` installs the management-router `enforce_token_scope` layer; wiring the MCP-tool gate onto the app-level generated tool routes is a follow-up composition (the generated MCP routes live outside the nested management router).
- **CLI (AC8)** — `harvest token create|list|revoke` (plus a `rotate` client-side convenience that mints a replacement via the create route). The `--token` bearer was already sent; the new layer consumes it.

### Tests

Pure unit tests (`api_token.rs`): hash determinism/hex, secret mint prefix/entropy, `MintResult`/`TokenView` redaction, the scope-from-class decision (deny-mutating / allow-readonly / fail-closed), `hvst_` discrimination, expiry predicate. Audit pin (`audit.rs`). No-DB HTTP layer tests (`security.rs`): pass-through of absent/non-`hvst_`/OPTIONS, 503-on-claimed-token-without-store, default-router-unchanged. DB integration (`token_auth_integration.rs`): create-returns-secret-once/stores-only-hash, list-metadata-only, verify-authenticates, unknown-401, revoke-denies-next-request, expired-401, the read-token 403/read sweep, mutate-token standalone admin access, `token:{id}` actor attribution (spoof-proof), create/revoke audited. CLI mapping + contract-coverage tests.
