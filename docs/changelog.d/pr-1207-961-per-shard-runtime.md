- **Phase 4** (implemented): Per-shard worker poll loops and scheduler ticks, finished and made falsifiable — see issue #961. Reconciliation slice in the #543/#593/#609/#753 precedent: most of the multi-shard runtime shipped piecemeal under #522 (per-shard poll loops, per-shard control loops, the stranded-work sampler), #796/#1157 (per-shard scheduler ticks, DAG->shard pinning, stale-row collection), #797 (per-shard scanner liveness) and #774 (queue coverage) — this closes the residuals and gives every AC a test that can fail.

  **Auto shard assignments (AC1, behaviour change).** An **empty** `WorkerConfig::shard_assignments` now means *auto*: cover every shard the process has a pool for. Previously it defaulted to a literal `[ShardId::new(0)]`, so a three-shard `ShardedDbPool` with no explicit `with_shard_assignments` call silently drained shard 0 and left the others permanently undispatched with no error anywhere. New pure `builder::resolve_shard_assignments(explicit, pool_shards)`; empty + **no pool preserves the empty list** rather than fabricating a `[ShardId::new(0)]` that asserts a shard number the process never established (Codex round 2 — the write-side twin of issue #1150, whose read-side consumers all normalise an empty array as "covers whatever shard the row was read from"; `ShardRouter` also accepts an arbitrary `default_shard`, so `0` is not a safe stand-in). Single-shard stays byte-for-byte unchanged (AC7): the poll loop's shard is `Option<ShardId>` and the per-shard `harvest.shard.dispatched{shard}` counter is emitted only when the worker has a shard identity, so a pool-less worker attributes no per-shard dispatch — its dispatch remains visible on `harvest.queue.dispatched{queue}` (#515). Resolution runs in `Worker::new` (and in the plugin runner right after the pool is assigned) — deliberately **not** in `From<WorkerConfig> for WorkerRuntimeConfig`, which runs before the runner assigns the pool and would therefore accomplish nothing; a regression test pins that ordering. `GET /admin/config` reports the **resolved** list (`worker.shard_assignments`), which is what the runbook's coverage check reads.

  **`with_shard_assignments(<empty>)` flips meaning.** It previously coerced to `[ShardId::new(0)]`; it now records the auto sentinel. Intended configuration is unaffected, but a **computed** list (`.with_shard_assignments(shards_from_env())` returning `vec![]` when the variable is unset) changes from "narrow to shard 0" to "fan out across every pool shard" (or, with no sharded pool, to the empty legacy shape every read-side consumer already normalises).

  **Third drifted copy of the shard-membership predicate closed.** `preflight::worker_can_cover` had its own inline `worker.shard_assignments.contains(&shard_id)` check with no empty-array normalization — issue #1150's third instance, after `shard_fanout` and `fleet_health`. It now delegates to `shard_fanout::worker_covers_shard`, so a worker on the auto default is no longer reported as covering nothing.

  **`ShardedInfo` lost `Copy`** (`effective_config.rs`) — it now carries a `shard_ids: Vec<i32>`.

  **Per-shard dispatch counter (AC5).** New `harvest.shard.dispatched{shard}` counter — the shard-dimension twin of #515's `harvest.queue.dispatched{queue}` — emitted from the two poll-loop sites that know which pool they claimed from (a task row carries no `shard_id` column; "which shard" *is* "which pool"). Standard three-touchpoint recipe plus dashboard panel, ADR-0001 §7 row, and `docs/telemetry.md`.

  **Starter alert entry (AC6).** New `harvest_shard_undrained` rule over the existing `harvest.shard.stranded_pending` gauge, with a full runbook section. Its narrow "no poller at all" variant uses `unless`, not `and ... == 0`: a shard that has never had a covering poller has no `harvest_shard_dispatched_total{shard}` series, so an `== 0` comparison drops the alert in exactly the case it exists to detect.

  **LISTEN/NOTIFY on the multi-shard path stays per-shard-URL only.** An earlier cut of this slice let the pool's *default* shard fall back to the global `notification_database_url`, to preserve the NOTIFY wake-up an auto-widened deployment previously had on shard 0. That was withdrawn on review (Codex P2): `notification_database_url` is configured independently of `sharded_pool`, so a numeric default-shard match does not establish that the URL targets that shard's database — and a pool override (`HarvestRunnerResources::with_sharded_pool`) can leave it aimed at the original `harvest_pool` entirely, opening a listener on the **wrong** database (real NOTIFYs missed, unrelated ones triggering needless claim attempts). It also contradicted the call the single-shard `global_safe` gate already documents for real multi-shard routing: *"an absent per-shard URL means poll-only for this shard rather than risking a wrong-database listener"* (#522 review). The resolver is now the pure `multi_shard_listener_url`, which takes **only** the per-shard map, so the hazard is unrepresentable rather than heuristically guarded. Consequence: a multi-shard worker with no `shard_notification_database_urls` falls back to poll-interval dispatch latency on **every** shard — a latency cost, never a correctness one (claiming always runs against the shard's own pool) — and a startup warning names the one-call fix.

  **Buffered-drain shard-encoding de-drift (AC4).** `drain_buffered_schedule_runs` gated on `schedule.dag_name.is_some()` while the main dispatch path used `scheduled_fire_encodes_shard`. Both now call one shared `scheduled_fire_exec_id`, guarded by a source-level anti-drift test. Not reachable today (the canary registers with `OverlapPolicy::Skip`, which never buffers) — it becomes live the moment an operator `PATCH`es that policy (#771).

  **Docs (AC8).** `docs/sharding.md` step 4 gained three falsifiable verification checks, and its fictional `[harvest.worker] shard_assignments` TOML block was replaced with the real Rust surface (`WorkerConfig::with_shard_assignments` / `HarvestRunnerResources::with_sharded_pool`) plus the note that multi-shard is `HarvestRunner`-only.

  **No new `WorkflowEvent` variant, no migration, no event-contract or replay-determinism change.** New DB suite `autumn-harvest/tests/integration/sharded_runtime_tests.rs` (real per-shard databases): auto-coverage, explicit narrowing, per-shard timeout scanner, per-shard external-signal outbox, per-shard scheduler HA over 100 contested slots per shard under two replicas, round-robin fairness against a self-replenishing backlog, stranded-shard detection (never-covered and worker-killed), DAG pinning across restart and widening, and a single-shard regression.

  **CRLF-safe source-level guard.** The AC4 anti-drift test parses `scheduler.rs` at test time to prove both fire paths mint through the shared decision; its `\n}\n` brace probe found nothing on a Windows checkout (`core.autocrlf`), so the test panicked there while passing everywhere else. It now normalizes line endings (the `sqlite_feasibility_docs.rs` convention) and — so a regression fails on *every* platform rather than only the Windows CI leg — runs the identical guard a second time over a CRLF copy of the same source.

  **`harvest.shard.dispatched` is exported by the built-in scraper too.** `HarvestPlugin::with_metrics_scrape()` installs `HarvestMetricsRecorder`, which is per-metric hand-maintained; the new counter initially fell through the trait's no-op default and so was absent from the recommended built-in Prometheus endpoint. That mattered here specifically because the `harvest_shard_undrained` alert shipped in this same PR reads `harvest_shard_stranded_pending` (already rendered by that recorder) and uses `harvest_shard_dispatched_total` to tell "no poller at all" from "poller present but backlogged" — the alert's primary signal was exported while its discriminator was not. Added as a counter family, mirroring the sibling gauge.

  **One canonical shard-membership predicate for the whole workspace.** `autumn_harvest::workers::shard_assignments_cover` now owns the "an empty assignment array covers whatever shard the row was read from" rule (issue #1150). It lives in **core**, not beside its first plugin caller, because core has consumers of its own — `apply_worker_filters` — that cannot reach into `autumn-harvest-plugin`, which is why independent copies kept drifting. `shard_fanout::worker_covers_shard` delegates to it, and two remaining literal-membership consumers were routed through it: `api.rs::evaluate_eligibility_for_shard` (which reported a healthy auto-assignment worker as `wrong_shard_assignment`) and `workers.rs::apply_worker_filters` (which omitted it from `GET /workers?shard_id=N`). A **malformed** (non-array) value still covers nothing — it is corrupt, not a legacy shape — so the eligibility check reads the raw JSON value rather than the decoded `Vec<i32>`, whose `unwrap_or_default()` would have collapsed malformed into the permissive empty shape.

  **Auto-resolution must not widen the blast radius of the existing multi-shard weaknesses (three P1s).** Auto-coverage makes the multi-shard path the *default* for any `ShardedDbPool`, which turned three latent weaknesses into default behaviour. (1) **`spawn_monitoring_tasks` fanned out quadratically.** It starts one timeout checker per assigned shard and handed every checker the *full* assignment list, but each `enforce_timeouts_once` pass iterates that list again (`fire_due_debounced_starts`, `fire_due_throttled_starts`, `fire_due_event_batches`, `fire_due_completion_deliveries`, `sweep_expired_start_idempotency`, and the three external outboxes) — so an N-shard worker performed N x N pool acquisitions and table scans every poll interval, and one unreachable shard aborted every healthy shard's remaining pass (`fire_due_event_batches` propagates its acquisition error with `?`, and completion-callback delivery plus the idempotency sweep run after it). Each monitor is now narrowed to its own shard via `monitor_shard_scope`; the union across the N monitors still covers every shard exactly once, so the pass is O(N), a shard's failure is contained to its own checker, and N checkers no longer contend on the same `FOR UPDATE SKIP LOCKED` rows. The residual — a wedged checker no longer has peers incidentally covering its shard — already applied to its own-database work and is what #797's per-shard `harvest.scanner.tick` liveness exists to detect. (2) **One unavailable pool stranded every peer shard.** Harvest configures no deadpool `Timeouts`, so every `pool.get().await` is unbounded, and the multi-shard path visits shards *sequentially* in two places: `run_multi_shard`'s startup loop (`register_in_fleet` + `register_rate_limit_buckets` per shard — a shard that never yields a connection means the poll loop is never reached **at all**) and `run_poll_loop_multi` (round-robin rotation cannot help, because the loop never reaches the rotation). Both now acquire through one `acquire_shard_conn` helper under `shard_acquire_bound`, so a bad shard costs an iteration instead of parking the loop; each site already had a graceful failure branch (the per-shard pending flag its heartbeat retries, or simply rotating on). The bound is floored at `MIN_SHARD_ACQUIRE_BOUND` (5s) rather than tracking `poll_interval` — a first cut used the poll interval directly and *starved* a shard that merely had a deep backlog, because a busy bounded pool legitimately takes far longer than one poll interval to hand over a connection. The cost is amortized, not free: an unavailable shard is re-probed once per rotation, which is degraded throughput for its peers rather than stranding; a per-shard cooldown or concurrent polling would remove even that and is a natural follow-up. (3) **The single-pool public entrypoint advertised coverage it never drained.** `run_with_listener` registers, heartbeats and polls exactly the one pool it is handed and attributes every dispatch to `shard_assignments[0]` — consistent while the default was a literal `[ShardId::new(0)]`, but auto-resolution widens an unconfigured worker to every pool shard, so a direct embedder would register a fleet row claiming N shards while draining one. That is worse than lost throughput: a worker falsely advertising coverage is exactly what suppresses this PR's own stranded-shard signals (`harvest.shard.stranded_pending`, shard health's `no_live_worker` gate), so the undrained shards would be invisible as well as idle. It now fails closed (`single_pool_entrypoint_rejects`), mirroring the fail-closed posture `run()` already takes for `missing_assigned_shard_pools`; `Worker::run` still routes a genuine multi-shard config to `run_multi_shard`, and its own internal call reaches the guard only when `use_multi_shard` is false. Single-shard is unchanged throughout (AC7): `shard_acquire_bound(false, ..)` is `None`, which is the original unbounded `pool.get().await` byte-for-byte, and a one-shard config never trips the entrypoint guard.
