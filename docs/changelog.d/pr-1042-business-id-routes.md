## Phase 3.51 — Address existing workflows by business `workflow_id` over HTTP (issue #805)

Embedders assign their own business `workflow_id` at start (e.g. `order-12345`, `subscription:user-42`), but every act-on-existing management route (`GET /workflows/{id}`, `/result`, `POST .../signal/{name}`, `/query/{name}`, `/cancel`, `/pause`, `/resume`, `/stack`, `/children`) previously accepted only the internal `exec_id` UUID (`parse_execution_id` rejects anything else). Acting on a workflow you already named required a list-then-act round-trip, and a cached `exec_id` is a **stale handle** — continue-as-new and reset fork a **new** `exec_id` under the **same** `workflow_id`, so code that pinned an `exec_id` can silently signal or read a terminal predecessor instead of the live run. This shipped a **business-id form** addressed by `(workflow_name, workflow_id)` alongside the existing `exec_id` routes, which stay **byte-for-byte backward compatible**.

**New routes** (prefix `P = /workflows/by-id/{workflow_name}/{workflow_id}`): `GET P` (describe), `GET P/result`, `GET P/stack`, `GET P/children`, `POST P/signal/{signal_name}`, `GET P/query/{query_name}`, `POST P/query/{query_name}`, `POST P/cancel`, `POST P/pause`, `POST P/resume`. Each **resolves** `(workflow_name, workflow_id) → ExecutionId` then **delegates** to the existing `exec_id` handler (no existing handler body changed), so admin posture and audit classification mirror the `exec_id` counterparts exactly: `cancel`/`pause`/`resume` carry the same `require_admin` route layer and `OP_WORKFLOW_CANCEL`/`OP_WORKFLOW_PAUSE`/`OP_WORKFLOW_RESUME` audit ops; `signal` is `OP_WORKFLOW_SIGNAL`; describe/result/stack/children/query are `ReadOnly` + `EXCLUDED_ROUTES`.

**Resolution rule (AC2):** the single **active** (non-terminal — `RUNNING`/`PAUSED`) run if one exists; otherwise the **most recent terminal** run by `started_at`; otherwise `404` (never `500`). Well-defined because at most one active run exists per `(workflow_name, workflow_id)` (the per-shard partial unique index). `workflow_name` is **required** (AC3): both path segments are mandatory, so a bare `workflow_id` never matches a by-id route.

**AC4 — the resolved `execution_id` is always returned:** every by-id response carries it in the `X-Harvest-Execution-Id` header (uniform, covers empty-body cases like `/result`'s `204`), and in the JSON body wherever one exists — `signal`/`query` responses are re-wrapped to add a top-level `execution_id`; `cancel`/`pause`/`resume` already carry it; `describe`/`stack` carry it nested; `result`/`children` surface it via the header.

**Shard strategy — always fan out.** `resolve_workflow_by_business_id` (plugin) fans out across `iter_shards()` rather than trusting a single rendezvous-hash fast path: `ShardRouter::pick_for_new_workflow` can drift from where a run actually lives once the writable shard subset changes, so a fast-path-then-miss design could resolve a live run to `404`. Resolution is not a hot path and the single-shard default is exactly one query. Per-shard candidates are merged by the pure `select_resolved_run`.

**Core (`autumn-harvest/src/execution.rs`, db-gated), no new `WorkflowEvent` variant, no migration** — resolution is read-only over the existing `UNIQUE (workflow_name, workflow_id)` index. New `ResolvedRun { exec_id, state, started_at }`; pure, no-DB, unit-tested `select_resolved_run(Vec<ResolvedRun>) -> Option<ResolvedRun>` (active-first, else most-recent-terminal, using `erase::is_terminal_state` so classification cannot drift — guarded by `resolve_terminal_states_matches_is_terminal_state`); shard-local `resolve_execution_id_by_workflow_id(conn, name, id)` (active-first query, else most-recent overall). Both re-exported from `lib.rs`.

**Registration surfaces:** all 10 routes registered in `management_api_routes()`, `management_api_request_fields()` (signal free-form, query POST `args`, cancel/pause `reason`, resume empty), `management_api_response_fields()` (describe/result/stack/children free-form; signal/query/cancel/pause/resume structured incl. `execution_id`), `docs/api-contract.json`, and `autumn_harvest::audit` (`CLASSIFIED_ROUTES` + `ALL_MUTATION_ROUTES` + `EXCLUDED_ROUTES` for the read-only ones). Docs: new "Addressing workflows by business id" section in `docs/management-api.md` (resolution semantics, required-name rule, always-present `execution_id`, shard-aware note, continue-as-new note).

**Tests:** pure `select_resolved_run` unit tests in `execution.rs` (empty/single/active-wins-over-terminals/most-recent-terminal/paused-active/sealed-terminal/two-actives-defensive/drift-guard); plugin HTTP integration `autumn-harvest-plugin/tests/by_id_integration.rs` (describe 200 + header/body execution_id match, unknown `(name,id)` → 404 not 500, malformed exec-id on the old route still 400, signal lands + execution_id in body/header, cancel + `401` unauthenticated, **continue-as-new correctness** — resolves to the RUNNING successor not the sealed predecessor, all-terminal resolves to the COMPLETED run, exec-id route unchanged); `contract_regression.rs` `*_route_is_classified` pins for every by-id route; one sorted line in `.github/ci/integration-suites.txt`. DB/HTTP integration tests are compile-checked in-sandbox and executed against a local Postgres 16 where available; the pure unit tests run under `cargo test -p autumn-harvest --lib`.
