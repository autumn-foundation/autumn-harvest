## Phase 3.x — Operator re-run of a terminal workflow (issue #777)

**Implemented.** New admin-gated management route `POST /api/harvest/workflows/{id}/rerun` starts a **brand-new execution** from a terminal source run's recorded start parameters. It is the complement to reset (issue #148), which forks an execution *mid-history* so the surviving prefix is replayed; a re-run replays nothing — it starts the whole workflow over with the same inputs, which is what an operator actually wants after fixing a transient downstream failure. Previously the only way to do this was to read the source row by hand and re-POST `/workflows/{name}/start` with reconstructed parameters, silently losing queue/memo/search-attrs/timeouts/SLA/owner/callbacks and leaving no provenance link back to the run being re-run.

**Core primitive** (`autumn-harvest/src/execution.rs`): `rerun_workflow_execution(conn, source_exec_id, RerunRequest, metrics) -> RerunOutcome`, mirroring `signal_with_start_workflow_execution_with_metrics`'s shape — a single outer `conn.transaction` with the deferred trigger starts / unfinished-handler checks / cancel metrics drained **after commit**, so a rolled-back re-run never leaves trigger workflows started.

**Re-runnable source states** — new `pub const RERUNNABLE_SOURCE_STATES: &[&str] = &["COMPLETED", "FAILED", "CANCELLED", "TIMED_OUT", "TERMINATED"]`. Deliberately **NOT** `erase::is_terminal_state`'s set, which includes `CONTINUED_AS_NEW`: re-running a chain predecessor would duplicate the work its successor is already doing (or has already done), so a CAN source is rejected `409` with a message pointing at the chain's latest run. A `RUNNING`/`PAUSED` source is likewise `409` ("re-run is for finished work — cancel or terminate it first, or use reset").

**Cloned verbatim from the source row**: input (unless overridden), queue, memo, search attributes, execution timeout, chain timeout, SLA, owner/runbook_url/severity, context headers, workflow retry policy, and completion callbacks. **The input is passed VERBATIM and never decoded** — `execution.input` is byte-for-byte what the original start wrote, so decoding it here would corrupt an encrypting (payload-codec) deployment's re-run and re-encrypt on write. The six replay-non-determinism diagnostic keys (issue #603) are stripped from the cloned search attributes via the reset-fork idiom (`worker::apply_raw_search_attrs_patch_in_memory` + `nd_search_attrs_clear_patch`, guarded on `Some` so a source with no attrs does not gain a stray `{}`) — a re-run has never diverged and must not display a phantom "blocked" reason.

**Deliberately NOT carried over**: `priority` (issue #249 — it lives on the task-queue row, not the execution row, so it is unrecoverable; documented gap), and `schedule_id`/`scheduled_for`/`origin`, which are cleared following the **reset-fork precedent** so an operator intervention is excluded from scheduled carryover (issue #488) and re-running an old slot cannot roll a later run's incremental cursor backward. The new run is a fresh continue-as-new chain origin (`inherited_chain_deadline_at: None`, no backlinks) and a fresh retry chain (`workflow_attempt: 1`, `retry_of_exec_id: None`).

**Provenance (issue #740)**: `start_source = "rerun"` (new `StartSource::Rerun` variant), `start_source_ref = <source execution id>`, and `started_by = <actor>` — re-run joins the existing actor-attribution writers of the `started_by` column (the plain start, signal-/update-with-start, batch start, manual schedule trigger, and the Vantage UI trigger all stamp it too).

**Business-key handling.** The source row is locked `FOR UPDATE` **first, checks after**, so two concurrent re-runs of one source serialize and the loser observes the sealed state rather than both starting a run. Then, under that lock: if the source itself still holds the target key (`COMPLETED`/`FAILED`/`CANCELLED`/`TIMED_OUT` are all inside the active-uniqueness index) the start uses `TerminateIfRunning` so `replace_execution` **seals the source to `CONTINUED_AS_NEW`**, freeing the key; if a **different** execution holds it, `409` naming the occupant (never seal someone else's run); if nothing holds it (a `TERMINATED` source, already released from the partial index) a plain `RejectDuplicate` insert. A `workflow_id` override always takes the `RejectDuplicate` path, so it never seals the source and an occupied override key surfaces as `409 AlreadyExists`.

**`completed_at` repair.** `replace_execution` stamps the seal with `now()`, which would rewrite the source's real finish time — the one durable record of when the original work actually ended. Inside the same transaction, and only when sealing, the original `completed_at` is restored with an `UPDATE … WHERE id = source AND state = 'CONTINUED_AS_NEW'`, touching **nothing** else (never `state`/`output`/`error`). The pre-seal state string, which the seal *does* destroy on the row, is returned as `source_prior_state` **and** persisted durably in the succeeded `workflow.rerun` audit row (`error_summary = "reran from state <STATE>"`, the free-text detail column a succeeded row carries — the scheduler's `skipped_overlap`/`deferred` rows set the same precedent). The response and that audit row are the only ROW-level records of the prior state; the source's `harvest_events` history survives the seal untouched, so its terminal event remains the authoritative forensic record.

**Hard create assertion.** An attach (`started.created == false`) is a hard error that rolls the transaction back — a re-run must never return `201` for a run the operator did not start.

**HTTP handler** (`autumn-harvest-plugin/src/api.rs`), modelled on `terminate_workflow` (issue #504): raw `Bytes` body so a body-less POST works, admin-gated via `require_admin`, and a validation ladder mirroring the start route — unregistered workflow type → `404`, registered DAG → `400` pointing at the DAG routes, and a **debounce / throttle / batch** policy → `400` (those defer the start and return no `execution_id`, so a re-run cannot honour its `201` contract). Per-key concurrency (#247), the effective input cap (#252), and the execution-timeout / chain-timeout / attempts ceilings are resolved exactly as the start route does, keyed on the **effective** input. Every rejection writes a best-effort **failed** audit row; success writes a succeeded one (op `workflow.rerun`, target = the SOURCE execution id). Admission-gate blocks surface as `503 {error, gate_id, reason}` byte-identical to any gated start.

**Response** `201 {ok, execution_id, workflow_name, workflow_id, state, reran_from, source_prior_state}` — it **never echoes the input** (the payload may be sensitive and a re-run response has no reason to return it).

**Tri-state `input` (a real bug caught in green).** The request field is `Option<Option<Value>>` via the existing `deserialize_tristate` helper, not `Option<Value>`: serde's stock `Option<Value>` deserializes JSON `null` to `None`, indistinguishable from an absent field, so `{"input": null}` would have silently *cloned* the source input instead of overriding it with `null`. Absent → clone verbatim; explicit `null` → override with `null`; a value → override.

**Invariants: NO new `WorkflowEvent` variant, NO migration.** The re-run reuses the ordinary start path, so the new run's history is a normal single `WorkflowStarted`; the only source-row mutation is the existing `CONTINUED_AS_NEW` seal (plus the `completed_at` repair). No replay-determinism impact — `start_source`/`start_source_ref`/`started_by` are metadata columns never read on replay.

**AC reconciliations.** (E1) The issue's `AllowDuplicate` wording is reconciled onto the seal/replace path, which is what actually frees a business key held by a terminal run; the state-string loss the seal causes is accepted and mitigated by returning `source_prior_state`, and the `completed_at` repair above closes the forensic gap the seal would otherwise open. (E2) The CLI's `@file` input syntax is reconciled to `--input-json` / `--input-file` (owned by the CLI agent; the contract entry ships the `["input", "workflow_id"]` request-body fields it depends on). (E4) AC4's "joining the business-key run chain (visible to #701)" is reconciled to shared-`workflow_id` + `start_source_ref` provenance: a re-run is deliberately **not** a continue-as-new successor and does not stamp `continued_from_exec_id`/`first_exec_id`, because co-opting the CAN linkage would misrepresent an operator restart as a continue-as-new (and would make `/run-chain` claim a lineage the engine never created). `GET /workflows/{id}/run-chain` therefore reports the source and the re-run as SEPARATE chains — pinned by a test that also asserts the endpoint never 500s for either id. The durable link is `start_source_ref` on the new row plus the `workflow.rerun` audit row. (E3) The issue's "decode the input" path is reconciled to a **verbatim clone** — decoding would corrupt an encrypting deployment, and the erased-input case (issue #495) is handled by an explicit `409` demanding an operator-supplied `input` rather than by re-running against `{"_harvest_erased": true}` tombstones.

**Schedule-attributed sources require a `workflow_id` override.** A default-key re-run of a source with `schedule_id IS NOT NULL` is rejected `409`. Sealing it would leave the row `CONTINUED_AS_NEW` while it still carries its `schedule_id`/`scheduled_for` — a state in NEITHER of `resolve_carryover`'s sets — so the next scheduled fire would resolve `last_completion_result` from the PRIOR slot (rolling an incremental cursor backward, issue #488) and `schedule_run_state_summary` would silently move the slot out of `succeeded`, deflating the cadence success ratio (issue #534). The `workflow_id`-override path never seals and stays fully available; its new run carries `schedule_id: None`, matching the reset-fork precedent that operator interventions are excluded from scheduled carryover.

**Erasure tombstones are not propagated.** `erase_workflow_payloads` (issue #495) tombstones `memo` and `search_attrs` as well as `input`. The erasure gate inspects only `input` and is skipped when an override is supplied, so a re-run-with-override of an erased source drops any tombstoned `memo`/`search_attrs` rather than cloning `{"_harvest_erased": true}` onto a fresh, never-erased run (which would pollute `?search_attr=` filtering and mislead compliance tooling). Shared, field-agnostic predicate: `erase::is_erasure_tombstone`.

**Faithful clone or loud failure.** `context_headers` and `workflow_retry_policy` are stored JSON. A parse failure now returns `HarvestError::Config` (409) naming the field instead of silently dropping it — starting the new run without the retry policy the operator believes it inherited would be worse than refusing. Defensive: both were written by a validated start path.

**Input-schema validation (issue #373) applies to the OVERRIDE only.** An explicitly supplied `input` is validated against the workflow's published input schema and rejected `400` with the standard `{error, violations}` body. A VERBATIM clone is never re-validated: a run started under an older or looser schema must stay re-runnable, since re-validating the clone would strand every historical run of that type the moment an author tightened the schema — exactly when re-running matters.

**Audit connections.** Every failure audit raised after the caller's DB connection is checked out rides THAT connection (mirroring `audit_decoded_read`, issue #608 round 2). The earlier pool-acquiring form asked for a second connection while the handler held one — which stalls a size-1 pool until the checkout times out, silently dropping the row, and on a multi-shard deployment writes it to the DEFAULT shard rather than the execution's own. Only the two pre-connection rejections (malformed execution id / malformed body) keep the pool-acquiring form. The succeeded row additionally persists the source's pre-seal state as `error_summary = "reran from state <STATE>"`.

**Documented consequence (R1).** Reusing the business key seals the source, so `GET /workflows/{source}/result` no longer reports the source's original terminal outcome — it observes `CONTINUED_AS_NEW` and follows the chain (issue #527). This is pinned by a dedicated test so a future change is a conscious decision, not a silent regression. A `workflow_id` override avoids it entirely.

**Registration.** Route registered in the axum router (admin-gated), `management_api_routes()`, `management_api_request_fields()` (`["input", "workflow_id"]`), `management_api_response_fields()` (the seven fields), `docs/api-contract.json`, and all three `autumn_harvest::audit` lists — `CLASSIFIED_ROUTES` (`Mutating`), `ALL_MUTATION_ROUTES` (`Some(OP_WORKFLOW_RERUN)`), and `AUDITED_OPERATIONS` — plus the `newly_classified_mutations_are_mutating_and_covered` privilege-escalation guard, so a read-only principal (issue #776) can never reach it.
