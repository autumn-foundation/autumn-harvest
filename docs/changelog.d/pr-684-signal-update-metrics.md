## Phase 3.5x — Signal & update lifecycle metrics (issue #684)

**Observability** (implemented): Six new `MetricsRecorder` counters give operators first-class, alertable visibility into the signal- and update-handler lifecycle, closing the gap where signal delivery/consumption and the update admit→complete/fail path had no metric surface. Modelled exactly on the issue #519 `record_workflow_terminal` recipe: additive no-op-default trait methods + a `metrics_rs_adapter` bridge + coverage tests. **AC7 invariant: no new `WorkflowEvent` variant, no migration, no macro-path change** — this is a pure additive-metrics slice.

The six counters (all bounded labels; `execution.id` is never a label, per ADR-0001 §7):

- `harvest.signal.received` (`workflow`, `name`, `queue`) — a `SignalReceived` event was durably delivered into a workflow's history. Emitted once per delivered signal at the single **live-only** delivery choke point (`ingest_due_timers_and_signals`, beside the existing `harvest.signal.deliver` span in `worker::process_workflow_task`), iterating `prepared.signals_delivered`. Each signal is marked consumed in `harvest_signals` so it appears in the delivered list exactly once; never emitted on replay.
- `harvest.signal.unhandled` (`workflow`, `name`, `queue`) — a delivered signal was never consumed (no `wait_for_signal`/`receive_signal`, no #546 push handler claimed it) by the time the run reached a terminal outcome. Emitted from the executor's `drive_workflow` terminal arms (`Ok(Ok)`/`Ok(Err)` — **never** the Suspended arm) via new `WorkflowContext::report_unhandled_signals`, after `flush_pending_signal_handlers` so push handlers get their last claim first. Backed by new `HistoryMatcher::unconsumed_signals_by_name`, which mirrors `has_non_lifecycle_unconsumed`'s two sources (cursor scan + `pending_signals` buffer) restricted to `SignalReceived` and grouped by name, honoring the issue #476 lost-signal-or-deadline-race carve-out (`late_race_signal_events`) and #546 push-handler consumption (`claim_pending_signal` marks consumed). **Honest coverage scope (deliberate, documented):** covers **Completed and Failed** (the graceful-terminal SLO) — the only terminal paths with a driven matcher; Cancel/Terminate/Execution-timeout/Parent-close are structurally out of scope (a force-killed run has no driven matcher, and its "unhandled signals" is not a graceful-completion SLO signal).
- `harvest.update.admitted` (`workflow`, `name`) — a workflow update was durably admitted (`UpdateAdmitted` appended). Emitted **post-commit** at the single admission choke point `store::admit_update_event`, which gained an `Option<&dyn MetricsRecorder>` param and now returns the resolved `workflow_name`. Threaded through its callers: the HTTP `admit_update` handler and Vantage-UI submit pass the runtime recorder; the in-process typed client (`handle::execute_update_in_process`) passes `None` (it wires no recorder — documented parity with the other engine metrics it omits); `update_with_start` passes `None` and emits at its own **outer-commit** boundary (gated on `outcome.update_admitted`) so a rollback never over-counts.
- `harvest.update.rejected` (`workflow`, `name`) — a workflow update was rejected by its registered validator before admission (a durable pre-admission `422`). Emitted at the two — and, by an independent audit of every `HarvestError::UpdateRejected` construction and every registered-validator invocation, the **only** — durable validator-rejection sites: the `admit_update` and `update_with_start` HTTP handlers. Scope is deliberately limited to **validator** rejections; non-`RUNNING`/paused admission-state conflicts are surfaced as caller errors, not counted here. Not emitted in `WorkflowContext::validate_update` (replay-driven) or `execute_update_in_process` (runs no validator). The scheduler's reuse of the `UpdateRejected` variant for DAG manual-trigger deferral is unrelated and untouched.
- `harvest.update.completed` (`workflow`, `name`, `queue`) / `harvest.update.failed` (`workflow`, `name`, `queue`) — an admitted update's handler returned success/error (`UpdateCompleted`/`UpdateFailed`). Emitted **post-commit** in the worker's `Persisted` arm via the pure, unit-tested `collect_update_result_metrics` helper: it resolves each `RecordUpdateResult` command's `update_id` → update name from the `UpdateAdmitted` events in the loaded history (the command carries only the id) and is collected **before** the persist transaction (which moves `pending_cmds`/`task`) but consumed only in the `Persisted` arm. Exactly-once: `RecordUpdateResult` is produced once on live execution (replay short-circuits in `execute_admitted_update`) and the arm runs once per successful persist.

**Emission discipline:** `record_signal_received` and `record_signal_unhandled` are live-frontier-only by construction (delivery choke point / non-replay executor path — `WorkflowReplayer` drives the strict/canary path, which never calls `report_unhandled_signals`, so a replay of an already-terminal history emits zero unhandled samples — AC2 no double-count on replay). The update counters emit post-commit at the persist boundary, mirroring #519's own persist-retry double-count edge (identical and equally rare). No `is_replaying()` guard is used on `report_unhandled_signals`: an unconsumed signal is itself an unconsumed event ahead of the cursor, so `is_replaying()` is `true` precisely when there is something to report — a guard would be actively wrong.

Bridged in `metrics_rs_adapter` (`MetricsRsRecorder`) using the existing `METRIC_LABEL_WORKFLOW`/`METRIC_LABEL_NAME`/`METRIC_LABEL_QUEUE` constants. Two new starter-pack alert rules (`harvest_update_rejected_rate`, `harvest_signal_unhandled_rate` — thresholds documented as starter defaults, not universal SLOs) with full runbook sections; six new dashboard panels (a "Signal & update lifecycle" row) in `docs/dashboards/starter-pack-v0.1.0.json`; ADR-0001 §7 catalogue and `docs/telemetry.md` updated.

Tests, TDD red→green: `metrics_coverage.rs` (RecordingMetrics impls + reachability + cardinality + exact-bounded-label test); `replay.rs` unit tests for `unconsumed_signals_by_name` (undrained/consumed-by-wait/consumed-by-push-handler/lost-race/multiple-same-name/stashed-but-unconsumed); `executor.rs` tests via `run_workflow_with_state_advancing_clock` (completed → emits once, failed → emits once, suspended → emits zero); `context.rs` unit tests for `report_unhandled_signals`; `worker.rs` unit tests for `collect_update_result_metrics` (name resolution, completed/failed split, unresolved → "unknown"); `metrics_rs_adapter.rs` label-content bridge test for all six; `replayer_tests.rs` AC2 test (replay path never emits `signal.unhandled` across ≥5 cycles); doc-enforcement registries in `dashboard_pack_docs.rs`/`alert_pack_docs.rs` extended.
