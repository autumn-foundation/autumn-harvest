# Phase 3.51 — Circuit-breaker reason codes in the stuck-task eligibility explainer (issue #611)

**Phase 3.51** (implemented): Circuit-breaker phase in the read-only stuck-task eligibility explainer — see issue #611. The eligibility explainer (`GET /api/harvest/admin/queues/{queue_name}/eligibility`, `GET /api/harvest/admin/tasks/{id}/eligibility`) now emits `circuit_open`/`circuit_half_open` reason codes for a pending task whose next activity's circuit breaker is OPEN/HALF-OPEN — closing a real gap where an open-breaker-blocked task previously had an EMPTY reason set and its otherwise-eligible worker was wrongly reported eligible (an operator triaging idle workers with a full queue would see no impediment at all). The existing `rate_limit_saturated` reason code was renamed to `rate_limit_exhausted` — a response-contract label change flagged for operator tooling; it is a live label, not persisted data, so nothing is orphaned by the rename. **#369 interaction (dispatch-vs-claim suppression):** for an activity that carries a circuit breaker, rate limiting is enforced at dispatch rather than at claim, so `queue::claim_task` skips the rate-limit gate (and token debit) for CB activities; the explainer therefore suppresses `rate_limit_exhausted` for a CB activity and surfaces the breaker phase (`circuit_open`/`circuit_half_open`) instead — never a stale rate-limit reason. **Lazy Open→HalfOpen read caveat:** `CircuitBreakerRegistry::list()` reads (and prunes each breaker's rolling failure window on) phase without transitioning it — the Open→HalfOpen transition is driven exclusively inside `on_dispatch` — so a cooled-down breaker reads `circuit_open` here through the cooldown until a probe dispatch is admitted, and `circuit_half_open` is only observable after that probe; the endpoint is strictly read-only (`list()`/`snapshot` only, never `on_dispatch`/`on_result`/`force_*`). **Documented boundary (from adversarial review):** a CB activity whose breaker is CLOSED but whose rate-limit bucket is exhausted surfaces NO claim-time impediment through this explainer — its stall is dispatch-side (visible via `GET /admin/circuits/{activity_name}` + the token bucket), a pre-existing #369 consequence deliberately out of scope for #611's open/half-open focus. AC2 (concurrency-only labeling) and AC5 (multi-reason accumulation) were already shipped; the genuinely new work is the circuit codes (AC3/AC4), the rename (AC1), docs (AC6), and tests (AC7). **Implementation:** a pure, no-DB, unit-tested `task_intrinsic_impediment_reasons` helper in `api.rs` computes the task-intrinsic impediments (per-key concurrency saturation, rate-limit exhaustion, and circuit-breaker phase) that block every worker equally; a `cb_phase` map is built once per shard-eval via `circuit_breakers().list(Instant::now())` and passed in. **No new `WorkflowEvent` variant, no migration, no new route, no replay/determinism impact, no shard-semantics change, no core-crate behavior change** — plugin-only, read-only labeling. Files: `autumn-harvest-plugin/src/api.rs`, `autumn-harvest-plugin/tests/eligibility_tests.rs`, `docs/runbooks/triage-pending-tasks-idle-workers.md`, `docs/api-contract.json`, `.github/workflows/ci.yml`. Tests: 9 pure unit tests in `api.rs` (`eligibility_reason_tests`, covering AC1–AC5, the #369 suppression, and the documented closed-breaker-CB-activity boundary that reports nothing); integration tests in `eligibility_tests.rs` (open-circuit → `circuit_open` with worker-absent / `no_eligible_workers` assertions and end-to-end #369 suppression via a shared-key non-CB sibling task; concurrency-only exact; rate-limit-exhausted exact). The eligibility integration tests are testcontainers-based and were NOT previously wired into CI at all — this slice adds both a `--no-run` compile step and a Docker-backed Linux execution step; the DB-backed tests are compile-checked in this sandbox (no Docker) and executed by CI, matching the repo's #543/#544/#601 precedent.
