## Fix — `enforce_external_cancels_outbox` self-deadlocked on aliased shards, hanging `Test DB (linux, shard 6)` for 6h on every CI run (issues #1350, #1357)

`Test DB (linux, shard 6)` never completed — it burned a full 6-hour GitHub Actions job on every run, on `trunk-dev` and on every PR, deterministically hanging at the same test every time: `shard_placement_by_id_tests::outbox_by_id_resolves_when_the_caller_holds_the_higher_aliased_shard`.

`autumn-harvest/src/timeout.rs`'s `enforce_external_cancels_outbox`, in its post-commit `deferred_checks` loop, compared two pools with `std::ptr::eq(pool.pool_for(entry), pool.pool_for(caller_shard))` to decide whether a peer shard's connection could be read off the one the sweep already holds rather than checked out fresh. `ShardedDbPool` stores each shard's pool in its own map slot, so even when two logical shards are backed by clones of one physical pool — a supported "colocated" topology, exactly what `ShardedDbPool::from_map` produces, and exactly what the hanging test builds (shards 0 and 1 both mapped to one `max_size(1)` pool) — `pool.pool_for(0)` and `pool.pool_for(1)` are two distinct struct instances at different addresses, so `std::ptr::eq` always reports "different pool" for an alias pair. That took the `else` branch — an unbounded `pool.get()` (deadpool has no configured acquisition `Timeouts` anywhere in this codebase) on the very pool whose only connection the sweep was still holding. Permanent hang, not a flake: because CI's `run-suites.sh` runs each shard's manifest rows sequentially in one script, this single hanging test blocked the whole shard-6 job until the 6-hour job limit, on every run that reached it.

The function's own doc comment, three lines above the bug, already correctly named the fix ("The identity test must be `same_underlying_pool`, NOT `std::ptr::eq`... issue #1146") and even explains why rounds 5/6 of that issue didn't catch it (they fixed this trap in the *resolution* path; this was the *delivery* side, which survived both rounds) — the code just didn't match the comment's already-correct diagnosis. Swapped `std::ptr::eq` for `crate::external_target_location::same_underlying_pool` (which compares `.manager()` pointers instead of the map-slot addresses), the same helper the function already uses correctly seven lines later for an adjacent comparison.

**Reproduced and verified the fix directly**, not just by reasoning about it: ran the exact hanging test under a bounded timeout before the fix (confirmed via `gdb`-attached backtrace that the tokio runtime was parked in `epoll_wait(timeout=-1)` at near-zero CPU — a genuine unbounded wait) and after. Before: hangs indefinitely. After: `outbox_by_id_resolves_when_the_caller_holds_the_higher_aliased_shard` passes in 2.13s; the full `shard_placement_by_id_tests` suite (23 tests) and `cross_shard_children_tests` (10 tests) both pass with no regressions.

**Zero unrelated engine impact:** the change is a single comparison swap inside one function; no new `WorkflowEvent` variant, no migration, no schema change, no public API change.

**Follow-up filed separately, not fixed here:** issue #1360 tracks a structurally similar but *unconfirmed* pool-size-1 risk in `batch.rs`'s `process_job` (holds `owning_conn` across a dispatch loop that can check out a second connection from the same pool) — flagged while tracing this bug's class, not reproduced, so not fixed speculatively.
