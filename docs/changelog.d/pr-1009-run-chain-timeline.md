- **Continue-as-new run-chain timeline API** (implemented): expose the complete, ordered continue-as-new succession for a workflow, resolvable from **any** member run (head, middle, or latest) in one call — see issue #701. Before this change, an operator holding a workflow's *latest* continue-as-new run had no way to see its predecessors: continue-as-new successors are inserted with `parent_id: None` and carried no backward link, so the sole forward link (the `WorkflowContinuedAsNew` event) could not be walked backward, and there was no single API for the whole chain — reconstructing a succession meant manual database spelunking. New read-only management route `GET /api/harvest/workflows/{id}/run-chain` (handler in plugin `api.rs`) and CLI subcommand `harvest workflow run-chain <exec_id> [--json]` return `{ head_unknown, workflow_id, runs: [{ exec_id, run_id, sequence, state, started_at, completed_at, outcome, continued_to_exec_id }] }` — `sequence` is zero-based over the ordered chain and `continued_to_exec_id` is `null` for the tail (AC2). **Additive back-link, no new `WorkflowEvent` variant, zero replay-determinism impact**: two nullable columns on `harvest_workflow_executions` — `continued_from_exec_id` (immediate predecessor) and `first_exec_id` (chain origin) — are stamped at the existing `persist_workflow_continue_as_new` successor-insert site; migration `20260710000002_harvest_workflow_continue_chain` is additive/nullable only, with partial indexes on both columns. **Design decisions**: (1) the dual-column back-link records both the immediate predecessor and the chain origin, so `first_exec_id` gives O(1) head resolution and a single indexed query (`WHERE id = head OR first_exec_id = head`) fetches the whole chain from any member — no per-hop history loads on a post-feature chain, hitting the p99 < 100 ms / N ≤ 100 success metric. (2) Pure core module `run_chain.rs` (`RunChainRecord`/`RunChainResponse`, `assemble_run_chain`, ordering + `head_unknown` derivation) is unit-tested without a database; ordering is bounded and cycle-safe (a `continued_from` linked-list walk with a deterministic `(started_at, exec_id)` fallback). (3) The `head_unknown` flag has a crisp rule — set when the resolved head lacks a back-link **and** participates in a continue-as-new chain **and** is not a confirmed origin (`head_lacks_backlink && head_participates_in_can && !confirmed_origin`), and additionally set when the resolved head declares a predecessor that is missing from the gathered set (e.g. a retention-pruned origin, from the correctness review). (4) **Graceful legacy degradation (AC5)**: pre-feature runs (which have no back-link columns populated) are forward-walked via the existing `WorkflowContinuedAsNew` events and the head is flagged `head_unknown: true` rather than ever returning a 500. **Shard-local by construction**: routing uses `db_conn_for_execution` (never `iter_shards`), and the legacy forward-walk reuses the held connection so the route is pool-size-1-safe (the #601 F4 precedent). The route is registered read-only across all four parallel plugin registries (`management_api_routes()`, request-fields, response-fields) plus `docs/api-contract.json` and the three `audit.rs` route lists (`CLASSIFIED_ROUTES` ReadOnly / `ALL_MUTATION_ROUTES` `None` / `EXCLUDED_ROUTES`), with a `contract_regression` pin test guarding the classification. **No mutation, no task claims, no `WorkflowEvent` appended, no macro impact.** Out of scope (per issue): parent→child spawn lineage (#621), reset-fork tree branching (#148/#538), cross-shard fan-out, merging chain event histories, and Vantage UI chain navigation. Tests: 14 pure `run_chain` unit tests (four canonical cases plus ordering/sequence/serialization/pruned-origin), 6 plugin integration scenarios in `run_chain_integration.rs` (404 + JSON body, 400 malformed id, 4-run chain resolved from head/middle/tail, standalone single run, legacy `head_unknown`, partial-shard) — compile-checked in this sandbox (no Docker) and executed by CI under Postgres, per the repo's #543/#544/#601 precedent — plus CLI mapping, contract-coverage, and contract-regression pin tests.
