- **Per-key activity rate limits** (implemented) — see issue #699. Extends the static per-activity rate limiter (#332) so an activity's rate-limit bucket key is resolved **per-execution from the workflow input** (dot-path), giving each tenant its own RPS bucket instead of sharing one cluster-wide bucket. Mirrors the per-key concurrency design (#247) and the workflow-start throttle's composite-key reuse of `harvest_rate_limit_buckets` (#607).

  **Declaration**: new nested `#[activity(rate_limit(key = "input.tenant_id", rps = 50, burst = 10))]` attribute (modelled on `#[workflow(concurrency(key = …, limit = …))]`; `key` and `rps` required, `burst` optional) or `ActivityInfo::rate_limit_key_expr` directly. The pre-existing **flat** `rate_limit_rps`/`rate_limit_burst`/`rate_limit_key` attributes are unchanged (AC3). The nested form is **rejected at compile time on `local = true` activities** (mirroring `circuit_breaker`) — local activities bypass the dispatch path where rate limiting is enforced.

  **New `ActivityInfo` field** `rate_limit_key_expr: Option<&'static str>` (the dot-path; presence selects dynamic mode). All workspace `ActivityInfo` construction sites initialise it to `None`.

  **Composite-key scheme**: `queue::dynamic_rate_bucket_key(expr, resolved: Option<&str>) -> "dyn-rate:{expr_component}:{resolved_component}"` — namespaced by both the key *expression* and the resolved *value* so activities declaring the same expression share one bucket per resolved value (matching the static limiter's "same key → shared bucket → must agree on rps" rule), while distinct tenants get independent buckets. The distinct `dyn-rate:` prefix can never collide with a static key (bare activity name / user string) or a throttle key (`start-throttle:`). An execution whose key expression cannot be resolved (missing / null / non-object input) is passed as `None` and falls back to a shared `dyn-rate:{expr}:U` bucket (the distinct `U` marker) so it is still bounded, not unbounded — kept **distinct** from `Some("")`, a legitimately-resolved empty-string tenant (which buckets under `dyn-rate:{expr}:L0:`), so a malformed/missing input never cross-throttles a real empty-string tenant (Codex round-5 P2; see the post-review bullet below). The `expr` is **normalized** by stripping a leading `input.` (so `key = "input.tenant_id"` and `key = "tenant_id"` — which `resolve_concurrency_key` treats as the same field — share one bucket and are validated together), and **both** the normalized `expr` and the resolved value are **length-bounded** (`MAX_KEY_COMPONENT_LEN = 256`, via the shared `bound_key_component` helper): a component longer than the bound is replaced with a stable, **collision-resistant SHA-256** digest so a pathological resolved value (a giant tenant id) *or* a pathological expression (a very long dot-path / hand-built `ActivityInfo.rate_limit_key_expr`) can never blow the `harvest_rate_limit_buckets` btree PRIMARY KEY size limit and wedge the enqueue transaction in a retry loop. With both components bounded the whole composite key is **provably ≤ ~530 bytes** regardless of the macro or a hand-built `ActivityInfo`. The key is **injective by construction** (post-review, Codex P2): `bound_key_component` emits each component as either a **length-tagged literal** `L{byte_len}:{value}` (self-delimiting: after the `L`, the decimal length up to the next `:` says exactly how many bytes follow) or a **fixed-width collision-resistant hash** `H{64hex}` (full 256-bit SHA-256, hex-encoded). The `L`/`H` first-byte tags are **structurally disjoint**, so (a) a literal value that happens to equal a hash's string encoding never collides with that hash — the earlier `h:{digest}` hash form was itself a valid short literal, so a long value hashing to digest `D` and a short literal value equal to the string `h:{D}` produced the same component (cross-tenant sharing without a hash collision), now closed because a literal `H0123…` encodes to `L{len}:H0123…` while the hash stays `H0123…`; and (b) a `:` inside `expr` (a dot-path can address a JSON key containing `:`) or inside `resolved` can never split ambiguously — the `(expr, resolved)` pair maps to exactly one key and vice-versa, whether either component passed through unchanged or was hashed. Without this self-delimiting encoding, `key = "a"` + resolved `"b:c"` and `key = "a:b"` + resolved `"c"` would both flatten to `dyn-rate:a:b:c` — two genuinely-distinct exprs colliding onto one bucket, and because builder validation keys on the (normalized) expr, their independently-validated (possibly different) rps configs would collide first-writer-wins.

  **Resolution at the worker enqueue site** (`worker::persist_scheduled_activities`): when `activity.rate_limit_key_expr` is `Some`, the key is resolved against the **workflow input** (`WorkflowExecution.input`, the plain start input, threaded into the function) via `concurrency::resolve_concurrency_key` and set as `params.rate_limit_key`. The static path is unchanged when `rate_limit_key_expr` is `None`.

  **Lazy bucket registration** (`queue::ensure_rate_limit_bucket`, shared with the static startup registration): the composite bucket is `INSERT … ON CONFLICT (key) DO NOTHING`-registered in the **same enqueue transaction** so the fail-closed `EXISTS` gate in `queue::claim_task` (and the circuit-breaker dispatch-time `try_consume_rate_limit_token`) always has a bucket row to read (else the task would stall forever). `refill_rate = rate_limit_rps`, `burst = rate_limit_burst.unwrap_or(rps)`. Static-limiter startup registration skips dynamic-key activities.

  **Claim / gate / debit unchanged**: `claim_task` keys entirely off the row's `rate_limit_key` value and is static-vs-dynamic agnostic. The circuit-breaker split (#369) is preserved — a breaker activity skips the claim-time gate and consumes at dispatch via `try_consume_rate_limit_token`, which now holds the composite key and works unchanged (its bucket exists because it was ensured at enqueue).

  **Cardinality landmine fixed** (team convention / ADR-0001 §7): `record_rate_limit_throttled` uses its argument as a metric **label**, and a composite dynamic key embeds unbounded tenant input. The metric is now labelled by the **bounded activity name** (`METRIC_LABEL_ACTIVITY`), never the raw bucket key — at the dispatch-defer site (`worker::process_activity_task`, passing `activity_name`) and the sampler site (`queue::check_throttled_keys` now returns distinct bounded `activity_name`s, not raw keys). The `harvest.rate_limit.throttled` metric's label changed from `key` to `activity` (BREAKING for operators — see post-review hardening below). The per-key token/refill **gauges** are separately fixed to exclude the unbounded key families (post-review #1).

  **Builder validation** (`validate_rate_limit_keys`): a dynamic-key activity without `rate_limit_rps` → `RateLimitKeyWithoutCap`; two activities declaring the same `rate_limit_key_expr` with different rps/burst → `RateLimitKeyMismatch`. Dynamic keys are validated in an **independent map keyed on the expression**, so a static key and a dynamic key_expr sharing the same string are never conflated.

  **SQLite guard** (`autumn-harvest-sqlite`): a dynamic-key activity is rejected at registration with the same unsupported-feature error as the static form.

  **Management API (AC7)**: `GET /admin/rate-limits` already enumerates all bucket rows, so composite `dyn-rate:…` keys appear automatically — no new surface; covered by a plugin HTTP test. A single-key fetch (`GET /admin/rate-limits/{key}`) works for a composite key too, but the key contains `:` and (for a nested path) `.`, so it **must be URL-encoded** in the path.

  **Post-review hardening** (issue #699 review):
  - **BLOCKER — per-key gauge cardinality (#1)**: the per-key token/refill **gauge** sampler (`worker::spawn_rate_limit_sampler`) emitted the bucket `key` as a metric label with no filter, so an unbounded `dyn-rate:{expr}:{tenant}` key (buckets are never GC'd) would create one time-series per tenant forever. The sampler now runs through `queue::sample_rate_limit_buckets`, whose SQL excludes the unbounded key families (`RATE_LIMIT_GAUGE_SAMPLER_FILTER` = `WHERE key NOT LIKE 'dyn-rate:%' AND key NOT LIKE 'start-throttle:%'` — the pre-existing throttle family, #607, is the same class of unbounded caller-resolved key and was silently exposed too, so it is excluded here as well). Bounded static keys keep their per-key gauges; per-tenant bucket state is observable via `GET /admin/rate-limits`, not metrics.
  - **BREAKING metric-label change (#2)**: `harvest.rate_limit.throttled` is now labelled `activity` (bounded) instead of `key` — any dashboard/alert keyed on the old `key` label must move to `activity`. The starter-pack dashboard panel, the anti-drift ground truth (`dashboard_pack_docs.rs`), and ADR-0001 §7 are updated.
  - **Worker-level resolution test (#3)**: a worker-driven DB test proves the composite key is resolved from the **workflow input**, not the activity's own input — two executions of one workflow/activity that differ only in workflow input (`{"tenant_id":"acme"}` vs `{}`) resolve to `dyn-rate:L9:tenant_id:L4:acme` and the unresolved fallback `dyn-rate:L9:tenant_id:U` respectively, while the activity input is identical for both.
  - **Coupled key-set with bucket-ensure (#4)**: `params.rate_limit_key` is stamped only inside the `if let Some(refill_rate)` block, so a dynamic key is never set without its bucket being ensured in the same transaction (a stamped key with no bucket row would stall the fail-closed claim/dispatch gate forever).
  - **`input.` prefix normalization (#6)** and **resolved-key length bound (#5)** — see the composite-key scheme above; both spellings share one bucket and are validated together, and an oversized resolved value is hashed.
  - **Flat + nested rejected at macro parse time (#7)**: combining the flat `rate_limit_rps`/`rate_limit_burst`/`rate_limit_key` attributes with the nested `rate_limit(...)` form is a compile error (they configure the same bucket incompatibly); trybuild fixture `rate_limit_flat_and_nested.rs`.
  - **Concurrency-contention safe-side test + documented known limitation (#9)**: `claim_task`'s `rate_limit_debit` CTE debits a token even when the `claimed` UPDATE matches 0 rows because a per-key concurrency (`concurrency_key`) advisory-lock race was lost. This is a **pre-existing** (byte-identical to trunk `claim_task`), **safe-side** (it over-throttles — the invariant "a real call always holds a token" is never violated; the leak only ever reduces dispatch below budget, never allows a claim without a token), **bounded** (≤1 token per lost claim), and **self-healing** (refills within one interval) leak, shared with the static-rate + concurrency path. The `claim_task` SQL is deliberately **not** modified (all reviewers praised its byte-for-byte invariant, and the fix would touch the hot path for a harmless-direction edge); documented in a code comment near the CTE and covered by a two-connection advisory-lock-contention DB test asserting RUNNING count never exceeds the cap nor the rate budget.
  - **Burst-fairness success-metric test (#10)**: a 10:1 burst DB test drains tenant A's bucket to 0 while B's is full and asserts B is claimed at exactly its burst while A is never claimed (zero cross-key bleed), making the headline "one noisy tenant cannot starve another" falsifiable.
  - **Dynamic-form builder error wording (#11)**: a dynamic-key activity missing `rps` now returns `RateLimitKeyExprWithoutCap` (names `rate_limit(key = "…", rps = N)`), not the static `rate_limit_key … remove the rate_limit_key` wording.
  - **Key delimiter injectivity (#13, and the follow-up Codex P2)**: the composite key is now **injective by construction** via self-delimiting, structurally-disjoint per-component encodings (`L{len}:{value}` literal / `H{64hex}` SHA-256 hash, `dyn-rate:{expr_component}:{resolved_component}`) rather than relying on `expr`/`resolved` being `:`-free or on the earlier ambiguous `h:{digest}` hash form — see the composite-key scheme above for the full rationale, the `key = "a"` + `"b:c"` vs `key = "a:b"` + `"c"` collision, and the literal-equal-to-a-hash collision it closes. The **payload-offload landmine (#14)** is noted below.
  - **Both key components length-bounded (Codex P2)**: the earlier fix bounded only the *resolved* value, leaving the *expression* unbounded — a very long dot-path or a hand-built `ActivityInfo.rate_limit_key_expr` could push the composite btree PRIMARY KEY past Postgres's ~2704-byte limit, so `ensure_rate_limit_bucket`'s `INSERT` would fail and roll back the enqueue transaction (the workflow can't schedule its activity). The bound-or-hash logic is now factored into a shared `bound_key_component` helper applied to **both** the normalized `expr` and the `resolved` value, and the injective length prefix is taken over the *bounded* expr component — so the whole PK is provably ≤ ~530 bytes regardless of the macro or a hand-built `ActivityInfo`. Distinct oversized exprs still hash to distinct keys (no cross-tenant bleed).
  - **`dyn-rate:` prefix reserved from static author keys (Codex P2)**: a static `rate_limit_key` is an unrestricted author string; a value like `rate_limit_key = "dyn-rate:L9:tenant_id:L4:acme"` would collide with the generated dynamic bucket for `rate_limit(key = "tenant_id")` tenant `acme`, and since static and dynamic keys are validated independently and both register `ON CONFLICT DO NOTHING`, they'd race first-writer-wins on the shared bucket's rate/burst. A static `rate_limit_key` beginning with the reserved `dyn-rate:` prefix is now **rejected at the macro parse site** (compile error; trybuild fixture `rate_limit_key_reserved_prefix.rs`), **in `HarvestBuilder::try_build`** (`RateLimitKeyReservedPrefix`), **and — for a worker built via a direct `HandlerRegistry` that bypasses both — in the worker path itself** (Codex P2, second review round): `persist_scheduled_activities` returns `HarvestError::Config` (failing the schedule/suspension transaction, so no `ActivityScheduled` event and no task row — the activity is never enqueued under the colliding key) and `register_rate_limit_buckets` logs a `tracing::error!` and skips the colliding bucket at startup, consistent with the round-3 dynamic-no-rps guard which likewise lives in both places. This keeps the static and dynamic bucket namespaces provably disjoint on every start path. Covered by a worker-driven DB test asserting the workflow never completes and neither the activity task row nor the colliding bucket row is ever registered. (The `start-throttle:` prefix from #607 is a separate pre-existing namespace; this PR reserves only `dyn-rate:` — the one it generates — and leaves `start-throttle:` as a follow-up.)
  - **Invalid dynamic key without `rps` fails loudly at schedule time (Codex P2)**: `HarvestBuilder::try_build` rejects a dynamic `rate_limit(key = "…")` with no `rps` (`RateLimitKeyExprWithoutCap`), but an application that builds the public `HandlerRegistry` **directly** bypasses that validation, so an `ActivityInfo { rate_limit_key_expr: Some(..), rate_limit_rps: None, .. }` could reach `persist_scheduled_activities`. Because the composite-key stamping and bucket-ensure both sit inside the `if let Some(refill_rate) = activity.rate_limit_rps` block (item #4 above), such an activity previously left **both** `params.rate_limit_key` and `dynamic_rate_buckets` unset and was silently enqueued with **no** rate limit — the exact failure a rate-limiting feature exists to prevent. `persist_scheduled_activities` now guards this: an activity with `rate_limit_key_expr.is_some() && rate_limit_rps.is_none()` returns `HarvestError::Config` **before** the stamping block, failing the schedule/suspension transaction (which rolls back — no `ActivityScheduled` event, no task row, so the activity is never enqueued unrated) rather than proceeding unrated. The failure surfaces loudly (logged `tracing::error! "task execution failed"`; the suspension-persist error propagates via `persist_workflow_outcome`'s non-terminal `Err` branch, so the task is re-dispatched and re-errors on the same invalid config — a loud retry-loop, strictly better than a silent no-limit, and only reachable on an unvalidated direct-registry build). A defensive `tracing::error!` in `register_rate_limit_buckets` also surfaces the invalid declaration at worker startup, before the first enqueue. Covered by a worker-driven DB test asserting the workflow never completes and the activity task row is never enqueued.

  - **Comprehensive rate-limit validation at worker startup (Codex round-5 P2)**: the public `HandlerRegistry` path bypasses ALL `HarvestBuilder::try_build` rate-limit validation, so an invalid config slipped through and was only caught piecemeal (or not at all) by the schedule-time guards. Rather than keep bolting on per-case schedule-time guards, the whole class is now validated **once at the fallible `Worker::new` startup boundary**: the builder's validation is factored into a shared `builder::validate_activity_rate_limits` (accepting an iterator of `&ActivityInfo` so both the builder's `Vec` and the registry's `HashMap::values()` validate without an owned copy — `ActivityInfo` is not `Clone`), and `Worker::new` calls it (mapped to `HarvestError::Config`) before its poll loop and first enqueue. This also closes two gaps the schedule-time guards never covered: (a) a dynamic `rate_limit(key = …)` on a **local** activity — which the `#[activity]` macro rejects at parse time but a hand-built `ActivityInfo` bypasses, silently running unrated inline via `run_local_activity_inline` — now rejected with the new `HarvestBuilderError::RateLimitKeyExprOnLocalActivity` (Codex worker.rs:4693); and (b) two activities sharing a normalized key-expression with **conflicting rps/burst**, whose shared `ON CONFLICT DO NOTHING` bucket would otherwise be insertion-order dependent (Codex worker.rs:4826). The schedule-time guards in `persist_scheduled_activities`/`register_rate_limit_buckets` remain as **defense-in-depth** behind this primary startup gate. Scope: the local reject covers the **dynamic** form only; the pre-existing static-rate-on-local #332 asymmetry stays a documented follow-up. Covered by direct-registry startup tests (`worker_startup_rejects_dynamic_rate_limit_on_local_activity`, `worker_startup_rejects_conflicting_rps_for_same_key_expr`, `worker_startup_accepts_valid_direct_registry`, plus the reframed dynamic-no-rps / reserved-prefix startup tests).
  - **Unresolved key distinct from an empty-string tenant (Codex round-5 P2, worker.rs:4720)**: `resolve_concurrency_key` returns `Some("")` for a real empty-string tenant (`{"tenant_id": ""}`) and `None` for missing/null/non-object input, but the enqueue site's `.unwrap_or_default()` collapsed **both** onto the same `L0:` fallback bucket — cross-throttling malformed/missing executions against a legitimate empty tenant. `dynamic_rate_bucket_key` now takes `resolved: Option<&str>` and encodes `None` as the structurally-disjoint single-byte `U` marker (`dyn-rate:{expr}:U`) while `Some("")` still encodes as `L0:` (`dyn-rate:{expr}:L0:`), so the two are provably distinct buckets (the `U`/`L`/`H` first-byte tags keep the whole composite key injective). The worker call site passes `resolve_concurrency_key(...).as_deref()` through instead of `.unwrap_or_default()`. Covered by `dynamic_rate_bucket_key_none_unresolved_is_distinct_from_empty_string_tenant` and the updated absent-field worker-resolution assertion.

  - **Collision-resistant SHA-256 digest for oversized key components (Codex P2, queue.rs:150)**: `bound_key_component`'s oversized (`H…`) form originally used a 64-bit `seahash::hash`, which is NOT collision-resistant against tenant-influenced input — two distinct >256-byte resolved values (or expressions) sharing a 64-bit digest would silently share one `dyn-rate` bucket (the `L`/`H` tags fix *format* collisions, not *digest* collisions). The `H` form is now the **full 256-bit SHA-256** of the component's UTF-8 bytes, hex-encoded (`H{64hex}`, 65 bytes; the `sha2` crate is already an unconditional `autumn-harvest` dependency, used by `payload_store.rs`/`completion_callback.rs`), so a digest collision is computationally infeasible and distinct oversized components get distinct buckets in practice. The `H` first-byte tag (disjoint from `L`/`U`) is preserved, so injectivity and the literal-vs-hash disjointness are unchanged; the composite key stays well under the ~2704-byte btree PK limit (both-oversized ≈ 140 bytes). `seahash` usage elsewhere (shard routing, jitter, build-id hashing, history-export digests) is untouched — only this tenant-facing bucket-key component needed collision resistance. The oversized-component tests recompute the expected digest via SHA-256; the disjointness test asserts the fixed 65-byte `H{64hex}` width.

  - **Reject non-finite / non-positive rate & burst in the shared validator (Codex P2, builder.rs:2330)**: the shared `validate_activity_rate_limits` (now run by both `try_build` and `Worker::new`) only checked that a dynamic key *had* an rps — not that `rate_limit_rps` (and `rate_limit_burst`, when set) is finite and strictly positive, which the `#[activity]` macro enforces universally (`n <= 0.0` → compile error). A direct-registry `rate_limit_rps: Some(0.0)` therefore started the worker, created a `burst = tokens = 0` bucket, and left every scheduled dynamic activity permanently unclaimable (the token gate can never reach 1). The validator now rejects any activity (static OR dynamic — the macro's positivity check is universal) whose `rate_limit_rps`/`rate_limit_burst` is `!is_finite() || <= 0.0` with the new `HarvestBuilderError::RateLimitRateNotPositive { activity, field }` (stricter than the macro: also catches `NaN`/`±inf`, which `n <= 0.0` alone lets through). Because it runs at both boundaries, the `HarvestBuilder` and the direct-`HandlerRegistry`/`Worker::new` paths are both covered. Covered by `worker_new_rejects_non_positive_dynamic_rate_limit_rps`, `worker_new_rejects_non_positive_or_non_finite_rate_limit_burst`, and `worker_new_accepts_valid_positive_dynamic_rate_limit`.

  **Forward-looking payload-offload note (#14)**: if the start-path `WorkflowStarted` input is ever routed through the large-payload claim-check offloader (#524), `WorkflowExecution.input` would be a small reference envelope rather than the real input object, so a dynamic key would resolve to `None` and land in the shared `dyn-rate:{expr}:U` fallback bucket for every such execution. That is deterministic (no replay bug) but degrades per-key isolation to a single shared bucket; the resolution site should inflate the offloaded input first, or resolve the key before offloading, when that path lands.

  **Pre-existing asymmetry (follow-up, not fixed here)**: the **static** rate-limit attributes are NOT rejected on `local = true` activities (only the new dynamic `rate_limit(...)` form is). A static rate-limited local activity silently bypasses rate limiting (local activities run inline, off the dispatch path). Flagged as a follow-up.

  **No new `WorkflowEvent` variant, no migration, no replay/determinism impact, no shard-routing change.** Buckets and enqueue are **shard-local** (consistent with per-key concurrency #247 and the activity limiter): a documented, out-of-scope limitation is that cross-shard global rate coordination is not attempted, so a key's effective rate across a multi-shard cluster is `per-shard-rate × shards` (see `docs/sharding.md`).

  **Tests**: pure unit tests for `dynamic_rate_bucket_key` (`queue.rs`); macro-expansion tests for the flat (AC3) and nested forms + two trybuild compile-fail fixtures (`rate_limit(...)` on `local = true`, `rate_limit(key = …)` missing `rps`); builder-validation tests (dynamic-without-rps, same-expr mismatch, matching/distinct exprs, static/dynamic independence); DB integration tests in `autumn-harvest/tests/integration/rate_limit_key_tests.rs` (cross-tenant isolation / success metric, shared bucket, defer-not-fail AC6, lazy registration, static-unchanged AC3, compose-with-#247-concurrency AC8); plugin HTTP integration test (`GET /admin/rate-limits` lists the composite key).
