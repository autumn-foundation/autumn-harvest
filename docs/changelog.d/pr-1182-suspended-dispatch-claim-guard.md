## Phase 3.x — Guard the suspended-dispatch catch-all against a stolen mid-flight claim (issue #1182)

**Fixed.** `handle_suspended_workflow`'s catch-all branch — reached when a live workflow-task invocation suspends with an empty command set, or a command combination the worker does not know how to persist — used to call `persist_workflow_failure` directly, with **no recheck that the dispatcher still owned the task's claim**. If a dispatcher's claim was stolen mid-flight (a poison-pill reclaim of a stale/zombie worker, an operator requeue, or a concurrent claim race) while it was still working through a slow invocation, the *original* dispatcher could go on to terminally fail a task that had already changed hands — corrupting the new owner's in-flight work with a spurious `WorkflowFailed` event and a `FAILED` execution state it never earned.

This was reported as a reproducible CI failure: `capability_miss_tests::a_claim_lost_mid_dispatch_makes_no_terminal_decision` panicked with byte-identical output on three consecutive `trunk-dev`/CI runs (a dispatcher whose claim was deliberately stolen mid-dispatch by the test harness still failed the task under its own stale ownership, instead of making no terminal decision at all).

**The fix.** New `fail_suspended_workflow_if_still_claimed` (`worker.rs`) replaces the unconditional `persist_workflow_failure` call in the catch-all branch. It reuses the existing `commit_terminal_failure_if_still_claimed` guarantee — the same primitive issue #804's round-28 fix built for the `AfterHandler` capability-miss escalation branch — with no escalation attached: it re-derives `next_event_id` fresh under a row lock, rechecks the claim (`worker_id` + `crash_strikes`) against the *current*, not the claim-time, state, and writes the terminal `WorkflowFailed` event only if the claim is still held. If the claim has moved (`TerminalWriteOutcome::ClaimLost`), it writes nothing and logs at `info` level — the stale dispatcher makes no terminal decision, and the row's new owner is free to drive the run to completion.

**No new `WorkflowEvent` variant, no migration.** This composes entirely from existing primitives (`commit_terminal_failure_if_still_claimed`, `PreloadedFailureHistory`, `TerminalWriteOutcome`) that issue #804 already introduced and hardened through many rounds of review; this PR is its second call site.

**Tests, TDD red → green:**
- The original flaky test, `a_claim_lost_mid_dispatch_makes_no_terminal_decision`, is unchanged and now passes reliably.
- A new, fully deterministic companion test, `a_stale_dispatcher_with_zero_emitted_commands_makes_no_terminal_decision_when_the_claim_moved`, seeds a claimed task, transfers its claim via a direct SQL update (no timing race, no sleep-based injection), and calls `fail_suspended_workflow_if_still_claimed` directly under the stolen-claim condition. It asserts the strongest possible negative: no `WorkflowFailed` event in history, the execution stays `RUNNING`, and the task row is untouched under its new owner (`worker_id == "thief"`). Confirmed genuinely RED by temporarily reintroducing the unguarded call (the reintroduced bug produces exactly the corrupted state the assertion rejects), then GREEN against the real fix.
- Full `capability_miss_tests` suite: at this point in the review, 42 of 43 pass; the one remaining failure, `peer_reregistering_mid_dispatch_is_seen_by_the_decision`, was initially (and, as the "post-review hardening round 2" section below records, **incorrectly**) suspected of being an unrelated pre-existing bug.
- Broader regression pass across `nd_block_tests`, `pause_tests`, `poison_pill_tests`, `workflow_retry_tests`, `retry_now_tests`, `retry_after_tests`, `worker_session_tests`, `queue_pause_tests`, `queue_pause_success_metric_tests`, `scheduler_auto_pause_tests`, and `executor_span_tests` — the suites most likely to exercise ordinary suspension/dispatch/pause/termination paths near the changed call site.

**Multi-angle review.** Three independent review passes (correctness/concurrency, test-quality/TDD-discipline, doc/style/scope) found: no correctness issues with the fix itself; no test-quality issues (determinism, on-target exercise of the fixed path, regression strength all confirmed); two style nits (doc-comment mood, `cargo fmt`), both fixed. The correctness review additionally surfaced a **broader, pre-existing** finding — the "normal"/happy-path terminal-write route (`queue::fail_task`, `queue::complete_task`, `update_workflow_execution_failed`/`_completed`, `check_paused_and_park`, and their `reject_child_continue_as_new`/`check_continue_as_new_type` callers) has **no** worker-ownership check at all, and is far more commonly reachable than the narrow branch this PR fixes. Independently re-verified by direct source reading and filed as its own issue, #1184, rather than folded into this PR — given the demonstrated historical fragility of this exact code area (30+ prior "round N" hardening fixes to the capability-miss/claim-theft machinery, several of which needed follow-up correction), it deserves its own scoped PR with a dedicated red/green test per write site.

**Post-review hardening (Codex, P1).** `queue::claim_still_held_for_update`'s `FOR UPDATE SKIP LOCKED` guard cannot distinguish a genuine ownership transfer from a concurrent, *unrelated* transaction merely holding the row's lock for a moment (e.g. `queue::wake_workflow_task`'s `wake_requested` fallback `UPDATE`, which touches this exact row for an instant while a sibling event wakes the same execution) — both read back identically as "not ours right now". The initial cut of this fix treated every `TerminalWriteOutcome::ClaimLost` result as "do nothing", which is correct only for the first case; in the second, the task would strand `RUNNING` forever under a worker who had already made its "no terminal decision" call and moved on, with nothing left to ever re-claim it.

The pre-existing capability-miss caller (issue #804's round-28/29 machinery) never has this gap: every path through it that withdraws — an escalation withdrawn at the commit boundary, or an ordinary release decision — always falls through to `release_capability_miss` → `queue::release_task_for_capability_miss`, a **plain** (non-`SKIP LOCKED`) `UPDATE` that blocks behind a transient lock holder instead of skipping it, then reconciles against the row's post-commit state.

New `queue::release_suspended_workflow_claim` mirrors that established pattern exactly, minus the capability-miss-specific bookkeeping columns (this isn't a capability miss — the handler DID run, it just made no progress): a plain, ownership-guarded (`worker_id` AND `crash_strikes`) `UPDATE`, deliberately **not** `SKIP LOCKED`, that clears `wake_requested` in the same write so a wake that landed in the contention window is reconciled rather than silently dropped. It is called only *after* `commit_terminal_failure_if_still_claimed`'s own transaction (which holds the execution row first, then attempts the task row via `SKIP LOCKED`) has already committed and released every lock it held, so it is a single, standalone task-row lock acquisition — it cannot participate in the execution-row/task-row ABBA cycle `SKIP LOCKED` exists to avoid in the first place (documented on `claim_still_held_for_update` itself: its own `SKIP LOCKED` choice is deadlock-avoidance against `poison_pill::quarantine_orphan`'s task-row-then-execution-row lock order, not a throughput optimization).

New deterministic regression test `a_dispatcher_that_still_owns_the_claim_is_released_when_skip_locked_is_a_false_positive`: holds an open transaction's lock on the task row (standing in for a concurrent wake) while a spawned dispatch races the `SKIP LOCKED` guard, confirming it reads the row as contended; releasing the lock lets the blocked release fallback proceed, and the test asserts the strongest possible outcome — the task is released back to `PENDING` with `wake_requested` cleared, not stranded `RUNNING`. Confirmed genuinely RED by temporarily reverting to the log-and-return behavior (the task is left `RUNNING` forever, exactly the stranding this fix closes), then GREEN against the real fix.

**Post-review hardening (Codex, round 2 — three findings, all fixed).**

**Finding 1 (P1) — the naive fix from the round above still had a latent ABBA deadlock.** Calling the blocking, non-`SKIP LOCKED` `queue::release_suspended_workflow_claim` directly from inside `fail_suspended_workflow_if_still_claimed` — which is itself invoked from *inside* `process_workflow_task`'s persistence transaction, the one that holds the **execution** row's `FOR UPDATE` lock (via `check_paused_and_park`) for its whole duration — would make this dispatch contend for the **task** row *while still holding the execution row*. `poison_pill::quarantine_orphan` (and other task-row-first actors) lock the task row first and then go on to touch the execution row. Two connections each holding one row and blocking on the other is a textbook ABBA cycle; Postgres's own deadlock detector eventually aborts one side with `deadlock detected` rather than letting either progress.

The fix splits the guard into two calls with a hard boundary between them. `fail_suspended_workflow_if_still_claimed` now returns `Err(HarvestError::SuspendedClaimAmbiguous { task_id })` instead of attempting any release itself — a new, non-`#[non_exhaustive]` `HarvestError` variant with a `suspended_claim_ambiguous()` accessor mirroring the existing `handler_not_registered()` convention. Propagating that error with `?` out of `process_workflow_task`'s `conn.transaction::<WorkflowPersistFlow, HarvestError, _>(async |conn| { .. })` closure forces Diesel to roll back the **entire** enclosing transaction — releasing the execution row's lock and discarding every other write made earlier in the same dispatch cycle (e.g. a `clear_nd_block` bookkeeping write) — *before* any release is attempted. Only after that rollback has completed, and the `.await` on the transaction call has returned, does `process_workflow_task`'s post-transaction `match` arm invoke `queue::release_suspended_workflow_claim` standalone, holding no other lock at all. At that point it cannot be the other half of an ABBA cycle: there is no second lock left for it to be waiting on anything else while it holds.

**Finding 2 — the whole-transaction-rollback claim needed its own proof**, since neither existing test called the guard from inside an actual `conn.transaction()` closure with anything else to roll back. New test `an_ambiguous_claim_rolls_back_every_earlier_write_in_the_same_transaction` reproduces `process_workflow_task`'s exact shape — an unrelated `UPDATE ... current_details` write followed by the ambiguous-claim guard, both inside one `conn.transaction(async |conn| { .. })` closure whose `Err` is propagated with `?`, precisely as the real code does — and asserts the unrelated write is genuinely gone afterward, not merely that the function itself returned an error. Falsified by temporarily swallowing the guard's error instead of propagating it: the test failed exactly as expected (the unrelated write survived the would-be rollback), confirming the assertion is load-bearing rather than vacuous.

**Finding 3 — stale capability-miss evidence must not survive a release reached only after the handler already ran.** `release_suspended_workflow_claim_query`'s `UPDATE` now also resets `capability_misses = 0, capability_miss_workers = '{}'`, matching `park_workflow_task_sticky_query`'s established `reset_capability_misses = true` precedent (issue #804) rather than `release_task_for_capability_miss_query`'s (which always *increments* it, since that release specifically records the releasing worker's own incapability). This release is reached only after `handle_suspended_workflow`'s handler dispatch has already run — the handler executed, it simply made no replay-significant progress — so it is unconditionally proof of capability, and any stale evidence naming a *different*, prior worker as incapable for this frontier must not survive it: leaving it would let the next dispatcher's capability-miss decision undercount the live, unaccounted fleet by one, based on a peer this exact release just proved wrong. Covered by the existing pure SQL-shape unit test `release_suspended_workflow_claim_query_is_ownership_guarded_and_not_skip_locked`, extended to assert both new clauses.

New deterministic ABBA-deadlock-avoidance test, `a_task_row_first_peer_touching_the_execution_row_never_deadlocks_the_release`, drives both halves of the would-be cycle concurrently and for real: connection A locks the task row and then the execution row (poison-pill's own order) while the dispatch's blocking release waits on connection A's task-row lock, holding nothing at all itself, bounded by a `tokio::time::timeout` so a regression fails loudly and immediately rather than hanging the suite. Falsified by patching the dispatch to also lock the execution row on its own connection *before* calling the release (simulating the exact broken shape Finding 1 describes): the falsified run reproduced a genuine deadlock, surfaced by Postgres itself as `Database("deadlock detected")` and by the test as a loud panic — proving the test would have caught the round-1 gap had it existed, before reverting the patch and confirming the real (fixed) code passes cleanly and repeatably.

Full `capability_miss_tests` suite re-run after all round-2 fixes: **46 of 46 pass** (43 pre-existing + the round-1 hardening test + the two round-2 tests above). Full broader regression pass (`nd_block_tests`, `pause_tests`, `poison_pill_tests`, `workflow_retry_tests`, `retry_now_tests`, `retry_after_tests`, `worker_session_tests`, `queue_pause_tests`, `queue_pause_success_metric_tests`, `scheduler_auto_pause_tests`, `executor_span_tests`): 147 of 147 pass, no regressions.

**Correction — `peer_reregistering_mid_dispatch_is_seen_by_the_decision` was misdiagnosed, and #1185's hypothesis was wrong.** That test was originally believed to be an unrelated, pre-existing bug and filed separately as issue #1185, with a *documented, not-yet-confirmed* lead pointing at `queue::invalidate_capability_miss_evidence_for_worker` only clearing the `capability_miss_workers` array column and never the `capability_misses` count column. Issue #1182's own tracking text names this test as part of the *same* regression, so it was investigated further as part of this PR. Extensive static analysis of the capability-miss decision machinery (`capability_miss_decision`, `fleet_capability_evidence`, `resolve_capability_miss_with_confidence`, `current_frontier_miss_state`) reached a contradiction with the observed failure, which was resolved empirically (temporary debug instrumentation dumping the failing task/execution rows): the test's `capability_misses`/`capability_miss_workers` columns were **completely unchanged** from their seeded values, proving the capability-miss decision code was never even reached, and the actual recorded error was `"workflow suspended without emitted commands; resumption is not implemented yet"` — a totally different failure mode than the one #1185 hypothesized.

The real root cause: the test's injected workflow handler performed a raw `AsyncPgConnection::establish(url).await` (a full TCP connect plus Postgres auth handshake) directly inside the workflow body, from within `workflow_invalidates_peer_then_misses`. `executor::SUSPENSION_TIMEOUT` gives a live workflow-task invocation only 100ms to reach a genuine command-emitting suspension point; under load, establishing a fresh connection inline reliably blows that budget, tripping the very "zero emitted commands" terminal-failure path this whole PR is about — before the workflow body ever reached the capability-miss-triggering `ctx.execute_activity_raw` call the test exists to exercise. This exact anti-pattern (a raw connect inside a workflow body under the 100ms budget) is a documented, previously-fixed hazard in the same test file, via the sibling `CLAIM_THEFT_INJECTION`/`prewarm_claim_theft_injection` pattern used by an already-passing test.

**Fix (test-only, no production code change):** `RACE_INJECTION` was converted from a `OnceLock<(String, String)>` (a raw URL) to a `OnceLock<(DbPool, String)>` (a pre-warmed connection pool), mirroring `CLAIM_THEFT_INJECTION` exactly, with a matching `prewarm_race_injection()` helper called before the worker starts. The workflow handler now checks out a pooled connection (`pool.get().await`) instead of establishing a fresh one, paying only the `UPDATE`'s round trip inside the 100ms budget rather than a full handshake. Confirmed deterministic (not flaky) both before and after: it failed identically and reproducibly on 3+ isolated runs pre-fix (including against the unmodified pre-round-1 base commit, ruling out any interaction with this PR's own changes), and passes reliably on 5+ isolated runs post-fix (consistently ~3.2s, down from the flaky ~3.7–3.8s of the failing runs). Issue #1185's stated hypothesis is now known to be incorrect and the issue is resolved by this PR rather than tracked separately.
