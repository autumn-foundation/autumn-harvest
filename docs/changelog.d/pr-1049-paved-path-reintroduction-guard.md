## Tooling — Guard against reintroducing hand-rolled migration bundles (PR #1049)

**Tooling/testing** (implemented): follow-up to #1031 / #1045. #1031 added a completeness guard for the `full_migrations_sql()` paved-path helper itself, and #1045 swept every DB fixture onto it — but nothing prevented a *new* fixture from **reintroducing** a hand-rolled `concat!(include_str!("...migrations/.../up.sql"), ...)` bundle that silently drifts as migrations land (failing only at runtime with `column ... does not exist`). Neither the existing `migration_hygiene` completeness guard nor the `ci_run_coverage` run-coverage guard catches a reintroduced hand-rolled bundle. **After:** a no-DB guard in `tests/integration/migration_hygiene.rs` fails if any file under `autumn-harvest/tests/**` or `autumn-harvest-plugin/tests/**` contains a hand-rolled migration `include_str!` outside a small, commented allowlist — making the paved path self-enforcing. **No product-code behavior change.**

**Allowlist** (deliberately-partial fixtures, each entry commented with why): `integration_e2e.rs` (legacy upgrade-path / workflow-start-uniqueness excluded); `schedule_update_integration.rs` (omits `harvest_start_throttle` for the `to_regclass` graceful-degradation path); `timeline_integration.rs` (inserts into `harvest_dag_runs`, which the full bundle drops — `20260514000000_drop_harvest_dag_runs`); and `outbox_integration.rs` (a separate plugin app-DB `harvest_workflow_outbox` migration, not part of the core `migrations/` bundle). Adding a new partial fixture requires a conscious allowlist edit + documented reason.

**Design:** the guard is *bidirectional* — it fails both on a new offender outside the allowlist **and** on a stale allowlist entry (a fixture later converted to `full_migrations_sql()` that no longer contains a hand-rolled include), so the allowlist can't rot. Detection is text-based (per-line: `include_str!` + `migrations` + `up.sql`), so it catches a reintroduction regardless of `#[cfg]` gating; the guard file itself is excluded (it carries those tokens as literals), and `ci_run_coverage.rs`'s own non-migration `include_str!(".github/...")` lines are correctly not flagged. A pure unit test (`line_detector_flags_a_handrolled_include_and_ignores_others`) locks the detector semantics. **No new suite** — a test fn added to the already-run no-DB `migration_hygiene` target, so no `integration-suites.txt` change; `ci_run_coverage` is unchanged (stays 13/13).

**No new `WorkflowEvent` variant, no new migration, no route/contract change, no replay/determinism impact, no production-logic change** — test infra only. Verification: red→green demonstrated (a stray hand-rolled `include_str!` appended to the non-allowlisted `audit_tests.rs` fails the guard naming that file; reverted → green); `cargo fmt --all --check` and `cargo clippy -p autumn-harvest --all-features --tests -- -D warnings` clean; `migration_hygiene` 6/6 (was 4) and `ci_run_coverage` 13/13 green in the no-DB leg.

**Post-review hardening (Codex P2):** the offender scan now uses a whole-file structural detector (`detects_handrolled_migration_include`) that collapses whitespace before checking each `include_str!` argument, so it catches the **rustfmt-wrapped** multi-line form (`include_str!(` and its `"…/migrations/…/up.sql"` path string on separate lines) that the previous per-line scan missed. The structural check is also strictly more precise — the tokens must belong to a real `include_str!` argument — so prose/doc comments merely mentioning `migrations/…/up.sql` are no longer flagged. The 4-entry allowlist and the single-line `line_is_handrolled_migration_include` unit predicate are unchanged.
