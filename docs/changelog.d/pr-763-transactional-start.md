## Phase 3.58 — Transactional workflow start: enqueue a run in the caller's own transaction (issue #763)

Closes the dual-write problem at the workflow-**start** boundary — the sibling of `ctx.run_transactional` (issue #352), which already solved it at the activity-**completion** boundary. An autumn-web handler that inserts a domain row (e.g. `orders`) and then starts a fulfillment workflow previously had two independent commits: a process crash (or any failure) between them left an order with no workflow, or — in principle — a started workflow whose triggering domain write never landed. Closing that gap by hand meant a transactional-outbox table plus a reconciliation poller. `WorkflowHandleClient::start_workflow_transactional` removes the need for either.

### What shipped

- **`WorkflowHandleClient::start_workflow_transactional(conn, workflow_name, workflow_id, input, options) -> HarvestResult<TransactionalStartOutcome>`** (`autumn-harvest/src/handle.rs`) — accepts a caller-owned `&mut AsyncPgConnection` (bare, or already inside an open `conn.transaction()`), stages the workflow start on it, and returns the resolved `ExecutionId` **synchronously** so the caller can persist it onto their own domain row in the same transaction (AC1).
- **`TransactionalStartOptions`** — fluent builder mirroring the shape of a plain HTTP start request: `with_shard`, `with_reuse_policy` (`WorkflowIdReusePolicy`, governs a terminal-prior collision), `with_conflict_policy` (`WorkflowIdConflictPolicy`, governs an active-prior collision, issue #685), `with_idempotency_key`, `with_queue_name`, `with_memo`, `with_search_attrs`, `with_parent_id`. Defaults: default (rendezvous) shard placement, `AllowDuplicate` / `Unspecified` id-reuse semantics, no idempotency key, the `"default"` queue.
- **`TransactionalStartOutcome`** — `#[must_use]` handle carrying `exec_id`, `workflow_name`, `workflow_id`, `state`, `created`, plus a private queue of deferred post-commit follow-ups (completion-trigger dispatch, unfinished-handler diagnostics, cancel metrics). `.finish()` is an optional latency optimization — eagerly runs those follow-ups — never a correctness requirement, since the existing periodic scanners deliver the same follow-ups if it's skipped or the process crashes before it runs.
- **Start-semantics parity (AC3):** `WorkflowInfo` defaults (`execution_timeout`, `sla` clamped to it, per-key concurrency), id-reuse / conflict policy, idempotency-key dedup, and published input-schema validation (issue #373) are all resolved and enforced identically to `POST /workflows/{name}/start` — a schema-validation failure aborts *before* any write, rolling back the caller's whole transaction along with it. `WorkflowHandleClient::with_workflows(...)` (new) registers the `WorkflowInfo` set the transactional path resolves these defaults against; `HarvestPlugin::start_harvest_runtime` wires it automatically from the runtime's own registry.
- **Sharding (AC4):** the started workflow's `ExecutionId` is derived from `options.shard` (or the default shard when unset — the single-shard deployment needs zero caller changes). No cross-shard transaction is attempted or possible: the API only ever writes on the one connection it was given.
- **Admission-gate integration (issue #618):** new `StartProducer::Transactional` — this path is **gated**, using `GateMode::CheckCached` so a raised gate durably blocks (and writes nothing for) a matching workflow name/queue/fleet, while an unrelated workflow name is unaffected by the same still-armed gate.
- **`StartSource::Transactional`** (issue #740) — every execution started through this path is attributable in `GET /workflows?start_source=transactional`, distinguishing it from `api`, `schedule`, `webhook`, etc.
- **Own idempotency implementation** (`start_workflow_transactional_idempotent`) rather than reuse of `start_or_load_workflow_execution_idempotent`: the latter unconditionally spawns its deferred follow-ups assuming its own transaction is outermost — a false assumption once nested inside a caller's transaction, since spawning before the caller's outer commit would dispatch follow-ups for work that might still roll back. The transactional variant instead queues them onto `TransactionalStartOutcome` for `.finish()` (or the periodic scanner) to pick up after the real commit.
- **`WorkflowInfo` now derives `Clone`** — safe, since every field is a `'static` primitive, an `fn` pointer, or a small `Clone` policy struct — needed so `WorkflowHandleClient::with_workflows` can own its own copy of the registry's `WorkflowInfo` set independent of the runtime's.
- Runnable example `examples/transactional_start_order.rs` (order-row insert + `fulfill_order` workflow start committing atomically, plus the rejected-input rollback path proving neither persists) and `docs/transactional-start.md` (full API reference, atomicity contract, start-semantics parity table including the currently-unsupported `TransactionalStartOptions` extension points, sharding notes, and the testing methodology).

### Invariants (AC6)

**No new `WorkflowEvent` variant. No migration.** Only the existing `WorkflowStarted` event and the existing dispatchable task-queue row are written — on the caller's own connection, inside the caller's own transaction (or a fresh one it owns). Every other non-transactional start path (plain start, signal-with-start, update-with-start, the scheduler) is untouched — this is a purely additive in-process API surface.

### Design decision: how atomicity actually holds

The mechanism is `diesel_async` 0.9.2's nested-transaction behavior: `conn.transaction(...)` on a connection that is **already** inside an open transaction issues a `SAVEPOINT` / `RELEASE SAVEPOINT`, not a fresh `BEGIN` / `COMMIT`. `start_or_load_workflow_execution_collect`'s own internal `conn.transaction()` call therefore nests correctly inside whatever transaction the caller opened, so a caller-side rollback undoes *everything* the transactional start staged — including a `WorkflowIdConflictPolicy::TerminateExisting` collision's cancellation of the prior execution and an idempotency-key reservation, which are proven never to be left orphaned/stranded/burned by a caller rollback (see test evidence below).

### Incidental discovery, documented but explicitly out of scope

While writing the `TerminateExisting`-collision regression tests, tracing `execution.rs`'s `ActiveConflictBehavior::Terminate` branch (shared, pre-existing code from issue #685 — not touched by this PR) surfaced that **every** Terminate-resolving collision (both the native `TerminateIfRunning` reuse policy and `conflict_policy = TerminateExisting`) calls `inline_cancel` (appends a `WorkflowCancelled` event, sets `state = CANCELLED`) immediately followed, in the same branch, by `replace_execution` (unconditionally overwrites `state = CONTINUED_AS_NEW`). The net observable effect is that the prior execution's *event log* records a genuine cancellation while its *state column* reads `CONTINUED_AS_NEW`. This is real, pre-existing, shared behavior unrelated to `start_workflow_transactional` and squarely out of issue #763's scope ("Out of Scope: Changes to existing non-transactional start paths — purely additive") to change; it is documented in the two collision tests below and in `docs/transactional-start.md` for whoever picks it up.

### Test evidence

`autumn-harvest/tests/integration/transactional_start_tests.rs`, 23 tests as originally shipped (34 after the post-review hardening below), executed against a real local Postgres 16 (`HARVEST_TEST_DATABASE_URL`), all green:

- **Atomicity / fault injection (AC2, AC5):**
  - `commit_makes_workflow_and_domain_row_atomically_visible`, `rollback_leaves_neither_domain_row_nor_workflow` — the canonical start-first ordering, both directions.
  - `atomicity_holds_when_domain_row_is_written_before_the_start`, `rollback_after_domain_first_write_leaves_neither_placeholder_nor_workflow` — the *other* legitimate ordering (a placeholder domain row written first, patched with the real `exec_id` once the start returns), proving atomicity holds regardless of which write comes first.
  - `fault_injection_zero_orphans_across_five_hundred_randomized_crash_points` — the AC5/Success-Metric test: **500** randomized crash points around the start boundary, asserting the domain row, the `WorkflowStarted` event, the execution row, and the task-queue row are always all-present or all-absent. **0 orphans in either direction across all 500 iterations.**
  - `outer_rollback_after_a_terminate_existing_collision_undoes_the_cancellation_too` — proves the `TerminateExisting` collision's `inline_cancel` + `replace_execution` sequence rolls back as a whole (the prior reverts to `RUNNING` with its `WorkflowCancelled` event gone) when the *caller's* outer transaction subsequently fails, even though `start_workflow_transactional` had already returned `Ok`.
- **Start-semantics parity (AC3):** `honors_workflow_info_execution_timeout_and_concurrency_key_defaults` (including the SLA-clamped-to-execution-timeout default, issue #487), `plain_workflow_with_no_declared_policies_gets_no_defaults`, `reject_duplicate_reuse_policy_rejects_a_second_start`, `conflict_policy_use_existing_attaches_without_a_second_workflow_started`, `finish_after_commit_dispatches_diagnostics_for_a_terminate_existing_collision` (asserts both the `WorkflowCancelled` event *and* the final `CONTINUED_AS_NEW` state, per the incidental discovery above), `idempotency_key_deduplicates_two_committed_starts`, `idempotency_key_is_not_burned_by_a_rolled_back_start` (a rolled-back reservation is not permanently burned — a retry with the same key still succeeds fresh), `schema_validation_failure_aborts_without_writing_anything`, `debounced_workflow_is_rejected_because_admission_cannot_be_deferred`, `batched_workflow_is_rejected_because_admission_cannot_be_deferred`, `throttled_workflow_is_rejected_because_admission_cannot_be_deferred` (all three deferred-start policies rejected independently, since a transactional start needs a synchronous `ExecutionId` a deferred admission can't provide), `unregistered_workflow_name_is_rejected` (with a DB-state assertion that nothing was written), `admission_gate_blocks_a_matching_workflow_name_and_spares_others` (a real armed `AdmissionGateCache`, issue #618).
- **Sharding (AC4):** `lands_on_the_shard_backing_the_connection_never_the_other_shard` (two genuinely separate Postgres databases), `single_shard_deployment_needs_no_with_shard_call`, `multi_shard_client_without_with_shard_is_rejected_writes_nothing`.
- **Connection discipline:** `finish_is_a_safe_no_op_when_no_follow_ups_were_produced`.

### Post-review hardening (Codex review, six P2 findings, all fixed)

**(1) Check idempotency before fresh-start validation.** The committed-replay probe (`probe_transactional_committed_replay`) previously ran *after* `validate_transactional_start_request`, so a retry of an already-committed keyed start could be rejected by a rule that only makes sense for a *fresh* admission — e.g. the target workflow's published input schema tightened, or it gained a debounce/batch/throttle policy, since the original delivery — even though the retry is replaying an already-succeeded start, not attempting a new one. This is the same issue #808 invariant `autumn-harvest-plugin::api::start_workflow` documents and enforces at the HTTP boundary. Fixed by moving the probe to the very top of `start_workflow_transactional`. Tests: `committed_replay_dedupes_despite_a_schema_that_tightened_since_the_original_delivery`, `committed_replay_dedupes_despite_a_debounce_policy_gained_since_the_original_delivery`.

**(2) Use the configured idempotency window.** The committed-replay probe and reservation hard-coded `DEFAULT_START_IDEMPOTENCY_WINDOW` (24h) instead of the operator's `HarvestBuilder::start_idempotency_window` the HTTP start path and purge logic use — so a deployment configuring a shorter/longer window would silently disagree between the two start paths on when a key expires. Fixed with a new `WorkflowHandleClient::with_start_idempotency_window`/`start_idempotency_window()` accessor pair, threaded into both the probe and the reservation. Test: `keyed_retry_honors_the_clients_configured_idempotency_window_not_the_hardcoded_default`.

**(3) Require a real outer transaction.** `start_workflow_transactional`'s non-keyed branch hard-coded `in_outer_transaction = true` when calling `start_or_load_workflow_execution_collect` — a lie when the caller passed a *bare* connection (no `conn.transaction()` wrapper), which the module docs explicitly permit. If a `TerminateExisting` pre-check cancellation committed and the replacement start subsequently failed (oversized input, a queue-DB write error, ...), the prior run was left durably cancelled with no outer transaction to roll it back, and its follow-ups (completion triggers, parent-close cascade) were never dispatched. Fixed by wrapping the non-keyed call in its own nested `conn.transaction()` unconditionally, mirroring the pre-existing `start_workflow_transactional_idempotent` pattern — on a bare connection this issues a genuine `BEGIN`/`COMMIT` around just that call, so a downstream failure reverts the cancellation on its own; nested inside a caller's own transaction it's a harmless `SAVEPOINT`/`RELEASE SAVEPOINT`. Test: `bare_connection_terminate_existing_collision_reverts_cancellation_on_replacement_failure`.

**(4) Default transactional starts to the actual shard.** An un-pinned start (`options.shard == None`) on a client built from a single-entry `ShardedDbPool`/`ShardRouter` pair whose one shard is numbered something other than 0 minted an `ExecutionId` with the bare `ShardId::UNENCODED` sentinel instead of resolving to the client's actual configured default shard. `StartWorkflowParams::shard_id()` — which persists the row's `shard_id` column, read by every shard-scoped admission gate and the idempotency purge scanner — hardcodes `0` for an unencoded id rather than consulting a router, so a write that actually landed on, say, shard 5 would silently persist `shard_id = 0`. Every other start path in the codebase (the HTTP start route, the scheduler, ...) always mints its exec id with a concretely resolved `ShardId` for exactly this reason. Fixed via a new `resolve_transactional_shard` helper resolving `options.shard.unwrap_or_else(|| self.inner.router.default_shard())` — byte-for-byte unchanged for the common `WorkflowHandleClient::single(...)` case, whose `default_shard()` is `ShardId::new(0)`. Test: `unpinned_start_on_a_non_default_single_shard_client_encodes_that_shard_not_zero` (also corrected `single_shard_deployment_needs_no_with_shard_call`'s assertion, which previously and correctly-at-the-time expected `ShardId::UNENCODED`).

**(5) Validate transactional idempotency keys.** The client stored the caller-provided `idempotency_key` verbatim, with no trim/empty/length validation — unlike the plain HTTP start route. An accidental empty or whitespace-only key became a real `(workflow_name, "")` claim in `harvest_start_idempotency` that would silently dedupe every other unrelated transactional start for the same workflow against each other, and an oversized key could exceed Postgres's ~2704-byte btree index tuple limit and abort the caller's own transaction with a raw database error. Fixed with a new shared, core-crate `start_idempotency::validate_start_idempotency_key` (mirroring `autumn-harvest-plugin::api::validate_start_idempotency_key`'s trim/reject-empty/cap-at-512-bytes logic), run first, before anything else, normalizing the key in place so every later read sees the same trimmed value. Tests: `empty_idempotency_key_is_rejected_writes_nothing`, `whitespace_only_idempotency_key_is_rejected_writes_nothing`, `oversized_idempotency_key_is_rejected_writes_nothing`, `idempotency_key_at_exactly_the_length_cap_is_accepted`, `idempotency_key_is_trimmed_before_use`.

**(6) Require an outer transaction for atomic starts (documentation correction).** A follow-up review of fix (3) above found the rustdoc on `start_workflow_transactional` overclaimed atomicity for a genuinely bare (non-transaction-wrapped) connection: it stated the workflow start's writes "live only inside whatever transaction is open on `conn`... if the caller later rolls that transaction back, none of them exist" unconditionally. That is only true when the caller already has a transaction open on `conn`. On a bare connection, `diesel-async 0.9.2`'s own transaction manager (`transaction_manager.rs`, branching on `TransactionManagerStatus::transaction_depth()`) has nothing to nest into and issues a real, top-level `BEGIN`/`COMMIT` of its own — the exact mechanism fix (3) relies on for the `TerminateExisting` collision's internal atomicity — that fully completes *before* `start_workflow_transactional` returns. By the time the caller has `Ok(outcome)`, the start is already durably committed; there is nothing left "open" for a caller write made afterward on that same connection to share a rollback boundary with. So a bare connection provides Harvest's own *internal* multi-statement consistency (fix (3)'s guarantee), but **not** dual-write atomicity with the caller's own domain write — the very thing this whole feature exists to provide. Rejecting bare connections outright was considered and declined: it would break the legitimate, narrower "start now with Harvest's own internal atomicity, no domain write of my own to tie it to" use case the fix-(3) test already relies on and documents. Fixed as a documentation correction instead (the reviewer's own suggested alternative remedy) — the rustdoc on `WorkflowHandleClient::start_workflow_transactional` now explicitly distinguishes the two connection modes and their differing guarantees, and `docs/transactional-start.md` gained a "Connection discipline" section plus a fourth numbered item in its "Testing" section (delivering on what the test file's own module doc had promised in its "Section 4" reference but the prose docs never actually wrote). Test: `bare_connection_commits_the_start_immediately_no_dual_write_atomicity` — proves the boundary concretely (the started execution is already visible from a completely independent connection with zero explicit `COMMIT` from the test, and a later domain-write failure on the same bare connection does not roll the start back).

Both (4) and (5)'s new logic was extracted into small private helper methods (`resolve_transactional_shard`, `normalize_transactional_idempotency_key`) to keep `start_workflow_transactional` under the workspace's `too_many_lines` clippy lint, following the file's own established "split out purely to keep that function under the line-count lint" convention (already used by `resolve_transactional_queue_name`, `resolve_transactional_start_defaults`).

Full local verification, all green: `cargo fmt --check`; `cargo clippy -p autumn-harvest --all-features --tests -- -D warnings` (CI's exact invocation); `cargo check -p autumn-harvest --example transactional_start_order --features db`; the full 34-test suite (`--test-threads=1` against Postgres 16).
