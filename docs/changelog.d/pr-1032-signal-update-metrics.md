## Phase 3.53 — Signal & update lifecycle metrics (issue #684)

**Observability** (implemented): Six new `MetricsRecorder` counters give operators first-class, alertable visibility into the signal- and update-handler lifecycle, closing the gap where signal delivery/consumption and the update admit→complete/fail path had no metric surface. Modelled exactly on the issue #519 `record_workflow_terminal` recipe: additive no-op-default trait methods + a `metrics_rs_adapter` bridge + coverage tests. **AC7 invariant: no new `WorkflowEvent` variant, no migration, no macro-path change** — this is a pure additive-metrics slice.

The six counters (all bounded labels; `execution.id` is never a label, per ADR-0001 §7):

- `harvest.signal.received` (`workflow`, `queue` — see the Codex P2 cardinality note below; the signal `name` is NOT a label) — a `SignalReceived` event was durably delivered into a workflow's history. Emitted once per delivered signal at the single **live-only** delivery choke point (`ingest_due_timers_and_signals`, beside the existing `harvest.signal.deliver` span in `worker::process_workflow_task`), iterating `prepared.signals_delivered`. Each signal is marked consumed in `harvest_signals` so it appears in the delivered list exactly once; never emitted on replay.
- `harvest.signal.unhandled` (`workflow`, `queue` — see the Codex P2 cardinality note below; the signal `name` is NOT a label) — a delivered signal was never consumed (no `wait_for_signal`/`receive_signal`, no #546 push handler claimed it) by the time the run reached a **Completed or Failed** terminal outcome. Backed by new `HistoryMatcher::unconsumed_signals_by_name`, which mirrors `has_non_lifecycle_unconsumed`'s two sources (cursor scan + `pending_signals` buffer) restricted to `SignalReceived` and grouped by name, honoring the issue #476 lost-signal-or-deadline-race carve-out (`late_race_signal_events`) and #546 push-handler consumption (`claim_pending_signal` marks consumed). **Emission is post-commit, in the worker's `Persisted` arm — the same discipline as `harvest.update.completed/failed` — so it counts DURABLE terminal outcomes only, not the executor:** the executor's `drive_workflow` terminal arms compute the map (after `flush_pending_signal_handlers`, so #546 push handlers claim first — the only place the driven matcher's authoritative consumed-set exists) via `WorkflowContext::unhandled_signals` and **carry it out on `WorkflowOutcome::Completed`/`Failed` (a new `unhandled_signals: BTreeMap<String,u64>` field)**; the **worker** collects the map before the persist transaction (`outcome_unhandled_signals`) and emits it via `emit_unhandled_signal_metrics` **only in the post-commit `Persisted` arm**, alongside the update-result emission. Because that arm is reached only after a successful commit, the emit is downstream of **both** the #603 ND-block gate (an ND-carrying `Failed` early-returns via `block_workflow_for_non_determinism` before persist, so an ND-blocked/re-driven cycle never counts) **and** `check_paused_and_park` (a claimed-then-paused race returns via the `ParkedPaused` transaction result, and a persist failure via the `Err` arm — neither reaches the emit). A retry/resume of such a discarded cycle therefore **cannot double-count** — closing the Codex P2 edge where the earlier pre-persist placement (co-located with `record_workflow_terminal`) incremented the counter without a durable terminal event/state. Emitting in the executor (as an even earlier cut did, via `report_unhandled_signals`) was **upstream** of the ND gate entirely and would re-fire unboundedly during a persistent ND-block. **Known limitation (deliberate, documented):** covers only **Completed and Failed** (a run that reaches a *graceful* terminal via its own logic) — the paths with a driven matcher. **`TIMED_OUT` / `CANCELLED` / `TERMINATED` / parent-close-cascade / history-cap-failure runs with an undrained signal are NOT counted** (a scanner/operator force-kill has no driven matcher to reconstruct the consumed-set, and reconstructing it would need a re-drive; a partial/inaccurate count on a watched SLO metric is worse than none). For the stuck-timed-out case, use the workflow-timeout counter (`harvest.workflow.timeout`) + the stack API instead.
- `harvest.update.admitted` (`workflow`, `name`) — a workflow update was durably admitted (`UpdateAdmitted` appended). Emitted **post-commit** at the single admission choke point `store::admit_update_event`, which gained an `Option<&dyn MetricsRecorder>` param and now returns the resolved `workflow_name`. Threaded through its callers: the HTTP `admit_update` handler and Vantage-UI submit pass the runtime recorder; **the in-process typed client (`handle::execute_update_in_process`) now passes the recorder too** — the client gained a `metrics: Arc<dyn MetricsRecorder>` field wired from the runtime at both `WorkflowHandleClient` construction sites (default no-op), because an in-process admit's *completion* runs through the worker (which emits update.completed/failed), so admitting without recording admitted would leave that path asymmetric; `update_with_start` passes `None` and emits at its own **outer-commit** boundary (gated on `outcome.update_admitted`) so a rollback never over-counts.
- `harvest.update.rejected` (`workflow`, `name`) — a workflow update was rejected by its registered validator before admission (a durable pre-admission `422`). Emitted at the two — and, by an independent audit of every `HarvestError::UpdateRejected` construction and every registered-validator invocation, the **only** — durable validator-rejection sites: the `admit_update` and `update_with_start` HTTP handlers. Scope is deliberately limited to **validator** rejections; non-`RUNNING`/paused admission-state conflicts are surfaced as caller errors, not counted here. Not emitted in `WorkflowContext::validate_update` (replay-driven) or `execute_update_in_process` (runs no validator). The scheduler's reuse of the `UpdateRejected` variant for DAG manual-trigger deferral is unrelated and untouched.
- `harvest.update.completed` (`workflow`, `name`, `queue`) / `harvest.update.failed` (`workflow`, `name`, `queue`) — an admitted update's handler returned success/error (`UpdateCompleted`/`UpdateFailed`). Emitted **post-commit** via the pure, unit-tested `collect_update_result_metrics` helper, which resolves each `RecordUpdateResult` command's `update_id` → update name from the `UpdateAdmitted` events in the loaded history (the command carries only the id). **Fires on every persist path (terminal, suspend, continue-as-new, and the two inline external-signal suspension branches), not just the terminal one.** The primary main-transaction emission (worker `Persisted` arm, post-commit) reads its `RecordUpdateResult`s via the new pure `update_result_command_source(&outcome, &pending_cmds)`: on a **Suspended** outcome the results live in `outcome.commands` (the executor returns `(Suspended{commands}, vec![])`, so `pending_cmds` is empty), on terminal/CAN they ride in `pending_cmds`. An earlier cut collected from `pending_cmds` only and therefore **undercounted the common case** — an update completes and the long-running workflow loops back to a `wait_for_signal`/activity and suspends. The two inline external-signal branches persist their update results outside the main transaction and strip them from the reconstructed suspension, so they emit inline (post-autocommit) via the shared `emit_update_result_metrics` helper. **No emit on the paused-park discard path** (the `ParkedPaused` transaction result returns before the `Persisted`-arm emission). Exactly-once: `RecordUpdateResult` is produced once on live execution (replay short-circuits in `execute_admitted_update`).

**Emission discipline:** `record_signal_received` is live-frontier-only by construction (delivery choke point). `record_signal_unhandled` is emitted by the worker **post-commit, only in the `Persisted` arm** when a terminal outcome carries the map — the same durable-commit gating as `harvest.update.completed/failed`, so a `ParkedPaused` discard or a persist failure never over-counts; `WorkflowReplayer` drives the strict/canary executor path (a different function that never populates the map / never reaches the worker), so a replay of an already-terminal history emits zero unhandled samples — AC2, pinned by `replay_of_terminal_history_never_emits_signal_unhandled`. The update counters emit at the same post-commit `Persisted` boundary.

Bridged in `metrics_rs_adapter` (`MetricsRsRecorder`) using the existing `METRIC_LABEL_WORKFLOW`/`METRIC_LABEL_NAME`/`METRIC_LABEL_QUEUE` constants (the two signal counters use `METRIC_LABEL_WORKFLOW`/`METRIC_LABEL_QUEUE` only — no `name`, per the Codex P2 cardinality note below). Two new starter-pack alert rules (`harvest_update_rejected_rate`, `harvest_signal_unhandled_rate` — thresholds documented as starter defaults, not universal SLOs) with full runbook sections; six new dashboard panels (a "Signal & update lifecycle" row) in `docs/dashboards/starter-pack-v0.1.0.json`; ADR-0001 §7 catalogue and `docs/telemetry.md` updated.

Tests, TDD red→green (verified RED→GREEN by reverting each fix): `metrics_coverage.rs` (RecordingMetrics impls + reachability + cardinality + exact-bounded-label test); `replay.rs` unit tests for `unconsumed_signals_by_name` (undrained/consumed-by-wait/consumed-by-push-handler/lost-race/multiple-same-name/stashed-but-unconsumed); `executor.rs` tests via `run_workflow_with_state_advancing_clock` proving the terminal outcomes **carry** the map and the executor **emits nothing** (Completed/Failed carry, Suspended does not, recorder sees zero samples); `context.rs` unit tests for the `unhandled_signals` reader; `worker.rs` unit tests for `collect_update_result_metrics` and `update_result_command_source` (the pure test that would have caught the suspend-path undercount), plus `outcome_unhandled_signals_reads_terminal_maps_and_is_empty_otherwise` / `emit_unhandled_signal_metrics_fires_once_per_occurrence` / `emit_unhandled_signal_metrics_is_a_noop_for_the_empty_collected_map` (the pure companions to the Codex-P2 post-commit move: the terminal map is captured before persist, and the `Persisted`-arm emit is a no-op for the empty map a non-terminal / discarded cycle carries); `metrics_rs_adapter.rs` label-content bridge test for all six; `replayer_tests.rs` AC2 test (replay path never emits `signal.unhandled` across ≥5 cycles); doc-enforcement registries in `dashboard_pack_docs.rs`/`alert_pack_docs.rs` extended. DB/worker integration tests: `metrics_integration.rs::update_completed_metric_fires_on_the_suspend_path` (an admitted update that completes while the workflow SUSPENDS emits exactly one `update.completed`) and `nd_block_tests.rs::{genuine_terminal_with_undrained_signal_emits_signal_unhandled, nd_blocked_cycle_does_not_emit_signal_unhandled}` — env-redirectable (`HARVEST_TEST_DATABASE_URL`) so they run against a migrated Postgres without Docker; the suspend-path and genuine-terminal-emits tests were executed green against a real local Postgres 16 (and confirmed RED against a reverted fix), while the ND-block-suppression test (which needs the testcontainer nd-block harness) is compile-checked, its suppression additionally guaranteed by the post-commit `Persisted`-arm placement being strictly downstream of the #603 ND-block gate (the base `divergent_replay_blocks_instead_of_failing` test already asserts `terminal_failed_count == 0` on an ND-block, so the still-later `Persisted` arm is never reached either).

**Post-review hardening (Codex P2):** `harvest.signal.unhandled` was initially emitted pre-persistence, co-located with `record_workflow_terminal` (#519), *before* the persist transaction and *before* `check_paused_and_park` could return `ParkedPaused`. On a claimed-then-paused race or a persist failure the counter incremented without a durable terminal event/state, and a retry/resume of that discarded cycle counted the same unhandled signal again. Fixed by mirroring the `harvest.update.completed/failed` discipline exactly: the `unhandled_signals` map is collected into a local (`outcome_unhandled_signals`) *before* the persist transaction moves `outcome`, and `emit_unhandled_signal_metrics` is called *only* in the post-commit `Persisted` arm — reached only after a successful commit, downstream of both the #603 ND-block gate and `check_paused_and_park`. `record_workflow_terminal` (#519) is untouched and keeps its own pre-persist placement.

**Post-review hardening (Codex P2 — cardinality):** the initial cut labeled `harvest.signal.received` / `harvest.signal.unhandled` with a `name` (signal name) label. Signals are delivered via the **free-form** route `POST /workflows/{id}/signal/{signal_name}` — the `signal_name` path segment is caller-controlled and, unlike activity names or `#[update]` handler names, has **no declared registry** to bound it, so a caller using per-entity / dynamic signal names would create unbounded metric series (worst for `signal.unhandled`, whose names are by definition the mismatched / unlistened-for ones), violating the ADR-0001 §7 cardinality contract. **Fixed by dropping the `name` label from both signal counters** — they are now labeled `workflow` + `queue` only (both bounded). The signal name remains a span-only attribute on `harvest.signal.deliver`. For `signal.unhandled`, the worker now **sums** the terminal outcome's per-name unconsumed map (`emit_unhandled_signal_metrics`) into one increment per unconsumed occurrence against the single `(workflow, queue)` series, preserving the total unconsumed volume without the unbounded dimension. Per-signal-name diagnostics are explicitly out of scope for this slice (use the per-workflow stack / open-awaitables API). The `MetricsRecorder::record_signal_received`/`record_signal_unhandled` trait signatures dropped the `signal_name` parameter, so a caller-free-form name cannot reach these counters by construction.

**AC3 reconciliation (update names kept; bounded where correctly feasible).** The four `harvest.update.*` counters keep the `name` label per AC3. A boundedness audit found a genuine unbounded risk: the raw route `POST /workflows/{id}/update/{name}` admits **any** name (the validator lookup is best-effort, so an *unregistered* free-form name falls through and is durably admitted), reaching `harvest.update.admitted` with the raw name; the same admitted name then fails the worker's handler lookup (`"update handler '<name>' not found"`), reaching `harvest.update.failed` with the raw name. **Crucial constraint found while fixing it:** update handlers register via *two* paths — declarative `#[update]` (→ `registry.update_handlers`) **and** imperative `ctx.register_update_handler` (→ the per-execution `WorkflowContext`, the common pattern, e.g. `metrics_integration::update_then_suspend_workflow`) — and only the declarative set is visible outside execution. **Bucketing against `registry.update_handlers` would therefore mislabel every legitimately imperatively-registered update as `__unregistered__`** (a worse regression than the theoretical risk; it also fails the existing `update_completed_metric_fires_on_the_suspend_path` label assertion). So the boundedness is scoped to where it can be done *correctly*:

- **`update.failed`** (the concrete unbounded vector): bounded via the **result**, not the registry. A genuinely-unregistered name is exactly the one whose result is the pure, exact `"update handler '<name>' not found"` error minted by `execute_admitted_update`; the worker's `collect_update_result_metrics` (new pure `is_unregistered_update_failure(name, result)` helper) buckets **only** that case to the new `UNREGISTERED_UPDATE_NAME = "__unregistered__"` sentinel. Every real handler — declarative **or** imperative — keeps its name, because the discriminator is the not-found result, not the declarative registry. This collapses a hostile `POST /update/{RANDOM}` storm's failed samples to one series.
- **`update.completed`**: inherently bounded — a completed update always ran a real handler, so its name is the app's real handler set.
- **`update.rejected`**: already bounded — validator rejection fires only for a *registered* handler.
- **`update.admitted`**: **documented residual.** The admission site has no result to key on and cannot see imperative handlers, so it cannot bound the name without mislabeling legitimate imperative updates; the raw name is kept. A hostile-admit storm is instead surfaced by the correlated, now-bounded `update.failed{name="__unregistered__"}` series (every unregistered admit produces a not-found failure). Flagged for the spec owner; a real fix would need either an admission-time reject of unresolvable names (a behavior change that would break imperative registration) or a declared-name registry that captures imperative handlers.

The durable `UpdateAdmitted` event always carries the **raw** name (the workflow needs it to resolve its handler); only the `failed` metric label is bucketed. **PM review note:** signals are labeled `workflow`+`queue` only (deliberately no per-name diagnostic); update `admitted` keeps a documented raw-name residual; if per-signal-name observability or airtight `admitted` bounding is later required, both need a bounding mechanism (a declared-name registry that also captures imperative handlers) that does not exist today.
