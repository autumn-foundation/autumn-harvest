## Phase — Post-commit completion-trigger supersede metrics and an observable nested-admission residual (issue #1197)

Follow-up to #811 (PR #1196), closing the two residuals that were deliberately deferred out of that slice rather than rushed in.

### Item 1: completion-trigger supersede metrics can no longer escape a rollback

`completion_trigger::evaluate_triggers_for_execution`'s same-shard inline trigger start called `execution::start_or_load_workflow_execution_with_metrics`, which emits `harvest.concurrency.superseded` and the incumbent's `harvest.workflow.terminal{outcome="cancelled"}` **at return** — inside the source workflow's still-open terminal transaction. If later trigger evaluation or terminal processing rolled that transaction back, both counters had already fired for a cancellation that never became durable. Bounded to rolled-back terminal transactions and strictly better than the pre-#811 state (an unconditional under-count), but not the correct guarantee.

**Fix, per the design the issue itself sketched.** A new `completion_trigger::evaluate_triggers_for_execution_collecting(conn, exec_id, state, metrics, pending: &mut Vec<StartCancelledRun>)` calls `execution::start_or_load_workflow_execution_collect` (the metrics-collecting-not-emitting primitive) instead of `_with_metrics`, and pushes the collected `StartCancelledRun` samples onto `pending` instead of emitting them. `evaluate_triggers_for_execution` (unchanged signature — the 56 pre-existing test call sites and any call site without a convenient post-commit hook stay untouched) now delegates to the collecting variant with a throwaway `Vec`, so it silently never emits these two counters — documented, intentional, and byte-identical to the pre-#811-metrics state for that path.

Of the 15 production call sites of `evaluate_triggers_for_execution` (6 in `worker.rs`, 3 in `timeout.rs`, 1 in `poison_pill.rs`, 5 in `execution.rs`), the 10 that thread a real, potentially-`Some` metrics recorder (`worker.rs`, `timeout.rs`, `poison_pill.rs`) were swept to the collecting variant, each threading its `pending_cancel_metrics` out to the exact point in that call's own commit chain already proven post-commit (the same point every one of them already spawns `DeferredTriggerStart`s or emits its own other terminal metrics), then calling `execution::emit_start_cancel_metrics` there. Partial adoption among THOSE 10 was rejected deliberately — a site left on the old variant would silently regress to the under-count with no signal. The remaining 5 (`execution.rs`'s `inline_cancel`, `cancel_workflow_execution_collect`, `cascade_cancel_detached_child`, `cascade_terminate_detached_child`, `terminate_workflow_execution_collect`) always pass `metrics: None` today — they were left calling the plain wrapper unchanged, since its own throwaway collector is already byte-identical to what a collecting-variant call with nothing to collect would do; converting them would only have added dead-variable noise with no correctness benefit (caught in review and reverted from an earlier draft that had converted all 15 uniformly).

**Acceptance, proven directly against real Postgres, not just reasoned about:** `completion_trigger_supersede_rollback_never_emits_metrics` wraps the collecting call in a `conn.transaction()` that deliberately returns `Err` right after the trigger evaluation succeeds (simulating "later processing rolls the transaction back") and asserts the incumbent is still RUNNING and the metrics recorder saw nothing. `completion_trigger_supersede_emits_the_counters` (updated) and `evaluate_triggers_for_execution_plain_wrapper_discards_supersede_metrics` (new) pin the commit-path and legacy-wrapper halves of the contract respectively. All three ran against a real, migrated Postgres 16 instance (not just compile-checked) and pass, alongside the full pre-existing `concurrency_supersede_tests` suite.

### Item 2: nested self-referential admission residual is now observable

Cancelling an incumbent runs its terminal chokepoint, which can synchronously start a completion-trigger target that also declares `on_conflict = "cancel_running"` on the same key. That nested admission sees the outer admission as a *protected* in-flight run (via the `ADMITTING` task-local re-entrancy guard) — it counts toward the population (fixed in #1196) but can never be selected for shedding. With `limit = 1` and no other candidates, the nested pass computes an overflow of 1, has nothing it may shed, and both runs commit — the key is left transiently over its declared limit until the next ordinary admission for the key self-heals it.

Of the three directions the issue sketched (registration-time rejection of self-referential shapes, a bounded post-commit reconcile sweep, or promoting the existing `tracing::warn!` to a counter), this ships the third: it is the only one that adds no new lock-ordering surface to the terminal-transaction hot path and needs no new convergence analysis — the population still converges exactly as it did before, and the residual is documented as an accepted, self-healing transient.

`telemetry::METRIC_CONCURRENCY_RESIDUAL_OVER_LIMIT` (`harvest.concurrency.residual_over_limit`, labeled `workflow` + the bounded `gap`) is emitted from `concurrency::supersede_inner` alongside the existing warn. The one reachable code path to this branch runs inside `execution::cancel_workflow_execution_collect`'s internal trigger evaluation, which — like every cancel/terminate/parent-close-cascade chokepoint — has no caller-supplied metrics recorder in scope; emission falls back to the process-global `admission_gate::global_admission_metrics()` recorder via a new shared `admission_gate::resolve_metrics_with_global_fallback` helper. That helper replaces a near-duplicate tuple-match idiom this fix originally inlined a second time (flagged in review) — `completion_trigger.rs`'s admission-gate-block branch, the one other place needing this exact fallback (issue #618, F-round5), now calls the same helper. Without the fallback, the new counter would be wired up but structurally unreachable with a real recorder in production.

**Proven end-to-end against real Postgres:** `nested_self_referential_admission_emits_residual_over_limit_counter` registers a workflow whose own completion trigger targets itself on the same key, drives the exact nested-admission scenario (incumbent A superseded by admission B, whose cancellation of A synchronously starts C on the same key), and asserts both runs commit (the key sits at 2 non-terminal runs against a limit of 1) and the counter fires exactly once with `gap = 1`.

**Post-review fix (Codex round 1, P1).** The documented full-surface `metrics_rs_adapter::MetricsRsRecorder` overrides `record_concurrency_superseded` but had no override for the new `record_concurrency_residual_over_limit`, so it silently resolved to the trait's no-op default — any deployment using this adapter (the one every doc example in the module points at) would never actually export the new counter. Added the missing bridge (`METRIC_LABEL_WORKFLOW` + new `METRIC_LABEL_GAP`), plus a label-content regression test mirroring the existing `bridges_concurrency_superseded_with_workflow_label_only` test exactly.

### Scope

Metrics/observability only — no new `WorkflowEvent` variant, no migration, no schema change, no behavior change to the `Defer` (default) strategy or to which runs get superseded. `docs/telemetry.md`'s metric catalogue and `tests/integration/metrics_coverage.rs`'s reachability/cardinality coverage were updated for the new counter (workflow + gap labels only — the concurrency key is never a label, per ADR-0001 §7, matching `harvest.concurrency.superseded`'s existing rule).
