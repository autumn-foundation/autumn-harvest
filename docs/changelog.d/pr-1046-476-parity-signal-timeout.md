**#476-parity — signal-or-deadline race follow-ups (from PR #1029 review).** Two fixes to the issue #476 `receive_signal_timeout` / `wait_for_signal_timeout` machinery, porting fixes already made to the issue #779 child-timeout twin (PR #1029). `context.rs`-only plus one pure read-only `replay.rs` helper; **no new `WorkflowEvent` variant, no migration.** (1) **Timer-retention leak on signal-win:** the still-armed `__signal_timeout:{seq}:{name}` durable timer was left `fired=false` in `harvest_timers` forever (a completed workflow's task is never re-claimed to ingest `TimerFired`, and `retention::should_skip_candidate` treats any pending timer as an inflight dependency), permanently pinning the run against retention. The `SignalOrTimerMatch::SignalWon` arm now pushes `WorkflowCommand::CancelRaceLosers { timers: [timer_id] }` (applied by `worker::apply_race_loser_cancellations` → `queue::delete_pending_timer`), **gated on the new pure `HistoryMatcher::history_contains_timer_started(&timer_id)`** so the stashed-signal-before-race short-circuit (which records no `TimerStarted`) emits no spurious teardown — a discriminator the child twin doesn't need (a winning child always records `ChildWorkflowStarted`+`TimerStarted`). The redundant `CancelRaceLosers` push in `race_timer_signal_impl` was removed (exactly one teardown per race-win). Re-pushing on every strict-replay cycle is divergence-free (`CancelRaceLosers` appends no event; `delete_pending_timer` is idempotent). Inherited residuals — a workflow-handler panic before persist (#782) or a history-hard-cap seal on the same cycle drops the pending teardown — documented not fixed, identical to the twin. (2) **Canary-frontier false non-determinism:** `match_signal_or_timer`'s `InProgress` arm errored unconditionally under `strict_replay`, so a deploy replay canary (`run_workflow_canary`) over a parked signal-timeout race false-reported non-determinism. Now suppressed under `self.canary_mode && at_frontier` (`at_frontier = !m.has_non_lifecycle_unconsumed()`), byte-identical to the child twin's `InProgress` guard; non-canary strict `WorkflowReplayer` runs still error (fixture-problem detection intact) and a genuine `Diverged` result always errors. (3) **Over-deadline reorder — deliberate refute:** unlike child terminals (appended out-of-band by worker child-wake / operator cancel-terminate / child execution-timeout), signals have no out-of-band `SignalReceived` append — `send_signal` only queues a `harvest_signals` row and wakes; `SignalReceived` is materialized solely by `ingest_due_timers_and_signals`, which atomically interleaves signal-vs-deadline by DB clock via `merge_wake_events` (`received_at < fires_at` ⇒ signal-first) — so the twin's `materialize_due_child_timeout_deadlines` hazard is structurally unreachable. Documented as a rustdoc asymmetry note on `wait_for_signal_timeout`; the existing `signal_timeout_timeout_branch_with_ignored_late_signal_replays_succeeded` replayer test already pins the "late signal after `TimerFired` loses" contract. **This supersedes the stale Phase 3.24 note** that "`wait_for_signal_timeout` itself still leaves its timer armed on signal-win — the same latent retention leak, tracked as a separate follow-up." Tests (red→green, no-DB): two `context.rs` unit tests (exactly-one / zero teardown), a `history_contains_timer_started` matcher test, four `replayer_tests.rs` canary-parity tests.
