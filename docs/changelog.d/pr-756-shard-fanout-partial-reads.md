## Partial availability for cross-shard fan-out READ endpoints (issue #756)

Before, a single unreachable shard's pool turned every cross-shard **read** endpoint into a whole-request `500`: each fanned-out loop did `acquire_conn(shard_pool).await?` inside `iter_shards()`, so one down shard `?`-propagated into a top-level error even though the other shards' data was readable. Now these endpoints **collect-and-continue**: a reachable shard's rows still flow, an unreachable shard is named in a machine-readable `unavailable_shards`, and the endpoint returns `200 OK` with the union plus a `status` verdict rather than failing wholesale. **Writes keep strict failure semantics**, and the single-execution business-id resolver (#805) keeps its `503`-to-avoid-false-`404` behavior.

**Reuses the existing `shard_fanout` scaffold** rather than reinventing partial-availability. New shared, pure, unit-tested helper `shard_fanout::collect_fanout_rows(observations) -> FanoutRows<R>` (`{ rows, status: FanoutStatus, unavailable_shards: Vec<UnavailableShard> }`) flattens per-shard `ShardObservation<R>`s into the union of reachable rows plus a `complete`/`partial`/`unavailable` verdict, alongside the existing `expected_shards`/`pools_by_shard`/`summarize_shard_errors`/`FanoutStatus`/`UnavailableShard` used by `workflow_count`/`usage`/`workflow_reachability`. A new async `api.rs::observe_shards(api_state, query_shard)` helper drives the collect-and-continue fan-out across `expected_shards` (so a router-known but pool-less shard mid a shard-add rollout is reported `unavailable`, never silently omitted), and `api.rs::fanout_list_json(items_key, rows, status, unavailable)` serializes the conditional envelope. The duplicate `api::UnavailableShard` struct (structurally identical to `shard_fanout::UnavailableShard`, used by the external-handoff coverage) was removed so the partial-availability shape is single-sourced.

**Response-shape design — conditional envelope for bare-array endpoints, additive fields for object endpoints (deviation from the initial "envelope-always" sketch, driven by AC3 + a large consumer audit).** The four legacy **bare-array** list endpoints — `GET /workflows` (standard default + the `?no_progress_minutes` stalled loader), `GET /workers`, `GET /admin/schedules`, `GET /dead-letters` — keep their **byte-for-byte bare-array shape on the happy path** (every shard reachable) and only switch to the `{ <items>, status, unavailable_shards }` envelope **when degraded**. This is the literal reading of AC2 ("*every degraded* response carries the indicator") + AC3 ("no breaking change for existing clients on the happy path"): wrapping the default bare array unconditionally would (a) be a genuine breaking change for external clients that parse the default `GET /workflows` array — which AC3 forbids — and (b) break ~57 internal test assertions across 6+ files (`workflow_filter_integration.rs`, `stalled_workflow_tests.rs`, `api_scheduler_integration.rs`, `batch_operations_integration.rs`, `build_routing_ui_integration.rs`, `legal_hold_integration.rs`) that parse those responses via `.as_array()`. The three **object** shapes get the two fields **additively (always present, `complete`/empty on the happy path)**: `GET /workflows?paginated` (`WorkflowListPage` gains `status` + `unavailable_shards`), `GET /workers/health` (`FleetHealth` fields stay top-level, `status` + `unavailable_shards` ride alongside via a serde-flatten wrapper — no field collision, core `FleetHealth` untouched), and `GET /dead-letters/aggregate` (the pre-#385 hard-`?` fan-out is now collect-and-continue; `DlqAggregateResponse`'s fields stay top-level with the two additive fields — core `merge_dlq_aggregates` unchanged). The `GET /dead-letters` runbook-enrichment secondary read was also made best-effort (skip a shard that goes unreachable mid-request rather than `500`).

**Consumer audit finding:** the Vantage UI (`ui.rs`) queries the shard DBs *directly* (it does not consume these HTTP JSON endpoints), so wrapping the JSON never affects UI rendering — the only internal Rust caller of `load_workflows_from_shards` (the UI workflow list) was updated to read `.executions` and now shows reachable-shard rows on a partial read. The `harvest` CLI is a generic passthrough that renders whatever JSON returns; the four `workflow list`/`worker list`/`schedule list`/`dlq list` subcommands now render a `WARNING: cross-shard read is partial; N shard(s) unavailable: <id>: <reason>, …` notice line above the data (new `fanout_partial_notice` helper in `render_response`, mirroring `format_usage_table`'s unavailable-shard block), only when the body is a degraded envelope — the happy-path bare array renders unchanged.

**Scope:** Tier 1 (the seven AC1-named loaders) is fully converted: `load_workflows_from_shards` (→ `WorkflowFanoutPage` + pure `build_workflow_fanout_page`), `load_stalled_workflows_from_shards` (→ `FanoutRows` + pure `build_stalled_fanout`), `list_schedules` (+ pure `build_schedule_fanout`; the internal strict `load_schedules_from_shards` used by `GET /dags` is left strict and untouched), `load_dead_letters_from_shards` (+ pure `build_dead_letter_fanout`), `aggregate_dead_letters`, `list_workers_handler`, and `workers_health`. Tier 2 (`GET /audit`, `GET /workflows/summaries`, `GET /admin/schedules/decisions`) is **deferred** to keep the PR reviewable and the contract churn bounded — each is a clean candidate for the same pattern but adds contract/CLI/test surface; noted as follow-up. The internal `query_running_count` scheduler read is deliberately left fail-loud (it's a correctness counter, not an operator read).

**No new `WorkflowEvent` variant, no migration, no shard-routing change** — this is entirely a plugin-layer read-path shape change. The eight cross-shard write loops (`batch_reset_workflows`, `create_completion_trigger`, `set_schedule_paused`, `delete_schedule`, `bulk_replay_from_shards`, `redrive_from_shards`, `bulk_discard_from_shards`, `replay_dead_letter_from_shards`) and the #805 `resolve_workflow_by_business_id` resolver were **not** touched.

**Contract (AC6):** the two always-object endpoints (`/workers/health`, `/dead-letters/aggregate`) list `status` + `unavailable_shards` in both `management_api_response_fields()` and `docs/api-contract.json` `success_response.fields`; the four conditional bare-array endpoints stay `free_form`/`None` (accurately: the happy-path response *is* a bare array) with the degraded envelope documented in each route's `success_response.description`. `contract_version` bumped `1` → `2` (additive). The `contract_regression` cross-check (code registry ↔ JSON) stays green.

**Tests:** four new pure unit tests for `collect_fanout_rows` (all-reachable → `complete` + row union; one-error → `partial` + named shard + other shards' rows present; all-error → `unavailable`; empty → `unavailable`) in `shard_fanout.rs`; five CLI unit tests for `fanout_partial_notice` + `render_response` (bare array → no notice; empty `unavailable_shards` → no notice; degraded envelope → notice naming shard+reason; `workflow list` renders notice above data; happy-path bare array → no notice). New DB/HTTP integration suite `autumn-harvest-plugin/tests/fanout_degradation_integration.rs` (dual-mode: `HARVEST_TEST_DATABASE_URL` or testcontainers): `GET /workflows` partial names the down shard + returns the reachable-shard run (AC7); happy path returns an unchanged bare array (AC3); `/workers`, `/admin/schedules`, `/dead-letters`, `/dead-letters/aggregate`, `/workers/health` all degrade to `partial` naming the down shard (AC1/AC2); a cross-shard **write** still fails `>=500` on a down shard (AC4); the #805 by-id read still `503`s (AC5). Registered in `.github/ci/integration-suites.txt` (one sorted line) for the Docker-backed Linux CI run. **Runbook (AC8):** a "Partial cross-shard list reads" stanza in `docs/runbooks/harvest-alerts.md` documenting the healthy-degradation contract and pointing at `GET /admin/shards/health`.
