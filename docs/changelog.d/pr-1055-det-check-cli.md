**Post-review hardening (Codex P1 — module-scoped workflows).** The initial `extract_all_functions` rewrite tracked a **flat** brace-depth counter and skipped every line at depth `> 0`, which conflated a `mod NAME { … }` opener with an `impl`/`fn`/`struct` block — so a `#[workflow]` (or its first-party helper) declared inside a Rust module was **never scanned**, a broad false-negative: `harvest det-check .` could pass despite hard-blocker code in module-scoped workflows. **This was a regression introduced by #778's rewrite** — the superseded `extract_workflow_bodies` on trunk scanned for `#[workflow]` at any brace depth and therefore did scan module-nested workflow bodies (it simply lacked transitive helper resolution). The fix makes extraction **module-aware**: a `Vec<ScopeKind>` scope stack classifies each opening brace as transparent `Module` (`mod NAME { … }`, keep item-scanning inside, at any nesting depth) or `Opaque` (`impl`/`trait`/`struct`/bare block, skip contents), so module-scoped `#[workflow]` entry points and their module-scope helpers are scanned for direct and one-hop transitive violations while **methods inside `impl`/`trait` blocks remain excluded** (the #386 boundary — never indexed as free helpers, a `self.method()`/`Type::method()` callee is never resolved). `#[activity]` bodies remain unscanned at any nesting; a `fn` body's internals are still consumed wholesale by `extract_fn_body` (local fns inside a body are not indexed as top-level helpers). New pure helpers `is_mod_block_decl` (inline `mod NAME { … }` vs. external `mod NAME;`), `strip_leading_visibility`, and `apply_line_braces`/`apply_line_braces_stripped` (the scope-stack walker); the now-unused `code_brace_delta` was removed. Tests, TDD red→green (red confirmed against the pre-fix scanner): `module_scoped_workflow_direct_violation_is_flagged`, `module_scoped_workflow_transitive_helper_violation_is_flagged` (asserts `via_helper`), `nested_module_workflow_direct_violation_is_flagged`, `module_scoped_det010_hashmap_iteration_is_flagged`, and the two negative guards `module_scoped_activity_violation_is_not_flagged` / `impl_method_callee_is_not_resolved_as_helper` (in `det_check_tests.rs`); `is_mod_block_decl_matches_inline_modules_only`, `strip_leading_visibility_handles_pub_forms`, `apply_line_braces_classifies_module_vs_opaque` (unit tests in `det_check.rs`); and `module_scoped_workflow_direct_violation_trips_the_gate` (CLI behavioral test in `det_check_cli.rs`).

**Post-review hardening (Codex P1/P2 — scope-aware same-name resolution + turbofish calls).** Two false-negatives the module-aware rewrite left, both fixed TDD red→green. **(P1) Scope-aware same-name helper resolution.** The prior code marked any identifier defined by more than one plain free helper as globally ambiguous (`None`) and never resolved *any* workflow call to it — even when the calling workflow's own in-scope sibling was the obvious, Rust-correct target (e.g. `mod a { #[workflow] async fn wf() { stamp(); } fn stamp() { chrono::Utc::now() } }` alongside an unrelated `mod b { fn stamp() -> String }` reported no findings, skipping the reachable hard-blocker in `a::stamp`). Resolution is now Rust-accurate nearest-scope: a candidate in the caller's **own module** (same file + `module_path`) wins, else the sole candidate in the caller's **file**, else a **globally unique** candidate, else (multiple candidates, none in the caller's module/file scope) the call is conservatively skipped — the only remaining safe false-negative. This is a strict accuracy improvement with no added false-positive risk (preferring the same-module/same-file definition is exactly what the compiler resolves a bare call to). Shadow-suppression still runs first, so a locally-bound name is never resolved. Implementation: `FnDef` gains a `module_path` (the `mod`-nesting path, tracked in `extract_all_functions` via a `mod_stack` maintained in lockstep with the `Module` scope entries — new `extract_mod_name` + `apply_line_braces_scoped`); the helper index changed from `HashMap<&str, Option<usize>>` to `HashMap<&str, Vec<usize>>`; new pure `resolve_helper(candidates, fns, caller)`. **(P2) Turbofish call form.** A generic first-party helper called with a turbofish (`bad::<u64>()`, `bad::<Vec<u8>>()`) had the byte `:` (not `(`) after the ident, so the call-paren matcher never scanned the helper body and a reachable violation was missed. `collect_direct_free_fn_calls` now skips an optional balanced `::<…>` segment (new `skip_balanced_angles`) before requiring `(`. The `.`/`:` before-guard is unchanged, so method (`x.method::<T>()`) and associated (`Type::assoc::<T>()`) turbofish calls are still never resolved. **Both fixes preserve every existing guarantee** — `#[activity]` bodies unscanned, impl/trait methods never indexed or resolved (#386), closure/fn-pointer shadow-suppression, and zero false positives on the real tree. Tests: `same_module_helper_resolves_over_unrelated_same_name`, `same_file_different_module_helper_disambiguates`, `genuinely_ambiguous_same_name_helper_is_skipped`, `same_name_impl_method_is_not_resolved_via_method_call`, `turbofish_helper_call_is_resolved`, `nested_generic_turbofish_helper_call_is_resolved`, `method_and_assoc_turbofish_are_not_resolved` (in `det_check_tests.rs`); `extract_mod_name_reads_the_module_identifier`, `skip_balanced_angles_matches_nested_generics` (unit tests in `det_check.rs`).

**Post-review hardening (Codex P2 — source-order shadow tracking).** The zero-FP shadow-suppression above used a **whole-body** shadow set: any locally-bound name (params + every `let` binding anywhere in the body) suppressed a call to that name, regardless of where the binding sat relative to the call. That over-suppressed a genuinely in-scope call: a free helper called **before** a later same-name `let` binding is resolved by Rust to the free helper (the binding is not yet in scope), but the whole-body set wrongly skipped it — a false-negative in AC4 transitive coverage (e.g. a free `fn bad()` reading `chrono::Utc::now()`, reached by a `bad()` call preceding a later `let bad = |x| …`, went unreported). Suppression is now **source-order aware** (`collect_body_let_idents` → `collect_body_let_binding_lines`, name → earliest binding line; `collect_direct_free_fn_calls` takes `params` + `let_binding_lines` and compares each call's source line): a `let` shadow suppresses a call only on a strictly-later source line (so a pre-shadow call — and a call on the binding's own line, `let bad = bad();` — resolves to the free helper, matching Rust); params still bind for the whole body. **No new false positive** — this only ever suppresses *less* than the whole-body set, so every previously-suppressed post-shadow call stays suppressed and the original closure / fn-pointer-param FP-avoidance (`local_closure_call_is_not_resolved_to_free_helper`, `fn_pointer_param_call_is_not_resolved_to_free_helper`) is preserved. A `let` shadow bound in an inner block already closed before an outer call still suppresses it (source-order, not full brace-scope tracking) — a documented safe-direction residual false-negative, never a false-positive. Tests, TDD red→green (red confirmed against the pre-fix whole-body set): `pre_shadow_call_resolves_to_free_helper_not_the_later_binding` and the residual pin `block_confined_shadow_before_call_is_a_documented_false_negative` (in `det_check_tests.rs`).

**Post-review hardening (Codex r4 — false-positive fix + raw identifiers).** Two more findings, both fixed TDD red→green. **(C) Removed the Rust-inaccurate same-file-different-module resolution (false positive).** `resolve_helper`'s prior order preferred the sole same-**file** helper (any module) before falling back to global uniqueness, but a bare call in a child module does **not** resolve to a same-file helper in a *different* module (a parent/sibling module of the file) unless brought in by a `use` — which this text-level analysis cannot see. So a module-scoped workflow doing `use crate::pure::helper; helper();` (real target: a clean `helper` imported from another file) had its call wrongly resolved to an unrelated file-root `fn helper()` and got that helper's `chrono::Utc::now()` reported as a hard blocker — a false positive that could **fail CI on innocent code**. Removing the same-file preference is strictly *more* Rust-accurate and only ever resolves **fewer** calls (removes an FP; cannot add one); shadow-suppression and source-order tracking still run first, and the same-module nearest-scope resolution (the #386 module-nested P1 fix) is untouched. **(D) Raw-identifier function names are now parsed.** `fn_decl_name` accepts an optional `r#` prefix (`async fn r#gen(…)` — `gen` is a reserved keyword in edition 2024, so `r#gen` is a valid, increasingly-real workflow name), retaining the `r#` on the extracted name; previously the parser stopped at `r`, failed the tail sanity check, and the `r#`-named workflow's body was **never scanned** (a direct `chrono::Utc::now()` in it passed with zero findings — a false negative). Tests, TDD red→green: `same_file_different_module_helper_is_not_resolved` (converts the now-incorrect `same_file_different_module_helper_disambiguates`, which asserted the buggy FP behavior — the real target is a `use`-imported helper, so the file-root helper's violation is not reachable and must not be flagged), `raw_ident_workflow_body_is_scanned` (in `det_check_tests.rs`), and raw-ident assertions added to the `fn_decl_name_handles_visibility_and_async` unit test (in `det_check.rs`). **Post-review hardening (Codex r5 — restrict one-hop resolution to same-module, ending the cross-module false-positive family structurally).** Codex found a second aliased-import false positive after r4: a `mod inner` workflow doing `use crate::pure_helper as helper; helper();` (real target: a clean, aliased-in helper from another file) still had its bare `helper()` call resolved cross-module — via the surviving **globally-unique (`[only]`) branch** — to an unrelated file-root `fn helper()` reading `chrono::Utc::now()`, reported as a hard blocker that would **fail CI on innocent code**. Root cause is fundamental: the line-based front-door **cannot see `use` imports/aliases**, so *any* cross-module resolution keeps producing this false-positive class (r4 was the same-file-different-module case with two candidates; r5 is the single globally-unique candidate; both are the same bug). Rather than chase each variant, resolution is now restricted **structurally to same-module candidates only**: `resolve_helper` resolves a bare call **only** to a helper declared in the caller's own module (same file + `module_path`), and treats **everything else** — cross-module, cross-file, `use`-imported, aliased, and even a *globally-unique* helper that is not same-module — as ambiguous and skips it (a safe false-negative, never a false-positive). The earlier globally-unique (`[only]`) and same-file-different-module fallbacks are **deleted**; this makes an import/alias false positive impossible by construction. For a CI gate a false positive (failing CI on innocent code) is the worst outcome and outranks marginal recall; because #386 is likewise body-only, it does not hard-block a violation inside a skipped cross-module helper either, so the backstop for these transitive false-negatives is runtime replay (`WorkflowReplayer` / the live `HistoryMatcher`) plus manual review, not #386. Shadow-suppression + source-order tracking (r3) still run before resolution; turbofish call matching (r2), raw-identifier parsing (r4), module-nested `#[workflow]` scanning (r1), and the `#[activity]` / impl-method exclusions (#386) are all orthogonal and unchanged. **Post-review hardening (Codex r7 — block `use` imports shadow the whole body, not source-order).** r6 added body-local `use` bindings to the shadow set but applied them **source-order** (a `use` only shadowed calls on strictly-later lines, like a `let`). That is wrong for `use`: unlike a sequential `let`, a Rust block `use` item is in scope for the **entire enclosing block** regardless of textual position, so a bare call may **precede** the `use` and still resolve to the import. A body doing `helper(); use crate::pure::helper;` therefore still false-positived — the call preceded the `use`, so r6's source-order check did not suppress it, and same-module resolution scanned the sibling `fn helper`'s `chrono::Utc::now()` and reported a hard blocker on code that never reaches that helper. Fix: body-local `use` bindings (and a body-local glob) now shadow the called name across the **whole body**, matching Rust's block-wide `use`-item scope — `collect_body_use_bindings` returns `(HashSet<String>, bool)` (a presence set + "any glob in the body") instead of source-line maps, and `collect_direct_free_fn_calls` suppresses a call whenever its name is in that set or any glob is present, on every line. **`let`/closure/param shadows stay source-order (r3) — only the `use`/glob half becomes whole-body.** This only ever suppresses *more*, so it introduces **no new false positive** (a genuine same-module call with no body `use` for that name — and no glob — is still resolved and flagged; a module/file-level `use` is still never a body shadow).
