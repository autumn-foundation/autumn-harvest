## Fix — `timer_overdue` false positive under saturated workflow dispatch slots (issue #1191)

`stall_diagnosis::workflow_wake_was_missed` gated the `timer_overdue` verdict on the run's own workflow-task row being `PENDING` with `scheduled_at` aged past a 60-second grace window (`TIMER_OVERDUE_GRACE_SECONDS`), on the assumption that only `persist_started_timer` (via `queue::reschedule_task`) re-pends a row to that exact shape. But `wake_workflow_task`'s `primary_repend_workflow_task_query` produces the identical row shape — `PENDING`, `scheduled_at` set to the wake instant — on a signal, child, or external-handoff completion, unrelated to any armed timer's deadline. Under saturated workflow dispatch slots that row can also age past the grace window, so the old check alone could not distinguish a genuinely missed timer wake from an already-woken, merely capacity-constrained run. That produced a false `timer_overdue`/`stalled` verdict, the worst error class for a triage endpoint (a per-execution root-cause classifier, issue #809).

**Fix.** New pure discriminator `timer_owns_the_wake(scheduled_at, fires_at)`: true only when the two timestamps match within `TIMER_OWNERSHIP_TOLERANCE_SECONDS` (2 seconds — kept strictly under `queue::IMMEDIATE_SCHEDULE_SKEW_ALLOWANCE`'s 5-second wake-instant backdating, so an exact timer-owned match still passes while a wake-instant repend needs an implausible coincidence to be mistaken for one). `classify_execution` now filters every overdue-timer candidate through it (via the new `is_the_missed_timer_wake` combinator) before reporting `timer_overdue`; when a `WorkflowTaskFacts` row is absent, the check passes through unconditionally (`Option::is_none_or`), preserving the pre-existing behavior for callers that never supply one. A genuinely missed timer wake — `scheduled_at == fires_at`, set by the one code path (`queue::reschedule_task`) that hands a timer ownership of the wake — is unaffected.

**No new `WorkflowEvent` variant, no migration, no event-contract change.** A pure read-path correlation between two facts (`WorkflowTaskFacts::scheduled_at`, `PendingTimerFacts::fires_at`) the endpoint already loads; the endpoint stays read-only (no task claims, no state mutation, no events appended).

**Tests (TDD).** RED-before-the-fix pure unit test (`overdue_timer_suppressed_when_a_different_wake_source_re_pended_the_task`) and DB/HTTP integration test (`overdue_timer_is_not_a_stall_when_a_different_wake_source_re_pended_the_task`) both reproduce the saturated-slot false positive end to end. New wiring-level boundary tests (`overdue_timer_correlates_at_exactly_the_tolerance_boundary`, `overdue_timer_does_not_correlate_one_second_past_the_tolerance`) and a two-timer disambiguation test (`overdue_timer_correlation_wins_over_an_earlier_non_owning_timer`, proving the filter-then-`min_by_key` ordering can't let an earlier, non-owning timer win) came out of a three-angle self-review before submission.

**Known, explicitly out-of-scope observation.** A self-review noted that other `harvest_task_queue.scheduled_at` writers on a workflow-type row (`queue_pause`'s resume-shift queries, `shard_rebalance`'s post-cutover re-pend) share the same "`PENDING` row aged past grace, not timer-owned" shape `wake_workflow_task` does, and would benefit from the same correlation this fix applies — filed as a follow-up rather than folded in here, since it broadens the diagnosis beyond the two re-pend paths issue #1191 names. See issue #1402.

**Automated-review addendum (Codex round 1 on the PR).** `timer_owns_the_wake`'s timestamp-proximity check alone was still coincidentally satisfiable: an unrelated armed timer whose `fires_at` happened to land within roughly `2 * TIMER_OWNERSHIP_TOLERANCE_SECONDS` of the true wake instant would pass it, reintroducing the same false positive in a narrower window. Fixed by adding a second, independent signal: `wake_source_repended_this_row` reads `harvest_task_queue.created_at`, which `primary_repend_workflow_task_query` is the only writer to touch on a workflow task row (setting it from the same instant as `scheduled_at`, in the same statement) — a fingerprint `queue::reschedule_task`'s genuine timer-owned path never produces. `created_at` is nullable (issue #501: pre-upgrade rows have none); `None` conservatively falls back to the proximity-only check. Required plumbing the already-existing `created_at` column through `WorkflowTaskFacts` and the plugin's diagnose loader (no migration). New pure truth table (`wake_source_repended_this_row_truth_table`, including the legacy-row `None` case), a `classify_execution`-level regression pin (`overdue_timer_does_not_correlate_via_coincidental_proximity_alone`), and a DB/HTTP test seeding the exact coincidence against a real row.

**Automated-review addendum (Codex round 2 on the PR).** `wake_source_repended_this_row`'s symmetric ±2s window around the 5-second skew could itself false-negative: `scheduled_at` is bound in Rust before `primary_repend_workflow_task_query`'s `UPDATE` runs, while `created_at`'s `clock_timestamp()` fires only once the server executes it, so multi-second database or network saturation between bind and execution pushes the gap outside the old window — reintroducing the original false positive if an unrelated timer also happened to sit within `timer_owns_the_wake`'s tolerance. Fixed by replacing the symmetric tolerance with an asymmetric range: a tight lower bound (2s, ordinary clock skew) and a generous upper bound (30s, absorbing realistic saturation delay). Safe to widen only upward: a genuinely timer-owned row's gap is never positive at all (`created_at`, the row's original untouched creation time, always precedes a timer's own future `fires_at`), so there is no coincidence risk from a wider upper bound. New `classify_execution`-level regression pin (`overdue_timer_does_not_correlate_when_the_wake_repend_was_delayed`) reproduces a 20-second-delayed re-pend coinciding with an unrelated timer's proximity match.

**Automated-review addendum (Codex round 3 on the PR).** `release_suspended_workflow_claim_query` (issue #1182) is a SECOND production path that resets a workflow task row for a fresh dispatch attempt, with a different fingerprint from `wake_workflow_task`'s: `scheduled_at = NOW()`, no backdating at all, so its gap is ~0s, not ~5s — outside the round-2 window entirely. Rather than widen the window again to also cover 0s (and risk missing whatever constant a future such path picks), replaced magnitude-matching with the general invariant every one of these paths shares, and a genuine timer-owned reschedule never can: `created_at` lands at or after `scheduled_at`, not meaningfully before it (a genuinely timer-owned row's `created_at` is its original, untouched creation time, which always precedes its own future `fires_at` by at least the timer's duration). This drops the need for an upper bound entirely — replaced `WAKE_REPEND_SKEW_SECONDS`/`_LOWER_TOLERANCE`/`_UPPER_TOLERANCE` with a single `WAKE_REPEND_MIN_GAP_SECONDS` (-2s, ordinary clock skew) — and covers any future path with the same "reset for redispatch" shape without naming it. The one honest residual: a genuine timer of a few seconds or less shares this same small negative slack, though only in combination with an unrelated timer's own coincidental proximity match, documented explicitly. New regression pin `overdue_timer_does_not_correlate_after_a_suspended_claim_release`.

Re-validating against the DB suite caught a real regression, fixed in the same round: `overdue_timer_still_wins_when_the_task_own_wake_was_missed` seeded its genuinely-timer-owned row via `seed_workflow_task`'s default `created_at` (insert time = now) instead of a realistic backdated value. That shape is unrepresentable in real production (a row's `created_at` can never postdate its own timer's `fires_at`), but it was enough to trip the new sign check in the test fixture itself — backdated explicitly to fix.

Full `stall_diagnosis` unit suite (140 tests) and the `stall_diagnosis_integration` DB suite (74 tests) pass; pre-existing regression pins for the genuinely-missed-timer-wake case (issue #476's signal-or-deadline race) and the healthy-activity-alongside-an-overdue-timer case are unaffected.
