## Phase 3.x — Task-queue pause/resume: hold dispatch during a downstream outage (issue #619)

**Implemented.** When a downstream dependency for a whole *class* of activities goes down (Stripe, SendGrid, the data warehouse), the operator's job-to-be-done is to **hold** the affected work, not fail it: freeze the queue, let the dependency recover, thaw, and have everything continue as if nothing happened. Before this, the closest primitives all did the wrong thing — the admission gate (#377/#618) halts new workflow *starts* while in-flight runs keep scheduling activities into the broken queue; the circuit breaker (#369) deliberately **fast-fails** dispatch, burning retry budget and pushing workflows down error branches; per-execution pause (#383/#609) holds *one* execution, useless when you know the queue but not the 50,000 executions behind it. **Gate the door, breaker the fast-fail, pause the hold.** New core module `queue_pause.rs` with the public surface `pause_queue`/`resume_queue`/`list_paused_queues`/`paused_queue_names`/`is_queue_paused`, the pure `validate_queue_name`/`queue_pause_suppresses_timeout`/`queue_pause_anti_join`, and the `PausedQueue`/`PauseOutcome`/`ResumeOutcome` records. **Enforcement is an anti-join, not a cache (the load-bearing design decision).** A pause is durable queue metadata enforced by a correlated `NOT EXISTS` conjunct on the claim path, exactly like the PAUSED-execution skip (#383) and the rate-limit gate (#332) — deliberately **not** an in-process cache like the admission gate's. AC1's "durable and re-applied before the worker pool begins claiming" is therefore true **by construction**: there is no boot window in which a held queue is briefly claimable, no refresh interval, no fleet-wide staleness, no global static, no fail-closed reasoning, and no write-through path that can diverge from the database. The cost is one primary-key probe per claim against a table bounded by the number of distinct queue names. Because the predicate is embedded verbatim in three separate SQL strings that do **not** share a table alias (the claim CTE and the oldest-pending-age scan are unaliased; the claimable-demand query uses `tq`), it is generated from one renderer `queue_pause_anti_join(outer_table)` with a drift-locked `const QUEUE_PAUSE_CLAIM_PREDICATE` for the allocation-free hot path — a paused queue a mirror query forgot about would report a phantom backlog and drive a false capacity alert during exactly the deliberate hold. **The outer column reference must be qualified**: inside the subquery an unqualified `queue_name` resolves against `harvest_queue_pauses` first, degenerating to `qp.queue_name = qp.queue_name` — always true, which would silently pause *every* queue the moment any one queue is paused. That was a real bug caught pre-commit and is now pinned by `anti_join_always_qualifies_the_outer_column`. **AC2/AC3 — hold, never fail.** The gate sits on the claim path only, so an already-`RUNNING` task finishes naturally (a pause holds *dispatch*, it does not abort in-flight work) and a held task simply stays `PENDING` — never `FAILED`, retried, or dead-lettered *because* the queue is paused. **AC4 — `schedule_to_start` suspended, `schedule_to_close` deliberately not.** The relative `schedule_to_start` timer is suspended for held tasks in **both** the scan predicate (`schedule_to_start_timeout_query` gains an unconditional queue carve-out) and the locked re-check inside `enforce_activity_timeout`, so neither a scan-vs-enforce race nor a pause landing mid-enforcement can time out held work. The **absolute** `schedule_to_close` deadline (#378) keeps ticking — issue #619 scopes crediting paused time back to an SLA deadline out explicitly, and that decision is pinned by its own test (`schedule_to_close_scan_does_not_exclude_paused_queues`). `Heartbeat`/`StartToClose` stay pause-blind (both apply only to `RUNNING` rows, mirroring the per-execution pause contract). **AC5 — the resume shift, the single most load-bearing query in the feature.** Without it, thawing a queue whose backlog waited past its `schedule_to_start` would immediately time out the *entire* held backlog — exactly the failure AC4/AC5 exist to prevent. `resume_queue` runs `scheduled_at += NOW() - GREATEST(scheduled_at, paused_at)` over the queue's **due** `PENDING` rows only: a task eligible *before* the pause is shifted by the full pause span (so 100 s of genuine pre-pause waiting is preserved), one that became eligible *mid-pause* collapses to `NOW()` (it was held from the instant it became due), and one *not yet due* (a retry backoff) is excluded entirely (it was never held, so its backoff must not be extended). The result is provably `<= NOW()` in every branch, so a thawed task is never pushed into the future — which would make it *un*claimable, the inverse of the intent. **AC9 — no new `WorkflowEvent` variant.** A pause writes nothing to `harvest_events`; replay of an execution that touched a paused queue is byte-identical to one that never paused. Pinned two ways: a source-level guard asserting `queue_pause.rs` never mentions `WorkflowEvent` or `harvest_events` outside its own doc prose, and a DB test that snapshots the raw event rows of an affected execution before the pause and compares them byte-for-byte after the resume. **Surfaces.** Migration `20260715000000_harvest_queue_pause` adds one table (`harvest_queue_pauses`, PK `queue_name`, plus `reason`/`paused_by`/`paused_at`/`scope_shard_id`). Three admin-gated management routes — `POST /admin/queues/{queue_name}/pause`, `POST /admin/queues/{queue_name}/resume`, `GET /admin/queues/paused` — registered across the axum router, all four plugin registries, `docs/api-contract.json`, and `autumn_harvest::audit` (`OP_QUEUE_PAUSE`/`OP_QUEUE_RESUME`/`TARGET_QUEUE`; the read route `ReadOnly` + `EXCLUDED_ROUTES`), with pins in **both** `audit.rs` and `contract_regression.rs` since the audit-side mutual cross-check stays green if a route is dropped from both lists. All three return `200 OK` (the hold is in effect the instant the row commits — there is no async application step, unlike `202`-returning `terminate`). Both mutations are **idempotent**: a repeat pause is a no-op that **preserves the original reason and operator** (a re-pause never rewrites the provenance of an existing hold), and resuming an unpaused queue is a success no-op so a retry after a lost response is safe. AC7's fleet-wide default is the absence of `shard_id`; supplying it scopes the hold to one shard, and the read endpoint merges per-shard rows into one entry with a `shards` array. **AC6 — audit + UI.** Both mutations write an audit row carrying the operator identity, operation, target queue, route, and source. The human-readable *reason* lives on the durable pause row (surfaced by the read API, the CLI, and the UI) rather than being duplicated into `error_summary`, which is failure-only across the entire codebase — this follows the #383 `OP_WORKFLOW_PAUSE` precedent exactly, and consistency with the sibling per-execution pause is what governs here. Because the pause row is deleted on resume, `ResumeOutcome` (and therefore the resume response, the CLI output, and the UI flash) **echoes back** `released_reason`/`released_paused_by` — the last moment the *why* is recoverable. The Vantage **Workers** page (the fleet page an operator lands on when investigating idle workers) grows a paused-queues banner listing each held queue with its reason, actor, `paused_at` and held-task count; per-shard rows are merged with held counts summed and the **earliest** `paused_at` winning (it is the one an operator reasons about), sorted by queue name so the banner is stable across refreshes. **Eligibility explainer coherence (#611).** `task_intrinsic_impediment_reasons` gained a `queue_paused` input that pushes `"queue_paused"` **first** — without it the explainer would report an *empty* (falsely "unimpeded") reason set for a held task during exactly the idle-worker triage it exists for. It is listed first because it is the operator's own deliberate action. **AC8 — gauge.** New `harvest.queue.paused` (`METRIC_QUEUE_PAUSED`, label `queue` only), `1` while a hold is in effect and `0` otherwise, sampled by `spawn_queue_pause_sampler` on the worker's poll interval across every shard of its `ShardedDbPool`. A read failure skips the whole tick so an outage never false-clears the gauge, and a queue that is no longer held is zero-filled rather than going stale. Wired through the three-touchpoint recipe (`telemetry.rs` const + no-op default + `metrics_rs_adapter` bridge) with the full anti-drift set: a dashboard panel in the "Queues & workers" row, the `harvest_queue_paused_too_long` alert rule (binary gauge → the **`for` duration is the threshold**, with a sharper `and harvest_queue_depth > 1000` variant so a hold on an idle queue stays quiet), a five-subsection runbook section, the ADR-0001 §7 catalogue, `docs/telemetry.md`, and the `dashboard_pack_docs`/`alert_pack_docs`/`metrics_coverage` registries. **CLI:** `harvest queue pause <q> --reason <why> [--shard-id N]` / `resume` / `list-paused` (aliases `list`, `status`); `--reason` is required at clap parse time (a hold with no stated cause is unauditable), and omitting `--shard-id` sends no field at all so the default stays fleet-wide. **Docs:** a `queue_paused` diagnosis in `docs/runbooks/triage-pending-tasks-idle-workers.md` calling out that a rising `harvest_queue_depth` while this gauge reads `1` is the hold working as designed — the single most common false capacity page during an outage freeze. **Tests, TDD red→green→refactor.** 7 pure unit tests in `queue_pause.rs` (incl. the const/renderer drift lock and the qualified-column regression guard) + 3 claim-query drift-lock tests in `queue.rs`; 20 tests in `tests/integration/queue_pause_tests.rs` (7 pure — claim + mirror queries carry the anti-join, the `schedule_to_start` scan excludes paused queues while the `schedule_to_close` scan pointedly does not, the timeout-suppression truth table, name validation, and the shift query never pushing `scheduled_at` past `NOW()`; 13 DB — hold-and-release, in-flight tasks not aborted, `schedule_to_start` suspended during and after, all three shift branches, idempotency, the read model, the gauge feed, and the two AC9 replay guards); 5 plugin HTTP tests in `queue_pause_integration.rs` (round trip with audit, idempotent resume, `400` validation, admin gate, and durability across a full API-state teardown — the "plugin restart" proxy, which passes with no re-application step precisely because the gate is a row); 2 no-DB admin-gate tests in `security.rs`; 4 UI banner tests; 14 CLI mapping/coverage tests; and the **success-metric** test `pause_holds_a_failing_backlog_and_every_task_succeeds_after_thaw` (`queue_pause_success_metric_tests.rs`), which drives a real worker through the whole story: downstream down → real attempts fail and burn retry budget (making the test falsifiable rather than trivially green on a queue that never ran anything) → operator pauses → hold across several poll cycles with **zero** further attempts claimed, zero `FAILED`, zero DLQ → downstream recovers → resume → **100%** of held workflows reach `COMPLETED` with an empty DLQ. All DB/HTTP suites were **executed** against a real local Postgres 16 (Docker is unavailable in the authoring sandbox), and all three suites are registered in `.github/ci/integration-suites.txt` for the Docker-backed Linux run. **Out of scope (per the issue):** per-execution pause (#609/#383), halting new workflow starts (#377/#618), fast-fail semantics (#369), schedule/cron pausing (#229), automatic health-driven pause, weighted multi-queue draining (#515), and crediting paused time back to `schedule_to_close` (#378) — this slice keeps the absolute SLA deadline ticking and suspends only the relative `schedule_to_start` timer. **Post-review hardening (three parallel review agents — correctness/concurrency, API surface/security, AC compliance — two findings reproduced empirically against Postgres 16).** (1) **P1, the enforcer's queue-pause re-check was not authoritative.** Its doc comment claimed parity with the execution-pause re-check, but that sibling works precisely because *both* sides lock the same execution row; `pause_queue` shares no row with `enforce_activity_timeout`, so the non-locking `is_queue_paused` read did not serialize — a reviewer reproduced a pause committing 38 ms into the enforcer's post-recheck write sequence and terminally `ScheduleToStart`-failing a task on the now-paused queue, violating AC2/AC3/AC4 during exactly the backing-up-backlog scenario the feature exists for. Fixed with a shared transaction-scoped advisory lock, `lock_queue_for_pause` (`pg_advisory_xact_lock(hashtext(queue_name))`, mirroring the `concurrency_key`/`ctx.mutex` patterns), taken by `pause_queue`, `resume_queue`, and the enforcer before its re-check — and, in the enforcer, **only** on the `ScheduleToStart` path, so the far more common in-flight timeout paths never take it. Pinned by `a_pause_committed_after_the_scan_still_suppresses_the_timeout`, which holds the lock open across the enforcer's run. (2) **P2, a pause racing a resume returned 500 and left the queue live.** `INSERT ... ON CONFLICT DO NOTHING` does not lock the conflicting row, so a concurrent resume could delete it between the insert and the fallback `SELECT`, whose `get_result` then `?`-propagated `NotFound` — rolling the transaction back into an opaque 500 while the queue kept dispatching (reproduced). Collapsed to a single atomic `ON CONFLICT (queue_name) DO UPDATE SET queue_name = harvest_queue_pauses.queue_name RETURNING ..., (xmax = 0) AS newly_paused`: `DO UPDATE` takes the row lock, the no-op `SET` preserves the original provenance on a re-pause, and `xmax = 0` is the standard insert-vs-update discriminator. Pinned by `pause_racing_a_concurrent_resume_still_holds_the_queue`. (3) **P2, a partially-applied fleet-wide hold reported success.** If any shard succeeded the handler returned `200 {"ok": true}` with the detail buried in a `partial_failures` string — while writing its own audit row as `failed`. An operator would believe the hold was fleet-wide while the missed shards kept dispatching into the outage. Both mutations now return **`207 Multi-Status`** with `ok: false` and `status: "partial"`, reusing the read side's existing `complete`/`partial` vocabulary; a fully applied request keeps `200`/`ok: true`/`status: "complete"` and omits `partial_failures`. Re-issuing is safe (idempotent). (4) **P2, `queue_pause_target_pools` silently skipped router-known-but-poolless shards**, so mid a shard-add rollout a fleet-wide pause returned an *unqualified* success with no diagnostic at all — strictly worse than a partial failure. It now derives its target set from `shard_fanout::expected_shards` (the same helper the read path uses for exactly this reason) and reports an unreachable-but-known shard as a partial failure; naming such a shard explicitly is now a `503` rather than a misleading `400 "unknown shard_id"`. (5) **P2, rejected attempts were unaudited.** A malformed body, blank/oversized queue name, missing reason, or unroutable shard all returned without a trace — on a route whose whole purpose is a fleet-wide dispatch kill switch, the rejected-attempt trail is what an incident review needs. New `write_queue_pause_rejection_audit` writes a `STATUS_FAILED` row on every rejection path (symmetric with `fail_activity_now`'s malformed-id handling). (6) **P2, the operator `reason` bypassed the shared 500-char `truncate_operator_reason` cap** that every other durable operator reason on the router uses — it is stored, re-serialized on every read poll, and rendered into the Vantage Workers page, the very page an operator lands on during a queue-pause incident. Now capped at the API boundary. (7) **P3, the queue name was validated trimmed but stored untrimmed**, so `--queue "payments "` inserted a row matching no task and reported a successful hold (`newly_paused: true`, `held_task_count: 0`) on a queue that kept dispatching. `validate_queue_name` now *returns* the canonical trimmed name and every read and write uses it. Pinned by `a_padded_queue_name_still_holds_the_real_queue`, which asserts the *unpadded* queue is genuinely held. (8) **CI-breaking: `queue_pause_success_metric_tests.rs` was missing its `#![cfg(feature = "db")]` gate** while importing the `db`-gated `integration_e2e` helpers — an unresolved-import compile failure on all three OSes of the `--no-default-features` CI leg. Added. (9) The same suite was not hermetic on a shared `HARVEST_TEST_DATABASE_URL` database (it scrubbed only `harvest_queue_pauses`), so a re-run inherited the previous run's `FAILED` rows and failed its own "zero tasks may transition to FAILED" assertion. It now scrubs every fixture it owns; CI's fresh testcontainer never needed this. (10) The `schedule_to_close`-keeps-ticking caveat was documented in code and the API contract but **absent from both operator runbooks**, which said a pause is "safe — nothing fails" — the one place an operator could lose work by trusting the runbook. Called out explicitly in both. **Coverage added for the gaps the AC audit named:** the AC7 multi-shard *write* path (a shard-scoped hold applies fully and reports its scope; a partially-applied fleet-wide hold is `207`; an unknown shard is `400` and audited), the AC4 locked-re-check race, the atomic-upsert race, name canonicalisation, rejected-attempt auditing, and the reason cap. **Clippy:** extracting the claim SQL into a shape-testable `const fn claim_task_query()` moved a 144-line string literal out of `claim_task`, which carried `#[allow(clippy::too_many_lines)]`; the allow moved with it.

**Post-review hardening (Codex automated review, PR #1135) — three findings, all genuine, all fixed:**

1. **P1 — a claim already in flight could beat the pause.** `claim_task` is a single autocommit statement, so under `READ COMMITTED` its whole CTE — including the pause anti-join — evaluates against **one snapshot taken at statement start**. A pause committing after that snapshot is invisible to it, so a claim already in flight when the operator paused still transitions its task to `RUNNING` and hands it to a worker that dispatches into the outage. The window is normally sub-millisecond but is unbounded in principle: the claim's rate-limit debit can block on a row lock held by a competing claim, and Postgres's `EvalPlanQual` re-check on unblock only re-evaluates conditions on the *locked row*, never a correlated subquery over another table. **Codex's literal suggestion — take the queue-scoped lock inside the claim path — was rejected**: it would serialize every claim for a queue against every other, defeating `FOR UPDATE SKIP LOCKED`'s parallel claiming for a feature that is inactive almost all of the time. Fixed instead with a post-claim authoritative re-check in a **fresh statement** (hence a fresh snapshot): new `queue_pause::release_claim_if_queue_paused`, one guarded `UPDATE` that returns the task to `PENDING` and **restores the `attempt`** the claim consumed (a hold must not burn retry budget — AC3), guarded on `state = 'RUNNING' AND worker_id = $2` so it can only ever undo *this* worker's own claim. Wired inside `claim_task` itself so the guarantee is a property of the primitive rather than of one caller; a released claim surfaces as `Ok(None)`, which both worker call sites already treat as "nothing to dispatch". Cost: one indexed primary-key probe per *successful* claim (never per empty poll). The contract becomes crisp: **a pause committed before the re-check's statement begins always wins**; one that commits after did not beat the claim, and AC2 explicitly allows an already-`RUNNING` task to finish naturally. The rate-limit token the claim debited is not refunded — the same safe-side, self-healing leak already documented for a lost claim in `claim_task` (it only ever under-dispatches). Tests: `a_pause_committed_mid_claim_still_holds_the_task` reproduces the race **deterministically end-to-end** by stalling the claim mid-statement on its rate-limit debit (the one part of the CTE that can block, since the candidate scan uses `SKIP LOCKED`) — hold the bucket row from another transaction, start the claim, commit the pause while it is parked, then release the bucket — plus `a_claim_that_beat_the_pause_is_released_with_its_attempt_restored`, the no-regression guard `an_ordinary_claim_is_not_released_when_the_queue_is_not_paused`, and a SQL-shape drift lock.

2. **P2 — ABBA deadlock between the timeout enforcer and resume.** `enforce_activity_timeout` locked the execution row, then the task row, and only then took the queue advisory lock; `resume_queue` takes the advisory lock first and *then* row-locks every `PENDING` task on the queue via its `scheduled_at` shift. Reaching those locks concurrently, enforcement would hold a task row while waiting on the advisory lock and resume would hold the advisory lock while waiting on that task row — Postgres breaks the cycle by aborting one, failing either the timeout pass or the operator's resume request. Fixed by hoisting the `ScheduleToStart` queue-pause check to the **top** of the enforcement transaction, so both paths take advisory-then-rows; also cheaper, since a held task now bails before the row locks and the history load. The ordering convention is documented at both sites (matching the `harvest_external_tasks` task-row→execution-row note from issue #609). Test: `enforcer_takes_the_queue_lock_before_the_row_locks_no_abba` proves the ordering deterministically without provoking an actual deadlock — hold the advisory lock, start the enforcer so it blocks on it, then probe both row locks with `FOR UPDATE NOWAIT` from a third connection and assert both are still free (mirrors the issue #779 `materializer_locks_execution_row_before_timers_no_abba` probe).

3. **P2 — divergent per-shard pause provenance was silently discarded.** The list handler merged by queue name with `or_insert_with`, keeping whichever shard the fan-out reached first and dropping the others' reason/actor/scope while still listing every shard id. That state is produced by the feature's *own* idempotency rule: a re-pause deliberately preserves the **original** provenance, so a fleet-wide hold landing over a pre-existing shard-scoped hold leaves that shard telling a different story — and the `shard_id` parameter explicitly supports pausing one queue on two shards separately. Showing only one of them hands the operator a reason and scope that are not true for part of the fleet. Fixed with a pure, unit-tested `merge_paused_queue_rows`: the top-level summary is the **earliest** hold (a deterministic rule, and the same one the Vantage banner uses, so the two surfaces never disagree), `shards` carries each shard's own `{shard_id, reason, paused_by, paused_at, scope_shard_id, held_task_count}`, and `provenance_uniform` is a single field a script can gate on. Uniformity compares `(reason, paused_by, scope_shard_id)` and deliberately **not** `paused_at` — each shard stamps its own `NOW()`, so including it would report almost every healthy fleet-wide hold as divergent. `docs/api-contract.json` notes updated. Tests: 4 pure no-DB tests covering the uniform fleet-wide collapse, the divergent case (earliest-wins summary + per-shard preservation + `provenance_uniform: false`), distinct queues staying separate, and empty.
