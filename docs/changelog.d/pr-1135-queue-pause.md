## Phase 3.x — Task-queue pause/resume: hold dispatch during a downstream outage (issue #619)

**Implemented.** When a downstream dependency for a whole *class* of activities goes down (Stripe, SendGrid, the data warehouse), the operator's job-to-be-done is to **hold** the affected work, not fail it: freeze the queue, let the dependency recover, thaw, and have everything continue as if nothing happened. Before this, the closest primitives all did the wrong thing — the admission gate (#377/#618) halts new workflow *starts* while in-flight runs keep scheduling activities into the broken queue; the circuit breaker (#369) deliberately **fast-fails** dispatch, burning retry budget and pushing workflows down error branches; per-execution pause (#383/#609) holds *one* execution, useless when you know the queue but not the 50,000 executions behind it. **Gate the door, breaker the fast-fail, pause the hold.** New core module `queue_pause.rs` with the public surface `pause_queue`/`resume_queue`/`list_paused_queues`/`paused_queue_names`/`is_queue_paused`, the pure `validate_queue_name`/`queue_pause_suppresses_timeout`/`queue_pause_anti_join`, and the `PausedQueue`/`PauseOutcome`/`ResumeOutcome` records. **Enforcement is an anti-join, not a cache (the load-bearing design decision).** A pause is durable queue metadata enforced by a correlated `NOT EXISTS` conjunct on the claim path, exactly like the PAUSED-execution skip (#383) and the rate-limit gate (#332) — deliberately **not** an in-process cache like the admission gate's. AC1's "durable and re-applied before the worker pool begins claiming" is therefore true **by construction**: there is no boot window in which a held queue is briefly claimable, no refresh interval, no fleet-wide staleness, no global static, no fail-closed reasoning, and no write-through path that can diverge from the database. The cost is one primary-key probe per claim against a table bounded by the number of distinct queue names. Because the predicate is embedded verbatim in three separate SQL strings that do **not** share a table alias (the claim CTE and the oldest-pending-age scan are unaliased; the claimable-demand query uses `tq`), it is generated from one renderer `queue_pause_anti_join(outer_table)` with a drift-locked `const QUEUE_PAUSE_CLAIM_PREDICATE` for the allocation-free hot path — a paused queue a mirror query forgot about would report a phantom backlog and drive a false capacity alert during exactly the deliberate hold. **The outer column reference must be qualified**: inside the subquery an unqualified `queue_name` resolves against `harvest_queue_pauses` first, degenerating to `qp.queue_name = qp.queue_name` — always true, which would silently pause *every* queue the moment any one queue is paused. That was a real bug caught pre-commit and is now pinned by `anti_join_always_qualifies_the_outer_column`. **AC2/AC3 — hold, never fail.** The gate sits on the claim path only, so an already-`RUNNING` task finishes naturally (a pause holds *dispatch*, it does not abort in-flight work) and a held task simply stays `PENDING` — never `FAILED`, retried, or dead-lettered *because* the queue is paused. **AC4 — `schedule_to_start` suspended, `schedule_to_close` deliberately not.** The relative `schedule_to_start` timer is suspended for held tasks in **both** the scan predicate (`schedule_to_start_timeout_query` gains an unconditional queue carve-out) and the locked re-check inside `enforce_activity_timeout`, so neither a scan-vs-enforce race nor a pause landing mid-enforcement can time out held work. The **absolute** `schedule_to_close` deadline (#378) keeps ticking — issue #619 scopes crediting paused time back to an SLA deadline out explicitly, and that decision is pinned by its own test (`schedule_to_close_scan_does_not_exclude_paused_queues`). `Heartbeat`/`StartToClose` stay pause-blind (both apply only to `RUNNING` rows, mirroring the per-execution pause contract). **AC5 — the resume shift, the single most load-bearing query in the feature.** Without it, thawing a queue whose backlog waited past its `schedule_to_start` would immediately time out the *entire* held backlog — exactly the failure AC4/AC5 exist to prevent. `resume_queue` runs `scheduled_at += NOW() - GREATEST(scheduled_at, paused_at)` over the queue's **due** `PENDING` rows only: a task eligible *before* the pause is shifted by the full pause span (so 100 s of genuine pre-pause waiting is preserved), one that became eligible *mid-pause* collapses to `NOW()` (it was held from the instant it became due), and one *not yet due* (a retry backoff) is excluded entirely (it was never held, so its backoff must not be extended). The result is provably `<= NOW()` in every branch, so a thawed task is never pushed into the future — which would make it *un*claimable, the inverse of the intent. **AC9 — no new `WorkflowEvent` variant.** A pause writes nothing to `harvest_events`; replay of an execution that touched a paused queue is byte-identical to one that never paused. Pinned two ways: a source-level guard asserting `queue_pause.rs` never mentions `WorkflowEvent` or `harvest_events` outside its own doc prose, and a DB test that snapshots the raw event rows of an affected execution before the pause and compares them byte-for-byte after the resume. **Surfaces.** Migration `20260715000000_harvest_queue_pause` adds one table (`harvest_queue_pauses`, PK `queue_name`, plus `reason`/`paused_by`/`paused_at`/`scope_shard_id`). Three admin-gated management routes — `POST /admin/queues/{queue_name}/pause`, `POST /admin/queues/{queue_name}/resume`, `GET /admin/queues/paused` — registered across the axum router, all four plugin registries, `docs/api-contract.json`, and `autumn_harvest::audit` (`OP_QUEUE_PAUSE`/`OP_QUEUE_RESUME`/`TARGET_QUEUE`; the read route `ReadOnly` + `EXCLUDED_ROUTES`), with pins in **both** `audit.rs` and `contract_regression.rs` since the audit-side mutual cross-check stays green if a route is dropped from both lists. All three return `200 OK` (the hold is in effect the instant the row commits — there is no async application step, unlike `202`-returning `terminate`). Both mutations are **idempotent**: a repeat pause is a no-op that **preserves the original reason and operator** (a re-pause never rewrites the provenance of an existing hold), and resuming an unpaused queue is a success no-op so a retry after a lost response is safe. AC7's fleet-wide default is the absence of `shard_id`; supplying it scopes the hold to one shard, and the read endpoint merges per-shard rows into one entry with a `shards` array. **AC6 — audit + UI.** Both mutations write an audit row carrying the operator identity, operation, target queue, route, and source. The human-readable *reason* lives on the durable pause row (surfaced by the read API, the CLI, and the UI) rather than being duplicated into `error_summary`, which is failure-only across the entire codebase — this follows the #383 `OP_WORKFLOW_PAUSE` precedent exactly, and consistency with the sibling per-execution pause is what governs here. Because the pause row is deleted on resume, `ResumeOutcome` (and therefore the resume response, the CLI output, and the UI flash) **echoes back** `released_reason`/`released_paused_by` — the last moment the *why* is recoverable. The Vantage **Workers** page (the fleet page an operator lands on when investigating idle workers) grows a paused-queues banner listing each held queue with its reason, actor, `paused_at` and held-task count; per-shard rows are merged with held counts summed and the **earliest** `paused_at` winning (it is the one an operator reasons about), sorted by queue name so the banner is stable across refreshes. **Eligibility explainer coherence (#611).** `task_intrinsic_impediment_reasons` gained a `queue_paused` input that pushes `"queue_paused"` **first** — without it the explainer would report an *empty* (falsely "unimpeded") reason set for a held task during exactly the idle-worker triage it exists for. It is listed first because it is the operator's own deliberate action. **AC8 — gauge.** New `harvest.queue.paused` (`METRIC_QUEUE_PAUSED`, label `queue` only), `1` while a hold is in effect and `0` otherwise, sampled by `spawn_queue_pause_sampler` on the worker's poll interval across every shard of its `ShardedDbPool`. A read failure skips the whole tick so an outage never false-clears the gauge, and a queue that is no longer held is zero-filled rather than going stale. Wired through the three-touchpoint recipe (`telemetry.rs` const + no-op default + `metrics_rs_adapter` bridge) with the full anti-drift set: a dashboard panel in the "Queues & workers" row, the `harvest_queue_paused_too_long` alert rule (binary gauge → the **`for` duration is the threshold**, with a sharper `and harvest_queue_depth > 1000` variant so a hold on an idle queue stays quiet), a five-subsection runbook section, the ADR-0001 §7 catalogue, `docs/telemetry.md`, and the `dashboard_pack_docs`/`alert_pack_docs`/`metrics_coverage` registries. **CLI:** `harvest queue pause <q> --reason <why> [--shard-id N]` / `resume` / `list-paused` (aliases `list`, `status`); `--reason` is required at clap parse time (a hold with no stated cause is unauditable), and omitting `--shard-id` sends no field at all so the default stays fleet-wide. **Docs:** a `queue_paused` diagnosis in `docs/runbooks/triage-pending-tasks-idle-workers.md` calling out that a rising `harvest_queue_depth` while this gauge reads `1` is the hold working as designed — the single most common false capacity page during an outage freeze. **Tests, TDD red→green→refactor.** 7 pure unit tests in `queue_pause.rs` (incl. the const/renderer drift lock and the qualified-column regression guard) + 3 claim-query drift-lock tests in `queue.rs`; 20 tests in `tests/integration/queue_pause_tests.rs` (7 pure — claim + mirror queries carry the anti-join, the `schedule_to_start` scan excludes paused queues while the `schedule_to_close` scan pointedly does not, the timeout-suppression truth table, name validation, and the shift query never pushing `scheduled_at` past `NOW()`; 13 DB — hold-and-release, in-flight tasks not aborted, `schedule_to_start` suspended during and after, all three shift branches, idempotency, the read model, the gauge feed, and the two AC9 replay guards); 5 plugin HTTP tests in `queue_pause_integration.rs` (round trip with audit, idempotent resume, `400` validation, admin gate, and durability across a full API-state teardown — the "plugin restart" proxy, which passes with no re-application step precisely because the gate is a row); 2 no-DB admin-gate tests in `security.rs`; 4 UI banner tests; 14 CLI mapping/coverage tests; and the **success-metric** test `pause_holds_a_failing_backlog_and_every_task_succeeds_after_thaw` (`queue_pause_success_metric_tests.rs`), which drives a real worker through the whole story: downstream down → real attempts fail and burn retry budget (making the test falsifiable rather than trivially green on a queue that never ran anything) → operator pauses → hold across several poll cycles with **zero** further attempts claimed, zero `FAILED`, zero DLQ → downstream recovers → resume → **100%** of held workflows reach `COMPLETED` with an empty DLQ. All DB/HTTP suites were **executed** against a real local Postgres 16 (Docker is unavailable in the authoring sandbox), and all three suites are registered in `.github/ci/integration-suites.txt` for the Docker-backed Linux run. **Out of scope (per the issue):** per-execution pause (#609/#383), halting new workflow starts (#377/#618), fast-fail semantics (#369), schedule/cron pausing (#229), automatic health-driven pause, weighted multi-queue draining (#515), and crediting paused time back to `schedule_to_close` (#378) — this slice keeps the absolute SLA deadline ticking and suspends only the relative `schedule_to_start` timer. **Post-review hardening (three parallel review agents — correctness/concurrency, API surface/security, AC compliance — two findings reproduced empirically against Postgres 16).** (1) **P1, the enforcer's queue-pause re-check was not authoritative.** Its doc comment claimed parity with the execution-pause re-check, but that sibling works precisely because *both* sides lock the same execution row; `pause_queue` shares no row with `enforce_activity_timeout`, so the non-locking `is_queue_paused` read did not serialize — a reviewer reproduced a pause committing 38 ms into the enforcer's post-recheck write sequence and terminally `ScheduleToStart`-failing a task on the now-paused queue, violating AC2/AC3/AC4 during exactly the backing-up-backlog scenario the feature exists for. Fixed with a shared transaction-scoped advisory lock, `lock_queue_for_pause` (`pg_advisory_xact_lock(hashtext(queue_name))`, mirroring the `concurrency_key`/`ctx.mutex` patterns), taken by `pause_queue`, `resume_queue`, and the enforcer before its re-check — and, in the enforcer, **only** on the `ScheduleToStart` path, so the far more common in-flight timeout paths never take it. Pinned by `a_pause_committed_after_the_scan_still_suppresses_the_timeout`, which holds the lock open across the enforcer's run. (2) **P2, a pause racing a resume returned 500 and left the queue live.** `INSERT ... ON CONFLICT DO NOTHING` does not lock the conflicting row, so a concurrent resume could delete it between the insert and the fallback `SELECT`, whose `get_result` then `?`-propagated `NotFound` — rolling the transaction back into an opaque 500 while the queue kept dispatching (reproduced). Collapsed to a single atomic `ON CONFLICT (queue_name) DO UPDATE SET queue_name = harvest_queue_pauses.queue_name RETURNING ..., (xmax = 0) AS newly_paused`: `DO UPDATE` takes the row lock, the no-op `SET` preserves the original provenance on a re-pause, and `xmax = 0` is the standard insert-vs-update discriminator. Pinned by `pause_racing_a_concurrent_resume_still_holds_the_queue`. (3) **P2, a partially-applied fleet-wide hold reported success.** If any shard succeeded the handler returned `200 {"ok": true}` with the detail buried in a `partial_failures` string — while writing its own audit row as `failed`. An operator would believe the hold was fleet-wide while the missed shards kept dispatching into the outage. Both mutations now return **`207 Multi-Status`** with `ok: false` and `status: "partial"`, reusing the read side's existing `complete`/`partial` vocabulary; a fully applied request keeps `200`/`ok: true`/`status: "complete"` and omits `partial_failures`. Re-issuing is safe (idempotent). (4) **P2, `queue_pause_target_pools` silently skipped router-known-but-poolless shards**, so mid a shard-add rollout a fleet-wide pause returned an *unqualified* success with no diagnostic at all — strictly worse than a partial failure. It now derives its target set from `shard_fanout::expected_shards` (the same helper the read path uses for exactly this reason) and reports an unreachable-but-known shard as a partial failure; naming such a shard explicitly is now a `503` rather than a misleading `400 "unknown shard_id"`. (5) **P2, rejected attempts were unaudited.** A malformed body, blank/oversized queue name, missing reason, or unroutable shard all returned without a trace — on a route whose whole purpose is a fleet-wide dispatch kill switch, the rejected-attempt trail is what an incident review needs. New `write_queue_pause_rejection_audit` writes a `STATUS_FAILED` row on every rejection path (symmetric with `fail_activity_now`'s malformed-id handling). (6) **P2, the operator `reason` bypassed the shared 500-char `truncate_operator_reason` cap** that every other durable operator reason on the router uses — it is stored, re-serialized on every read poll, and rendered into the Vantage Workers page, the very page an operator lands on during a queue-pause incident. Now capped at the API boundary. (7) **P3, the queue name was validated trimmed but stored untrimmed**, so `--queue "payments "` inserted a row matching no task and reported a successful hold (`newly_paused: true`, `held_task_count: 0`) on a queue that kept dispatching. `validate_queue_name` now *returns* the canonical trimmed name and every read and write uses it. Pinned by `a_padded_queue_name_still_holds_the_real_queue`, which asserts the *unpadded* queue is genuinely held. (8) **CI-breaking: `queue_pause_success_metric_tests.rs` was missing its `#![cfg(feature = "db")]` gate** while importing the `db`-gated `integration_e2e` helpers — an unresolved-import compile failure on all three OSes of the `--no-default-features` CI leg. Added. (9) The same suite was not hermetic on a shared `HARVEST_TEST_DATABASE_URL` database (it scrubbed only `harvest_queue_pauses`), so a re-run inherited the previous run's `FAILED` rows and failed its own "zero tasks may transition to FAILED" assertion. It now scrubs every fixture it owns; CI's fresh testcontainer never needed this. (10) The `schedule_to_close`-keeps-ticking caveat was documented in code and the API contract but **absent from both operator runbooks**, which said a pause is "safe — nothing fails" — the one place an operator could lose work by trusting the runbook. Called out explicitly in both. **Coverage added for the gaps the AC audit named:** the AC7 multi-shard *write* path (a shard-scoped hold applies fully and reports its scope; a partially-applied fleet-wide hold is `207`; an unknown shard is `400` and audited), the AC4 locked-re-check race, the atomic-upsert race, name canonicalisation, rejected-attempt auditing, and the reason cap. **Clippy:** extracting the claim SQL into a shape-testable `const fn claim_task_query()` moved a 144-line string literal out of `claim_task`, which carried `#[allow(clippy::too_many_lines)]`; the allow moved with it.

**Post-review hardening (Codex automated review, PR #1135) — three findings, all genuine, all fixed:**

1. **P1 — a claim already in flight could beat the pause.** `claim_task` is a single autocommit statement, so under `READ COMMITTED` its whole CTE — including the pause anti-join — evaluates against **one snapshot taken at statement start**. A pause committing after that snapshot is invisible to it, so a claim already in flight when the operator paused still transitions its task to `RUNNING` and hands it to a worker that dispatches into the outage. The window is normally sub-millisecond but is unbounded in principle: the claim's rate-limit debit can block on a row lock held by a competing claim, and Postgres's `EvalPlanQual` re-check on unblock only re-evaluates conditions on the *locked row*, never a correlated subquery over another table. **Codex's literal suggestion — take the queue-scoped lock inside the claim path — was rejected**: it would serialize every claim for a queue against every other, defeating `FOR UPDATE SKIP LOCKED`'s parallel claiming for a feature that is inactive almost all of the time. Fixed instead with a post-claim authoritative re-check in a **fresh statement** (hence a fresh snapshot): new `queue_pause::release_claim_if_queue_paused`, one guarded `UPDATE` that returns the task to `PENDING` and **restores the `attempt`** the claim consumed (a hold must not burn retry budget — AC3), guarded on `state = 'RUNNING' AND worker_id = $2` so it can only ever undo *this* worker's own claim. Wired inside `claim_task` itself so the guarantee is a property of the primitive rather than of one caller; a released claim surfaces as `Ok(None)`, which both worker call sites already treat as "nothing to dispatch". Cost: one indexed primary-key probe per *successful* claim (never per empty poll). The contract becomes crisp: **a pause committed before the re-check's statement begins always wins**; one that commits after did not beat the claim, and AC2 explicitly allows an already-`RUNNING` task to finish naturally. The rate-limit token the claim debited is not refunded — the same safe-side, self-healing leak already documented for a lost claim in `claim_task` (it only ever under-dispatches). Tests: `a_pause_committed_mid_claim_still_holds_the_task` reproduces the race **deterministically end-to-end** by stalling the claim mid-statement on its rate-limit debit (the one part of the CTE that can block, since the candidate scan uses `SKIP LOCKED`) — hold the bucket row from another transaction, start the claim, commit the pause while it is parked, then release the bucket — plus `a_claim_that_beat_the_pause_is_released_with_its_attempt_restored`, the no-regression guard `an_ordinary_claim_is_not_released_when_the_queue_is_not_paused`, and a SQL-shape drift lock.

2. **P2 — ABBA deadlock between the timeout enforcer and resume.** `enforce_activity_timeout` locked the execution row, then the task row, and only then took the queue advisory lock; `resume_queue` takes the advisory lock first and *then* row-locks every `PENDING` task on the queue via its `scheduled_at` shift. Reaching those locks concurrently, enforcement would hold a task row while waiting on the advisory lock and resume would hold the advisory lock while waiting on that task row — Postgres breaks the cycle by aborting one, failing either the timeout pass or the operator's resume request. Fixed by hoisting the `ScheduleToStart` queue-pause check to the **top** of the enforcement transaction, so both paths take advisory-then-rows; also cheaper, since a held task now bails before the row locks and the history load. The ordering convention is documented at both sites (matching the `harvest_external_tasks` task-row→execution-row note from issue #609). Test: `enforcer_takes_the_queue_lock_before_the_row_locks_no_abba` proves the ordering deterministically without provoking an actual deadlock — hold the advisory lock, start the enforcer so it blocks on it, then probe both row locks with `FOR UPDATE NOWAIT` from a third connection and assert both are still free (mirrors the issue #779 `materializer_locks_execution_row_before_timers_no_abba` probe).

3. **P2 — divergent per-shard pause provenance was silently discarded.** The list handler merged by queue name with `or_insert_with`, keeping whichever shard the fan-out reached first and dropping the others' reason/actor/scope while still listing every shard id. That state is produced by the feature's *own* idempotency rule: a re-pause deliberately preserves the **original** provenance, so a fleet-wide hold landing over a pre-existing shard-scoped hold leaves that shard telling a different story — and the `shard_id` parameter explicitly supports pausing one queue on two shards separately. Showing only one of them hands the operator a reason and scope that are not true for part of the fleet. Fixed with a pure, unit-tested `merge_paused_queue_rows`: the top-level summary is the **earliest** hold (a deterministic rule, and the same one the Vantage banner uses, so the two surfaces never disagree), `shards` carries each shard's own `{shard_id, reason, paused_by, paused_at, scope_shard_id, held_task_count}`, and `provenance_uniform` is a single field a script can gate on. Uniformity compares `(reason, paused_by, scope_shard_id)` and deliberately **not** `paused_at` — each shard stamps its own `NOW()`, so including it would report almost every healthy fleet-wide hold as divergent. `docs/api-contract.json` notes updated. Tests: 4 pure no-DB tests covering the uniform fleet-wide collapse, the divergent case (earliest-wins summary + per-shard preservation + `provenance_uniform: false`), distinct queues staying separate, and empty.

**Post-review hardening, round 2 (Codex automated review of `26faefb`, PR #1135) — two findings, both genuine, both fixed:**

4. **P2 — the pause response echoed the request's scope, not the effective one.** `pause_queue` is idempotent and deliberately preserves the **original** row on a re-pause, and the handler already echoed the preserved `reason`/`paused_by`/`paused_at` from that row — but it serialized `scope_shard_id` from the *request*. So re-pausing a hold scoped to shard 0 with a fleet-wide request (no `shard_id`) returned `newly_paused: false` and the original reason/actor/time alongside `scope_shard_id: null`, describing a hold that covers one shard as though it covered the fleet. That is precisely the mis-read that lets an operator believe an outage is contained when part of the fleet is still dispatching into it. The core is not at fault — `pause_queue`'s `ON CONFLICT DO UPDATE SET queue_name = harvest_queue_pauses.queue_name RETURNING ... scope_shard_id` leaves the column untouched and returns the stored value, which its doc comment already documents as "the effective value (the original on a re-pause)". Fixed by serializing `effective.scope_shard_id` so the whole response describes one coherent row. `docs/api-contract.json`'s `idempotency` note now states the guarantee explicitly. The resume response was audited for the same class and carries no `scope_shard_id`, so it is unaffected. Test: `an_idempotent_repause_echoes_the_effective_scope_not_the_request` (RED-verified — it failed on exactly the `scope_shard_id` assertion before the fix).

5. **P2 — the Vantage banner attributed a fleet-wide held total to one shard's story.** The finding is the UI-side twin of round 1's item 3: `merge_paused_queue_banner_rows` summed every shard's held tasks but labelled the total with only the earliest shard's reason and actor, giving an operator no indication that the displayed provenance applied to part of the fleet. Having just fixed the API to expose per-shard provenance and a `provenance_uniform` flag for exactly this supported case (two shards holding one queue with different reasons, whether via `shard_id` scoping or the idempotent re-pause), the banner had become the inconsistent surface — and it is the one an operator actually lands on during an idle-worker incident. Fixed by mirroring the API's merge rule exactly: the banner merge now takes `(shard_id, row)` pairs so the earliest-wins summary is tie-broken by shard id (deterministic, never fan-out-order dependent) and computes the same `provenance_uniform` over `(reason, paused_by, scope_shard_id)` — deliberately **not** `paused_at`, since each shard stamps its own `NOW()`. `PausedQueueBannerRow` gains `scope_shard_id` and `provenance_uniform`; the rendered banner gains a **Scope** column (`fleet-wide` or `shard N`) and, when a row's shards disagree, marks the reason and actor cells `(mixed across shards)` plus a summary count pointing at `GET /admin/queues/paused` for the per-shard detail. A uniform hold renders exactly as before apart from the new Scope column. Tests: `divergent_shard_provenance_is_flagged_and_visibly_marked` (asserts both the flag and the rendered marking) and `differing_paused_at_alone_does_not_flag_divergence` (the guard that keeps a healthy fleet-wide hold from being falsely marked, pinning the API/UI rule parity).

**Post-review hardening, round 3 (Codex automated review of `4fabb85`, PR #1135) — two findings, both genuine, both fixed:**

6. **P2 — a fleet-wide re-pause labelled a fleet-wide held total with one shard's story.** The mutation-response twin of round 1's item 3 (which fixed the *list* endpoint) and round 2's item 5 (which fixed the *Vantage banner*): with those two done, the pause **mutation** response had become the last surface still collapsing divergent provenance. `apply_pause_across_shards` summed `held_task_count` across every shard but kept only the **first successful** shard's `PauseOutcome` for the top-level `reason`/`paused_by`/`paused_at`/`scope_shard_id`. That state is produced by the feature's own idempotency rule — a re-pause preserves each shard's **original** provenance — so a fleet-wide request landing over pre-existing scoped holds legitimately leaves the shards disagreeing, and the response would then pair a fleet-wide total with shard 0's reason, actor, timestamp and scoped `scope_shard_id`, none of which are true for the rest of the fleet. Worse, "first successful" is fan-out-order dependent, so the same request could report different provenance on successive calls. Fixed by keeping every shard's outcome (`PauseApplication.per_shard: Vec<(i32, PauseOutcome)>`) and summarising with the pure, unit-tested `summarise_pause_provenance`: the top-level summary is the **earliest** hold tie-broken by shard id — the *same* rule `merge_paused_queue_rows` and the Vantage banner already use, so all three surfaces now agree by construction — `shards` carries each shard's own `{shard_id, newly_paused, reason, paused_by, paused_at, scope_shard_id, held_task_count}`, and `provenance_uniform` is a single field a script can gate on. Uniformity compares `(reason, paused_by, scope_shard_id)` and deliberately **not** `paused_at`, since each shard stamps its own `NOW()` — including it would flag almost every healthy fleet-wide hold as divergent. Both new fields registered in `management_api_response_fields()` and `docs/api-contract.json`. **Post-review hardening, round 9 (two Codex P2 findings, both confirmed genuine and both in the same failure direction as the earlier rounds — the operator's hold reports success while dispatch keeps flowing, or the hold fails opaquely):** (1) **The resume-time `scheduled_at` shift charged the resume's own runtime to every held task.** `resume_shift_scheduled_at_query` measured the thaw with `NOW()`, which is `transaction_timestamp()` — frozen at transaction *start*, i.e. before `resume_queue` waits on the advisory lock, before the pause-row `DELETE`, and before the bulk `UPDATE` runs — yet the hold stays in force until that transaction **commits**. Every second the resume itself spends was therefore omitted from the credit, so any task whose `schedule_to_start` is shorter than the resume's runtime timed out the instant the queue thawed: precisely the AC3/AC4 promise ("never failed *solely because* of the pause") being broken by the thaw itself. The same frozen value also excluded rows that fell due *during* the transaction from the `scheduled_at <= NOW()` predicate. Verified empirically rather than assumed, because Postgres clock semantics decide the fix: `NOW()` held steady across a 2 s in-transaction wait while `clock_timestamp()` advanced by 2.01 s; and replaying the shift arithmetic showed a task with a genuine 100 s pre-pause wait reading as **103 s** after a resume that spent 3 s on the lock, versus **100 s** with the live clock. Fixed by using `clock_timestamp()` for both the credit and the due-ness predicate — volatile, so it is re-read per row at execution time, after the lock is held and as the scan progresses. It remains a deliberate **lower bound**: the true thaw instant is commit time, which no in-statement expression can know, so a row is under-credited by at most the remaining duration of the `UPDATE` — the *safe* direction, since over-crediting past commit would push `scheduled_at` into the future and make the task **un**claimable (the inverse of AC5). The `<= clock_timestamp()` result still holds in every branch, so the never-pushed-into-the-future invariant is preserved. (2) **A reason padded past the truncation cap turned an audited 400 into a 500 with the queue still dispatching.** The route validates the reason for non-emptiness and then bounds it with `truncate_operator_reason` (500 chars) before the core sees it, while the core independently re-rejects a whitespace-only reason — so validating the raw string and truncating a *different* one let the two disagree: 500+ leading spaces followed by real text passed the check (it trims to something), truncated to pure whitespace, and was then rejected by every shard, surfacing as `500 "queue pause failed: shard 0: invalid configuration: a queue pause requires a non-empty reason"` at exactly the moment the operator needed the hold. Fixed by normalizing (`trim`) in `parse_pause_request`, the same place the non-empty rule is enforced, so the value that was validated **is** the value that is stored — which makes the failure impossible *by construction* rather than by adding a second check: a trimmed non-empty string starts with a non-whitespace character, so every non-empty prefix of it still contains one. It also stops padding from evicting the operator's actual words from the 500-character budget (`490 spaces + "Stripe outage"` now stores `Stripe outage`). Scoped deliberately to this route rather than to the shared helper: an audit of all four `truncate_operator_reason` call sites found queue-pause is the only one that pairs truncation with a non-empty precondition (erase-payloads, legal-hold and force-fail all take an optional reason whose core path does not re-reject whitespace), so changing the shared helper would have altered three unrelated routes' stored values for no benefit here. Tests, both RED-verified: the pure `resume_shift_never_uses_the_frozen_transaction_clock` (forbids `NOW()`/`transaction_timestamp()`/`statement_timestamp()` and requires the live clock in *both* positions, since a frozen predicate silently skips rows that fall due mid-transaction) and the behavioural `resume_credits_the_time_the_resume_itself_spends_waiting`, which injects the delay the way production does — by holding the very advisory lock `resume_queue` takes — and first asserts the injected delay exceeds its own tolerance so a slow runner fails loudly rather than silently stopping falsifying anything (RED: `expected ~100s of genuine pre-pause wait preserved, got 102s`); plus the pure `trimming_before_truncation_can_never_yield_a_whitespace_only_reason` (which also asserts the pre-fix ordering *is* broken, so the guard cannot be vacuous) and `trimming_keeps_the_operator_words_inside_the_budget`, and the HTTP `a_reason_padded_past_the_cap_still_holds_the_queue`, which asserts the hold is genuinely in effect afterwards and that a truly blank reason is still the audited 400 (RED: the reviewer's predicted 500, verbatim).

**Post-review hardening, round 10 (three P2s):** (1) **Credit tasks enqueued during the thaw.** `resume_queue`'s `scheduled_at` shift ran once, so a task enqueued after that statement's snapshot but before the transaction committed got no credit at all — even though it was genuinely held: the pause row's `DELETE` is uncommitted for the rest of the resume, so a concurrent claimer's snapshot still sees the hold and skips the queue. Uncredited, such a task thaws carrying its full apparent wait and the `schedule_to_start` scanner can kill it for time it spent held — the exact AC3/AC4 failure the shift exists to prevent. Fixed with a **narrowing second pass**, `resume_shift_late_arrivals_query`, run last (so it sees the freshest snapshot) and **disjoint** from the primary shift by `created_at` vs `transaction_timestamp()`: the primary pass gained `AND (created_at IS NULL OR created_at < transaction_timestamp())` and owns only the backlog that existed when the resume began, while the new pass owns everything enqueued during it (see the partition-totality note below for why the `IS NULL` arm is required rather than cosmetic). The partition is load-bearing — the primary pass's `+=` credit is *relative*, so applying it to a row twice would erase the pre-pause wait it exists to preserve, and it makes the summed `released_task_count` exact rather than double-counting. The frozen `transaction_timestamp()` is exactly "when this resume began", so the same property that made it *wrong* for the credit amount in round 9 makes it precisely *right* as the partition marker, with no extra bind or round trip. The late-arrivals pass is an **absolute** `SET scheduled_at = clock_timestamp()`, not the relative delta: a row created during the hold has no pre-pause wait to preserve (it was held from the moment it became due, so it accrues none), and an absolute assignment is idempotent under repetition — it can only move `scheduled_at` to a later instant that is still `<= clock_timestamp() <= commit time`, never into the future. **Irreducible residual, documented not eliminated:** this narrows the uncredited window from "the whole bulk `UPDATE`" to "this final, small statement", but a row committed after *its* snapshot and before commit is still held and still uncredited; the under-credit is bounded by that statement's remaining runtime (microseconds when there are no late arrivals) and is in the same safe direction as round 9's lower-bound credit. Closing it completely would mean serializing **enqueue** behind the queue's advisory lock — a queue-scoped serialization point on the hot enqueue path for every task on every queue, paused or not, which is the exact trade this module's design notes already reject for the claim path — so it is not worth paying for a sub-millisecond credit. (2) **State the `schedule_to_close` exception in the alert pack.** The `harvest_queue_paused_too_long` rule's `description` said a pause is safe because "nothing fails, retries, or dead-letters" — true of the relative `schedule_to_start` timer, which a pause suspends and credits back, but **not** of the absolute `schedule_to_close` deadline (issue #378), which keeps running during a hold. That is unsafe in the one alert an operator consults after the 1h/4h threshold, so the description now states the exception explicitly and tells the responder to check whether the held activities declare `schedule_to_close` and whether the remaining budget covers the outage — matching what the API contract and the runbook (`docs/runbooks/harvest-alerts.md#harvest_queue_paused_too_long`) already said. (3) **Surface pause-read failures in the Workers banner.** `load_paused_queues_from_shards` used `.ok()?`, so a shard whose connection or pause read failed contributed no rows. The loader now returns a `PausedQueueScan` carrying the failed shard ids alongside the merged rows, and `render_paused_queues_banner` renders a "Queue pause state incomplete" warning **first and even when there are zero rows** — naming the failed shards, saying a hold may be MISSING entirely, warning that a shown `Scope` can understate real coverage, and pointing at `GET /admin/queues/paused`. Same class as the round-7 eligibility fix, which propagated the failure rather than silently reporting "not paused". A bare `<` / `>=` split would therefore have left such a legacy row matching **neither** pass and credited by **neither**, silently regressing against the pre-partition query (which had no `created_at` predicate at all and shifted it). Tests: the DB `resume_credits_a_task_enqueued_between_the_two_shift_passes`, which drives the two passes by hand with an enqueue interleaved between them (the window exists only *inside* `resume_queue`'s transaction, so no end-to-end call can produce it) and first asserts the primary pass genuinely missed the row so the second-pass assertion cannot be vacuous, then asserts the late arrival accrues ~0s while the pre-existing backlog keeps its genuine ~100s pre-pause wait and both passes report exactly one row; the DB `resume_credits_a_legacy_task_with_no_created_at` (a row with `created_at` nulled out is still credited its 600s hold, counted as released, and claimable); the pure `the_two_resume_passes_partition_on_created_at`, `late_arrivals_pass_is_absolute_and_bounded` and `the_partition_is_total_for_a_null_created_at`, plus the round-9 frozen-clock guard refined to judge the SET clause and the WHERE clause separately (so the partition predicate's one legitimate use of the frozen clock is allowed while the credit arithmetic still may not touch it); the alert-pack anti-drift guard `queue_pause_alert_states_the_schedule_to_close_exception`, which pins the exception in **both** the rule description and the runbook section so the two cannot drift apart; and for the banner the pure `unreadable_shard_warns_even_with_no_visible_holds` and `unreadable_shard_warning_composes_with_a_visible_hold` (which also pins the ordering: "we do not know" outranks the partial-coverage detail it may itself explain) plus the end-to-end `ui_workers_warns_when_a_shards_pause_state_is_unreadable`, which renders the real Workers page against a two-shard pool with one unreachable shard and nothing paused on the reachable one — the exact silent-clean-page case — and asserts the warning appears while no hold is claimed.

**Post-review hardening, round 11 (three P2s — two fixed, one confirmed-narrow and documented rather than redesigned):** (1) **Stamp the pause time after acquiring the queue lock.** The pause row's `paused_at` came from the column's `DEFAULT NOW()`, i.e. `transaction_timestamp()`, frozen at transaction *start* — before `pause_queue` waits on the queue's advisory lock. So a pause that queued behind a concurrent claim or resume recorded a `paused_at` earlier than the instant the hold actually took effect. Worked the arithmetic rather than inheriting the reviewer's implied severity: with `paused_at` understated by the lock wait `L`, the resume credit `clock_timestamp() - GREATEST(scheduled_at, paused_at)` grows by up to `L`, but **both** branches of the `GREATEST` still clamp the result to `<= clock_timestamp()`, so the un-claimability hazard (the AC5 inverse) cannot materialise. The genuine harms are the two reported values an operator reads — the pause start and, downstream, `harvest_queue_paused_too_long`'s duration, both overstated by `L` — and an *understated* preserved pre-pause wait for a task due before the pause, which is the **safe** direction for `schedule_to_start`. Fixed by extracting the upsert into a shape-testable `pause_upsert_query()` that stamps `paused_at` from `clock_timestamp()` in the INSERT list, read *after* the lock is held. Deliberately only in the INSERT half: the `ON CONFLICT DO UPDATE` clause is a no-op `SET queue_name = harvest_queue_pauses.queue_name` (present solely to take the row lock and drive the `(xmax = 0)` insert-vs-update discriminator), so an idempotent re-pause still **preserves** the original `paused_at`, reason and actor rather than silently restarting the hold clock. Tests, both RED-verified against the reverted `DEFAULT NOW()` form: the pure `pause_upsert_stamps_paused_at_from_the_live_clock` (requires the live clock, bans all three frozen spellings) and `pause_upsert_does_not_restamp_paused_at_on_a_repause` (splits at `DO UPDATE` **and** again at `RETURNING` so only the conflict SET clause is judged, then asserts `RETURNING` still names `paused_at` so the guard cannot pass by deleting the projection); plus the DB `pause_stamps_paused_at_after_the_lock_wait_not_at_transaction_start`, which injects the delay the way production does — by holding the very advisory lock `pause_queue` takes — and first asserts the pause genuinely blocked so a fast runner fails loudly instead of silently stopping falsifying anything (RED: `got 85ms` against the required ~3000ms), and `a_repause_preserves_the_original_paused_at`. (2) **Report expected shards that have no local pool.** The round-10 banner loader created observations only from `pool.iter_shards()`, while the coverage calculation beside it deliberately expands the expected set with router-known shards (`expected_shards`) — so mid a shard-add rollout a shard the router advertises but this process has no pool for yet got no future at all, could never enter `unreadable_shards`, and if it was the *only* shard holding a queue the Workers page again rendered no pause warning whatsoever. That is the same presence-vs-coverage gap round 10 closed, reached through a missing pool instead of a failing read. Fixed by fanning out over the expected set, resolving pools through the API's own `crate::api::resolve_expected_shard_pools` (promoted to `pub(crate)`) rather than a second hand-mirrored copy of the rule — a poolless shard maps to `None` and is reported, never silently resolved through `ShardedDbPool::pool_for`'s default-shard fallback, which would query the *default* shard's database in its place and let coverage read `fleet`. The read half was split into `scan_paused_queues` so the reporting rule is directly testable: reaching a poolless-but-expected shard through `api_state` needs an installed runtime with a widened router, but the rule under test — *a `None` pool is reported, never dropped* — needs neither, and its counterpart (a router-known poolless shard resolves to `None`, not a fallback pool) is already guarded on the API side by `resolve_expected_shard_pools_flags_poolless_shard_not_default_fallback`. Tests, RED-verified by mutating the `None` arm to the pre-fix "contributes nothing" behaviour: `scan_reports_an_expected_shard_that_has_no_local_pool` (a poolless shard is reported, both failure kinds are reported sorted, and the banner is therefore non-empty) and `scan_reports_a_lone_poolless_shard` (the fold does not depend on some other shard producing a future). (3) **"Include tasks repended during the thaw" — confirmed narrow, doc corrected, query left alone.** The reviewer is right that the round-10 partition is not absolutely total: a row that is `RUNNING` in the primary pass's snapshot and re-pended afterwards is invisible to that pass, and carries a `created_at` predating the transaction, so it also fails the late-arrivals predicate. Rather than patch the feature's most load-bearing query for a third consecutive round, every re-pend path was enumerated: `queue::requeue_for_retry` (`scheduled_at = now + backoff`), `poison_pill` reclaim (`scheduled_at = now()`) and `primary_repend_workflow_task` (which refreshes `created_at` too, so it lands on the late-arrival side and *is* credited) all **refresh** `scheduled_at` to an instant inside the resume — such a row only became due during the thaw, accrued no held time, and is under-credited by at most this transaction's remaining runtime, the residual already documented for the late-arrivals pass. The single path that re-pends while *preserving* a pre-pause `scheduled_at` is `release_claim_if_queue_paused`, which does so deliberately so a released claim keeps the wait it had already accrued — and it is not reachable in this window in practice, because it runs in the same function call as the claim it undoes, so it fires at pause-creation time rather than hours later during a resume. Closing it exactly would need the primary pass to return its row ids for the second to exclude (`id <> ALL($ids)`), which does not scale to a large backlog; the tempting alternative of taking the queue's advisory lock inside the release is **wrong** and was rejected after reading the call site — that statement runs on *every* claim, so locking there would serialize claims per queue and defeat `SKIP LOCKED`, the exact trade `queue::claim_task`'s design already rejects. So the fix is to the over-claim, not the query: the doc now states the partition is total **within a single snapshot** and carries the per-path enumeration, the one theoretically-affected path, why it is practically unreachable, and both rejected remedies with their costs.

**Post-review hardening, round 12 (one Codex P2):** **Emit observed pauses despite an unrelated shard's read failure.** The `harvest.queue.paused` gauge sampler guarded its whole cycle with `if read_failed { continue; }`, which discarded the **positive** `record_queue_paused(queue, true)` emissions along with the zero-fill. So a queue genuinely held on a readable shard never set the gauge to `1` while any other shard's connection or pause read was failing — the dashboard showed nothing and `harvest_queue_paused_too_long` could not fire for the entire duration of an outage that had nothing to do with the paused queue. That is AC8 broken in precisely the compound-incident case an operator most needs it, and the third instance in this PR of the same class (round 10's silent Workers banner, round 11's unreported poolless shard): a shard read failure suppressing a *presence* signal. The distinction that makes the original guard wrong here — and right for its sibling — is that a pause is **boolean per queue**, so a hold observed on a healthy shard is true regardless of what an unreadable shard would have said; whereas `compute_active_gauge_emissions` (issue #770) reports a *count*, where a partial fan-out is a wrong number and skipping the tick is the only honest option. Fixed by extracting the decision into the pure, unit-tested `worker::compute_queue_pause_emissions` (mirroring that sibling's shape), which always emits the holds it observed and, on an incomplete scan, suppresses **only** the zero-fill: a queue absent from a partial scan may simply live on the shard we could not read, so reporting `false` would be the inverse lie ("the hold was released") during a database blip. Such a queue is *retained* in the returned previous-state set (**union**, not replace) so it is neither forgotten nor falsely cleared, and a later **complete** scan that finds it genuinely resumed zero-fills it exactly once rather than leaving it stale at `1` forever — a replace would have dropped it and lost the zero-fill entirely. `docs/telemetry.md`'s metric-catalogue row said "a read failure skips the whole tick", which the fix makes inaccurate, so it now states the emit-holds/suppress-zero-fill split and the retain-and-zero-fill-later behaviour. No metric name or label change, so the dashboard, the alert pack and their anti-drift guards are untouched. Tests: four pure guards in `worker.rs` — `queue_pause_emissions_report_observed_holds_on_an_incomplete_scan` (the RED discriminator: **fails** against the pre-fix skip-everything semantics), plus `..._never_zero_fill_on_an_incomplete_scan`, `..._zero_fill_once_on_a_complete_scan` and `..._zero_fill_a_forgotten_hold_after_recovery`, which hold under both the old and new behaviour and therefore guard the zero-fill suppression the fix must **not** regress.

**Post-review hardening, round 16 (three Codex P2s).** **(1) Advisory-lock namespace isolation.** `lock_queue_for_pause` took `pg_advisory_xact_lock(hashtext($1))` — the **1-argument** `bigint` keyspace, which is shared process-wide by every other feature that hashes a name into it. A queue name and a per-key concurrency key (`crate::queue`) that happen to hash to the same 64-bit value would serialize against each other for no reason, and — worse — a `pg_try_advisory_xact_lock` caller that loses to an unrelated queue-pause holder fails **silently** (it yields no task rather than erroring), so the symptom is a stalled queue with no diagnostic. Fixed by moving queue-pause onto the **2-argument** `(int, int)` keyspace, which is disjoint from the 1-argument one by construction: `pg_advisory_xact_lock($1, hashtext($2))` with `$1 = QUEUE_PAUSE_LOCK_CLASS` (`619`, a new `pub const` named for the issue). A collision now requires *another* feature to also claim class `619`, which is a visible, greppable constant rather than an invisible hash coincidence. Scope note: four features share the 1-argument keyspace today (`queue.rs` concurrency keys, `queue_pause.rs`, `wasm_store.rs` ×2, `mutex.rs`); only the one this PR introduces is moved — the other three are pre-existing and out of scope. Guarded by the shape test `queue_pause_lock_uses_its_own_advisory_namespace` (RED-verified: reverting to the 1-arg form fails it). **(2) Correlated held-task count.** `list_paused_queues_query`'s `held_task_count` aggregated `harvest_task_queue` **without correlating on queue name**, so every listed pause reported the whole shard's `PENDING` backlog rather than its own — an operator reading `GET /admin/queues/paused` during an incident would see an alarming, identical, and wrong number on every row. Fixed with a correlated scalar subquery (`WHERE t.queue_name = p.queue_name AND t.state = 'PENDING'`), which also drops the old `LEFT JOIN` + `GROUP BY` shape. RED-verified at both levels: the shape test `list_paused_queues_counts_per_paused_queue_not_the_whole_backlog` and the DB test `list_paused_queues_reports_reason_and_held_count` (2 held on the paused queue, 1 on an unpaused sibling, against a shared database carrying every other test's backlog) both fail against the uncorrelated query. **(3) Partition the resume shift semantically, not temporally.** The two-pass resume shift split its rows on `created_at < transaction_timestamp()` ("existed when this resume began"), which is subtly wrong: `created_at` records when the enqueuing `INSERT` *executed*, but whether a pass can **see** the row is decided by when that enqueuing transaction **committed**, and the two can straddle the resume. A row inserted *before* the resume began but committed *after* pass 1 took its snapshot satisfied **neither** predicate — invisible to pass 1, and excluded from pass 2 by its own `created_at` test — so it thawed carrying its entire uncredited held wait and could be schedule-to-start-failed the instant the queue came back, the exact AC3/AC4 failure the shift exists to prevent. Fixed by comparing `created_at` against the bound **`paused_at`** (`$2`) in both passes, which removes visibility from the question altogether: both values are fixed on rows that already exist, so a row's side is the same no matter which statement first observes it. It is also the more meaningful split — "did this task accrue wait before the hold, or was it held from birth?" — which is exactly the distinction the relative (`+=`) and absolute (`= clock_timestamp()`) formulas encode. The nullable-`created_at` arm (a legacy pre-`20260619000000` row belongs on the primary side) and the totality/re-pend analysis are unchanged. New DB test `resume_credits_a_task_committed_late_but_inserted_before_the_resume` constructs the straddle deterministically by holding the enqueuing transaction open across pass 1 — the only way to separate insert time from commit time — and is the behavioural guard the round-10 late-arrivals test could not be: that one's row is inserted **and** committed inside the window, so its `created_at` is after the resume's transaction start and the old predicate caught it too. RED-verified (against the reverted `transaction_timestamp()` partition it fails on `late_shifted == 1`, proving the row is dropped by both passes). **Test-fixture correction shipped with (3):** `backdate_scheduled_at` now moves `created_at` with `scheduled_at`, because that is the only shape a real row can have — `queue::enqueue` sets `created_at = NOW(), scheduled_at = NOW() + delay`, so a task that has been *due* for N seconds was necessarily *created* at least N seconds ago. Backdating `scheduled_at` alone fabricated a row claiming to have waited since before it existed; harmless while the partition keyed on `transaction_timestamp()`, but it decides the row's side now and silently moved pre-pause backlog fixtures onto the late-arrival side. A row whose `created_at` is already `NULL` keeps it, so the legacy-row test still constructs the pre-migration shape it is testing. **No new `WorkflowEvent` variant, no migration, no schema change** — all three are query-shape changes plus one new `pub const`.
 **Post-review hardening, round 17 (PR #1135, two Codex P2s — atomicity and wake-up).** Both are about what happens at the *edges* of the two mechanisms rounds 2 and 10 introduced, and neither changes the pause contract itself. **(1) Make the post-claim pause re-check atomic with the claim.** The round-2 P1 fix runs `release_claim_if_queue_paused` as a **separate statement** after `claim_task`'s claim query, deliberately: a fresh `READ COMMITTED` snapshot is the entire mechanism that lets the re-check see a pause the claim's own snapshot predated. But two *autocommit* statements are not atomic, so a re-check that **errors** (a transient DB failure, a connection reset, a `statement_timeout`) leaves the claim already durable: the row stays `RUNNING` with its attempt consumed, `claim_task` returns `Err`, and the worker never receives the task. Nothing recovers it in bounded time — the poison-pill reclaimer (#367) keys on a **missing worker heartbeat**, and this worker is alive and polling, so it never touches the row; `start_to_close`/`heartbeat_timeout` would eventually reclaim it, but both are **optional**, so an activity declaring neither strands indefinitely. Fixed by running the claim and the re-check inside **one** `diesel_async` `build_transaction().read_committed()` block: each statement still takes its own snapshot (the re-check keeps working exactly as before), and a re-check failure rolls the claim back to `PENDING` with its attempt restored. The isolation level is **pinned on the `BEGIN`** rather than inherited from `default_transaction_isolation` — a deployment configured for `REPEATABLE READ` would otherwise share one snapshot across both statements and the re-check would go blind to the pause, silently reinstating the round-2 P1 this guard exists to close (the two-autocommit-statement shape was immune to that by construction, so the isolation had to become explicit the moment they were wrapped). Cost is one extra PK-indexed probe of transaction lifetime on the claim path — the same statement that already ran, now inside a `BEGIN`. New DB test `a_failed_pause_recheck_rolls_the_claim_back_instead_of_stranding_it` reuses the round-2 mid-claim harness (hold the rate-limit bucket row so the pause commits while the claim is blocked, which is what makes the re-check fire at all) plus a `BEFORE UPDATE` trigger that raises only on the release-shaped update (`RUNNING -> PENDING` with `worker_id` cleared — a shape the claim's own `PENDING -> RUNNING` update cannot match); `claim_task` returns `Err` under both designs, so the assertion is purely on the row, which is exactly the finding. RED-verified. **(2) Ring the queue doorbell when a resume releases work.** A worker configured with `notification_database_url` parks in `QueueListener::wait_for_notification(poll_interval)` and re-polls only on a queue notification or the timeout. `resume_queue` flipped held rows to claimable but emitted **nothing**, so on a fleet tuned for a long `poll_interval` (the whole point of running with LISTEN/NOTIFY) the thawed backlog sat idle for up to a full interval after the operator declared the outage over — dashboard green, nothing moving. Fixed by emitting the existing `notify::notify_task_enqueued` **inside the resume transaction**, gated on the resume actually having released rows: Postgres queues `NOTIFY` and delivers it at `COMMIT`, so listeners wake exactly when the hold lifts — never earlier (an early wake would still see the uncommitted pause row and skip the queue) and never at all if the resume rolls back. **Post-review hardening, round 22 (one Codex P2, confirmed genuine):** **The `schedule_to_start` sweep could deadlock a concurrent per-execution resume.** The documented `harvest_task_queue` lock order is **execution row → task row**, and `resume_workflow_execution` (issue #383/#609) follows it: it takes the execution row `FOR UPDATE` and then shifts that execution's task rows with `shift_schedule_to_close_on_resume_query`, a plain **waiting** `UPDATE` — unlike its external-task sibling `shift_external_schedule_to_close_on_resume_query`, which was given `FOR UPDATE SKIP LOCKED` in the issue #609 round-9 hardening precisely so it could never join a lock cycle. ### Round 23 — Codex automated review (94ba32f)

Two P2s, both in `queue_pause.rs`, both genuine.

- **P2 — a resume materialised one UUID per shifted task in the API process.**
  The two-pass `scheduled_at` shift needs pass 2 to exclude exactly the rows
  pass 1 shifted (round 19: a `created_at` predicate cannot do that job), and it
  was carrying that set through this process — `RETURNING id` loaded into a
  `Vec<Uuid>`, then re-serialised onto the wire as an array bind for `unnest`.
  Linear in the released backlog *twice over*, all while the resume holds the
  queue's exclusive advisory lock. A multi-million-row outage backlog is exactly
  the case an operator reaches for this feature in, and exactly the case where
  that allocation could exhaust the API process or blow the bind size — failing
  the resume and rolling back the thaw. Worth noting the module had already
  refused `RETURNING id` on the notify path for this reason (round 11,
  `resumed_queue_notify_task_query`); the shift path just never got the same
  treatment.

  The passes genuinely need two statements — pass 2 exists to catch rows that
  committed after pass 1's snapshot, and one statement has one snapshot — so
  merging them into a CTE would defeat the round-19 fix. Fixed instead by
  keeping the id set **server-side**: pass 1 is now a data-modifying CTE feeding
  a transaction-scoped scratch table (`resume_shifted_scratch_query`,
  `ON COMMIT DROP`), and pass 2 anti-joins against that table instead of an
  array bind. Application-side memory is O(1) in the backlog, and the lock hold
  shrinks by the round trip removed. The `PRIMARY KEY` is not for uniqueness
  (the ids are unique by construction) but to bound the plan: a fresh temp table
  has no statistics, and the index keeps even a nested-loop anti-join at
  O(rows × log ids) rather than the O(rows × ids) scan round 19 rejected
  `<> ALL` for.

- **P2 — two queue names could share one advisory lock.** Round 16 put this
  feature's lock in the two-argument `pg_advisory_xact_lock(int, int)` keyspace
  under a dedicated class id, because the single-argument `bigint` keyspace is
  already shared unnamespaced by several features — most importantly
  `claim_task`'s own `concurrency_key` gate. That separation is load-bearing and
  still is. But spending 32 of the 64 bits on a constant class left **queue
  identity** at the 32 bits of `hashtext`, so two unrelated queue names collide
  with probability ≈ n²/2³³ — and the consequence is precisely the failure this
  feature exists to prevent. An exclusive pause on queue `a` makes
  `try_lock_queue_for_claim` fail for the colliding `b`, and since that call is
  the *try* variant the failure is silent: `b`'s workers release every claim and
  stop dispatching for the length of an unrelated pause or resume, on a queue
  that was never paused.

  Fixed by spending **both** slots on identity: `queue_lock_keys` derives
  `(key1, key2)` from the halves of a domain-separated SHA-256 digest, so a
  false share now needs a 64-bit collision. Two rejected alternatives are worth
  recording. A *pair* of class-scoped locks (32 identity bits each) would make
  it **worse** — lock conflicts are per key, so a claim needing both fails if
  **either** collides, doubling the false-share probability rather than squaring
  it away. The *single-argument* 64-bit form gives the same width but drops us
  into the keyspace `claim_task` already hashes into, trading an intra-feature
  collision for a cross-feature one with a worse blast radius. SHA-256 over a
  fast hash for the same reason issue #699's rate-limit bucket keys use it: a
  collision here silently shares state between unrelated queues, and it is
  computed once per lock call in-process, so it costs nothing next to the round
  trip it rides on.

  Dropping the class id costs the self-identifying `619` in `pg_locks`, which is
  recovered differently: `objsubid = 1` is the two-key form, and this feature is
  its only user, so `locktype = 'advisory' AND objsubid = 1` selects exactly the
  queue-pause locks. That "only user" claim is no longer a convention — a source
  guard walks the crate and fails if any other module reaches for the
  two-argument form.

Both are RED-verified. The collision fix's money test is **self-falsifying**
rather than depending on a code revert: it *searches* Postgres for a real
`hashtext` collision (a 32-bit space, so ~300k candidates finds several),
asserts the pair genuinely collides, then demonstrates the pre-fix key stalling
the unrelated queue **live** — holding `pg_advisory_xact_lock(619, hashtext(a))`
and showing `pg_try_advisory_xact_lock_shared(619, hashtext(b))` fails — before
asserting the shipped key does not, while still excluding claims on the queue
actually being paused. The scratch table's own test drives three resumes
back-to-back on one pooled connection, which fails without `ON COMMIT DROP`.
