## Phase 3.55 — Per-activity-type pause/resume for surgical incident containment (issue #807)

**Implemented.** An operator can hold dispatch for a **single activity type**, fleet-wide, while a scoped downstream dependency is down — leaving every other activity type sharing the same task queue flowing untouched. It is the surgical sibling of the queue pause (issue #619): reach for the queue pause when the whole queue's dependency is down, and for this when one broken downstream would otherwise force you to stop healthy work too. New admin-gated routes `POST /api/harvest/activities/{activity_name}/pause` and `/resume`, reads `GET /api/harvest/activities` and `/activities/{activity_name}`, and CLI parity `harvest activity pause|resume|list|get`.

**Invariants — no new `WorkflowEvent` variant, no replay-determinism impact.** A pause is a **claim-layer dispatch gate**, not an execution event: nothing is appended to `harvest_events`, so the append-only invariant, the adjacently-tagged event JSON contract, and every replay path are untouched by construction. One additive migration (`20260722000000_harvest_activity_pause`) creates `harvest_activity_pauses (activity_name TEXT PRIMARY KEY, reason, paused_by, paused_at, scope_shard_id)`. No `schema.rs`/`models.rs` entry — the module is 100% raw `sql_query`, matching the queue-pause precedent.

**Held, never failed.** While an activity type is paused, `queue::claim_task` does not claim its tasks: they stay `PENDING` and are never failed, retried, or dead-lettered. An already-`RUNNING` attempt finishes naturally — a pause is a *dispatch* gate, so it can neither observe nor abort work already handed to a handler. On resume the time each task spent held is credited back to its `scheduled_at`, so the thaw does **not** retroactively schedule-to-start-time-out the backlog. The `schedule_to_start` timeout scanner carries the same anti-join, so a held task cannot be timed out *while* held either. **The absolute `schedule_to_close` deadline (issue #378) keeps ticking** — a pause is not an SLA extension, and the runbook and route description both say so.

**The `'mixed_signal_suspension'` sentinel hazard — found and closed.** A *workflow* task can carry a non-NULL `activity_name`: the engine stamps that sentinel there (`queue.rs`). Reasoning about the pause predicate purely through SQL's NULL semantics (`NULL = ANY(...)` → `NULL` → `NOT NULL` → `NULL` → row excluded) therefore protected workflow tasks only by a **naming coincidence** — pausing an activity literally named `mixed_signal_suspension` would have frozen every mixed-suspension workflow task fleet-wide. Every copy of the predicate is instead scoped by `task_type = 'activity'`: the shared renderer `activity_pause::activity_pause_anti_join`, the inline `MATERIALIZED` CTE in `claim_task`, the `schedule_to_start` scan, both read-path mirrors, and the plugin's eligibility-explainer copy. Three drift guards (`queue.rs`, `timeout.rs`, plugin) assert each site still matches the shared renderer, and a DB test (`a_pause_never_holds_a_workflow_task_even_with_the_sentinel_name`) pauses an activity by exactly that name and proves the workflow task still dispatches.

**Barrier design — three layers, no advisory lock, documented residual.** (1) A `MATERIALIZED` CTE pre-filter in the claim query (hot path). (2) A post-claim, fresh-statement re-check (`release_claim_if_activity_paused`) that releases a claim taken in the pre-filter's snapshot window, restoring `attempt = GREATEST(attempt - 1, 0)` and guarded on `state = 'RUNNING' AND worker_id = $2` so it can only ever release *this* worker's own claim. (3) A fresh in-transaction re-check (`is_activity_paused`) in the `schedule_to_start` enforcer, placed after the queue re-check and before the unlocked expiry re-read. **No new advisory lock is taken**, deliberately: the CI guard `queue_pause_owns_the_two_argument_advisory_keyspace` walks all of `src/` and hard-fails on a second two-argument user, the single-argument keyspace is already shared by five subsystems, and a lock here would impose a fleet-wide queue-before-activity ordering rule on every future contributor to avoid ABBA. The residual window is documented precisely on `is_activity_paused`: it is bounded by one statement's snapshot — a pause committing between that read and the enforcement transaction's `COMMIT` is not observed, so one *already-scanned* task can still be schedule-to-start-failed, and one *already-claimed* task can still dispatch. Both are bounded by a single sub-millisecond round trip and by one task per racing worker; the leaked task's next attempt is held like any other. The resume direction needs no barrier at all, because a task released a moment early is simply claimed a moment early.

**Resume credits late arrivals too — a second pass (PR review, Codex P1).** Under READ COMMITTED each statement takes its own snapshot, so a task enqueued *after* the primary shift began but *before* the resume's pause `DELETE` commits is invisible to that pass while still being genuinely held (every other session still sees the uncommitted pause row and still skips it). With a single pass such a row thawed carrying its whole held wait, and the `schedule_to_start` scanner could terminally fail it the instant the hold lifted — the exact failure the credit exists to prevent, and widest on a large backlog where the bulk `UPDATE` and the per-queue notification pass keep the transaction open longest. `resume_shift_scheduled_at_query` now `RETURNING id`s the rows it shifted and `resume_shift_late_arrivals_query` credits every other due `PENDING` row, excluded **by id rather than by predicate** — which makes coverage total for *any* commit order, since "which rows a statement saw" is a question about visibility, not about the row. Adopted wholesale from the queue-pause sibling's own two-pass design (issue #619 rounds 16/19), including the `NOT EXISTS (… unnest …)` spelling (a hash anti-join, O(rows + ids), rather than `<> ALL`'s per-row array scan). The residual it cannot close — a row committing after *this* statement's snapshot — is bounded by that one small statement, errs in the same safe direction, and is documented rather than eliminated: closing it would mean serializing **enqueue** behind an activity-scoped lock, putting a serialization point on the hot enqueue path for every task, paused or not.

**The read model reports real coverage, not stored intent (PR review, Codex P1).**
A fleet-wide pause that only reaches some shards returns `207` at mutation time,
but the rows it *did* write are byte-identical to a complete hold
(`scope_shard_id = NULL`) and the shards it missed hold no row at all. A later
read that reaches every shard therefore has a `complete` status and rows that
agree, so a read driven by "any shard has a row" would present a clean
fleet-wide hold while part of the fleet keeps dispatching the very activity the
operator believes they stopped. Both read endpoints now derive an
`effective_scope` (`fleet` / `partial_fleet` / `shard`) from the shards that
actually hold the activity versus `shard_fanout::expected_shards`, by **reusing**
`queue_pause::classify_pause_coverage` rather than restating the rule — so the
activity and queue read models can never disagree about what "fleet-wide" means.
An unheld activity reports `null` (no hold, no coverage), mirroring the other
null provenance fields. `harvest activity list` gains a `SCOPE` column for the
same reason `LOCAL` has one: it is the second way `PAUSED: yes` can be a lie, and
leaving it to `--json` would hide the one field that contradicts the headline
answer behind a flag nobody reaches for mid-incident. The three read models that
need an expected-shard set now share one `expected_shard_ids` helper.

**The down migration drops the index too (PR review, Codex P2).** `idx_harvest_tq_activity_pause` lives on `harvest_task_queue`, which this migration does not own, so dropping `harvest_activity_pauses` alone left it behind. A rollback that leaves an index on a hot, high-write table has not restored the previous schema — the deployment keeps paying its storage and per-`INSERT` maintenance cost for a feature that is no longer there.

**Multi-queue thaw.** A paused activity's held tasks can span multiple queues (a per-call `queue_override` sends the same activity type to different queues), so the resume doorbell selects `DISTINCT ON (queue_name)` and rings **every** queue the activity spans, not just the first. Pinned by `resume_releases_the_backlog_on_every_queue_the_activity_spans`.

**Circuit-breaker composition (issue #369).** An operator pause **wins over** a tripped breaker: the task is held at claim, before dispatch, so the breaker never gets to fast-fail it into an `ActivityFailed`. Resuming a pause does **not** auto-close a tripped breaker — the breaker's own half-open probe still governs recovery, so a resume cannot accidentally re-arm a broken dependency. Precedence is pinned by a DB test. The no-auto-close direction is pinned *structurally* instead — a behavioural test cannot fail there, because `resume_activity` takes a connection and no registry handle, so asserting "the breaker is still open afterwards" would pass against an empty function body and would still pass if breaker-clearing were later wired in at the plugin layer. The shipped test asserts the property that actually guarantees it: `activity_pause.rs` contains no code path to a `CircuitBreakerRegistry` at all.

**Idempotent, with provenance preserved.** Re-pausing an already-paused type is a `200` no-op returning `newly_paused: false` and preserving the **original** reason, operator, `paused_at`, and `scope_shard_id` — the response always describes the hold actually in effect, never the request. Resuming an unpaused type is a `200` no-op (`newly_resumed: false`). The resume response echoes `released_reason`/`released_paused_by`, because the pause row is deleted by the resume and that is the last moment the *why* is recoverable (its permanent home is the audit row).

**Partial application is `207`, never `200`.** A hold that did not reach every shard is not in effect fleet-wide — the shards it missed keep dispatching into exactly the outage the operator is riding out. That is reported as `207` with `ok: false` and a `partial_failures` summary, and the CLI gates its exit code on the body (a `207` is 2xx, so an HTTP-status-only check would call it success).

**Reads are an inventory, not a pause list.** `GET /activities` is driven by the registered activity **catalogue**, so a healthy activity appears with `paused: false` — the read has to answer "is `charge_card` held?", which a list of only the already-broken things cannot. An activity that is paused but **not** registered in this process is listed anyway, flagged `registered: false`, so a mistyped hold can never become invisible on the one surface used to find it. `GET /activities/{name}` 404s only when the name is neither registered **nor** paused anywhere the read could reach.

**Input validation.** `validate_activity_name` rejects blank, whitespace-padded, and over-255-character names. It runs at the HTTP boundary on all four routes — including the two reads, so `GET /activities/{name}` and `POST .../pause` diagnose the same bad input the same way — **and** inside `pause_activity`/`resume_activity` themselves, matching `queue_pause::pause_queue`: a `pub` write path must not depend on every caller remembering, or an unvalidated whitespace-padded name would insert a row the claim gate (which matches exactly) can never match, giving an operator a hold that *lists* as active while holding nothing. Whitespace is **rejected rather than trimmed**: trimming would let `" charge_card"` silently pause `charge_card`, so a hold could be placed under a name that does not match what the operator typed and later fail to be found by it. Only rejecting cannot lie.

**Indexed for the incident, not the steady state.** Unlike the queue-pause sibling — whose every predicate leads with `queue_name` and is served by the existing poll index — this feature's four queries (`held_task_count`, the correlated count behind `GET /activities`, the resume's bulk `scheduled_at` shift, and the resume doorbell) narrow by **activity** first with no queue to seek on, and no pre-existing index leads with `activity_name`. Without one the correlated count is O(paused × task_queue) on every read of the list view — worst exactly mid-incident, with the backlog at its largest and an operator refreshing during triage. The migration therefore adds a partial index `idx_harvest_tq_activity_pause ON harvest_task_queue (activity_name, state) WHERE task_type = 'activity' AND activity_name IS NOT NULL`, gated on the same `task_type` scoping every pause predicate carries, so workflow rows never enter it and the hot enqueue path pays nothing.

**Pause and its reported count are atomic.** `pause_activity` wraps the upsert and the held count in one transaction, matching `resume_activity`. Split across two autocommit statements, a failure of the *count* — a best-effort observability read, and the statement most likely to be slow on a large backlog — would invert the reported outcome of a live mutation: the pause row commits and the claim gate starts holding fleet-wide, while the operator sees a 500 and concludes the hold did not take. That is the worst possible failure mode for an incident brake.

**Observability.** New counter `harvest.activity.pause_actions` (`METRIC_ACTIVITY_PAUSE_ACTIONS`), labelled `activity` (`METRIC_LABEL_ACTIVITY`) and a bounded `action` (`ActivityPauseAction::as_str()` — `pause`/`resume`). The `activity` label is bounded **by bucketing**, not by validation: the pause routes accept an *unregistered* name on purpose (an operator must be able to pre-pause an activity before its fleet rolls out, and a paused-but-unregistered hold must stay inspectable), so the raw name is caller-controlled free text — bounded in length, but not in cardinality, which is what ADR-0001 §7 actually forbids. The emitter resolves it against the registered activity catalogue and substitutes `UNREGISTERED_ACTIVITY_NAME` (`__unregistered__`) when absent, the same fix as the issue #684 update-name label. The durable row and the read API keep the raw name — a counter rather than a gauge because the operator question is "did someone hold this, and when?", which a gauge that reads 0 both before a pause and after a resume cannot answer. Emission is gated on `newly_paused`/`newly_resumed`, so an idempotent retry does not inflate the count. `execution.id` is never a label (ADR-0001 §7). Bridged in `metrics_rs_adapter`, catalogued in `docs/telemetry.md` and ADR-0001 §7, and paneled in the starter-pack dashboard.

**Eligibility explainer.** The stuck-task explainer (`GET /admin/queues/{queue}/eligibility`, `/admin/tasks/{id}/eligibility`) reports the new reason code `activity_paused`, listed **first** alongside `queue_paused` because an operator's own deliberate action should be checked before chasing a capacity or routing cause. Both codes are reported when a task is held by both, so resuming the one you see first does not silently leave it stuck behind the other. Scoped by `task_type = 'activity'`, so it never appears against a task the engine would happily dispatch.

**Audit.** `activity.pause` / `activity.resume` (`OP_ACTIVITY_PAUSE`/`OP_ACTIVITY_RESUME`), registered in all four `audit.rs` registries; **rejected** attempts are audited too — a refused hold on a dispatch kill switch is exactly what an incident review needs to see. The `actor` body field is a **label** for attribution, not authentication: the audit row always carries the authenticated actor and records the on-behalf-of relationship when the two differ, so the field can never rewrite the security trail.

**Docs.** New §6 `activity_paused` in `docs/runbooks/triage-pending-tasks-idle-workers.md` with the full pause → triage → resume loop and a three-way decision table (activity pause vs. queue pause vs. circuit breaker).

**Tests.** 17 DB integration tests in `tests/integration/activity_pause_tests.rs` (registered in `.github/ci/integration-suites.txt`) plus unit tests in `activity_pause.rs`, `queue.rs`, `timeout.rs`, and `telemetry.rs`. The headline success-metric test `a_sibling_activity_on_the_same_queue_is_completely_untouched` proves zero cross-activity impact directly. `resume_credits_the_held_time_only_not_the_whole_wait` proves **both** halves of the credit rule — an in-budget task survives the thaw, and a task whose deadline had *already* blown before the pause still fails, so a pause cannot be used to launder an expired deadline.

**The credit pass is the resume's last statement (PR review, Codex P1).** The resume originally ran `primary shift -> late-arrivals credit -> notify SELECT -> one pg_notify per queue -> COMMIT`. Because the pause row's `DELETE` is not visible to any other session until COMMIT, every task enqueued before that commit is genuinely held and owed a credit — so the uncredited residual is bounded by whatever still runs *after* the final credit. With the notification pass last, that residual was the notification pass: one round-trip per queue holding backlog, i.e. widest during exactly the incident being resumed. `resume_shift_late_arrivals_query`'s own docs already claimed the residual was "this final, small statement"; the code did not honour it. The notify `SELECT` and its `pg_notify` loop now run **before** the credit pass, so the claim is true. The trade is asymmetric, which is what settles the order: a row committing after the notify `SELECT` loses only its own doorbell and waits one poll tick (workers still poll), whereas the same row losing its **credit** keeps its whole held wait and the `schedule_to_start` scanner can terminally fail it the instant the hold lifts. The doorbell is per-queue, so it goes silent only for a late arrival that is the sole due row on its queue. Pinned by `resume_credits_a_task_that_arrives_during_the_notification_pass`, which hand-drives the statements on an explicit transaction (the idiom the existing between-the-two-passes test establishes) and opens the window *after* the doorbell; its pre-window assertion proves the row is genuinely uncredited at that point, so the post-commit assertion cannot pass vacuously. Stated plainly, that test pins the ordering **contract** rather than `resume_activity`'s wiring — landing a concurrent commit *inside* the notification pass is not blockable (`pg_notify` takes no lock, and the notify `SELECT` blocks only on `ACCESS EXCLUSIVE`, which the resume's own transaction already holds conflicting rights against), and the only alternative — flooding inserts and hoping one lands in the window — is probabilistic in the *passing* direction, i.e. a flaky guard rather than a real one.

**`paused_at` is stamped after the backlog count, not at transaction start (PR review, Codex P2).** The pause upsert wrote `NOW()`, which is `transaction_timestamp()` — frozen the moment the transaction starts, whichever statement reads it. But the hold only takes effect for other sessions at COMMIT, so the recorded `paused_at` preceded the effective hold by the whole transaction, dominated by `held_task_count_query`, whose cost scales with the backlog. That is not cosmetic: `paused_at` is the `$2` the resume credit passes subtract from, so a back-dated hold credits back wait the tasks spent **claimable and unheld** — laundering a `schedule_to_start` budget already burned, the one thing the credit rule promises a pause cannot do. Fixed in two halves: the upsert now stamps `clock_timestamp()` (volatile, read when the statement actually executes), and the count runs **before** the upsert so nothing slow sits between the stamp and the commit. The count reads only `harvest_task_queue` and never the pause row, so its answer does not depend on the upsert having run; reordering also shortens how long the pause row's lock is held, so a concurrent pause or resume of the same activity queues behind it for less time. An idempotent re-pause is unaffected — `DO UPDATE` writes the existing `paused_at` back, so only a fresh insert stamps. The residual mirrors the resume side's and is documented the same way: the true freeze instant is commit, which no in-statement expression can know, so `paused_at` still precedes it by the upsert plus the commit — bounded by microseconds instead of an unbounded backlog scan, and still erring toward over-crediting rather than the unsafe direction (a stamp *later* than the effective hold would under-credit and could time out a task that was genuinely held). Pinned deterministically by `pause_stamps_paused_at_after_the_backlog_count_not_at_transaction_start`, which blocks the count for a known duration with an `ACCESS EXCLUSIVE` lock taken from a second session and asserts the stamp lands after the block (verified RED against the previous code), plus the SQL-shape test `pause_upsert_stamps_the_volatile_clock_not_the_frozen_transaction_clock`.

**The pause audit row records the hold in effect, not the request (PR review, Codex P2).** `pause_activity` preserves each shard's ORIGINAL provenance on an idempotent re-pause — that is what makes it idempotent — but the success-path audit row wrote the *incoming request's* reason. So a second pause carrying different words, or (most starkly) omitting the reason entirely and resolving to the default, recorded a reason that was in effect on no shard at all. The response body already reports the effective provenance for exactly this reason (issue #619 review); the durable row is the half that matters, since the resume `DELETE`s the pause row and leaves the audit trail as its only permanent home. Fixed by rendering the audit reason from the effective per-shard provenance via a new `held_holds_audit_reason`, the pause mirror of the resume side's already-correct `released_holds_audit_reason`: shards holding for one incident collapse into a single `(reason, operator)` group, so the row grows with the number of genuinely distinct holds rather than the shard count, and the divergent case — retrying a partial fleet pause, where the reached shards keep the original reason and the newly reached ones take the retry's — records **every** reason rather than losing whichever one is not the summary. The earliest hold leads, matching the response's top-level `reason`/`paused_at`, so the row and the response can never tell two stories. `on_behalf_of` deliberately stays request-scoped by contrast: it records what *this* caller claimed, which is a security fact about the request rather than a description of the hold. **The queue pause (#619) carried the identical bug and is fixed in the same commit** — the helper is feature-neutral and shared, so the two audit trails cannot drift on the same question; the queue side's format is unchanged for a uniform hold apart from now naming the effective operator. Pinned by `pause_audit_reason_records_the_effective_hold_not_the_request` and `pause_audit_reason_preserves_every_divergent_shard_reason` (pure, both features), and at the wiring level by `a_re_pause_audits_the_effective_hold_not_the_new_request`, which drives the real route and reads the real `harvest_audit_log` row (verified RED against the previous code).

**Out of scope** (per the issue): aborting in-flight instances; pausing by `(queue, activity)` tuple or by search-attribute predicate; automatic or conditional pausing; auto-expiry/TTL on a hold; pausing workflow types or local activities.
