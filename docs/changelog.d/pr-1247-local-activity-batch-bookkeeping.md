## Fix — local-activity batch silently dropped co-batched bookkeeping commands (issue #1247)

`extract_run_local_activity` (`autumn-harvest/src/worker.rs`) walked a drained `RunLocalActivity` command batch with a `match` that handled only four kinds (`RecordMarker`, `RecordSideEffect`, `SpawnDetachedChildWorkflow`, `RunLocalActivity`) and ended in a `_ => {}` catch-all. `local_activity_batch_conflict` (issue #950 AC8) already rejects a local activity co-batched with a durable awaitable, so every other command that could reach the catch-all was legal bookkeeping — and every one of those was silently discarded.

**Root cause and scope.** Five of the eight bookkeeping kinds the original report named — `UpsertSearchAttributes`, `SetCurrentDetails`, `RecordLog`, `PublishProgress`, `ReleaseMutex` — are already persisted correctly: `process_workflow_task`'s `RunLocalActivity` dispatch arm calls `persist_search_attrs_from_commands`, `persist_current_details_from_commands`, `persist_workflow_logs_from_commands`, `notify_progress_from_commands`, and `process_mutex_releases_from_commands` before `extract_run_local_activity` ever runs, and none of those five produces a `harvest_events` row, so the catch-all dropping them there was a documented no-op, not a defect. The three genuine drops: `CancelTimer` lost both its `harvest_timers` row delete and its `TimerCancelled` event; the `for_await: false` `ArmTimer` (a fresh `start_timer`/`reset`) lost its `TimerStarted` event; `RecordUpdateResult` lost its `UpdateCompleted`/`UpdateFailed` event outright, with no later cycle to re-emit it — the most severe of the three, since (unlike the timer commands) nothing re-derives an update result from replay.

**Fix.** `extract_run_local_activity`'s match is now exhaustive over every `WorkflowCommand` variant, with no `_` arm: a `CancelTimer`/fresh `ArmTimer` gets its positional `TimerStarted`/`TimerCancelled` event via the existing pure `plan_timer_lifecycle_pure` (shared with the general suspension path, so the dedup/ordering rules are identical); a `RecordUpdateResult` converts straight to `UpdateCompleted`/`UpdateFailed`; the five already-handled no-op kinds get a documented empty arm; every remaining variant is provably unreachable here (rejected upstream by `local_activity_batch_conflict`, the dispatch arm's `AcquireMutex` guard, or `split_mixed_signal_batch`) and panics by name if one ever arrives — so a future `WorkflowCommand` variant fails to compile here rather than silently falling through again. New `delete_local_activity_cancelled_timers` deletes the `harvest_timers` row a co-batched `CancelTimer` targets, called from the `RunLocalActivity` dispatch arm right after the existing `ReleaseMutex` resolution and for the same reason: a stale row surviving into the local activity's execution window is exactly the race the sweeper could win, appending `TimerFired` where replay expects `TimerCancelled`.

**No new `WorkflowEvent` variant, no migration.** `TimerStarted`, `TimerCancelled`, `UpdateCompleted`, and `UpdateFailed` all already exist and are already written by the general suspension path; an existing history decodes unchanged. This closes the one path (a local activity's batch) that was not emitting them.

**Tests (TDD, red before the fix).** Three unit tests on `extract_run_local_activity` (`extract_run_local_activity_preserves_cancel_timer_before_local_command`, `extract_run_local_activity_preserves_fresh_timer_arm_after_local_command`, `extract_run_local_activity_preserves_record_update_result_success_and_failure`) fail against the pre-fix catch-all and pass after, pinning both the event contents and the pre/post-`LocalActivityScheduled` positional ordering. A new DB integration test, `cancel_timer_co_batched_with_a_local_activity_deletes_its_row_and_keeps_its_event` (`mixed_suspension_tests.rs`), drives a real worker through an `[ArmTimer, CancelTimer, RunLocalActivity]` batch end to end and asserts `TimerStarted` precedes `TimerCancelled` precedes `LocalActivityScheduled` in history, that no `TimerFired` is ever recorded, and that a pre-seeded `harvest_timers` row is gone afterward (`seed_pending_timer_row` seeds the row directly, standing in for the row a real `ArmTimer { for_await: true }` cycle from an earlier task would have left, so the DB-delete path is exercised deterministically rather than by racing the scheduler for a live window). Full `worker` unit suite and the `mixed_suspension_tests` DB suite pass with no regressions.

**Self-review round 1 (three independent angles: correctness/replay-determinism, test quality, invariants/style).** Two review agents independently found the same defect from different evidence: the exhaustive match's residual `unreachable!()` arm was wrong about `CancelRaceLosers`. A resolved `ctx.race()` can leave `CancelRaceLosers` in the very same batch as a `RunLocalActivity` — its loser branches were dispatched on an *earlier* cycle, so this batch carries no start command for them, and `local_activity_batch_conflict` has nothing to reject. Before this fix the old catch-all silently dropped it (never cleaning up the losers); after the first cut of this fix it panicked instead — a poison pill, strictly worse than the original bug, since `process_workflow_task` has no `catch_unwind`. First fix: call the existing `apply_race_loser_cancellations` directly from the `RunLocalActivity` dispatch arm. Superseded in round 2 below.

The correctness review also found the `RecordUpdateResult` fix was incomplete for one composition: when a local-activity batch also carries `SignalExternalWorkflow`/`RequestCancelExternalWorkflow`/`AwaitExternalWorkflow`, `split_mixed_signal_batch` strips `RecordUpdateResult` from the remaining commands *before* `extract_run_local_activity` ever sees it — the exact same class of silent drop this issue set out to fix, just one level up. This mirrors a defect issue #684 already fixed at the two other `split_mixed_signal_batch` call sites (both call `persist_update_result_commands` + `emit_update_result_metrics` before splitting); the `RunLocalActivity` arm was missing that step. Fixed by adding the same persist-then-emit call before the split, gated to the external-command branch only so the plain (no external command) branch is not double-persisted.

The test-quality review additionally found the restored `RecordUpdateResult` event was not paired with its `harvest.update.*` metrics in the plain (no external command) branch: the Persisted-arm's metrics emission only sees the *final* cycle's commands, and a local activity re-drives the workflow before reaching it, so this cycle's `RecordUpdateResult` metrics were never counted. Fixed by capturing `collect_update_result_metrics` on the final (post-split) command list before it is consumed, then calling `emit_update_result_metrics` once the local activity's events are durably appended — mirroring the same "emit here, post-commit" pattern the two `split_mixed_signal_batch` sites already use.

**Automated PR review, round 2 (three findings, two P1 and one P2).** (1) Round 1's `apply_race_loser_cancellations` fix called it as its own autocommitted step, ahead of `run_local_activity_inline`'s own transaction — but that function's own doc requires it to commit in the SAME transaction as the batch's winner marker: a crash in the gap leaves a durably-cancelled loser with no recorded winner, free for a later replay to pick a different one. Fixed properly: `LocalActivityCommandBatch` gained a `race_loser_commands` field, `extract_run_local_activity` collects `CancelRaceLosers` into it instead of resolving it, and `run_local_activity_inline` now calls `apply_race_loser_cancellations` from inside its own existing event-append transaction, before appending the prefix/post-schedule events, threading the advanced event-id cursor through both. The dispatch-arm preamble call from round 1 is gone. (2) The external-command branch's `RecordUpdateResult` persist (round 1's other fix) durably appended `UpdateCompleted`/`UpdateFailed` but never added those events to the in-memory `history_events` the same cycle's local-activity re-drive replays against — so that re-drive would see only `UpdateAdmitted`, take the live path in `execute_admitted_update`, and run the update handler a second time. Fixed by reconstructing the same events locally and extending `history_events` right after the persist call succeeds. (3) `LocalActivityInlineOutcome::HistoryCapReached` durably appends the update-result event (it is part of `events`) but the caller returned before reaching the `emit_update_result_metrics` call in the `Complete` arm, so a `RecordUpdateResult` landing exactly at the history cap boundary was silently uncounted. First fix: emit the same metrics in the `HistoryCapReached` arm too. Superseded in round 3 below.

New unit test `extract_run_local_activity_collects_a_co_batched_cancel_race_losers` pins that `CancelRaceLosers` is carried through rather than resolved inline or dropped. New DB integration test `race_resolved_by_activity_then_local_activity_in_one_batch` drives a real `ctx.race()` resolved by its activity branch, immediately followed by a local activity in the same decision cycle — the `[RecordMarker, CancelRaceLosers, RunLocalActivity]` shape both review rounds are about — end to end: the workflow completes with the correct winner and local-activity result, and the loser timer's `harvest_timers` row is gone.

**Automated PR review, round 3 (one P2 finding).** Round 2's `HistoryCapReached`-arm fix for the update-result metrics gap was itself incomplete: a plain (no external command) batch's `RecordUpdateResult` event is durable as soon as `run_local_activity_inline`'s prefix transaction commits, but the caller only emitted its metrics from the `Ok` arms of that call — a LATER failure inside the same function (a handler attempt, the frontier-resolving append) returns `Err`, and the caller's error arm never touched the metrics at all. Since the update event is already terminal in history, no later replay re-derives the command, so the metric was permanently lost on that path. Fixed by moving the emission itself: `run_local_activity_inline` now takes the precomputed `update_result_metrics` as a parameter and emits them right after its prefix transaction commits, before running the handler at all — covering every exit this function can take afterward (success, retry exhaustion, the history cap, or a propagated `Err`) in one place. The caller's two post-hoc `emit_update_result_metrics` calls (round 2's `HistoryCapReached` fix included) are removed as redundant.

**Automated PR review, round 4 (one P2 finding).** Round 2's `apply_race_loser_cancellations` fix ran it FIRST inside the prefix transaction, ahead of `detached_spawns.persist`. `apply_race_loser_cancellations` records its loser-cancellation telemetry (`harvest.activity.*`, `harvest.workflow.terminal`) as a synchronous side effect with no rollback of its own — so if `persist` then failed with the explicitly-recoverable `QuotaExceeded` (issue #946), the whole transaction rolled back, the task was retried, and the eventual successful retry re-ran `apply_race_loser_cancellations` and double-counted that telemetry. Every OTHER call site in the codebase avoids this by construction: `persist_bookkeeping_and_requeue_workflow` (and its siblings) always call `detached_spawns.persist` BEFORE `apply_race_loser_cancellations`, so a recoverable failure there means the cancellation, and its telemetry, never ran yet in that attempt. Fixed by reordering to match: `apply_race_loser_cancellations` now runs LAST in the transaction, after both the event append and `detached_spawns.persist`, with the event-id cursor threaded accordingly.

**Automated PR review, round 5 (one P1 finding).** `apply_race_loser_cancellations` durably appends its cancelled-loser events (a synthetic `ActivityFailed`, or — reloaded from `notify_awaited_parent_of_child_terminal`'s own append — a child's terminal) but, before this round, returned only the deferred triggers. `run_local_activity_inline`'s immediate in-process re-drive replays against `history_events`, so those durable-but-unreturned events were invisible to that replay even though the DB already had them: a real divergence risk (`replay.rs`'s `consume_race_loser_frontier` documents that a *later* replay of a recorded winner resolves each loser via its recorded terminal, which would be missing from the in-memory copy). Fixed by widening `apply_race_loser_cancellations`'s return type to `(Vec<DeferredTriggerStart>, Vec<WorkflowEvent>)` — every one of its 12 other call sites destructures and discards the events (they never re-drive in-process against a stale in-memory history; the next task claim loads fresh from the DB) — and folding the events into `run_local_activity_inline`'s own returned `events`, right where `prefix_events` is assembled, so every exit path (`Complete`, `HistoryCapReached`) carries them. The child-terminal case required its own fix: `notify_awaited_parent_of_child_terminal` doesn't return what it appends (a `ChildWorkflowFailed` plus a variable number of materialized `__child_timeout` deadlines), so the child-cancellation arm now diffs `next_event_id` before/after the call and reloads the newly appended tail from history, rather than reconstructing a fixed shape by hand.

New DB integration test `race_resolved_by_activity_with_an_open_activity_loser_then_local_activity` drives an activity-loser race (the existing round-2 test's loser is a timer, which produces no event at all and so never exercised this path) immediately followed by a local activity, and asserts the loser's `ActivityFailed` appears exactly once and the local activity is scheduled exactly once — no lost event, no divergence-driven duplicate. Honesty check: experimentally reverting just the events-folding line and re-running this test, it still passed — for this exact composition (the workflow returns immediately after the local activity, with no further positional command to diverge on), the missing in-memory event did not produce an externally observable failure. The fix is still correct on its own logical merits — a durably-appended event omitted from the in-memory replay is the same class of bug the round-2 `RecordUpdateResult` finding was, and `consume_race_loser_frontier`'s own doc comment describes exactly the later-replay path that would need it — but no regression test in this PR discriminates the specific hazard the reviewer described; a composition with a further positional command after the local activity would be needed to construct one, and was judged out of proportion to add here.

**Automated PR review, round 6 (two P2 findings on round 5's fix).** Round 5's child-terminal reload ran two problems together, both inside the same `for child_id in children` loop iteration. (1) `emit_workflow_terminal` for the cancelled child ran BEFORE that iteration's `store::load_history_with_codecs` reload — a later, genuinely fallible read. A reload failure returns `Err`, rolling back the whole transaction (the cancellation included), but the metric had already been recorded and has no undo: the same lost-atomicity shape round 4 fixed for the cancellation telemetry itself, one call further down. (2) The reload ran once per losing child, each pass decoding the parent's FULL history from scratch — O(K × H) for K losing children and H history events, all while the cancellation transaction still held its row locks, risking a transaction timeout on a long history with several losing children in one race.

Fixed by decoupling collection from emission and reloading once, not per child: the loop now pushes each cancelled child's `(workflow_name, queue_name)` onto a new `child_terminal_metrics` accumulator instead of emitting inline, and does no per-child reload. After the loop, one `store::load_history_with_codecs` call reloads the parent's history exactly once; the tail slice size is the delta between `next_event_id` at function entry and `next_event_id` after the loop, which is exactly the sum of every child cancellation's appended events (synthetic activity-loser events are not appended until the block that follows, so they are not yet in that delta). Only once that single reload succeeds does the function iterate `child_terminal_metrics` and emit each deferred metric — so a reload failure now rolls back the transaction with no metric recorded for it, and a race with several losing children touches the database once for this step instead of K times. The single reload plus its gated metric emission is factored into a new private helper (`reload_race_loser_events_and_emit_metrics`, extended in round 7 below), because inlining it pushed `apply_race_loser_cancellations` over Clippy's `too_many_lines` limit (108/100 in CI's `--all-features --tests` lint, which this repo's default feature set had not caught locally); a second, pre-existing `useless_let_if_seq` finding in `run_local_activity_inline` — the same all-features gap — was fixed alongside it by rewriting the two-variable default-then-overwrite pattern around `race_loser_deferred`/`race_loser_events` as a single `let (a, b) = if cond { .. } else { .. };` expression.

**Automated PR review, round 7 (one P2 finding, same class as round 6).** Round 6 deferred the child-cancellation metric past the post-loop reload but missed a sibling instance one loop earlier: the activity-loser metric trio (`record_activity_completed_with_error_type`, `record_activity_failed`, `record_activity_attempt`) still fired immediately inside the `for activity_id in activities` loop, ahead of the same reload. `cancel_activity_task`'s row delete is not durable until this transaction commits, so a reload failure rolls it back along with any child cancellation — but the activity metrics, recorded synchronously with no rollback of their own, survive and are emitted again when the retry re-cancels the same still-open activity.

Fixed the same way as round 6: the loop now pushes each cancelled activity's `(activity_name, queue_name)` onto a new `activity_loser_metrics` accumulator instead of calling the three metric functions inline. The post-loop helper (renamed `reload_race_loser_events_and_emit_metrics` to reflect covering both loser kinds) takes this accumulator alongside `child_terminal_metrics` and, once the single reload succeeds, emits both — activity metrics using the same three calls and arguments as before, just moved past the gate.

All fixes plus the DB tests were re-verified: `cargo test -p autumn-harvest --lib` (3408 tests), `cargo check --features db`, `cargo clippy -p autumn-harvest --all-features --tests -- -D warnings` (the exact CI Lint invocation, which caught round 6's `too_many_lines`/`useless_let_if_seq` gap), and the touched `mixed_suspension_tests` DB tests plus the `#779` event-id-accounting integration test that exercises `apply_race_loser_cancellations` directly (run individually against a real Postgres — Docker was unavailable in this environment, so each ran against a freshly migrated database rather than the suite's usual one-container-per-test isolation) are all green, and `docs/audits/comment-hygiene.py --base origin/trunk-dev` reports no Tier A findings and no Tier B regressions. Round 3's fix has no direct test of its own (the failure window it closes — a handler-stage error after the prefix commits — is best exercised with fault injection, out of proportion to a P2 telemetry gap); it was verified by re-reading the code against the reviewer's exact claim and by the full suite staying green. Rounds 6 and 7's deferred-metrics ordering are likewise verified by code inspection against the reviewer's claims rather than fault injection — the existing `race_resolved_by_activity_with_an_open_activity_loser_then_local_activity` and `#779` tests confirm the single reload still produces the correct events and cursor, but neither injects a mid-reload failure to observe either metric class staying unrecorded.
