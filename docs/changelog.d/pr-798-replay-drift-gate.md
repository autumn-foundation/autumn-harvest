- **Phase 3.x** (implemented): In-flight replay-drift gate — sample what is running now, replay it against the candidate build, block promotion on divergence (issue #798). A determinism regression in a `#[workflow]` body does not fail at compile time and does not fail on a fresh run: it fails when an **already-running** execution is resumed by the new code, minutes or hours after the deploy, by which time the run is nd-blocked (#603) or dead-lettered. The pre-existing `ReplayVerifier` (#251) replays a *curated fixture directory of completed histories* **strictly** and cannot answer the deploy question ("will the executions running right now survive this build?"); the replay canary (#512) can, but only *server-side, after* the build is already reachable. This slice closes that window with a CI-side loop: one read-only export command plus a ~15-line gate binary in the embedder's own crate.

  **Core — `replay_sample.rs`** (new, pure, no DB, unconditional): the single source of truth for the bundle wire shape, shared by the API (producer), the CLI (writer), and the testing harness (reader). `IN_FLIGHT_STATES` (`RUNNING`/`PAUSED`), `DEFAULT_PER_WORKFLOW_SAMPLE` (50), `MAX_PER_WORKFLOW_SAMPLE` (500), `MAX_SAMPLE_TOTAL` (2000); `SampleOrder` (`Oldest`/`Newest`), `SampleStatus` (`Complete`/`Partial`/`Unavailable`, `from_counts`); `SampleWorkflowCoverage { workflow_name, sampled, in_flight_total }` with `truncated()`; `SampleManifest` (with the reserved `FILE_NAME = "harvest-sample-manifest.json"`, `is_complete()`, `is_truncated()`); `normalize_sample_states`, `clamp_per_workflow`, `merge_coverage`, `fixture_file_name`. **`SUSPENDED` is accepted as a documented alias for `RUNNING`** — the AC's literal default state set names it, but `SUSPENDED` is not a persisted state (it is absent from `KNOWN_WORKFLOW_STATES` and forbidden by the CHECK constraint; a parked run's row is `RUNNING`), so the alias makes the AC's default resolve to the correct non-terminal set. A **terminal** state in `states` is rejected (`Err`), never silently dropped — the gate replays in-flight histories, so a request for `COMPLETED` is a caller error, not an empty result. `fixture_file_name` sanitizes the workflow name to `[A-Za-z0-9_-]`, caps both components at 64 chars, and appends the execution UUID so a hostile or merely awkward name can never escape the bundle directory.

  **Core — `ReplayDriftReport` + `replay_bundle` (`testing.rs`, feature `testing`)**: `WorkflowReplayer::replay_bundle(dir)` and `ReplayVerifier::replay_bundle(dir)` return `ReplayDriftReport { total, succeeded, diverged: Vec<ReplayDrift>, blocked: Vec<ReplayBlocked>, skipped, coverage: Option<SampleManifest>, … }`, where each `ReplayDrift` carries `execution_id`, `workflow_name`, `kind: NonDeterminismKind`, `first_divergence`, and `fixture_path`. **The load-bearing design decision is the replay MODE.** Wiring `replay_bundle` to the existing `verify_dir` would have made the gate **100% false-red on every in-flight fixture**: `verify_dir` → `replay_from_snapshot` → `outcome_to_report(.., canary_mode: false)`, whose `WorkflowOutcome::Suspended` arm returns `NonDeterminismDetected` — but a healthy non-terminal execution *always* suspends at its recorded frontier; that is its correct outcome. `replay_bundle` therefore uses the new private `FixtureReplayMode::InFlight` → `replay_canary_snapshot`, while `verify_dir` keeps `FixtureReplayMode::Strict`; both share one `replay_dir` engine so there is one replay path with two documented modes rather than a fork. Genuine divergences still fail in canary mode (they surface as `WorkflowOutcome::Failed { non_deterministic_details: Some(_) }`) and leftover unconsumed history is still caught. **Verified by falsification**: swapping the mode to `Strict` made 5 tests fail including the money test; restored and re-verified green.

  **The false-GREEN failure mode is closed too.** `verify_dir` over an empty or mistyped directory returns `fixtures_total: 0` → exit 0; a gate that passes having verified nothing is worse than no gate. `is_clean()` is *defined* as `exit_code() == 0` so the two helpers can never disagree, and the exit ladder is: `0` clean · `1` diverged · `2` blocked (a fixture the harness could not evaluate — dominates `1`, mirroring `CiReport`) · `3` **empty bundle** (opt out with `allow_empty_bundle(true)` for a legitimately idle fleet) · `4` `require_complete_coverage(true)` and the manifest reports partial shard coverage. `collect_json_files` excludes the reserved manifest filename, so a well-formed bundle never produces a spurious harness error — and the pre-existing `verify_dir` is protected from breaking on a #798 bundle.

  **Plugin — `GET /admin/history/export-sample`** (new, admin-gated, read-only): stratified in-flight sample export. **One statement, two window functions** (`HISTORY_SAMPLE_CANDIDATES_{OLDEST,NEWEST}_SQL`): `ROW_NUMBER() OVER (PARTITION BY workflow_name ORDER BY started_at, id)` performs the stratification — without it a plain `LIMIT` returns the noisiest workflow type's rows and nothing else, the exact failure this route exists to prevent — and `COUNT(*) OVER (PARTITION BY workflow_name)` reports the population the sample was drawn from. Computing both in the *same* statement is what makes `sampled <= in_flight_total` true by construction; a second query could observe a different snapshot and report a sample larger than its own population. Two SQL constants rather than an interpolated `ORDER BY` direction (which would be an injection seam), selected by a `const fn`. Deliberately **no `harvest_events` join**: the batch export needs one for `last_history_event_at`, but that column is only ever a sort key there and is never carried into the export document, so the sample orders by the indexed `started_at` and stays cheap on a large in-flight fleet. **The per-type cap is global, not per shard**: each shard returns its own top-N (a superset of the global top-N, since an execution in the global top-N is necessarily in its own shard's top-N), then `stratify_sample_rows` re-sorts the union by the same key and re-truncates — so `--per-workflow 50` means 50 fleet-wide. A new `HistorySampleCandidate` converts into the existing `HistoryExportCandidate`, so the **entire** batch-export pipeline is reused unchanged (payload policy, #608 read-path decoding, `max_bytes`, per-entry failure reporting, shard coverage) — which is also how AC3 is satisfied for free. An unreachable shard degrades the manifest to `partial` and names the shard rather than failing the request. Registered in all four parallel registries (`harvest_api_router`, `management_api_routes()`, response-fields, `docs/api-contract.json`) and in `autumn_harvest::audit` (`CLASSIFIED_ROUTES` `ReadOnly` / `ALL_MUTATION_ROUTES` `None` / `EXCLUDED_ROUTES`), with a pinned `history_export_sample_route_is_classified` guard in `contract_regression.rs` (the audit-side mutual cross-check stays green if a route is dropped from BOTH lists). Read-only classification matters twice here: the route feeds a CI gate, and a misclassification as `Mutating` would make it unreachable to the read-only operator role (#776) a CI token is most likely to hold. It is admin-gated; the older `/admin/history/exports` sibling predates that posture and is left as-is (tightening an existing route's auth is out of scope).

  **AC2 — no silent truncation.** A workflow type whose entire sample failed the per-execution size ceiling still appears in the manifest with `sampled: 0` and its real `in_flight_total`, so an operator can never mistake "nothing was exported for this type" for "this type has nothing in flight". `sampled` is counted from the documents **actually exported**, not from the rows selected, so a size-limit failure is never counted as a sample.

  **CLI — `harvest history export-sample --output-dir <DIR>`** with `--per-workflow`, `--states` (repeatable **and** comma-separated, so a recipe copied from either idiom samples the same population), `--workflow-name`, `--order`, `--shard-id`, `--payload-policy`, `--max-bytes`. Writes a replay **bundle** (one `.json` fixture per sampled execution plus `harvest-sample-manifest.json`) rather than a single blob, so the directory feeds straight into `replay_bundle`; `-o json` still prints the raw response for scripting. The writer is split into two pure, unit-tested functions — `history_sample_bundle_files` (which files, named how; a sanitization collision is disambiguated, never overwritten, since overwriting would silently shrink the bundle below what the manifest claims) and `render_history_sample_summary` (the coverage table, which prints a `WARNING … LOWER BOUND` block on partial shard coverage and a `NOTE: the sample is truncated` line whenever `sampled < in_flight_total`). A non-sample response body fails loudly rather than writing an empty bundle a gate would then evaluate for the wrong reason.

  **AC7 — zero new `WorkflowEvent` variants, no migration.** The export is `SELECT`-only (no state transition, no event appended, no task claimed) and the replay is pure. Nothing in this slice touches `harvest_events`, the adjacently-tagged event JSON contract, or the shard-routing model.

  **Post-review hardening (four reviewers: replay-determinism, sharding/SQL, CI-gate honesty, tests/AC-evidence).** Every finding is a variant of one failure: *the gate says something confidently false*. (1) **A redacted bundle is refused, not replayed.** The CLI's `--payload-policy` default is `redacted`, and redaction rewrites payload-bearing fields **in place** — but both replay paths run with `strict_replay = true`, so `match_activity_strict` compares the redacted stub against the input the code computes and **every** fixture passing a non-trivial activity input diverges. Replaying such a bundle does not produce a weaker gate, it produces a confidently wrong one that reports a determinism regression in code that is fine. The new `unreplayable_fixture_reason` refuses it as a *harness error* (exit 2) naming the fix, alongside a wrong-population check (a terminal fixture handed to the in-flight gate, or vice versa). The two fields it reads are export-document metadata, so they are parsed from the fixture JSON via a private `FixtureGuardFields` side struct rather than added to `HistorySnapshot` — which would have forced every hand-built fixture in the workspace to declare export metadata it has no notion of. Empirically confirmed RED: before the guard, a redacted bundle reported `0 clean, 1 diverged`. (2) **`require_complete_coverage` fails closed.** It previously passed when the manifest was **missing or unparseable** (`read_bundle_manifest` is fail-open by design). A caller who sets that flag has said they will not certify against a partial read of the fleet, and *no manifest proves nothing* — so absent evidence now exits 4 via the new `coverage_claim_unsatisfied()`, deliberately stricter than `has_incomplete_coverage()` (which correctly answers the different question "did the bundle *claim* partial coverage?"). (3) **Alphabetical starvation.** `MAX_SAMPLE_TOTAL` was applied as a running total over name-sorted rows, so a fleet with more types than budget gave the alphabetically-late ones **zero** coverage while the gate exited 0 — the same "noisy crowds out quiet" failure the per-type stratification exists to prevent, on a different axis. The global cap is now divided across the observed type count. Confirmed RED at 60 types: 40 covered, 20 silently blind. (4) **Two logical shards sharing one physical database double-counted.** The sample query had no `shard_id` predicate (every other cross-shard count in the repo carries one — `COUNT_WHERE_CLAUSE`, `schedule_run_state_summary`, `non_terminal_counts_by_workflow_name`), so the fan-out ran the same statement twice over the same rows: `in_flight_total` doubled — corrupting the exact denominator AC2 exists to state honestly — **and** every execution was sampled twice, halving real per-type coverage while `sampled` looked unchanged. Both silent. Confirmed RED end-to-end: 3 executions reported `in_flight_total: 6` with every fixture duplicated. (5) **The liveness canary (#796) leaked into bundles.** Its probe workflow is engine-internal and registered by no user gate binary, so a sampled probe lands in `blocked` — which dominates the exit ladder — pinning the gate at exit 2 forever on any deployment that enables the canary. Excluded with `starts_with`, not `LIKE` (the prefix is underscore-heavy and `_` is a `LIKE` wildcard), with a test pinning the literal to `canary::CANARY_WORKFLOW_NAME_PREFIX`. (6) **Re-exporting into a directory replaces the bundle.** Fixture names embed the execution id so they never overwrite — they *accumulate* — while the manifest has a fixed name and *is* overwritten, so the gate replayed executions from every past run while the coverage record described only the latest. Cleaning is scoped narrowly: only when the manifest marker is present, and using the *same* predicate the gate's own walk uses (recursive, every `*.json` at any depth — see rounds 15/17) so a stale fixture cannot survive the clean and still be replayed. A JSON-bearing directory with no manifest is **refused**, so `--output-dir .` cannot eat a user's files. (7) `context_headers` are now carried through the sample export, so a workflow reading ambient headers replays against the same ones it saw live instead of false-diverging. **The same family, closed exhaustively (Codex round-12 P1):** `queue_name` — supplied by the live worker from the claimed task row, present in no `WorkflowEvent` — was likewise dropped, so an *unchanged* workflow branching on `ctx.queue_name()` (or embedding it in a recorded activity input) replayed under `""` and false-reported drift. It now rides `HistoryExportRequest`/`HistoryExportDocument`/`HistorySnapshot` at the same top-level name (additive, `skip_serializing_if`, so a legacy export still parses), is populated by **all four** export producers (single, batch, #798 sample, retention archive), is applied to the replay context by `run_workflow_strict`/`_advancing_clock`/`run_workflow_canary`, and is carried across the `replay_bundle` -> `ReplayVerifier` delegation via `FixtureReplayDefaults` (with a `WorkflowReplayer::with_queue_name` global fallback for a hand-built fixture). Two further instances of the same gap were found while fixing it and closed: the DB canary (`query_running_executions`/`run_canary`, which filtered on `queue_name` but never selected it) and `WorkflowTestEnv::replay_check` (which threads the env's configured queue into the LIVE run via span_meta but not onto the replay snapshot). **The `build_id` half of the family is the inverse case (Codex round-13 P1), and closing it fixes a false GREEN rather than a false red.** `ctx.build_id()` is *not* a recorded per-execution value: the live worker reports its own configured `WorkerConfig::build_id` through span metadata, never the execution's recorded `assigned_build_id`. Every replay path left it at `None`, so candidate-only code such as `if ctx.build_id() == Some("v2") { … }` was **unreachable during the gate** — the historical branch replayed clean and the gate certified a build that diverges the moment it takes traffic. That inverts the correct source, so unlike `queue_name` this value is deliberately **not** carried on the fixture: a snapshot-sourced build id would be the *recording* build and would reintroduce exactly the blind spot. It is instead a uniform, operator-supplied replay-config value — `WorkflowReplayer::with_build_id` / `ReplayVerifier::with_build_id` ("pass the build you are about to promote"), threaded through `FixtureReplayDefaults` so the `replay_bundle` → `ReplayVerifier` delegation carries it, and applied to the replay context by all three entry points (`run_workflow_strict`/`_advancing_clock`/`run_workflow_canary`). Three further instances of the same blind spot were found while fixing it and closed: the **deploy replay canary** and the **replay-diagnosis endpoint** (both run *inside* the deployed candidate and ask what the currently-deployed code does, yet replayed with no build id — now threaded from this process's own `EffectiveConfigView.worker.build_id` via a shared `running_build_id` helper, treating an empty configured build as `None` so it matches what the live worker reports); and the harness path `run_workflow_with_state_advancing_clock`, which threaded six span-meta values but silently dropped `build_id`, so a `WorkflowTestEnv::with_build_id` run would never have seen it. `WorkflowTestEnv` gains `with_build_id` wired to **both** halves — the live span metadata and the `replay_check` self-check — with a symmetry test pinning them together, because wiring only the live half is precisely what made `queue_name` a bug. Falsified: neutering the canary's `.with_build_id(…)` makes the money test report `1 clean, 0 diverged` on a fixture whose candidate branch genuinely diverges — the exact false GREEN, reproduced and then closed. **A fourth axis: the deadline can go stale between discovery and fetch (Codex round-14 P2).** The remaining mutable candidate field is `deadline_at`, which pause (#383) moves — resume pushes it forward by the pause span. Candidate discovery and the per-candidate history fetch are separate round-trips with the whole export loop between them (up to `MAX_SAMPLE_TOTAL` candidates), so a `PAUSED` execution resumed inside that window was exported with a history from *after* the resume and a deadline from *before* it. `should_continue_as_new()` (#772) reads the live shifted deadline, and the stale, earlier value reports **less** remaining budget — so replay could trip the checkpoint fraction and emit a `ContinueAsNew` the recorded history cannot contain (a sampled execution is non-terminal by definition), reporting a divergence the candidate build did not cause. Fixed in the shared per-candidate loader `export_history_candidate`, so the **batch** export inherits it too, by re-reading `execution_timeout`/`deadline_at` from the row immediately *after* the history load. Reading last is not merely a narrower window: it flips the residual READ COMMITTED race into the safe direction, since a deadline *fresher* than the history makes the checkpoint **less** likely to fire, which always matches a history carrying no `ContinueAsNew`. A row that vanished between the two reads (retention collects the execution and its events in one transaction) is recorded as an export failure rather than shipped as a fixture, so it blocks the gate at rung 2 instead of letting a silently biased bundle exit 0. Falsified: driving the export with a deliberately stale candidate reports `left: 12:19Z, right: 13:19Z` — exactly the one-hour pause span — before the fix, and the row's current value after. (8) **The docs recipe did not work**: the Rust snippets did not compile (`workflows![]` takes bare fn names, and `allow_empty_bundle`/`require_complete_coverage` live on `ReplayVerifier`, not `WorkflowReplayer`), the CI job used a nonexistent `HARVEST_API_URL` (it is `HARVEST_URL`), the flag table advertised a phantom `omit` policy value, and the headline two-command loop omitted `--payload-policy full` — so following it verbatim produced a bundle the gate now refuses. All fixed, and the CLI now warns at **write** time when it produces a redacted bundle, so the problem surfaces when the bundle is created rather than as a wall of BLOCKED lines later.

Measured **26.4 s** wall clock in a debug build, with the phase split printed for diagnosability: **export 0.89 s + bundle write 0.14 s + replay 25.5 s**. The DB-bound half — the part that actually scales with fleet size and shard count — is under a second; replay is pure local CPU and accounts for ~96% of the clock. **Post-review hardening, round 15 (Codex P2 — JSON symlinks in the bundle replace).** The re-export cleaner (`clear_stale_bundle`) and the replay walk (`testing::collect_json_files`) disagreed about what counts as a fixture: the cleaner required a **regular file** (`file_type().is_file()`), while the replay walk collects any **non-directory** entry ending in `.json`. A `*.json` **symlink** therefore fell in the gap — skipped by the cleaner, replayed by the gate. Three consequences, all confirmed by red tests before fixing: (1) the stale linked fixture survived a re-export and was replayed against the fresh manifest, so the gate reported drift the candidate never caused and exited 2 on an unchanged build — the exact false red this feature exists to prevent; (2) because `fs::write` **follows** a symlink, a leftover link whose name collides with a fixture about to be written sent that write **outside** `--output-dir` (reproduced concretely: a file containing `"ORIGINAL"` in an unrelated directory was overwritten with a Harvest fixture); (3) the "is this our bundle?" evidence is the count of JSON entries, so a directory holding *only* a linked JSON read as empty, the refusal never fired, and the command wrote into a directory it did not create. Fixed by making the cleaner's fixture predicate **byte-identical to the replay walk's** — "not a directory, ends in `.json`" — so the two can no longer disagree; `fs::remove_file` removes the **link**, never the file it points at, and clearing it before the write is what keeps the replace contained. The manifest **marker** is deliberately held to a *stricter* rule than the fixtures it guards (a top-level **regular file**), because it is what *authorizes* deleting a directory's contents: a *linked* manifest is not evidence this CLI wrote the directory, so it falls through to the `.json` branch and **blocks** the replace instead of licensing it — which also keeps the manifest write itself contained, since it is a name the export is about to `fs::write`. Also corrected a **stale doc bullet** on the same function claiming "only top-level `*.json` entries are removed. Subdirectories … are left alone", which the earlier recursive-cleanup fix had already made untrue. Tests (`#[cfg(unix)]`, matching the repo's existing symlink-test precedent): `a_json_symlink_in_a_marked_bundle_is_cleared_like_a_regular_fixture` (link cleared, **target survives**), `a_re_export_never_writes_through_a_colliding_json_symlink` (outside file byte-unchanged), `a_directory_whose_only_json_is_a_symlink_is_refused_not_written_into`, and `a_symlinked_manifest_does_not_authorize_clearing_the_directory` (already passing — pinned so the stricter marker rule cannot regress). **No new `WorkflowEvent` variant, no migration** — CLI-only.

**Post-review hardening, round 16 (Codex P2 — erased fixtures must not produce a verdict).** A fixture whose payloads were **erased** (issue #495) carries `{"_harvest_erased": true}` tombstones instead of the real inputs, so replaying it compares the candidate's real values against scrubbed placeholders — reporting drift that does not exist, or a "clean" result that certifies nothing. Neither the export nor the gate rejected it. Codex named the sample-export race (an execution selected while in flight completes and is erased before the sequential per-candidate fetch reaches it; the cloned candidate still reads `RUNNING`, and the round-14 refresh re-reads only the two deadline fields). Verifying it surfaced a **second, wider door that needs no race at all**: erasure is *terminal-only*, and the **batch** export has no in-flight restriction — so the executions it exports are exactly the population erasure is permitted to touch. Fixed at the **gate** rather than only at export, because that one placement covers both doors plus a hand-curated bundle and a fixture erased *after* it was written: new `erased_fixture_reason` joins the existing `unreplayable`/`offloaded`/`codec_opaque` guard chain in `testing.rs`, making erasure the third member of the opaque-payload family (the one that is *irreversible*, so the remedy is never "decode it" but "re-export a sample that excludes this execution"). Reported as a **harness error (exit 2)**, never silently skipped — a dropped fixture shrinks coverage while the manifest still claims it, the one failure this gate must not have. Detection keys on a tombstone occupying a **payload field**, not on the marker string appearing anywhere in the document, so a workflow whose own data mentions `_harvest_erased` still replays (guarded by a dedicated test, so the fix for one false red does not invent another); a cheap `json.contains` pre-check skips the per-event walk for every healthy fixture. Tests: `an_erased_fixture_blocks_the_gate_instead_of_reporting_drift` (money test — blocked, exit 2, **not** counted as drift, reason names the cause and issue #495) and `a_payload_that_merely_mentions_the_tombstone_key_still_replays`. Falsified by neutering the guard: the money test then fails at the `blocked.len() == 1` assertion. **No new `WorkflowEvent` variant, no migration** — a read-side guard in the replay harness.

  **Post-review hardening (Codex round-18 P1): `allow_empty_bundle` certified a release against an export outage.** The flag exists for a fleet that is legitimately idle, but a bundle is also empty when the *exporter could not read the fleet* — a total shard outage yields zero fixtures and a manifest whose `status` is `unavailable`. From the fixture count alone the two are identical, so the opt-out converted an outage into exit `0`: a release certified against zero workflows, the worst verdict this gate can produce. **Neither existing rung caught it**, which is why it survived seventeen rounds of review: rung `2`'s `export_is_incomplete` is `truncated_by_size || export_failures > 0`, and a *total* outage selects no candidates at all — so there are no per-candidate fetch failures to count and no size ceiling to hit, both `0`/`false`; rung `4` does read the status, but only under `require_complete_coverage(true)`, which is off by default. The manifest said `unavailable` and nothing looked. Fixed at rung `3` with `ReplayDriftReport::emptiness_is_contradicted()`: the `allow_empty_bundle` opt-out is void when the bundle's own manifest reports anything other than complete coverage, because an export that never saw the whole fleet cannot make the claim "the fleet is idle" that the flag licenses. **Deliberately scoped to a manifest that *contradicts* emptiness, not to one that *proves* it** — a bundle carrying **no** manifest keeps the opt-out. `build_bundle_files` pushes the manifest unconditionally, alongside the fixtures and even when it produced none, so a Harvest-produced bundle always has one and "no manifest" means the bundle did not come from the exporter (a hand-assembled directory, or a gate binary pointed at the wrong path) — not the outage case this closes. An operator who wants absent evidence to fail closed already has `require_complete_coverage(true)`, whose `coverage_claim_unsatisfied` does exactly that; applying that rule here unconditionally would have overridden an explicitly-set opt-out on evidence that does not exist, and would have broken the documented all-skipped opt-out (`a_bundle_whose_fixtures_were_all_skipped_verifies_nothing`), which has nothing to do with export health. The first cut did exactly that and was caught by those two pre-existing tests. Tests: `an_empty_bundle_from_a_failed_export_is_not_licensed_by_allow_empty_bundle` (money test — `unavailable` manifest, exit `3`, and the report names the manifest as the cause), `an_empty_bundle_from_a_partial_export_is_not_licensed_either` (a half-read fleet is the same defect when nothing was verified — the unreachable shards are exactly where the drift would be), plus two **boundary** tests pinning the scope so a future tightening cannot swallow the opt-out along with the bug: `an_empty_bundle_with_complete_coverage_is_still_licensed` and `an_empty_bundle_with_no_manifest_keeps_the_opt_out` (which also asserts `require_complete_coverage(true)` still exits `4` on the same directory). Falsified by neutering `emptiness_is_contradicted` to `false`: both money tests then report `left: 0, right: 3` — the exact false green — while every boundary test stays green under both versions, proving the fix is scoped to the finding. **No new `WorkflowEvent` variant, no migration** — one predicate on the exit ladder.
