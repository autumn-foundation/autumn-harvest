## Phase 3.51 — workflow-type reachability follow-up: samples, orphan summary, boot gate (issue #700)

Thin follow-up on the already-shipped workflow-type reachability check (issue #520 / Phase 3.35), closing the four re-scoped ACs of #700. **No new `WorkflowEvent` variant, no migration, no new route** — this is a read-path (samples + top-level summary) plus a startup-read gate, entirely additive.

- **AC2 — bounded execution-id samples.** `execution::non_terminal_counts_by_workflow_name` now returns up to `REACHABILITY_SAMPLE_CAP` (=5, documented) representative *non-terminal* execution ids per workflow type via `(ARRAY_AGG(id ORDER BY started_at ASC, id ASC))[1:5]` folded into the existing `GROUP BY` — so an operator can drill straight into a stuck run of an `orphaned` type instead of paginating `GET /workflows`. Terminal executions are excluded by the existing state filter (`RUNNING`/`SUSPENDED`/`PAUSED` only), so a sample never points at a completed run. New `sample_execution_ids: Vec<Uuid>` on `WorkflowTypeNonTerminalCount` (core) and `WorkflowTypeReachability` (plugin); the plugin caps the cross-shard union to the same cap in shard-iteration order — documented as *representative and bounded*, not a guaranteed global-oldest-across-shards set. Empty for `safe_to_remove` types. (The `ARRAY_AGG` slice materialises the full ordered id array per group before slicing — transient memory proportional to group size, acceptable under the < 2 s / 100k-execution budget; the drop-in fallback for very large groups is a `LATERAL (SELECT … ORDER BY started_at LIMIT n)` per group.)
- **AC3 — top-level orphan summary.** `WorkflowReachabilityReport` gains `orphaned: bool` (true when any type has an `orphaned` verdict) and `total_orphaned_executions: i64` (sum of `non_terminal_count` over `orphaned`-verdict types — a count of stranded *executions*, not types), so a CI/CD gate asserts "zero orphans" against a single field instead of walking `items[]`. Both reflect only the inspected shards; when `status` is `partial`/`unavailable` an unreachable shard could still host an orphaned type. Registered in `management_api_response_fields()` and `docs/api-contract.json` (kept in sync, guarded by `contract_regression`); nested `sample_execution_ids` is documented in the route description (precedent: `next_retry_at`/`input` on `/stack` live in the description, not the top-level `fields` list).
- **AC4 — boot-time fail-fast (default warn).** New `[harvest.startup] orphaned_workflows = off|warn|fail` config (env override `AUTUMN_HARVEST_STARTUP__ORPHANED_WORKFLOWS`, case-insensitive), mirroring the `require_shard_readiness` precedent. `start_harvest_runtime` runs `build_workflow_reachability_report` at the earliest point the handler registry and storage pool are both installed, and feeds `(report.orphaned, report.status)` into the pure `startup_orphan_decision(action, orphaned, status) -> StartupOrphanDecision` — the single source of the fail/warn/partial policy (AC4 reads AC3's two fields). `off` skips the check; `warn` (default, non-breaking — a mixed fleet mid-rollout must not crash-loop) logs the orphaned types and continues; `fail` refuses startup, returning `Err` **before** `admission_guard.commit()` (published gate cache + metrics roll back) after tearing down runner/outbox/gate-refresh so a refused boot leaks no background tasks. A failure of the check *itself* only warns (never blocks boot on its own error). **Crash-loop safety:** `fail` aborts **only** when orphaned types are present **and** the cross-shard report is `Complete`; a `partial`/`unavailable` report degrades to `Warn` — a boot loop has no human in the loop, so a transient unreachable shard must never hard-fail startup. This is deliberately **asymmetric** with the CLI gate (`harvest workflow-types reachability`), which fails *closed* (exit 2) on a partial report because a human reads its exit code. Truth-table clarification: `orphaned == false` resolves to `Continue` for every action (a clean boot never warns). **Architecture deviation (deliberate):** the gate lives in the plugin (`[harvest.startup]` + `startup_orphan_decision`), not on `HarvestBuilder`, because the cross-shard fan-out is plugin territory — `build_workflow_reachability_report` *is* the programmatic embedder access the AC's "e.g. a `HarvestBuilder` method" refers to.
- **AC9 — runbook.** `docs/runbooks/safe-deploy.md` gains a "Pre-cutover handler-coverage gate" section ahead of the #512 replay canary: its deploy-ladder position (worker drain #386 → this gate → #512 canary → #480 → #614 → #538/#510), the CLI (exit 2 on orphan/partial) and API single-field `orphaned`/`total_orphaned_executions` gate, the per-group `sample_execution_ids` drill-in, and the boot-time `[harvest.startup] orphaned_workflows` option with its crash-loop-safe partial-shard behavior. Cross-linked to `safe-handler-removal.md` (type-level vs build-id vs `ctx.version()` distinction), with a back-pointer added there.

**CI:** wired the plugin `workflow_reachability_integration` suite (previously ALLOWLIST debt, only compile-checked) and the new core `workflow_reachability_samples_tests` module into `.github/ci/integration-suites.txt`; removed the now-covered ALLOWLIST entry and lowered `ALLOWLIST_MAX_LEN` 74 → 73.

**Tests, TDD red→green:** pure unit tests in `workflow_reachability.rs` (samples cap/merge/empty, orphan summary, `startup_orphan_decision` truth table) and `config.rs` (default/TOML/env/unknown-value on both the env AND TOML paths); core DB `workflow_reachability_samples_tests` (executed against Postgres — includes a `samples_are_oldest_first` test seeding staggered `started_at` values in reverse insertion order to pin the `started_at ASC, id ASC` ordering); plugin HTTP `orphaned_group_surfaces_bounded_execution_id_samples` + `endpoint_exposes_top_level_orphaned_and_total` (testcontainers, compile-checked where Docker is unavailable, executed by CI on Linux, per the #543/#544/#601 precedent).

**Post-review hardening (consolidated ship-list, PR #1109):** three review lenses + the Gemini bot returned no blockers; the following polish items were applied. (1) **Sample-cap drift guard** — Diesel `sql_query` cannot interpolate the `REACHABILITY_SAMPLE_CAP` const into the SQL string, so the per-shard slice stays a hardcoded `[1:5]` literal; a DB-free guard unit test now fails if the literal and the const drift apart, an inline SQL comment names the invariant, and the const doc was corrected (it aspirationally wrote `[1:REACHABILITY_SAMPLE_CAP]` while the code hardcodes `[1:5]`). (2) **Boot-gate decision coverage** — new `boot_gate_{fail_aborts,warn_allows,fail_allows_clean}` integration tests drive the exact two-step decision path `start_harvest_runtime` composes (`build_workflow_reachability_report` + `startup_orphan_decision`) against a seeded database, each filtering to a unique workflow type for race-free isolation; the private, config/migration/pool-coupled `start_harvest_runtime` shell (thin task-teardown glue over this decision) is not integration-callable. (3) **Default-boot-query cost + drain-first callout** — `safe-deploy.md` now states the reachability check runs **by default** under `warn` on every boot (a bounded cross-shard `GROUP BY … ARRAY_AGG` aggregate; `off` is the only zero-cost setting, the per-group `LATERAL … LIMIT n` fallback bounds memory), and warns that enabling `fail` refuses boot **fleet-wide** until a persistent orphan drains — so confirm `orphaned == false` via the CLI gate before flipping it on. (4) **Readability** — the boot-gate decision compares against the `ReachabilityReportStatus` alias name to match its parameter type, and the cross-shard sample-dedup rationale was corrected (execution ids are globally unique and each lives on exactly one shard).
