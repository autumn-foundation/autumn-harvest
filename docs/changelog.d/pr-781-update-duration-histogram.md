## Phase 3.54 — Update admit→terminal latency histogram (issue #781)

**Observability** (implemented): Closes the residual of issue #781 (PR #1032 shipped the six `harvest.*` signal/update lifecycle **counters**; this adds the remaining success metric — a p99 admit→complete latency panel). New histogram `harvest.update.duration` (`METRIC_UPDATE_DURATION`) records the wall-clock seconds from an update's durable admission (`UpdateAdmitted`) to its terminal result recording (`UpdateCompleted`/`UpdateFailed`). **AC: no new `WorkflowEvent` variant, no migration, no macro-path change** — a pure additive-metrics slice modelled on the #519/#487 recipe (additive no-op-default trait method + `metrics_rs_adapter` bridge + coverage tests).

**Naming / family:** shipped as `harvest.update.duration` (family-consistent with #1032's `harvest.update.*` counters, NOT the issue's literal `harvest.workflow.update.duration`). Prometheus series `harvest_update_duration_{bucket,count,sum}`.

**Labels — `workflow`, `name`, `queue`, `outcome`** (all bounded; `execution.id`/`update_id` never a label, ADR-0001 §7). Mirrors the exact label vocabulary of the `harvest.update.completed`/`failed` counters (`workflow`, `name`, `queue` — the update name resolved to the registered/imperative handler set, an unregistered raw-route name bucketed to the `__unregistered__` sentinel by the shared `collect_update_result_metrics`), plus an `outcome` label (`completed`/`failed`) so one histogram covers both terminal kinds. **Rejected updates are excluded** — no handler runs, so they never enter the histogram.

**Duration source:** the admit timestamp comes directly from the `UpdateAdmitted.timestamp` field already present in the loaded `history_events` slice (no new event variant, no timestamped-history load). The terminal time is `Utc::now()` at the post-commit emit (`UpdateCompleted`/`UpdateFailed` carry no timestamp). New pure, unit-tested helper `worker::update_admit_duration_secs(admit_ts: Option<DateTime<Utc>>, now) -> Option<f64>` computes `(now - admit).max(ZERO)` in seconds — a clock-skew negative delta **clamps to `0`** (never a garbage/negative sample), and a `None` admit (the admit could not be resolved from history) **skips the histogram sample entirely** (the counter still fires with name `"unknown"`).

**Emission point (piggybacks on #1032's exact path — inherits its delivery semantics):** `collect_update_result_metrics` was extended to carry the admit `Option<DateTime<Utc>>` alongside each `(name, completed)` pair, and `emit_update_result_metrics` now captures one `now` per cycle and calls `record_update_duration(workflow, name, queue, outcome, secs)` alongside the existing completed/failed counter emit — at all three call sites (the terminal/suspend `Persisted` arm and the two inline external-signal branches). No separate `is_replaying` gate: `RecordUpdateResult` is produced only on live execution and the emit is only post-commit, so exactly-once is inherited by construction. **Delivery semantics (documented by reference to the #684 counters, not over-claimed):** exactly-once on the happy path; a crash after the persist commit but before the post-commit emit drops the sample (at-most-once for that window, never a double-count).

**`metrics_scrape.rs` — deliberately OMITTED (with justification):** the plugin's built-in Prometheus scrape recorder is per-metric hand-maintained (only `workflow_duration`/`activity_duration` histograms have a field + `record_*` override + `push_histogram` call; there is no generic histogram render path). The #1032 update lifecycle **counters are entirely absent** from it — the `HarvestMetricsRecorder` impl implements no `record_update_*`, so all update metrics fall through to the trait no-op and are exposed only via the `metrics-rs` adapter path. Adding `harvest.update.duration` there would be the lone update-family metric in the scrape recorder, inconsistent with its five sibling counters; omission is the consistent choice (the `_bucket` p99 series comes from the metrics-rs Prometheus exporter regardless).

Bridged in `metrics_rs_adapter` (`MetricsRsRecorder::record_update_duration` → `histogram!` with the `METRIC_LABEL_WORKFLOW`/`METRIC_LABEL_NAME`/`METRIC_LABEL_QUEUE`/`METRIC_LABEL_OUTCOME` constants). One new dashboard panel (id 908, "Update latency (admit → terminal)") in the "Signal & update lifecycle" row of `docs/dashboards/starter-pack-v0.1.0.json` — p99 `histogram_quantile` over `_bucket` plus a bucket-less `_sum`/`_count` avg fallback, mirroring the `harvest_workflow_pause_duration` panel. **No alert rule added** — panel only (an arbitrary latency threshold is a review-time decision). ADR-0001 §7 catalogue, `docs/telemetry.md` (emission-points + labels tables), and the CLAUDE.md telemetry module row updated; anti-drift coverage extended (`DASHBOARD_PROMETHEUS_SERIES` + `SERIES_LABELS` in `dashboard_pack_docs.rs`).

Tests, TDD red→green (verified RED via compile errors + a live anti-drift failure): telemetry constant-name + no-op-default unit tests; `metrics_rs_adapter` label-content bridge test (`bridges_update_duration_histogram_with_bounded_labels`, via `metrics::with_local_recorder`); `worker.rs` pure unit tests (`update_admit_duration_secs` none/positive-delta/negative-clamp, and `collect_update_result_metrics_carries_admit_timestamp` — plus the four existing collect tests updated to the 3-tuple); `metrics_coverage.rs` reachability + bounded-label test (`update_duration_histogram_reachable_with_bounded_labels`); `dashboard_pack_docs.rs` anti-drift gate (panel + series + labels). All executed green in the sandbox (no-DB surfaces); the worker pure helpers run under `--features db --lib` without a live database.
