## Phase 3.x — `ctx.race()`: follow-on durable command no longer nd-blocks when a loser is in-flight (issue #1126)

Fixed a `ctx.race()` (issue #600) replay bug where a durable command issued in the **same decision cycle** immediately after the race resolved — a plain activity, `ctx.mutex(k).acquire()` (issue #691), a timer, any positional `match_*` — would nd-block (issue #603) whenever a **losing activity branch was still in-flight** at resolution.

**Root cause.** In the live resolving cycle, `HistoryMatcher::settle_terminal` consumes the winner branch's own `ActivityStarted`, but a losing branch that resolved as `ActivityInProgress` has its synthetic terminal (`ActivityFailed`, from the pending `CancelRaceLosers` bookkeeping command) appended **only at persist time** — invisible to this cycle's matcher. Its recorded `ActivityStarted` was therefore left unconsumed straddling the cursor, so the next positional `match_*` for the follow-on command diverged (`ActivityScheduleMismatch`) → nd-block → permanent wedge until a rollback. Later replays already worked (they take the `peek_u64_marker` branch, where the recorded winner marker + synthetic `ActivityFailed` reposition the cursor), so **only the live resolving cycle was broken**. Child-workflow races were unaffected (no separate started event to strand).

**Fix (matcher-side only — append-only contract preserved).** New `HistoryMatcher::consume_race_loser_frontier(&[ActivityExecId], &[ExecutionId])`, called from `WorkflowContext::settle_race`'s **first winner-recording branch** (the `else` arm) after the loser id sets are collected and before the `CancelRaceLosers` push. It scans from the cursor, marks-consumed only the given losers' unconsumed `ActivityStarted` / `ActivityHeartbeat` (and, defensively, a losing child's `ChildWorkflowStarted`), then advances the cursor past them. Scoped strictly to the resolving race's own loser ids, so it is safe under `futures::join!(race1, race2)` interleaving (a sibling race's events are untouched); no-op (early return) when there are no losers; never invoked on later replays (they take the `peek_u64_marker` branch). **No event mutation, no new `WorkflowEvent` variant, no persist-ordering change, no migration** — histories recorded before the fix replay identically after it.

**Behavior change.** The `ctx.race()`-then-`ctx.mutex(k).acquire()` (and race-then-any-durable-command) pattern in the **same** decision cycle now completes cleanly. This flips the `ctx.race()` interop **known limitation** documented on the `ctx.mutex` primitive (issue #691 / PR #1122) from a documented workaround to resolved behavior — the CLAUDE.md prose is updated accordingly.

**Test evidence.**
- **RED reproducer** (`context::tests::race_with_in_flight_activity_loser_does_not_wedge_a_follow_on_command`, no-DB): builds a history with a race, an in-flight loser `ActivityStarted`, and the winner's `ActivityCompleted`, resolves the race, then asserts the follow-on `match_activity("next_step")` returns `HistoryMatch::NoMatch` (fresh dispatch at the frontier) rather than diverging. Fails before the fix, passes after.
- **Replay-neutrality fixtures** (`replayer_tests::replay_race_with_in_flight_loser_and_follow_on_activity_succeeds`, `..._race_ending_at_race_no_follow_on_succeeds`): a post-fix history with the follow-on and a pre-fix history ending at the race both `ReplaySucceeded` — proving histories recorded before the fix replay identically after it.
- **DB end-to-end regression coverage** (`mutex_tests`, testcontainers/local-Postgres): a race with a fast winner + a genuinely in-flight slow loser (shared-barrier) followed by (a) a plain activity and (b) `ctx.mutex(k).acquire()` + critical section both reach `COMPLETED` with `nd_blocked_at IS NULL` — the flagship flip of the #691 known limitation to regression coverage.
- All 28 `race_` unit tests and 196 `replay::` matcher unit tests remain green.
