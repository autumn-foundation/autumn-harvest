## Phase 3.51 — Chain-scoped workflow lifetime cap (issue #617)

A **chain-scoped lifetime cap** (`chain_execution_timeout`) distinct from the per-run `execution_timeout` (#243): it is anchored at the FIRST run's start and CARRIED VERBATIM across every continue-as-new, so a runaway loop cannot escape the cap by continuing-as-new. Enforced by the existing timeout scanner and the existing `WorkflowExecutionTimedOut` event — **no new `WorkflowEvent` variant**.

**Storage** (one additive migration `20260714000000_harvest_workflow_chain_timeout`, mirroring #243's dual-column shape): two nullable columns on `harvest_workflow_executions` — `chain_execution_timeout INTERVAL NULL` (the chain-cap DURATION) and `chain_deadline_at TIMESTAMPTZ NULL` (the absolute enforcement deadline, `first_run.started_at + chain_execution_timeout`, copied verbatim into every continue-as-new successor). Partial index `idx_harvest_executions_chain_deadline ON (chain_deadline_at) WHERE state = 'RUNNING' AND chain_deadline_at IS NOT NULL`. Both columns added to `schema.rs`, `WorkflowExecution` (read struct — additive serialized fields on the nested `.execution` describe surface, matching the `deadline_at`/`sla_deadline_at` precedent, non-breaking, no contract-registry change) and `NewWorkflowExecution` (insert struct).

**Anchor & inheritance rules** (the core semantic):
- **Fresh chain-origin start** (HTTP start, scheduler tick/backfill, typed stub, etc.): `chain_deadline_at = target_start_time + effective_chain_timeout`.
- **Continue-as-new successor** (`worker::persist_workflow_continue_as_new`): CARRY BOTH COLUMNS VERBATIM — copy the predecessor's absolute `chain_deadline_at`, never recompute `now + timeout` (the per-run `deadline_at`/`sla_deadline_at` right above it are re-anchored; the chain deadline is not).
- **Workflow-level retry (#523)** (`worker.rs`): CARRY — `StartWorkflowParams.inherited_chain_deadline_at = exec_ref.chain_deadline_at` used verbatim (a retry is the same logical run continuing).
- **Reset fork (#148)** (`reset::insert_fork_execution`): RE-ANCHOR — a fresh chain origin (`chain_deadline_at = now + source.chain_execution_timeout`), consistent with `first_exec_id: None`/`schedule_id: None` (the #488 lineage-break precedent).
- **Child workflow** (`worker.rs`): a fresh chain origin resolving the child's OWN `WorkflowInfo.chain_execution_timeout` at spawn, exactly as it resolves the child's per-run `execution_timeout`/`sla` — awaited children resolve it (`now + effective`); the detached-child path (which resolves no `execution_timeout` at spawn) gets `None`, matching the existing pattern precisely.

**Effective resolution + ceiling (AC4 — a deliberate divergence from #243):** the pure `timeout::effective_chain_timeout(workflow, ceiling)` returns the MIN of all present values, and `None` only if both are absent — so the builder ceiling acts as BOTH a cap AND a fleet-wide DEFAULT (`(None, Some(c)) => Some(c)`). This diverges from #243's per-run ceiling (which only caps a *specified* value, `(None, Some) => None`) so an operator can cap every chain even when a workflow under-specifies. Documented in code and `docs/getting-started/07-reliability-knobs.md`.

**Config surfaces (AC4):** `#[workflow(chain_execution_timeout = "7d")]` macro attribute (parsed exactly like `execution_timeout`, added to the "unsupported attribute" list); `WorkflowInfo::chain_execution_timeout` field + `with_chain_execution_timeout` fluent builder; `HarvestBuilder::max_workflow_chain_timeout(...)` ceiling + `max_workflow_chain_timeout_ceiling()` accessor (mirrors `max_workflow_execution_timeout`); `WorkflowSchedule::chain_execution_timeout` field + `with_chain_execution_timeout` builder are **currently inert** (not persisted on `harvest_schedules`, not read at tick — at exact parity with #243's own dead `WorkflowSchedule::execution_timeout`; kept for API symmetry). The *functional* schedule-level chain default reaches scheduled runs through the workflow-type `#[workflow(chain_execution_timeout = "…")]` attribute inherited via `WorkflowInfo` at tick, plus the fleet-wide ceiling. **AC4 fleet-wide ceiling threading** (review fix): the ceiling (which doubles as a fleet-wide default) is applied at every ORIGIN start path — plain HTTP start, signal-with-start, update-with-start, batch start, trigger-now, and workflow backfill (via `HarvestApiState::max_workflow_chain_timeout()`), and the scheduler tick + buffered drain (via a new `HandlerRegistry::max_workflow_chain_timeout` field, since the core scheduler has no `api_state`). Debounce/throttle/batch DEFERRED starts carry the declared cap + ceiling through two additive `DebounceStartOptions` fields (`chain_execution_timeout_secs`, `max_workflow_chain_timeout_ceiling_secs`) resolved at admission and threaded at all four fire sites. DAGs carry NO chain cap (the `#[dag]` macro has no chain attr; DAG start paths pass `None`). `StartWorkflowParams` gains three fields (`chain_execution_timeout`, `max_workflow_chain_timeout_ceiling`, `inherited_chain_deadline_at`), defaulted `None` at every construction site except the retry site and the resolving HTTP/scheduler/typed-stub start sites. `WorkflowHandleClient` and the plugin `HarvestApiState` mirror the ceiling (`with_max_workflow_chain_timeout` / `set_max_workflow_chain_timeout` / `max_workflow_chain_timeout()`), wired from `BuiltHarvest::max_workflow_chain_timeout`.

**Deliberately NOT threaded into `WorkflowContext`/`ctx.deadline()`/`should_continue_as_new()`** (issue #772 stays bound to the per-run `deadline_at`) — the chain cap is SCANNER-ONLY enforcement, so a runaway loop cannot "escape" it via CAN. **Not shifted on pause/resume** — `chain_deadline_at` is absolute wall-clock (runaway-protection/compliance reading; chain-deadline extension is out of scope).

**Scanner (AC2, timeout.rs):** `enforce_workflow_execution_timeouts` selects `state='RUNNING' AND ((deadline_at < NOW()) OR (chain_deadline_at < NOW()))`; the const `workflow_execution_timeout_query()` string reflects the same disjunct. Per expired row, the pure `classify_workflow_timeout(deadline_at, chain_deadline_at, now) -> (fired, TimeoutKind)` decides which fired with **chain precedence** (a chain-only expiry has no per-run `deadline_at` and is handled without panicking). New additive `TimeoutType::WorkflowChain` enum variant (distinct Display "workflow chain lifetime exceeded"; NOT a `WorkflowEvent` variant) used for chain timeouts' error string.

**Metric (AC6):** new counter `harvest.workflow.chain_timeout` (`METRIC_WORKFLOW_CHAIN_TIMEOUT`, labels `workflow`/`queue`; additive no-op default `record_workflow_chain_timeout` on `MetricsRecorder`, bridged in `metrics_rs_adapter`). The scanner emits it for `TimeoutKind::Chain` and `harvest.workflow.timeout` for `TimeoutKind::Run`; both still emit `harvest.workflow.terminal{outcome="timed_out"}` (the chain-vs-run distinction lives only in the two timeout counters). Dashboard panel in `docs/dashboards/starter-pack-v0.1.0.json`, catalogue rows in `docs/telemetry.md` and ADR-0001 §7, and the anti-drift `dashboard_pack_docs` coverage gate updated (series + label ground truth).

**Backward compatible:** `None` default everywhere; a workflow with no chain cap and no ceiling behaves byte-for-byte as before. **No new `WorkflowEvent` variant, no replay-determinism impact.**

**Docs/examples:** `docs/getting-started/07-reliability-knobs.md` (run-cap vs chain-cap decision, runaway-loop story, ceiling-as-default, absolute-wall-clock/pause note); `examples/long_running.rs` (run-cap vs chain-cap usage).
