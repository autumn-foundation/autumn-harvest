## Phase 3.51 — declarative DAG signal/approval gate nodes (issue #746)

A unified `#[dag]` can now **pause on a named signal** between graph nodes, with an optional durable timeout — the declarative way to insert a human approval or external-event wait without abandoning the DAG surface for a hand-written `#[workflow]`. A **gate node** is a `DagTask` whose new `signal: Option<DagSignalGate>` field is `Some`; it has no activity dispatch, its node identity (`activity_name`) is the signal name, and it composes like any other node (`.upstream(&gate)`, `.map_activity(f).over(&gate)`, `.condition(...)`). Fluent `DagBuilder::signal_gate(name)` and `signal_gate_with_timeout(name, timeout, on_timeout)` return a `DagTaskRef`; new public types `DagSignalGate` and `GateTimeoutAction` (`FailRun` | `Continue`). **No new `WorkflowEvent` variant, no migration** — gates lower onto the existing #476 `receive_signal_timeout` / `wait_for_signal` machinery, reusing `TimerStarted` / `TimerFired` / `SignalReceived`, so a gated run is durable and replays deterministically (whichever of the signal or the deadline is recorded first in history wins on every replay).

**Semantics.** Signal arrives → node `Succeeded` with the payload as output; `on_timeout = Continue` deadline → `Succeeded` with `Value::Null`; `on_timeout = FailRun` deadline → `Failed` (the run fails). **AC2 "continue to a named branch" is expressed declaratively** — there is no bespoke branch-target mechanism; under `Continue`, the gate's null-vs-payload output *is* the branch selector via a downstream `.condition(...)` (e.g. `.condition(|ups| ups[0].is_null())` for the timed-out branch). A signal delivering a JSON array fans out a downstream `.map_activity(f).over(&gate)` node with zero map-lowering change (Gap B). Deliver the unblocking signal with the ordinary standalone `POST /workflows/{id}/signal/{name}` route (AC3).

**Level isolation** (highest-risk design point). The worker requires homogeneous suspension batches, so a `WaitForSignal` command must not share a batch with a level's `ScheduleActivity` dispatches. A `DagBuilder::build()` post-pass splits each Kahn level so **each gate occupies its own singleton execution level**. When a DAG contains no gates the level vector is returned byte-for-byte unchanged, so every existing DAG test and replay is untouched.

**Single-sourced walker.** The macro previously emitted two byte-approximate copies of the level walker (inlined `DagInfo.workflow_handler` and the shadow `WorkflowInfo.handler`), which had **already drifted** on error handling in the collect-all map branch. Both copies now shrink to a call into one core helper, `dag::run_unified_dag(ctx, input, levels, tasks)`, so the gate branch is written once and the drift bug is fixed (adopting the propagating, fail-fast-consistent behavior).

**Classic-DAG rejection (AC6).** A new `validate_dags_have_no_signal_gates_on_classic_path()` in `try_build` rejects any DAG with `workflow_handler.is_none()` (the classic discriminator) containing a gate, with `HarvestBuilderError::DagSignalGateRequiresUnifiedExecution { dag, signal }` naming both.

**Graph-view (AC4).** `dag_graph::DagRunNode` gains `kind: DagNodeKind` (`Activity` | `Gate`) and `DagNodeStatus::Waiting`; `build_run_graph` classifies a gate as `Waiting` while un-signalled on a RUNNING run and `Succeeded` once its `SignalReceived` is in history.

**MCP restoration (Gap A).** `DagInfo::consumes_signals()` reports whether a unified DAG has ≥1 signal-gate node. `McpWorkflowDescriptor` gains a `consumes_signals` flag sourced from it; the `signal_{dag}` tool suppression in `tool_operation_ids` / `tool_route_specs` (issue #597) is refined from a blanket `is_dag` to `is_dag && !consumes_signals`, so a signal-capable DAG regains its `signal_{dag}` tool (an agent can unblock a gate by handle) while an activity-only DAG still suppresses it.

Docs: "Signal / approval gates" section in `docs/getting-started/08-dags-and-schedules.md` (the schedule-vs-DAG decision table now points the single-signal-gate case at gate nodes). Example: `autumn-harvest/examples/dag_approval_gate.rs` (extract → approval gate → load, with a `FailRun` primary and a `Continue` + `.condition` named-branch fallback; four embedded `WorkflowTestEnv` + `WorkflowReplayer` tests). Tests: pure builder-API unit tests (gate metadata, timeout/action, level isolation, upstream/map composition, classic-DAG rejection) and unified `WorkflowReplayer` money tests (signal-first and timer-first histories replay deterministically) in `tests/integration/dag_signal_gate_tests.rs`; graph-view gate tests in the plugin `dag_graph`; the new `collect_descriptors_signal_capable_dag_keeps_its_signal_tool` mcp_tools unit test.
