## Phase 3.5x — Recursive cross-shard execution lineage tree (issue #621)

**Implemented.** New read-only management route `GET /api/harvest/workflows/{exec_id}/tree` returns the **entire descendant lineage** of an execution as one nested JSON tree, assembled across every readable shard in a single request. Before this, the only relationship primitive was `GET /workflows/{id}/children` (direct children only), so triaging a 4-level saga or fan-out meant hand-walking `parent_id` links level by level — and because a spawned child gets a fresh rendezvous-hashed `ExecutionId`, it can land on a **different shard** than its parent, so a naive single-shard `parent_id` walk silently misses cross-shard children. **No new `WorkflowEvent` variant, no migration, no event-JSON/tagging change, no macro `::autumn_harvest::` path change, zero replay-determinism impact** — a pure read-path slice over existing `harvest_workflow_executions` rows. **Any node is a valid root** (re-rooting mid-tree returns just the subtree below it; the chosen root is always `depth: 0` and still reports its own `parent_id`, so an operator can see they are inside a larger tree). Each node carries `execution_id`, `workflow_name`, `workflow_id`, `state`, `started_at`, `closed_at`, `parent_id`, `depth`, `shard_id`, and the **spawn relationship** — `await_mode: "awaited"` (the parent suspended on this child; not covered by the parent-close cascade) vs `"detached"` + `parent_close_policy` (`abandon`/`request_cancel`/`terminate`, issue #347) — so a `FAILED` detached child under a still-`RUNNING` parent, the classic "nobody noticed" case, is visible at a glance. **`?summary=true`** returns a per-state descendant roll-up instead of the tree: `counts` are strictly *descendant* counts (the root's own state is echoed separately on `root.state` and deliberately **excluded**, matching the AC's "per-state descendant counts" wording), and every `KNOWN_WORKFLOW_STATES` key is always present at `0` so a client can assert `.counts.failed > 0` with no presence check. **Performance — batched frontier, not per-node recursion.** The naive shape (what a `/children`-style recursive walk would do) is O(nodes × shards): for the issue's success-metric shape (depth 6, 200 executions, 8 shards) that is ~1600 queries. A recursive CTE is structurally impossible here because children can live on a different physical database. Instead the walk is **level-synchronous and batched**: one `parent_id = ANY($1)` query per shard per level, with all shards for a level dispatched concurrently via `futures::future::join_all` (mirroring `workflow_reachability`), giving **O(depth × shards)** ≈ 48 queries for the same shape. Two new `db`-gated core loaders in `store.rs` back it — `load_workflow_children_batch` (whole-frontier batch, `ORDER BY (started_at, id)`, `LIMIT` bounded by the live node budget) and `load_parents_with_children` (a cheap `SELECT DISTINCT parent_id` existence probe) — plus the new `LineageChildRow` (the existing `WorkflowChildRow` carries neither `workflow_id` nor `parent_id`); the issue explicitly sanctions "a thin `load_workflow_children`-style helper". **Bounded, and never silently.** `max_depth` (default **20**, ceiling 50) and `max_nodes` (default **1000** *including* the root, ceiling 10000) are per-request query params; an out-of-range value is rejected `400` **naming the offending parameter** rather than clamped, and the response always echoes the `limits` that actually ran. On a cut, the response sets `truncated: true` plus a machine-readable `truncation_reason` (`"max_depth"` | `"max_nodes"`) and **names the dropped subtrees' parents** in `truncated_parent_ids` so the operator can re-root the call at one of them and continue. To avoid sending operators chasing subtrees that do not exist, the named set is filtered through the bounded existence probe — only parents that *provably* have children are listed (documented residual: on a `max_nodes` cut, a parent whose children all fell beyond the per-shard fetch window is not observed, so `truncated: true` remains the authoritative incompleteness signal while `truncated_parent_ids` is the actionable, bounded subset; the list itself is capped at `TRUNCATED_PARENTS_CAP = 100` with a `truncated_parents_capped` flag). When both bounds fire, `max_nodes` wins the `truncation_reason` because it is what actually terminated the walk. **Determinism under sharding:** merged cross-shard rows are re-sorted `(started_at, exec_id)` *inside* `admit_level` **before** any budget cut, so which rows survive a truncation can never depend on shard iteration order. **Cycle/duplicate safe by construction:** a `visited: HashSet<Uuid>` seeded with the root guarantees each `execution_id` appears exactly once, so a malformed/forged `parent_id` loop (A→B→A) terminates instead of recursing forever; an over-budget row is `continue`d rather than `break`ed (so *every* dropped parent is still named) and its id removed from `visited` again. **Partial availability (issue #756):** the fan-out uses the shared `shard_fanout` scaffold (`expected_shards`, so a router-known but pool-less shard mid-rollout is reported rather than silently skipped), and an unreachable shard degrades to `200` with `status: "partial"` + the shard named in `unavailable_shards` rather than failing the whole call — a triage read must not `500` during exactly the incident it exists to diagnose. **Not admin-gated**, matching the sibling `/children` (which already traverses depth cross-shard over the same rows) and `/run-chain`; gating it while `/children` stays open would be an inconsistency, not a hardening. New pure plugin module `lineage.rs` owns the whole walker (`LineageWalk`, `LineageNode`, `LineageTreeReport`, `LineageSummaryReport`, `LineageLimits`, `TruncationReason`) as `db`-free, unit-testable logic; `api.rs` holds only the thin I/O driver. Route registered in all five parallel surfaces — the axum router, `management_api_routes()`, `management_api_response_fields()` (the **union** of both polymorphic shapes, with the polymorphism explained in `success_response.notes`, following the `POST /batch-operations` dry-run precedent), `docs/api-contract.json`, and core `autumn_harvest::audit` (`CLASSIFIED_ROUTES` `ReadOnly` / `ALL_MUTATION_ROUTES` `None` / `EXCLUDED_ROUTES`) — with pin tests in **both** `audit.rs` and plugin `contract_regression.rs`, since the audit mutual cross-check stays green if a route is dropped from both lists at once. **CLI:** `harvest workflow tree <id> [--summary] [--max-depth N] [--max-nodes N] [--json]` renders an indented tree (`└─ ` branch marker, `[detached:policy]` suffix) or the roll-up, with explicit `TRUNCATED (...)` / `PARTIAL (...)` footer blocks so neither condition can be missed in a terminal. **Runbook** `docs/runbooks/trace-execution-lineage.md` walks the summary-first triage flow, the `jq recurse` one-liner for finding a failed descendant, mid-tree re-rooting, reading truncation, and — per the AC — an explicit note that the snapshot is **per-shard assembled and may be marginally time-skewed** (no cross-shard transaction; re-run to confirm anything contradictory). Out of scope (per the issue): mutating the tree, activity-level granularity, classic-DAG node graphs, streaming, cross-shard transactional consistency, and pagination beyond the `max_nodes` cap. **Tests, TDD red→green→refactor** (RED confirmed as compile errors against the not-yet-existing API, per the #593 precedent): 7 core DB tests in `tests/integration/lineage_store_tests.rs` (batch loader returns every frontier parent's children in one query, empty-frontier short-circuit, oldest-first ordering for deterministic truncation, `await_mode`/`parent_close_policy` derivation; existence probe names only parents that actually have children, is distinct per parent, and returns empty for empty input); 23 pure no-DB unit tests in `lineage.rs` (limit parsing/ceilings, budget accounting, level admission + sort-before-cut, cycle and duplicate-edge guards, dropped-parent naming, reason precedence, probe no-op on empty, root-node shape, nesting, summary roll-up excluding the root); and 15 HTTP+DB integration tests in `autumn-harvest-plugin/tests/lineage_tree_integration.rs` — including the headline **cross-shard** test (two real databases: root + same-shard child on shard 0, a cross-shard child + grandchild on shard 1; asserts correct nesting and `shard_id == 1`), the **forged-cycle** test (A→B→A via raw `UPDATE`), the **unreachable-shard → partial** test, both truncation modes with dropped-parent naming, the exactly-at-the-cap non-truncation boundary, mid-tree re-rooting, leaf → empty `children` array, `404`/`400` cases, summary counts, and the **success-metric** test (depth 6 / 200 executions returned complete in one call). All DB/HTTP suites were **executed green against a real Postgres 16**, not merely compile-checked, and both new suites are registered in `.github/ci/integration-suites.txt` for the Docker-backed Linux CI run.

**Post-review hardening (four-angle agent review: correctness/determinism, API-contract/registries, sharding/partial-availability, test-quality/AC-coverage).** Two independent reviewers converged on the same **P1**, plus a third real defect and a tautological test; all fixed TDD red→green. **(1) `?max_nodes=1` was a silent cap.** The budget counts the root, so `is_exhausted()` is already true on the first loop iteration and the walk broke **before querying a single shard** — leaving the walk's internal `last_level_ids` mirror empty, so the existence probe was skipped, `truncated` stayed `false`, and `status` read `complete`. A root with 400 live descendants was byte-indistinguishable from a leaf, exactly the silent cap AC4 forbids. Fixed by probing the driver's **live `frontier`**, which is the authoritative unexpanded set on every exit path (empty when the tree completed naturally, the deepest admitted level on a depth exit, and `[root]` when the budget was spent before a round ran); the now-dead `unexpanded_frontier()`/`last_level_ids` mirror was deleted. **(2) An exactly-spent budget blamed the wrong bound.** A level can consume the budget precisely — no row is ever budget-rejected, so `admit_level` never sets a reason — after which `record_probe_result` unconditionally inserted `MaxDepth`. An operator (or a `truncation_reason`-keyed alert) would raise `max_depth` and see no change while `max_nodes` was the actual constraint. The reason is now chosen from the live budget (`is_exhausted() ? MaxNodes : MaxDepth`), with `get_or_insert` still preserving a verdict already set by a rejected row. **(3) `status` was arithmetic, not evidence.** `inspected = expected.len() - errors.len()` assumes every expected shard was queried, which is false on the zero-round path above; it now counts shards that **actually answered** (matching every sibling cross-shard endpoint). **(4) The `remaining + 1` fetch sentinel could be defeated.** A row dropped by the cycle/duplicate guard consumes a fetch-window slot without consuming budget, so the SQL `LIMIT` may cut rows the budget check never observes. A saturated window with no budget rejection is now reported as a `MaxNodes` truncation (`note_saturated_fetch_window`) — over-reporting sends an operator to re-root needlessly, while under-reporting is the silent cap the bounds exist to prevent. **(5) The deterministic-ordering test was tautological.** Every fixture paired uuid `id(N)` with timestamp `t(N)`, so a mutant sorting purely by `exec_id` passed the whole suite — despite that sort being the load-bearing guarantee that truncation cannot depend on shard iteration order. Fixtures are now **decorrelated** (`id(300)` at `t(10)`, `id(100)` at `t(30)`), plus an equal-timestamp case pinning the `exec_id` tiebreak; the uuid-only mutant was re-applied and **confirmed to fail**. **(6) `?summary=<garbage>` silently meant `false`** — a caller who typos the value received a full tree with a `200` and no way to notice, contradicting the same handler's own hard-`400` treatment of its numeric bounds; unrecognised values are now rejected `400`. Also: `visited.remove()` on a budget-rejected row was removed (exhaustion is monotone, so it was provably inert while remaining a latent duplicate-node hazard if that invariant is ever relaxed), and the CLI's `--max-depth`/`--max-nodes` now range-validate at parse time (matching the adjacent `workflow children` subcommand) instead of spending a round-trip on a server `400`. New coverage for the gaps the review named: budget-floor truncation and its childless control, exactly-spent-budget reason, exact-fit completeness (the guard against over-correcting into false-positive truncation), a never-queried shard, summary mode preserving `status`/`unavailable_shards` under a shard outage, a **terminal root**'s own `closed_at`/identity, all three `parent_close_policy` spellings, the saturated-fetch-window verdict, decorrelated ordering, and a depth-2 CLI indent fixture (the previous 2-level fixture let a constant-indent mutation survive). The plugin HTTP/DB suite grew 15 → 22 tests and the pure walker suite 23 → 26, all executed green against a real Postgres 16 alongside the full local CI mirror (fmt, per-crate clippy `-D warnings` incl. the `webhooks`/`mcp,unified-dag-execution`/`metrics` plugin feature combos, MSRV `cargo +1.88.0 check --workspace`, and the 1071-test no-DB integration suite).


**Post-review hardening, round 2 (Codex automated review, P2): the root lookup must not fall back to the default shard.** The descendant fan-out enumerates shards through `shard_fanout::expected_shards` and honestly reports a router-known-but-pool-less shard as `unavailable`, but the **root** lookup routed through `db_conn_for_execution` → `ShardedDbPool::pool_for_execution` → `pool_for`, whose documented contract is to **fall back to the default shard** when the requested shard has no entry (`shard.rs`: `.get(&shard).or_else(|| .get(&default_shard))`). So for a root whose `ExecutionId` encodes a shard this node has no pool for — the normal state at step 2 of the documented shard-add rollout, where `readable_shards` is widened *before* the pool is provisioned — the lookup silently queried the **wrong database**, found nothing, and answered a confident `404 "workflow execution … not found"` for a run that may well exist on its own shard. Two harms: a `404` reads as authoritative ("no such run") where existence is genuinely *undetermined* and a `503` is retryable, which is precisely the false-negative the sibling business-id resolver (#805) already fails closed against ("fail closed with 503 rather than risk a false 404"); and it made a **single response self-contradictory** — the same shard reported `unavailable` for descendants while implied "does not exist" for the root. Fixed with a new `db_conn_for_execution_exact` helper that resolves the owning shard through `ShardedDbPool::exact_pool_for_execution` (no fallback; the `ShardId::UNENCODED` sentinel still maps to the default shard, so pre-sharding rows and tests are unaffected) and, when there is no pool, decides the answer from **`shard_fanout::expected_shards`** — the *same* helper the fan-out uses, so the root check and the descendant walk can never disagree about which shards this deployment claims: a shard the deployment knows about → `503` naming it, a shard neither the pools nor the router know about → `Ok(None)` so the caller keeps its honest `404` (an operator pasting a wrong UUID decodes to an arbitrary shard number, and turning that into a confusing `503` would have been an over-correction). **Scope deliberately limited to this route**: the lenient `db_conn_for_execution` is left in place for the ~40 other single-execution routes, since switching them all is a behaviour change across the whole management API and belongs in its own slice — the helper is written and documented to be adoptable there later. **No new `WorkflowEvent` variant, no migration, no route/contract change** (the `503` is a status, not a new response field). Tests, TDD red→green (RED confirmed as the literal `404 "workflow execution … not found"` body): `a_root_on_a_router_known_shard_with_no_pool_is_503_not_a_false_404` (router knows shards 0+1, pools hold only 0, root id encodes shard 1 → `503` naming the shard) and its mandatory over-correction guard `a_root_on_a_shard_this_deployment_does_not_know_is_still_404` (shard 7 known to neither → stays `404`). Runbook `docs/runbooks/trace-execution-lineage.md` §6 gains a "`503` means *cannot tell*, not *not found*" bullet. Plugin HTTP/DB suite 22 → 24 tests, executed green against a real Postgres 16.

**Post-review hardening, round 3 (Codex automated review of `7f09e3d`, two P2s — both docs).** (1) **The runbook's `jq` triage one-liner was broken.** It read `[.root] | [recurse(.children[]?)] | .[] | select(...)`, which wraps the root in an array *before* recursing — and an array has no `children` field, so the walk never descends. Verified empirically against a realistic response fixture on jq 1.7: it is not merely an empty result but a hard **error**, `Cannot index array with string "children"` (exit 5), because the `?` binds to the `[]` iteration rather than to the `.children` index and so cannot suppress it. An operator copy-pasting the command mid-incident would get a jq error instead of the failed descendant's id — the single most likely command in the whole runbook to be used under pressure. Corrected to `.root | recurse(.children[]?) | select(.state=="FAILED") | .execution_id`, which is also simpler (no array round-trip), and re-tested by extracting the one-liner *verbatim from the committed doc* and running it against the fixture. (2) **The `503` introduced by round 2 was undocumented in the route contract.** `docs/api-contract.json` listed only `400`/`404`/`500` for `GET /workflows/{id}/tree`, so a contract-driven consumer would treat the new transient status as an unexpected failure exactly during a shard-add rollout. Added a `503` entry (33 other routes already document one, so this follows established form) spelling out both triggers — a router-known owning shard with no configured pool, and a pool whose connection cannot be acquired — plus *why* it is deliberately not a `404`, and the distinction that matters for a reader: the `503` applies only to the **root** lookup, whereas an unreachable shard hit during the **descendant** walk degrades to `200` with `status: "partial"`. The `404` description was extended in the same pass to cover round 2's other branch (an id encoding a shard neither the pools nor the router know about). Docs only — no code change, no new `WorkflowEvent` variant, no migration.

**Post-review hardening, round 4 (Codex automated review of `8f3f72c`, P2): retention-summarised lineage was silently dropped.** With tiered summary retention (issue #752, opt-in) enabled, a **terminal child is independently retention-eligible**: it can be demoted into `harvest_execution_summaries` and have its `harvest_workflow_executions` row collected while its long-running parent is still live. `load_workflow_children_batch` reads only the executions table, so that child — and everything beneath it — vanished from the tree while the response still reported `truncated: false`, `status: "complete"`, and (in summary mode) `counts.failed == 0`. A `FAILED` demoted child was therefore indistinguishable from no failure at all: precisely the silent-omission class this feature's own AC4 ("never a silent cap") exists to reject, and the one an operator is least able to detect. Retention deliberately preserves `harvest_execution_summaries.parent_id` for exactly this case (it skips the terminal-child `parent_id` null-out when summary retention is on), and `erase::collect_child_ids` already unions both tables on it for the #495 cascade — so the data was present and the traversal precedent already existed; only the read side ignored it. **Fix — surface the omission (the reviewer's second option), deliberately not the union.** New core probe `store::load_parents_with_summary_children` (a `SELECT DISTINCT parent_id` against the summaries table, structurally the twin of the existing `load_parents_with_children`) runs once per shard after the walk against **every admitted id** — not just the unexpanded frontier, since a demoted child can hang off any node in the tree — and its result is reported in a new additive response field `retained_summary_parent_ids` on **both** the tree and `?summary=true` shapes, naming the nearest *live* ancestor of each omitted subtree. It fails soft exactly like every other per-shard read (folded into a `ShardObservation`, so a shard predating the summaries migration degrades the report rather than 500ing), and returns nothing on the default configuration where the table is empty. **Why not union the summary rows into the tree** (the reviewer's first option, which would let an operator actually *see* the demoted child): a summary row carries no `parent_close_policy`, and `await_mode` is derived solely from it — so a summary-derived node's spawn relationship is genuinely unknowable, and unioning would make AC2's "every node carries the spawn relationship" nullable for some nodes. That is a documented per-node contract change plus a second data source inside a core `store.rs` loader; it was escalated to the maintainer rather than taken unilaterally, and this additive signal does not foreclose it. Documented as a **third, independent incompleteness signal**: `truncated == false` and `status == "complete"` together no longer imply every descendant is present. The runbook §6 gains a bullet covering both retention modes (summary-retention omissions are named and readable via `GET /workflows/summaries`; hard-deleted descendants under the default config leave no trace the tree could report), and the contract's `success_response.notes` says the same for API consumers. **No new `WorkflowEvent` variant, no migration, no change to any existing field's meaning.** Tests, TDD red→green (RED verified by disabling only the probe call and re-running): four new HTTP+DB tests — a demoted `FAILED` child under a live root is named while the live sibling still nests normally, a summarised child of an *interior* node is caught (proving the probe covers all admitted ids, not just the frontier), the roll-up carries the same signal so a `--summary` triage pass cannot read `failed: 0` as authoritative, and a no-summaries control confirms the signal stays empty on the default configuration. Plugin HTTP/DB suite 24 → 28 tests, executed green against a real Postgres 16.

**Post-review hardening, round 5 (Codex automated review of `be3ca4b`, two P2s — both regressions introduced by round 4's own fix).** (1) **The CLI silently discarded the new incompleteness signal.** Round 4 added `retained_summary_parent_ids` to the API but never wired it into `format_lineage_footer`, which both default renderers (`harvest workflow tree` and `--summary`) call — so the footer printed only the `TRUNCATED` and `PARTIAL` blocks. Because a retention omission can fire on a tree that is otherwise entirely clean (`truncated: false`, `status: "complete"`, `counts.failed == 0`), the terminal showed an apparently-healthy family that was missing a failed descendant — the exact silent omission round 4 existed to close, reintroduced one layer up, and specifically in the `--summary` roll-up the runbook names as the *first* triage step. Fixed by rendering a third `RETENTION` block, deliberately worded as an omission rather than a truncation (re-rooting there would not surface the rows — they are no longer in `harvest_workflow_executions` at all) and naming `harvest workflow summaries` as the command that reads them. Both renderers share the one footer, so the fix covers both. (2) **The probe inspected nodes that were not in the returned tree.** `admitted_ids()` sourced its id set from `visited`, but `admit_level` inserts an id there *before* the budget check and — by deliberate design, as a duplicate-guard hardening from the first review round — **leaves a budget-rejected id in place**. `visited` is therefore a strict superset of the response. If a node dropped by `max_nodes` had a demoted summary child, its id was emitted in `retained_summary_parent_ids`, violating the field's own documented contract ("names nodes **in the returned tree**") and handing the operator an id they could not find in the output. Fixed by taking the reviewer's first suggestion — build the list from the root plus the actually-admitted `nodes`, i.e. exactly what `finish` assembles into the response — via a new `root_id` field on `LineageWalk`; `visited` keeps its cycle/duplicate-guard role and its doc comment now states that it must not be used to enumerate the response's nodes. A dropped subtree remains reported through `truncated_parent_ids`, which is the correct channel for it. **No new `WorkflowEvent` variant, no migration, no contract change** (the fix makes the implementation match the contract text that was already published). Tests, TDD red→green (RED confirmed for all three before either fix): pure `admitted_ids_excludes_budget_rejected_rows` (walker), `lineage_tree_render_calls_out_retention_collected_descendants` + `lineage_summary_render_calls_out_retention_collected_descendants` + the cry-wolf control `lineage_render_stays_quiet_when_nothing_was_retention_collected` (CLI), and the end-to-end `a_budget_dropped_node_is_never_named_as_a_retention_summary_parent` (HTTP+DB — a `max_nodes`-dropped node that owns a demoted child must not be named). Plugin HTTP/DB suite 28 → 29, walker suite 26 → 27, executed green against a real Postgres 16.
