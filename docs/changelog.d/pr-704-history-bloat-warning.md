## Phase 3.x — Operator early-warning for workflow history bloat near the cap (issue #704)

**Implemented.** Before this, the only signal that a still-running workflow's recorded event history was approaching its optional `event_hard_cap` (`WorkflowHistoryPolicy`) was the hard cap itself — the run would eventually reach it, terminally force-fail, and land in the DLQ, with zero prior warning. This ships two complementary, purely additive surfaces: a discovery filter to *find* offending live executions on demand, and a counter that *pages* the moment one crosses a configurable soft fraction of the cap. **No new `WorkflowEvent` variant, one additive nullable-column migration, no shard-routing change, no replay-determinism impact** — this is a read-path discovery filter plus a post-commit telemetry emission over already-recorded state.

**Discovery filter (AC1/AC2/AC6/AC7).** `GET /api/harvest/workflows?min_history_events=<N>` restricts the response to **live (non-terminal)** executions whose current recorded `harvest_events` count is `>= N`, fanned out across every shard via the existing `observe_shards`/`iter_shards()` scaffold and globally sorted by history size descending (`build_history_bloat_fanout`: a pure, unit-tested merge that concatenates every shard's *unbounded* per-shard result set — no per-shard `ORDER BY`/`LIMIT` — sorts once at the merge stage, then truncates to `limit`, so the global top-K-across-shards ordering is correct by construction). Each row carries its current `history_event_count` (AC2) so an operator can rank/triage without a second call. `min_history_events` composes with the existing `state=`/`order=` filters as its own dedicated discovery path; it rejects composition with `cursor`/`page_size`/`order` pagination with `400` (the computed sort has no keyset cursor, so silently mis-ordering or ignoring the request would be worse than a clear rejection), and rejects a non-numeric or negative value with `400` and a JSON error body (AC7) — never a `500`, never a silent empty match. `0` is a well-defined boundary (matches every live execution, not a "disabled" sentinel). The "live (non-terminal)" filter derives from `erase::TERMINAL_STATES` — the engine's existing single source of truth for terminal-state classification — rather than a second hand-maintained literal, so it can never silently drift from the states `is_terminal_state`/`resolve_execution_id_by_workflow_id` (issue #805) already recognize as terminal. Registered in `docs/api-contract.json` (AC6) and exposed via `harvest workflow list --min-history-events <N>` (`autumn-harvest-cli`), with `contract_coverage`/`request_mapping` test coverage.

**Soft-threshold counter (AC3/AC4).** `harvest.workflow.history_bloat` (`METRIC_WORKFLOW_HISTORY_BLOAT`, bridged in `metrics_rs_adapter.rs`) fires **exactly once** per still-`RUNNING` execution the moment its recorded history first crosses `history_bloat_warn_fraction * event_hard_cap` — labeled by `workflow` (the registered `#[workflow]` type name) only, per ADR-0001 §7's cardinality rule (`execution.id` is never a label). The soft fraction is configurable via `HarvestBuilder::history_bloat_warn_fraction` / `WorkflowHistoryPolicy::with_history_bloat_warn_fraction` (clamped `[0.0, 1.0]`, default `DEFAULT_HISTORY_BLOAT_WARN_FRACTION = 0.75`); `0.0` (or an unconfigured `event_hard_cap`) is a documented, test-covered no-op (AC4). The pure decision function `history_bloat_threshold_crossed(current_history_event_count, cap, fraction, already_warned) -> bool` performs the inclusive `>=` comparison with truncating cast (`(cap as f64 * fraction) as u64`) and is unit-tested at the exact boundary plus zero-cap/negative-fraction/fraction-1.0 edge cases. Persistence follows the codebase's established "compute pure decision before the transaction, act only in the post-commit `Persisted` arm" discipline (the same pattern `harvest.update.completed`/`failed`/`harvest.signal.unhandled`, issue #684, already use): `should_warn_history_bloat` is computed at the top of `process_workflow_task` — gated on `!is_canary` (issue #796's synthetic liveness probe contributes to no `harvest.workflow.*` business signal, mirroring the sibling `record_workflow_completed`/`history_size`/`continue_as_new` gates) and `matches!(&outcome, WorkflowOutcome::Suspended { .. })` — and only marked/emitted after a successful commit, so a paused-park discard, an ND-block (#603), or a persist failure can never mark an execution "warned" for a decision cycle that never became durable. The exactly-once guarantee is enforced by a single guarded `UPDATE harvest_workflow_executions SET history_bloat_warned_at = NOW() WHERE id = $1 AND history_bloat_warned_at IS NULL` (`store::mark_history_bloat_warned`, returning whether *this* call performed the transition) against a new nullable `history_bloat_warned_at TIMESTAMPTZ` column (migration `20260716000000_harvest_workflow_history_bloat_warn`; deliberately unindexed — it is read/written only by exact-row PK operations, never filtered in a `WHERE`) — race-safe by construction (a single atomic statement, not select-then-update), and correctly reset-to-`NULL`-by-default for continue-as-new successors and reset forks (each is a fresh row tracking its own history from zero).

**Alerting/dashboards/docs (AC5).** A starter alert `harvest_workflow_history_bloat` was added to `docs/alerts/starter-pack-v0.1.0.json` (ticket severity, `sum by (workflow) (increase(harvest_workflow_history_bloat_total[15m])) > 0` — alerting on any increase within the window rather than a sustained rate, since this is a per-run crossing event, not a rate signal) with a `first_action` pointing at `harvest workflow list --min-history-events <threshold>` and a full runbook stanza at `docs/runbooks/harvest-alerts.md#harvest_workflow_history_bloat`. Dashboard panel, ADR-0001 §7 catalogue row, and `docs/telemetry.md` entries were added and are enforced by the existing anti-drift tests (`dashboard_pack_docs.rs`, `alert_pack_docs.rs`) so the metric/alert/panel triad cannot silently drift apart.

**Success metric.** Operator MTTD for a runaway-history workflow drops from "never, until the hard cap force-fails it to the DLQ" to the soft-threshold crossing instant — bounded below one poll/telemetry-flush interval, well under the issue's <1 minute target — since the counter fires the moment the crossing is durably committed.

**Out of scope (per issue, unchanged):** the existing hard-cap terminal-fail/DLQ behavior; auto-`continue_as_new`; per-execution gauges (would be unbounded label cardinality); retroactively emitting history-size for already-terminal runs. The per-shard discovery query's unbounded row-scan cost (no `LIMIT` until the merge stage) is a pre-existing, accepted pattern already shared with the sibling `load_stalled_workflows` endpoint — not a novel risk this feature introduces — and fixing it would require a larger SQL restructure (a per-shard `ORDER BY` + `LIMIT`) that risks the just-verified top-K-across-shards correctness; left as a documented, accepted characteristic rather than addressed here.

**Tests, TDD red→green→refactor, then multi-angle review (replay-determinism, AC-completeness, cardinality/security, shard-fanout correctness, docs/usability) with all findings closed.** Pure unit tests for `history_bloat_threshold_crossed` (worker.rs, 6 cases incl. the exact-threshold boundary, disabled fraction, negative fraction, zero cap) and `build_history_bloat_fanout` (api.rs, merge/sort/truncate). DB integration in `autumn-harvest/tests/integration/metrics_integration.rs`: `history_bloat_counter_fires_once_when_a_still_suspended_execution_crosses_the_soft_threshold` (real worker + Postgres transaction, cap=8/fraction=0.5 exact-threshold crossing, plus a direct second `mark_history_bloat_warned` call proving the SQL guard is race-safe), `history_bloat_counter_never_fires_when_the_soft_threshold_is_disabled` (AC4, end-to-end through the real registry/worker path), and — added during the review pass to close the one real coverage gap the review surfaced — `history_bloat_counter_fires_exactly_once_across_two_real_live_suspension_cycles`: a dedicated probe workflow that suspends on a short (1s), genuinely-firing timer, is woken for a real *second* live decision cycle by the worker's own timeout scanner, and re-suspends on a long timer; the test polls for a durable `TimerStarted("history-bloat-second-suspension")` event to prove cycle 2 actually ran, then asserts the counter recorder shows **zero** new emissions after that cycle — a stronger, genuinely end-to-end proof than the sibling test's direct second function call. HTTP integration in `autumn-harvest-plugin/tests/history_bloat_integration.rs` (8 tests): sorted-descending + `history_event_count` presence (AC1/AC2), full terminal-state exclusion across all six `erase::TERMINAL_STATES` values including `CONTINUED_AS_NEW`, non-numeric/negative `400` rejection (AC7), pagination-combo `400` rejection, a `min_history_events=0` boundary test, and — the other genuine review-surfaced gap — `min_history_events_merges_and_sorts_globally_across_shards`: a real **two-Postgres-database** test (mirroring `workflow_filter_integration.rs`'s `setup_sharded_databases`/`build_two_shard_pool` pattern) seeding above/below-threshold rows on both shards plus a large terminal row, proving the HTTP path performs a genuine global sort across shards rather than concatenating each shard's already-sorted page. All DB/HTTP suites were executed green against real Postgres 16 (not merely compile-checked), registered in `.github/ci/integration-suites.txt` for the Docker-backed Linux CI run, and the full workspace quality gate (fmt, clippy `-D warnings` on all three touched crates, the full no-DB core suite, plugin lib suite, and CLI suite) was re-verified green after the review-fix batch.
