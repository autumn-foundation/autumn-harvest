## Phase 3.x — Operator early-warning for workflow history bloat near the cap (issue #704)

**Implemented.** Before this, the only signal that a still-running workflow's recorded event history was approaching its optional `event_hard_cap` (`WorkflowHistoryPolicy`) was the hard cap itself — the run would eventually reach it, terminally force-fail, and land in the DLQ, with zero prior warning. This ships two complementary, purely additive surfaces: a discovery filter to *find* offending live executions on demand, and a counter that *pages* the moment one crosses a configurable soft fraction of the cap. **No new `WorkflowEvent` variant, one additive nullable-column migration, no shard-routing change, no replay-determinism impact** — this is a read-path discovery filter plus a post-commit telemetry emission over already-recorded state.

**Discovery filter (AC1/AC2/AC6/AC7).** `GET /api/harvest/workflows?history_bloat_min_events=<N>` restricts the response to **live (non-terminal)** executions whose current recorded `harvest_events` count is `>= N`, fanned out across every shard via the existing `observe_shards`/`iter_shards()` scaffold and globally sorted by history size descending (`build_history_bloat_fanout`: a pure, unit-tested merge that concatenates every shard's *unbounded* per-shard result set — no per-shard `ORDER BY`/`LIMIT` — sorts once at the merge stage, then truncates to `limit`, so the global top-K-across-shards ordering is correct by construction). Each row carries its current `history_event_count` (AC2) so an operator can rank/triage without a second call. `history_bloat_min_events` is its own dedicated discovery path — it rejects composition with `cursor`/`page_size`/`order` pagination with `400` (the computed sort has no keyset cursor, so silently mis-ordering or ignoring the request would be worse than a clear rejection), and rejects a non-numeric or negative value with `400` and a JSON error body (AC7) — never a `500`, never a silent empty match. `0` is a well-defined boundary (matches every live execution, not a "disabled" sentinel). The "live (non-terminal)" filter derives from `erase::TERMINAL_STATES` — the engine's existing single source of truth for terminal-state classification — rather than a second hand-maintained literal, so it can never silently drift from the states `is_terminal_state`/`resolve_execution_id_by_workflow_id` (issue #805) already recognize as terminal. Registered in `docs/api-contract.json` (AC6) and exposed via `harvest workflow list --history-bloat-min-events <N>` (`autumn-harvest-cli`), with `contract_coverage`/`request_mapping` test coverage. **`history_bloat_min_events` is a deliberately distinct query parameter from the pre-existing, general-purpose `min_history_events` filter (issue #493)** — see "Post-review hardening" below for why the two must never share a name.

**Soft-threshold counter (AC3/AC4).** `harvest.workflow.history_bloat` (`METRIC_WORKFLOW_HISTORY_BLOAT`, bridged in `metrics_rs_adapter.rs`) fires **exactly once** per still-`RUNNING` execution the moment its recorded history first crosses `history_bloat_warn_fraction * event_hard_cap` — labeled by `workflow` (the registered `#[workflow]` type name) only, per ADR-0001 §7's cardinality rule (`execution.id` is never a label). The soft fraction is configurable via `HarvestBuilder::history_bloat_warn_fraction` / `WorkflowHistoryPolicy::with_history_bloat_warn_fraction` (clamped `[0.0, 1.0]`, default `DEFAULT_HISTORY_BLOAT_WARN_FRACTION = 0.75`); `0.0` (or an unconfigured `event_hard_cap`) is a documented, test-covered no-op (AC4). The pure decision function `history_bloat_threshold_crossed(current_history_event_count, cap, fraction, already_warned) -> bool` performs the inclusive `>=` comparison with truncating cast (`(cap as f64 * fraction) as u64`) and is unit-tested at the exact boundary plus zero-cap/negative-fraction/fraction-1.0 edge cases. Persistence follows the codebase's established "compute pure decision before the transaction, act only in the post-commit `Persisted` arm" discipline (the same pattern `harvest.update.completed`/`failed`/`harvest.signal.unhandled`, issue #684, already use): `should_warn_history_bloat` is computed at the top of `process_workflow_task` — gated on `!is_canary` (issue #796's synthetic liveness probe contributes to no `harvest.workflow.*` business signal, mirroring the sibling `record_workflow_completed`/`history_size`/`continue_as_new` gates) and `matches!(&outcome, WorkflowOutcome::Suspended { .. })` — and only marked/emitted after a successful commit, so a paused-park discard, an ND-block (#603), or a persist failure can never mark an execution "warned" for a decision cycle that never became durable. The exactly-once guarantee is enforced by a single guarded `UPDATE harvest_workflow_executions SET history_bloat_warned_at = NOW() WHERE id = $1 AND history_bloat_warned_at IS NULL` (`store::mark_history_bloat_warned`, returning whether *this* call performed the transition) against a new nullable `history_bloat_warned_at TIMESTAMPTZ` column (migration `20260716000000_harvest_workflow_history_bloat_warn`; deliberately unindexed — it is read/written only by exact-row PK operations, never filtered in a `WHERE`) — race-safe by construction (a single atomic statement, not select-then-update), and correctly reset-to-`NULL`-by-default for continue-as-new successors and reset forks (each is a fresh row tracking its own history from zero).

**Alerting/dashboards/docs (AC5).** A starter alert `harvest_workflow_history_bloat` was added to `docs/alerts/starter-pack-v0.1.0.json` (ticket severity, `sum by (workflow) (increase(harvest_workflow_history_bloat_total[15m])) > 0` — alerting on any increase within the window rather than a sustained rate, since this is a per-run crossing event, not a rate signal) with a `first_action` pointing at `harvest workflow list --history-bloat-min-events <threshold>` and a full runbook stanza at `docs/runbooks/harvest-alerts.md#harvest_workflow_history_bloat`. Dashboard panel, ADR-0001 §7 catalogue row, and `docs/telemetry.md` entries were added and are enforced by the existing anti-drift tests (`dashboard_pack_docs.rs`, `alert_pack_docs.rs`) so the metric/alert/panel triad cannot silently drift apart.

**Success metric.** Operator MTTD for a runaway-history workflow drops from "never, until the hard cap force-fails it to the DLQ" to the soft-threshold crossing instant — bounded below one poll/telemetry-flush interval, well under the issue's <1 minute target — since the counter fires the moment the crossing is durably committed.

**Out of scope (per issue, unchanged):** the existing hard-cap terminal-fail/DLQ behavior; auto-`continue_as_new`; per-execution gauges (would be unbounded label cardinality); retroactively emitting history-size for already-terminal runs. The per-shard discovery query's unbounded row-scan cost (no `LIMIT` until the merge stage) is a pre-existing, accepted pattern already shared with the sibling `load_stalled_workflows` endpoint — not a novel risk this feature introduces — and fixing it would require a larger SQL restructure (a per-shard `ORDER BY` + `LIMIT`) that risks the just-verified top-K-across-shards correctness; left as a documented, accepted characteristic rather than addressed here.

**Tests, TDD red→green→refactor, then multi-angle review (replay-determinism, AC-completeness, cardinality/security, shard-fanout correctness, docs/usability) with all findings closed.** Pure unit tests for `history_bloat_threshold_crossed` (worker.rs, 6 cases incl. the exact-threshold boundary, disabled fraction, negative fraction, zero cap) and `build_history_bloat_fanout` (api.rs, merge/sort/truncate). DB integration in `autumn-harvest/tests/integration/metrics_integration.rs`: `history_bloat_counter_fires_once_when_a_still_suspended_execution_crosses_the_soft_threshold` (real worker + Postgres transaction, cap=8/fraction=0.5 exact-threshold crossing, plus a direct second `mark_history_bloat_warned` call proving the SQL guard is race-safe), `history_bloat_counter_never_fires_when_the_soft_threshold_is_disabled` (AC4, end-to-end through the real registry/worker path), and — added during the review pass to close the one real coverage gap the review surfaced — `history_bloat_counter_fires_exactly_once_across_two_real_live_suspension_cycles`: a dedicated probe workflow that suspends on a short (1s), genuinely-firing timer, is woken for a real *second* live decision cycle by the worker's own timeout scanner, and re-suspends on a long timer; the test polls for a durable `TimerStarted("history-bloat-second-suspension")` event to prove cycle 2 actually ran, then asserts the counter recorder shows **zero** new emissions after that cycle — a stronger, genuinely end-to-end proof than the sibling test's direct second function call. HTTP integration in `autumn-harvest-plugin/tests/history_bloat_integration.rs` (8 tests, since renamed to `history_bloat_min_events_*` — see "Post-review hardening" below): sorted-descending + `history_event_count` presence (AC1/AC2), full terminal-state exclusion across all six `erase::TERMINAL_STATES` values including `CONTINUED_AS_NEW`, non-numeric/negative `400` rejection (AC7), pagination-combo `400` rejection, a `history_bloat_min_events=0` boundary test, and — the other genuine review-surfaced gap — `history_bloat_min_events_merges_and_sorts_globally_across_shards`: a real **two-Postgres-database** test (mirroring `workflow_filter_integration.rs`'s `setup_sharded_databases`/`build_two_shard_pool` pattern) seeding above/below-threshold rows on both shards plus a large terminal row, proving the HTTP path performs a genuine global sort across shards rather than concatenating each shard's already-sorted page. All DB/HTTP suites were executed green against real Postgres 16 (not merely compile-checked), registered in `.github/ci/integration-suites.txt` for the Docker-backed Linux CI run, and the full workspace quality gate (fmt, clippy `-D warnings` on all three touched crates, the full no-DB core suite, plugin lib suite, and CLI suite) was re-verified green after the review-fix batch.

**Post-review hardening (PR #1139 review, two findings, both fixed).** **P1 — query-parameter name collision (correctness/regression).** The initial cut triggered the discovery path above on the existing, shipped, general-purpose `min_history_events` filter (issue #493, landed independently before this PR) — silently breaking every caller who combined `min_history_events` with `state=`, `order=`, or cursor pagination, since the new dedicated path forces "live (non-terminal) only, sorted by size, no pagination" onto a parameter that previously composed freely. This is the same "semantic merge conflict" failure class this repo has hit before: no line-level `git` conflict exists (the two features were developed independently and never touch the same lines), so only careful review caught it. Fixed by renaming the AC1 discovery trigger to a new, dedicated query parameter, `history_bloat_min_events` — `min_history_events` (issue #493) is restored to its original, unmodified, freely-composable behavior across every call site: `WorkflowFilters` gains a distinct `history_bloat_min_events: Option<u64>` field alongside the untouched `min_history_events: Option<u64>`; the query-string parser gains a new `"history_bloat_min_events"` match arm (the pre-existing `"min_history_events"` arm and its two downstream consumers in `load_workflows`/`load_stalled_workflows` are byte-for-byte unchanged); `list_workflows`'s routing branch now checks `filters.history_bloat_min_events.is_some()`; and the CLI, `docs/api-contract.json`, both starter-pack JSON files, `docs/telemetry.md`, and `docs/runbooks/harvest-alerts.md` were all updated to the new name (`harvest workflow list --history-bloat-min-events <N>` / `?history_bloat_min_events=<N>`). Regression-proofed with three new HTTP integration tests exercising the *restored* `min_history_events` (#493) behavior directly: `min_history_events_composes_with_state_including_terminal` (the exact composition the collision broke — `?state=COMPLETED&min_history_events=N` must return a matching **terminal** row, which the AC1 dedicated path would always exclude), `min_history_events_composes_with_page_size_pagination`, and `min_history_events_composes_with_order_pagination` (both proving `min_history_events` + pagination returns `200` with the paginated object shape, not the `400` `history_bloat_min_events` deliberately produces for the same combination). **P2 — a `history_bloat_warn_fraction` of exactly `1.0` silently disables the counter.** The public builder API (`with_history_bloat_warn_fraction`) accepted the full `[0.0, 1.0]` range, but `process_workflow_task`'s unconditional hard-cap force-fail check runs *before* the warn-fraction crossing calculation and short-circuits with an early return whenever `current_history_event_count >= cap` — the exact condition a fraction of `1.0` requires to cross. So `harvest.workflow.history_bloat` could never fire for a `1.0`-configured workflow, silently contradicting the documented "only `0.0` disables it" contract. Fixed by clamping the public config surface's upper bound below `1.0` rather than reordering `worker.rs`'s hard-cap/soft-warn control flow (the two live in separate code paths — the hard-cap teardown and the post-commit warn-emit — and reordering them was judged more invasive than tightening the input range): new `MAX_HISTORY_BLOAT_WARN_FRACTION: f64 = 0.999` constant in `context.rs`; `with_history_bloat_warn_fraction` now clamps to `[0.0, MAX_HISTORY_BLOAT_WARN_FRACTION]` (was `[0.0, 1.0]`). This is a deliberate divergence from the sibling `DEFAULT_CONTINUE_AS_NEW_DEADLINE_FRACTION` knob (issue #772), which safely clamps to the full `[0.0, 1.0]` because it has no competing hard-cap early-return race — the two mechanisms are structurally different and the divergence is intentional, not an inconsistency. Existing unit tests in `context.rs`/`builder.rs` asserting the old "clamps to `1.0`" behavior were updated to assert clamping below `1.0`, plus a new explicit `1.0`-input case pinning the fix. No `WorkflowEvent` variant, no migration, no route/contract change from either fix — the P1 fix is a query-parameter rename plus doc updates, and the P2 fix is a config-surface input-range tightening.

**Post-review hardening (PR #1139 review, second pass, four findings, all fixed).** **Finding #1 (P1) — the soft-threshold warning never fired on the hard-cap terminal-fail path.** `should_warn_history_bloat` was computed and emitted only inside the `Persisted` arm for a still-`Suspended` outcome, but every one of `process_workflow_task`'s six `fail_workflow_for_history_cap` early-return sites (local-activity-inline, external-signal-inline, mixed-batch, and the primary suspension check) short-circuits *before* that arm whenever `current_history_event_count >= cap` — precisely the scenario a soft-threshold crossing exists to warn about *before* it happens, and by construction the fraction is always `< event_hard_cap` (the P2 clamp above guarantees `fraction <= MAX_HISTORY_BLOAT_WARN_FRACTION < 1.0`), so a decision that reaches the hard cap has *always already* crossed the soft threshold in the same instant — meaning the counter silently never fired for the single most important case: a workflow whose history bloat is severe enough to trip the hard cap in one decision, rather than being caught earlier while still healthy. Fixed by extracting the mark+emit logic (previously inline in the `Persisted` arm only) into a new shared helper, `emit_history_bloat_warning_if_crossed`, called from **both** the `Persisted` arm and the new choke point inside `fail_workflow_for_history_cap` itself (which every one of the six call sites already funnels through) — so the two call shapes can never independently drift. `fail_workflow_for_history_cap` gained a `registry: &HandlerRegistry` parameter (threaded through all six call sites) to resolve `history_bloat_warn_fraction`; the mark+emit runs *before* the terminal DLQ transition, gated on `!is_canary_workflow(...)` (mirroring the sibling `Suspended` gate) and the same pure `history_bloat_threshold_crossed` decision function, so a canary probe is still excluded and the guard column is still exactly-once. **Finding #2 (P1) — the mark-then-emit ordering was not crash-recoverable.** The original ordering called `store::mark_history_bloat_warned` *before* emitting the counter; a worker crash in the narrow window between the two would leave the guard column stamped `NOT NULL` with the counter never actually emitted — a *permanent, silent* loss of the signal, since the guard column exists precisely to make the crossing a one-shot event with no future retry to fall back on (unlike this codebase's other best-effort telemetry emissions — `run_deferred_schedule_counter`, `emit_update_result_metrics`, `emit_unhandled_signal_metrics` — which recur and self-heal on a later cycle). Fixed by reversing the order inside the new shared helper: **emit the counter first, mark the guard column second**. A crash in the window between the two now leaves `history_bloat_warned_at` `NULL`, so a future retry of the same decision cycle (this codebase's existing crash-recovery mechanism — no new machinery introduced) re-detects the still-unmarked crossing and re-emits, rather than the mark permanently silencing a signal that was never delivered. This is a deliberate, documented divergence from the mark-then-emit convention used elsewhere in this codebase: it trades a rare crash-window duplicate emission (an accepted cost for a best-effort early-*warning* signal, not a durable audit record) for eliminating a permanent-loss failure mode that is uniquely severe for a one-shot, non-recurring gate. `docs/telemetry.md`, `docs/runbooks/harvest-alerts.md`, and `docs/alerts/starter-pack-v0.1.0.json` were all updated to describe the corrected at-least-once (not exactly-once) delivery semantics and the new dual emission sites, including runbook guidance that a lone duplicate-looking page for an already-warned execution is the benign crash-retry case, not evidence of a second distinct crossing. **Finding #3 (P2) — `failure_cause` was silently ignored by the history-bloat discovery loader.** `list_workflows` parses and applies `failure_cause` on the general-purpose `load_workflows`/`load_stalled_workflows` paths, but the dedicated `load_history_bloat_workflows` loader never consulted it at all — so `?history_bloat_min_events=N&failure_cause=non_determinism` silently ignored the second filter and returned every above-threshold row regardless of its recorded cause, rather than narrowing to the ones the caller actually asked for. Fixed by applying the identical `search_attrs @> {"failure_cause": <cause>}` JSONB-containment predicate (`sql::<Bool>("search_attrs @> ").bind::<Jsonb, _>(...)`) inside `load_history_bloat_workflows`, immediately after the shared `apply_search_attr_filters` call. **Finding #4 (P2) — `no_progress_minutes` and `history_bloat_min_events` silently let one filter win when combined.** These are two separate, mutually-exclusive discovery paths (stalled-workflow discovery, issue #486, vs. history-bloat discovery, this issue) that each sort by a *different* computed value the other loader neither computes nor honors — `list_workflows` checked them in sequence with no interaction guard, so combining both params in one request silently dropped whichever filter's branch ran second rather than telling the caller. Fixed by rejecting the combination up front with a clear `400` (`AutumnError::bad_request_msg`), mirroring the existing `history_bloat_min_events` + pagination precedent, so a caller who accidentally combines the two discovery paths gets an explicit error instead of a silently mis-filtered page (AC7's "never a silent, mis-filtered page" contract). Regression-proofed with five new tests: `history_bloat_counter_fires_even_when_the_same_decision_reaches_the_hard_cap` (`metrics_integration.rs`, finding #1 — a real worker + Postgres transaction where `event_hard_cap=4`/`fraction=0.5` makes the SAME decision reach both the hard cap `4 >= 4` and the soft threshold `4 >= 2` at once, asserting the execution terminally `FAILED` via the DLQ path *and* `history_bloat_warned_at` is stamped *and* the counter fired exactly once), `history_bloat_min_events_composes_with_failure_cause` and `history_bloat_min_events_combined_with_no_progress_minutes_returns_400` (`history_bloat_integration.rs`, findings #3/#4, against real Postgres). All DB/HTTP suites were re-executed green against real Postgres 16 (not merely compile-checked), and the full workspace quality gate (fmt, clippy `-D warnings` on both touched crates, plus the no-DB `ci_run_coverage`/`migration_hygiene` guard suites) was re-verified green after this second review-fix batch. No `WorkflowEvent` variant, no migration, no route/contract change from any of the four fixes — findings #1/#2 are a `worker.rs`-internal control-flow and ordering fix behind the existing metric/guard-column contract, and findings #3/#4 are `api.rs`-internal query-building fixes behind the existing `history_bloat_min_events` parameter contract.
