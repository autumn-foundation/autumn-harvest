## Phase 3.50 — Non-blocking signal drain for the aggregator pattern (issue #775)

Four synchronous, **non-suspending** signal-consumption methods on `WorkflowContext` that make the canonical aggregator / entity-workflow pattern (collect N events via signals, batch-process, `continue_as_new`) O(1) tasks + O(N) replay instead of O(N) tasks + O(N²) replay. Before this, collecting a batch required one blocking `receive_signal` call per signal — each in its own workflow task, each replaying the whole growing history.

**New public API on `WorkflowContext`** (all `fn`, not `async fn` — they never `.await` and never push a `WaitForSignal` command, so they can never suspend the workflow):
- `try_receive_signal::<O>(signal_name) -> HarvestResult<Option<O>>` — the oldest buffered, not-yet-consumed signal of `signal_name` (FIFO recorded-history order), or `None` when none is buffered.
- `drain_signals::<O>(signal_name) -> HarvestResult<Vec<O>>` — consumes and returns **all** currently-buffered signals of `signal_name` in recorded-history order; empty `Vec` when none. Typed = untyped + `serde_json::from_value`, fail-fast (the first undeserializable payload aborts with `HarvestError::Serialization` via the existing `#[from] serde_json::Error`; earlier payloads in the same drain are already consumed).
- `try_wait_for_signal(signal_name) -> HarvestResult<Option<serde_json::Value>>` — untyped sibling of `try_receive_signal`.
- `drain_signals_raw(signal_name) -> HarvestResult<Vec<serde_json::Value>>` — untyped sibling of `drain_signals`.

**Matcher engine (`replay.rs`).** `drain_signals_raw` reuses the **existing** `HistoryMatcher::claim_pending_signal` (the cursor-bound, race-reserved-skipping FIFO drain built for issue #546 push handlers) verbatim — its behavior is unchanged. `try_*` adds a new `pub(crate) fn try_claim_pending_signal(&mut self, signal_name) -> Option<Value>` that mirrors `match_signal`'s fast path (`pending_signals.iter().position(...)` + `remove()` → exactly one) but adds the two guards that fast path lacks and `claim_pending_signal` already carries: it runs `prepare_match()` first (the cursor-advancing, signal-draining sweep every `match_*` opens with) and skips `race_reserved_signal_events`. It never falls through to a suspension.

**Determinism / ordering contract** (documented on all four methods): a signal recorded *after* an activity/timer the workflow has not yet reached in this replay cycle is invisible until the workflow's own `match_*` call for that event advances the cursor past it — mirroring `wait_for_signal`'s history-order contract. Claimed events are marked consumed, so a later `receive_signal`/`wait_for_signal`/push handler for the same name never re-sees them (no double delivery in either direction). A signal reserved for an **open** `receive_signal_timeout`/`wait_for_signal_timeout` race (issue #476) is never resolved by a drain, so a drain can never silently flip an open race's outcome from `SignalWon` to `TimerWon`; a signal that already *lost* a resolved `TimerWon` race is fair game (identical to `wait_for_signal`). History order is authoritative, consistent with `match_signal_or_timer`.

**All four route through `match_history(|m| ...)`** so the `pump_signal_handlers` post-hook keeps push-handler ordering consistent (mirrors `wait_for_signal`).

**`WorkflowTestEnv` faithfulness (`testing.rs`).** The `WaitForSignal` command handler now promotes **every** currently-queued signal matching the awaited name into history in queued order in one step (was: only the first), mirroring production `ingest_pending_signals` batch promotion. `match_signal` then consumes the first for the `wait_for_signal`, leaving the rest buffered for a following non-blocking `drain_signals`/`try_receive_signal`. Verified zero regressions across the full 66-test `WorkflowTestEnv` suite (no existing test queues multiple same-name signals expecting one-per-`wait` sequential delivery, so the batch-promotion change is behavior-preserving for all of them).

**No new `WorkflowEvent` variant, no migration, no shard-semantics change** — the methods only consume already-recorded `SignalReceived` events. `claim_pending_signal`'s behavior is untouched (additive only); the `race_reserved_signal_events` guard is preserved on both the drain and try paths.
