## Phase 5.0 — `autumn-harvest-sqlite` companion crate (issue #1068)

New workspace member `autumn-harvest-sqlite`: an embedded, single-writer **SQLite** backend for the workflow engine, targeting edge / local-first deployments. It productizes the R&D feasibility spike (issue #966 / PR #1066) into a real crate following the separate-companion-crate recommendation (option ii) — the Postgres path is **completely untouched**.

**What it reuses vs. reimplements.** The crate depends on `autumn-harvest` with `default-features = false`, pulling in only the pure, backend-neutral determinism core (`run_workflow`, `WorkflowEvent`, the replay engine, `WorkflowContext`) — no Diesel/Postgres. It reuses that core **wholesale** (the decision loop calls `run_workflow_with_state(exec, history, handler, input, empty_shared_state(), None).await` with plain values — no connection, no trait object) and reimplements only *persistence* on `rusqlite` (`bundled`, so no system SQLite and **no Docker** for tests): the event store (`store.rs`), the task queue + durable timers (`queue.rs`), and the worker pass (`worker.rs`), wired by `SqliteRuntime` (`runtime.rs`). **No in-crate `StorageBackend` trait** — the core is already reusable as a library.

**Single-writer / single-server contract** (documented in the crate docs): `BEGIN IMMEDIATE` replaces `SELECT … FOR UPDATE SKIP LOCKED` (exactly-once by construction under one writer); polling replaces `LISTEN`/`NOTIFY`; restart = drop the runtime + re-open the file, with an orphan-reclaim on `open()` flipping any crash-stranded `RUNNING` task back to `PENDING` (activity execution is **at-least-once** — bodies should be idempotent). Durable timers use the **real wall clock**: a timer's absolute deadline (`now + duration`) is stored at arm time, so timers are naturally monotonic across restarts with **no virtual clock to persist or reset**; the public drivers use `Utc::now()`, and `*_as_of(now)` variants inject an as-of time so restart/timer tests are deterministic without sleeping.

**The load-bearing correctness work — decision-cycle persistence atomicity as a CLASS invariant.** The spike prototype left the append-then-mutate ordering non-transactional (an open Codex P1). Every persist site in this crate wraps its event append(s) **and** its durable-row mutation(s) in ONE `conn.transaction()`, so a crash (or a mid-write drop) can never leave the event history and the durable rows observably out of sync across a reopen:
- **start** — execution-row insert + `WorkflowStarted` append.
- **dispatch** — the whole decision cycle's `ActivityScheduled`/`TimerStarted` appends + task/timer row inserts (a mid-batch unsupported command rolls the whole cycle back — no half-written cycle).
- **drain** — the activity body runs *outside* the transaction (a SQLite write lock cannot be held across arbitrary user I/O — hence at-least-once), but the terminal `ActivityCompleted`/`ActivityFailed` append + task-row completion (or the retry requeue + attempt audit) commit together.
- **timer fire** — `TimerFired` append + mark-timer-consumed in one transaction (a crash between them would otherwise double-fire the timer and leave a stray non-lifecycle `TimerFired` in history).
- **signal delivery** — `SignalReceived` append + the `harvest_signals` delivered-flag update ride the same cycle transaction.
- **terminal** — `WorkflowCompleted`/`WorkflowFailed` append + execution-state → terminal in one transaction. The cycle's drained bookkeeping commands (see below) are appended **before** the terminal event, in command order, inside that same transaction (mirroring the Postgres worker's `persist_terminal_outcome_commands`); any non-bookkeeping command in a terminal drain is rejected loudly with `SqliteError::Unsupported`, rolling the whole terminal transaction back.
- **bookkeeping** — a `RecordSideEffect` command (from `ctx.system_now`/`new_uuid`/`random_*`/`side_effect`) is persisted as a `SideEffectRecorded` event, and `RecordMarker` as `MarkerRecorded`, **never silently dropped** — whether it rides a suspending batch (via `apply_commands`) OR is emitted in the cycle that completes/fails the workflow with no further suspension (e.g. `ctx.new_uuid()` right before `Ok(..)`, persisted on the terminal path above). Both cases join the same atomic cycle transaction, so replay never re-mints a different value and a history written here always replays byte-identically on the core `WorkflowReplayer`. `ctx.set_current_details(...)` (issue #593) and a re-park `WaitForActivity` are benign **no-ops** (they append no event and gate no control flow) rather than `Unsupported` errors, so a workflow that publishes an operator status breadcrumb is not wedged.
- **timer re-arm** — a timer id may be RE-ARMED under the same name after a prior fire (the poll-loop idiom `loop { ctx.timer("tick", 1).await?; … }`, which the core supports via cursor-based per-id FIFO pairing). Arm idempotency keys on OCCURRENCE (`store::pending_timer_arms` = recorded `TimerStarted` minus `TimerFired` for the id), NOT the bare id, and `enqueue_timer` uses `INSERT OR REPLACE` so the fresh arm supersedes the spent (`fired = 1`) row — a bare-id guard would wrongly match the prior fired arm and wedge the re-arm at `Stuck`.

**Determinism / cross-backend guarantee.** A history written here is byte-identical **per event** to one the Postgres backend would write (both serialize `WorkflowEvent` via the shared adjacently-tagged `#[serde(tag = "type", content = "data")]` form), so it replays unchanged on the core `WorkflowReplayer` — including a deterministic side effect emitted in a terminal (completing/failing) cycle, which is now persisted (see the terminal/bookkeeping bullets above). The claim is *per-event encoding byte-identity + replay-equivalent event SETS*, not identical event streams: the Postgres engine appends an `ActivityStarted` on claim that this backend never writes, and the two replay identically because `HistoryMatcher::scan_activity_terminal` skips `ActivityStarted`. Retryable activity failures go to a `harvest_activity_attempts` audit table + the task-row `attempt` counter (mirroring the Postgres `requeue_for_retry`), so only terminal outcomes ever reach the replayable event log.

**Signals are pull-only (documented non-goal).** A staged signal reaches history (`SignalReceived`) only when a workflow reaches a pull primitive that consumes it. The supported pull surface is the plain waits (`ctx.wait_for_signal` / `ctx.receive_signal`) **and** the signal-or-deadline waits `ctx.wait_for_signal_timeout` / `ctx.receive_signal_timeout` (issue #476) — see the Codex #1069 P2 fix below. The push-handler and non-blocking drain APIs — `register_signal_handler` (#546), `drain_signals` / `try_receive_signal` (#775) — depend on the Postgres task-preparation ingest that promotes *all* pending signals into history up front, which this single-writer backend does not implement; restrict to the pull primitives here (push-based signal *handlers* are a follow-up).

**Codex #1069 review — P2: handle `CancelRaceLosers` so `wait_for_signal_timeout` completes.** A workflow using `ctx.wait_for_signal_timeout(...)` / `receive_signal_timeout(...)` suspends on a `StartTimer` + `WaitForSignal` race. When the **signal wins**, the determinism core pushes a `WorkflowCommand::CancelRaceLosers { timers: [<deadline timer>], .. }` (issue #476/#600) to durably delete the losing deadline timer. Both command-drain sites — `apply_commands` (a teardown riding a suspending batch) and `persist_terminal_pending_commands` (the common `let s = ctx.wait_for_signal_timeout(..).await?; Ok(s)` terminal-drain shape) — previously treated it as `SqliteError::Unsupported("Unknown")`, so *after* `SignalReceived` was already committed the next cycle errored and the execution could never complete — wedging every normal pull-style signal workflow that adds a timeout. Both sites now delegate to a shared `apply_cancel_race_losers` (mirroring the Postgres `worker::apply_race_loser_cancellations`): it deletes each losing timer's still-pending `harvest_timers` row (new `queue::delete_pending_timer`, returning whether a row changed so the idempotent re-push on later replay cycles reports no progress and the decision loop still converges) and, for a race over activities, cancels each losing still-open task row (new `queue::cancel_activity_task`) and appends the synthetic `ActivityFailed { error: "lost race to a sibling branch", non_retryable: true, .. }` the core records — only for a row it actually cancelled, so an activity that genuinely completed first keeps its real terminal. All teardown joins the same cycle transaction (atomic with the winner/terminal event). A non-empty `children` set (a child-workflow race — `StartChildWorkflow` is outside the single-writer subset, so it can never have been dispatched here) is still rejected loudly rather than silently dropping a loser the core would cancel. **No new `WorkflowEvent` variant, no schema change** (the `CANCELLED` task state is terminal for the claim query, which only selects `PENDING`). Regression tests (`tests/signal_timeout.rs`): signal-wins completes with the payload and the losing deadline timer row is actually deleted (verified via a raw connection) and the history replays on the core `WorkflowReplayer`; deadline-wins returns the timeout branch (`None`); and a typed `receive_signal_timeout` with a trailing activity exercises the suspending-batch (`apply_commands`) site. The two signal-win tests fail against the pre-fix code and pass after.

**Codex #1069 review — P1: engine non-determinism must NOT seal FAILED / poison history.** When replay detects workflow-code drift (a bad deploy), the determinism core returns `WorkflowOutcome::Failed { non_deterministic_details: Some(_) }`. The `drive_one_cycle` terminal `Failed` arm previously ignored that field and persisted a normal `WorkflowFailed` event + `FAILED` state — sealing an engine bug as an author failure and poisoning history against the rolled-back build. The arm now branches on `non_deterministic_details`: `None` (a genuine author `Err`) fails terminally, unchanged; `Some(_)` (an engine-detected divergence) **discards the whole divergent decision cycle** — appends NO terminal event, persists NONE of the cycle's pending bookkeeping commands (a marker from the bad build would poison history), and does NOT transition state — leaving the execution `RUNNING`/resumable and surfacing the new `SqliteError::NonDeterministic { execution_id, details }`. Because the `?` never runs, `harvest_events` is byte-identical to before the drive; a later drive with a corrected (compatible) handler resumes from the same unchanged history and completes. Propagating the error out of the drive also terminates the decision loop, so `run_until_blocked`/`poll_once`/`run_until_idle` cannot spin — the operator fixes/rolls back and re-drives. This is the minimal-correct mirror of the Postgres engine's issue #603 gate (which additionally does an automatic block-with-backoff — a documented follow-up here). Regression test (`tests/runtime_robustness.rs::engine_nondeterminism_is_nonterminal_and_resumable`): a phase-1 workflow arms a durable timer (records `[WorkflowStarted, TimerStarted]` and blocks); flipping an injected drift flag makes the SAME workflow schedule an activity at that command slot; re-driving the unchanged history surfaces `NonDeterministic`, appends NOTHING (no `WorkflowFailed`, history byte-identical, execution still `RUNNING`), and after restoring the compatible build the run resumes and completes — plus `author_error_still_seals_failed` pins the `None` arm. Both fail against the pre-fix code (the drive returns `Ok(RunState::Failed)`).

**Codex #1069 review — P2: an unregistered-activity claim is released, not stranded.** `queue::claim_next_ready_task` commits a task to `RUNNING` *before* the worker resolves its handler; if the activity name has no registered body, the drain previously returned `UnregisteredActivity` with the row left `RUNNING` — invisible to later drains (which only re-claim `PENDING`) until a full DB close+reopen ran the orphan reclaim (`UnregisteredActivity → Stuck` until a reopen). `drain_ready` now RELEASES the claim back to `PENDING` (new decrement-free `queue::release_claim`, guarded on `state = 'RUNNING'`, consuming no attempt and not advancing `run_at` — the body never ran) before surfacing the error, so a later drain re-claims it once the body is registered in the SAME runtime, no reopen. Regression test (`unregistered_activity_releases_claim_and_is_reclaimable`): after the error the task row is `PENDING` (verified via a raw connection), and registering the body + re-driving completes the workflow — fails pre-fix (task stranded `RUNNING`). The pre-existing `durability.rs::orphaned_running_task_is_reclaimed_and_body_reruns` test used the unregistered-activity path to *fabricate* a stranded-`RUNNING` orphan; it now fabricates that genuine crash-BEFORE-finalize state directly (raw `UPDATE ... SET state = 'RUNNING'`), keeping its real orphan-reclaim / at-least-once intent intact.

**Codex round 8 — activity-panic containment.** A registered activity body that `panic!()`s (rather than returning `Err`) would unwind past the finalize/requeue branch AFTER the task row is already `RUNNING`, so no failure/requeue ever commits and the run wedges permanently (the claim query only re-selects `PENDING`; a single-process design has no live-peer poison-pill net). `drain_ready` now wraps the body invocation in `std::panic::catch_unwind(AssertUnwindSafe(...))` and converts a caught panic into the crate's NORMAL retryable-activity-failure path — treated exactly like `Err(msg)`: `finalize_activity_result` records the attempt and follows the retry policy (requeue if attempts remain, else terminal `ActivityFailed`). `AssertUnwindSafe` is sound (the body ran outside any transaction; on a caught panic its result is discarded). Mirrors the Postgres worker's handler-panic containment (issue #782), using the shared `autumn_harvest::error::panic_message` extractor. Regression tests: `panicking_activity_is_contained_and_exhausts_to_terminal` (a body that always panics, `max_attempts = 2` → both attempts caught+recorded → terminal `ActivityFailed`/`WorkflowFailed`, task never stranded `RUNNING`) and `panicking_activity_retry_then_succeeds` (panic on attempt 1, succeed on attempt 2 → the workflow completes, no terminal `ActivityFailed` in the log, the panic recorded only in the per-attempt audit). Both fail pre-fix (the panic unwinds through the tokio test).

**Codex round 8 — mixed timer + activity batch.** A single decision cycle emitting BOTH a `StartTimer` and a `ScheduleActivity` (`tokio::join!`) is dispatched correctly: `apply_commands` already appends a cycle's schedule events in COMMAND order (a `for cmd in commands` loop), so **no drain-order change was needed** — the Codex "went Stuck" symptom is a poll-order concern, not a schedule-order one. Regression test (`mixed_timer_activity_batch_completes_and_replays`): with the activity as the first joined future (`join!(activity, timer)`), the batch dispatches both, the activity completes, the run blocks cleanly on the still-armed timer (not Stuck), a later drive fires the timer, the workflow completes, the two schedule events are in command order, and the resulting history replays byte-identically on the core `WorkflowReplayer` — proving the core matcher tolerates the interleaved sibling terminals (`ActivityCompleted` then `TimerFired`). **Documented CORE limitation (not a backend bug):** the REVERSE order — `join!(timer, activity)`, the timer polled first — is unsupported by the *core* determinism engine itself. `HistoryMatcher::match_timer_strict` (replay.rs) breaks its forward `TimerFired` scan at an unconsumed `ActivityScheduled` (it skips consumed siblings, child workflows, signals, external, update, and cancellable-timer events, but stops on an unconsumed activity); verified directly — the core `WorkflowReplayer` rejects even an ideal timer-first history with `NonDeterminismDetected(EarlyCompletion)`. This is shared with the Postgres engine and out of scope for this backend to change; put the activity branch first in a mixed `join!`. On this backend a timer-first mixed batch does not silently loop forever — the driver's `MAX_ITERATIONS` bound surfaces `SqliteError::Stuck` — but it is not a supported shape.

**Durability & concurrency pragmas.** `open()` sets `PRAGMA synchronous = FULL` (fsync on every commit — the conservative durability the crash-then-reopen tests rely on), `PRAGMA journal_mode = WAL` (the idiomatic single-writer + occasional-reader embedded choice; a harmless no-op on an in-memory database), and `PRAGMA busy_timeout = 5000` (a second connection racing the writer's `BEGIN IMMEDIATE` claim retries briefly instead of failing instantly with `SQLITE_BUSY`). WAL + FULL is fully durable. `run_until_idle()` returns the new `SqliteError::Runaway` when the fleet driver never quiesces within its iteration safety bound, rather than swallowing it as a clean `Ok(())` a caller could not distinguish from genuine quiescence (mirroring `run_until_blocked`'s `Stuck`).

**No import/seed API** — the cross-backend guarantee is export-shaped (a SQLite-produced history → the core `WorkflowReplayer`) and needs none; a future edge → hub ingest path that rebuilds derived task/timer rows from open scheduled work (or rejects such histories) is a follow-up.

**Public API.** `SqliteRuntime::open(path)` / `open_in_memory()` (reopen-safe — all state in the DB), `register_workflow(&WorkflowInfo)` / `register_activity(name, ActivitySpec)`, `start_workflow(name, input) -> ExecutionId`, `send_signal(exec, name, payload)`, `poll_once()` / `run_until_idle()` / `run_until_blocked(exec)` (+ `*_as_of` test seams), `load_history(exec) -> Vec<WorkflowEvent>`, `activity_attempts(exec, name)`, and the `outcome(exec)` accessor. Typed `SqliteError`/`SqliteResult` (thiserror). `RunState` / `ExecutionOutcome` / `ActivitySpec` / `ActivityBody` / `ActivityAttempt` are re-exported.

**Known limitations (documented):** a crash *mid activity body* leaves the task `RUNNING` and is recovered by the reclaim on next `open()` (re-running the body — at-least-once); a single-process design has no live-peer heartbeat/poison-pill reclaimer, by design. Signals are pull-only (see above). The `activity_attempts(exec, name)` audit accessor is name-scoped: a workflow scheduling the same activity *name* more than once returns a single merged, attempt-ordered list across those instances (`load_history` remains the per-instance source of truth). (The former "deterministic side effect in a completing cycle is dropped" limitation is **fixed** — see the terminal/bookkeeping bullets above.)

**Tests (no Docker; `rusqlite` bundled):** 8 inline unit tests pinning the atomic rollback/commit of each dispatch/drain/timer-fire site; a **reopen-consistency sweep** (`tests/reopen_consistency.rs`) that drives one workflow through every persist-site type (start → side effect → activity dispatch+drain → timer arm+fire → signal → terminal), reopens the DB at each stage, and asserts history ⟷ durable rows are always consistent (no scheduled event without its task row, no terminal event with a still-pending row, no fired timer left unmarked, execution state matches the terminal event) plus the activity body running exactly once across all reopens; durability scenarios (`tests/durability.rs`: activity retry-then-success, timer fires across restart, signal delivery, deterministic replay after a crash-AFTER-commit not re-executing the activity, and orphaned-RUNNING reclaim re-running the body after a crash-BEFORE-commit); cross-backend replay (`tests/cross_backend.rs`: a SQLite history replays on the core `WorkflowReplayer`, per-event JSON byte-stability, a hardcoded GOLDEN encoding assertion, PG-shaped-history event-SET equivalence, and a frozen `ctx.new_uuid()` side effect persisting across a reopen and replaying byte-identically); and a review-hardening suite (`tests/review_fixes.rs`: terminal-only + after-last-suspension side effects persist and replay, `set_current_details` does not wedge completion, activity retry-exhaustion → `ActivityFailed`/`WorkflowFailed`/`Failed` outcome, direct `Err` return fails terminally, an unsupported mid-batch command rolls the whole cycle back, a re-armed timer id fires again across a reopen, and `run_until_idle` drives multiple executions). CI gains a `Clippy autumn-harvest-sqlite` step (lint job) and a `cargo test -p autumn-harvest-sqlite` step (test job); the `msrv` `cargo check --workspace` auto-covers compile.

**No new `WorkflowEvent` variant, no core-crate changes, no migration — the Postgres path is byte-unaffected.** The crate depends on the pure core surface only; `rusqlite 0.38` (`bundled`, `libsqlite3-sys 0.36.0`) unifies with the existing dependency graph.
