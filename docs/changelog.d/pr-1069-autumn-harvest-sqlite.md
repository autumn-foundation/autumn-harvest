## Phase 5.0 — `autumn-harvest-sqlite` companion crate (issue #1068)

New workspace member `autumn-harvest-sqlite`: an embedded, single-writer **SQLite** backend for the workflow engine, targeting edge / local-first deployments. It productizes the R&D feasibility spike (issue #966 / PR #1066) into a real crate following the separate-companion-crate recommendation (option ii) — the Postgres path is **completely untouched**.

**What it reuses vs. reimplements.** The crate depends on `autumn-harvest` with `default-features = false`, pulling in only the pure, backend-neutral determinism core (`run_workflow`, `WorkflowEvent`, the replay engine, `WorkflowContext`) — no Diesel/Postgres. It reuses that core **wholesale** (the decision loop calls the pure `run_workflow_with_state_history_policy_and_caps(...)` entry point with plain values — no connection, no trait object — threading the real registered `workflow_name` so `ctx.info().workflow_type` matches the Postgres worker; see the FIX C entry below) and reimplements only *persistence* on `rusqlite` (`bundled`, so no system SQLite and **no Docker** for tests): the event store (`store.rs`), the task queue + durable timers (`queue.rs`), and the worker pass (`worker.rs`), wired by `SqliteRuntime` (`runtime.rs`). **No in-crate `StorageBackend` trait** — the core is already reusable as a library.

**Single-writer / single-server contract** (documented in the crate docs): `BEGIN IMMEDIATE` replaces `SELECT … FOR UPDATE SKIP LOCKED` (exactly-once by construction under one writer); polling replaces `LISTEN`/`NOTIFY`; restart = drop the runtime + re-open the file, with an orphan-reclaim on `open()` flipping any crash-stranded `RUNNING` task back to `PENDING` (activity execution is **at-least-once** — bodies should be idempotent). Durable timers use the **real wall clock**: a timer's absolute deadline (`now + duration`) is stored at arm time, so timers are naturally monotonic across restarts with **no virtual clock to persist or reset**; the public drivers use `Utc::now()`, and `*_as_of(now)` variants inject an as-of time so restart/timer tests are deterministic without sleeping.

**The load-bearing correctness work — decision-cycle persistence atomicity as a CLASS invariant.** The spike prototype left the append-then-mutate ordering non-transactional (an open Codex P1). Every persist site in this crate wraps its event append(s) **and** its durable-row mutation(s) in ONE `conn.transaction()`, so a crash (or a mid-write drop) can never leave the event history and the durable rows observably out of sync across a reopen:
- **start** — execution-row insert + `WorkflowStarted` append.
- **dispatch** — the whole decision cycle's `ActivityScheduled`/`TimerStarted` appends + task/timer row inserts (a mid-batch unsupported command rolls the whole cycle back — no half-written cycle).
- **drain** — the activity body runs *outside* the transaction (a SQLite write lock cannot be held across arbitrary user I/O — hence at-least-once), but the terminal `ActivityCompleted`/`ActivityFailed` append + task-row completion (or the retry requeue + attempt audit) commit together.
- **timer fire** — `TimerFired` append + mark-timer-consumed in one transaction (a crash between them would otherwise double-fire the timer and leave a stray non-lifecycle `TimerFired` in history).
- **signal delivery** — `SignalReceived` append + the `harvest_signals` delivered-flag update ride the same cycle transaction.
- **terminal** — `WorkflowCompleted`/`WorkflowFailed` append + execution-state → terminal in one transaction. The cycle's drained bookkeeping commands (see below) are appended **before** the terminal event, in command order, inside that same transaction (mirroring the Postgres worker's `persist_terminal_outcome_commands`); any non-bookkeeping command in a terminal drain is rejected loudly with `SqliteError::Unsupported`, rolling the whole terminal transaction back.
- **bookkeeping** — a `RecordSideEffect` command (from `ctx.system_now`/`new_uuid`/`random_*`/`side_effect`) is persisted as a `SideEffectRecorded` event, and `RecordMarker` as `MarkerRecorded`, **never silently dropped** — whether it rides a suspending batch (via `apply_commands`) OR is emitted in the cycle that completes/fails the workflow with no further suspension (e.g. `ctx.new_uuid()` right before `Ok(..)`, persisted on the terminal path above). Both cases join the same atomic cycle transaction, so replay never re-mints a different value and a history written here always replays byte-identically on the core `WorkflowReplayer`. `ctx.set_current_details(...)` (issue #593) and a re-park `WaitForActivity` are benign **no-ops** (they append no event and gate no control flow) rather than `Unsupported` errors, so a workflow that publishes an operator status breadcrumb is not wedged.
- **timer re-arm** — a timer id may be RE-ARMED under the same name after a prior fire (the poll-loop idiom `loop { ctx.timer("tick", 1).await?; … }`, which the core supports via cursor-based per-id FIFO pairing). Arm idempotency keys on OCCURRENCE (`store::pending_timer_arms` = recorded `TimerStarted` minus `TimerFired` for the id), NOT the bare id, and `enqueue_timer` uses `INSERT OR REPLACE` so the fresh arm supersedes the spent (`fired = 1`) row — a bare-id guard would wrongly match the prior fired arm and wedge the re-arm at `Stuck`.

**Determinism / cross-backend guarantee.** A history written here is byte-identical **per event** to one the Postgres backend would write (both serialize `WorkflowEvent` via the shared adjacently-tagged `#[serde(tag = "type", content = "data")]` form), so it replays unchanged on the core `WorkflowReplayer` — including a deterministic side effect emitted in a terminal (completing/failing) cycle, which is now persisted (see the terminal/bookkeeping bullets above). The claim is *per-event encoding byte-identity + replay-equivalent event SETS*, not identical event streams: the Postgres engine appends an `ActivityStarted` on claim that this backend never writes, and the two replay identically because `HistoryMatcher::scan_activity_terminal` skips `ActivityStarted`. Retryable activity failures go to a `harvest_activity_attempts` audit table + the task-row `attempt` counter (mirroring the Postgres `requeue_for_retry`), so only terminal outcomes ever reach the replayable event log.

**Signals are pull-only (documented non-goal).** A staged signal reaches history (`SignalReceived`) only when a workflow reaches a pull primitive that consumes it. The supported pull surface is the plain waits (`ctx.wait_for_signal` / `ctx.receive_signal`) **and** the signal-or-deadline waits `ctx.wait_for_signal_timeout` / `ctx.receive_signal_timeout` (issue #476) — see the Codex #1069 P2 fix below. The push-handler and non-blocking drain APIs — `register_signal_handler` (#546), `drain_signals` / `try_receive_signal` (#775) — depend on the Postgres task-preparation ingest that promotes *all* pending signals into history up front, which this single-writer backend does not implement; restrict to the pull primitives here (push-based signal *handlers* are a follow-up).

**Codex #1069 review — P2: handle `CancelRaceLosers` so `wait_for_signal_timeout` completes.** A workflow using `ctx.wait_for_signal_timeout(...)` / `receive_signal_timeout(...)` suspends on a `StartTimer` + `WaitForSignal` race. When the **signal wins**, the determinism core pushes a `WorkflowCommand::CancelRaceLosers { timers: [<deadline timer>], .. }` (issue #476/#600) to durably delete the losing deadline timer. Both command-drain sites — `apply_commands` (a teardown riding a suspending batch) and `persist_terminal_pending_commands` (the common `let s = ctx.wait_for_signal_timeout(..).await?; Ok(s)` terminal-drain shape) — previously treated it as `SqliteError::Unsupported("Unknown")`, so *after* `SignalReceived` was already committed the next cycle errored and the execution could never complete — wedging every normal pull-style signal workflow that adds a timeout. Both sites now delegate to a shared `apply_cancel_race_losers` (mirroring the Postgres `worker::apply_race_loser_cancellations`): it deletes each losing timer's still-pending `harvest_timers` row (new `queue::delete_pending_timer`, returning whether a row changed so the idempotent re-push on later replay cycles reports no progress and the decision loop still converges) and, for a race over activities, cancels each losing still-open task row (new `queue::cancel_activity_task`) and appends the synthetic `ActivityFailed { error: "lost race to a sibling branch", non_retryable: true, .. }` the core records — only for a row it actually cancelled, so an activity that genuinely completed first keeps its real terminal. All teardown joins the same cycle transaction (atomic with the winner/terminal event). A non-empty `children` set (a child-workflow race — `StartChildWorkflow` is outside the single-writer subset, so it can never have been dispatched here) is still rejected loudly rather than silently dropping a loser the core would cancel. **No new `WorkflowEvent` variant, no schema change** (the `CANCELLED` task state is terminal for the claim query, which only selects `PENDING`). Regression tests (`tests/signal_timeout.rs`): signal-wins completes with the payload and the losing deadline timer row is actually deleted (verified via a raw connection) and the history replays on the core `WorkflowReplayer`; deadline-wins returns the timeout branch (`None`); and a typed `receive_signal_timeout` with a trailing activity exercises the suspending-batch (`apply_commands`) site. The two signal-win tests fail against the pre-fix code and pass after.

**Codex #1069 review — P1: engine non-determinism must NOT seal FAILED / poison history.** When replay detects workflow-code drift (a bad deploy), the determinism core returns `WorkflowOutcome::Failed { non_deterministic_details: Some(_) }`. The `drive_one_cycle` terminal `Failed` arm previously ignored that field and persisted a normal `WorkflowFailed` event + `FAILED` state — sealing an engine bug as an author failure and poisoning history against the rolled-back build. The arm now branches on `non_deterministic_details`: `None` (a genuine author `Err`) fails terminally, unchanged; `Some(_)` (an engine-detected divergence) **discards the whole divergent decision cycle** — appends NO terminal event, persists NONE of the cycle's pending bookkeeping commands (a marker from the bad build would poison history), and does NOT transition state — leaving the execution `RUNNING`/resumable and surfacing the new `SqliteError::NonDeterministic { execution_id, details }`. Because the `?` never runs, `harvest_events` is byte-identical to before the drive; a later drive with a corrected (compatible) handler resumes from the same unchanged history and completes. Propagating the error out of the drive also terminates the decision loop, so `run_until_blocked`/`poll_once`/`run_until_idle` cannot spin — the operator fixes/rolls back and re-drives. This is the minimal-correct mirror of the Postgres engine's issue #603 gate (which additionally does an automatic block-with-backoff — a documented follow-up here). Regression test (`tests/runtime_robustness.rs::engine_nondeterminism_is_nonterminal_and_resumable`): a phase-1 workflow arms a durable timer (records `[WorkflowStarted, TimerStarted]` and blocks); flipping an injected drift flag makes the SAME workflow schedule an activity at that command slot; re-driving the unchanged history surfaces `NonDeterministic`, appends NOTHING (no `WorkflowFailed`, history byte-identical, execution still `RUNNING`), and after restoring the compatible build the run resumes and completes — plus `author_error_still_seals_failed` pins the `None` arm. Both fail against the pre-fix code (the drive returns `Ok(RunState::Failed)`).

**Codex #1069 review — P2: an unregistered-activity claim is released, not stranded.** `queue::claim_next_ready_task` commits a task to `RUNNING` *before* the worker resolves its handler; if the activity name has no registered body, the drain previously returned `UnregisteredActivity` with the row left `RUNNING` — invisible to later drains (which only re-claim `PENDING`) until a full DB close+reopen ran the orphan reclaim (`UnregisteredActivity → Stuck` until a reopen). `drain_ready` now RELEASES the claim back to `PENDING` (new decrement-free `queue::release_claim`, guarded on `state = 'RUNNING'`, consuming no attempt and not advancing `run_at` — the body never ran) before surfacing the error, so a later drain re-claims it once the body is registered in the SAME runtime, no reopen. Regression test (`unregistered_activity_releases_claim_and_is_reclaimable`): after the error the task row is `PENDING` (verified via a raw connection), and registering the body + re-driving completes the workflow — fails pre-fix (task stranded `RUNNING`). The pre-existing `durability.rs::orphaned_running_task_is_reclaimed_and_body_reruns` test used the unregistered-activity path to *fabricate* a stranded-`RUNNING` orphan; it now fabricates that genuine crash-BEFORE-finalize state directly (raw `UPDATE ... SET state = 'RUNNING'`), keeping its real orphan-reclaim / at-least-once intent intact.

**Codex round 8 — activity-panic containment.** A registered activity body that `panic!()`s (rather than returning `Err`) would unwind past the finalize/requeue branch AFTER the task row is already `RUNNING`, so no failure/requeue ever commits and the run wedges permanently (the claim query only re-selects `PENDING`; a single-process design has no live-peer poison-pill net). `drain_ready` now wraps the body invocation in `std::panic::catch_unwind(AssertUnwindSafe(...))` and converts a caught panic into the crate's NORMAL retryable-activity-failure path — treated exactly like `Err(msg)`: `finalize_activity_result` records the attempt and follows the retry policy (requeue if attempts remain, else terminal `ActivityFailed`). `AssertUnwindSafe` is sound (the body ran outside any transaction; on a caught panic its result is discarded). Mirrors the Postgres worker's handler-panic containment (issue #782), using the shared `autumn_harvest::error::panic_message` extractor. Regression tests: `panicking_activity_is_contained_and_exhausts_to_terminal` (a body that always panics, `max_attempts = 2` → both attempts caught+recorded → terminal `ActivityFailed`/`WorkflowFailed`, task never stranded `RUNNING`) and `panicking_activity_retry_then_succeeds` (panic on attempt 1, succeed on attempt 2 → the workflow completes, no terminal `ActivityFailed` in the log, the panic recorded only in the per-attempt audit). Both fail pre-fix (the panic unwinds through the tokio test).

**Codex round 8 — mixed timer + activity batch.** A single decision cycle emitting BOTH a `StartTimer` and a `ScheduleActivity` (`tokio::join!`) is dispatched correctly: `apply_commands` already appends a cycle's schedule events in COMMAND order (a `for cmd in commands` loop), so **no drain-order change was needed** — the Codex "went Stuck" symptom is a poll-order concern, not a schedule-order one. Regression test (`mixed_timer_activity_batch_completes_and_replays`): with the activity as the first joined future (`join!(activity, timer)`), the batch dispatches both, the activity completes, the run blocks cleanly on the still-armed timer (not Stuck), a later drive fires the timer, the workflow completes, the two schedule events are in command order, and the resulting history replays byte-identically on the core `WorkflowReplayer` — proving the core matcher tolerates the interleaved sibling terminals (`ActivityCompleted` then `TimerFired`). **Documented CORE limitation (not a backend bug):** the REVERSE order — `join!(timer, activity)`, the timer polled first — is unsupported by the *core* determinism engine itself. `HistoryMatcher::match_timer_strict` (replay.rs) breaks its forward `TimerFired` scan at an unconsumed `ActivityScheduled` (it skips consumed siblings, child workflows, signals, external, update, and cancellable-timer events, but stops on an unconsumed activity); verified directly — the core `WorkflowReplayer` rejects even an ideal timer-first history with `NonDeterminismDetected(EarlyCompletion)`. This is shared with the Postgres engine and out of scope for this backend to change; put the activity branch first in a mixed `join!`. On this backend a timer-first mixed batch does not silently loop forever — the driver's `MAX_ITERATIONS` bound surfaces `SqliteError::Stuck` — but it is not a supported shape.

**Codex #1069 review (commit `524823a`) — P1: a late signal must not beat an expired timeout.** When a workflow is parked in `wait_for_signal_timeout` / `receive_signal_timeout`, the decision cycle consumed any staged signal (`apply_commands`'s `WaitForSignal` branch, previously `store::take_pending_signal`) BEFORE `worker::drain_ready` appended the due `TimerFired` later in the same cycle. If the deadline passed while the runtime was idle and a signal arrived AFTER that deadline but before the next poll, history recorded `SignalReceived` first, so the timeout wrongly resolved as an approval — even though the core models a late signal as `TimerFired` **then** `SignalReceived` (so the late signal remains observable to a later plain wait). Fixed by mirroring the Postgres `merge_wake_events` arrival-time ordering: `harvest_signals` gains a `received_at` epoch-second column (set by `stage_signal`; a new doc-hidden `send_signal_as_of(exec, name, payload, now)` seam injects it deterministically, paired with the `*_as_of` drivers, while `send_signal` uses the wall clock). The `WaitForSignal` branch now delegates to `worker::ingest_awaited_signal`, which peeks the oldest pending signal's `received_at` and, via `queue::due_timers_before_signal`, fires every due deadline timer whose `fire_at <= received_at` **first** (ties to the timer, matching `received_at < fires_at` ⇒ signal-first), then appends the `SignalReceived`; a due timer whose deadline is *after* the signal arrived is left for the ordinary `drain_ready` pass to fire *after* the signal, so an on-time signal still wins even when the run is only driven past the deadline. **No new `WorkflowEvent` variant** (this is a brand-new crate, so the additive column needs no migration). A plain `wait_for_signal` (no deadline timer) and any wait driven before its deadline are unchanged — a pending signal only ever interleaves with a deadline timer that is already *due* at drive time, so the three pre-existing `signal_timeout.rs` tests (which deliver before the deadline) are unaffected. Regression tests (`tests/signal_timeout.rs`): `late_signal_does_not_beat_expired_timeout` (signal delivered after the deadline → the run resolves `auto_rejected`, `TimerFired` precedes the still-recorded `SignalReceived`, and the history replays on the core `WorkflowReplayer`) and `on_time_signal_still_wins` (signal delivered before the deadline but driven past it → the approval wins, `SignalReceived` precedes the later-fired `TimerFired`). The first fails against the pre-fix ordering (the late signal wins).

**Codex #1069 review (commit `524823a`) — P1: a workflow-handler panic must not seal FAILED on the first strike.** `run_workflow_with_state` distinguishes a caught **workflow-handler** panic (`Failed { handler_panic: true }`, distinct from an activity-body panic — that already had containment) from an author `Err`. The `drive_one_cycle` terminal `Failed` arm treated it like an author `Err(...)`: it appended `WorkflowFailed` and sealed `FAILED` on the FIRST strike, permanently closing a transiently-panicking or hotfix-able run. A new gate — placed beside the non-determinism gate, BEFORE any terminal side effect — now contains it (issue #782 analog). A per-execution consecutive-panic strike counter (`SqliteRuntime.workflow_panic_strikes`, in-process, cleared on any non-panic outcome so only *consecutive* panics count) is bounded by the new `WORKFLOW_PANIC_MAX_ATTEMPTS = 3` const (mirroring the Postgres worker's default). Under budget the panicked cycle is **discarded** — no terminal event appended, none of its (already-empty) pending commands persisted, state stays `RUNNING` — and surfaced as the new `SqliteError::WorkflowPanicked { execution_id, details }`, which propagates out of the drive loop (mirroring the non-determinism gate) so a hotfix/rollback can re-drive the UNCHANGED history to completion; only at/over budget is the run sealed with the typed `HandlerPanic` error (as a normal `RunState::Failed`). A genuine author `Err(...)` carries no panic flag and still fails terminally on the first strike, unchanged. Regression tests (`tests/runtime_robustness.rs`): `workflow_handler_panic_is_not_sealed_on_first_strike` (a workflow whose body always `panic!()`s stays `RUNNING` with no terminal event under budget and seals `WorkflowFailed` only after the budget is exhausted — never on the first strike) and `workflow_handler_panic_then_hotfix_resumes` (panic on the first drive, flip an injected hotfix flag so the corrected handler completes → the run completes `42`, and the history is exactly `[WorkflowStarted, WorkflowCompleted]`, proving the panicked cycle persisted nothing). Both fail against the pre-fix code (sealed on the first strike).

**Codex #1069 review (commit `524823a`) — FIX C: thread the real `workflow_name` into the executor (cross-backend fidelity).** The decision loop called `run_workflow_with_state(exec, history, handler, input, empty_shared_state(), None)` — the trailing `None` is span-metadata, so the core built the `WorkflowContext` with an EMPTY `workflow_name` (the `workflow_name` param that populates `ctx.info().workflow_type`, issue #698, is separate from `span_meta.workflow_name`, which feeds only the OTel span this backend has no worker for). A workflow that used the documented replay-safe `ctx.info().workflow_type` — in an activity input, an idempotency key, or a branch — therefore recorded/replayed `""` here while the Postgres worker injects the real handler name: a divergence on the very byte-identity guarantee the crate makes. Fixed by driving through the pure, already-`pub` caps-carrying entry point `executor::run_workflow_with_state_history_policy_and_caps(...)`, passing the registered `workflow_name` (available from the execution row) in the dedicated load-bearing parameter and reproducing `run_workflow_with_state`'s own defaults for every other argument (`WorkflowHistoryPolicy::default()`, no declarative handlers, the `DEFAULT_MAX_*`/`DEFAULT_CURRENT_DETAILS_CAP_BYTES` caps, empty context headers, no offload, `NoOpMetrics`; `span_meta` stays `None`). **No core change** — the entry point and the cap consts were already `pub`. Regression test (`tests/cross_backend.rs::workflow_type_reaches_ctx_info_and_replays_on_core`): a workflow reads `ctx.info().workflow_type`, routes it through an activity input, and returns it — the run completes with the real registered name (NOT `""`), the recorded activity input carries it, and the history replays `ReplaySucceeded` on the core `WorkflowReplayer`. Fails pre-fix (records/returns `""`).

**Codex #1069 review (commit `1e346f1`) — P2: `send_signal` rejects unknown / terminal targets.** `send_signal` staged a signal row unconditionally, and `harvest_signals` has no FK/state check, so a typoed `ExecutionId` or a signal to an already-`COMPLETED`/`FAILED` run returned `Ok(())` while the wakeup was silently lost — no live pull primitive (`wait_for_signal` / `receive_signal[_timeout]`) will ever consume it. `send_signal` (via `send_signal_as_of`) now validates the target BEFORE staging, mirroring the Postgres `signal::send_signal` rejections (and the crate's own `outcome()` not-found pattern): an unknown id → `SqliteError::ExecutionNotFound`; a terminal execution (per `autumn_harvest::erase::is_terminal_state`) → the new `SqliteError::WorkflowNotRunning { execution_id, state }`; a `RUNNING` execution stages (and later consumes) the signal exactly as before. The single-writer runtime holds SQLite's only write handle, so the state read and the stage cannot race a concurrent transition. **No new `WorkflowEvent` variant, no schema change.** Regression test (`tests/runtime_robustness.rs::send_signal_rejects_unknown_and_terminal_targets`): an unknown id → `ExecutionNotFound` with zero staged rows; a `COMPLETED` execution → `WorkflowNotRunning` with zero staged rows; a `RUNNING` execution stages and drives to completion consuming the payload. The two rejection cases fail against the pre-fix code (which returned `Ok(())` and staged an unconsumable row).

**Codex #1069 review (commit `1e346f1`) — P2: "fire expired timers before draining activities" assessed and DECLINED (a replay regression for the only reachable shape).** The finding proposed reordering `worker::drain_ready` to fire due `TimerFired` events *before* running ready activity bodies, so an activity-vs-timeout race that is only driven past the deadline records the deadline first. This was implemented, tested end-to-end, and **reverted**: for the *only* mixed activity+timer suspension expressible in this crate's subset — `tokio::join!(activity, timer)` with the activity polled first (the documented "Codex round 8 — mixed timer + activity batch" shape; the reverse order is already an unsupported core limitation) — the reorder produces a history the **core** determinism engine cannot replay. The core's `HistoryMatcher::scan_activity_terminal` (replay.rs) skips `TimerStarted`/`TimerCancelled` mid-scan but **breaks its forward `ActivityCompleted` scan at an unconsumed `TimerFired`** (`_ => break`), so `[…, TimerFired, ActivityCompleted, …]` leaves the activity permanently in-progress → the run wedges at `SqliteError::Stuck`. Verified directly on the core `WorkflowReplayer`: the current (activity-first) drain order `[…, ActivityCompleted, TimerFired]` replays `ReplaySucceeded`, while the finding's proposed order `[…, TimerFired, ActivityCompleted]` replays `NonDeterminismDetected`. The finding's premise ("replay resolves the activity branch even though the deadline passed") presupposes an order-tolerant activity-vs-timeout **race** matcher (the analog of `match_signal_or_timer`, which is why the sibling late-*signal* ordering fix in `ingest_awaited_signal` is sound); no such matcher exists for activity+timer, and `ctx.race()` explicitly rejects a mixed activity+timer shape (`HarvestError::Config`, pinned by the core's own `race_rejects_mixed_activity_and_timer_shape`). Correcting the finding would require a core change to `scan_activity_terminal` (out of scope — no `autumn-harvest/src/` changes) plus a new activity-vs-timer race primitive — far beyond a minimal faithful fix. The current drain order is therefore left unchanged.

**Durability & concurrency pragmas.** `open()` sets `PRAGMA synchronous = FULL` (fsync on every commit — the conservative durability the crash-then-reopen tests rely on), `PRAGMA journal_mode = WAL` (the idiomatic single-writer + occasional-reader embedded choice; a harmless no-op on an in-memory database), and `PRAGMA busy_timeout = 5000` (a second connection racing the writer's `BEGIN IMMEDIATE` claim retries briefly instead of failing instantly with `SQLITE_BUSY`). WAL + FULL is fully durable. `run_until_idle()` returns the new `SqliteError::Runaway` when the fleet driver never quiesces within its iteration safety bound, rather than swallowing it as a clean `Ok(())` a caller could not distinguish from genuine quiescence (mirroring `run_until_blocked`'s `Stuck`).

**No import/seed API** — the cross-backend guarantee is export-shaped (a SQLite-produced history → the core `WorkflowReplayer`) and needs none; a future edge → hub ingest path that rebuilds derived task/timer rows from open scheduled work (or rejects such histories) is a follow-up.

**Public API.** `SqliteRuntime::open(path)` / `open_in_memory()` (reopen-safe — all state in the DB), `register_workflow(&WorkflowInfo)` / `register_activity(name, ActivitySpec)`, `start_workflow(name, input) -> ExecutionId`, `send_signal(exec, name, payload)`, `poll_once()` / `run_until_idle()` / `run_until_blocked(exec)` (+ `*_as_of` test seams), `load_history(exec) -> Vec<WorkflowEvent>`, `activity_attempts(exec, name)`, and the `outcome(exec)` accessor. Typed `SqliteError`/`SqliteResult` (thiserror). `RunState` / `ExecutionOutcome` / `ActivitySpec` / `ActivityBody` / `ActivityAttempt` are re-exported.

**Known limitations (documented):** a crash *mid activity body* leaves the task `RUNNING` and is recovered by the reclaim on next `open()` (re-running the body — at-least-once); a single-process design has no live-peer heartbeat/poison-pill reclaimer, by design. Signals are pull-only (see above). The `activity_attempts(exec, name)` audit accessor is name-scoped: a workflow scheduling the same activity *name* more than once returns a single merged, attempt-ordered list across those instances (`load_history` remains the per-instance source of truth). (The former "deterministic side effect in a completing cycle is dropped" limitation is **fixed** — see the terminal/bookkeeping bullets above.)

**Codex #1069 review (commit `48d54b2`) — P2: a deterministic tie-breaker for equal timer deadlines.** `queue::due_timers` (and its signal-interleave sibling `due_timers_before_signal`) ordered due rows by `fire_at` ALONE, so two timers armed with the same deadline — e.g. `tokio::join!(ctx.timer("a", 1), ctx.timer("b", 1))` — fired in SQLite's *unspecified* tie order. If the backend appended `TimerFired(b)` before `TimerFired(a)` while the `join!` polls `a` first, the run's history no longer replays: the core `HistoryMatcher::match_timer_strict` (replay.rs) scans forward for its OWN `TimerFired`, skipping interleaved `TimerStarted`/`TimerCancelled` siblings, but **STOPS (`break` → `NoMatch`) at an unconsumed sibling `TimerFired`** of a different id. Verified empirically on the core `WorkflowReplayer`: a history that fires in `TimerStarted`-append order `[…, TimerStarted(a), TimerStarted(b), TimerFired(a), TimerFired(b), …]` → `ReplaySucceeded`, while the reversed fire order `[…, TimerFired(b), TimerFired(a), …]` → `NonDeterminismDetected(EarlyCompletion)`. **Codex #1069 review (commit `9e480b8`) — P2: decode activity-failure envelopes into the terminal event (cross-backend byte-identity, AC5).** When a registered activity returned an encoded `ActivityFailure` string (the typed-failure path, issue #227 — e.g. `ActivityFailure::non_retryable("PaymentDeclined", …).with_details({…}).into_error_payload()`), the exhausted-retries terminal path recorded the RAW `harvest_activity_failure_v1` envelope as `error` and HARD-CODED `error_type = "Error"`, `non_retryable = false`, `details = None`. **Codex #1069 review (commit `9e480b8`) — P2: consume pending signals in ARRIVAL order, not insertion order.** `store::peek_pending_signal` selected the oldest undelivered same-name signal with `ORDER BY signal_seq LIMIT 1` — insertion (`AUTOINCREMENT`) order, which can DIFFER from arrival (`received_at`) order when signals are staged out of order. So `worker::ingest_awaited_signal` compared the WRONG arrival time against a `wait_for_signal_timeout` deadline: a LATE signal staged first + an ON-TIME signal staged second let the timeout win (the late signal's `received_at` was past the deadline) and marked the late row delivered while the on-time row stayed queued. Fixed to `ORDER BY received_at, signal_seq LIMIT 1` (arrival-time primary, `signal_seq` the deterministic tie-break for equal arrival times) — mirroring the Postgres `harvest_signals.received_at` ordering — so a signal-timeout race compares the actual earliest-arrived signal's arrival time. **No new `WorkflowEvent` variant, no schema change** (`received_at` already exists, at millisecond precision from commit `6de2d8b`). Regression test (`tests/retry_policy_and_failure_fidelity.rs`, verified RED against the pre-fix code): `pending_signals_are_consumed_in_arrival_order_not_insertion_order` — two `"approval"` signals staged out of arrival order (FIRST/lowest `signal_seq` = LATE, `received_at = t0+3700s` past the 1h deadline; SECOND = ON-TIME, `received_at = t0+10s`), driven before the deadline → the on-time signal (earliest `received_at`) is consumed and WINS the race (`approved:ontime`), no `TimerFired`, and the history replays `ReplaySucceeded` on the core. **Codex #1069 review (commit `5e90f5f`) — P2: anchor a policy retry's backoff to the FAILURE time, not the pre-body cycle-start `now` (supersedes the `now`-anchored backoff from `9e480b8`).** The whole-policy backoff fix (commit `9e480b8`) requeued a retryable failure at `run_at = now + compute_retry_delay(...)` where `now` was captured at the *start* of the decision cycle, BEFORE the activity body ran. Because a body can consume real wall-clock time before returning `Err`, a `RetryPolicy::fixed(60s)` body that failed 45s in scheduled its next attempt only ~15s after the actual failure (or *immediately* if the body ran longer than the delay) — unlike the Postgres path, which computes the delay AFTER handling the result. Fixed by threading a `failure_now` clock seam through `drive_one_cycle` → `worker::drain_ready` → `finalize_activity_result`/`finalize_within_tx`: it is read at *finalize* time (after the body returns), per activity, and a POSITIVE policy backoff anchors to it (`run_at = failure_now + delay`). The wall-clock drivers (`run_until_blocked`/`poll_once`) pass a closure that re-reads the runtime's `now_fn` clock seam (a cheap `Arc` clone captured once, so it never borrows `self` across the `&mut self` cycle call); the `_as_of` drivers pass one returning the caller-fixed epoch, so `failure_now() == now` and deterministic simulation is byte-identical to before (the existing `retry_policy_backoff_delays_the_requeue` `_as_of` test is unchanged). **A ZERO computed delay is an IMMEDIATE retry requeued at the CYCLE-START `now`** — covering both the raw `execute_activity_raw` path (`retry_policy == None`) AND a zero-interval policy (`RetryPolicy::fixed(n, 0ms)`) — so it re-claims in the same drain pass and the retry sequence converges in one call (anchoring an immediate retry to `failure_now`, which is `>= now` under the wall clock, would defer it past the drain pass and make `run_until_blocked` return `WaitingTimer` early — a regression the pre-existing wall-clock `declared_retry_policy_raises_attempts_over_registered_spec` 0ms-policy convergence test catches). Only a positive backoff anchors to `failure_now`. The `+ Send + Sync` bound on the `failure_now: &(dyn Fn() -> i64 + …)` trait object keeps the async `drive_one_cycle` future `Send` (clippy `future_not_send`). **No new `WorkflowEvent` variant, no schema change, no core change** (retry `run_at` is a task-row scheduling field, never recorded in `harvest_events`). Regression tests: `worker.rs` unit `retry_backoff_anchors_to_failure_time_not_cycle_start` (`finalize_within_tx` with distinct `now = 1s` and `failure_now = 46s`: `fixed(60s)` → `run_at = 106s`, NOT `61s`; `fixed(10s)` → `run_at = 56s > failure_now`, so a delay shorter than the body runtime is still in the future — RED pre-fix, `left: 61000, right: 106000`), `raw_path_retry_requeues_at_cycle_now_ignoring_failure_now` and `zero_delay_policy_retry_requeues_at_cycle_now_not_failure_now` (both pin the immediate-retry-at-cycle-`now` convergence invariant), plus the wall-clock integration test `tests/retry_policy_and_failure_fidelity.rs::retry_policy_backoff_anchors_to_failure_time` (an advancing `set_clock` makes the body appear to consume 45s before failing → the 60s backoff anchors to the failure instant `t0+45s`, not the cycle start `t0`; RED pre-fix — anchored to `t0`).

**Codex #1069 review (commit `5e90f5f`) — P2: retry jitter DECLINED as an accepted v0.1 simplification.** The whole-policy retry fix now persists the full `RetryPolicy`, but the backoff path calls the non-jitter `compute_retry_delay`, so a policy with `JitterPolicy::Full`/`Equal`/`Decorrelated` is retried at the deterministic base delay rather than the seeded jitter helper (`compute_retry_delay_with_seed`). Jitter exists to de-synchronize a FLEET of concurrent workers; this backend is single-writer / single-server (there is no fleet to de-synchronize — activities are drained one at a time under one write lock and one polling driver), so the base delay is behaviorally equivalent, and retry timing (`run_at`) is not recorded in `harvest_events`, so honoring or not honoring jitter has ZERO replay / byte-identity impact. Documented as an accepted v0.1 simplification (crate docs, retry bullet) rather than adding fleet-oriented jitter machinery (and an entropy-source decision) to a single-process backend where it is definitionally a no-op.
