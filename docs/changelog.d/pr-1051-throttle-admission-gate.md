## Phase 3.51 — Admission gate authoritative on the single-start throttle route (issue #607 / PR #1051)

Production bug fix. The single-start workflow-start route (`POST /workflows/{name}/start`) has a throttle branch (issue #607) that, when a throttled workflow's token bucket is empty, durably **defers** the start and returns `202 Accepted` — and it did so **before** any admission-gate check. The admission gate (#377 / #618, PR #1014) is a "halt starts during an incident" control that must win over throttle's "pace starts" control (`"halt beats pace"`): PR #1014 wired `gate_cache().check()` into the debounce branch and the batch route, and made the plain/keyed start gate-check authoritatively inside the core start primitive (`GateMode::Check`), but a throttle DEFER returns `202` from this branch and never reaches that core create path — so a genuinely-new throttled start submitted while a gate was armed silently slipped it (`202` instead of `503`). The fix adds the gate check in the single-start throttle branch, **before `reserve_or_defer`**, mirroring the batch route exactly — including its two idempotent-retry bypasses (an explicit caller-supplied `workflow_id` whose start already committed as an active execution, matching `AllowDuplicate`; or one already durably deferred in `harvest_start_throttle`, via `throttle::has_pending_throttle_for_workflow_id`) — so #808 keyed-replay and idempotent retries are **not** regressed (a retry of a committed or already-deferred start still gets its idempotent `202`, only a genuinely-new fresh start under an armed gate becomes `503`), reusing the same `record_admission_blocked` + `503 {"error":"admission blocked","gate_id","reason"}` response the debounce/batch branches emit. **Behavior change:** a fresh throttled start under an armed admission gate now returns `503` instead of `202`. Throttle semantics are otherwise unchanged (gate open → defer `202` exactly as before). `start_throttle_integration` was moved off the `ci_run_coverage` allowlist onto a `linux` CI run row in `.github/ci/integration-suites.txt`, so the throttle-vs-gate contract now runs against live Docker Postgres. **No new `WorkflowEvent` variant, no migration, no test changes** (the existing `retry_with_a_pending_throttle_row_bypasses_the_admission_gate` test was already correct). Surfaced by the #1045 diagnosis of the 202-vs-503 discrepancy on this route.
