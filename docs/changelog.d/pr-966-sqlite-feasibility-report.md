- **R&D** (implemented): SQLite edge/local-first storage-trait feasibility report — see issue #966. Closes the one deliverable of the #966 spike that was never written. The spike's *code* half shipped and then some — the prototype (PR #1066) was productized into the `autumn-harvest-sqlite` companion crate (issue #1068, Phase 5.0; hardened in Phase 5.1) — but **Deliverable 1, the written storage-trait extraction report, did not exist**: `docs/rnd/` held only `wasm-activities-spike.md`, and `docs/sqlite-backend.md` is a *user guide* for the shipped crate, not the leadership decision doc the issue's success metric demands ("leadership can green-light or kill the direction **from the report alone**, without reading the spike code"). Resolved by the #543/#593/#609 reconciliation precedent: map the ACs onto the shipped prior art and close only the genuine gaps. **New `docs/rnd/sqlite-feasibility.md`**, framed honestly as a **retrospective decision record** (the report trails the productization it justifies — stated in the first paragraph rather than buried, and recorded as a process lesson: the written deliverable should gate the productization issue, not trail it).

  **Contents.** A one-page decision summary; a **coupling-mechanism table** — ten mechanisms, with reach measured live: `diesel` query layer 42 modules, `raw-sql` escape hatch 26, `row-lock` (blocking `.for_update()`) 15, `skip-locked` 13, `raw-pg-sql` (identified Postgres-only syntax) 18, `advisory-lock` (`pg_advisory_*`/`pg_try_advisory_*`) 9, `interval-sql` 8, `to_regclass` 6, `listen/notify` 4, `gen_random_uuid` 1 — plus the 83 Postgres-DDL migrations; the **exhaustive 43-row module-by-module inventory** (43 of the 93 core modules are coupled), every row classified **(a)** trivially trait-able **(8)** / **(b)** needs a semantic substitute **(17)** / **(c)** fundamentally Postgres-shaped, i.e. portable only by dropping a capability or reimplementing wholesale **(18)**; a costed sizing of the never-built `StorageBackend` seam and its **cost to the Postgres path**; the **test-suite portability** split (replay/event-schema → ported; single-execution lifecycle → ported with substitutes; multi-worker contention → *semantically void*, not merely hard; fleet/operational surfaces → out of model); the **go/no-go recommendation** (**go, as a separate companion crate — option ii — not a core trait**, which is what shipped) with its known capability losses; **hub-handoff scoping only** (edge `ExecutionId` shard semantics, `(workflow_name, workflow_id)` conflict rules for two disconnected nodes starting the same id, replay fidelity on ingest — with export-only archival named as the credible first cut); a paragraph on **other embedded backends** (libSQL/Turso as the strongest adjacent option, since it is file- and wire-compatible and could relax the single-writer constraint; DuckDB declined as an OLAP engine mismatched to high-frequency point writes; `sled` declined); and the **timebox** with the method note.

  **On the trait's cost to the Postgres path.** The report explicitly does **not** rest the rejection on performance. A coarse-grained generic seam (`<B: StorageBackend>`, the whole claim as one trait method) is monomorphised *and* keeps the fused claim CTE inside the Postgres impl, paying in viral type parameters rather than runtime — so the dispatch and query-decomposition objections are design-specific, not inherent, and the section says so with a two-design comparison rather than asserting the stronger claim. The costs that do carry are **code complexity** (an abstraction layer between the hardest bug class in this codebase — concurrency edges, lock ordering, claim-vs-scanner races — and the concrete SQL semantics every one of those fixes reasons about) and a **doubled test matrix** that is mostly meaningless skips, since the interesting suites (multi-worker contention, lock ordering, HA claim exclusivity) are not merely hard but *semantically void* against a single writer.

  **Load-bearing finding surfaced by the audit:** two modules (`store`, `concurrency`) reference `SKIP LOCKED` **only in comments** — they *consume* the claim invariant without issuing the SQL, so a `StorageBackend` trait derived mechanically from SQL call sites would have abstracted the invariant's *writers* and silently orphaned its *consumers* (compiles, passes unit tests, wrong under concurrency). That is the empirical reason the classification is a human judgement rather than a generated table.

  **Anti-rot enforcement (the TDD deliverable):** new no-DB guard suite `autumn-harvest/tests/integration/sqlite_feasibility_docs.rs` (**14 tests**) makes the report's "exhaustive … verifiable against a `grep`-level audit" claim **falsifiable** instead of aspirational. It re-derives the coupling inventory from `autumn-harvest/src/*.rs` at test runtime — never a hardcoded module list, which would rot identically to the prose — and asserts bidirectionally that every detected module is inventoried (failing with a **paste-ready table row** naming the new module and its mechanisms); that no row names a module that no longer exists or is no longer coupled; that every row carries an explicit (a)/(b)/(c) and names **exactly** the mechanisms grep finds for it (set equality, so a row can no more *over*-claim a mechanism — overstating the port — than under-claim one); that the per-mechanism counts, the (a)/(b)/(c) split, the 43/93 ratio and the migration count all match a live audit; that a module using raw SQL is **never** classified (a); that the cited cross-backend replay test exists; and that the zero-regression invariant is *structurally* true (core has no `rusqlite` and no `autumn-harvest-sqlite` dependency; the SQLite crate depends on core with `default-features = false`). Three further guards pin the suite's own machinery rather than the report: `markdown_section` is line-ending-agnostic and fence-aware, and the CI-step reader is bounded at the next `- name:` so a step key written *after* `run:` is still seen (YAML key order is not significant, so a guard that stopped at `run:` was evadable by reordering). Every guard is mutation-verified. Deliberately **not** guarded: the report's prose judgements (seam sizing, cost estimates, go/no-go reasoning) — those are argument, not fact, and freezing them would stop the document being revisable.

  **Detector design — precise, not generous.** An inventory padded with noise discredits the report as badly as one with holes, so every token was verified to produce zero Rust false positives before adoption. Rejected for that reason: bare `INTERVAL` (matches `DEFAULT_WORKER_POLL_INTERVAL`), bare `diesel` (matches the guardrail lint's own prose listing forbidden crates), bare `FOR UPDATE` (flags `mutex` for a doc comment reading "No `FOR UPDATE`" and for a unit test asserting `!expr.contains("FOR UPDATE")` — reporting a module as coupled because it documents that it is *not* — and cannot separate `FOR UPDATE OF t SKIP LOCKED` from a blocking lock), bare `LATERAL` (`queue` and `execution` both *document* it), bare `::` (every Rust path), `::uuid` (the re-exported `autumn_harvest::uuid`), `::interval` (`tokio::time::interval`), and blanket case-insensitive matching (would flag `diesel::sql_types::Text` as a Postgres cast). Four modules (`effective_config`, `guardrail`, `history_export`, `wasm_activities`) are false positives under a loose detector and are correctly excluded.

  **Closed rules vs open ones — the design lesson the review rounds produced.** `raw-pg-sql` *enumerates* Postgres-only syntax, and an enumeration of a dialect cannot terminate: four review rounds each found another construct it had missed (the blocking row lock; JSONB `#>>`/`LATERAL`/`~`; JSONB `@>`/`||` and `NOW()`; then every *lowercase* spelling of the casts already named). Each miss understated the port, always in the same direction, so **that count is documented as a lower bound**. `raw-sql` instead detects the *escape hatch* — any module reaching for `sql::<…>` or `sql_query` — and cannot miss a construct because it does not enumerate constructs. It is a weaker claim (raw SQL may be portable ANSI), so it is deliberately not evidence of coupling by itself; what it establishes is that such a module's portability **cannot be read off its Diesel usage**, which is exactly what class (a) asserts, and CI enforces the consequence. The split was then validated by the very next round: expanding the open rule more than doubled it (8 → 18 modules) and **changed not one classification**, because the closed rule had already caught all eighteen. The open rule keeps being wrong about *how much*; the closed rule has not been wrong about *which class* — and the class is the only thing a reader decides on. Two of the four misses were a third, distinct shape: not new constructs but the *same* construct spelled differently (`pg_advisory` does not substring-match `pg_try_advisory_xact_lock`; the cast list was UPPERCASE-only). Case and prefix are *bounded* dimensions, so those are closable exactly, and both are closed — the advisory prefix pair covers all ten Postgres advisory-lock functions, and casts are matched on cast *position* (`'::`, `)::`, neither valid Rust syntax) rather than by enumerating type names.

  **One literal AC gap closed:** Deliverable 2 words the first durability scenario as "one workflow with **two activities** and a retry", and the prototype only had the single-activity retry. New `two_activities_with_retry` puts the retry on the *first* activity, whose recovered output is the second's input, and asserts the value the second activity **received** (`(21*2)+1 == 43`, `double` twice, `increment` exactly once) — so a hand-off corrupted by the retry surfaces as a wrong input, not merely a wrong final answer. The report gains a scenario→test table so the "4/4" claim is checkable rather than asserted.

  **Docs + tests only — zero production code touched** (no core, no plugin, no `autumn-harvest-sqlite` source), so the "zero behavior/perf regression to the default Postgres build" invariant holds by construction; **no new `WorkflowEvent` variant, no migration, no route/contract change, no replay/determinism impact.** Cross-links added from the SQLite crate README and `docs/sqlite-backend.md`. No CI manifest change was needed for the guard module — the pre-existing `allos autumn-harvest integration testing -` row runs the whole no-DB target on all three OSes, so it is wired by its `mod.rs` registration alone; a separate ungated `lint` step is what makes it also run on docs-only PRs, which CI's docs-only filter would otherwise skip entirely.
