The spike's *code* half shipped and then some — the prototype (PR #1066) was productized into the `autumn-harvest-sqlite` companion crate (issue #1068, Phase 5.0; hardened in Phase 5.1) — but **Deliverable 1, the written storage-trait extraction report, did not exist**: `docs/rnd/` held only `wasm-activities-spike.md`, and `docs/sqlite-backend.md` is a *user guide* for the shipped crate, not the leadership decision doc the issue's success metric demands ("leadership can green-light or kill the direction **from the report alone**, without reading the spike code"). Resolved by the #543/#593/#609 reconciliation precedent: map the ACs onto the shipped prior art and close only the genuine gaps. **New `docs/rnd/sqlite-feasibility.md`**, framed honestly as a **retrospective decision record** (the report trails the productization it justifies — stated in the first paragraph rather than buried, and recorded as a process lesson: the written deliverable should gate the productization issue, not trail it). Contents: a one-page decision summary; a **Coupling mechanisms** table (eight mechanisms — Diesel query layer 42 modules, blocking row lock (`.for_update()`) 15, `SKIP LOCKED` 13, `INTERVAL`/`make_interval` 8, `pg_advisory_xact_lock` 7, `to_regclass` 6, `LISTEN`/`NOTIFY` 4, `gen_random_uuid` 1 — plus the 83 Postgres-DDL migrations); the **exhaustive 43-row module-by-module inventory** (43 of the 93 core modules are coupled) with every row classified **(a)** trivially trait-able (13) / **(b)** needs a semantic substitute (12) / **(c)** fundamentally Postgres-shaped, i.e. portable only by dropping a capability or reimplementing wholesale (18); a costed sizing of the never-built `StorageBackend` seam; its estimated **cost to the Postgres path** (dynamic dispatch on the benchmarked claim hot path, loss of the fused single-statement claim query, an abstraction layer between the hardest bug class in the codebase and the SQL it reasons about, and a doubled test matrix that is mostly meaningless skips); the **test-suite portability** split (replay/event-schema → ported; single-execution lifecycle → ported with substitutes; multi-worker contention → *semantically void*, not merely hard; fleet/operational surfaces → out of model); the **go/no-go recommendation** (**go, as a separate companion crate — option ii — not a core trait**, which is what shipped) with its known capability losses; **hub-handoff scoping only** (edge `ExecutionId` shard semantics, `(workflow_name, workflow_id)` conflict rules for two disconnected nodes starting the same id, and replay fidelity on ingest — with export-only archival named as the credible first cut); a paragraph on **other embedded backends** (libSQL/Turso as the strongest adjacent option since it is file- and wire-compatible and could relax the single-writer constraint; DuckDB declined as an OLAP engine mismatched to high-frequency point writes; `sled` declined); and the **timebox** with the method note. **Load-bearing finding surfaced by the audit:** two modules (`store`, `concurrency`) reference `SKIP LOCKED` **only in comments** — they *consume* the claim invariant without issuing the SQL, so a `StorageBackend` trait derived mechanically from SQL call sites would have abstracted the invariant's *writers* and silently orphaned its *consumers* (compiles, passes unit tests, wrong under concurrency). That is the empirical reason the classification is a human judgement rather than a generated table. **Anti-rot enforcement (the TDD deliverable):** new no-DB guard suite `autumn-harvest/tests/integration/sqlite_feasibility_docs.rs` (8 tests) makes the report's "exhaustive … verifiable against a `grep`-level audit" claim **falsifiable** instead of aspirational — it re-derives the coupling inventory from `autumn-harvest/src/*.rs` at test runtime (never a hardcoded module list, which would rot identically to the prose) and asserts bidirectionally that every detected module is inventoried (failing with a **paste-ready table row** naming the new module and its mechanisms), that no row names a module that no longer exists or is no longer coupled, that every row carries an explicit (a)/(b)/(c), that every row names the mechanisms grep actually finds for it, that the per-mechanism counts quoted in the report match a live grep, that the cited cross-backend replay test (`sqlite_history_replays_on_core_replayer`) actually exists, and that the zero-regression invariant is *structurally* true (core has no `rusqlite` and no `autumn-harvest-sqlite` dependency; the SQLite crate depends on core with `default-features = false`). The detector is deliberately **precise, not generous**: a bare `INTERVAL` matches Rust constants such as `DEFAULT_WORKER_POLL_INTERVAL` and a bare `diesel` matches the guardrail lint's own prose listing forbidden crates — four modules (`effective_config`, `guardrail`, `history_export`, `wasm_activities`) are false positives under a loose detector and are correctly excluded, since an inventory padded with noise would discredit the report as badly as one with holes. Deliberately **not** guarded: the report's prose judgements (seam sizing, cost estimates, go/no-go reasoning) — those are argument, not fact, and freezing them would stop the document being revisable. **Review fix (Codex P2, PR #1164):** the first cut tracked `FOR UPDATE SKIP LOCKED` but not the *blocking* `SELECT … FOR UPDATE` row lock, so five modules that hold pessimistic row locks (`dlq`, `erase`, `external_task`, `reset`, `signal`) were misclassified **(a) plain CRUD** — the single error most likely to make a port look cheaper than it is, since those modules genuinely look like straightforward inserts. Added `row-lock` as an eighth mechanism and reclassified all five to **(b)** (the lock is subsumed by the single writer's global write lock, the same argument that carries the advisory locks). Detected via the Diesel DSL `.for_update()` rather than the raw `FOR UPDATE` text: the raw text would flag `mutex` *twice* for a doc comment reading "No `FOR UPDATE`" and a unit test asserting `!expr.contains("FOR UPDATE")` — reporting a module as coupled because it documents that it is **not** — and cannot separate `FOR UPDATE OF t SKIP LOCKED` from a blocking lock; the DSL set is a superset of the modules issuing genuine raw-SQL row locks (`queue`, `timeout`, both of which also use the DSL), and the codebase has no `.skip_locked()` DSL call, so `.for_update()` is unambiguously blocking. Every guard was mutation-verified (drop a row / add a phantom row / stale a count / strip a classification / drop a mechanism from a row → each caught by exactly one guard, 7 passed 1 failed; plus a simulated new coupled module landing in `src/`). **Docs + tests only — zero production code touched** (no core, no plugin, no `autumn-harvest-sqlite` source), so the "zero behavior/perf regression to the default Postgres build" invariant holds by construction; **no new `WorkflowEvent` variant, no migration, no route/contract change, no replay/determinism impact.** **Review round 2 (agent review + a live Windows CI failure).** Six fixes. (1) **A real Windows CI failure, root-caused and fixed:** `markdown_section` reconstructed byte offsets as `line.len() + 1` from `str::lines()`, which strips `\r` — so under the CRLF checkout on the Windows leg the running offset drifts one byte per line. The drift only *panics* when it lands inside a multi-byte character, which is why it passed on Linux and on a CRLF copy of the working-tree report, then panicked in CI against the committed one at `byte index 14684 ... inside '→'`. Reproduced byte-for-byte locally, fixed by normalising line endings once on read (mirroring `performance_docs::read_normalized`) and by taking offsets from `split_inclusive('\n')` rather than reconstructing them. Because the failure is *content-dependent* — a one-line edit above an em dash flips whether it panics — the invariant is now pinned directly by `markdown_section_is_line_ending_agnostic` on a fixture with a known multi-byte character, rather than left to the live document being unlucky; mutation-verified by reintroducing the exact original arithmetic. (2) **The guards could not run on the change class they exist for.** A PR editing only `docs/rnd/sqlite-feasibility.md` matches both clauses of CI's docs-only filter, sets `code=false`, and skips the entire `test` matrix — so the anti-rot suite was inert on exactly a docs-only edit. Fixed with an ungated `lint`-job step, and pinned by `guards_run_on_docs_only_changes` (the `performance_docs` precedent, which exists because that suite spent three rounds in the same hole): the step must exist, name this module, live in `lint`, and carry no `if:`. (3) **Parsing hardened from substring to structure.** Inventory rows are now parsed *by cell index* — coupling from cell 2, classification from cell 3 — with **set equality** on the coupling cell rather than containment, so a row can no longer over-claim a mechanism (overstating the port cost) as freely as under-claim one; the classification is matched exactly (`(a)`/`(b)`/`(c)`), so a note reading "not (a)" no longer satisfies it; per-mechanism counts are parsed as *numbers* from the reach cell, so `contains("13 modules")` can no longer be satisfied by "113 modules"; duplicate rows now fail loudly; `#` inside a fenced code block is no longer treated as a heading; and the manifest guards compare against comment-stripped TOML directives, so a comment can neither satisfy nor break them. (4) **New guard `derived_totals_agree_with_the_table_and_the_tree`** pins the figures a reader actually quotes in a decision — the (a)/(b)/(c) split recomputed from the report's own table, the `43 of the 93 core modules` ratio against a live module count, and `83 migrations` against the migration directory — each mutation-verified. A new subdirectory under `autumn-harvest/src` now fails the detector loudly rather than being silently skipped by the flat scan. (5) **The one literal AC gap closed:** Deliverable 2 words the first scenario as "one workflow with **two activities** and a retry", and the prototype only had the single-activity retry. New `two_activities_with_retry` covers the literal shape and the more interesting one — the retry is on the *first* activity, whose recovered output is the second's input, so the test pins the value the second activity received (`(21*2)+1 == 43`, `double` twice, `increment` exactly once) rather than only the final answer. The report gains a scenario→test table so the "4/4" claim is checkable rather than asserted. (6) **Report corrections:** the type layer is ~2 500 lines (~100 KB), not "~185 KB"; the scanner family is seven named modules, no longer conflated with the 13 `skip-locked` total; `store`'s cell now says it issues no *`SKIP LOCKED`* SQL (it does issue Diesel SQL, so the flat "issues no SQL" was wrong); and the test counts are re-verified live (164 SQLite; 1849 lib + 1188 integration no-DB). Cross-links added from the SQLite crate README and `docs/sqlite-backend.md`.
