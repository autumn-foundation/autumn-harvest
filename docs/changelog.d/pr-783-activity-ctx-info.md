- **Phase 3.52** (implemented): Activity run metadata and deadline via `ctx.info()` — see issue #783. The activity-side mirror of the workflow-side `ctx.info()` (issue #698). **Before:** an `#[activity]` body could read its `attempt()`, `max_attempts()`, and `previous_failure()`, but not *which run it belonged to* — so a log line from an activity could not be correlated back to the owning workflow without threading the ids through the activity's own input, and an activity had no way to ask how much of its `start_to_close` budget was left. A long activity therefore had exactly two options: finish, or be killed mid-item by the timeout scanner and lose everything it had done. **After:** one read-only, zero-footprint accessor `ActivityContext::info() -> ActivityExecutionInfo` bundles the attempt's owning-run and dispatch metadata — `execution_id`, `workflow_id`, `workflow_type`, `activity_type`, `activity_id`, `attempt`, `max_attempts`, `is_local`, `queue_name`, `task_id` — plus three deadline accessors: `deadline() -> Option<DateTime<Utc>>`, `time_remaining() -> Option<Duration>`, and the guard `is_expiring_within(reserve) -> bool`. Each `info()` field also has a standalone accessor (`ctx.execution_id()`, `ctx.workflow_id()`, …). **One-hop correlation (AC3):** the reported `execution_id` is exactly the `{exec_id}` segment of `GET /api/harvest/workflows/{exec_id}` — it renders as the bare UUID and round-trips through `FromStr` — so an on-call engineer paging from a log line opens the run with zero directory lookups. Alongside it, `task_id` is the `harvest_task_queue` row PK the operator `retry-now` (#516) / `fail-now` (#765) routes address, so the pair is directly actionable (`None` for a local activity, which has no queue row). **Retry-stable identity (AC4):** the new `ActivityIdentity` struct (`execution_id`/`workflow_id`/`workflow_type`/`activity_type`/`activity_id`, returned by `ActivityExecutionInfo::identity()`) is byte-identical on every attempt of one logical invocation; only `attempt` and the deadline advance. Asserting on the struct rather than a hand-written field list keeps a stability test honest as fields are added. Deriving an idempotency key from `identity()` therefore reuses one key across retries. **Deadline is the minimum of two clocks (a deliberate extension of the issue's literal scope, flagged for spec-owner review):** `deadline()` returns the earliest of the attempt's `start_to_close` budget (`started_at + start_to_close`) and the activity's cross-retry `schedule_to_close` deadline (#378). The issue names only `start_to_close`, but `schedule_to_close` enforcement kills a `RUNNING` row too, so reporting only the per-attempt budget would over-report the time available and let an activity work right up to a kill that discards everything — the destructive direction. `time_remaining()` saturates at zero (never negative). `is_expiring_within(reserve)` is **always `false` when unbounded**, closing an `Option`-ordering trap: `None < Some(_)`, so a naive `ctx.time_remaining() < Some(reserve)` checkpoints *immediately* on an unbounded activity. **Zero mid-timeout progress loss (the success metric):** an activity can now resume from `ctx.heartbeat_details()`, check `is_expiring_within(reserve)` before each unit of work, and yield with a retryable error while there is still time to flush — so the retry resumes from the checkpoint and re-executes **nothing**. **Threading (no new queries):** `append_activity_started_if_pending` already loaded the full `WorkflowExecution` row under its `FOR UPDATE` lock and discarded it; it now returns a `StartedActivity { activity_id, workflow_id, workflow_name }`, so the regular dispatch path gets the owning identity for free. The local path takes the same pair from the caller's already-loaded `prepared.execution`. Local activities report `is_local: true`, `task_id: None`, the owning workflow's `queue_name`, and a deadline drawn from `WorkerConfig::max_local_activity_start_to_close` (the same clamped `per_attempt_timeout` the inline `tokio::time::timeout` enforces), so an unset — or above-cap — `start_to_close` reports the cap (AC5). **No new `WorkflowEvent` variant, no migration, no replay-determinism impact** (AC6): activities are never replayed, so every field is plain already-resolved dispatch state and no value crosses the event log. New `#[must_use]` builders (`with_execution_id`, `with_workflow_id`, `with_workflow_type`, `with_activity_type`, `with_activity_id`, `with_queue_name`, `with_task_id`, `with_deadline`) make each field settable on a test-constructed context (AC7), joined by two testing-gated constructors: `ActivityContext::new_test_with_heartbeat(tx)` (exercise the checkpoint pattern without a worker or database) and `new_test_with_identity(identity)`. `ActivityIdentity` and `ActivityExecutionInfo` are re-exported from `lib.rs` and the prelude. **Refactor:** the metrics/WASM-anchor `let started_at = Instant::now()` in `process_activity_task` was renamed `attempt_clock_start` — that name belongs to `task.started_at`, the wall-clock `TIMESTAMPTZ` both the start-to-close scanner and `deadline()` are anchored to, and conflating the two would silently disagree with the mechanism that kills the attempt. Docs: "Activity run metadata and deadline" in CLAUDE.md (with two new rows on the local-vs-regular decision matrix and a cross-reference from the #698 section); example `autumn-harvest/examples/activity_ctx_info.rs` (operator correlation + deadline-aware checkpointing, 5 embedded tests). Tests, TDD red→green→refactor: 13 pure unit tests for the extracted helpers `attempt_deadline` / `time_remaining_from` / `should_checkpoint` (incl. the min-of-two-clocks rule in both directions, the "never fall back to `scheduled_at`" trap, overflow → `None`, saturate-at-zero, and the `Option`-ordering trap made explicit); 11 pure unit tests for the accessor surface; 6 DB/worker integration tests in `tests/integration/activity_info_tests.rs` — AC1+AC3 (every field describes the real run, `execution_id` round-trips and selects the seeded row, `task_id` addresses the real queue row), AC2 (the reported deadline is exactly `started_at + start_to_close` read off the row the scanner reads, *and* the real `find_timed_out_tasks` reclaims a probe row positioned just past that arithmetic while sparing one just short of it), min-of-two-clocks, AC4 (identity byte-identical across a real worker-driven retry while attempt and deadline advance), AC5 (local `is_local`/`task_id: None`/cap-derived deadline/above-cap clamp), and the success metric (12 items across a forced retry, ledger asserts every item ran **exactly once**, with a negative control proving an unguarded activity is killed by the start-to-close scanner and its work discarded). Both worker-threading mutants (deadline → `None`, identity → synthetic) were verified to fail the suite. **Post-review hardening (four review agents: correctness/threading, API design/semver, test quality/falsifiability, replay safety/invariants — no P1 correctness or replay defect found; every finding below addressed):** (1) **`with_heartbeat_details` doc was false and the example was red** — the builder seeds the resume snapshot and the auto-heartbeat re-send cell but does not attach a flusher, so `heartbeat_details()` still rejects on a bare `new_test()` context. Corrected the doc (rather than clearing `heartbeat_unsupported_reason`, which would make `ctx.heartbeat(..)` silently `Ok(())` into a dropped payload — a worse footgun) and switched the example's attempt-2 context to `new_test_with_heartbeat`, matching a real retry; pinned by a new unit test asserting both directions. (2) **AC5's cap assertion was one-sided and passed a mutant** that ignored the cap entirely (`deadline >= before` is vacuous); replaced with a two-sided `before + cap ..= after + cap` sandwich on both the unset and above-cap halves — **verified to fail** a hardcoded-1s-deadline worker mutant. (3) **AC2's "`None` when unbounded" was only covered by the pure helper**; TEST A now dispatches a second, genuinely unbounded activity and asserts `deadline() == None` through the real worker — **verified to fail** a `.or(Some(now + 1h))` mutant. (4) **`queue_name` was unfalsifiable** (workflow queue, activity queue and asserted value were all `"default"`); the worker now polls a second queue and the sibling activity is dispatched on it, so a hardcoded `"default"` fails. (5) **The negative control asserted the wrong thing** — the start-to-close scanner reclaims the task *row* while the in-flight future keeps running in memory, so the control's in-process ledger legitimately shows every item; the "work was discarded" claim is now asserted on the durable record (no `ActivityCompleted` ever appended) plus a non-empty ledger, and the misleading comment corrected. (6) **The heartbeat clock is a third `RUNNING`-matching scanner predicate** not folded into `deadline()`; documented on the public accessor (not only on the `pub(crate)` helper) with the reasoning — it is dynamic, and freezing the worst case would make a correctly-heartbeating activity with a short `heartbeat_timeout` believe it is permanently out of budget and yield on every attempt — plus the practical rule (`heartbeat_timeout < start_to_close` must actually heartbeat) and a corrected doc example that no longer demonstrates the trap. (7) **The claimed local-activity over-report was refuted, and the real residual documented**: the enclosing workflow-task budget is `max(workflow_task_timeout, max_local_activity_start_to_close)`, so on stock defaults it is 60s, not 10s — extracted as the pure `worker::effective_workflow_task_timeout` and pinned by a unit test, since the `max` is load-bearing for this feature; the genuine residual (cycle time consumed *before* a local attempt is charged to the enclosing budget, not to the reported deadline) is documented on `deadline()` and the over-claiming inline comment corrected. (8) `ActivityIdentity::for_test()` gated behind `testing`, matching its only consumer. (9) `ActivityContext::identity()` added — the docs recommend asserting on `identity()`, and `ctx.info().identity()` cloned the shared strings twice. (10) `ActivityContext::new_test_local()` added: `is_local` is constructor-set, so downstream code previously had no way to unit-test an activity that branches on it. (11) The local path's `owner: (&str, &str)` tuple replaced with a named `OwningRun` struct — two adjacent same-typed `&str`s where a transposition type-checks silently and would mislabel every local activity's owning run. (12) Two gratuitous `String` clones dropped from the regular dispatch path. (13) `with_task_id` gained a debug-assert against the `is_local` + `Some(task_id)` state the worker never produces. (14) Documented divergences from the workflow-side `ctx.info()` sibling (nominal-vs-enforced deadline, `chrono::Duration` negative vs saturating `std::time::Duration`, and how to recover overrun magnitude), reciprocally on both sides; plus the claim-time-snapshot/pause-shift caveat, the Postgres-vs-host clock-domain note, `queue_name`'s empty-in-bare-test-contexts case, `task_id`'s `None` ⇏ local biconditional, the raw-`uuid::Uuid` rationale, and `ActivityIdentity`'s `Hash`/`new()`-is-the-downstream-path notes. (15) Test hygiene: TEST C's vacuous `Utc::now()`-relative sanity assertion replaced with a comparison against the actual un-shortened clock; AC4 extended to pin `task_id`/`queue_name`/`is_local` across a real retry; `identity()`'s projection pinned field-by-field; `checkpoint_start` now fails loudly instead of silently resuming from 0; the `FLUSH_WAIT`/`RESERVE` margins re-derived and widened; the TEST B module doc corrected to describe what part 2 actually drives; and the probe rows' orphan `PENDING` workflow tasks retired so a shared `HARVEST_TEST_DATABASE_URL` database cannot leak them into a later suite. **AC3 gap closed:** the core-crate suite could only prove the reported id round-trips through `FromStr` and selects the right `harvest_workflow_executions` row — the management-API route lives in `autumn-harvest-plugin`, so AC3's literal "`GET /api/harvest/workflows/{id}` → 200" clause was unproven.
