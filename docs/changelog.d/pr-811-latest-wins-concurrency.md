## Phase 3.5x — Latest-wins concurrency strategy (`on_conflict = "cancel_running"`) (issue #811)

Per-key concurrency (#247) had exactly one overflow behaviour: **defer** (enqueue and wait at the claim gate). For an idempotent recompute — reindex a document, refresh a dashboard, re-run a per-tenant sync — that is backwards: the in-flight run is stale the moment a newer request arrives, so the queue fills with runs whose output is discarded. This adds a second, opt-in strategy: **latest-wins**, where a new admission supersedes the oldest in-flight run(s) for the same key.

**Declaration.** `#[workflow(concurrency(key = "input.doc_id", limit = 1, on_conflict = "cancel_running"))]` — a new optional third key on the existing nested attribute. **Omitting it, or spelling `on_conflict = "defer"`, is byte-for-byte today's behaviour**, so every pre-#811 workflow is unchanged (AC1). A typo'd value is a compile error (trybuild fixture `concurrency_invalid_on_conflict.rs`), never a silent fallback to `defer` — an author who believes they configured latest-wins must not get the opposite semantics with no signal.

**Types.** New bounded `ConcurrencyOnConflict { Defer (default), CancelRunning }` in `concurrency.rs` (snake_case serde, `as_str`/`parse`/`is_cancel_running`), carried on `ConcurrencyPolicy.on_conflict` (constructed via the new `ConcurrencyPolicy::new(key, limit)` + `.with_on_conflict(..)`, so every existing literal-struct construction site migrated to the constructor). Also settable directly at start via a new `StartWorkflowParams.concurrency_on_conflict` field, for non-macro/HTTP callers (AC2).

**Where it applies.** Every genuine *admission* path resolves the declared strategy: the plain start route, `signal-with-start`, `update-with-start`, an operator re-run (`RerunRequest`), the typed client stub, and the deferred debounce/throttle/batch fire paths (which carry it through `DebounceStartOptions`). It deliberately does **not** apply to *in-flight continuation* — child spawn, detached child spawn, continue-as-new, and workflow-level retry (#523) keep `Defer`, matching how the #618 admission gates and #607 throttles treat those paths. Letting a retry supersede would invert latest-wins: a retry of an *older* run would cancel the *newer* one that replaced it. The cross-shard completion-trigger outbox re-resolves the strategy from `GLOBAL_WORKFLOW_METADATA` at relay time rather than persisting it, so **no migration** is needed there either.

**Mechanics — where the hook sits is load-bearing.** `concurrency::supersede_running_for_key` runs **inside** the start transaction, **after** the admitted run's own execution row + task row are durable, and **only** on the fresh-insert path (`created == true`). Both halves matter: superseding *before* the insert would cancel the incumbent and then let the reuse policy attach to the very run it just cancelled; superseding on an *attach* would cancel runs on behalf of a start that admitted nothing. The admitted run excludes itself by `exec_id`, so latest-wins can never cancel itself.

**Serialization.** The pass takes `pg_advisory_xact_lock(hashtext(key)::bigint)` — the **same namespace** the claim-time concurrency gate uses — so a supersede and a claim never interleave for the same key. Against `queue::claim_task` this is deadlock-free by construction: the claim side uses the non-blocking `pg_try_advisory_xact_lock` and skips the row rather than waiting on us while holding row locks we need. Taken **only** on the `CancelRunning` path, so a `Defer` start issues zero extra statements. This lock is also what makes AC6's tie-break a function of *admission order* rather than wall-clock: the later-admitted run always wins.

**Known lock-ordering hazard against `ctx.mutex` (#691).** Postgres's one-argument advisory locks share a single 64-bit space, and the durable mutex takes a *blocking* lock in that same space. Two inverted orders exist: *mutex-key then concurrency-key* (a mutex holder reaching a terminal state whose completion trigger starts a `cancel_running` workflow) and *concurrency-key then mutex-key* (this pass, holding the concurrency lock while cancelling an incumbent that holds a mutex). Concurrently, Postgres detects the cycle and aborts one side with SQLSTATE `40P01`, surfacing as a database error on the *start*. The aborted transaction rolls back atomically — no partial supersede, no orphaned cancellation — and the start is safe to retry, so this is a **liveness** hazard, not a correctness one. It requires a workflow that both declares `cancel_running` and participates in `ctx.mutex` on the same terminal path. Documented in `docs/sharding.md`, `CLAUDE.md`, and the `lock_concurrency_key` doc comment (which no longer claims unqualified deadlock-freedom).

**Re-entrancy guard.** A cancellation runs the superseded run's terminal chokepoint, which can start a completion-trigger target **in the same transaction** — and that nested start may itself supersede. Because the outer admission's row is already inserted (uncommitted but transaction-visible) and carries the same key, a nested pass with a different `self_exec_id` would otherwise treat it as a candidate and cancel the very run the outer start is reporting as `created: true`. A `tokio::task_local!` (`ADMITTING`) carries the ids of every start transaction still open on the task; each pass scopes its own id for the duration of its cancellations and every nested scan excludes the whole set.

**Candidate scan.** `(workflow_name, concurrency_key)`-scoped, `state IN ('RUNNING','PAUSED')`, ordered `started_at ASC, id ASC`, joined to `harvest_task_queue` for the resolved key, and **bounded to `limit + SUPERSEDE_SCAN_LIMIT` rows** — the caller only needs enough candidates to compute the clamped shed count, so flipping a long-backlogged `Defer` key to `cancel_running` never materialises the whole backlog while holding the advisory lock. Note the superseded population is *non-terminal execution rows*, a superset of what the #247 claim gate counts (`RUNNING` task rows with a live worker): a `PAUSED` run, or one still deferred at the claim gate, occupies no dispatch slot yet is still superseded — the intended "at most `limit` non-terminal runs per key" reading. Scoping to the workflow *type* as well as the key is what keeps this **migration-free** (the resolved key lives on the task-queue row, so no new column on `harvest_workflow_executions`) and is also a safety property: a different workflow type that merely resolved the same key string, and never opted in, is never cancelled. `SUSPENDED` is deliberately absent — it is not a persisted state (the CHECK constraint forbids it), so `RUNNING`/`PAUSED` is the complete active set (same reconciliation as #609 AC6).

**Shed count.** The pure `supersede_count(existing_others, limit)` computes `(existing + 1).saturating_sub(max(limit, 1))`, capped by `SUPERSEDE_SCAN_LIMIT` (32). Latest-wins is a per-key fair-share control, not a bulk-cancel tool: a single start must never open an unbounded transaction cancelling hundreds of executions (each cancel appends events, fails task rows, and runs the parent-close cascade). Excess beyond the cap is shed by the *next* admission for the same key, so the population still converges without one start paying an unbounded cost.

**Cancellation is the ordinary cooperative path (AC5).** `cancel_workflow_execution_collect` — chosen over the cheaper `inline_cancel` because only the full path notifies an awaited parent (#787) and runs the parent-close cascade. The superseded run reaches `CANCELLED`, its `ctx.is_cancelled()` / Saga compensation fire, and its `ParentClosePolicy` cascade runs normally. A candidate that reached a terminal state between the scan and the cancel is **skipped, not an error** (the goal — "not running" — is already met). That skip is narrowed to the two already-terminal error shapes the cancel primitive itself raises (`is_already_terminal_cancel_race`); `HarvestError::Config` is a general-purpose variant, and swallowing it wholesale would also hide genuine faults reachable from inside the cancel (a malformed `parent_close_policy` column, a completion-trigger start rejected by an admission gate) while silently leaving the key over its declared limit. Such a candidate is still skipped — one corrupt neighbour must not wedge every future admission for the key — but a `tracing::warn!` names the candidate, the key, and the error. Only a cancel that actually transitioned the run (`newly_cancelled`) is counted, so an idempotent no-op cancel is never a supersede. **No new `WorkflowEvent` variant, no migration** — a `WorkflowCancelled` event is recorded exactly as today.

**Source-visible signature change.** Five `pub` functions in `execution.rs` — `start_or_load_workflow_execution_collect`, `start_or_load_workflow_execution_idempotent`, `signal_with_start_workflow_execution_with_metrics`, `rerun_workflow_execution`, `update_with_start_workflow_execution_with_metrics` — changed their 4th tuple element from `Vec<(String, String)>` to `Vec<StartCancelledRun>`. This breaks a downstream caller that binds or iterates that element (see the metric-plumbing rationale below for why the shape had to change). The wrapper functions most callers use (`start_or_load_workflow_execution`, `..._with_metrics`) are unchanged, as is every other public signature.

**Metric plumbing — designed so a caller cannot forget it.** The initial cut hung `superseded_workflow_names` off `StartedWorkflowExecution`, but signal-with-start / update-with-start return *different* outcome structs, so a caller could silently drop the counter. Reverted: the start primitive's 4th tuple element changed from `Vec<(String, String)>` to `Vec<StartCancelledRun>` (a named struct carrying `workflow_name`, `queue_name`, and a `superseded: bool` discriminator), and one shared `emit_start_cancel_metrics()` emitter walks it. That both makes the counter impossible to omit and collapses 6 duplicated consumer loops to a single call each.

**New metric (AC7).** `harvest.concurrency.superseded` (`METRIC_CONCURRENCY_SUPERSEDED`), counter, label `workflow` **only** — the *superseded* run's type. The concurrency key is resolved from workflow input (tenant/document ids) and is unbounded, so labelling by it would violate the ADR-0001 §7 cardinality rule; the per-key view lives on `GET /admin/concurrency` instead. Emitted **post-commit** (a rollback must never leave a phantom count) and **canary-excluded**, mirroring `emit_workflow_terminal`. A superseded run also increments the pre-existing `harvest.workflow.terminal{outcome="cancelled"}` — the new counter isolates the supersede subset from operator/parent-close cancellations. Wired through the full three-touchpoint recipe: no-op default trait method, `metrics_rs_adapter` bridge, dashboard panel (id 930, "Latest-wins supersedes"), `docs/telemetry.md` emission + labels rows, ADR-0001 §7 catalogue row, and the anti-drift `DASHBOARD_PROMETHEUS_SERIES`/`SERIES_LABELS` ground truth.

**Admin read (AC7).** `GET /admin/concurrency` rows gain an additive `workflows: Vec<ConcurrencyWorkflowStrategy>` array (`{workflow_name, on_conflict}`), attributing each `(key, task_type)` group to the workflow type(s) with live tasks on it and reporting the effective strategy each declares. Populated **only** by the management API — the new `queue::concurrency_key_workflows` join is never on the worker's in-process concurrency-sampler hot path, and `#[serde(default, skip_serializing_if = "Vec::is_empty")]` keeps the sampler-shaped value byte-identical to the pre-#811 wire form. The attribution query shares `concurrency_key_stats`'s row filter, pinned by a unit test (the two are separate `sql_query` strings and would otherwise be free to drift). A workflow declaring no policy reports `defer`, matching what the start path resolves. The route is `free_form` in the contract registry so `contract_regression` cannot catch a shape drift — a hand-written serde test pins it instead.

**Sharding (AC8).** `docs/sharding.md`'s #247 scope contract is extended: latest-wins is **shard-local** (the advisory lock and the candidate scan are both shard-scoped), so a multi-shard deployment gets "at most `limit` per shard" and a run on shard A is never superseded by an admission on shard B. Cross-shard latest-wins is explicitly out of scope — it would need a distributed lock plus a cross-shard cancellation transaction, and the sharding design deliberately avoids cross-shard transactions. Pin the key with an explicit `residency_key` (#697) if the guarantee must be global.

**Tests, TDD red→green→refactor.** 12 pure unit tests in `concurrency.rs` (`ConcurrencyOnConflict` round-trip/parse/default, `supersede_count` truth table incl. the `limit = 0` clamp and the `limit = N` boundary); macro-attribute tests for `cancel_running` / explicit `defer` / omitted-defaults-to-Defer in `macros_workflow.rs`; a trybuild compile-fail fixture for a typo'd value; telemetry constant + canary-exclusion + emit-once-per-run unit tests; a real label-content `metrics_rs_adapter` bridge test (a swapped/dropped/extra label is caught, not just "does not panic"); a `metrics_coverage.rs` reachability + forbidden-label test; `queue.rs` serde-shape and SQL-drift tests; and a DB integration suite `tests/integration/concurrency_supersede_tests.rs` driving the **real production wrapper** `start_or_load_workflow_execution_with_metrics` (not the lower-level collect fn, so the post-commit emission plumbing is exercised too) — AC3 `limit = 1` supersede, AC4 `limit = N` oldest-first shedding, AC1/AC2 `Defer` cancels nothing, AC5 the `WorkflowCancelled` event is recorded, AC6 the later-admitted run survives, cross-workflow-type isolation, distinct-key independence, and the **success metric**: 100 rapid same-key starts leave exactly ONE non-terminal run (the last admitted) and 99 `CANCELLED`, with the "never two non-terminal at once" invariant asserted after **every** admission rather than only at the end, plus an assertion that the survivor's workflow task row is still `PENDING`/claimable (a supersede pass that cancelled the survivor's own task row would otherwise leave the execution `RUNNING` forever while the run hangs, and every other assertion would still pass).

Six further tests close the gaps a review pass identified, each killing a mutation the original suite could not: `later_admitted_run_wins_even_when_its_started_at_is_older` pushes the incumbent's `started_at` an hour into the *future* before the second admission, so admission order and wall-clock order disagree — the **distinguishing half of AC6**, which every sequential test is structurally unable to falsify; `concurrent_admissions_converge_to_one_survivor` (multi-thread runtime, pooled connections) storms one key with 10 genuinely concurrent admissions and asserts exactly one survivor, `n-1` cancelled, zero errors, and `n-1` counter samples — the first test to actually contend the advisory lock AC3's "same serialized critical section" rests on; `paused_incumbent_is_superseded` pins `PAUSED` in the active set (dropping `'PAUSED'` from the scan passes every other test); `attach_does_not_supersede` pins the `created == true` gate (every other test uses a distinct `workflow_id`, so the attach branch was never taken); `supersede_records_the_supersede_reason` asserts the `WorkflowCancelled` payload names `SUPERSEDE_CANCEL_REASON` — the operator's only signal distinguishing a supersede from an operator cancel; and `scan_limit_clamps_shed_per_admission_and_still_converges` builds a `SUPERSEDE_SCAN_LIMIT + 2` backlog under `Defer`, then asserts the first latest-wins admission sheds exactly 32 and the next one converges — the documented safety bound previously had zero tests. **RED phase proven**: neutering the shed computation fails exactly the 4 supersede tests while both `Defer`/isolation controls stay green. Run against real Postgres 16; registered in `.github/ci/integration-suites.txt` for the Docker-backed Linux run.

**Post-review hardening (Codex round 1, two P2s).** (1) **Scheduled fires emitted no supersede counters.** The scheduler resolves the declared `on_conflict` from the registered `WorkflowInfo` and threads it into `StartWorkflowParams`, so a scheduled tick genuinely *does* supersede an incumbent — but both workflow start sites (`tick_one_workflow_schedule` and the buffered-drain `drain_buffered_schedule_runs`) called the metrics-*discarding* `start_or_load_workflow_execution` wrapper, so neither `harvest.concurrency.superseded` nor the cancelled terminal counter fired for the shed run. AC7 says "once per superseded run", and a scheduled fire supersedes like any other admission. Both sites now call `start_or_load_workflow_execution_with_metrics` with the tick's own recorder (already in scope on both functions), so the post-commit `emit_start_cancel_metrics` runs. This also closes an adjacent under-report on the same two sites: `_with_metrics` threads the recorder into `check_and_report_unfinished_handlers` as well, so a scheduled start that replaces a run holding unfinished update handlers now emits `harvest.workflow.unfinished_handlers` instead of silently dropping it. The DAG path is unaffected — it passes `concurrency_key: None` + `Defer`, so it can never supersede. Regression test `scheduled_tick_supersede_emits_the_counters` drives the **real public `tick_once`** against a due schedule with a live incumbent and asserts both counters; confirmed RED against the pre-fix wrapper (the supersede happened — the incumbent reached `CANCELLED` — while the recorder saw zero samples). (2) **`GET /admin/concurrency` advertised an unenforced strategy for activity rows.** An activity task can carry a `concurrency_key` too (#247), but latest-wins is a workflow-*start* admission control: the supersede runs inside the start primitive and sheds workflow *executions*. Nothing sheds an in-flight activity for a newcomer, so an activity group always defers — yet the handler resolved the owning workflow's declared policy onto the `task_type = "activity"` row, reporting `cancel_running` for a group where it is never enforced. New pure helper `effective_admin_on_conflict(task_type, declared)` reports the declared strategy only for `task_type = "workflow"` and `Defer` otherwise (including for an unrecognised task type). Covered by a pure unit test plus the DB/HTTP test `admin_concurrency_reports_defer_for_activity_rows`, which seeds a workflow task **and** an activity task on one key owned by the same `cancel_running` workflow and asserts the two rows report `cancel_running` and `defer` respectively — confirmed RED by mutating the helper to a pass-through.
