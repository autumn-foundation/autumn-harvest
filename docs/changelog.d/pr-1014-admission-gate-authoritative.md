## Phase 3.51 — Admission gate authoritative across all workflow-start producers (issue #618)

- **Make the admission gate authoritative across all workflow-start producers** (implemented) — see issue #618. The admission gate (#377) lets an incident operator halt new workflow starts fleet-wide or by name/queue/shard/owner while in-flight work drains, but it was **not** authoritative: three in-process producers started workflows without consulting it. It is now either gated or **explicitly, observably exempt** on every in-process producer. New bounded `admission_gate::StartProducer` enum (`Api`/`BatchStart`/`CompletionTrigger`/`WebhookDelegate`/`Scheduler`/`Debounce`/`Throttle`/`Outbox`, `as_str()` + `ALL`) plus the discoverable `producer_contract()` (`ProducerContractEntry { producer, status: ProducerGateStatus::{Gated, ExemptByDesign}, rationale }`). **Completion triggers (AC1) — the main gap, now closed:** `completion_trigger::evaluate_triggers_for_execution` reaches the shared `AdmissionGateCache` through a new process-global `GLOBAL_ADMISSION_GATE_CACHE` static (mirroring `GLOBAL_WORKFLOW_METADATA`/`GLOBAL_CALLBACK_CONFIG`), published by the plugin at boot with the **same `Arc`** the management API and background refresh loop use — so no cache is threaded through the ~17 call sites and gate creates/lifts propagate automatically. The gate is checked **inside the source workflow's terminal-commit transaction**, before the fires-row insert, evaluating every scope (routing + owner resolved up-front). A block is a **clean skip that never rolls back the source terminal** (mirroring the #810 `condition_unmet` resolved-skip shape): it records `record_admission_blocked` (the *same* `AdmissionBlocked` outcome a direct API start records) and writes an exactly-once resolved-skip row in `harvest_completion_trigger_fires` with the new `outcome = 'admission_blocked'` through the existing `ON CONFLICT DO NOTHING` PK path, so cascade re-entry dedupes it and this terminal never retries the start. A blocked completion-trigger start is therefore **dropped, not deferred** — identically to a direct API start being refused during an incident. When no gate cache is installed (standalone integrations, or the plugin's brief boot window) the check is skipped and behaviour is **byte-identical to pre-#618** (no extra DB read on the no-gate path). **Webhook delegate (AC2):** the inbound webhook receiver (#344) delegates `Starts`/`SignalsWithStart` straight to `api::start_workflow`/`signal_with_start_workflow`, which already check the gate — so a scoped gate blocks a matching webhook-triggered start and lets a non-matching one through, by construction. **Outbox relay (AC3) — exempt-by-design + observable:** `outbox::dispatch_workflow_start_request` relays workflow-start requests durably committed *before* any gate was raised; gating them would drop already-accepted in-flight work (the opposite of the gate contract, "halt **new** starts while in-flight work drains"). It is left un-gated but now increments the new `harvest.admission.bypassed{producer="outbox"}` counter on every relayed start so the exemption is never silent. **New metric (AC4)** via the standard 3-touchpoint recipe: `METRIC_ADMISSION_BYPASSED = "harvest.admission.bypassed"` + `METRIC_LABEL_PRODUCER = "producer"` (telemetry.rs), a no-op-default `MetricsRecorder::record_admission_bypassed(producer)` trait method, and the `metrics_rs_adapter` bridge (`execution.id` is never a label, ADR-0001 §7). **Discoverable contract (AC5):** `GET /admin/gates` now returns a `producers` block alongside `gates` listing each producer's `gated`/`exempt_by_design` status and rationale, so the contract is discoverable without reading source; documented in `docs/operations/admission-gate-producers.md` and `docs/api-contract.json`. **Known-gaps note removed (AC6):** the stale "Known gaps — ungated workflow producers" comment in `src/admission_gate.rs` is replaced by a "Start-producer contract" section since all three gaps are resolved. Scheduler already gated (`scheduler.rs` `check_admission`); debounce/throttle are gated at admission time on the HTTP start route (their scanners only relay already-admitted work), so they are classified `gated` in the contract. **No new `WorkflowEvent` variant, no change to event JSON tagging, NO migration, no `::autumn_harvest::` macro-path change (AC7)** — the `admission_blocked` outcome reuses the existing nullable `harvest_completion_trigger_fires.outcome TEXT` column from #810; the gate cache is an in-process static; the whole change is start-path policy resolution + telemetry + a read-only API field. **Success metric:** with a `Fleet` gate raised, 100% of workflow-start attempts across the in-process producers this PR touches (API start, completion trigger, outbox) are either blocked-and-counted or bypassed-and-counted — measured by the `fleet_gate_leaves_zero_uncounted_admissions` integration test, which drives all three with a gate active, asserts exactly one target execution (the exempt outbox one) is created, and asserts every start attempt landed in either the blocked or the bypassed counter (zero un-counted admissions), verified against a shared `CapturingMetrics` recorder. **Tests, TDD red→green:** core unit tests in `admission_gate.rs` (`StartProducer::as_str` bounded/unique, `producer_contract` covers every producer + outbox exempt, `GLOBAL_ADMISSION_GATE_CACHE` set/get shared-Arc round-trip), `telemetry.rs` (constant name + no-op default), `metrics_rs_adapter.rs` (bridge does-not-panic); core DB integration `autumn-harvest/tests/integration/admission_gate_authoritative_tests.rs` (Fleet gate blocks a completion-trigger start with the block counted + `admission_blocked` fires row + source terminal not rolled back; no-gate-cache backward compat starts the target with a NULL-outcome fire; scoped `WorkflowName` gate match blocks / miss proceeds); plugin HTTP+outbox integration `autumn-harvest-plugin/tests/admission_gate_authoritative_localpg.rs` (`GET /admin/gates` producer contract; outbox relay exempt + bypass counted under a live Fleet gate; scoped gate blocks/passes the start route the webhook delegate forwards to; the zero-un-counted-admissions success-metric test). **All DB/HTTP tests were actually executed against a real local Postgres 16** (the core `admission_gate_authoritative` suite via `HARVEST_TEST_DATABASE_URL` and the plugin `admission_gate_authoritative_localpg` suite over the real axum router + real outbox relay), not merely compile-checked. Out of scope (per issue): new gate scopes/matching semantics, gating starts from outside the plugin process, auto-lifting/scheduling gates, rate-limited recovery replay.

**Post-review hardening (four-reviewer pass, all fixed TDD-style):** (F1) the four deferred-fire producers that could relay a start past a gate raised *after* admission are now exempt-with-bypass-counter, mirroring the outbox: `debounce`/`throttle`/`event_batch` scanner fires and the completion-trigger **cross-shard** relay (`enforce_completion_triggers_outbox`, now threaded a `metrics` recorder from `enforce_timeouts_once`) each increment `harvest.admission.bypassed{producer=…}` with a distinct label. (F2) `StartProducer` gains `EventBatch` + `CompletionTriggerOutbox` variants (now 10), and `ProducerGateStatus` gains a `GatedAtAdmission` variant so the contract distinguishes the deferred-fire producers' split behaviour (gated at HTTP admission; scanner fire exempt-with-counter) from a flat `gated`. (F3) `AdmissionGateCache::check()`'s fail-closed sentinel (`Uuid::nil()`, now single-sourced via `admission_gate::sentinel_gate_id()`) no longer permanently drops a completion-trigger start on a transient gate-DB blip: the completion-trigger path distinguishes the sentinel from a real operator gate and **proceeds** (no block, no fires row, no count) rather than dropping already-committed in-flight continuation; a real gate still blocks + drops + counts. (F4) the `admission_blocked` block is counted exactly once — the fires-row `inserted` count now gates the `record_admission_blocked` call, and cascade re-entry records a `deduped` outcome instead of a second block. (F5) `set_global_admission_gate_cache` warns on a divergent re-publish, and `stop_harvest_runtime` clears the global (ptr-eq guarded so a stopping plugin never clobbers a live sibling's cache). (F9) the target queue is resolved at most once on the gate-present completion-trigger path. (F10) the global-cache accessor/setter recover a poisoned lock (`into_inner`) rather than failing to `None`. (F11) the global cache is published *before* `HarvestRunner::start` spawns the workers/scanners (safe now that F3 makes a boot-window fail-closed sentinel proceed). (F12) the event-batch HTTP gate pre-check's bounded TOCTOU window is documented (it shares the debounce path's non-atomic check-then-admit shape); a start that slips it is durably deferred and its scanner fire is counted as a bypass, so no un-counted admission results. (F13) the module docs and `docs/operations/admission-gate-producers.md` gain an explicit **out-of-scope — in-flight continuation** section (workflow-level retry #523, continue-as-new, child/detached-child spawn, reset forks, in-process client handle), and the ops doc is linked from `docs/runbooks/contain-runaway-execution.md` and `docs/runbooks/harvest-alerts.md`. **Deferred (noted, not fixed):** a completion-trigger evaluation on the cancel/terminate path passes `metrics: None`, so a block there is gated-but-uncounted (pre-existing `None`-passing pattern; correctness unaffected). **F6:** the `fleet_gate_leaves_zero_uncounted_admissions` success-metric test now drives all seven in-process producers (API + completion-trigger blocked-and-counted; outbox + CT cross-shard relay + debounce + throttle + event-batch bypassed-and-counted) under a live Fleet gate and asserts zero un-counted admissions; the plugin local-PG suite is dual-mode (`HARVEST_TEST_DATABASE_URL` preferred, testcontainers fallback) and runs Docker-backed in CI. New core DB tests cover the F3 sentinel-proceeds and F4 no-double-count paths. All DB/HTTP suites executed against a real local Postgres 16.

**Post-review hardening, round 3 (two Codex findings on commit `956178c`):** (F1, P1 — `plugin.rs` boot ordering) the F11 change published the gate-cache `Arc` to the process-global static *before* `HarvestRunner::start` spawned the workers/scanners, but the boot-time `load_active_gates` that populates the snapshot ran **after** the runner started — so a scanner tick or completion trigger firing in the startup window ran `check_cached()` against an EMPTY snapshot and PROCEEDED, bypassing persisted Fleet/queue/name gates uncounted at boot. Fixed by reordering `start_harvest_runtime`: the boot-time `load_active_gates` → `refresh` now runs on `harvest_pool` **before** it is moved into `runner_resources` — i.e. before the cache is published to the global and before the runner spawns — so the published `Arc` (and the one workers see) already carries the persisted gates. A genuine gate-DB outage at boot is unchanged: the snapshot stays empty and completion triggers proceed (the same bounded caveat as a mid-run fail-closed with no cached match), never converted into a permanent block-drop; the direct HTTP start path still fails closed via `check()`. (F2, P2 — `completion_trigger.rs` cross-shard queue resolution) for a cross-shard trigger (target hashing to a shard other than the source's, no explicit trigger queue), the inline gate check called `resolve_target_queue(conn, …)` on the SOURCE transaction connection — which for a `target_shard == 0` target queries the source shard's `harvest_schedules`, missing the target's schedule and falling back to the default queue, so a `Queue(q)` gate scoped to the real target queue was MISSED (and the outbox relay, which resolves the real queue on the target connection at fire time, is exempt-with-counter, so nothing downstream caught it). Fixed with the new `pub` `completion_trigger::resolve_cross_shard_target_queue`, which — for a cross-shard target — resolves the queue on the **target shard's** connection (mirroring how `enforce_completion_triggers_outbox` resolves it at fire time), falling back to the source connection only when the target-shard pool is unavailable (Fleet/name gates still match; only a Queue gate could be missed in that unreachable-pool edge). Same-shard targets keep the single-connection (no extra DB read) path. Tests, TDD red→green: `boot_load_of_persisted_gate_blocks_completion_trigger` (persist a Fleet gate, run the exact `load_active_gates` → `refresh` boot-load path, evaluate a matching trigger → blocked + counted + `admission_blocked` fires row — the behavioural guarantee the reordering provides; the private-`start_harvest_runtime` ordering itself is verified by code reading); `cross_shard_gate_check_resolves_target_queue_on_target_shard` (a genuine two-database multi-shard setup — shard 0/target owns the `ag_target_wf -> ag_priority_q` schedule, shard 1/source does not — proving `resolve_cross_shard_target_queue` resolves on the target shard where the pre-fix `resolve_target_queue(source_conn, …)` missed it; needs only `harvest_schedules`, so it runs against a fresh `INIT_SQL` DB). Both new tests plus the full core suite (9/9) and the plugin `admission_gate_authoritative_localpg` suite (4/4) executed green against a real local Postgres 16. **Pre-existing gap flagged (not one of the two findings, discovered while writing the F2 test):** this suite's curated `INIT_SQL` omits `harvest_build_policies` and several `harvest_workflow_executions` columns (`priority`/`assigned_build_id`/`completion_callbacks`), so tests that call `start_or_load_workflow_execution` cannot run against a pure-`INIT_SQL` testcontainers DB (the CI Docker step) — they were only ever run against a fully-migrated local database. The F2 test was written to avoid `start_or_load` (it only needs `harvest_schedules`), so it is testcontainers-safe; the broader `INIT_SQL` completeness gap is left for separate triage (all 72 migrations verified to apply cleanly, so the fix is a straightforward `INIT_SQL` expansion, but it needs single-batch validation and touches the whole suite).

**Post-review hardening, round 2 (Codex P1 on PR #1014):** the round-1 F3 fix over-corrected. `AdmissionGateCache::set_fail_closed()` retains the cached gates snapshot (it only flips the `initialized` flag), but the completion-trigger path collapsed *every* fail-closed result onto the nil sentinel and PROCEEDED — so a real Fleet/name/queue gate already loaded into the cache, followed by a failed refresh (fail-closed), would let completion-trigger starts BYPASS the active gate uncounted while direct API starts still blocked: a gate leak during exactly the incident the gate exists for. Fixed by adding `AdmissionGateCache::check_cached()` (runs the pure `check_admission` matcher against the current snapshot regardless of the initialized flag, returning only a REAL matching gate, never the sentinel) and rewriting the completion-trigger branch to use it: a real cached gate matching the start → block + drop + count (keeping the F4 `inserted > 0` no-double-count guard); no cached gate matches → proceed (transient-blip / boot-window case, still avoiding a permanent drop). The `sentinel_gate_id()` special-casing was removed from `completion_trigger.rs` (the helper stays — `check()` still returns it for the API block-everything path). Deliberate, documented divergence: when initialized-and-healthy the API and triggers see identical gates; under fail-closed the API blocks everything (caller retries) while triggers honour only known-cached gates (they cannot retry). Bounded caveat (documented in `docs/operations/admission-gate-producers.md`): a gate ADDED during a gate-DB outage — never loaded into the snapshot — won't block completion triggers until the next successful refresh; strictly better than either permanent-drop or unconditional-bypass. Tests, TDD red→green: new core DB `completion_trigger_fail_closed_with_cached_gate_blocks` (a real Fleet gate loaded then `set_fail_closed()` → target NOT started, `admission_blocked` counted, fires row present — confirmed FAILING against the round-1 code, then green); the former `completion_trigger_fail_closed_sentinel_proceeds` renamed to `completion_trigger_fail_closed_no_cached_gate_proceeds` (empty snapshot → proceeds); unit tests `check_cached_honours_snapshot_under_fail_closed` / `check_cached_returns_none_on_empty_snapshot`. Executed against local Postgres 16.
