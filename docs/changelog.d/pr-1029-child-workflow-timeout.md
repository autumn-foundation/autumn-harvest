## Phase 3.51 — Child-or-deadline waits for bounded sub-orchestrations (issue #779)

`WorkflowContext::execute_child_workflow_timeout::<O>(info, input, timeout) -> HarvestResult<Option<O>>` (typed) and the untyped sibling `spawn_child_workflow_timeout(name, input, timeout) -> HarvestResult<Option<Value>>` bound a **child-workflow** await with a durable deadline — the primitive for a sub-orchestration that must not run past an SLA. It mirrors `receive_signal_timeout` (#476) one level up: instead of racing a signal against a timer, it races a child workflow's terminal outcome against a timer. `Ok(Some(output))` = child terminal **success** before the deadline; `Ok(None)` = deadline fired first (the still-running child is **request-cancelled**); `Err(_)` = child **failure** before the deadline, with the typed failure preserved end-to-end (issue #767 — `err.workflow_error_type()`/`workflow_details()`/`is_workflow_non_retryable()` all readable on the parent side).

**No new `WorkflowEvent` variant, no migration, core-only.** The race composes the existing `ChildWorkflowStarted`/`ChildWorkflowCompleted`/`ChildWorkflowFailed` events with the existing `TimerStarted`/`TimerFired` events; the winner is decided by **recorded history order** (order-stable across workers and replays), via the new `HistoryMatcher::match_child_or_timer` returning the new `ChildOrTimerMatch` enum (exported from `lib.rs`). The matcher positionally matches **both** `ChildWorkflowStarted` (capturing the `child_id`) and `TimerStarted`, then forward-scans for the earliest-recorded resolution: a child-win consumes the stray `TimerFired` transparently; a timer-win genuinely consumes the loser child's terminal (so `has_non_lifecycle_unconsumed` stays clean) and returns a `child_already_terminal` flag used to gate the on-deadline cancel to exactly one live cycle. Reserved-signal-events machinery is untouched — child-timeout timers use a `__child_timeout:{seq}:{name}` id namespace disjoint from `__signal_timeout:`.

**Worker path (additive):** the two-phase "spawn child then arm the timer in a later batch" shape was rejected — it deadlocks if the child hangs (the parent is never woken until the child terminates, so the deadline would never arm). Instead the primitive spawns the child and arms the deadline in **one** mixed `StartChildWorkflow + StartTimer` suspension batch via a dedicated `extract_child_timeout_race` (accepts exactly one child + one timer + bookkeeping; any extra command falls through to the generic "unsupported commands" failure) and a new `persist_child_timeout_race` transaction (child new-vs-existing resolution + `ChildWorkflowStarted`, then the durable timer arm + `reschedule_task(fires_at)`, factoring shared helpers out of `persist_all_started_child_workflows`/`persist_started_timer`), plus a child-terminal **self-wake re-check** after commit so a child that reaches terminal in the park window is not missed. A new dispatch branch is inserted before the timer branch and a matching branch added to the history-cap event-count predictor. On-deadline request-cancel reuses `ctx.race()`'s existing `WorkflowCommand::CancelRaceLosers { children }` → `apply_race_loser_cancellations` (synchronously seals the awaited child and appends its terminal in the same transaction; benign no-op on replay). Per-context `child_timeout_seq` counter added to `WorkflowContext` and initialised in all three constructors.

**Composition caveats** (mirroring #476): cannot share a single suspension batch with a *new* `ScheduleActivity`/`StartChildWorkflow` — the child is spawned+raced in this call's own single mixed batch, so `tokio::join!`-ing two child-timeouts or racing a child-timeout against other new work is rejected fail-loud; the deadline default is request-cancel (no "abandon" variant — a follow-up); detached children are out of scope; and on a child-win the deadline timer is **proactively torn down** (see the post-review note below).

**Post-review hardening (Codex P2):** on a child-win (both the `ChildCompleted` and `ChildFailed` branches) the still-armed `__child_timeout:{seq}` durable timer is now proactively torn down via a `WorkflowCommand::CancelRaceLosers { timers: [...] }` bookkeeping command (`queue::delete_pending_timer`), mirroring `ctx.race()`'s `race_timer_signal_impl` signal-won branch. Left armed, the unfired `harvest_timers` row (`fired = false`) is treated as an in-flight dependency by `retention::has_inflight_dependencies`, which would **pin the terminal parent forever** (retention never collects it). The delete appends **no event**, so pushing it on every replay cycle (not just the first) is strict-replay-safe — the executor's completion-time drain-command check already excludes `CancelRaceLosers` from the "new commands beyond recorded history" divergence check, so the child-win replayer fixture still reports `ReplaySucceeded`. Verified end-to-end by the new DB e2e `child_win_tears_down_deadline_timer_no_retention_pin` (child completes → parent COMPLETED → no unfired `__child_timeout:` row remains) and the updated context unit tests (child-completed / child-failed both assert exactly one `CancelRaceLosers` targeting the race timer). **Follow-up:** `wait_for_signal_timeout` has the same latent retention leak on signal-win (its timer is still left armed) — tracked separately, out of scope for this PR.

`WorkflowTestEnv` exercises both branches deterministically without real sleeping (a resolving child mock → child branch; omitting it auto-fires the deadline timer). Example `examples/child_with_timeout.rs` (both branches via `WorkflowTestEnv`). Tests: `match_child_or_timer` matcher unit tests in `replay.rs` (child-win / timer-win / `child_already_terminal` / typed-child-failure / diverged / in-progress / interleaved-sibling transparency), context unit tests in `context.rs`, `extract_child_timeout_race`/predictor unit tests in `worker.rs`, `WorkflowReplayer` fixtures in `tests/integration/replayer_tests.rs` (incl. 1,000 randomized child-vs-timer orderings, parallel to #476), `WorkflowTestEnv` harness tests, and Docker-backed DB e2e (`tests/integration/child_timeout_tests.rs`: child completes before deadline → `Some`; child hangs → `None` + child sealed `CANCELLED`; child fails → typed `Err`).
