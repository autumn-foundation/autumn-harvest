## Phase 3.51 — Child-or-deadline waits for bounded sub-orchestrations (issue #779)

`WorkflowContext::execute_child_workflow_timeout::<O>(info, input, timeout) -> HarvestResult<Option<O>>` (typed) and the untyped sibling `spawn_child_workflow_timeout(name, input, timeout) -> HarvestResult<Option<Value>>` bound a **child-workflow** await with a durable deadline — the primitive for a sub-orchestration that must not run past an SLA. It mirrors `receive_signal_timeout` (#476) one level up: instead of racing a signal against a timer, it races a child workflow's terminal outcome against a timer. `Ok(Some(output))` = child terminal **success** before the deadline; `Ok(None)` = deadline fired first (the still-running child is **request-cancelled**); `Err(_)` = child **failure** before the deadline, with the typed failure preserved end-to-end (issue #767 — `err.workflow_error_type()`/`workflow_details()`/`is_workflow_non_retryable()` all readable on the parent side).

**No new `WorkflowEvent` variant, no migration, core-only.** The race composes the existing `ChildWorkflowStarted`/`ChildWorkflowCompleted`/`ChildWorkflowFailed` events with the existing `TimerStarted`/`TimerFired` events; the winner is decided by **recorded history order** (order-stable across workers and replays), via the new `HistoryMatcher::match_child_or_timer` returning the new `ChildOrTimerMatch` enum (exported from `lib.rs`). The matcher positionally matches **both** `ChildWorkflowStarted` (capturing the `child_id`) and `TimerStarted`, then forward-scans for the earliest-recorded resolution: a child-win consumes the stray `TimerFired` transparently; a timer-win genuinely consumes the loser child's terminal (so `has_non_lifecycle_unconsumed` stays clean) and returns a `child_already_terminal` flag used to gate the on-deadline cancel to exactly one live cycle. Reserved-signal-events machinery is untouched — child-timeout timers use a `__child_timeout:{seq}:{name}` id namespace disjoint from `__signal_timeout:`.

**Worker path (additive):** the two-phase "spawn child then arm the timer in a later batch" shape was rejected — it deadlocks if the child hangs (the parent is never woken until the child terminates, so the deadline would never arm). Instead the primitive spawns the child and arms the deadline in **one** mixed `StartChildWorkflow + StartTimer` suspension batch via a dedicated `extract_child_timeout_race` (accepts exactly one child + one timer + bookkeeping; any extra command falls through to the generic "unsupported commands" failure) and a new `persist_child_timeout_race` transaction (child new-vs-existing resolution + `ChildWorkflowStarted`, then the durable timer arm + `reschedule_task(fires_at)`, factoring shared helpers out of `persist_all_started_child_workflows`/`persist_started_timer`), plus a child-terminal **self-wake re-check** after commit so a child that reaches terminal in the park window is not missed. A new dispatch branch is inserted before the timer branch and a matching branch added to the history-cap event-count predictor. On-deadline request-cancel reuses `ctx.race()`'s existing `WorkflowCommand::CancelRaceLosers { children }` → `apply_race_loser_cancellations` (synchronously seals the awaited child and appends its terminal in the same transaction; benign no-op on replay). Per-context `child_timeout_seq` counter added to `WorkflowContext` and initialised in all three constructors.

**Composition caveats** (mirroring #476): cannot share a single suspension batch with a *new* `ScheduleActivity`/`StartChildWorkflow` — the child is spawned+raced in this call's own single mixed batch, so `tokio::join!`-ing two child-timeouts or racing a child-timeout against other new work is rejected fail-loud; the deadline default is request-cancel (no "abandon" variant — a follow-up); detached children are out of scope; and on a child-win the deadline timer is **proactively torn down** (see the post-review note below).

**Post-review hardening (Codex P2):** on a child-win (both the `ChildCompleted` and `ChildFailed` branches) the still-armed `__child_timeout:{seq}` durable timer is now proactively torn down via a `WorkflowCommand::CancelRaceLosers { timers: [...] }` bookkeeping command (`queue::delete_pending_timer`), mirroring `ctx.race()`'s `race_timer_signal_impl` signal-won branch. Left armed, the unfired `harvest_timers` row (`fired = false`) is treated as an in-flight dependency by `retention::has_inflight_dependencies`, which would **pin the terminal parent forever** (retention never collects it). The delete appends **no event**, so pushing it on every replay cycle (not just the first) is strict-replay-safe — the executor's completion-time drain-command check already excludes `CancelRaceLosers` from the "new commands beyond recorded history" divergence check, so the child-win replayer fixture still reports `ReplaySucceeded`. Verified end-to-end by the new DB e2e `child_win_tears_down_deadline_timer_no_retention_pin` (child completes → parent COMPLETED → no unfired `__child_timeout:` row remains) and the updated context unit tests (child-completed / child-failed both assert exactly one `CancelRaceLosers` targeting the race timer). **Follow-up:** `wait_for_signal_timeout` has the same latent retention leak on signal-win (its timer is still left armed) — tracked separately, out of scope for this PR.

**Post-review hardening (Codex P1) — order a due deadline ahead of an out-of-band child terminal:** a child that completes/fails **after** its deadline appends its terminal to the parent history out-of-band (via `wake_parent_for_child_completion`/`wake_parent_for_child_failure`), while the deadline `TimerFired` was otherwise only ingested at parent claim (`ingest_due_timers_and_signals`). If the parent was claimed late, the child terminal landed in history *before* the overdue `TimerFired`, so the pure recorded-order `match_child_or_timer` declared the child the winner and the primitive returned `Some`/`Err` instead of `None` — even though the deadline genuinely elapsed first (confirmed reproduced against real Postgres 16). Fixed in the wake path: a new `worker::materialize_due_child_timeout_deadlines(conn, parent_exec_id)` materializes every currently-due `__child_timeout:` deadline as a `TimerFired` event **before** the child terminal is appended, in **both** wake functions, so the recorded order becomes `[.., TimerFired, ChildWorkflowCompleted|ChildWorkflowFailed]` and the race resolves to the timeout branch (`None`) — restoring the #476 "deadline reached ⇒ deadline won regardless of when the parent is claimed" guarantee for the child case. Correlation to the completing child is deliberately not required (this child's own due deadline lands before its terminal; an unrelated sibling race's due deadline landing early is resolved by that race's own scan). Scope is strictly the escaped-LIKE `\_\_child\_timeout:%` prefix, so unrelated `ctx.timer()` rows are never fired or reordered, and a child with no due deadline (plain child-await, or a child that beat its deadline) materializes nothing — **byte-identical** to the pre-fix wake path. Double-fire vs the parent-claim ingest is prevented by selecting the due rows `FOR UPDATE` (EvalPlanQual re-evaluates `fired = false` against the latest committed version, so a deadline already fired-and-committed by ingest is excluded, and a deadline this path fires blocks ingest's `SET fired = true` until the wake transaction commits). **No new `WorkflowEvent` variant, no migration, no change to `match_child_or_timer` or `ingest_due_timers_and_signals` — the fix is contained to the child-wake path.** `match_child_or_timer`'s existing timer-win branch already consumes a loser child terminal recorded after the fire (via `consume_loser_child_terminal`, which handles both `ChildWorkflowCompleted` and `ChildWorkflowFailed`) and reports `child_already_terminal`, so no cancel command is pushed for the already-sealed loser. Tests, red→green (red confirmed by temporarily disabling the fix — the ordering assertion fails and the primitive returns `Some`): DB e2e `over_deadline_child_completion_orders_deadline_first_and_resolves_none` + `over_deadline_child_failure_orders_deadline_first_and_resolves_none` (drive the REAL doc-hidden-`pub` wake functions over a hand-built overdue-timer prefix, assert the `[TimerFired, terminal]` history order + `None`), the focused helper test `materialize_due_child_timeout_deadlines_fires_only_due_child_timeout_timers` (fires exactly the due `__child_timeout` timer, leaves a not-yet-due one alone, ignores a due non-`__child_timeout` timer), and two context replay-determinism unit tests (`..._over_deadline_completion_loser_is_none`/`..._over_deadline_failure_loser_is_none` — the post-fix `[TimerFired, loser-terminal]` order resolves to `None` across 3 independent replay cycles). Verified green against a real local Postgres 16 (Docker/testcontainers unavailable in the implementing sandbox); Docker-run in CI.

**Post-review hardening (Codex P2) — preserve the canary-at-frontier exception for in-flight replay:** the deploy replay canary (`run_workflow_canary`) samples still-running executions and expects a workflow parked at the recorded-history frontier to *suspend* → `ReplaySucceeded`. A workflow parked on `spawn_child_workflow_timeout` replays to `ChildOrTimerMatch::InProgress` at the frontier (the `ChildWorkflowStarted`/`TimerStarted` pair is recorded, but neither resolution is), and the primitive's `InProgress` arm unconditionally reported non-determinism whenever `strict_replay` was set — so healthy in-flight child-timeout workflows surfaced as *false* canary failures and could block deploy verification. Fixed by mirroring `check_strict_replay_no_match`'s existing canary-at-end exception exactly in the `InProgress` arm: the hard error is now suppressed only when `self.canary_mode && position >= len` (the recorded-history frontier), letting the arm fall through to re-park (which suspends). Genuine-divergence detection is untouched — a real code-vs-history divergence resolves as `ChildOrTimerMatch::Diverged` (a different arm that always nd-errors, never canary-excepted), and strict `WorkflowReplayer` runs (non-canary) still treat an unresolved race as a fixture problem. Contained to the context suspend branch: `match_child_or_timer`, `ingest_due_timers_and_signals`, `merge_wake_events`, and the Codex-P1 wake-path fix are all untouched; no new event variant, no migration. Tests, red→green (red confirmed as the exact `NonDeterminismDetected(expected="ChildOrTimerResolved", actual="ChildOrTimerInProgress")` at the frontier): the money test `child_timeout_in_flight_canary_replays_succeeded` (in-flight history in canary → `ReplaySucceeded`) plus two mandatory guards — `child_timeout_in_flight_strict_still_reports_nondeterminism` (same history in strict/non-canary → still non-determinism, the exception must not weaken strict) and `child_timeout_genuine_divergence_still_detected_in_canary` (a child-input mismatch replayed in canary → still non-determinism, the exception must not mask real divergence) — all in `tests/integration/replayer_tests.rs`. **Note:** `wait_for_signal_timeout` (#476) has the same latent behavior in its own `InProgress`/strict arm; left untouched here (a separate, shipped feature) and tracked as a follow-up. Verified via the no-DB `--features testing` replayer suites (Docker/testcontainers for the DB child_timeout suite unavailable in the implementing sandbox; the fix is pure replay and touches no worker/DB path).

`WorkflowTestEnv` exercises both branches deterministically without real sleeping (a resolving child mock → child branch; omitting it auto-fires the deadline timer).
