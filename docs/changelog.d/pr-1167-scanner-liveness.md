## Phase 3.x — Scanner liveness heartbeats: detect a wedged control loop (issue #797)

**Implemented.** Harvest's correctness in production depends on a fleet of background control loops running as bare spawned Tokio tasks inside the worker/plugin process: timeout enforcement, the soft-SLA scanner, the poison-pill orphan reclaimer, the external signal/cancel/await outboxes, the retention janitor, the schedule ticker, and the bounded-pause auto-resumer. If one of them panics, deadlocks on a poisoned connection, or stalls on a never-returning query, it fails **silently** — and the operator only learns about it when a downstream correctness symptom surfaces minutes to hours later (a workflow that should have timed out but didn't, an SLA that never fired, a DLQ that never filled).

**Why the existing metrics could not catch this.** Every pre-existing loop metric emits **only when there is work to do** — `harvest.retention.deleted` counts deletions, `harvest.schedule.fire_attempts` counts fires, the timeout/SLA/quarantine counters count enforcements. So a healthy idle loop and a wedged loop both emit *zero*: indistinguishable. That is the exact gap this slice closes.

**Two halves, one choke point.** New core module `scanner_health.rs` exposes a single call, `record_scanner_tick(metrics, owner)`, which drives **both**:

1. a monotonic `harvest.scanner.tick` counter (`METRIC_SCANNER_TICK`), emitted **unconditionally on every loop iteration** — including a no-work pass, an enforcement error, and a failed DB-connection checkout — so a flat-lined counter *is* the wedge signal; and
2. an in-process last-tick registry (`ScannerLiveness`) whose staleness verdict is surfaced by a new `scanner_liveness` check in `GET /admin/preflight`.

Because one call drives both, a call site can never emit the counter without the timestamp (or vice versa). **The timestamp is bumped unconditionally, before the recorder call**, so the health check keeps working on a deployment that has configured no metrics recorder at all (proven by `record_scanner_tick_bumps_liveness_even_with_a_noop_recorder`).

**Bounded label by construction.** The `scanner` label is a closed `Scanner` enum (`timeout`, `sla`, `poison_pill`, `external_outbox`, `retention`, `schedule`, `pause_auto_resume`) rather than a free string, mirroring `SlotType`/`TunerDecision`: per ADR-0001 §7 a metric label must have bounded cardinality, and an enum makes that true *by construction* rather than by convention. `execution.id` is never a label.

**Seven labels, five loops — and an honest shared fate.** `sla` and `external_outbox` are enforcement responsibilities *inside* the timeout loop, not separately spawned tasks. They are registered and ticked **by that loop**, alongside `timeout`, so the three share one liveness fate and cannot diverge. That is deliberate: a tick placed mid-pass (inside `enforce_timeouts_once`) would sit behind a `?` and be **skipped on a transient DB error**, giving a flat-lined counter two possible meanings — "the loop is wedged" and "a query failed" — which destroys the one property the signal exists to have. It also keeps liveness bookkeeping out of a `pub` primitive that ~40 tests and embedders drive by hand (a hand-driven call would otherwise fabricate a scanner the process is not running, which would then age into `Wedged` and report a phantom outage — pinned by `enforce_timeouts_once_records_no_scanner_ticks`). The three keep distinct labels because the issue's bounded set names them and because they name distinct responsibilities; attributing a *partial* pass failure to a specific sub-pass is the job of that pass's own work counters and its `tracing::error!`, not of a liveness heartbeat.

**Staleness policy — and how the success metric actually holds.** `staleness_threshold(poll_interval) = max(2 × poll_interval, 60s)`. `classify_scanner` maps age → `Healthy` / `Stale` (≥ 1 threshold → `warn`) / `Wedged` (≥ 2 thresholds → `fail`). The issue's success metric ("detect a wedged loop within ≤ 2× its poll interval") is satisfied for **every** shipped loop, but by two different mechanisms, and the distinction matters to an operator sizing a window: a loop polling **at or above 30 s** (the hourly retention janitor) is bounded by the `2×` multiplier, so detection latency is literally `2 × poll_interval` (2 h); a loop polling **faster than 30 s** (the other six, at 500 ms–5 s) is bounded by the 60 s floor, so its detection is *far better in absolute terms* (60 s, not hours) but *worse as a multiple* of its interval. The floor is deliberate, and the reason is that a loop's **iteration period is not its poll interval**: each pass sleeps the interval and *then* does real work — the timeout checker calls `pool.get().await` (deadpool waits for a free connection, by default with no timeout at all) and then runs a multi-query enforcement pass — so under a saturated pool or a slow query a perfectly healthy 500 ms loop legitimately takes seconds per iteration, and a 1 s threshold would report `stale` continuously on a busy-but-working system. The cost asymmetry settles it: this verdict feeds `GET /admin/preflight`, and the CLI exits `2` on `warn`, so a false `warn` **breaks a deploy pipeline** — strictly worse than 60 s of detection latency. `success_metric_detection_bound_holds_for_every_shipped_interval` pins this against the **real shipped constants** rather than a convenient 30 s example, and asserts explicitly that a 500 ms loop is detected in 60 s (the floor), *not* in 1 s — so the metric is not over-claimed and a future change to a poll interval surfaces there. `the_floor_tolerates_a_slow_but_healthy_iteration` guards the deviation in the other direction, so the floor cannot be quietly shrunk toward a literal `2×` into flapping territory.

**Register-on-spawn is what avoids boot false positives.** Each loop registers itself with its poll interval *before* its first iteration, receiving a `ScannerOwner` handle it ticks for the rest of its life. One mechanism thereby supplies three things: the *expected* scanner set (so an API-only replica reports an empty snapshot rather than seven phantom wedged scanners), the boot grace window (a just-registered loop is `Healthy` until its first threshold elapses, even before its first tick), and the per-scanner threshold. `OwnerState::reference()` returns `max(last_tick, registered_at)` so a fresh registration re-grants grace to *that instance* without discarding its observed history.

Registration also **initializes the tick series at zero** (`MetricsRecorder::record_scanner_registered`, bridged as an `increment(0)` on the *same* `harvest.scanner.tick` counter key). Without it the metric half of the feature had a silent hole the health-check half never did: a loop that panics or hangs on its **first** iteration never reaches a tick, so no series is ever created — and `rate(harvest_scanner_tick_total{...}[5m]) == 0` only evaluates series that *exist*, so the paging alert would stay silent forever for exactly the failure it exists to catch. (`absent()` is deliberately not used as a substitute: an API-only replica legitimately exports no series and would page falsely forever.) The health check was always correct here, because registration precedes the first iteration and `reference()` falls back to `registered_at`, so such a loop ages into `Stale`/`Wedged` with `has_ticked: false`. The one cost lands on the hourly retention janitor: the series now exists from process start, so `increase(...[3h]) == 0` reads zero throughout hour 0–1 of a fresh process — and Prometheus evaluates `increase()` over a **partial** window, so two scrapes are enough to page through every healthy startup. (A pre-existing flap that merely shifts earlier: before this, a series first appearing at a constant `1` made `increase` zero during hour 1–2 anyway.) The alert pack's schema carries no `for:` field, so the hold is encoded in the expression: the retention arm ANDs on `max_over_time(harvest_scanner_tick_total{scanner="retention"}[3h]) > 0`, gating on the counter having reached a nonzero value in the same window, which needs neither `process_start_time_seconds` (not exported) nor any assumption about scrape interval. The gate is a **function result rather than a bare selector** for a load-bearing PromQL reason: set operators match on the *full* label set including `__name__`, and `increase()` drops `__name__` while a bare selector keeps it — so `increase(...) == 0 and harvest_scanner_tick_total{...} > 0` would match no series and *silently disable the alert*. Both sides being functions over the same selector and window keeps their label sets identical; the test asserts the gate is not a bare selector, so that trap cannot be reintroduced. The cost of *that* is symmetric and stated in the notes: a retention loop wedging before its **first** tick is invisible to the alert — unavoidable from the counter alone, since during the startup hour it is indistinguishable from a healthy sleeping janitor — and is covered instead by `scanner_liveness`, which knows the registration timestamp and flags a never-ticked retention loop once 2 h elapse. The sub-minute arm deliberately carries **no** such gate: those loops tick within seconds of registration, so there is no startup window to ride out, and gating them would blind the alert to exactly the first-iteration wedge that initializing the series at zero exists to catch (`scanner_stalled_retention_expression_cannot_fire_during_the_startup_hour` pins both halves). The gate needs **no** `resets()`- or uptime-scoped term on top, and that is worth stating because the omission looks like an oversight: on a restart that preserves the label set the counter resets to zero, but `increase()` is reset-*aware* — it computes `last - first + correction`, adding the pre-reset value back at each reset — so a healthy janitor that ticked at least once before the restart reads `increase > 0` (`3,4,5,reset,0,0 → 0 - 3 + 5 = 2`), the `== 0` side fails, and the rule cannot fire at all; the gate is never even consulted. The only post-restart shape that fires is one whose pre-restart samples were **flat** (`5,5,5,reset,0,0 → 0`), i.e. the janitor had already been stalled for the whole window and the rule was already correctly firing — it merely continues for at most one more hour until the new process proves liveness. Adding `unless resets(...[3h]) > 0` would instead blind the alert for a full window after **every** deploy, hiding a genuine post-restart wedge, so the same test also pins the absence of a `resets()` term and the presence of the reasoning in `prometheus.notes`.

**Per-instance tracking is what stops a healthy peer masking a wedged one.** A `Scanner` label can cover **more than one loop instance** in one process: a multi-shard worker spawns a timeout checker, poison-pill reclaimer, and pause auto-resumer **per assigned shard**, and two runtimes can share a process. The registry therefore keys on the instance, not the label, and the health check **classifies each instance against its own registered poll interval, then keeps the instance with the worst verdict** — reporting that one instance's `poll_interval`, `age`, and `last_tick_at` (plus the **sum** of tick counts, matching the counter). So the single-status-per-scanner payload is unchanged while three healthy shards can no longer hide the fourth's panicked loop (`a_wedged_instance_is_not_masked_by_a_healthy_peer`).

Folding `age` and `poll_interval` *independently* — worst age, most lenient interval — is the subtle trap here, and it silently launders a genuine outage: two runtimes in one process may register the same scanner at different cadences, and a 30 s loop silent for 200 s (`Wedged` by its own configuration) reads `Healthy` when measured against an hourly sibling's 7200 s threshold. Every field in the folded status therefore describes **one** instance, so `classify_scanner(&status)` reproduces the folded verdict exactly (`a_wedged_instance_is_not_laundered_by_a_lenient_siblings_interval`, `a_folded_status_reclassifies_to_the_worst_per_instance_verdict`). Per-instance classification also removes the need for the lenient-interval workaround it replaces: a slow poller is protected because it is judged on its own threshold, not because everyone else inherits it (`a_slow_healthy_poller_is_not_falsely_stale_next_to_a_fast_sibling`). The amplifier is fixed too: a *newly registered* peer's boot grace no longer launders an already-wedged sibling (`a_freshly_registered_peer_does_not_regrant_grace_to_a_wedged_sibling`), and a retired slow instance leaves no sticky interval behind.

**A *graceful* stop deregisters.** A clean loop exit releases its own handle; the scanner leaves the expected set only when its **last** instance deregisters, so a process running two workers keeps reporting the surviving one. This is what stops a process that drains its worker while continuing to serve HTTP from reporting `fail` forever. Deliberately placed **after** the loop rather than in a drop guard: a panic unwinds past that point, so a **panicked loop stays registered and correctly ages into `Wedged`** — precisely the signal this feature exists to produce. Ids are never reused, so a straggling tick from a retired handle can neither resurrect it nor refresh a live peer's clock, and a repeated `deregister` is a no-op that cannot evict a live instance.

Deregistration is **in-process only**, and that asymmetry is documented rather than hidden: a Prometheus counter cannot be un-exported, so a deliberately drained loop's series stays at its final value and reads `rate() == 0` forever. The `scanner_liveness` check is unaffected (it knows what is registered). For the metric, a process that *exits* after draining takes its scrape target with it and the alert resolves itself; a process that keeps serving HTTP after draining needs the alert gated on it still owning worker duties. The runbook and the shipped rule's `prometheus.notes` now carry a concrete expression for that (`and on(instance) (count by (instance) (harvest_worker_slots_available) > 0)` — the worker's own sampler stops when it drains but keeps reporting while a scanner is merely wedged), which also covers the narrow case of a process that registers its loops and drains before any first tick.

**The check has to survive the failure it reports on.** `build_preflight_report` awaited its database-dependent checks inline, and every one of them starts with `pool.get().await` — which deadpool serves with no wait timeout by default. So an **exhausted pool** blocked `GET /admin/preflight` forever, and the report never reached the operator. That is precisely backwards for this feature: pool exhaustion is one of the listed causes of a wedged control loop, so the one diagnostic that would *name* the stalled loop was suppressed by the very condition it exists to report. The five DB checks are now evaluated as a group under a generous `DB_CHECK_BUDGET` (30 s), with the six in-memory checks — `scanner_liveness` among them — computed **before** anything can block and always present in the report. On the happy path the checks returned are identical, and in the same order, as before; on a stall the report still returns, carrying every in-memory verdict plus a `db_checks` `fail` whose remediation routes the reader to the `scanner_liveness` entry beside it. A hang becomes an actionable answer.

**Operator surface.** The `scanner_liveness` preflight check folds worst-of across all registered scanners and names the stale ones in both its summary and its `details` payload (`scanners_registered`, `stale_scanners`, and per-scanner `verdict` / `shard` / `tick_count` / `has_ticked` / `age_secs` / `poll_interval_secs` / `staleness_threshold_secs` / `last_tick_at`), with remediation pointing at the runbook. Because it participates in the overall preflight verdict and the CLI exits `2` on `warn` / `1` on `fail`, a stale scanner **blocks a pipeline that gates on `harvest preflight`** — intended, and now documented in the runbook. Starter alert `harvest_scanner_stalled` added to `docs/alerts/starter-pack-v0.1.0.json` with a full five-subsection runbook section in `docs/runbooks/harvest-alerts.md` (including the label → loop mapping table), a new dashboard row in `docs/dashboards/starter-pack-v0.1.0.json`, and catalogue rows in ADR-0001 §7 and `docs/telemetry.md`.

**The alert windows are per-cadence, not uniform — and deliberately not `sum by (scanner)`.** The loops do not share a poll interval: six are sub-minute (timeout/sla/external_outbox 500 ms, schedule 1 s, poison_pill/pause_auto_resume 5 s) but the **retention janitor polls hourly by default**. A single 5-minute window — the obvious first cut — would therefore page *continuously* on a perfectly healthy retention loop, which trains operators to silence the rule the runbook tells them never to silence. The shipped rule carries two expressions instead: a 5 m window for `{scanner!="retention"}` and a 3 h window for `{scanner="retention"}`. Neither aggregates with `sum by (scanner)`: **every replica runs its own copy of all seven loops**, so summing across instances would let two healthy replicas mask a third's wedged loop — the scrape target's own `instance` label is what names the affected process. Both dashboard panels group by `(scanner, instance)` for the same reason.

The same cadence asymmetry sizes the dashboard's low-frequency panel. Its window must be **longer than the slowest loop's cadence**, or the panel is false exactly where it is authoritative: at any window under an hour a perfectly healthy janitor contributes zero increments to most evaluations, so the panel alternates to zero on its own while its own description says a line at zero means wedged — and the rate panel beside it points operators there specifically because retention is illegible at a short `$__rate_interval`. It is therefore a 3 h window (matching the alert), on a **log axis**, because a 500 ms loop contributes ~21,600 ticks over that span against the janitor's ~3 and a linear scale would flatten retention back onto zero. `low_frequency_scanner_panel_window_outlasts_the_retention_cadence` pins the window against the cadence so a future "tighten the window" pass cannot silently reintroduce the false reading.

**One documented blind spot, stated rather than papered over.** The registry is **per process**: pointed at an API-only replica the check reports `scanners_registered: 0` and `pass`, which is correct for *that* process and says nothing about the worker — the runbook's triage step now says so and routes you via the metric first.

The *metric* carries a bounded **`shard` label** for the same reason the registry keys on the instance: without it every per-shard loop instance would increment one series on one scrape target, so a healthy shard's ticks would hold `rate(...) > 0` while a sibling's loop was dead and the paging alert would **never fire**. That is *masking*, not merely a lost localisation — the alert exists precisely to catch a wedged loop, and on a multi-shard worker it would silently not. The label value is the shard id, or the `SCANNER_SHARD_LABEL_NONE` sentinel (`"none"`) for the process-wide `retention`/`schedule` loops and single-shard deployments, so the series family has a uniform label set rather than a sometimes-present dimension. Cardinality stays bounded (shard count is operator-configured and small), matching the existing `shard`-labelled `harvest.dlq.entries` and `harvest.shard.stranded_pending`. The health check carries the shard too, all the way to the payload: the `ShardId` is already in hand where the per-shard loops are spawned (`shard_pools_for_monitors` is built by mapping over `shard_assignments`, then discarding the id), so it is carried into registration, stored per instance, folded through with the worst instance, and surfaced both in the summary (`1 of 5 background control loops are stale: timeout (shard 1)`) and as a `shard` field on the per-scanner entry. Without it the check could say a timeout checker had died but not **which database was left unprotected** — while both the dashboard panel and the alert notes send operators here for exactly that. **Every** stale instance's shard populates the **standard `affected_shards` contract field** every preflight check shares — the field the CLI's SCOPE column derives from exclusively — so `harvest preflight` renders `shards=1,2` rather than `-`. All of them, not just the worst one's: the worst-instance fold is right for the *verdict* (one verdict per scanner, reproducible from the folded status) and wrong for the *blast radius*, since reporting only the worse of two wedged shards sends an operator to one database while the other stays equally unprotected. `ScannerStatus::stale_shards` carries them through the fold; it lists only the stale instances, so a healthy sibling shard is never reported as affected. `shard` is `null` (and `affected_shards` empty) for the process-wide loops (`retention`, `schedule`) and on single-shard deployments, and `stale_scanners` deliberately stays a list of bare scanner names so it remains a stable machine-readable field. Proven end to end through a **real spawner** (`spawned_poison_pill_reclaimer_registers_ticks_and_deregisters` asserts the shard reaches the global snapshot), not only through a hand-built registry.

**A duplicate `shard_assignments` entry is deduplicated at the config boundary** (`builder::dedup_shard_assignments`, applied by both `WorkerConfig::with_shard_assignments` and the `WorkerConfig -> WorkerRuntimeConfig` conversion — the latter because `shard_assignments` is a `pub` field an embedder can set directly, and the conversion is the single choke point every worker's config passes through on its way to the per-shard monitor fan-out). This is a root-cause fix, not a metrics workaround: the worker fans its per-shard control loops out over the assignment list one-to-one, so `[0, 0]` previously spawned **two** timeout checkers, **two** poison-pill reclaimers, and **two** pause auto-resumers against the *same* database — doubling enforcement passes, connection pressure, and DB load for no added coverage, since each pair scans identical rows. It also collapsed those instances onto one `(scanner, shard)` tick series, so a healthy duplicate would mask its wedged twin. First-occurrence order is preserved rather than sorted, so a deliberate polling order stays intact.

**Scanner liveness is sampled *after* the bounded DB group, not before it.** It is the one in-memory check whose answer *ages* — a pure function of wall-clock time since each loop's last tick — so sampling it before a wait that can legitimately consume the full `DB_CHECK_BUDGET` (30 s) would let a loop cross its staleness threshold *during* that wait and still be reported healthy in a report whose `observed_at` is stamped afterwards. That is most likely under pool exhaustion, which is both a listed cause of a wedged loop and the reason the DB group is slow, so the two co-occur precisely when the answer matters. Moving the sample does **not** weaken the anti-suppression guarantee that put it outside the DB group in the first place: `check_scanner_liveness` is synchronous and touches no pool, and `tokio::time::timeout` always returns within its budget, so the sample is reached whether the DB checks completed, errored, or timed out. The other five in-memory checks read configuration or registry state that does not age during the wait and stay up front. Guarded by `scanner_liveness_is_sampled_after_the_bounded_db_group`, a source-scan assertion in the style of the existing `scanner_liveness_tests.rs` anti-drift scan — a timing test is not available here, since the staleness floor is 60 s and the registry reads `std::time::Instant`, which tokio's paused clock does not virtualize.

**Both scanner dashboard panels render `shard` in their legends.** They group by `(scanner, instance, shard)`, but legended only `{{scanner}} @ {{instance}}`, so two shards drew under the same name — the series were separate while the legend and tooltip still could not say which shard had stalled, defeating the point of the dimension. Now `{{scanner}} shard={{shard}} @ {{instance}}`. Guarded by `scanner_panel_legends_render_every_grouped_dimension` in `dashboard_pack_docs.rs`, which asserts the general property (every dimension a scanner panel groups by must appear in its legend) rather than the literal string, so it also catches a future panel that adds a grouping key without legending it.

**Residual, documented rather than papered over: two runtimes on one shard in one process.** `(instance, scanner, shard)` separates every instance the deployment shapes Harvest supports actually produce — one worker process per shard, or one multi-shard worker — but it does **not** separate two *independently constructed* runtimes (two `Worker`s, or two `RetentionRuntime`s) polling the **same** shard inside one process; their ticks share a series, so a healthy one holds `rate(...) > 0` after its peer wedges. A per-owner metric label was rejected rather than overlooked: registry owner ids are monotonic and never reused, so labelling by them would grow without bound in any process that restarts a runtime — an ADR-0001 §7 violation, and a worse bug than the one it would fix. A separate "worst registered owner" gauge was likewise rejected, since exporting it needs its own sampler loop, which is another background loop carrying the very wedge risk this feature exists to detect. The capability is not absent, only on a different surface: the registry tracks those owners **separately** (that is what the `ScannerOwner` ids are for), so the `scanner_liveness` check still reports the worst of them and names the affected shard — an operator running two runtimes of the same kind in one process should treat that check, not the counter, as the authority for those scanners. Stated in the module doc, the alert's `prometheus.notes`, and a dedicated runbook bullet.

**Invariants.** **No new `WorkflowEvent` variant, no `harvest_events` footprint, no migration, no replay-determinism impact, no shard-semantics change.** The registry is in-process only. `record_scanner_tick` and `record_scanner_registered` are new **additive no-op-default** methods on the public `MetricsRecorder` trait (both bridged in `metrics_rs_adapter`), so every existing downstream implementor still compiles unchanged. Detection only: auto-restart of a wedged loop, cross-replica scanner ownership/leader election, a persisted cross-process heartbeat row, and the worker poll loop itself are all explicitly out of scope per the issue.
