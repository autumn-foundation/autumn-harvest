## CI — gate `webhook_receiver_integration` and fix its `TestApp::plugin` deadlock (test-infra)

**Tooling/testing** (implemented): the Docker-gated plugin suite `autumn-harvest-plugin/tests/webhook_receiver_integration.rs` (issue #344) was absent from `.github/ci/integration-suites.txt`, so CI only *compile-checked* it — it had **zero runtime regression coverage** and was listed in the `ci_run_coverage.rs` `ALLOWLIST` as a `webhooks`-feature-gated, all-`#[ignore]`d suite that "no CI run can execute". This slice reproduces and fixes a genuine test-harness **deadlock** in 5 of its 6 tests, un-`#[ignore]`s the suite, and wires it into the manifest so it runs for real against Docker Postgres. **Test-harness change only — no production webhook code touched, no new `WorkflowEvent` variant, no migration, no route/contract change.**

**Root cause — current-thread runtime + `TestApp::plugin`.** `TestApp::plugin(HarvestPlugin)` runs the plugin startup hook on a spawned thread via `Handle::block_on` while the test thread blocks on its join; under a plain `#[tokio::test]` (single current-thread runtime) that mutual block **deadlocks**. PR #1095 (issue #740) discovered this when it added `webhook_start_records_webhook_source` and fixed *that one* test with `#[tokio::test(flavor = "multi_thread", worker_threads = 2)]` — but the 5 pre-existing tests, never actually run in CI (`#[ignore]` + no manifest row), kept the plain-`#[tokio::test]` shape and the latent deadlock.

**Red→green.** Reproduced against a live Postgres 16 (testcontainers, `--include-ignored`, 90 s per-test timeout): the 5 pre-existing tests (`duplicate_webhook_delivery_creates_exactly_one_execution_with_same_exec_id`, `duplicate_webhook_delivery_to_signals_target_delivers_signal_exactly_once`, `blank_delivery_id_is_rejected_as_missing_for_signals_target`, `upstream_idempotency_key_header_does_not_trip_throttle_mutual_exclusion_on_starts`, `distinct_deliveries_sharing_an_upstream_idempotency_key_are_not_collapsed`) all **hung/deadlocked** (killed at the timeout); `webhook_start_records_webhook_source` (already multi-thread) passed in 1.88 s. After applying the same multi-thread flavor to the 5, two consecutive serial full-suite runs were fully green: `test result: ok. 6 passed; 0 failed; 0 ignored` (4.55 s, then 2.56 s).

**Fix pattern (mirrors #1095 exactly).** Each of the 5 pre-existing tests changed from `#[tokio::test]` to `#[tokio::test(flavor = "multi_thread", worker_threads = 2)]`, with a one-line rationale comment pointing at the fuller note on `webhook_start_records_webhook_source`.

**Gating (the actual runtime-coverage enabler).** The manifest `linux` runner never passes `--include-ignored`, and `ci_run_coverage.rs::all_tests_ignored` disqualifies an all-`#[ignore]`d suite from being credited — so the `#[ignore = "requires Docker (testcontainers)"]` attribute was removed from **all 6** tests (matching every other `linux` plugin suite, e.g. `fail_now`/`timeline`, which are un-ignored and run against Docker Postgres). The file's `#![cfg(feature = "webhooks")]` gate means a plain `cargo test -p autumn-harvest-plugin` (no `webhooks` feature) still compiles it away entirely, so no default-feature developer flow is affected. Added one sorted manifest line — `linux  autumn-harvest-plugin  webhook_receiver_integration  webhooks  -` — and updated the coverage guard: dropped `webhook_receiver_integration` from the `paved_path_db_tests_are_classified_and_flagged_all_ignored` all-ignored self-test, and removed its `ALLOWLIST` entry (it is now covered by a real `linux` run). `webhook_durable_integration` and `mcp_tools_integration` stay all-ignored/allowlisted (out of scope).

**Verification.** Full local CI mirror green: `cargo fmt --all -- --check` (1.97.0), `cargo clippy -p autumn-harvest --all-features --tests -- -D warnings` (covers `ci_run_coverage.rs`), `cargo clippy -p autumn-harvest-plugin --all-targets --features webhooks -- -D warnings` (covers the webhook suite), MSRV `cargo +1.88.0 check --workspace`, and the 13-test `ci_run_coverage` guard (all green, including `manifest_is_sorted_and_unique` and `every_db_gated_test_has_a_ci_run_step_or_is_allowlisted`).
