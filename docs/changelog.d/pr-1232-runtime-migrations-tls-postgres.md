## Fix `ensure_runtime_migrations` panicking on a TLS-enabled Postgres database URL

**Bug fix** (implemented): the plugin's startup migration step (`autumn-harvest-plugin::plugin::ensure_runtime_migrations`, invoked from the `on_startup` hook's `start_harvest_runtime`) panicked unconditionally — before any network I/O — whenever the configured `DATABASE_URL` requested TLS (`sslmode=require`/`verify-ca`/`verify-full`), crashing the process on boot with `"Cannot start a runtime from within a runtime"`. A plaintext or `sslmode=disable`/`prefer` URL was unaffected.

**Root cause.** `ensure_runtime_migrations` was a plain synchronous `fn`, called with no `spawn_blocking` wrapper from `start_harvest_runtime` — an `async fn` invoked via `.await` from the `on_startup` hook, i.e. from a thread that is already actively driving the Tokio runtime's async tasks. It delegates to `autumn_web::migrate`, which selects a migration-connection strategy per `sslmode`: a plaintext/`disable`/`prefer` URL takes the synchronous libpq `PgConnection::establish` path (safe from any thread); a TLS-requesting URL routes through `establish_migration_connection`'s rustls arm, which calls `tokio::runtime::Handle::try_current()` — succeeding by reusing the *same* ambient runtime handle — and then `handle.block_on(tls::establish(..))`. Tokio forbids nesting `block_on` on a thread already driving that runtime's own tasks and panics immediately with `"Cannot start a runtime from within a runtime. This happens because a function (like `block_on`) attempted to block the current thread while the thread is being used to drive asynchronous tasks."` — before any connection attempt completes, so the failure is deterministic and unrelated to network reachability. `establish_migration_connection`'s own doc comment states this precisely: *"Never call from an async executor thread ... Sync contexts (the CLI) and `spawn_blocking` tasks (the startup migration path) are both fine."*

**Fix.** `ensure_runtime_migrations` is now an `async fn` that clones its (already-cheap, already-owned) inputs and runs the unchanged synchronous body — renamed `ensure_runtime_migrations_blocking` — inside `tokio::task::spawn_blocking`, awaiting the join handle and mapping both a task panic/cancellation (`JoinError`) and the inner `Result` to the existing error type. `spawn_blocking` moves the closure to a dedicated blocking-thread-pool thread that is *not* marked as actively driving the runtime's scheduler, so the nested `Handle::block_on` inside `establish_migration_connection` is explicitly sound there — exactly the sanctioned pattern the doc comment above calls out, and the same pattern already used elsewhere in this codebase (`autumn-harvest::worker` wraps a similar nested-`block_on` WASM-activity invocation the same way) and in `autumn-web`'s own internal startup-migration sequence. The single call site was updated from `ensure_runtime_migrations(..)?` to `ensure_runtime_migrations(..).await?`.

**No new `WorkflowEvent` variant, no migration, no route/contract change, no replay/determinism impact** — this is a pure runtime-startup bug fix confined to `autumn-harvest-plugin`.

**Tests.** Two new unit tests in `autumn-harvest-plugin/src/plugin.rs` reproduce the hazard hermetically — no real TLS-enabled Postgres server is needed. A URL like `postgres://user:pass@127.0.0.1:1/harvest?sslmode=require` selects the TLS/rustls migration-connection path (port 1 is essentially never bound, so the connection is refused near-instantly), and the panic occurs before any connection attempt, so the fixture is deterministic:
- `ensure_runtime_migrations_blocking_panics_if_called_directly_from_an_async_task` (`#[should_panic]`, driven from a `#[tokio::test]`) calls the renamed synchronous function directly from an async-task context and asserts it panics — proving the reproduction fixture genuinely exercises the reported hazard (the fixture's backtrace confirms the panic originates inside `establish_migration_connection`'s `handle.block_on` call and propagates through Tokio's `current_thread::CoreGuard::block_on` internals, matching the mechanism described above).
- `ensure_runtime_migrations_does_not_panic_on_a_tls_requiring_database_url` calls the new async `ensure_runtime_migrations` from the same async-task context and asserts a clean `Err` result with no panic.

Both new tests pass; the full `autumn-harvest-plugin` lib unit test suite (961 tests) is green with zero regressions. `cargo fmt --all -- --check` and `cargo clippy -p autumn-harvest-plugin --all-targets -- -D warnings` are both clean.

**Production confirmation.** This diagnosis and fix were independently corroborated by a live crash report from a deployment on a TLS-enabled Postgres URL: the reported panic location (`establish_migration_connection`'s `handle.block_on(tls::establish(..))` call) and message (`"Cannot start a runtime from within a runtime"`) match exactly, immediately following an `on_startup hook: executing start_harvest_runtime` log line — the precise call site this fix wraps.
