## Phase 5.1 — autumn-harvest-sqlite v0.1 hardening: freeze activity defaults, reuse-policy matrix, race fairness (issue #1068)

Implements three follow-up hardening checkboxes tracked on #1068 (v0.1 PR #1069 deferred each with an explicit Codex P2 reply). Footprint: the `autumn-harvest-sqlite/` crate only — **zero core changes** (both required core types, `WorkflowIdReusePolicy` and `WorkflowEvent::WorkflowCancelled`, are already re-exported without the `db` feature).

**Item 1 — Freeze resolved activity defaults on the durable task row.** The retry policy (`max_attempts`/backoff/non-retryable list), the cross-retry `schedule_to_close` deadline, and per-attempt `start_to_close` are now resolved ONCE and frozen on the `harvest_tasks` row — at schedule time when the activity is already registered, else at first claim (the sanctioned fallback for a late-registered activity, guaranteed present since an unregistered activity is released back to PENDING and never claimed). Later claims read the frozen values verbatim and never re-consult the mutable in-memory registry, so a crash/reopen or a re-registration of the activity between attempts can no longer shift an in-flight task's policy/deadlines (matching the Postgres path, which stores these on the task). Two additive columns on `harvest_tasks`: `schedule_to_close_at` (frozen absolute deadline = `scheduled_at + schedule_to_close`) and `defaults_frozen` (a flag disambiguating "not yet resolved" from "resolved to None", so a genuinely-None field is never re-resolved from a changed registry). Existing DB files are upgraded by an additive `schema::migrate()` — a `PRAGMA table_info` probe + `ALTER TABLE ADD COLUMN` (never drop/rename, idempotent on every open). Frozen scalars live only on `harvest_tasks`, never `harvest_events`, so replay determinism and the append-only invariant are untouched; the `max_attempts` read-site is self-enforcing (a frozen task never falls back to `spec.max_attempts`).

**Item 2 — `(workflow_name, workflow_id)` reuse-policy matrix for `start_workflow_with_id`.** Previously every call minted a fresh `ExecutionId`, so duplicate webhook/business-id delivery created multiple executions and repeated side effects. The core PLAIN-start `WorkflowIdReusePolicy` matrix is now implemented faithfully (verified cell-by-cell against `autumn-harvest/src/execution.rs`), enforced atomically in the single-writer start transaction (no Postgres-style partial unique index — that would fail to build on reopen of a pre-#1068 file already holding duplicate active ids; a non-unique lookup index is added instead). `start_workflow_with_id` becomes idempotent-by-default (`AllowDuplicate`); a new `start_workflow_with_reuse_policy(name, id, input, policy) -> StartOutcome{exec_id, created}` takes an explicit policy and surfaces the new `SqliteError::AlreadyExists`. Matrix over the states the backend holds (none/RUNNING/COMPLETED/FAILED): AllowDuplicate → return existing; RejectDuplicate → AlreadyExists; AllowDuplicateFailedOnly → replace a FAILED prior (seal + fresh) else return existing; TerminateIfRunning → cancel-if-RUNNING (append `WorkflowCancelled` + release pending tasks/timers) + seal + fresh. "Seal" mirrors core's `replace_execution` (prior → `CONTINUED_AS_NEW`); the active-prior lookup excludes the sealed set `{CONTINUED_AS_NEW, TERMINATED}`, faithfully reproducing core's uniqueness-excludes-terminal nuance (RejectDuplicate rejects COMPLETED/FAILED priors but creates fresh over a sealed prior). No new `WorkflowEvent` variant. sqlite's single-writer `TerminateIfRunning` forcefully seals the prior (equivalent observable outcome to core: prior inactive + cancellation recorded, new run active) since the prior is immediately replaced and never driven again.

**Item 3 — `ctx.race()` fairness under zero-delay retry policies.** Previously a race branch using `RetryPolicy::fixed(_, 0ms)` requeued at the same `now` keeping its original lower `seq`, so `claim_next_ready_task(... ORDER BY seq ...)` re-selected it before any ready sibling — letting the lowest-index branch monopolize the drain and settle the race by failing, cancelling a ready sibling that would have won. On an IMMEDIATE (zero-delay) requeue (`run_at <= now`), the task is now moved to the BACK of the ready queue via a fresh `MAX(seq)+1` (`requeue_task_to_back`), so `ORDER BY seq` yields to every ready sibling before the just-failed branch re-runs (round-robin). A genuine backoff (`run_at > now`) already yields via its future `run_at` and is left byte-for-byte unchanged. The winner remains a pure function of recorded history (the core `race_winner:` marker + terminal-event order), so replay is deterministic.
