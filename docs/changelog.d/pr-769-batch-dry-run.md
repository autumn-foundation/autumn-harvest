## Phase 3.51 — Dry-run preview for batch operations (issue #769)

`POST /api/harvest/batch-operations` (the fleet-wide Cancel/Terminate/Signal surface, #102/#533) — the single most destructive engine surface, acting on **every** workflow matching a `BatchFilter` across all shards with no preview — gains an additive `dry_run: bool` (`#[serde(default)]` = `false`). Reset, worker drain, schedules, and DAG retry were all previewable; batch now is too, so an operator sees the exact blast radius (count + a bounded sample) before committing.

- `dry_run: false`/omitted → **byte-for-byte unchanged**: `202` + `{batch_job_id}`, the audit row, and the job lifecycle are all identical to a pre-#769 client. `SubmitBatchOperationRequest` has no `deny_unknown_fields`, so pre-#769 clients that never send `dry_run` are unaffected.
- `dry_run: true` → resolves the SAME filter across ALL shards and returns `200` with `{ dry_run, action, filter, matched_count, per_shard: [{shard_id, matched_count}], sample: [{execution_id, workflow_name, state}], sample_cap (100), sample_truncated, status, unavailable_shards }`. `matched_count` is an EXACT `COUNT(*)` per shard summed (never derived from the capped sample); `sample` is globally capped at 100 across shards (ordered by `id` ascending, so the sample is deterministic across repeated previews); `sample_truncated = matched_count > sample.len()`. Performs **zero** writes — no workflow transitions, no signals, no `harvest_task_queue` rows, no `harvest_batch_jobs` job row, and **no audit row for any outcome** (a preview is read-only introspection, like the other `preview`/`dry_run` surfaces).
- **Partial-shard degradation (mirrors `POST /workflows/batch_reset`):** an unreachable shard no longer fails the whole preview with a `500`. Each shard's connect/count/sample errors are caught and folded into `status: "partial"` naming the shard in `unavailable_shards: [{shard_id, reason}]` (`"complete"` + omitted `unavailable_shards` on the happy path). When any shard is unavailable, `matched_count`/`per_shard` cover reachable shards ONLY — a documented **lower bound**. The cross-shard accumulation (sum exact counts, fill the GLOBAL sample cap across shards, compute `sample_truncated`, derive `status`/`unavailable_shards`) is a pure, unit-tested helper `fold_batch_shard_previews(Vec<ShardPreviewOutcome>, sample_cap)` in the plugin `api.rs`, so the multi-shard sum / global-cap / partial-degradation logic is testable without a multi-shard database.
- An empty/criteria-less filter is rejected in `dry_run` mode with the same `400` guard the real submit uses (the shared `batch::BATCH_EMPTY_FILTER_ERR` constant), writing zero audit rows.

**Anti-drift (the load-bearing constraint):** the real target resolver, the dry-run count, and the dry-run sample all build their WHERE clause through ONE shared predicate builder — `batch::apply_batch_filters(query, action, filter)` in `autumn-harvest/src/batch.rs` — extracted from `resolve_targets_on_shard`. The two new `db`-gated functions `count_targets_on_shard` (exact `COUNT(*)`, no cap) and `sample_targets_on_shard` (bounded `SELECT (id, workflow_name, state) LIMIT n`) both call it, so a preview can never drift from what a real submit would act on. Proven by the `dry_run_matches_real_submit_target_count` integration test, which asserts the dry-run `matched_count` equals the real job's resolved `total`. Per-action state defaults (Terminate → `state NOT IN ('CANCELLED','TERMINATED')`; Cancel/Signal → `state IN ('RUNNING','PAUSED')`) are shared identically.

**Handler:** `submit_batch_operation` (plugin `api.rs`) widened its return type from `Result<(StatusCode, Json<SubmitBatchOperationResponse>), AutumnError>` to `Result<axum::response::Response, AutumnError>` so the 200-preview and 202-submit bodies differ; the 202 arm's bytes are unchanged. The dry-run branch is placed after the action-parse + `KNOWN_WORKFLOW_STATES` validations (so it can echo the resolved action) and before `submit_batch_job` / the signal-payload cap (a preview is filter-determined and deliberately skips the Signal `signal_name` requirement and payload cap — it reports blast radius, not signal validity). The action-parse and unknown-state early-validation audit writes are guarded by `if !request.dry_run` so a malformed dry-run request writes no audit row either.

**CLI (`autumn-harvest-cli`):** `harvest batch submit <action> --filter-json … --dry-run [--json]`. The `--dry-run` flag inserts `body["dry_run"] = true` only when set (a real-submit body stays byte-identical to a pre-#769 client). By default the preview renders as a table (count + per-shard breakdown + sample + a truncation note); `--json` prints the raw preview body. A real submit (no `--dry-run`) falls through to the default JSON renderer unchanged.

**Contract/registries:** `dry_run` added to the `POST /batch-operations` request-field registry; the polymorphic response's full set of TOP-LEVEL fields — `batch_job_id`, `dry_run`, `action`, `filter`, `matched_count`, `per_shard`, `sample`, `sample_cap`, `sample_truncated`, `status`, `unavailable_shards` — enumerated in BOTH `management_api_response_fields()` AND `docs/api-contract.json` `success_response.fields` (the `GET /workflows/{id}/stack` + `GET /admin/build-routing` precedent, which the `contract_response_fields_match_code_registry` test cross-checks for exact set equality), with `success_response.notes` reserved for the 202-vs-200 polymorphism and the nested `per_shard`/`sample`/`unavailable_shards` object shapes. Route stays classified `Mutating` (no `audit.rs` change) — `dry_run` is a field on a mutating route, so a `dry_run` preview is admin-only (a read-only principal cannot preview). Runbook: a "Fleet-wide batch: preview before you commit" section added to `docs/runbooks/contain-runaway-execution.md`, including the admin-only, Signal-not-validated, partial-lower-bound, and single-shard-seq-scan caveats.

**No new `WorkflowEvent` variant, no migration, no shard-routing change, no replay/append-only surface.** New core types re-exported from `autumn_harvest::batch`: `BatchTargetSample`, `BATCH_EMPTY_FILTER_ERR`, `count_targets_on_shard`, `sample_targets_on_shard`.

Tests: 4 pure (no-DB) `fold_batch_shard_previews` unit tests in the plugin `api.rs` test module (2-shard count sum, GLOBAL sample cap ≠ per-shard, `sample_truncated` boundary at/over cap, one-shard-errored → `status=partial` + lower-bound `matched_count`); 10 plugin integration tests in `autumn-harvest-plugin/tests/batch_operations_integration.rs` (matched_count + capped/truncated sample with full filter echo + UUID-parseable sample ids + `status:complete`, sample-below-cap-not-truncated, `matched_count == cap` boundary → not truncated, `search_attrs`-filter echo, zero-writes, anti-drift count-equals-real-submit, empty-filter-400-no-audit, Terminate-default-excludes-terminal, real-submit-still-writes-job **plus the correlated `batch.submit`/`succeeded` audit row**, and the `Signal --dry-run` without `signal_name` → 200 + zero `harvest_signals` rows) plus the 12 pre-existing batch tests (regression) — executed green against real Postgres 16; 4 CLI request-mapping tests (`--dry-run` sets the body flag; omitting it adds no key; `Signal --dry-run` without `--signal-name` builds a preview request; a non-dry-run `Signal` without `--signal-name` is rejected by the manual `batch_request` guard) plus 4 CLI unit tests (preview table renderer incl. the `per_shard` block; `--dry-run --json` compact raw body; `--json` without `--dry-run` rejected at clap parse via `requires`). The `Signal` `signal_name` arg dropped clap's `required_if_eq` in favor of the manual guard so a `Signal --dry-run` may omit it. The batch suite's `setup_database()` now honors `HARVEST_TEST_DATABASE_URL` (creating a fresh per-test database off the admin URL) with a testcontainers fallback, and is registered in `.github/ci/integration-suites.txt` (Docker-backed Linux run).
