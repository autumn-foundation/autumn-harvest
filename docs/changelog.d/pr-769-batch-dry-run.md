## Phase 3.51 — Dry-run preview for batch operations (issue #769)

`POST /api/harvest/batch-operations` (the fleet-wide Cancel/Terminate/Signal surface, #102/#533) — the single most destructive engine surface, acting on **every** workflow matching a `BatchFilter` across all shards with no preview — gains an additive `dry_run: bool` (`#[serde(default)]` = `false`). Reset, worker drain, schedules, and DAG retry were all previewable; batch now is too, so an operator sees the exact blast radius (count + a bounded sample) before committing.

- `dry_run: false`/omitted → **byte-for-byte unchanged**: `202` + `{batch_job_id}`, the audit row, and the job lifecycle are all identical to a pre-#769 client. `SubmitBatchOperationRequest` has no `deny_unknown_fields`, so pre-#769 clients that never send `dry_run` are unaffected.
- `dry_run: true` → resolves the SAME filter across ALL shards and returns `200` with `{ dry_run, action, filter, matched_count, per_shard: [{shard_id, matched_count}], sample: [{execution_id, workflow_name, state}], sample_cap (100), sample_truncated }`. `matched_count` is an EXACT `COUNT(*)` per shard summed (never derived from the capped sample); `sample` is globally capped at 100 across shards; `sample_truncated = matched_count > sample.len()`. Performs **zero** writes — no workflow transitions, no signals, no `harvest_task_queue` rows, no `harvest_batch_jobs` job row, and **no audit row for any outcome** (a preview is read-only introspection, like the other `preview`/`dry_run` surfaces).
- An empty/criteria-less filter is rejected in `dry_run` mode with the same `400` guard the real submit uses (the shared `batch::BATCH_EMPTY_FILTER_ERR` constant), writing zero audit rows.

**Anti-drift (the load-bearing constraint):** the real target resolver, the dry-run count, and the dry-run sample all build their WHERE clause through ONE shared predicate builder — `batch::apply_batch_filters(query, action, filter)` in `autumn-harvest/src/batch.rs` — extracted from `resolve_targets_on_shard`. The two new `db`-gated functions `count_targets_on_shard` (exact `COUNT(*)`, no cap) and `sample_targets_on_shard` (bounded `SELECT (id, workflow_name, state) LIMIT n`) both call it, so a preview can never drift from what a real submit would act on. Proven by the `dry_run_matches_real_submit_target_count` integration test, which asserts the dry-run `matched_count` equals the real job's resolved `total`. Per-action state defaults (Terminate → `state NOT IN ('CANCELLED','TERMINATED')`; Cancel/Signal → `state IN ('RUNNING','PAUSED')`) are shared identically.

**Handler:** `submit_batch_operation` (plugin `api.rs`) widened its return type from `Result<(StatusCode, Json<SubmitBatchOperationResponse>), AutumnError>` to `Result<axum::response::Response, AutumnError>` so the 200-preview and 202-submit bodies differ; the 202 arm's bytes are unchanged. The dry-run branch is placed after the action-parse + `KNOWN_WORKFLOW_STATES` validations (so it can echo the resolved action) and before `submit_batch_job` / the signal-payload cap (a preview is filter-determined and deliberately skips the Signal `signal_name` requirement and payload cap — it reports blast radius, not signal validity). The action-parse and unknown-state early-validation audit writes are guarded by `if !request.dry_run` so a malformed dry-run request writes no audit row either.

**CLI (`autumn-harvest-cli`):** `harvest batch submit <action> --filter-json … --dry-run [--json]`. The `--dry-run` flag inserts `body["dry_run"] = true` only when set (a real-submit body stays byte-identical to a pre-#769 client). By default the preview renders as a table (count + per-shard breakdown + sample + a truncation note); `--json` prints the raw preview body. A real submit (no `--dry-run`) falls through to the default JSON renderer unchanged.

**Contract/registries:** `dry_run` added to the `POST /batch-operations` request-field registry; the polymorphic response documented in `management_api_response_fields()` and `docs/api-contract.json` (202 `{batch_job_id}` or 200 preview, via the `success_response.notes` precedent). Route stays classified `Mutating` (no `audit.rs` change) — `dry_run` is a field on a mutating route. Runbook: a "Fleet-wide batch: preview before you commit" section added to `docs/runbooks/contain-runaway-execution.md`.

**No new `WorkflowEvent` variant, no migration, no shard-routing change, no replay/append-only surface.** New core types re-exported from `autumn_harvest::batch`: `BatchTargetSample`, `BATCH_EMPTY_FILTER_ERR`, `count_targets_on_shard`, `sample_targets_on_shard`.

Tests: 7 plugin integration tests in `autumn-harvest-plugin/tests/batch_operations_integration.rs` (matched_count + capped/truncated sample, sample-below-cap-not-truncated, zero-writes, anti-drift count-equals-real-submit, empty-filter-400-no-audit, Terminate-default-excludes-terminal, real-submit-still-writes-job) plus the 12 pre-existing batch tests (regression) — all 19 executed green against real Postgres 16; 2 CLI request-mapping tests (`--dry-run` sets the body flag; omitting it adds no key) plus 2 CLI unit tests for the preview table renderer. The batch suite's `setup_database()` now honors `HARVEST_TEST_DATABASE_URL` (creating a fresh per-test database off the admin URL) with a testcontainers fallback, and is registered in `.github/ci/integration-suites.txt` (Docker-backed Linux run).
