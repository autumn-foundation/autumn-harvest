## Phase 3.51 — Activity execution interceptors (issue #680)

Register an ordered middleware chain that wraps **every** activity execution on the worker — regular (task-queue-dispatched) *and* local (inline) — so applications add cross-cutting behavior (structured logging, custom metrics, header propagation, input/output shaping, test fault-injection) **once** at registration time instead of editing every `#[activity]` function. New core module `interceptor.rs`: the object-safe `ActivityInterceptor` trait (generic over a lifetime only, stored as `Arc<dyn ActivityInterceptor>`; no `async_trait` — manual `Pin<Box>` alias `ActivityInterceptorFuture<'a>` mirroring `PayloadStore`/`HistoryArchiver`/`CompletionCallbackDeliverer`), the `ActivityInvocation<'a>` read-only metadata carrier (`name`/`is_local`/`queue_name`, private fields + accessors for forward-compat), the `ActivityInterceptorNext<'a>` continuation (`.run(input)` proceeds to the next interceptor or the terminal handler; not calling it short-circuits so the handler never runs), and the shared `pub(crate) dispatch_with_interceptors` helper (zero-overhead direct handler call when the chain is empty — the default path is byte-for-byte unchanged). **First-registered interceptor is the OUTERMOST wrapper**, the activity handler is innermost.

Registration: `HarvestBuilder::activity_interceptor(impl ActivityInterceptor)` (repeatable, push-order = registration-order = index-0-outermost; mirrors `history_archiver`), threaded through both `into_worker_parts` / `into_worker_parts_with_extra_state` into `HandlerRegistry::with_activity_interceptors` (+ private field, `Vec::new()` default, and an `activity_interceptors()` accessor). Both worker dispatch sites — the regular `process_activity_task` handler call and the local `run_local_activity_inline` per-attempt call — build the execution future through `dispatch_with_interceptors`, wrapping the exact existing `(handler)(&ctx, input)` terminal.

**Error / panic / retry / circuit-breaker transparency by construction.** An interceptor future resolves to the *exact* `Result<serde_json::Value, String>` `Output` of `ActivityHandlerFn`, so its error rides the same internal String channel the handler uses: an interceptor `Err(String)` is treated identically to a handler error (normal retry → circuit-breaker `on_result` → terminal `ActivityFailed`, no special-casing; typed failures via `ActivityFailure::retryable/non_retryable(...).into_error_payload()`), and a **panic** in an interceptor (construction or poll) is caught by the same `catch_construct` + `catch_unwind` guard that contains handler panics (issue #782) → retryable `HandlerPanic` → worker survives, no poison-pill / DLQ row. Interceptors run **after** the per-activity circuit-breaker admit gate, so a circuit-open short-circuit never runs them. The local-activity chain runs **inside** the per-attempt local timeout (interceptor time counts against `start_to_close`) — the one documented behavioral difference from the regular path.

**Replay safety, no schema cost.** Interceptors live only on the worker dispatch path; the replay engine never invokes activity handlers (it reads recorded `ActivityCompleted`/`ActivityFailed`). The value the chain returns *becomes* the recorded activity result, so replay reads it back and interceptors are never re-invoked for a completed activity. Input reaches an interceptor already-decoded (task-queue rows store plaintext; codecs/offload apply only to `harvest_events`). **No new `WorkflowEvent` variant, no migration, no event-schema change** — additive/minor bump, and a worker with no interceptors registered is byte-for-byte identical to before.

Re-exported from `lib.rs` and `prelude.rs` (`ActivityInterceptor`, `ActivityInterceptorFuture`, `ActivityInterceptorNext`, `ActivityInvocation`). Testing surface (feature `testing`): `ActivityInvocation::for_test` + `run_interceptor_chain_for_test` drive a chain without a worker. Example `autumn-harvest/examples/activity_interceptor.rs` (a `LoggingMetricsInterceptor` recording a per-activity `harvest.user.activity.duration_ms` histogram + structured logs, registered once across two `#[activity]` functions with embedded tests). Tests, TDD red→green→refactor: 6 pure no-DB unit tests in `interceptor.rs` (outermost-first ordering, input transform, result transform, short-circuit-without-next, error transform, empty-chain fast path) + an object-safety assertion; 7 DB/worker integration tests in `tests/integration/activity_interceptor_tests.rs` (wraps-regular-and-records-transformed, not-reinvoked-on-replay, wraps-local with `is_local()==true`, panicking-interceptor→contained `HandlerPanic` + worker-survives + no DLQ, interceptor-error→retry-then-terminal like a handler error, zero-interceptor control unchanged, registration-order-outermost-first end-to-end). CI gains a Docker-backed run step for the integration suite.

**Post-review hardening (Codex P2) — transactional-activity consistency.** A transactional activity (`ctx.run_transactional`) atomically commits its `ActivityCompleted` event and marks its task `COMPLETED` *inside the user's transaction* — before an outer interceptor regains control from `next.run`. An interceptor that transforms the result after `next` (`Ok(V)`→`Err(e)` or `Ok(V)`→`Ok(V′)`) therefore cannot change the recorded history (the seal is immutable), but the worker was consuming that discarded post-interceptor result for its per-attempt metrics **and** the per-activity circuit breaker. As a result an interceptor mapping a committed `Ok` to `Err` would trip the breaker and record `Failed` on an outcome history records as `ActivityCompleted` — an observability/history divergence NEW to interceptors (nothing on the pre-interceptor path could alter a self-committed handler's returned value). Applying the chain *inside/before* the user transaction is out of scope (a transactional activity genuinely seals its own outcome atomically and an interceptor cannot un-commit it). Fix, in two parts: **(A)** the inherent limitation is now documented — an interceptor **observes but cannot transform** a transactional activity's recorded outcome (interceptor module docs, `run_transactional` constraints); **(B)** the engine keeps observability consistent with the committed history — `ActivityContext` carries an interior-mutable self-commit flag (`transactional_commit_occurred`, set only on a successful `run_transactional` commit), and after the interceptor chain resolves the worker reads it: a self-committed activity records the attempt as `Completed`, feeds the circuit breaker `Success`, and skips the finalize/retry path entirely (which would otherwise no-op or, on a retryable post-interceptor `Err` with retry budget, spuriously attempt a `requeue_for_retry` that logs `NotFound` against the already-COMPLETED task). A single `tracing::warn!` still surfaces the misuse when an interceptor's transform turned the committed success into an error. **Byte-for-byte unchanged** for the no-interceptor / observe-only / non-transactional cases (the flag is false for non-transactional activities, and a committed transactional activity with no outcome-transforming interceptor already recorded `Completed` / `Success` and no-oped in finalize). **No new `WorkflowEvent` variant, no migration.** Tests: 2 new DB/worker integration tests in `activity_interceptor_tests.rs` — `interceptor_error_transform_on_transactional_activity_does_not_trip_breaker` (the load-bearing one: committed `Ok`→`Err` interceptor leaves the breaker closed, records `Completed`, seals history as `ActivityCompleted` with the committed value, no retry/DLQ; fails pre-fix) and `interceptor_result_transform_on_transactional_activity_is_observably_ignored` (committed `Ok(V)`→`Ok(V′)` interceptor: history + workflow + metrics all reflect `V`).
