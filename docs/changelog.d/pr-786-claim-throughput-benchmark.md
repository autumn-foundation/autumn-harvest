- **Tooling** — Task-claim / enqueue throughput benchmark and CI-gated performance contract — see issue #786. Harvest published a CPU-path budget for replay (10k events < 200 ms, #135) but **nothing at all** for `queue::claim_task`, the single most scalability-critical query in the engine and the one that has accreted roughly a `WHERE` predicate per phase since 3.7 (build-id routing #171, per-key concurrency #247, rate-limit gate #332/#699, circuit-breaker tracked set #369, `schedule_to_close` #378, PAUSED skip #383, worker sessions #606, queue pauses #619, capability labels #382, sticky routing #235). Each was added for correctness; none was measured. **Zero engine impact (AC6): no new `WorkflowEvent` variant, no migration, no schema change, no public API change, and the claim query is byte-for-byte unchanged** — `git diff --name-only 301c70a..HEAD | grep -E "^autumn-harvest/src/|migrations/"` is empty. This slice measures; tuning is separate work, and tuning without a published baseline is how you get an unfalsifiable "optimisation". **Three artifacts sharing one harness.** `autumn-harvest/tests/integration/claim_bench_support.rs` is the harness; `benches/claim_bench.rs` is the exploratory report; `tests/integration/claim_budget_tests.rs` is the CI gate. The bench reaches across to the harness via `#[path = "../tests/integration/claim_bench_support.rs"]` rather than duplicating it, so the **published numbers and the gated number can never be produced by different code**. **Why not criterion:** `claim_task` is destructive (`PENDING → RUNNING`), so criterion's repeat-the-closure model would drain the seeded backlog and end up timing "claim against an empty queue" — the opposite of the thing under test. Hence `[[bench]] harness = false` with its own `main()`, seeding a backlog of N and performing a bounded number of claims (never more than `N/5`, `measured_claims_for`). **Headline measured findings** (published in the new `docs/performance.md`, framed explicitly as starter reference numbers, not an SLO; all tables from one run on an idle 4-core reference box against Postgres 16): (1) **claim latency scales superlinearly with pending-backlog depth** — 1k → 10k rows costs ~24x latency (9.92 ms → 234.22 ms p50), 10k → 100k a further ~15x (→ 3 531.95 ms), so a queue parked at 100k pending rows collapses fleet throughput to ~2 claims/s regardless of worker count while the *write* side still sustains ~3 650 enqueues/s — **a queue that deep does not drain**; (2) **the cause is structural** — the claim query's `ORDER BY` leads with a non-indexable `CASE` on `sticky_worker_id`/`sticky_until` (#235), so `idx_harvest_tq_poll` cannot serve the ordering and Postgres `Seq Scan`s + `Sort`s all 10 000 eligible rows to satisfy a `Limit 1` on every claim (`EXPLAIN (ANALYZE, BUFFERS)` is printed by the bench and excerpted in the doc), with the `harvest_queue_pauses` anti-join (#619) contributing `loops=10000` — 20 000 of 20 223 buffer hits; (3) **per-gate attribution (AC2)**: circuit-breaker tracked set +1%, rate-limit gate +5%, build-id routing +15%, **per-key concurrency +590%**, and all gates together +1690%; (4) **enqueue is not the problem (AC3)** — ~3 500 rows/s at p50 ~1.8 ms, flat from 1k to 100k backlog (7% spread, inside run-to-run noise). **An equal-depth control corrected a published conclusion.** An earlier revision compared the `paused_rows` scenario against `baseline`, measured +1319%, and concluded the PAUSED-execution skip was the most expensive predicate on the claim path. It is not. `paused_rows` seeds its PAUSED ballast *in addition to* the claimable backlog, so it walks a table twice as deep — and claim latency is strongly superlinear in depth, so that delta charged the anti-join for the extra rows. The new `ClaimGate::DoubleBacklog` control seeds the same 20 000 total rows with **no PAUSED predicate at all** and costs **+1357%**; measured against that honest comparand (`ClaimGate::comparand()` reports `paused_rows` against it, not against baseline) the anti-join costs **−2%**, indistinguishable from zero. The *operational* finding survives — pausing executions still does not take their work out of the claim path, and a paused population still costs ~14x (+1321% vs baseline) — but the mechanism is that the rows are *there*, not that the predicate is expensive: deleting the predicate would buy nothing, draining the rows would buy everything. `the_paused_rows_control_seeds_equal_total_depth` pins the control's equal-depth property and was verified RED by mutation. **The CI gate (AC5)** runs the headline scenario (10 000 pending / 8 claimers / 4 queues) via a new `linux` row in `.github/ci/integration-suites.txt` and fails the build when **p50** exceeds **1 500 ms** (~6.4x the 234 ms quiet-box reference, ~2.9x the worst loaded observation). **It asserts p50 rather than p99, from measurement, not preference:** the scenario deliberately oversubscribes the box (8 claimers on 4 cores), and an oversubscribed *tail* measures the run queue rather than the claim path — across repeated reference runs p50 moved ~2.3x between an idle and a loaded box while p99 moved ~15x (~300 ms → ~4 665 ms), and a p99 gate at this budget failed **2 runs in 6** during review on the same hardware class that produced the published numbers. p99 is still measured, still published, and printed in the failure message, so a genuine tail regression stays visible; it is simply not the assertion. The budget is documented as a **cliff detector, not a drift detector** — it cannot catch a 50%-slower predicate when the reference statistic itself moves 2.3x with machine load, but the two measured predicates that *do* add a per-row subplan to the full scan land at 6.9x and 14.6x, so 6.4x headroom sits below them and above the noise — and the doc says plainly that the number was derived on the reference machine, that the first Linux CI runs are the real calibration, and that the fix for flake there is to re-derive from CI observations rather than widen by guesswork. Overridable with `HARVEST_CLAIM_BUDGET_MS` (deliberately *not* named for a statistic, so the name cannot become a lie). **Four** soundness assertions fail *loudly* rather than reporting a meaningless percentile — ≥100 samples collected, **the run was not truncated by the wall-clock ceiling**, ≥90% of operations actually claimed a task, and the backlog was not drained below 80% (enforced two ways: the planned operation count is capped at `backlog / 5`, and `claims_for_claimer` splits it exactly rather than rounding up, so the claimers between them can never exceed the plan). The truncation assertion earned its place immediately: it fired on the first real run and exposed that the 60 s wall-clock ceiling was *smaller* than a run at the 1 500 ms latency budget would need (`(800/8) × 1.5 s = 150 s`), so truncation would have fired before the latency verdict ever rendered; the default is now 240 s and `wall_clock_budget_admits_a_run_at_the_latency_budget` holds the two constants to a coherent pair. Locally (no Docker, no `HARVEST_TEST_DATABASE_URL`) the gate skips with a notice; **under `CI` it fails instead**, because a performance gate that silently no-ops when its dependency is missing is not a gate. A companion test proves the gate is falsifiable *against real measured data* (a budget below the observed p50 must trip it), `each_gate_scenario_actually_seeds_its_trigger_column` censuses the seeded rows so the published cost table cannot silently start lying (verified RED by mutating the build-id seed expression to `NULL`), and `enqueue_throughput_is_measured_against_a_non_empty_queue` now asserts the post-run `PENDING` count equals `backlog + rows` so the harness cannot quietly stop seeding and still pass while measuring the easy case. **Measurement hygiene** (each of these is a defect that was found and fixed during the work, not a precaution): percentiles are **nearest-rank** so a reported p99 is a claim someone actually waited for; **a tenth of each claimer's observations is discarded as warmup, applied post-hoc rather than by planned index** — an earlier revision discarded a flat 3 per claimer and the headline p99 read ~2 900 ms instead of ~300 ms, i.e. the metric had silently become a cold-start measurement, while applying the fraction after collection also stops a wall-clock-truncated scenario from discarding every sample it took; **zero samples render as `n/a`, never `0.00`**, so a scenario that measured nothing cannot publish a number that looks instantaneous, a truncated scenario is marked `⚠` with its sample count shown, and a scenario below the gate's own 100-sample floor is marked `‡` and flagged directional-only; `ANALYZE` runs after every set-based seed; the pool is always sized above the claimer count so no measurement includes pool-checkout queueing; and `explain_claim` asserts its bind count before substituting literals, so the printed plan cannot silently drift from the real query. The report's per-gate table is **streamed row by row** rather than buffered (a full sweep takes tens of minutes), which is sound only because every comparand is measured before its dependent — pinned by `every_gate_is_ordered_after_its_comparand`. The doc is candid about what reproduces: across three independent runs only `build_policy` (+15%, +13%, +15%) and `paused_rows` vs `baseline` (+1319%, +1346%, +1321%) repeat to the point; `rate_limited` and `circuit_breaker_set` have *swapped rank with each other* between runs, so they are reported as "free" rather than as an ordering; and `concurrency_key` (+306%, +283%, +590%) grows as a run progresses, consistent with its `COUNT(*)` subquery counting a `RUNNING` population the benchmark itself is growing. `all_gates` is explicitly **not** a strict upper bound — its circuit-breaker tracked set short-circuits the rate-limit `EXISTS` and the debit CTE via `= ANY($5)`, so a deployment with rate limiting and no breaker executes strictly more work. **AC7 — platform safety:** the bench is `required-features = ["db"]`, and with neither Docker nor `HARVEST_TEST_DATABASE_URL` it prints a skip notice and exits 0, so `cargo bench` on a laptop without Docker is not a failure and `--no-default-features` / Windows builds are untouched. When `HARVEST_TEST_DATABASE_URL` **is** set it is treated as an **admin** URL: a freshly-named database is created and migrated per run (so a 100k-row backlog can never leak into a shared database), and stale databases from earlier runs are swept at *setup* — which also reclaims databases orphaned by a run that panicked, something a teardown hook could never do — skipping any whose owning pid is still alive so concurrent runs cannot delete each other's working set (the liveness check is Linux-only, documented). `ci_run_coverage.rs` gained a principled `is_db_harness_only` rule so the shared harness module is classified as a harness rather than an uncovered suite, plus three tests pinning that classification; the rule bites the moment that file gains a `#[tokio::test]` or `block_on`. Also verified: profile is not a variable (debug p50 228–256 ms vs release 242–256 ms at the headline scenario — the work is server-side), so gate and bench numbers are directly comparable. Documented known limitations include the degenerate sort-key distribution of the seeded backlog, that queue count is a parameter held at 4 rather than swept, and that four claim-path predicates (capability labels #382, `schedule_to_close` #378, worker sessions #606, sticky routing #235) are present in the query but held constant. Docs cross-linked from `README.md`, `docs/getting-started/README.md` and `docs/sharding.md` (the backlog-depth table is a sharding trigger). **Post-review hardening (PR #1156, Codex bot — four findings, all valid, all fixed, all confined to the harness so AC6 still holds):** (1) **Credential leak into CI logs.** The admin-connect failure path interpolated the whole `HARVEST_TEST_DATABASE_URL` into its `SkipReason`, which both the bench and the gate print — so a transient connection blip published a password to anyone with read access to the log. New pure `redact_url` replaces the `user:password@` segment while keeping host/port/database so the message stays diagnostic. Probing `diesel`/`tokio-postgres` with a password-bearing URL across connection-refused, DNS-failure and malformed-string cases showed they report only `"error connecting to server"` / `"invalid connection string"` and never echo the URL, so redacting our own interpolation closes the exposure rather than merely narrowing it — confirmed live, the real skip path now prints `connect postgres://***@localhost:5432/postgres`. (2) **`with_db_name` corrupted URLs carrying options.** Splicing at `rfind('/')` silently dropped `?sslmode=require` (making a TLS-requiring server unreachable through the advertised existing-server mode) and, when a parameter value contained a slash, spliced *inside the query*. Rewritten to replace only the path component and carry query/fragment through; RED-verified against the old body, where the three new tests fail with `postgres://h:5432/postgres?sslrootcert=/etc/ssl/bench_1` (database name spliced into the certificate path) and — worse than reported — `postgres://host` collapsing to `postgres://b`, losing the host entirely. Both functions were moved to the **pure** section so they are covered on every OS including the `--no-default-features` leg. (3) **Stale-database sweep could kill a live run on another host.** `process_is_alive` consults the local `/proc`, so when several machines share one admin URL a run elsewhere looks dead and `DROP DATABASE ... WITH (FORCE)` terminates it mid-measurement. Fixed by asking the one party that can see every client — the server — via `pg_stat_activity`; a database with any backend attached is never reclaimed. Deliberately *not* the suggested host/run marker in the name: a marker answers "is it mine", while the actual question is "is it in use", and only the server can answer that. The local pid check is kept as the cheap same-host path, and both checks fail toward "in use", so the worst outcome remains a leaked database. (4) **The wall-clock ceiling was not enforced during a claim.** The deadline was tested only between calls, and `claim_task` is an unbounded await, so one stalled claim would overrun the advertised 240 s cap indefinitely — precisely the stall the cap exists to bound. Each call is now wrapped in a timeout derived from the remaining budget; expiry marks the run truncated, which the gate already treats as measurement-unsound. Abandoning a connection mid-query can leave it unusable, which is fine and terminal here: the claimer breaks immediately, the pool recycles it, and the run is being discarded anyway.
