- **Tooling** — Task-claim / enqueue throughput benchmark and CI-gated performance contract — see issue #786. Harvest published a CPU-path budget for replay (10k events < 200 ms, #135) but **nothing at all** for `queue::claim_task`, the single most scalability-critical query in the engine and the one that has accreted roughly a `WHERE` predicate per phase since 3.7 (build-id routing #171, per-key concurrency #247, rate-limit gate #332/#699, circuit-breaker tracked set #369, `schedule_to_close` #378, PAUSED skip #383, worker sessions #606, queue pauses #619, capability labels #382, sticky routing #235). Each was added for correctness; none was measured. **Zero engine impact (AC6): no new `WorkflowEvent` variant, no migration, no schema change, no public API change, and the claim query is byte-for-byte unchanged** — the diff touches no file under `autumn-harvest/src/`. This slice measures; tuning is separate work, and tuning without a published baseline is how you get an unfalsifiable "optimisation". **Three artifacts sharing one harness.** `autumn-harvest/tests/integration/claim_bench_support.rs` is the harness; `benches/claim_bench.rs` is the exploratory report; `tests/integration/claim_budget_tests.rs` is the CI gate. The bench reaches across to the harness via `#[path = "../tests/integration/claim_bench_support.rs"]` rather than duplicating it, so the **published numbers and the gated number can never be produced by different code**. **Why not criterion:** `claim_task` is destructive (`PENDING → RUNNING`), so criterion's repeat-the-closure model would drain the seeded backlog and end up timing "claim against an empty queue" — the opposite of the thing under test. Hence `[[bench]] harness = false` with its own `main()`, seeding a backlog of N and performing a bounded number of claims (never more than `N/5`, `measured_claims_for`). **Headline measured findings** (published in the new `docs/performance.md`, framed explicitly as starter reference numbers, not an SLO): (1) **claim latency scales superlinearly with pending-backlog depth** — 1k → 10k rows costs ~23x latency (9.35 ms → 219.69 ms p50), 10k → 100k a further ~14x (→ 3 142.97 ms), so a queue parked at 100k pending rows collapses fleet throughput to ~2 claims/s regardless of worker count; (2) **the cause is structural** — the claim query's `ORDER BY` leads with a non-indexable `CASE` on `sticky_worker_id`/`sticky_until` (#235), so `idx_harvest_tq_poll` cannot serve the ordering and Postgres `Seq Scan`s + `Sort`s every eligible pending row per claim (`EXPLAIN (ANALYZE, BUFFERS)` is printed by the bench and excerpted in the doc), with the `harvest_queue_pauses` anti-join (#619) contributing `loops=10000` — 20 000 of 20 223 buffer hits; (3) **per-gate attribution (AC2)**: circuit-breaker tracked set +3%, rate-limit gate +7%, build-id routing +15%, **per-key concurrency +306%**, **PAUSED-execution ballast +1319%**, all gates +1580% — i.e. *pausing executions does not take their work out of the claim path*, the rows stay `PENDING` and every claim by every worker pays for them; (4) **enqueue is not the problem (AC3)** — ~4 000 rows/s at p50 1.5 ms, flat from 1k to 100k backlog. **Attribution runs at 2 claimers, not the headline 8**, because at 8 claimers on a 4-core box the tail columns stopped reproducing between runs (an identical baseline scenario reported a 285 ms max in one run and 3 093 ms in the next) while the p50 deltas held steady — the tails were measuring run-queue scheduling, not the query; `p50 vs baseline` is the attribution statistic and the doc says so. **The CI gate (AC5)** runs the headline scenario (10 000 pending / 8 claimers / 4 queues) via a new `linux` row in `.github/ci/integration-suites.txt` and fails the build when p99 exceeds **1 500 ms** — derived from measurement (8 runs, 5 release + 3 debug, p99 range 268–599 ms, median ~296 ms), so ~2.5x the worst observation and ~5x the median. It is documented as a **cliff detector, not a drift detector**: it will not catch a predicate that makes claims 50% slower, and the headroom is deliberate because a gate that flakes is a gate everyone learns to ignore. Overridable with `HARVEST_CLAIM_BUDGET_P99_MS`. Three soundness assertions fail *loudly* rather than reporting a meaningless percentile — ≥100 samples collected, ≥90% of operations actually claimed a task, and the backlog was not drained below 80%. Locally (no Docker, no `HARVEST_TEST_DATABASE_URL`) the gate skips with a notice; **under `CI` it fails instead**, because a performance gate that silently no-ops when its dependency is missing is not a gate. A companion test proves the gate is falsifiable *against real measured data* (a budget below the observed p99 must trip it), and another asserts every accreted gate scenario still actually claims tasks so the published cost table cannot silently start lying. **Measurement hygiene** (each of these is a defect that was found and fixed during the work, not a precaution): percentiles are **nearest-rank** so a reported p99 is a claim someone actually waited for; **a tenth of each claimer's observations is discarded as warmup, applied post-hoc rather than by planned index** — an earlier revision discarded a flat 3 per claimer and the headline p99 read ~2 900 ms instead of ~300 ms, i.e. the metric had silently become a cold-start measurement, while applying the fraction after collection also stops a wall-clock-truncated scenario from discarding every sample it took; **zero samples render as `n/a`, never `0.00`**, so a scenario that measured nothing cannot publish a number that looks instantaneous, and a truncated scenario is marked `⚠` with its sample count shown; `ANALYZE` runs after every set-based seed; the pool is always sized above the claimer count so no measurement includes pool-checkout queueing. **AC7 — platform safety:** the bench is `required-features = ["db"]`, and with neither Docker nor `HARVEST_TEST_DATABASE_URL` it prints a skip notice and exits 0, so `cargo bench` on a laptop without Docker is not a failure and `--no-default-features` / Windows builds are untouched. When `HARVEST_TEST_DATABASE_URL` **is** set it is treated as an **admin** URL: a freshly-named database is created and migrated per run (so a 100k-row backlog can never leak into a shared database), and stale databases from earlier runs are swept at *setup* — which also reclaims databases orphaned by a run that panicked, something a teardown hook could never do — skipping any whose owning pid is still alive so concurrent runs cannot delete each other's working set. `ci_run_coverage.rs` gained a principled `is_db_harness_only` rule so the shared harness module is classified as a harness rather than an uncovered suite, plus three tests pinning that classification; the rule bites the moment that file gains a `#[tokio::test]` or `block_on`. Also verified: profile is not a variable (debug p50 228–256 ms vs release 242–256 ms at the headline scenario — the work is server-side), so gate and bench numbers are directly comparable.
