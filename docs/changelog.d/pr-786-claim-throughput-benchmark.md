- **Tooling** — Task-claim / enqueue throughput benchmark and CI-gated performance contract — see issue #786. Harvest published a CPU-path budget for replay (10k events < 200 ms, #135) but **nothing at all** for `queue::claim_task`, the single most scalability-critical query in the engine and the one that has accreted roughly a `WHERE` predicate per phase since 3.7 (build-id routing #171, per-key concurrency #247, rate-limit gate #332/#699, circuit-breaker tracked set #369, `schedule_to_close` #378, PAUSED skip #383, worker sessions #606, queue pauses #619, capability labels #382, sticky routing #235). Each was added for correctness; none was measured. **Zero engine impact (AC6): no new `WorkflowEvent` variant, no migration, no schema change, no public API change, and the claim query is byte-for-byte unchanged** — `git diff --name-only 301c70a..HEAD | grep -E "^autumn-harvest/src/|migrations/"` is empty. This slice measures; tuning is separate work, and tuning without a published baseline is how you get an unfalsifiable "optimisation". **Three artifacts sharing one harness.** `autumn-harvest/tests/integration/claim_bench_support.rs` is the harness; `benches/claim_bench.rs` is the exploratory report; `tests/integration/claim_budget_tests.rs` is the CI gate. The bench reaches across to the harness via `#[path = "../tests/integration/claim_bench_support.rs"]` rather than duplicating it, so the **published numbers and the gated number can never be produced by different code**. **Why not criterion:** `claim_task` is destructive (`PENDING → RUNNING`), so criterion's repeat-the-closure model would drain the seeded backlog and end up timing "claim against an empty queue" — the opposite of the thing under test. Hence `[[bench]] harness = false` with its own `main()`, seeding a backlog of N and performing a bounded number of claims (never more than `N/5`, `measured_claims_for`). **Headline measured findings** (published in the new `docs/performance.md`, framed explicitly as starter reference numbers, not an SLO; all tables from one run on an idle 4-core reference box against Postgres 16): (1) **claim latency scales superlinearly with pending-backlog depth** — 1k → 10k rows costs ~24x latency (9.92 ms → 234.22 ms p50), 10k → 100k a further ~15x (→ 3 531.95 ms), so a queue parked at 100k pending rows collapses fleet throughput to ~2 claims/s regardless of worker count while the *write* side still sustains ~3 650 enqueues/s — **a queue that deep does not drain**; (2) **the cause is structural** — the claim query's `ORDER BY` leads with a non-indexable `CASE` on `sticky_worker_id`/`sticky_until` (#235), so `idx_harvest_tq_poll` cannot serve the ordering and Postgres `Seq Scan`s + `Sort`s all 10 000 eligible rows to satisfy a `Limit 1` on every claim (`EXPLAIN (ANALYZE, BUFFERS)` is printed by the bench and excerpted in the doc), with the `harvest_queue_pauses` anti-join (#619) contributing `loops=10000` — 20 000 of 20 223 buffer hits; (3) **per-gate attribution (AC2)**: circuit-breaker tracked set +1%, rate-limit gate +5%, build-id routing +15%, **per-key concurrency +590%**, and all gates together +1690%; (4) **enqueue is not the problem (AC3)** — ~3 500 rows/s at p50 ~1.8 ms, flat from 1k to 100k backlog (7% spread, inside run-to-run noise). **An equal-depth control corrected a published conclusion.** An earlier revision compared the `paused_rows` scenario against `baseline`, measured +1319%, and concluded the PAUSED-execution skip was the most expensive predicate on the claim path. It is not. `paused_rows` seeds its PAUSED ballast *in addition to* the claimable backlog, so it walks a table twice as deep — and claim latency is strongly superlinear in depth, so that delta charged the anti-join for the extra rows. The new `ClaimGate::DoubleBacklog` control seeds the same 20 000 total rows with **no PAUSED predicate at all** and costs **+1357%**; measured against that honest comparand (`ClaimGate::comparand()` reports `paused_rows` against it, not against baseline) the anti-join costs **−2%**, indistinguishable from zero. The *operational* finding survives — pausing executions still does not take their work out of the claim path, and a paused population still costs ~14x (+1321% vs baseline) — but the mechanism is that the rows are *there*, not that the predicate is expensive: deleting the predicate would buy nothing, draining the rows would buy everything. `the_paused_rows_control_seeds_equal_total_depth` pins the control's equal-depth property and was verified RED by mutation. **The CI gate (AC5)** runs the headline scenario (10 000 pending / 8 claimers / 4 queues) via a new `linux` row in `.github/ci/integration-suites.txt` and fails the build when **p50** exceeds **1 500 ms** (~6.4x the 234 ms quiet-box reference, ~2.9x the worst loaded observation). **It asserts p50 rather than p99, from measurement, not preference:** the scenario deliberately oversubscribes the box (8 claimers on 4 cores), and an oversubscribed *tail* measures the run queue rather than the claim path — across repeated reference runs p50 moved ~2.3x between an idle and a loaded box while p99 moved ~15x (~300 ms → ~4 665 ms), and a p99 gate at this budget failed **2 runs in 6** during review on the same hardware class that produced the published numbers. p99 is still measured, still published, and printed in the failure message, so a genuine tail regression stays visible; it is simply not the assertion. The budget is documented as a **cliff detector, not a drift detector** — it cannot catch a 50%-slower predicate when the reference statistic itself moves 2.3x with machine load, but the two measured predicates that *do* add a per-row subplan to the full scan land at 6.9x and 14.6x, so 6.4x headroom sits below them and above the noise — and the doc says plainly that the number was derived on the reference machine, that the first Linux CI runs are the real calibration, and that the fix for flake there is to re-derive from CI observations rather than widen by guesswork. Overridable with `HARVEST_CLAIM_BUDGET_MS` (deliberately *not* named for a statistic, so the name cannot become a lie). **Four** soundness assertions fail *loudly* rather than reporting a meaningless percentile — ≥100 samples collected, **the run was not truncated by the wall-clock ceiling**, ≥90% of operations actually claimed a task, and the backlog was not drained below 80% (enforced two ways: the planned operation count is capped at `backlog / 5`, and `claims_for_claimer` splits it exactly rather than rounding up, so the claimers between them can never exceed the plan). The truncation assertion earned its place immediately: it fired on the first real run and exposed that the 60 s wall-clock ceiling was *smaller* than a run at the 1 500 ms latency budget would need (`(800/8) × 1.5 s = 150 s`), so truncation would have fired before the latency verdict ever rendered; the default is now 240 s and `wall_clock_budget_admits_a_run_at_the_latency_budget` holds the two constants to a coherent pair. Locally (no Docker, no `HARVEST_TEST_DATABASE_URL`) the gate skips with a notice; **under `CI` it fails instead**, because a performance gate that silently no-ops when its dependency is missing is not a gate. A companion test proves the gate is falsifiable *against real measured data* (a budget below the observed p50 must trip it), `each_gate_scenario_actually_seeds_its_trigger_column` censuses the seeded rows so the published cost table cannot silently start lying (verified RED by mutating the build-id seed expression to `NULL`), and `enqueue_throughput_is_measured_against_a_non_empty_queue` now asserts the post-run `PENDING` count equals `backlog + rows` so the harness cannot quietly stop seeding and still pass while measuring the easy case. **Measurement hygiene** (each of these is a defect that was found and fixed during the work, not a precaution): percentiles are **nearest-rank** so a reported p99 is a claim someone actually waited for; **a tenth of each claimer's observations is discarded as warmup, applied post-hoc rather than by planned index** — an earlier revision discarded a flat 3 per claimer and the headline p99 read ~2 900 ms instead of ~300 ms, i.e. the metric had silently become a cold-start measurement, while applying the fraction after collection also stops a wall-clock-truncated scenario from discarding every sample it took; **zero samples render as `n/a`, never `0.00`**, so a scenario that measured nothing cannot publish a number that looks instantaneous, a truncated scenario is marked `⚠` with its sample count shown, and a scenario below the gate's own 100-sample floor is marked `‡` and flagged directional-only; `ANALYZE` runs after every set-based seed; the pool is always sized above the claimer count so no measurement includes pool-checkout queueing; and `explain_claim` asserts its bind count before substituting literals, so the printed plan cannot silently drift from the real query. The report's per-gate table is **streamed row by row** rather than buffered (a full sweep takes tens of minutes), which is sound only because every comparand is measured before its dependent — pinned by `every_gate_is_ordered_after_its_comparand`. The doc is candid about what reproduces: across three independent runs only `build_policy` (+15%, +13%, +15%) and `paused_rows` vs `baseline` (+1319%, +1346%, +1321%) repeat to the point; `rate_limited` and `circuit_breaker_set` have *swapped rank with each other* between runs, so they are reported as "free" rather than as an ordering; and `concurrency_key` (+306%, +283%, +590%) grows as a run progresses, consistent with its `COUNT(*)` subquery counting a `RUNNING` population the benchmark itself is growing. `all_gates` is explicitly **not** a strict upper bound — its circuit-breaker tracked set short-circuits the rate-limit `EXISTS` and the debit CTE via `= ANY($5)`, so a deployment with rate limiting and no breaker executes strictly more work. **AC7 — platform safety:** the bench is `required-features = ["db"]`, and with neither Docker nor `HARVEST_TEST_DATABASE_URL` it prints a skip notice and exits 0, so `cargo bench` on a laptop without Docker is not a failure and `--no-default-features` / Windows builds are untouched. Redaction is now **fail-closed** on that offset: anything the parser could not consume — an unterminated quote, a keyword with no value — is replaced with `***` rather than printed, so a form nobody anticipated degrades to withholding instead of leaking. The allowlist of printable connection *shape* parameters is unchanged; the change is that a value is only ever printed after it has actually been parsed as one. (Z) `db_name_from_url` — documented as the inverse of `with_db_name` and its literal neighbour — still read only a URL path, so for the keyword/value form that round 14 had just taught `with_db_name` to emit it returned `None` for exactly the strings the harness now produces, and both existing-server tests `.expect()` that value: the documented full gate suite panicked for a supported connection-string form. (Before round 14 the rewrite emitted a stray `/` that this parser happened to read as a path, so the inverse had been working only by accident.) Fixed by giving it a keyword branch — last `dbname` wins, matching `Config::param`, which simply assigns on each occurrence — and, in the same pass, by honouring the *query-over-path* precedence on the URL side that round 14 established for its twin. Leaving that half unfixed would have left two neighbouring functions disagreeing about which parameter names the database for the same input, which is the shape of the next finding rather than the end of this one. (AA) The measurement clock started before the claimer tasks were even spawned, so each claimer began sampling the moment *its own* `pool.get()` returned: claimer 0 could be several operations in while claimer 7 was still connecting. The "8 concurrent claimers" row therefore contained a lower-concurrency ramp-up at the head of its sample — flattering p50 for precisely the scenarios that exist to measure contention — and `wall_secs` counted lazy pool construction as though it were measured work, inflating the throughput denominator. Fixed with a start barrier after checkout and a measurement clock that begins on its release, in both the claim and enqueue runners; the throughput denominator is now the widest per-worker span from that release, which is the real measured phase. The scenario deadline is deliberately **not** re-anchored — it still precedes checkout, because `pool.get()` is an unbounded await and a ceiling that starts after it would not bound it (a round-8 fix this round had to be careful not to undo). Every task arrives at the barrier, including one that failed checkout and is about to return, so a party that is never coming cannot park its peers there; the wait is additionally bounded by the same deadline as every other await in the task, as a backstop for any future path that forgets. The published numbers were re-measured rather than carried over, because a change to the throughput denominator invalidates a throughput column by construction whether or not it moves it. **Round 16 review (BB, CC) — one shared split of the *driver's* URL grammar.** Both findings were the same root cause seen twice: the harness parsed `HARVEST_TEST_DATABASE_URL` as an RFC 3986 URL, but `tokio-postgres` hand-rolls its own `UrlParser` and that grammar differs in two ways that matter. (BB, P1) `parse_params` runs `self.decode(key)?` *before* dispatching to `Config::param`, so `?db%6Eame=admin` is a `dbname` override — but `with_db_name`'s strip-the-overriding-parameter filter (the round 14 P1 fix) compared the key raw and carried it through untouched. The rewritten string then *read* as though it targeted the isolated bench database while every connection opened from it — sweep lock, lease, migrations, and the benchmark's own `TRUNCATE` — went to the operator's admin database instead: the identical P1 round 14 closed, reached through a spelling that filter could not see. (CC, P2) `parse_params` terminates a value with `take_until(&['&'])` and the parser has no fragment concept at *any* stage (`parse_host` stops at `/` or `?`; `parse_path` runs `take_until(&['?'])` and otherwise takes the rest of the string), so `?password=#hunter2` authenticates with the literal `#hunter2` — but the redactor split the URL at `#` and appended the tail verbatim, printing most of a live password on exactly the connection-failure line operators paste into tickets. Rather than patch the two named call sites — which is the pattern that kept generating these findings — the grammar is now parsed **once**, by `split_driver_url`, into the regions the driver actually sees (`prefix`, `authority`, `path`, `query`, no fragment), and `redact_url`, `with_db_name` and `db_name_from_url` all derive from that single split. Query keys are compared after `percent_decode`, which mirrors `UrlParser::decode` exactly: plain percent-decoding, `+` is *not* a space, and invalid UTF-8 falls back to the raw span rather than being dropped (the driver rejects such a string outright, so there is no live connection for the fallback to disagree with). `db_name_from_url` decodes the value it returns for the same reason `parse_path` does — its result is fed to a `datname` lookup, and `%5F` names a database called `_`, not `%5F` — which changes its return type to an owned `String`. The keyword/value grammar is deliberately left comparing raw keys and *not* decoded: that form has no percent-encoding, so `dbname=%41` names a database literally called `%41`, and decoding it would be a new bug in the opposite direction. Two existing tests asserted the RFC reading (`.../bench_1#frag` → `bench_1`, and a fragment surviving a `dbname` strip) and were inverted to the driver's, with the reason recorded at each: `#frag` is part of the name and part of the value respectively, and reading it any other way has this harness look for a database the driver never asked for.

**Round 17 review — parse the driver's *order*, not just its grammar; count Unicode whitespace; measure every worker on one clock.** Three findings, two of them further instalments of the same lesson round 16 started: modelling the connection string on the *specification* rather than on `tokio-postgres`' actual code keeps producing credential leaks in the one place they hurt most — the connection-failure line an operator pastes into a ticket. (FF, P2) Round 16 split the URL into regions, but split them the way RFC 3986 defines an authority: stop at the first `/` or `?`, then look for `@` inside what is left. `UrlParser::parse` does not do that. It calls `parse_credentials` **before** `parse_host`, and credentials are `take_until(&['@'])` over the *entire* remaining string, with no `/` or `?` terminator. So `postgres://alice:sec/ret@db:5432/postgres` authenticates as `alice` / `sec/ret` against host `db:5432` — a perfectly ordinary password that happens to contain a slash — while the authority-first split saw `alice:sec`, found no `@` in it, and printed the whole credential verbatim. `split_driver_url` now mirrors the driver's call order (credentials → host → path → query) and reports `credentials` and `host` as separate fields; `redact_url` replaces the whole credential span with `***` and `with_db_name` re-emits it verbatim, because that function rewrites the connection *target* and a truncated credential yields a URL that no longer authenticates. Using the **first** `@` rather than the last is deliberate: it is what the driver does, and for a well-formed URL they are the same character. (DD, P2) The libpq keyword/value tokenizer added in round 15 separated pairs on `u8::is_ascii_whitespace`, but `Parser::skip_ws` is `take_while(char::is_whitespace)` and both value readers break on `c.is_whitespace()` — Unicode, not ASCII. A no-break space genuinely ends a value and starts a new pair for the driver, so `host=db.internal\u{00A0}password=hunter2` is two pairs to it and one to us: the whole tail became the value of the *allowlisted* `host` key and the password was printed in full. The tokenizer is now char-based throughout (`find_from`/`skip_ws`/`simple_value_end`/`quoted_value_end`), which also fixes the byte-arithmetic in the escape handling — `\` is one byte but the char it escapes need not be. (EE, P2) The start barrier added in round 15 removed pool checkout from the measured window, but each worker then timed itself with an `Instant::now()` taken *after* its own `gate.wait()` returned, and the scenario's wall clock was the maximum of those per-worker elapsed times. A worker is not polled the moment the barrier releases — with eight claimers on a four-thread runtime, most are not — so every worker's release-to-resume delay was dropped from the denominator while all of its claims stayed in the numerator, reporting throughput higher than the run achieved. Workers now report a `(resume, finish)` pair and the new pure `measured_window` folds them into one interval on the shared monotonic clock, from the earliest resume (the closest observable stand-in for the release itself) to the last completion. Both the claim and enqueue runners use it, and `docs/performance.md` is republished from a fresh run because the correction moves the denominator up and therefore every claims/s and rows/s figure down. `measured_window` lives in the pure section rather than the `db` module precisely so it is covered by the no-DB suite: its regression test drives two workers that each run for 1 s with the second resuming 2 s late, where the true window is 3 s and the old maximum-per-worker reading was 1 s — a threefold overstatement. **Post-review hardening, round 18 (Codex GG, P2):** the URL/keyword form was chosen by searching for `://` *anywhere*, but `UrlParser::remove_url_prefix` strips `postgres://`/`postgresql://` with `str::strip_prefix` and otherwise hands the whole string to the keyword parser — the form is decided by how a string *begins*, byte-exact. So `host=db password=http://hunter2` was read as a URL, split at a scheme that was really part of a value, and redacted nothing; `with_db_name` corrupted the same string into one that parses as neither form (the surviving `dbname=admin` still selecting the operator's real database while `/bench` was appended to the password). Selection is now `strip_prefix` against the two exact prefixes, which also routes a case variant like `POSTGRES://alice:hunter2@db/x` to the keyword redactor — where it has no `=` at all, and the passthrough that keeps a malformed-string message diagnostic would have printed its userinfo verbatim. That passthrough now drops everything through the last `@` when one is present. The doc's premise for that passthrough ("no `=` ⇒ carries no `key=value` secret") is true of keyword form and false of a scheme-shaped string whose secret is in userinfo; both halves shipped together because the first fix is what makes the second reachable.

**Post-review hardening, round 19 (Codex HH, P2):** `connect` and `seed` run *before* the measured phase and therefore before its deadline exists, so neither was bounded by anything — a server that accepted the TCP connection and then stopped answering would park the bench, and the CI gate that calls it, until the outer workflow timeout, while the page advertises a per-scenario cap. Every other await in both runners was already bounded; these two were the hole. The new `with_setup_deadline` wraps each step in `tokio::time::timeout` and panics with a message naming the step, and the shared `connect_and_seed` applies it on both the claim and enqueue paths so the bound cannot exist on one and not the other. Setup gets its *own* deadline rather than sharing the measured phase's: a single ceiling spanning both would let a slow seed eat the measurement window and report `truncated`, which says "the claim path is slow" about a run whose claim path was never the problem. Two phases, two ceilings — the worst case is bounded at twice the budget instead of unbounded, and each number means what it says. The same `scenario_time_budget` value is reused so raising `HARVEST_BENCH_SCENARIO_SECS` for a slow machine widens setup with it. The three tests live in `claim_budget_tests.rs` rather than beside the function: a `#[tokio::test]` in the shared harness would reclassify it from harness to suite and trip `ci_run_coverage::claim_bench_support_is_classified_as_a_harness_not_a_suite`, whose own remedy is to put the test in a file that already has a manifest row. They run on a paused clock, so the stalled-server case is decided by the deadline rather than by waiting out four real minutes; with the timeout removed the same test hangs (`cargo test` killed at 40 s against a pre-built binary), which is the bug it pins.
