## Phase 3.50 — Inline-resolved external op wakes every standard mixed-suspension shape immediately (issue #1034)

Follow-up to #678 / PR #1033. Closes the remaining latency (and, for one shape, indefinite-hang) bug where a workflow that races an external op — `signal_external_workflow` / `request_cancel_external_workflow` — against a **non-timer** branch in one decision cycle, with the external target on the **same shard**, failed to wake on the inline-resolved external terminal.

**Before.** #678 fixed exactly one suspension shape: a mixed `[StartTimer, SignalExternalWorkflow/RequestCancelExternalWorkflow]` batch. For a same-shard target, `persist_external_signal_inline` appends `External{Signal,Cancel}{Delivered,Failed}` to history **in this decision cycle**, so the terminal is already durable — but the self-wake that re-claimed the parked task lived inside the timer-only `persist_started_timer` path. Any other mixed shape got no wake:
- **signal-wait** (`select!{ signal_external_workflow(target), wait_for_signal("other") }`): the task parked on the signal wait and **hung** until the *other* signal arrived — potentially forever.
- **scheduled-activity** (`select!{ signal_external_workflow(target), execute_activity(slow) }`): the task waited out the **full activity** before noticing the already-resolved external branch.

**After.** The workflow wakes **immediately** on the inline-resolved external terminal and completes on the external branch right away. This covers every **standard** mixed-suspension park shape whose park leaves the workflow-task row re-pend-eligible: the issue's three named shapes (timer, signal-wait, scheduled-activity) **plus** child-workflow, external-activity-wait, and the child-timeout race (issue #779) — all use the same RUNNING-park / `mixed_signal_suspension`-stamp mechanism, so the single arm-level wake re-pends them uniformly.

**How.** Lifted the #678 inline-external self-wake out of the timer-only `persist_started_timer` path up to a single arm-level `queue::wake_workflow_task` in `persist_workflow_outcome`'s `WorkflowOutcome::Suspended` dispatch, gated on `!resolved_inline_external.is_empty()` (so a pure suspension, or a cycle whose externals routed to the outbox / were already observed, never false-wakes). Each shape's park leaves the workflow task `wake_workflow_task`-eligible: RUNNING-parked for signal-wait / scheduled-activity / child-workflow, and `mixed_signal_suspension`-stamped for the timer shape — so one arm-level wake re-pends them via the primary re-pend query. Retired the timer-only special case; **kept** `persist_started_timer`'s `mixed_signal_suspension` stamp (still set from the threaded `resolved_inline_external`) so the arm-level wake re-pends the timer's PENDING row. Runs **inside the enclosing persist transaction**, so park + re-pend commit atomically and the NOTIFY defers to the outer commit — no crash window.

**Known limitation (pre-existing, out of scope).** The one uncovered park shape is the issue #768 cancellable-timer `await_fire` `armed_fires_at` bookkeeping remainder — composing an armed cancellable-timer handle with an external op in a single `select!` is documented in #768 as an unsupported follow-up: that path reschedules the workflow row to `PENDING@future` **without** the `mixed_signal_suspension` stamp, so the arm-level wake no-ops for it and the run sleeps to the armed deadline (this is pre-existing #768 behaviour, not a #1034 regression).

**No new `WorkflowEvent` variant, no migration, no replay-determinism change** — the fix is entirely in the worker's suspension / self-wake bookkeeping; the resolved-id threading and `resolved_external_ids` helper from #678 are reused unchanged. Every suspension path other than the mixed external arm still threads `ResolvedExternalIds::default()` (empty), so their behaviour is byte-for-byte unchanged.

**Tests.** Four DB integration tests added to `tests/integration/cross_workflow_signal_tests.rs`, each starting the target **first** (confirmed `RUNNING`, so the caller's external op resolves inline) and bounding the caller's completion tightly to prove an immediate wake rather than a park-out: `test_mixed_signal_wait_suspension_external_signal_resolves_inline_wakes_immediately`, `test_mixed_signal_wait_suspension_external_cancel_resolves_inline_wakes_immediately`, `test_mixed_activity_suspension_external_signal_resolves_inline_wakes_immediately`, and `test_mixed_child_workflow_suspension_external_signal_resolves_inline_wakes_immediately` (the child-workflow shape, backing the "covers more than the three named shapes" claim above — RED without the arm-level wake, GREEN with it). The activity and child-workflow tests use a 60s slow branch with a 30s completion bound (the buggy path waits out the full 60s → trips the bound; the fixed path completes in ~seconds regardless of the branch length) for robustness on slow CI. The #678 timer-shape tests and the unresolved/outbox control are unchanged and still pass, confirming no regression to the cross-shard / `NotFound` route.
