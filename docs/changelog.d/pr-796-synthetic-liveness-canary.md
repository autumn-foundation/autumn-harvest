## Phase 3.51 — Synthetic liveness canary (issue #796)

**Opt-in built-in synthetic liveness canary** that continuously probes the *live* `start → dispatch → activity → durable-timer → complete` execution path so a wedged pipeline (workers polling but never completing, a stalled scheduler tick, a write-blocked shard) is detected within one probe interval — before any customer workflow misses its SLA — with zero operator-authored workflow code. **Distinct from the #512 replay canary**, which validates *code changes* by replaying in-flight histories; this validates *the running pipeline* by actively executing a throwaway workflow end to end (the two share only the word "canary"; no symbol collision — `is_canary_workflow`/`CANARY_*` vs `run_workflow_canary`/`canary_mode`).

**Opt-in and byte-identical when off (AC1):** `HarvestPlugin::synthetic_canary(CanaryConfig::new(interval))` enables it; absent that call the canary is entirely off and the runtime is byte-for-byte identical. The reserved names/predicates live in the core crate (`autumn_harvest::canary`: `CANARY_WORKFLOW_NAME_PREFIX = "__harvest_canary_probe"`, `CANARY_ACTIVITY_NAME`, `is_canary_workflow`, `is_reserved_canary_name`); the plugin (`autumn-harvest-plugin/src/canary.rs`) owns registration (hand-built `WorkflowInfo`/`ActivityInfo`, per-writable-shard schedule, self-cleaning retention) and the opt-in `CanaryConfig`.

**Probe (AC2/AC3):** for each configured probe queue the plugin registers a per-queue probe workflow `{PREFIX}__{queue}` (a real handler that dispatches one genuinely **non-local** activity on the probe's target queue, then waits on a short **durable** timer, then completes) plus one shared reserved canary activity (`is_local = false`, load-bearing). One canary + schedule per queue so a single wedged worker pool is distinguishable from "some queue is draining".

**Per-writable-shard coverage (AC4):** a new additive `#[serde(default)]` `WorkflowSchedule::all_writable_shards` flag (set via `with_all_writable_shards()`) is honored in `register_workflow_schedules_for_shard` (upsert on every `router.writable_shards()` shard) and the fire-path exec_id branch (mint `ExecutionId::new_for_shard(current_shard)`), so a single canary schedule definition runs its own probe loop on every writable shard. Single-shard/off is byte-identical.

**`harvest.canary.*` metrics + read model (AC5/AC7):** three metrics `harvest.canary.success` / `harvest.canary.failure` (counters) and `harvest.canary.roundtrip` (histogram), labels **`queue` + `shard` only** — `execution.id` is impossible by construction (three-touchpoint recorder methods take `queue: &str, shard: u16`). Emitted at the two primary terminal sites: `worker.rs::process_workflow_task` (success + roundtrip on Completed) and `timeout.rs::enforce_workflow_execution_timeouts` (failure on a per-probe-timeout). New read-only, admin-guarded `GET /admin/canary` reconstructs per-`(queue, shard)` freshness (`last_success_at`, `age`, `last_roundtrip_ms`, success/failure counts, `stale`) by cross-shard fan-out (`shard_fanout`), unioning the writable-shard grid with observed leftovers; an unreachable shard is named in `unavailable_shards` with `status: partial`/`unavailable` (never a hard 500). Registered across the axum router, `management_api_routes()`/`response_fields()`, `docs/api-contract.json`, and all three `audit` route lists (`RouteClass::ReadOnly`). Dashboard panels + `docs/telemetry.md` catalogue rows added.

**Business-observability exclusion (AC8):** a canary probe emits **only** `harvest.canary.*` and contributes to **no** `harvest.workflow.*` business SLO counter. Routed airtight through a single choke point `telemetry::emit_workflow_terminal` (generic over `&(impl MetricsRecorder + ?Sized)`) that skips `is_canary_workflow` probes; **every** `record_workflow_terminal` call site across the engine (worker completion/failure, execution-timeout, poison-pill quarantine, event-batch, execution cancel/terminate ×7, debounce, throttle, and the plugin batch-cancel) routes through it, so a canary can never leak `harvest.workflow.terminal` no matter which terminal path it reaches during exactly the distress the canary exists to detect. `harvest.workflow.started`/`.duration`/`.history_size`/`.continue_as_new` are also gated on `!is_canary` in `process_workflow_task`. `harvest.activity.*`/`harvest.queue.*` are unchanged (the canary legitimately exercises them). The canary is likewise excluded from `GET /workflows` (default list) **and** the stalled-workflow loader (`?no_progress_minutes=N`) unless a caller explicitly filters to a canary `workflow_name`, and from the cross-shard `GET /workflows/count`. `is_reserved_canary_name` is wired into `preflight::required_queues` and `shard_health`'s equivalent so the canary activity's `default_queue: None` never injects a phantom `"default"` required queue (which would flip a healthy non-default-queue deployment to a preflight/readiness failure).

**Self-clean retention (AC9):** `register_canary` adds an aggressive self-cleaning per-workflow retention override so the canary's own history is purged shortly after each run even with no global `max_age`. `CanaryConfig::effective_retention` is floored at `max(2 × staleness_window, 1h)` in **every** config path (an explicit `with_retention` below the floor is raised with a warning), so the last success row always outlives the freshness check that reads it — no false-positive stale alert on a healthy pipeline — and is clamped within the core `RetentionConfig` validator's bounds so `try_build()` can never fail.

**Config guardrails (AC6):** `CanaryConfig::new` clamps an interval below `MIN_CANARY_INTERVAL` (10s) up (with a warning); the derived `per_probe_timeout` is always in `[PROBE_MIN_RUNTIME (5s), interval - 1s]` — above the probe's own minimum runtime (a dispatched activity + a 1s durable timer + task wakeups) so a **healthy** probe never false-fails, and strictly below the interval so a wedged probe times out before the next tick (non-blocking). `with_per_probe_timeout` clamps out-of-range overrides (0, `>= interval`) into the same band. 30s is the recommended interval.

**Deliberate design decision (probe-queue polling):** `register_canary` does **not** force the local worker to poll the probe queue — the probed queue must be polled by some worker in the fleet built from this builder (the fleet whose liveness is being tested). Auto-adding a probe queue to the local worker would make it claim a dedicated remote fleet's real customer tasks and could report a false-"healthy". The default `"default"` queue is already polled by the builder's default worker, so the out-of-the-box config works with no extra wiring; probing any other queue requires the operator wire a worker (local `with_queues` or a separate process) for it.

**AC10 — no engine-schema cost:** the canary is registered as an ordinary `#[workflow]`/`#[activity]` on the standard execution path — **no new `WorkflowEvent` variant, no migration, no replay-determinism change**. The `all_writable_shards` flag is an additive `#[serde(default)]` schedule field with a back-compat deserialize test.

**P3 behaviors (documented):** an orphaned non-DAG `all_writable_shards` canary schedule left on a shard removed from `writable_shards` keeps firing probes there until the row is manually cleaned; its executions are bounded by retention (self-cleaning), so it is wasted probing, not unbounded growth. A probe queue with no live poller in the fleet under test simply times out — correctly flagging "this queue has no live pollers".

**Tests:** core `is_canary_workflow`/`is_reserved_canary_name` predicate unit tests; the `telemetry::emit_workflow_terminal` choke-point record-vs-skip unit test; plugin `CanaryConfig` interval/timeout/retention clamp unit tests, `register_canary` registration + `try_build` unit tests, and pure `build_canary_report` read-model unit tests (fresh/stale/never-succeeded/empty-shard/unreachable-shard/mixed-grid); `GET /admin/canary` HTTP integration + admin-guard tests; the three-metric dashboard/contract/audit anti-drift guards. New DB-backed core suite `autumn-harvest/tests/integration/canary_tests.rs` (RecordingMetrics) drives a real worker completing a probe (asserts `harvest.canary.success`/`roundtrip`, no `harvest.workflow.*` for the probe — AC5/AC8), a backdated-deadline execution-timeout (asserts `harvest.canary.failure`, no terminal/timeout — AC6/AC8), and a normal workflow still recording `harvest.workflow.terminal`; wired into `.github/ci/integration-suites.txt` (one sorted line, ci_run_coverage green), compile-checked in-sandbox and RUN by CI's Docker-backed Linux step.
