## Phase 3.51 — `WorkflowIdConflictPolicy` for idempotent plain workflow starts (issue #685)

Splits the single, overloaded `WorkflowIdReusePolicy` into two **orthogonal** axes so an idempotent plain start can express "attach to a currently-running run" without abusing the reuse semantics that were designed for terminal priors:

- `WorkflowIdReusePolicy` (unchanged, 4 variants) governs **TERMINAL** priors (COMPLETED/FAILED/CANCELLED/TIMED_OUT).
- New `WorkflowIdConflictPolicy` (`types.rs`, re-exported from `lib.rs`) governs **ACTIVE** (RUNNING/PAUSED) priors: `Unspecified` (default — defer to the reuse policy's native active behavior), `Fail` (→ `Err(AlreadyExists)`), `UseExisting` (attach: return the running handle, `created == false`, no new `WorkflowStarted` event, no task enqueued, no cancel), `TerminateExisting` (cancel + start fresh). Wire values `unspecified`/`fail`/`use_existing`/`terminate_existing`.

The two axes **compose** in the start-path admission logic: the conflict axis has no effect on a terminal prior, and the reuse axis has no effect on an active prior (except via the `Unspecified` fallback). Because `Unspecified` maps each reuse policy to its exact documented active behavior (`AllowDuplicate`→Attach, `RejectDuplicate`→Fail, `AllowDuplicateFailedOnly`→Attach, `TerminateIfRunning`→Terminate), **every existing caller is byte-for-byte unchanged (AC-6)**.

**Core changes (`execution.rs`):** new pure helpers `ActiveConflictBehavior { Fail, Attach, Terminate }`, `is_active_conflict_state(state)` (RUNNING|PAUSED), `effective_active_conflict_behavior(reuse, conflict)` (all `pub`). `start_will_create_new_execution` gains a `conflict_policy` parameter and branches active-vs-terminal first. `StartWorkflowParams` gains a `conflict_policy: WorkflowIdConflictPolicy` field (swept to `Unspecified` at ~123 literal sites workspace-wide). The start transaction's existing-prior `match` was restructured to branch on active-vs-terminal first: an active prior is resolved by the effective conflict behavior; a terminal prior is resolved by the reuse axis exactly as before.

**Admission-gate / pre-check interaction:** the two-transaction `TerminateIfRunning` pre-check cancel and its unlocked POINT-1 gate now fire on `terminate_via_pre_check = (reuse == TerminateIfRunning && effective == Terminate)` — identical to the old `reuse == TerminateIfRunning` for `Unspecified`, and correctly excluding `TerminateIfRunning` + `UseExisting`/`Fail` (so a `UseExisting` override never cancels the prior). A conflict-driven Terminate with a non-`TerminateIfRunning` reuse (e.g. `AllowDuplicate` + `TerminateExisting`) is handled **atomically inside** the start transaction (active branch: `inline_cancel` + `replace_execution`), never via a pre-check cancel that would otherwise route the just-cancelled prior through the reuse policy's attach branch. This deviates from the literal spec's "POINT-1 gates on `effective == Terminate`" (which would wrongly block an attach to a terminal prior); the goal — "the gate is applied exactly when a fresh execution WILL be created, skipped for a genuine attach" — is met precisely.

**No new `WorkflowEvent` variant, no migration, no persisted field** — `conflict_policy` is a request-time caller concern only, exactly like `reuse_policy`.

Plugin/CLI/HTTP wiring of the new axis is a follow-up; the plugin's two `start_will_create_new_execution` call sites and the `#[workflow]` typed-stub currently pass `Unspecified` (behavior-preserving).

**Tests:** unit matrix in `execution.rs` (`start_will_create_tests` extended with the active-conflict axis + an explicit legacy-truth-table `unspecified_matches_today` regression guard; new `active_conflict_tests` for the helpers). DB matrix in `integration_e2e.rs`: `conflict_use_existing_running_attaches_no_new_run` (attach, prior stays RUNNING, zero new events), `conflict_use_existing_paused_attaches`, `conflict_terminate_if_running_reuse_plus_use_existing_completed_starts_fresh` and `..._running_attaches` (AC-3 corners, proving the pre-check gate fix), `conflict_fail_running_errors`, `conflict_terminate_existing_running_cancels_and_starts_fresh`, `conflict_unspecified_preserves_allow_duplicate_running_attaches` (AC-6 guard), and `conflict_concurrency_race_use_existing_converges` (the success-metric proof — 20 concurrent `UseExisting` starts against one running prior all converge on the same `exec_id`, zero `AlreadyExists`, zero terminations). `setup_test_db` now honours `HARVEST_TEST_DATABASE_URL` for local-Postgres runs when Docker is unavailable.

### Plugin + CLI + HTTP wiring (issue #685, second half)

Exposes and enforces the `conflict_policy` axis on the standalone HTTP start route and the CLI (the core half above landed it behind `Unspecified`-defaulted plugin call sites):

- **HTTP `POST /workflows/{workflow_name}/start`** (`autumn-harvest-plugin/src/api.rs`): new optional body field `conflict_policy` (`unspecified`|`fail`|`use_existing`|`terminate_existing`), parsed by `parse_conflict_policy` (mirrors `parse_reuse_policy`; unknown value → `400`, echoed). Threaded into **both** the plain and the #808 idempotency-key `StartWorkflowParams`. An attach (`use_existing` over an active prior) returns `200` + `created:false`; a fresh replacement (`terminate_existing`) returns `201`; `fail` over an active prior returns `409`.
- **`started_fresh` surfacing (AC-4/AC-7):** the no-key success response now includes `started_fresh: Some(start.created)` **only when the request sent a `conflict_policy` field** (even `unspecified`); omitting the field omits `started_fresh` so the response is byte-for-byte identical to a pre-#685/#808 build.
- **Admin gate (security parity):** the handler's top-of-function admin gate — previously `reuse_policy == terminate_if_running` — now **also** requires admin for `conflict_policy == terminate_existing`, since both can forcibly cancel a live prior. Without admin → `401`. (This closes a privilege gap that would otherwise let `conflict_policy` reach the identical cancel-and-replace behavior without auth.)
- **Deferred-start mutual exclusion:** a non-default `conflict_policy` combined with a throttle / debounce / batch policy returns `400` (the start is deferred and has no active prior to resolve at request time), mirroring the `idempotency_key`-vs-deferred-start rule. `conflict_policy` + `idempotency_key` compose (allowed).
- **Contract:** `conflict_policy` added to `management_api_request_fields()` and `docs/api-contract.json` (request field + `401`/`400`/`409` error descriptions + success-note `started_fresh` semantics); `contract_regression` parity guard stays green.
- **CLI:** `harvest workflow start --conflict-policy <unspecified|fail|use_existing|terminate_existing>` (`autumn-harvest-cli`), mapped 1:1 onto the body field; omitting the flag sends no field.
- **Docs:** CLAUDE.md "Standalone Start — Conflict Policy" matrix; `docs/getting-started/10-operations.md` "Conflict policies" section.
- **Tests:** plugin `parse_conflict_policy` unit tests + a DB/HTTP suite `autumn-harvest-plugin/tests/conflict_policy_integration.rs` (attach-200, AC-3 terminate_if_running+use_existing corner, fail-409, terminate_existing-201-cancels-prior, omit-preserves-response, unknown-400, throttle-mutual-exclusion-400, no-admin-401, and a 20-way concurrent `use_existing` convergence proof) — wired into `.github/ci/integration-suites.txt`. CLI mapping tests (`conflict_policy_tests`) + `contract_coverage` body-field coverage.

### Post-review hardening (issue #685 review)

- **Capability-precise admin gate (narrowed).** The plugin start handler's admin gate no longer raw-string-matches `reuse_policy == terminate_if_running || conflict_policy == terminate_existing` before parsing. It now parses **both** policies first and requires admin **iff the request can cancel a live run** — i.e. `effective_active_conflict_behavior(reuse, conflict) == ActiveConflictBehavior::Terminate`. This keeps `conflict=terminate_existing` (any reuse) and `reuse=terminate_if_running` + default/omitted conflict admin-gated (unchanged), while **allowing the flagship non-admin idempotent-starter shape** `reuse=terminate_if_running` + `conflict=use_existing` (resolves to *attach*, provably cannot cancel a live run) — previously wrongly forced to require admin. `terminate_if_running` + `fail` (resolves to `409`) is likewise now non-admin. The gate moves after the two policy parses (an invalid value now returns `400` before the gate) and after the #808 committed-replay probe (safe: a replay returns the already-committed run and performs no new cancel, and a non-admin can never commit a Terminate start). New HTTP tests: `terminate_if_running_plus_use_existing_is_not_admin_gated` (RUNNING prior → `200` attach, zero `WorkflowCancelled`; also the HTTP AC-3 RUNNING-prior corner), `terminate_if_running_plus_use_existing_over_completed_is_not_admin_gated` (COMPLETED prior → `201` fresh), `terminate_if_running_without_conflict_still_requires_admin` (no-regression `401`).
- **AC-2 coverage gap closed.** New core DB tests `conflict_terminate_existing_paused_cancels_and_starts_fresh` (the IN-TRANSACTION `inline_cancel` + `replace_execution` on a PAUSED prior — a path the pre-check-based native `TerminateIfRunning` never reaches: asserts fresh `created`, prior sealed `CONTINUED_AS_NEW`, exactly one `WorkflowCancelled`) and `conflict_fail_paused_errors` (`Fail` over PAUSED → `Err(AlreadyExists)`, `existing_state == "PAUSED"`).
- **AC-4 strengthened.** `conflict_use_existing_running_attaches_no_new_run` now also asserts at the DB level that a `UseExisting` attach enqueues **no** `harvest_task_queue` row against the allocated-but-unused fresh `exec_id`.
- **Concurrency note documented.** Concurrent `terminate_existing` starts of the same `(workflow_name, workflow_id)` against one live prior are last-writer-wins; a loser may observe a transient `404 NotFound` (a pre-existing `load_workflow_execution_by_key_for_update` race, more reachable without a pre-check). It does not corrupt data, deadlock, or double-run — retry the start (documented in `execution.rs`, CLAUDE.md, and `10-operations.md`).
- **Coverage nits.** Mutual-exclusion guard now exercised for **all three** deferred-start legs (`conflict_policy_on_debounced_workflow_returns_400`, `conflict_policy_on_batched_workflow_returns_400`, alongside the existing throttle test). Docstring drift in `start_throttle_integration.rs` updated to the 3-arg `start_will_create_new_execution(_, _, Unspecified)` signature.

### Post-review hardening, round 2 (issue #685 review, Codex P2 — concurrent `terminate_existing` convergence)

- **Bounded seal-race retry replaces the transient `NotFound`.** The concurrency note above documented a real gap: concurrent `conflict=terminate_existing` (or any replace-type) starts of one live `(workflow_name, workflow_id)` could leave a LOSER with a transient `HarvestError::NotFound` (→ HTTP `404`) instead of a successful idempotent start. The loser's post-INSERT `load_workflow_execution_by_key_for_update` (a single `FOR UPDATE` SELECT) takes its statement snapshot before a concurrent winner commits, blocks on the prior's row lock, and — on the winner's commit — sees the prior filtered out by the load's non-sealed filter (winner sealed it → `CONTINUED_AS_NEW`) while the winner's freshly-inserted replacement row is invisible to that same statement's snapshot → the load returns `None` → `NotFound`. This was a pre-existing race in the shared active-`Terminate` branch, now the PRIMARY path for `terminate_existing` (which has no pre-check cancellation), so newly reachable on a normal concurrent-delivery scenario.
- **Fix (in-transaction bounded retry).** The active-conflict load is now wrapped in a bounded retry loop (`execution.rs`, `start_or_load_workflow_execution_collect`): under READ COMMITTED each SELECT statement gets a fresh snapshot, so re-issuing the load after the winner has committed picks up the winner's replacement RUNNING row and the start CONVERGES (last-writer-wins) instead of surfacing a transient `NotFound`. The loser holds no conflicting lock after a `None` load (`ON CONFLICT DO NOTHING` never locks the conflicting row; a `None` `FOR UPDATE` locks nothing), and once a row IS found and `FOR UPDATE`-locked the subsequent `inline_cancel` + `replace_execution` cannot be sealed out from under us. Each retry's `FOR UPDATE` naturally blocks on the current lock holder (forward progress, not a busy-loop), so N concurrent contenders serialize and the last loser waits behind at most N-1 winners; the cap (`SEAL_RACE_MAX_LOAD_RETRIES = 64`) is set generously above realistic concurrent-delivery bursts, with a small fixed backoff guarding the pathological "prior sealed without a replacement" case (e.g. a concurrent reset), which falls back to the pre-existing terminal `NotFound`. Scoped to the seal race only (a `None` load after a no-op INSERT) — transparent to every non-racing path and to `UseExisting`/`Fail`/`Attach`. The `idempotency_key` path (`in_outer_transaction = true`, #808) is untouched — its same-key dedup already collapses concurrent same-key retries.
- **Docs corrected.** The "concurrent terminate_existing … a loser may get a transient NotFound and should retry" note is updated in `execution.rs`, CLAUDE.md, and `docs/getting-started/10-operations.md` to reflect that the transient failure is now handled internally: concurrent `terminate_existing` on one key is last-writer-wins and CONVERGES to a single surviving run via a bounded internal retry — no transient `NotFound` is surfaced.
- **Test.** New `conflict_terminate_existing_concurrent_converges` (`autumn-harvest/tests/integration/integration_e2e.rs`): seed one RUNNING prior, spawn 20 concurrent `allow_duplicate + terminate_existing` starts on a shared pool (multi-thread runtime), assert ZERO calls errored (no `NotFound`, no `AlreadyExists`) and the storm settled to exactly ONE surviving RUNNING execution with all others sealed. The race is timing-dependent, so the test guards the convergence invariant rather than deterministically reproducing the pre-fix 404.
- **Docs (contract) — capability-precise start admin gate (Codex P2).** The `POST /workflows/{workflow_name}/start` `401` note in `docs/api-contract.json` (and the `conflict_policy` field note) claimed `reuse_policy=terminate_if_running` unconditionally requires admin. Corrected to describe the gate by the resolved active-conflict behavior: admin is required only when the request can cancel a live (RUNNING/PAUSED) prior — `conflict_policy=terminate_existing` (any reuse), or `reuse_policy=terminate_if_running` with the default/omitted conflict — so the flagship non-admin idempotent-starter shape (`terminate_if_running` + `use_existing`) is documented as non-admin and API-contract-following clients no longer needlessly admin-route it. Docs-only; signal-with-start / update-with-start notes (which lack `conflict_policy`) are accurate and unchanged.
