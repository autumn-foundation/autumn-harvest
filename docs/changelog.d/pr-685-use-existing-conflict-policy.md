## Phase 3.51 — `WorkflowIdConflictPolicy` for idempotent plain workflow starts (issue #685)

Splits the single, overloaded `WorkflowIdReusePolicy` into two **orthogonal** axes so an idempotent plain start can express "attach to a currently-running run" without abusing the reuse semantics that were designed for terminal priors:

- `WorkflowIdReusePolicy` (unchanged, 4 variants) governs **TERMINAL** priors (COMPLETED/FAILED/CANCELLED/TIMED_OUT).
- New `WorkflowIdConflictPolicy` (`types.rs`, re-exported from `lib.rs`) governs **ACTIVE** (RUNNING/PAUSED) priors: `Unspecified` (default — defer to the reuse policy's native active behavior), `Fail` (→ `Err(AlreadyExists)`), `UseExisting` (attach: return the running handle, `created == false`, no new `WorkflowStarted` event, no task enqueued, no cancel), `TerminateExisting` (cancel + start fresh). Wire values `unspecified`/`fail`/`use_existing`/`terminate_existing`.

The two axes **compose** in the start-path admission logic: the conflict axis has no effect on a terminal prior, and the reuse axis has no effect on an active prior (except via the `Unspecified` fallback). Because `Unspecified` maps each reuse policy to its exact documented active behavior (`AllowDuplicate`→Attach, `RejectDuplicate`→Fail, `AllowDuplicateFailedOnly`→Attach, `TerminateIfRunning`→Terminate), **every existing caller is byte-for-byte unchanged (AC-6)**.

**Core changes (`execution.rs`):** new pure helpers `ActiveConflictBehavior { Fail, Attach, Terminate }`, `is_active_conflict_state(state)` (RUNNING|PAUSED), `effective_active_conflict_behavior(reuse, conflict)` (all `pub`). `start_will_create_new_execution` gains a `conflict_policy` parameter and branches active-vs-terminal first. `StartWorkflowParams` gains a `conflict_policy: WorkflowIdConflictPolicy` field (swept to `Unspecified` at ~123 literal sites workspace-wide). The start transaction's existing-prior `match` was restructured to branch on active-vs-terminal first: an active prior is resolved by the effective conflict behavior; a terminal prior is resolved by the reuse axis exactly as before.

**Admission-gate / pre-check interaction:** the two-transaction `TerminateIfRunning` pre-check cancel and its unlocked POINT-1 gate now fire on `terminate_via_pre_check = (reuse == TerminateIfRunning && effective == Terminate)` — identical to the old `reuse == TerminateIfRunning` for `Unspecified`, and correctly excluding `TerminateIfRunning` + `UseExisting`/`Fail` (so a `UseExisting` override never cancels the prior). A conflict-driven Terminate with a non-`TerminateIfRunning` reuse (e.g. `AllowDuplicate` + `TerminateExisting`) is handled **atomically inside** the start transaction (active branch: `inline_cancel` + `replace_execution`), never via a pre-check cancel that would otherwise route the just-cancelled prior through the reuse policy's attach branch. This deviates from the literal spec's "POINT-1 gates on `effective == Terminate`" (which would wrongly block an attach to a terminal prior); the goal — "the gate is applied exactly when a fresh execution WILL be created, skipped for a genuine attach" — is met precisely.

**No new `WorkflowEvent` variant, no migration, no persisted field** — `conflict_policy` is a request-time caller concern only, exactly like `reuse_policy`.

Plugin/CLI/HTTP wiring of the new axis is a follow-up; the plugin's two `start_will_create_new_execution` call sites and the `#[workflow]` typed-stub currently pass `Unspecified` (behavior-preserving).

**Tests:** unit matrix in `execution.rs` (`start_will_create_tests` extended with the active-conflict axis + an explicit legacy-truth-table `unspecified_matches_today` regression guard; new `active_conflict_tests` for the helpers). DB matrix in `integration_e2e.rs`: `conflict_use_existing_running_attaches_no_new_run` (attach, prior stays RUNNING, zero new events), `conflict_use_existing_paused_attaches`, `conflict_terminate_if_running_reuse_plus_use_existing_completed_starts_fresh` and `..._running_attaches` (AC-3 corners, proving the pre-check gate fix), `conflict_fail_running_errors`, `conflict_terminate_existing_running_cancels_and_starts_fresh`, `conflict_unspecified_preserves_allow_duplicate_running_attaches` (AC-6 guard), and `conflict_concurrency_race_use_existing_converges` (the success-metric proof — 20 concurrent `UseExisting` starts against one running prior all converge on the same `exec_id`, zero `AlreadyExists`, zero terminations). `setup_test_db` now honours `HARVEST_TEST_DATABASE_URL` for local-Postgres runs when Docker is unavailable.
