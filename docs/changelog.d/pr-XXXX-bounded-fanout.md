## Phase 3.52 — Bounded / windowed activity fan-out (issue #750)

Bounded-concurrency variants of the four activity fan-out shapes, so a wide fan-out applies natural backpressure to workers and downstreams instead of scheduling every input at once. This is a pure `context.rs` scheduling change — **no new `WorkflowEvent` variant, no migration, no worker/replay/executor change.** Four new public `WorkflowContext` methods (a `max_in_flight: usize` window `W` argument added to each existing shape): `execute_activity_fan_out_windowed<I,O>(info, inputs, W)`, `execute_activity_fan_out_collect_windowed<I,O>(info, inputs, W)`, `execute_activity_fan_out_raw_windowed(activities, W)`, `execute_activity_fan_out_collect_raw_windowed(activities, W)` — the typed variants resolve queue/retry/timeout from `info` and serialize/deserialize exactly like the unbounded typed methods. Two new self-contained impls (`fan_out_raw_windowed_impl`, `fan_out_collect_raw_windowed_impl`); the four existing unbounded public methods and their impls are left byte-for-byte untouched.

**Scope: activity fan-out only.** Child-workflow bounded fan-out is an explicit deferred follow-up (mirroring how #601 followed #359) — the issue's ACs, problem statement, and success metric are all activity-focused (`harvest_task_queue` rows).

**Mechanics (two-phase: resume-then-dispatch).** Each windowed call runs the shared `check_cancellation()` → `next_fan_out_seq()` → `check_fan_out_count(seq, N)` prologue (the marker records **only `N`**, never `W`), including on the empty-input path so an empty windowed fan-out records `marker(count=0)` then returns `Ok(vec![])` — identical to the unbounded path. `W` is then clamped `max(1)` (never `chunks(0)`/`take(0)`). The call then runs in **two phases**. **Phase 1 (resume):** the number of this fan-out's slots already scheduled in recorded history — a contiguous input-order prefix `[0..s)` — is read via the new read-only, cursor-non-mutating `HistoryMatcher::count_pending_scheduled_activities(cap)` (called right after the count marker is consumed; `cap = N` both bounds the scan and stops a fully-completed fan-out's continuation from inflating the prefix with a later unrelated activity), and slots `[0..s)` are resumed as **one homogeneous `try_join_all` batch** — every prefix slot is in history, so each resolves to `Matched` (emits nothing) or `ActivityInProgress` (emits only `WaitForActivity`), **never `ScheduleActivity`**. **Phase 2 (dispatch):** once the prefix is fully resolved, the fresh remainder `[s..N)` is dispatched in `W`-sized waves, each `try_join_all`ed before the next is drawn. `check_cancellation()` runs before the resume batch and at the start of every fresh wave. Fail-fast: the first activity failure aborts and later waves are never dispatched (a deliberate backpressure semantic — a bounded fail-fast may process fewer items than the unbounded path would). Collect-all maps per-slot `ActivityFailed`/`Timeout` to `Ok(Err(..))` (a shared classification closure), so `try_join_all` never short-circuits and every wave dispatches / all `N` inputs are processed.

**Determinism / replay (the whole point).** Because activities dispatch in input order, `ActivityScheduled` events are recorded globally in input order `0..N`, so replay is **window-independent — including across a window CHANGE**: the same recorded history replays *and resumes* to identical results regardless of the `W` the replaying code is configured with, whether that `W` is larger or smaller than the one that produced the recorded partial state (`W` governs live dispatch only and is never in history). This is the load-bearing property the two-phase resume guarantees: phase 1 isolates the already-scheduled in-flight prefix into a homogeneous batch, so a mid-flight window **increase** can no longer regroup an in-flight slot together with never-scheduled fresh slots into a mixed `[WaitForActivity + ScheduleActivity]` suspension batch — a batch the worker's `handle_suspended_workflow` cannot persist, which terminally **FAILED** the run under the original single-loop implementation. On a window **decrease**, work already scheduled under the old larger window cannot be un-dispatched, so the resume phase waits on the whole already-scheduled prefix (up to the old width) before the smaller window governs further dispatch; peak in-flight can briefly exceed the newly-lowered `W` during the resume (inherent and correct — the window bounds *new* dispatch, never work already in flight, and there is no new stampede). Every fixed-window case emits **byte-identical** commands to the unbounded path (fresh live cycle → phase 1 empty, phase 2 dispatches `[0..W)`; full-history replay → phase 1 resumes all, phase 2 empty; `W >= N` → a single wave = marker + N `ScheduleActivity`). Recorded count stays `N`; a recorded-`N`-vs-current-code-`N` mismatch still surfaces `HarvestError::NonDeterministic`, exactly as unbounded. `W == 0`/`< 1` clamps up to 1 (documented, deterministic — never a panic, hang, or silent no-op). The shared `fan_out_seq` counter is reused, so a windowed then an unbounded fan-out get `fan_out:1`, `fan_out:2`. The two `try_join_all` known limitations of the unbounded fan-out carry over **per-wave** (narrowed, not widened). Trade-off: chunked waves, not a true sliding window — a wave does not refill until every activity in it completes (convoy effect on heterogeneous latencies), documented in CLAUDE.md.

**Post-review hardening (determinism-critical fix).** The original single-loop windowed impl regrouped an in-flight slot with never-scheduled fresh slots on a mid-flight window CHANGE, emitting a mixed `[WaitForActivity + ScheduleActivity]` suspension batch the worker cannot persist — terminally FAILING the run (falsifying the window-independence AC). Fixed by the two-phase resume-then-dispatch restructure above, backed by the new read-only `HistoryMatcher::count_pending_scheduled_activities(cap)` (cursor-non-mutating; changes no matching semantics or event contract). Every fixed-window case stays byte-identical, so all pre-existing windowed tests pass unchanged; the only new behavior is the now-correct window-change case in both directions.
