## Phase 3.52 — Bounded / windowed activity fan-out (issue #750)

Bounded-concurrency variants of the four activity fan-out shapes, so a wide fan-out applies natural backpressure to workers and downstreams instead of scheduling every input at once. This is a pure `context.rs` scheduling change — **no new `WorkflowEvent` variant, no migration, no worker/replay/executor change.** Four new public `WorkflowContext` methods (a `max_in_flight: usize` window `W` argument added to each existing shape): `execute_activity_fan_out_windowed<I,O>(info, inputs, W)`, `execute_activity_fan_out_collect_windowed<I,O>(info, inputs, W)`, `execute_activity_fan_out_raw_windowed(activities, W)`, `execute_activity_fan_out_collect_raw_windowed(activities, W)` — the typed variants resolve queue/retry/timeout from `info` and serialize/deserialize exactly like the unbounded typed methods. Two new self-contained impls (`fan_out_raw_windowed_impl`, `fan_out_collect_raw_windowed_impl`); the four existing unbounded public methods and their impls are left byte-for-byte untouched.

**Scope: activity fan-out only.** Child-workflow bounded fan-out is an explicit deferred follow-up (mirroring how #601 followed #359) — the issue's ACs, problem statement, and success metric are all activity-focused (`harvest_task_queue` rows).

**Mechanics (chunked-wave dispatch).** Each windowed call runs the shared `check_cancellation()` → `next_fan_out_seq()` → `check_fan_out_count(seq, N)` prologue (the marker records **only `N`**, never `W`), including on the empty-input path so an empty windowed fan-out records `marker(count=0)` then returns `Ok(vec![])` — identical to the unbounded path. `W` is then clamped `max(1)` (never `chunks(0)`/`take(0)`), and inputs are consumed in **input order** in successive waves of at most `W`, each wave `try_join_all`ed before the next is drawn. `check_cancellation()` runs **before each wave**. Fail-fast: the first activity failure aborts and later waves are never dispatched (a deliberate backpressure semantic — a bounded fail-fast may process fewer items than the unbounded path would). Collect-all maps per-slot `ActivityFailed`/`Timeout` to `Ok(Err(..))` (copying the unbounded classification arm), so `try_join_all` never short-circuits and every wave dispatches / all `N` inputs are processed.

**Determinism / replay (the whole point).** Because activities dispatch in input order, `ActivityScheduled` events are recorded globally in input order `0..N`, so replay is **window-independent**: the same recorded history replays to identical results regardless of the `W` the replaying code is configured with (`W` governs live dispatch only and is never in history). `W >= N` produces a single wave = byte-identical marker + N `ScheduleActivity` commands to the unbounded path. Recorded count stays `N`; a recorded-`N`-vs-current-code-`N` mismatch still surfaces `HarvestError::NonDeterministic`, exactly as unbounded. `W == 0`/`< 1` clamps up to 1 (documented, deterministic — never a panic, hang, or silent no-op). The shared `fan_out_seq` counter is reused, so a windowed then an unbounded fan-out get `fan_out:1`, `fan_out:2`. The two `try_join_all` known limitations of the unbounded fan-out carry over **per-wave** (narrowed, not widened). Trade-off: chunked waves, not a true sliding window — a wave does not refill until every activity in it completes (convoy effect on heterogeneous latencies), documented in CLAUDE.md.

Docs: CLAUDE.md "Fan-out / Parallel Activities" method table + a "Bounded / windowed fan-out" subsection. Example: `examples/fanout_batch.rs` gains a `windowed_batch` workflow (single-call fan-out over a collection larger than the window) with an embedded `#[cfg(all(test, feature = "testing"))]` `WorkflowTestEnv` test; a `cargo test --features testing --example fanout_batch` CI step is added.

Tests, TDD red→green→refactor: 11 pure unit tests in `tests/integration/fanout_tests.rs` (first-wave ≤ W, ≤ W-in-flight-every-wave via a hand-rolled multi-cycle drive over 10 inputs, input-order results, W>=N identical-history-to-unbounded, W=0-clamps-to-1, collect-all-processes-every-input-despite-failure, fail-fast-stops-later-waves, shared-seq-counter, empty-records-marker, count-mismatch → non-deterministic, cancellation → Cancelled); 3 `WorkflowReplayer` fixtures in `tests/integration/replayer_tests.rs` (ReplaySucceeded, window-independence across W=1/2/100/unbounded with byte-identical results, and ≥25 randomized-completion-order histories all replaying clean with input-order results — the falsifiable determinism bar, per the #476 precedent); a `WorkflowTestEnv` drive-to-completion test in `tests/integration/workflow_test_env_tests.rs`; and the DB e2e success-metric test `windowed_fan_out_peak_task_rows_bounded_by_window` in `tests/integration/integration_e2e.rs` (N=20, W=5: a concurrent DB poller confirms peak `RUNNING`/`PENDING` activity rows for the execution stays ≤ 5, results are byte-identical to an unbounded fan-out over the same inputs, and exactly 20 `ActivityScheduled` + one `fan_out` marker are recorded). All pure/testing tests and — via a local Postgres 16 (`HARVEST_TEST_DATABASE_URL`) — the DB e2e test were executed green.
