## Phase 4 — Scoped API tokens + rotation for the management API (issue #942)

Adds a first-class, least-privilege credential layer for the Harvest management API: create / list / revoke scoped, optionally-expiring, individually-revocable API tokens, with every mutating operation attributable to a named actor. Entirely a `autumn-harvest-plugin` auth layer plus **one additive config-table migration** — **no new `WorkflowEvent` variant, zero replay-determinism impact, no change to `harvest_events`** (AC9). The deterministic execution core is untouched.

### What shipped

- **Token table (`harvest_api_tokens`, migration `20260713000000`)** — a small, Postgres-only, shard-agnostic control table (`id`, `name`, `token_hash`, `scope`, `created_at`, `expires_at?`, `last_used_at?`, `revoked_at?`, `created_by`), mirrored into core `schema.rs`/`models.rs` exactly like `harvest_audit_log`. Verified on the **default (control) shard**; rows carry no `shard_id`.
- **Wire format & secret hygiene (AC2)** — a token secret is opaque `hvst_<base64url(32 random bytes)>`. Only `token_hash = hex(SHA256(secret))` is stored (UNIQUE-indexed); the plaintext is returned **exactly once** at creation and never persists. Verification hashes the presented secret and does one indexed `SELECT` — **no in-Rust hash comparison** (a 256-bit random hash is not an iterable timing oracle), so no constant-time-compare crate is added. `GET /admin/tokens` returns a **metadata-only** `TokenView` DTO that structurally cannot hold the hash/secret (the #695 redaction-view pattern, exhaustive-destructure guard); `MintResult`/`NewApiToken` redact the secret/hash in `Debug`. Uses `sha2`/`base64`/`rand` — all already workspace/core deps.
- **Scope from route classification (AC3/AC4)** — a token carries `read` or `mutate`, derived from the existing `audit::CLASSIFIED_ROUTES` (the #776 single source of truth — **no second route taxonomy**). The scope gate is `deny_readonly_mutation` over `classify_route`, which **fails closed**: an unclassified path resolves to `Mutating` and is denied to a `read` token. A `read` token gets **403 on 100% of `ALL_MUTATION_ROUTES`** and reaches 100% of read-only routes (the 100%/0% success-metric sweep).
- **Enforcement layer (`api_token::enforce_token_scope`)** — a `from_fn_with_state` layer installed on the nested `harvest_api_router` **only** under the new `HarvestPlugin::enable_api_tokens()` opt-in (default off → byte-identical, AC7). A bearer that does not start with `hvst_` (or an absent bearer) is passed through untouched — token auth **composes with**, never replaces, `api_with_auth` (AC7). A claimed `hvst_` bearer that cannot be verified (store unavailable) is rejected 503, never trusted unverified.
- **Rotation & expiry (AC5)** — optional `expires_at`; an expired or revoked token is rejected 401 on the **next request** because there is **no grant cache** (every request re-queries the table; bounded TTL = 0). Rotation is create-replacement → cut over → revoke old, over the existing routes.
- **Actor attribution (AC6)** — on a verified token the layer strips any inbound `x-harvest-actor` and injects `token:{id}`, so every audited mutation is attributed to the token (never the secret/hash) and a caller cannot spoof a different actor. The `token:` audit-actor namespace is **reserved**: on the pass-through path (no/invalid `hvst_` bearer, incl. OPTIONS) the layer also strips any inbound `x-harvest-actor` whose value starts with `token:`, so a caller admitted by some *other* means (a session admin, or any request under an embedder admin boundary) cannot forge a token-namespaced actor and impersonate a minted token. Non-`token:` actor values pass through untouched — legacy embedder-authed requests keep the documented `x-harvest-actor`/`anonymous` fallback. A verified `TokenPrincipal` extension lets `require_harvest_admin` admit a token-authenticated request in standalone-token mode.
- **Routes (AC1)** — `POST /admin/tokens` (create, 201, audited `token.create`), `GET /admin/tokens` (list, metadata-only, read/no-audit), `DELETE /admin/tokens/{id}` (revoke, audited `token.revoke`), all admin-gated and registered across every registry: `harvest_api_router`, `management_api_routes()`/`_request_fields()`/`_response_fields()`, `docs/api-contract.json`, and core `audit` (`CLASSIFIED_ROUTES`, `ALL_MUTATION_ROUTES`, `AUDITED_OPERATIONS`, `OP_TOKEN_CREATE`/`OP_TOKEN_REVOKE`/`TARGET_TOKEN`, `EXCLUDED_ROUTES` for the GET), with a dedicated `token_routes_are_classified_and_audited` pin.
- **MCP composition** — a token-aware `enforce_token_scope_mcp_mutation` layer (mirroring `enforce_read_only_mcp_mutation`) is provided in `api_token` to hard-deny a `read`-scoped token the mutating generated MCP tool routes. `enable_api_tokens()` installs the management-router `enforce_token_scope` layer; wiring the MCP-tool gate onto the app-level generated tool routes is a follow-up composition (the generated MCP routes live outside the nested management router).
- **CLI (AC8)** — `harvest token create|list|revoke` (plus a `rotate` client-side convenience that mints a replacement via the create route). The `--token` bearer was already sent; the new layer consumes it.
- **Single source of truth for hashing** — the pure token-secret helpers (`mint_secret`, `hash_secret`, `looks_like_harvest_token`, `TOKEN_PREFIX`) live in **core** (`autumn_harvest::api_token`, no `db` feature — they use only the non-optional `base64`/`sha2`/`rand` core deps). The plugin's mint route re-exports and calls them, and the offline `harvest token bootstrap` CLI calls the same functions, so the server mint path and the offline seed path can **never drift** on how a secret is generated or hashed. `sha2`/`base64`/`rand` were removed from the plugin's own `Cargo.toml` (they now live only in core).

### First-token bootstrap — standalone (tokens-only) mode

**The problem (Codex P1).** In pure standalone mode — where scoped API tokens are the *only* auth, with no embedder `api_with_auth` admin boundary — there is a chicken-and-egg gap: `POST /admin/tokens` is an admin-gated mutation, so minting a token requires an admin `TokenPrincipal`, which only a *previously-minted* token can provide. There is no way to mint the **first** token via the API. (Composed mode — tokens layered on the embedder's own admin auth — is unaffected: an existing admin caller mints the first token normally.)

**The fix — `harvest token bootstrap` (offline seed CLI).** A new local-only CLI subcommand generates a fresh token, prints the plaintext secret **exactly once** (same "shown once — store it now, it cannot be recovered" framing as the create route), and prints the exact `INSERT INTO harvest_api_tokens (...) VALUES (...)` statement for the operator to run against their database out-of-band. It opens **no** DB connection and issues **no** HTTP request (print-only). The printed SQL embeds **only the hash** (never the secret), with `id`/`created_at` taking the column defaults (`gen_random_uuid()`/`NOW()`) and every user-supplied string single-quote escaped (`'` → `''`) to neutralize injection through a crafted `--name`/`--created-by`. `--expires-at` is validated as RFC 3339 before any SQL is emitted. `--scope` defaults to **mutate** (a seed token must be able to mint the rest via the API). Usage: `harvest token bootstrap [--name <name>] [--scope mutate|read] [--expires-at <rfc3339>] [--created-by <who>]`. The operator (who already has DB access — the trust anchor) runs the printed SQL once to seed a single `mutate` token, then mints every further token through the API.

**Why option (a) — offline seed CLI — over the alternatives.** (a) keeps **zero new server-side auth surface** and anchors trust in the DB access the operator already has (the same trust anchor the migration itself requires), leaving composed mode byte-identical. A server-side bootstrap secret (b) would add a *static, long-lived credential* the operator must provision, guard, and eventually rotate — a standing liability for a one-time ceremony. A docs-only "insert a row by hand" note (c) would ship an advertised standalone mode that is effectively unusable out of the box and would force operators to hand-derive the `hex(SHA256(secret))` hash correctly (the exact drift hazard this feature removes). The CLI reuses the shared core hashing helper, so a bootstrap-seeded token authenticates **byte-for-byte identically** to a route-minted one — proven by a dedicated parity integration test.
- **`last_used_at` is debounced** — the best-effort last-used bump runs off the request critical path (fire-and-forget) **and** is skipped when the token's `last_used_at` is newer than 60 s, so a high-rate token client (the intended CI-fleet case) does not turn every read into a write or double the pool-checkout pressure.

### Operational caveats

- **Standalone-token mode should sit behind a rate-limiting proxy.** With `enable_api_tokens()` as the *only* auth (no reverse proxy / `api_with_auth`), any request whose `Authorization` begins with `hvst_` triggers one indexed token lookup before authentication — inherent to any bearer-token scheme. In that deployment shape, front the management API with a reverse proxy / load balancer that rate-limits (per-source) to bound unauthenticated lookup floods; the lookup is a single cheap indexed `SELECT` per probe and the connection is released promptly, but the mitigation is deployment-level.
- **Incident response for a compromised `mutate` token must audit `created_by` lineage.** A `mutate` token can reach `POST /admin/tokens`, so it can mint replacement tokens (the 2-level read/mutate model has no scope that grants mutation but withholds token management — fine-grained RBAC is explicitly out of scope). Revoking a leaked `mutate` token is therefore insufficient on its own: also audit the `created_by` provenance and revoke the entire lineage of tokens the compromised token minted.

### Tests

Pure unit tests (core `api_token.rs`): hash determinism/hex, secret mint prefix/entropy, minted-secret-round-trips-through-hash, `hvst_` discrimination. Pure unit tests (plugin `api_token.rs`): `MintResult`/`TokenView` redaction, the scope-from-class decision (deny-mutating / allow-readonly / fail-closed), expiry predicate (exercising the re-exported core helpers). Audit pin (`audit.rs`). No-DB HTTP layer tests (`security.rs`): pass-through of absent/non-`hvst_`/OPTIONS, 503-on-claimed-token-without-store, default-router-unchanged. DB integration (`token_auth_integration.rs`): create-returns-secret-once/stores-only-hash, list-metadata-only, verify-authenticates, unknown-401, revoke-denies-next-request, expired-401, the read-token 403/read sweep, mutate-token standalone admin access, `token:{id}` actor attribution (spoof-proof on the token path), a pass-through anti-spoof test proving a non-token caller cannot forge a `token:`-namespaced audit actor (AC6, reserved-namespace strip), create/revoke audited, plus the **bootstrap parity test** (`bootstrap_seeded_token_authenticates_identically_to_route_minted`): proves the mint route stores exactly `hash_secret(secret)` and that a row seeded offline with the shared core helpers authenticates + audits as `token:{id}` identically to a route-minted token. CLI unit tests (`token_bootstrap_tests` in `lib.rs`): builder emits a `hvst_` secret + hash-only INSERT SQL (secret never embedded), default scope `mutate`, invalid-scope rejected, flag-values flow through, RFC-3339 expiry validated/embedded, single-quote escaping. CLI mapping + contract-coverage tests.
