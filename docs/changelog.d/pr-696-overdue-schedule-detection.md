## Phase 3.51 — Server-side overdue-schedule detection (issue #696)

Harvest's schedule suite (jitter, overlap policy, calendars, backfill, catchup windows, `end_at`/`max_runs` bounds, HA claim exclusivity #350, failure-driven auto-pause #360) had no answer to the most common cron failure mode: a schedule that should be firing **silently stops** (scheduler loop not ticking, `next_run_at` wedged in the past, an HA claim that never released, all scheduler replicas down, or a config slip). The only prior signal was the starter alert `harvest_schedule_missed_runs`, which *inferred* a problem from the **absence** of `harvest.schedule.runs` (`increase(...runs...[1h]) == 0`) — brittle, forces operators to hand-encode each schedule's cadence into Prometheus, noisy for low-frequency schedules, and unable to name *which* schedule is wedged or *how late*. Since Harvest already stores every schedule's `next_run_at` + cadence in Postgres, it can compute "overdue" authoritatively server-side. **Read/observability slice over existing `harvest_schedules` columns: no new `WorkflowEvent` variant, no migration, schedules fire byte-identically.**

**Pure predicate (AC2, `scheduler.rs`).** New `pub fn schedule_overdue(schedule, next_run_at, now, jitter, tick_interval, is_paused, auto_paused_at, exhausted_at, at_capacity) -> OverdueVerdict` (unit-tested, no DB). A schedule is overdue iff it is *active* AND `now − next_run_at > grace`, where `grace = cadence_step + jitter + tick_interval` — so a healthy schedule caught mid-tick (tick term), deferred by jitter (jitter term), or one full cadence behind (cadence-step term) is never flagged. Cadence step is derived by the private `cadence_step` helper: the interval for `Interval`, and the gap to the next occurrence strictly after the missed slot for `Cron`/`CronInTimezone` (so DST-variable cron steps use the actual upcoming step), reusing the existing `next_run_after`/`interval_period` primitives directly. `pub const SCHEDULER_TICK_INTERVAL` re-exports the scheduler's own 1s tick so read/sampler callers pass the identical grace term. `OverdueVerdict { overdue: bool, overdue_by_secs: Option<i64> }` reports `now − next_run_at` (not `lag − grace`).

**AC3 exclusions + §2 false-positive guard.** Intentionally-not-firing states are never overdue: `is_paused`, `auto_paused_at` set (#360), `Schedule::Manual`, and `end_at`/`max_runs`-exhausted (`exhausted_at`, #478/#543). The predicate also takes an `at_capacity` (running ≥ `max_active_runs`) suppression input: the scheduler tick **deliberately** holds `next_run_at` at the past due slot while a schedule is at capacity (`OverlapPolicy::Skip` under catchup retains the overdue slot; the catchup dispatch loop defers remaining slots at the cap), so an at-capacity schedule is deliberately deferring, not wedged. Verified against the tick: in *every other* fire decision (Skip without catchup, all Buffer/Cancel/Terminate policies, the normal dispatch path) `next_run_at` advances forward; jitter deferral is bounded by the jitter grace term; end_at/max_runs deferral sets `exhausted_at`; and backfill (#337) creates independent executions and never touches the live schedule's `next_run_at`. So `running ≥ max_active_runs` is the *only* unbounded-lag-without-a-wedge case, and it is suppressed. The suppression is self-healing: once capacity opens, `at_capacity` drops and a genuine wedge is flagged on the next sample.

**Read surface (AC1/AC5).** `ScheduleEntry` gains `overdue: bool` + `overdue_by_secs: Option<i64>`, computed in `schedule_entry_from_row` via the pure predicate. Surfaces automatically on both `GET /admin/schedules` (list) and `GET /admin/schedules/{id}` — no new route, no audit/contract-registry churn — riding the existing #756 cross-shard fan-out and conditional-envelope contract. The read's `at_capacity` is a cross-shard-summed running count (`load_running_counts_across_shards`): a conservative over-suppression that guarantees no read false-positive; in single-shard deployments (the common case) it equals the shard-local count the gauge and tick use, so read and gauge agree exactly. Create/re-register responses pass `at_capacity = false` (a fresh `next_run_at` is never overdue); the PATCH response computes it (a non-cadence patch preserves a possibly-stale `next_run_at`).

**Metric (AC4).** New gauge `harvest.schedule.overdue{kind, name}` (`METRIC_SCHEDULE_OVERDUE`; `record_schedule_overdue(kind, name, overdue)` no-op default on `MetricsRecorder`, bridged in `metrics_rs_adapter` as `set(1.0/0.0)`). Labels are bounded `kind` (`workflow`/`dag`) + registered `name`; per ADR-0001 §7 the schedule/execution id is never a label. Same-named schedules aggregate (overdue if either).

**Emission (AC5/AC8).** `scheduler::sample_overdue_schedules(conn, now, metrics)` computes the verdict for every schedule on one shard (loading a shard-local RUNNING/PAUSED count that matches the tick's own `running` query, so `at_capacity` fires exactly when the tick would hold `next_run_at`) and emits the gauge, aggregating per `(kind, name)` within the shard so a healthy same-named schedule can't mask an overdue one. `scheduler::overdue_schedule_samples` is the returning core (used by tests). A new worker sampler `spawn_schedule_overdue_sampler` (modeled on the DLQ/queue samplers, gated on `is_enabled()`, iterating every shard pool) runs it on the `poll_interval` cadence — on the **worker**, not the scheduler tick, so a wedged tick cannot suppress its own health signal and a dead scheduler is still detected while any worker is alive (a *total* process outage falls back to the tertiary absence-of-runs expression + an `up`/scrape-health signal). The scheduler tick stays byte-identical (AC8). ALL schedules are sampled every pass (including paused/exhausted, which emit `0`) so the gauge stays fresh; deleted schedules go stale (standard gauge property).

**Alert + docs (AC7).** `harvest_schedule_missed_runs` in `docs/alerts/starter-pack-v0.1.0.json` now leads with the precise `max by (kind, name) (harvest_schedule_overdue) > 0`, keeps the skipped-counter expression, and retains the absence-of-runs expression only as a tertiary total-process-death signal (paired with `up`). `docs/runbooks/harvest-alerts.md#harvest_schedule_missed_runs`, `docs/telemetry.md` (ADR-0001 §7 catalogue + label table), a new dashboard panel in `docs/dashboards/starter-pack-v0.1.0.json`, and the `docs/api-contract.json` schedule route descriptions are updated.

**Tests (AC6).** Pure predicate table tests in `scheduler.rs` (overdue past grace across interval + hourly/5-min/daily/weekly cron with the correct cadence step; healthy within grace incl. the exact-at-grace boundary; jitter absorbed by grace; every AC3 exclusion + `at_capacity`; manual/none/null-next; and a 100-schedule healthy fleet under varied cadence/jitter/overlap reporting **zero** false positives). DB integration suite `tests/integration/scheduler_overdue_tests.rs` (testcontainers + `full_migrations_sql()` + a `RecordingMetrics` capturing `record_schedule_overdue`): wedged→overdue, healthy/paused/exhausted→not-overdue, at-capacity→not-overdue (§2 guard in the DB path), and the returning helper's `overdue_by_secs` lag. Plugin read-field test in `api_scheduler_integration.rs` asserting `overdue`/`overdue_by_secs` on `GET /admin/schedules` and `/{id}`. One new sorted line in `.github/ci/integration-suites.txt`.
