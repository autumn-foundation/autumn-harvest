# Phase 3.52 — Contain workflow and activity handler panics as clean failures (issue #782)

**Phase 3.52** (implemented): Handler-panic containment at the dispatch boundary — see issue #782. Before, a `panic!()` in a `#[workflow]` or `#[activity]` handler body (a stray `unwrap()` on `None`, an out-of-bounds index, an arithmetic overflow) was **not** contained: the handler runs inside a fire-and-forget spawned tokio task, so the panic unwound past the DB state-transition boundary without ever reaching the completion/failure code and left the `harvest_task_queue` row stuck `RUNNING`. Because the worker *process* survives (the panic is isolated to one async task), the poison-pill reclaimer (#367) — which only reclaims rows whose worker has **no live heartbeat** — never touched it, so an un-timed workflow task could sit `RUNNING` indefinitely and the eventual operator signal (a DLQ `PoisonPill` entry / consumed `crash_strikes`) told the wrong story for an ordinary code bug. Now the panic is caught at the dispatch boundary via `catch_unwind` and routed into the engine's existing clean failure paths, the same way returning `Err` does; the worker process stays up and the task leaves `RUNNING` within one poll interval.

- **Activity / local-activity panic** → converted to a retryable typed `ActivityFailed` (`error_type = "HandlerPanic"`, panic message captured as the failure detail) that follows the activity's **existing retry policy**, then fails terminally — no DLQ row, `crash_strikes` never consumed.
- **Workflow-body panic** → caught in the executor and surfaced through a new internal `WorkflowOutcome::Failed { handler_panic }` flag into a bounded, configurable panic-retry gate in `process_workflow_task` (an in-process per-execution strike map + capped-exponential backoff). After the budget is exhausted the execution fails terminally via the existing `WorkflowFailed` event (`error_type = "HandlerPanic"`). Budget: `WorkerConfig::workflow_panic_max_attempts` (default **3**; `0` = terminal on first panic). #523 workflow-level retry is explicitly skipped for a panic terminal so a panicking workflow is not double-retried.
- **Two panic-distinct counters** for alerting on handler-panic rate separately from process-crash quarantine: `harvest.activity.panic` and `harvest.workflow.panic`.
- **Determinism preserved**: a workflow-body panic is treated like any other workflow-task failure on replay; the replay/non-determinism contract is unchanged.
- **Two panic counters on the starter dashboard**: `harvest.activity.panic` (labels `activity`, `queue`) and `harvest.workflow.panic` (labels `workflow`, `queue`) each get a panel under the "Handler panics" row of `docs/dashboards/starter-pack-v0.1.0.json`, are catalogued in `docs/telemetry.md` and ADR-0001 §7, and are enforced by the anti-drift `dashboard_pack_docs.rs` coverage gate. `execution.id` stays span-only per ADR-0001 §7.

Documented caveats surfaced by review:

- **Inline-append-before-terminal limitation is inherited from the ND-block work (#603), not introduced here.** A workflow-body panic re-dispatches under the panic-retry budget, so a hotfix that changes replay-relevant history *structure* **before** an already-committed inline event (a local-activity result, an external-signal delivery) may re-diverge that in-flight run into a non-determinism *block* (#603) rather than data corruption — the same boundary the ND-block feature already documents. The common case — fixing the panicking line itself without reordering the commands recorded before it — replays cleanly and simply resumes.
- **Containment requires `panic = "unwind"`.** The guarantee rests on `catch_unwind` at the dispatch boundary. A downstream binary compiled with `[profile.*] panic = "abort"` turns a handler panic into an immediate process abort, so the panic is **not** contained — the worker process dies and the stuck-`RUNNING` row is instead recovered by the poison-pill reclaimer (#367) via the missing-heartbeat path. Keep the default `unwind` strategy for the workflow/activity worker binary to retain clean panic containment.
- **A repeatedly-panicking activity trips its circuit breaker (#369) exactly like a repeated `Err(String)`, by design.** A contained activity panic is surfaced as an ordinary retryable typed failure, so it counts toward a per-activity `CircuitBreakerPolicy`'s rolling failure window the same way any other retryable failure does; a burst of panics can open the breaker and fast-fail subsequent dispatches. This is intended — the breaker treats "the handler keeps failing" uniformly, whether the failure is a panic or a returned error.

**Post-review hardening (Codex bot, PR #1012): contain panics during future *construction*, not just poll.** The initial `catch_unwind` boundaries wrapped only the *future* returned by a handler, but a handler `fn` is *called* (constructed) first — so synchronous work a hand-written `WorkflowInfo`/`ActivityInfo` handler does before returning its `Box::pin(...)` future (a stray `unwrap()`, `panic!()`) still unwound the spawned worker task uncaught, bypassing the `HandlerPanic` conversion, the panic metric, and leaving the task on the old `RUNNING`/poison-pill path. (Macro-generated `#[workflow]`/`#[activity]` handlers can't hit this — the whole body is inside the returned async block — but the public `handler` fields and `WorkflowReplayer::register_fn` are a supported hand-written surface.) Closed uniformly by wrapping the synchronous handler *call* itself in `catch_unwind` (new `pub(crate) crate::error::catch_construct`) at every invocation site — activity (`worker.rs`), local activity (`worker.rs`), the shared workflow drive/strict/canary cycle (`executor::run_workflow_handler_cycle`), and both query-replay drives (`executor::drive_query_replay`, `handle::execute_query_in_process`). A construction panic maps to the same contained path as a poll panic: the same retryable typed `HandlerPanic` activity envelope (metric emitted once per panicking attempt, unchanged), the same `WorkflowOutcome::Failed { handler_panic: true }`, and the same `QueryReplayOutcome::Panicked` / `QueryHandlerPanicked` (503). `AssertUnwindSafe` is sound — on a construction panic the future is never produced and the borrowed context is dropped without reuse. Tests: `catch_construct` unit tests (`error.rs`), a construction-panic workflow unit test (`executor.rs`), a construction-panic query-replay test (`query_terminal_tests.rs`), an activity construction-panic envelope test (`worker.rs`), and an end-to-end DB test `workflow_construction_phase_panic_is_contained_as_handler_panic_terminal` (`panic_containment_tests.rs`).

**No new `WorkflowEvent` variant and no migration** — contained panics reuse the existing `ActivityFailed` / `WorkflowFailed` events, preserving the append-only invariant. Files: `builder.rs`, `executor.rs`, `failure.rs`, `metrics_rs_adapter.rs`, `queue.rs`, `telemetry.rs`, `testing.rs`, `worker.rs`, plus the new `tests/integration/panic_containment_tests.rs` (and a one-line `workflow_panic_max_attempts` field added to the `WorkerRuntimeConfig` literals across ~14 existing integration-test files). Tests: 4 integration tests in `panic_containment_tests.rs` (`activity_handler_panic_is_contained_and_retried_then_terminal`, `local_activity_handler_panic_is_contained_and_retried_then_terminal`, `workflow_handler_panic_is_re_dispatched_then_terminal_within_budget`, `workflow_panic_max_attempts_zero_is_terminal_on_first_panic`) assert the worker process stays up, the task leaves `RUNNING` within a poll interval, the activity retries per policy, the workflow fails terminally after the bounded budget, and no spurious crash-strike / poison-pill entry is created — run against a real local Postgres 16 (run twice); `cargo fmt --check`, `cargo clippy -p autumn-harvest --all-features --tests -- -D warnings`, and the 1704 library unit tests are green locally. Out of scope (per issue): unbounded retry-the-workflow-task-forever mode, any change to poison-pill process-crash semantics (#367), hung/infinite-loop detection (#494/#703), operator force-fail (#765).
