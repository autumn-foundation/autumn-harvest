# Stage 2 gate — cold decision rate and history load (issue #2257)

> **Status:** measurement record. It gives the bench half of the gate for
> the owner-local disk cache (#2258). The fleet half needs a production
> fleet for a week. This record gives the instruments and the queries for
> it. **Verdict: undecided.**

## Question

Stage 2 of epic #2247 is a disk cache next to each decision owner. It
saves the history read of a cold decision. It also lets the cache hold
more runs than RAM allows. The typed-state-snapshot spike set the
thresholds that would justify it
([`typed-state-snapshots.md`](typed-state-snapshots.md), section 5).
Either one trips the gate:

- `harvest.workflow.resident{outcome="cold"}` is above 20% of decisions on
  a fleet for a week.
- The p99 time of a cold decision is above 50 ms.

Each rule is a strict `>`.

## What this change adds

- **`harvest.workflow.resident.duration{workflow, queue, outcome}`.** A
  histogram in seconds. The worker records one sample with each
  `harvest.workflow.resident` count. The clock starts before the history
  load and stops at the end of the first drive. Before this change no
  metric gave a cold p99. `harvest.workflow.duration` has no `outcome`
  label, and it starts after the load.
- **A dashboard panel.** "Stage 2 gate: cold share and cold p99" in the
  starter pack, row "Cache, retention & shards".
- **`examples/history-load-gate`.** It times one history load from
  Postgres and from a local SQLite file, and the warm-up after an owner
  restart. It drives the real `WorkflowCache` to model the cold share of
  the cache cap. It applies the thresholds to fleet values. See its
  [README](../../examples/history-load-gate/README.md).

## Fleet method

The fleet runs a release with this change, with owner mode on (issue
#2252, `decision_owner::enable_owner_mode`) and resident workflows on, the
default. The exporter needs a histogram bucket bound at 0.05 s. A week of
a representative load gives the two values:

```promql
# Cold share over the week.
sum(increase(harvest_workflow_resident_total{outcome="cold"}[7d]))
  / sum(increase(harvest_workflow_resident_total[7d]))

# Cold p99 over the week, in seconds.
histogram_quantile(0.99,
  sum by (le) (increase(harvest_workflow_resident_duration_bucket{outcome="cold"}[7d])))
```

Record the live runs per owner too. The cache model below shows that this
count sets a floor for the cold share:

```sql
SELECT count(*) FILTER (WHERE state = 'RUNNING')::float
       / NULLIF((SELECT count(DISTINCT holder) FROM harvest_decision_owner
                 WHERE lease_until > now()), 0) AS live_runs_per_owner
FROM harvest_workflow_executions;
```

Then apply the gate:

```sh
FLEET_COLD_SHARE=0.07 FLEET_COLD_P99_MS=41 SIZES= RUNS= MODEL_RUNS= \
DATABASE_URL=postgres://... cargo run -p history-load-gate --release
```

One trip gives `go`. Both values with no trip give `no-go`.

## Bench method

```sh
DATABASE_URL=postgres://postgres:postgres@localhost:5432/history_load_gate \
  cargo run -p history-load-gate --release
```

- **One history.** The binary starts a run through
  `start_or_load_workflow_execution` and appends the rest with
  `store::append_events`. Event 0 is `WorkflowStarted`. The rest alternate
  `ActivityScheduled` and `ActivityCompleted`. Each payload holds 256 bytes
  of text, unless the run says otherwise. The binary times
  `store::load_history_inflated`, the worker load path, with the identity
  codec and no offload. The cold path of the worker reads the full history
  twice, so the binary also times two reads in a row. The SQLite side
  stores the same events in a file with the schema of
  `autumn-harvest-sqlite`. It reads them through
  `SqliteRuntime::load_history`. One untimed load warms each store. Then
  30 timed loads give p50 and p99.
- **Warm-up.** The binary copies one run of 21 events into 1k, 10k and
  100k runs, in SQL. It loads every run once to warm the buffers, then
  times one more pass. Postgres runs on 1 connection and on 8, the
  decision cap of one worker. SQLite runs on 1 connection, because its
  runtime holds the single-writer lock.
- **Cache model.** The binary drives the real `WorkflowCache` with 1,000
  entries as the worker does: a decision takes the entry of its run, and
  the commit puts it back. It counts 200,000 decisions after one warm-up
  pass.

## Reading

- **The history read dominates a cold decision.** The spike measured
  replay only: `decision_cost` takes 1.25 ms for 10,000 events. One
  Postgres read of the same history takes 55 to 60 ms. The cold path reads
  it twice, 137 to 155 ms at p50. Event count drives the cost far more
  than payload size. At 10k and 50k events, 32-byte payloads cut the cold
  path by about a quarter.
- **The p99 threshold trips for long histories.** The cold path passes
  50 ms at p99 between 2,000 and 5,000 events, near 3,500. So the fleet
  cold p99 trips when 1% of cold decisions load a history of about 3,500
  events or more.
  At the 50,000-event cap, a cold decision reads for about 0.9 s.
- **The cold share depends on live runs per owner.** Under owner mode, an
  owner keeps its runs for good. Once its live runs pass the 1,000-entry
  cap, LRU eviction alone gives cold decisions. A uniform load passes 20%
  at 1,250 live runs per owner. A round robin, such as many runs on one
  periodic timer, thrashes the cache at 1,001: every decision is cold.
- **A local SQLite read is 1.9 to 3.6 times faster than one Postgres
  read.** Against the cold path of today, it is 4.5 to 9 times faster.
- **Warm-up after a restart.** 100k live runs take 7.6 s on 8 Postgres
  connections and 4.7 s from SQLite on one. Only 1,000 of them then stay
  warm in RAM. A disk cache keeps the rest warm across the restart.

### Finding: the cold path reads the history twice

`load_workflow_replay_state` in `worker.rs` reads the full history with
`load_history_inflated`. It uses only `next_event_id` from it. After the
wake ingest it reads the full history again, with the byte sum. Each read
decodes every event. A single read after the ingest would cut the cold
path by about half, with no new store. That change touches the decision
path, so it is out of scope here. It needs its own issue.

## Provisional reading

This is not the verdict. The verdict needs the fleet week.

- Both thresholds are reachable on plausible fleets: one with long
  histories, or one with more than about 1,250 live runs per owner.
- Two cheaper changes come before a disk cache. Remove the first read of
  the cold path. Size `WorkflowCache` by memory as well as by entries.
  Then read the fleet week.
- A disk cache still wins when the live runs per owner exceed what RAM can
  hold, or when restarts are frequent. Each cold read is 1.9 to 3.6 times
  faster from a local file.

## Limits

- One box. Postgres runs on the same host, so a read pays no network
  round trip. A fleet adds one round trip per read, and contention.
- Both stores run warm. A restarted owner keeps the page cache of its
  host and of Postgres, so this matches a process restart, not a host
  replacement.
- The events are synthetic: activity pairs with a fixed payload. No
  codec, no offload and no partitioned layout.
- The bench times the load, not the replay. `decision_cost` in
  `benches/replay_bench.rs` gives the replay.
- The cache model has no restart, no change of owner and no time. Real
  loads are neither uniform nor round robin. It gives a floor, not the
  fleet value.
- SQLite runs on one connection. A disk cache could read on more.
