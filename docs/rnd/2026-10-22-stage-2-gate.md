# Stage 2 gate — cold decision rate and history load (issue #2257)

> **Status:** measurement record. It gives the bench half of the gate for
> the owner-local disk cache (#2258). The fleet half needs a production
> fleet for a week. This record gives the instruments and the queries for
> it. **Verdict: undecided.** See [Acceptance status](#acceptance-status).

## Question

Stage 2 of epic #2247 is a disk cache next to each decision owner. It
saves the history read of a cold decision. It also lets the cache hold
more runs than RAM allows. The typed-state-snapshot spike set the
thresholds that would justify it
([`typed-state-snapshots.md`](typed-state-snapshots.md), section 5).
Either one trips the gate:

- `harvest.workflow.resident{outcome="cold"}` is above 20% of decisions on
  a fleet for a week.
- The p99 time of a cold decision is above 50 ms.

Each rule is a strict `>`. The spike wrote the second rule for the replay
time. No metric gave that time, so this gate applies 50 ms to the new
histogram below. Its window is broader than the replay: it also holds the
history load, the wake ingest and the live part of the first drive. A
disk cache saves only the load. Read the `hit` p99 beside the cold p99 to
see the part that stays.

## What this change adds

- **`harvest.workflow.resident.duration{workflow, queue, outcome}`.** A
  histogram in seconds. The worker records one sample with each
  `harvest.workflow.resident` count. The clock starts before the history
  load and stops at the end of the first drive, before any later write.
  `harvest.workflow.duration` has no `outcome` label, and it starts after
  the load.
- **A dashboard panel.** "Stage 2 gate: cold share and cold p99" in the
  starter pack, row "Cache, retention & shards".
- **`examples/history-load-gate`.** It times one history load from
  Postgres and from a local SQLite file, and the warm-up after an owner
  restart. It drives the real `WorkflowCache` to model the cold share of
  the cache cap. It applies the thresholds to fleet values. See its
  [README](../../examples/history-load-gate/README.md).

## Fleet method

The fleet runs a release with this change, with owner mode on (issue
#2252, `decision_owner::enable_owner_mode`) and resident workflows on, the
default. The exporter needs a histogram bucket bound at 0.05 s. A week of
a representative load gives the two values:

```promql
# Cold share over the week.
sum(increase(harvest_workflow_resident_total{outcome="cold"}[7d]))
  / sum(increase(harvest_workflow_resident_total[7d]))

# Cold p99 over the week, in seconds.
histogram_quantile(0.99,
  sum by (le) (increase(harvest_workflow_resident_duration_bucket{outcome="cold"}[7d])))
```

Record the live runs per owner too. The cache model below shows how this
count drives the cold share. Run it on each shard. It gives a mean per
owner:

```sql
SELECT (SELECT count(*) FROM harvest_workflow_executions
        WHERE state = 'RUNNING')::float
       / NULLIF((SELECT count(DISTINCT holder) FROM harvest_decision_owner
                 WHERE lease_until > now()), 0) AS live_runs_per_owner;
```

Then apply the gate. With `SIZES` and `RUNS` empty, the binary opens no
database:

```sh
FLEET_COLD_SHARE=<share, 0 to 1> FLEET_COLD_P99_MS=<ms> SIZES= RUNS= MODEL_RUNS= \
  cargo run -p history-load-gate --release
```

One trip gives `go`. Both values with no trip give `no-go`. Anything else
is `undecided`.

## Bench method

```sh
DATABASE_URL=postgres://postgres:postgres@localhost:5432/history_load_gate \
  SIZES=1000,2000,5000,10000,50000 cargo run -p history-load-gate --release
```

- **One history.** The binary starts a run through
  `start_or_load_workflow_execution` and appends the rest with
  `store::append_events`. Event 0 is `WorkflowStarted`. The rest alternate
  `ActivityScheduled` and `ActivityCompleted`. Each payload holds 256 bytes
  of text, unless the run says otherwise. The binary times
  `store::load_history_inflated`, the worker load path, with the identity
  codec and no offload. The SQLite side stores the same events in a file
  with the schema of `autumn-harvest-sqlite`. It reads them with the query
  of that backend. Both sides decode each row through
  `PayloadCodecs::decode_event`, as a disk cache must.
- **Cold path.** The worker reads the full history twice, so the binary
  also times two reads in a row. The worker's second read also sums the
  stored bytes. The bench read skips that sum, so the bench cold path is a
  little short.
- **Samples.** One untimed load warms each store. Then 100 timed loads
  give the nearest-rank p50 and p99.
- **Warm-up.** The binary copies one run of 21 events into 1k, 10k and
  100k runs. Both stores keep the rows of one run together. It loads every
  run once to warm the buffers, then times one more pass. Each store runs
  on 1 connection and on 8. 8 is the default of `CONCURRENCY`, not a
  worker setting.
- **Cache model.** The binary drives the real `WorkflowCache` with 1,000
  entries. It copies the worker: a decision takes the entry of its run,
  and the commit puts it back. It counts 200,000 decisions after one
  warm-up pass.

## Reading

- **The history read dominates a cold decision.** The spike measured
  replay only: `decision_cost` takes 1.25 ms for 10,000 events. One
  Postgres read of the same history takes 44 to 64 ms at p50. The cold
  path costs 2.1 to 2.4 times one read, 100 to 138 ms at p50. Event count
  drives the cost more than payload size. At 10k and 50k events, 32-byte
  payloads cut the cold path by 18 to 27%. At 1k events they change
  nothing.
- **The p99 threshold trips for long histories.** On this box, with no
  network round trip, the cold path passes 50 ms between 2,000 and 5,000
  events: near 3,400 events at p99, and near 4,800 at p50. So the fleet
  cold p99 trips when about 1% of cold decisions load a history in that
  range or longer. At the 50,000-event cap, a cold decision reads for 0.6
  to 0.9 s.
- **The cold share depends on live runs per owner.** Under owner mode, an
  owner keeps its runs until a restart or a change of owner. Once its live
  runs pass the 1,000-entry cap, LRU eviction gives cold decisions. A
  uniform load reaches 20% at 1,250 live runs per owner, so it trips just
  above that. A round robin, such as many runs on one periodic timer,
  thrashes the cache at 1,001: every decision is cold. A skewed load
  misses less than a uniform one.
- **A local SQLite read is 2.2 to 3.3 times faster than one Postgres
  read**, with the same decode on both sides.
- **Warm-up after a restart.** 100k live runs take 6.1 to 6.6 s on 8
  Postgres connections, and 2.1 to 2.2 s on 8 SQLite connections. Only
  1,000 of them then stay warm in RAM. A disk cache serves the rest from
  local disk after the restart.

### Finding: the cold path reads the history twice

`load_workflow_replay_state` in `worker.rs` reads the full history with
`load_history_inflated`. On success it uses only `next_event_id`. On a
decode error it fails the run before the wake ingest writes. After the
ingest it reads the full history again, with the byte sum. Each read
decodes every event.

One read after the ingest would cut the cold path by about half, with no
new store. It must keep the early failure on a bad row. That change
touches the decision path, so it needs its own issue.

Several commit paths also read the full history again, such as the park
of an activity wait or a signal wait. Those reads fall outside the
duration window. They run on warm decisions too, and a disk cache would
not remove them.

## Provisional reading

This is not the verdict. The verdict needs the fleet week.

- Both thresholds are reachable on plausible fleets: one with long
  histories, or one with more than about 1,250 live runs per owner under
  a uniform load.
- Two cheaper changes come before a disk cache. Remove the first read of
  the cold path. Size `WorkflowCache` by memory as well as by entries.
  Then read the fleet week.
- A disk cache still wins when the live runs per owner exceed what RAM can
  hold, or when restarts are frequent. Each cold read is 2.2 to 3.3 times
  faster from a local file.

## Limits

- One box. Postgres runs on the same host, so a read pays no network
  round trip. A fleet adds one round trip per read, and contention.
- Both stores run warm. A restarted owner keeps the page cache of its
  host and of Postgres, so this matches a process restart, not a host
  replacement.
- The events are synthetic: activity pairs with a fixed payload. No
  codec key, no offload and no partitioned layout.
- Both stores keep the rows of one run together. A busy fleet scatters
  them in Postgres, which costs more page reads.
- The bench times the load, not the replay. `decision_cost` in
  `benches/replay_bench.rs` gives the replay.
- The cache model has no restart, no change of owner and no time. Real
  loads are neither uniform nor round robin.
- A run killed by a signal leaves its seeded rows. Drop the database
  then.
